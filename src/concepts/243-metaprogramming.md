## Definition

Metaprogramming is writing code that DEFINES or MODIFIES code at
RUNTIME — Ruby's dynamic method definition (`define_method`), the
ability to intercept calls to methods that don't exist
(`method_missing`), and runtime introspection let a program construct or
reshape its own behavior programmatically, rather than everything being
fixed at the time the source is written.

## Problem

Writing out MANY near-identical methods by hand (a getter/setter for
every field, a wrapper method for every API endpoint) duplicates the
same PATTERN repeatedly — metaprogramming lets that pattern be expressed
ONCE, generatively, producing all the actual methods programmatically at
runtime instead of by hand, one at a time.

## Execution

Looping over a list of attribute names and calling `define_method`
inside that loop GENERATES getter and setter methods for each one,
without writing separate method definitions by hand for each
↓
Calling one of the dynamically-defined methods works exactly like a
normal, hand-written one
↓
Overriding `method_missing` lets an object respond to method calls that
DON'T actually exist as real methods, deciding dynamically what to do
(commonly used to build flexible, dynamic proxy-like objects)
↓
`respond_to_missing?` should be overridden ALONGSIDE `method_missing`, to
keep introspection methods like `.respond_to?` accurately reporting
which "phantom" methods the object will actually handle

## Computer Science

Metaprogramming exploits Ruby's OPEN, dynamic object model — classes
remain modifiable after their initial definition (you can add methods to
`String` itself, at runtime, from anywhere), and this same "code that
manipulates code" capability underlies how much of Ruby's own standard
library (like `attr_accessor` itself) is implemented.

Tags: Open classes, Dynamic method definition, Runtime code generation

## Software Engineering

Metaprogramming is powerful but trades away some static readability and
tooling support (an IDE can't always "see" a dynamically-defined method
the way it can a hand-written one) — it's best reserved for genuine
repeated-pattern generation (like `attr_accessor`-style boilerplate
elimination), not used pervasively where explicit, hand-written code
would be just as clear.

Tags: Readability tradeoffs, Tooling support limitations, Judicious use

## Common Mistakes

- Overriding `method_missing` without ALSO overriding `respond_to_missing?` — this leaves `.respond_to?` reporting INCORRECT information about which methods the object will actually handle, breaking code that relies on introspection to check before calling.
- Using metaprogramming to generate methods dynamically when a small, fixed, explicitly-written set of methods would be just as easy to write and far easier for other developers (and tooling) to follow.

## ruby

```ruby
class Product
  ['name', 'price'].each do |attr|
    define_method(attr) { instance_variable_get("@#{attr}") }
    define_method("#{attr}=") { |val| instance_variable_set("@#{attr}", val) }
  end
end

p = Product.new
p.name = "Widget"
p.price = 9.99
puts p.name
puts p.price

class Ghost
  def method_missing(name, *args)
    "you called #{name} with #{args.inspect}, but I have no such method"
  end
end

g = Ghost.new
puts g.anything_at_all(1, 2, 3)
```
Walkthrough: `define_method` generates `name`, `name=`, `price`, and
`price=` from a single loop over the attribute list, rather than writing
four separate method definitions by hand — calling `p.name = "Widget"`
and `p.name` afterward proves these dynamically-generated methods behave
exactly like normal ones. `Ghost#method_missing` intercepts a call to a
method that was never actually defined at all, letting the object
respond dynamically instead of raising a `NoMethodError`.
