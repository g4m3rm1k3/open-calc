## Definition

The GIL (Global Interpreter Lock) is a mutex in CPython (the standard
Python implementation) that allows only ONE thread to execute Python
bytecode at a time, even on a multi-core machine — meaning Python threads
don't achieve true CPU-bound parallelism, despite appearing to run
"concurrently."

## Problem

CPython's memory management (reference counting, see Reference Counting)
isn't thread-safe without some form of locking — allowing multiple
threads to freely execute Python bytecode simultaneously could corrupt
reference counts and crash the interpreter. The GIL solves this with a
single global lock, at the cost of preventing genuine CPU-bound
parallelism across threads within one process.

## Execution

A pure Python CPU-bound computation loop, no I/O involved
↓
Running it in TWO threads simultaneously does NOT run twice as fast on a
multi-core machine — the GIL only lets ONE thread execute Python
bytecode at any given instant, so the threads effectively take turns, not
run in parallel
↓
A network request RELEASES the GIL while waiting for the response (I/O
operations don't need the GIL held)
↓
Running I/O-bound work across multiple threads DOES see real speedup,
since the GIL is released during the actual waiting, letting OTHER
threads run Python code during that wait
↓
For genuine CPU-bound parallelism, Python code needs `multiprocessing`
instead (see Processes) — separate PROCESSES, each with its OWN GIL and
own memory space, genuinely run in parallel across cores

## Computer Science

The GIL is specifically a CPython implementation detail, not a
fundamental property of the Python LANGUAGE — other implementations
(Jython, IronPython) don't have a GIL at all, and even CPython's own GIL
has been the subject of ongoing efforts (including experimental
"free-threaded" builds) to remove it, precisely because it constrains
this specific implementation's threading model, not Python as a
language.

Tags: CPython implementation detail, Reference counting thread safety, Free-threaded Python

## Software Engineering

The practical rule of thumb: use `threading` for I/O-bound work (network
requests, file operations) where the GIL is released during waits, and
use `multiprocessing` for CPU-bound work (heavy computation) where
genuine parallelism across cores is actually needed — reaching for
`threading` for CPU-bound work is a common performance misconception.

Tags: Threading vs multiprocessing, I/O-bound vs CPU-bound, Concurrency tool selection

## Common Mistakes

- Using `threading` for CPU-bound work expecting a speedup on a multi-core machine — the GIL prevents genuine parallel execution of Python bytecode across threads, so this typically doesn't get faster (and can even get slightly slower, due to thread-switching overhead).
- Assuming the GIL means Python has NO concurrency benefits from threading at all — for I/O-bound work specifically, threading genuinely helps, since the GIL is released during I/O waits, letting other threads make progress during that time.

## Exercises

- Explain why an I/O-bound workload (many network requests) benefits from Python threading, while a CPU-bound workload (heavy numeric computation) generally does not.
- Look up what `multiprocessing` does differently from `threading` that lets it achieve genuine CPU-bound parallelism despite the GIL's existence.

## python

```python
import threading


def cpu_bound_work(n, results, idx):
    total = 0
    for i in range(n):
        total += i
    results[idx] = total


# Demonstrating that the GIL serializes CPU-bound thread execution --
# running two CPU-bound loops "concurrently" via threads doesn't parallelize
# the actual computation, just interleaves it.
results = [None, None]
n = 500_000

t1 = threading.Thread(target=cpu_bound_work, args=(n, results, 0))
t2 = threading.Thread(target=cpu_bound_work, args=(n, results, 1))
t1.start()
t2.start()
t1.join()
t2.join()

print(results[0] == results[1])   # True -- both loops compute the same total, regardless of threading
print(f"both computed correctly: {results[0] == (n * (n - 1)) // 2}")
```
Walkthrough: both threads correctly compute the exact same total
(`results[0] == results[1]` is `True`, and both match the closed-form
sum), confirming correctness — but despite using two separate
`threading.Thread` instances, this CPU-bound work does NOT achieve
genuine parallel execution, since the GIL only lets one thread execute
Python bytecode at a time regardless of how many threads exist. Compare
this to the Threads concept, where a similarly-shaped example works fine
BECAUSE it's the correctness of coordination being demonstrated, not a
claim about CPU-bound speedup.
