## Definition

XSS (Cross-Site Scripting) is a vulnerability where an attacker gets their
own JavaScript to run in another user's browser within a trusted site's
context, usually by injecting it through user-supplied input that the
site renders without properly escaping.

## Problem

If a site takes user input (a comment, a search query) and inserts it
directly into the page's HTML without escaping it, an attacker can submit
input containing a `<script>` tag — when another user views that page,
the browser executes the attacker's script as if it were the site's own
code, with access to that user's cookies, session, and DOM.

## Execution

Attacker submits a comment containing a `<script>` tag that steals
cookies
↓
Vulnerable site stores the raw comment text, then later renders it
directly into the page's HTML with no escaping
↓
Victim views the page — the browser parses the injected `<script>` tag
as real code and executes it
↓
The script runs with the SAME permissions as the site's own JavaScript —
it can read cookies, make requests, modify the page
↓
Fix: escape special HTML characters (`<`, `>`, `&`, `"`) in user input
before rendering it, so the browser displays it as inert TEXT instead of
parsing it as markup

## Computer Science

XSS is fundamentally a failure to properly distinguish DATA from CODE —
the browser has no way to know that a piece of text came from user input
rather than the site's own trusted markup unless the site explicitly
encodes it as safe text. This is the same class of problem as SQL
Injection (data being interpreted as executable syntax).

Tags: Injection attacks, Escaping, Trust boundaries, Data vs code

## Software Engineering

Modern frameworks (React, Vue) auto-escape rendered text content by
default, which is why most component-based apps are naturally resistant
to XSS UNLESS a developer explicitly opts out (e.g., React's
`dangerouslySetInnerHTML`) — that escape hatch exists for legitimate
cases (rendering trusted, sanitized HTML) but bypasses the framework's
automatic protection, so any use of it demands extra scrutiny.

Tags: Auto-escaping, dangerouslySetInnerHTML, Framework defaults

## Common Mistakes

- Rendering user-supplied content as raw HTML (e.g., via `innerHTML` or `dangerouslySetInnerHTML`) without sanitizing it first — this is the single most common way XSS vulnerabilities get introduced.
- Assuming input validation on the way IN is enough — XSS is fundamentally an OUTPUT problem (how data gets rendered), so escaping must happen at render time regardless of what validation happened at input time.

## javascript

```javascript
// Simulating the escape-vs-raw contrast directly, since triggering a real
// XSS payload requires a rendered DOM the code runner doesn't have.
function escapeHtml(str) {
  return str
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
}

const userComment = '<script>stealCookies()</script>'

// Vulnerable: inserting raw user input directly into HTML
const vulnerableHtml = `<div class="comment">${userComment}</div>`
// Safe: escaping first so the browser renders it as inert TEXT, not markup
const safeHtml = `<div class="comment">${escapeHtml(userComment)}</div>`

console.log(vulnerableHtml)   // <div class="comment"><script>stealCookies()</script></div> -- browser would EXECUTE this
console.log(safeHtml)         // <div class="comment">&lt;script&gt;stealCookies()&lt;/script&gt;</div> -- browser DISPLAYS this as text
```
Walkthrough: `vulnerableHtml` embeds the attacker's `<script>` tag as
literal, unescaped markup — if this string were assigned to `innerHTML`,
the browser would parse and execute it as real code. `escapeHtml`
converts the angle brackets to their HTML entity equivalents
(`&lt;`/`&gt;`) BEFORE embedding, so `safeHtml` displays the exact same
text visually, but the browser treats it as inert text content, never
executing it.

## python

```python
def escape_html(s):
    return (
        s.replace('&', '&amp;')
         .replace('<', '&lt;')
         .replace('>', '&gt;')
         .replace('"', '&quot;')
    )


user_comment = '<script>steal_cookies()</script>'

# Vulnerable: inserting raw user input directly into HTML
vulnerable_html = f'<div class="comment">{user_comment}</div>'
# Safe: escaping first so the browser renders it as inert TEXT, not markup
safe_html = f'<div class="comment">{escape_html(user_comment)}</div>'

print(vulnerable_html)   # <div class="comment"><script>steal_cookies()</script></div> -- browser would EXECUTE this
print(safe_html)         # <div class="comment">&lt;script&gt;steal_cookies()&lt;/script&gt;</div> -- browser DISPLAYS this as text
```
Walkthrough: identical escape-before-render mechanics as the JavaScript
version — `escape_html` neutralizes the angle brackets so the exact same
visible text is rendered without ever being parsed as executable markup.
