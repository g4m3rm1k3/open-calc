## Definition

MVC (Model-View-Controller) is an architectural pattern that separates an
application into three distinct responsibilities — the Model (data and
business logic), the View (what the user sees/renders), and the
Controller (handles input, coordinates between Model and View) — so each
concern can change independently.

## Problem

Mixing data logic, rendering, and input-handling all together in one
place makes an application hard to change — updating how data is
displayed risks breaking the logic that computes it, and vice versa. MVC
separates these concerns so, e.g., the View can be redesigned without
touching the Model's business logic, and the Model can be tested without
needing any UI at all.

## Execution

User clicks a button (input)
↓
Controller receives the input, decides what it means (e.g., "increment
the counter")
↓
Controller tells the Model to update itself
↓
Model updates its own internal state, independent of any UI concerns
↓
Controller tells the View to re-render, using the Model's NEW state
↓
View reads the Model's current data and renders it — the View never
modifies the Model directly, and the Model never knows anything about how
it's displayed

## Computer Science

The core discipline is a strict separation of responsibility, enforced as
a one-directional flow (input → Controller → Model → View reads Model) —
the Model has zero knowledge of the View's existence, which is precisely
what allows the same Model to be reused behind a completely different
View (a web UI, a CLI, a test) with no changes to its own logic.

Tags: Separation of concerns, Unidirectional flow, Testability, Reusable business logic

## Software Engineering

This is the conceptual ancestor of most modern UI frameworks' own
patterns (React's component-plus-state loosely mirrors View-plus-Model,
Vue's similar split) — even frameworks that don't use the literal MVC name
still typically enforce SOME version of "don't let rendering logic and
business logic bleed into each other," for the same testability and
independent-change reasons MVC was designed to provide.

Tags: Modern UI frameworks, Component architecture, Design pattern lineage

## Common Mistakes

- Putting business logic directly inside the View (e.g., computing a total price inside a rendering function) — this makes the logic untestable without rendering a UI, and duplicates it if the same computation is needed somewhere else.
- Letting the View modify the Model directly, bypassing the Controller — this scatters the logic for "what counts as a valid state change" across every View that happens to touch the Model, instead of centralizing it.

## javascript

```javascript
// Simulating the three MVC roles directly, with the Model having zero
// knowledge of the View, and the Controller mediating between them.
class CounterModel {
  #count = 0
  increment() { this.#count += 1 }
  get value() { return this.#count }
}

class CounterView {
  render(value) { return `Count is: ${value}` }   // View only reads what it's given -- never touches the Model directly
}

class CounterController {
  constructor(model, view) {
    this.model = model
    this.view = view
  }
  handleIncrementClick() {
    this.model.increment()             // Controller tells the Model to update itself
    return this.view.render(this.model.value)   // Controller tells the View to render the Model's NEW state
  }
}

const controller = new CounterController(new CounterModel(), new CounterView())
console.log(controller.handleIncrementClick())   // 'Count is: 1'
console.log(controller.handleIncrementClick())   // 'Count is: 2'
```
Walkthrough: `CounterModel` has no reference to `CounterView` at all — it
just tracks its own state. `CounterController` is the only piece that
talks to both: it tells the Model to update, then passes the Model's
current value to the View to render. The View itself just formats
whatever value it's given, with zero awareness of how that value was
computed.

## python

```python
class CounterModel:
    def __init__(self):
        self._count = 0

    def increment(self):
        self._count += 1

    @property
    def value(self):
        return self._count


class CounterView:
    def render(self, value):
        return f'Count is: {value}'   # View only reads what it's given -- never touches the Model directly


class CounterController:
    def __init__(self, model, view):
        self.model = model
        self.view = view

    def handle_increment_click(self):
        self.model.increment()                          # Controller tells the Model to update itself
        return self.view.render(self.model.value)        # Controller tells the View to render the Model's NEW state


controller = CounterController(CounterModel(), CounterView())
print(controller.handle_increment_click())   # Count is: 1
print(controller.handle_increment_click())   # Count is: 2
```
Walkthrough: identical Model/View/Controller separation as the JavaScript
version — the Model tracks state with no knowledge of rendering, the View
only formats a given value, and the Controller is the sole mediator
between them.
