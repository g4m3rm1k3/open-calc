## Non-negotiable conventions established so far

These were decided deliberately, some after real mistakes. Do not silently relitigate them.

- **Language 1 is Clojure, taught from zero.** Only basic Python-level constructs (variables, loops, functions) are assumed of the reader. Every Clojure construct — `if`, `defn`, `map`, `shuffle`, `rand-int`, vector literals, `assoc`, `declare`, everything — gets its own isolated "New Code" introduction before first real use. Never use a construct before its own lesson (or an earlier one) has taught it.
- **No `let`, anywhere, ever.** This is deliberate. Work around it with helper functions that take an already-computed value as an argument (e.g. Lesson 56's `combine-egcd`, Lesson 87's `dequeue-from-ready`) rather than introducing a binding. **This includes `loop`** — its binding vector is structurally a `let`. Lesson 39 (Section II, written before this convention was locked in) used `loop`/`recur` for bottom-up DP; that lesson is frozen and not being revised, but Lesson 119 (Section VI) deliberately did *not* reuse that pattern, using recursion-with-an-accumulator instead, and says so explicitly in its own text. Treat `loop`/`recur` as off-limits going forward, the same as bare `let`.
- **No vector/array indexing until Lesson 84.** Before that lesson, "position in a list" is built via recursive accessor functions (e.g. Lesson 81's `value-at`), never `nth`/`get`. From Lesson 84 onward, vectors and `get`/`assoc` are fair game and are this section's array representation.
- **Dependency ordering is strict.** A lesson may only use constructs and results taught in itself or an earlier lesson. Check this before finalizing any lesson — it has been violated and caught before (Lesson 4 draft originally). Before citing a prior lesson's function by name, confirm what it actually exports — Lesson 87's queue, for instance, only assigned `queue-empty?` as an *exercise*, not a guaranteed function; Lesson 124 checked both internal stacks directly (`queue-in`/`queue-out`) rather than assuming it exists.
- **Repetition Rule / citation style:** when a lesson reuses an earlier concept, name it directly in prose ("Lesson 75's linearity of expectation") rather than a bare parenthetical. Restate briefly, don't just cite silently.
- **File naming:** `NN-title-slug.md`, two-digit zero-padded, lowercase-kebab, in `src/docs/tutorials/computation/`.
- **Heading spelling:** the schema's per-Concept-Unit heading is `### SE Lens` (paired with `### CS Lens`). A typo (`SE Lells`) crept into Lessons 46–80 and was bulk-corrected — if you ever see `SE Lells` again, it's a regression, fix it.

This happened once already (34 files corrupted, then fixed via a cp1252-roundtrip reversal). ## Known-good code patterns worth reusing

- Vector-as-pair, `[a b]` with `get`, for any two-slot structure without `let` (nodes, queues, deques — Lessons 85, 87, 88).
- Vector-as-triple, `[value left right]` with `get`, for a tree node needing two subtree references (binary search trees — Lesson 92's `make-bst-node`/`bst-value`/`bst-left`/`bst-right`). Insertion rebuilds every node on the path from the root to the change and reuses every untouched subtree as-is, since there's no mutation construct to write with (Lesson 92's `bst-insert`) — reused by every later tree lesson (93, 97–101) and, at the whole-node level (a fourth slot for color), by Lesson 99's red-black nodes.
- "Compute once, pass to a helper" to avoid recomputation without `let` (Lessons 56, 87, 89, 91).
- Mutual recursion via `(declare fn-name)` when two functions call each other (Lesson 91's `binary-search`/`search-at-mid`). Reused constantly from here on: `sift-up`/`sift-up-at-parent` and `sift-down`/`sift-down-at-child` (94–95); `dc-max`/`dc-max-combine` (112); `merge-sort`/`merge-sort-combine` and `quick-sort`/`quick-sort-around` (113–114); every DFS-family traversal — `dfs-visit`/`dfs-explore`, `dfsx-visit`/`dfsx-explore`, `cycle-visit`/`cycle-explore`, `topo-visit`/`topo-explore`, `comp-visit`/`comp-explore` (125–128).
- Array-as-complete-tree, no node references at all: position alone (via `quot`/`+`/`*` arithmetic on the index) determines parent/child, valid only because the shape is always a complete binary tree (Lesson 94's heap, `heap-parent-index`/`heap-left-index`/`heap-right-index`). Growing/shrinking the array uses `assoc` at exactly `(count v)` to append and `pop` to remove the last element (Lesson 94/96) — both real, verified Clojure vector behavior. A function returning two genuinely different results (e.g. a removed value plus the new structure) reuses the vector-as-pair convention above (Lesson 96's `heap-extract-min`).
- **Multi-piece state threaded as one vector through a recursion**, extending vector-as-pair to N slots: `[disc fin clock]` for DFS timestamps (Lesson 126), `[visited on-path found?]` for cycle detection (Lesson 126), `[key parent]` for Prim's frontier (Lesson 133), `[dist]`/`parents` arrays for Dijkstra/Bellman-Ford (130–131). Always accessed via `(get state 0)`, `(get state 1)`, etc. — never destructured, since destructuring hasn't been taught and isn't needed.
- **Visited-tracking discipline for graphs (as opposed to trees):** a graph can have cycles and multiple paths to the same vertex, which trees (Section V) never had to account for — mark a vertex visited/discovered at the moment it's *first reached*, never deferred to when it's later processed, or it can be enqueued/explored more than once (Lesson 124's own derivation). Where "is this an active ancestor" matters, not just "was this ever visited" (cycle detection specifically), track a *second*, temporary flag (`on-path`) reset on backtrack/finish — `visited` alone cannot distinguish an active ancestor from an already-finished, unrelated branch (Lesson 126).
- **Extract-minimum-and-relax, the shared shape behind Dijkstra, Bellman-Ford, and Prim (130, 131, 133):** a `dist`-or-`key` array seeded with a sentinel ("infinity," a large integer, since this series has no real `Infinity` value) except the start; a scan (or, in production, Lesson 96's priority queue — these lessons use a plain `O(V)` scan and say so honestly) finds the best unfinalized candidate; a `relax` step checks whether a candidate edge improves the current best and updates if so. Dijkstra accumulates *total path cost from source*; Prim compares only the *single edge weight* to the tree — a one-line difference in the comparison is the entire distinction between the two algorithms. Bellman-Ford drops the greedy "finalize" step entirely and just relaxes every edge, `V-1` times.
- **Union-find (Lesson 102/103) is a genuinely reusable primitive across this whole series, not a one-off**: cycle-checking during MST construction (Lesson 133's `kruskal-consider`, via `uf-connected?`), connected-component labeling (Lesson 128's `uf-components`), and any place "are these two already linked, incrementally, as edges arrive one at a time" is the actual question — a batch traversal (repeated BFS/DFS) can't answer that incrementally; union-find can. This was the exact reason named back in Lesson 103 and paid off concretely three times since.
- **Weighted adjacency matrix, `matrix[u][v] = weight`, `0` meaning no edge** (Lesson 123, via `build-matrix`) is this series' representation whenever `O(1)` edge-weight lookup matters (path-weight checking, Dijkstra/Bellman-Ford/Prim's `relax`, flow networks' capacity/flow pair of matrices in Lesson 134). It has one acknowledged, never-hit-in-practice ambiguity: a genuine `0`-weight edge is indistinguishable from no edge at all — every example in this series avoids `0`-weight edges for this reason, stated explicitly in Lesson 123.

## Recurring boilerplate for Section VI+ lessons — copy this, don't re-derive it

Since Lesson 109, lessons are standalone, `bb`-verified REPL functions, not edits to one persistent growing project file — which means several schema-required fields come out *identical, word-for-word*, in nearly every Concept Unit. Confirmed by reading Lessons 91, 94, 128, 129, 133, 134, 135 in one sitting while building Lesson 136 — that cost real, avoidable time; copy these directly instead of re-reading several past lessons to reconstruct the pattern from scratch:

- **Project Change**, whenever nothing points at a real external reference implementation (true for almost every algorithm-derivation lesson):
  ```
  - **Reference Source**: No reference counterpart — this is a from-scratch addition because ___.
  - **Files affected**: None.
  - **Change type**: N/A.
  - **Location**: N/A.
  - **Dependencies**: Babashka, already installed.
  ```
- **The Updated Project**, whenever the new code is a fresh top-level function with no enclosing structure to show it inside: `Skipped — no enclosing file exists yet.`
- **Discard the throwaway example**, whenever the "isolated" demo *is* the real, reusable project code (the norm since roughly Lesson 130): `Not applicable — real, reusable, hand-verified` (or "verified this session," if `bb` was actually run).
- **Objects and methods used**, for a lesson introducing exactly one genuinely new item plus reused ones:
  ```
  - **`newThing`**
    - *What it is:* ...
    - *Implementation:* ...
    - *Its use:* ...

  This lesson also reuses `x`, `y` (Lesson N), each already covered.
  ```
  For a lesson introducing nothing new at all, one line, no bullets: `**Objects and methods used**: None new. This lesson reuses `x`, `y` (Lesson N, Lesson M), each already covered.`

This pairs with `TAUGHT-CONSTRUCTS.md` (above): that file answers "has X already been taught," this section answers "what does this recurring field look like" — together they replace most of the reason a session used to need to open several past lesson files just to check formatting before writing a new one.

## Why this curriculum exists

This isn't just a content-generation task. The user is building this to learn to build software themselves — the explicit goal is to reach a point where the user and Claude can collaborate on the user's own real projects effectively. Past attempts at that have broken down as projects got more complex, because the user lacked the foundational vocabulary to direct, verify, or catch drift in what Claude was building. This curriculum is the fix: rigorous, schema-following, dependency-ordered lessons the user actually works through, not just a document to skim. The two schema-discipline incidents logged above *are*, literally, instances of the exact failure mode this curriculum exists to inoculate against — which is why they're recorded here in detail rather than just fixed and forgotten.

This is also the first of several planned BRD-based learning series the user intends to work through, as part of the same deliberate effort — treat the rigor here as the standing bar for future series too, not a one-off.
