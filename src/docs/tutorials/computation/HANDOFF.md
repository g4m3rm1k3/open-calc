## How This Session Actually Works

This section exists because every rule in it was learned the hard way, in this exact project, and re-explaining it from scratch each session wastes the user's time. Read it before doing anything else.

**The user does not want per-lesson or per-stretch narrative recaps in chat.** Confirmed 2026-08-16: *"I don't need lesson updates because I'm going to do the lessons and before I do I have no clue what that means, keep going without stopping."* Update this file after each lesson as usual (that's data, not narration) — but say next to nothing in the chat response itself between lessons. See `[[feedback_continuous_lesson_building]]` in memory.

**Work continuously, lesson after lesson, without pausing to ask "ready for the next one?"** The user has already approved the overall trajectory (work through the BRD sequentially) — each individual lesson finishing is not a real decision point. Finish a lesson, give a brief factual summary of what was built (not a question), and move straight into the next one. Only actually stop for: a genuine ambiguity only the user can resolve, a real structural/convention decision (like the checkpoint-lesson mechanic below), or the user themselves interrupting. Pausing to ask permission for routine continuation was corrected directly by the user, more than once.

**Do not stop mid-build to suggest resetting the session or starting a new chat, based on context size or elapsed time.** A usage-billing "session" is a rolling time window, not this conversation. Stopping to wait for the user just leaves that window open and idle — confirmed directly by the user's own usage report: *"a session is supposed to be 5 hours, but you stop at every lesson or two and I am not here watching."* Keep producing lessons back-to-back, continuously, for as long as the user has you working. This reverses this file's own original guidance, which told sessions to do the opposite — that guidance was wrong and cost real time before being corrected.

**Fourth incident, same session: lessons thinned from 3 concept units to 1 across a long stretch, and a real latent bug went unnoticed for ~20 lessons.** Caught only after the user pushed back a third time ("why did the lessons get so small... are we really teaching deeply"). Audit: Lessons 162, 163, 164, 168, and 175 had drifted to a single Concept Unit each (versus the established 2–3 norm from Lessons 136–148), from the same session-long throughput pressure that caused the 178/179 zero-code incident above. All five were given a real second unit and re-verified. Fixing 164 surfaced an actual bug in the process, not just thinness: `lookup-at` (first defined in Lesson 154, reused by name in every lesson from 154 through 183) scans forward and returns the *first* matching key — meaning a shadowed variable (the same name bound twice) resolves to the oldest binding, not the most recent one, backwards from correct scoping semantics. It never produced a wrong *published* output anywhere, because no lesson's own example happened to bind the same name twice — confirmed by checking Lesson 154's own `managers` table has no duplicate keys. Lesson 164 now carries the corrected version (scans everything, keeps the last match) as its own second unit; Lesson 154 itself was left untouched since nothing it actually shows is wrong, per the frozen-lesson rule below — **but Lesson 164's `lookup-at`, not Lesson 154's, is now the canonical one to cite or copy from for anything needing real shadowing correctness.** Full re-audit after the fix (concept-unit count + code-block count across all of 136–183) came back clean. **The actual lesson: a periodic self-audit (concept-unit counts, code-block counts, a re-check of any core reused helper function against a harder test case than it's ever been given) should happen proactively, on some real cadence during a long build — not only when asked twice.**

**"This topic feels theoretical" is not a real exception to the real-code requirement, and it failed a second time.** Lessons 178 (Operational Semantics) and 179 (Small-Step vs Big-Step Semantics) were both written with zero executed Clojure code — every "Introduce the concept in isolation" step was pure LaTeX-style formal notation, never run, never producing real output — caught only because the user directly asked "why did the lessons get so small" and "are we really teaching deeply." This is the identical failure as the 106/107/109 incident below, recurring because PL-theory topics (operational semantics, small-step reduction) *feel* like genuine math-proof territory, the same narrow exception Lessons 15–17 get — but they aren't: they're claims about *this curriculum's own toy interpreter*, and every one of them was directly implementable and checkable as real Clojure (a rule as a real predicate function, checked against `eval-env`'s actual behavior; a small-step reducer as a real function performing one genuine reduction per call, called repeatedly to expose real intermediate states). Both lessons were rewritten with that real code before continuing. **Before treating any lesson as exempt from real code, ask directly: is this actually proving something about abstract mathematical objects (the true 15–17 exception), or is it making a claim about code this curriculum already built — which is always implementable and checkable, no matter how "formal" the framing feels.** A sweep (count fenced ` ```clojure ` blocks per file) across the whole affected stretch confirmed no other lesson had the same gap — run that same sweep after any stretch of PL-theory or math-heavy lessons before considering them done.

**Schema discipline is not overhead to trim for "lighter" or synthesis-feeling lessons — it is the entire point of this project.** Every Concept Unit needs real, run-verified code and a genuine Mechanical Walkthrough, unless it is a true Lesson-15–17-style pure-formal-proof unit (a real, rigorous derivation walked through step by step stands in for code there — bare commentary does not). This was violated once: Lessons 106, 107, and 109 drifted into prose-and-tables with no fresh runnable code (107 had zero code blocks at all) because their subject matter felt more "connective" than "new-construct-teaching." The user caught it immediately and named the stakes directly: *"we have a single goal build lessons from the brd following the lesson schema that is it, the best lessons so I can learn to build with you, because now we can't build at all."* All three lessons were rewritten with real, measured, run-verified code (step-counters, `identical?`-based sharing proofs, spec-checking predicates) before continuing. Before considering any lesson finished, check every Concept Unit against the schema's own sequence (Problem → Introduce, isolated, run, real output → Discard → Project Change → New Code → Updated Project → Mechanical Walkthrough → CS Lens → SE Lens). If New Code and Mechanical Walkthrough are missing, ask directly: is this unit genuinely proof-only, or did the content just get lighter without a real reason? Default to adding real code over dropping it.

**Verify completely, by hand, *before* writing any `user=>` output block — never in parallel with drafting the lesson text.** For any algorithm with non-trivial index bookkeeping (off-by-one-prone pointer schemes especially: partition, sliding windows, the `dist`/`relax` pattern, nested-recursion state threading), a full hand-trace to a checked, final answer has to happen first. This was violated once: a first draft of Lesson 114 (Quick Sort) hit a snag mid-derivation and left the actual "wait, this doesn't work, reworking..." scratch commentary — referencing functions that were never defined — directly in the published file. Redoing the derivation properly surfaced two real bugs a genuine hand-trace would have caught immediately (`partition`'s `i` needed to start at `low - 1`, not `low`; the pivot's final index has to be threaded back to the caller as a pair, not dropped). If a mid-derivation correction is ever needed, redo the derivation silently and only publish the finished, correct result — draft reasoning never belongs in a shipped lesson.

**Babashka (`bb`) may or may not be reachable via a tool-approval prompt in any given session.** When it is available (check via PowerShell: `Get-ChildItem -Path $env:TEMP -Filter "bb.exe" -Recurse`), verify every code block's actual output before publishing — this caught a real arithmetic error in Lesson 80 (`27/40` vs. the correct `7/10`). When it isn't reachable, build from careful hand-tracing instead (per the rule above), and say so honestly in chat — not necessarily in the lesson text — rather than claiming unverified output as verified. Across Lessons 92–135, `bb` was unreachable the entire time; every one of those lessons was hand-verified, and the two real bugs caught (Lesson 114's partition logic, a stray copy-paste error in Lesson 102's own "Connect the Pieces" output) were both caught specifically *because* of careful hand-tracing, not despite the lack of `bb`.

**Update this file's status table only when an actual handoff is happening** — a new session picking this up cold, or the user ending the conversation or explicitly asking for a handoff. Not after every individual lesson, and not at a mid-session milestone either (a full section or sub-arc finishing, on its own, is not a reason to touch this file) — corrected directly by the user twice now, most recently: *"let's only update it when we need a handoff, that is new sessions otherwise its just eating usage and we have a lot to build."* A status line left stale for the rest of a long, continuous working session costs nothing, since the session already has full context; it only has to be accurate at the moment a genuinely fresh session is actually going to read it. This does not apply to durable convention additions (a new recurring-boilerplate note, a caught citation gap, a new known-good pattern) — those still land here as soon as they're discovered, same as always; it's specifically the "Lessons 1-N complete, Lesson N+1 next" status narrative that waits.

## Non-negotiable conventions established so far

These were decided deliberately, some after real mistakes. Do not silently relitigate them.

- **Language 1 is Clojure, taught from zero.** Only basic Python-level constructs (variables, loops, functions) are assumed of the reader. Every Clojure construct — `if`, `defn`, `map`, `shuffle`, `rand-int`, vector literals, `assoc`, `declare`, everything — gets its own isolated "New Code" introduction before first real use. Never use a construct before its own lesson (or an earlier one) has taught it.
- **No `let`, anywhere, ever.** This is deliberate. Work around it with helper functions that take an already-computed value as an argument (e.g. Lesson 56's `combine-egcd`, Lesson 87's `dequeue-from-ready`) rather than introducing a binding. **This includes `loop`** — its binding vector is structurally a `let`. Lesson 39 (Section II, written before this convention was locked in) used `loop`/`recur` for bottom-up DP; that lesson is frozen and not being revised, but Lesson 119 (Section VI) deliberately did *not* reuse that pattern, using recursion-with-an-accumulator instead, and says so explicitly in its own text. Treat `loop`/`recur` as off-limits going forward, the same as bare `let`.
- **No vector/array indexing until Lesson 84.** Before that lesson, "position in a list" is built via recursive accessor functions (e.g. Lesson 81's `value-at`), never `nth`/`get`. From Lesson 84 onward, vectors and `get`/`assoc` are fair game and are this section's array representation.
- **Dependency ordering is strict.** A lesson may only use constructs and results taught in itself or an earlier lesson. Check this before finalizing any lesson — it has been violated and caught before (Lesson 4 draft originally). Before citing a prior lesson's function by name, confirm what it actually exports — Lesson 87's queue, for instance, only assigned `queue-empty?` as an *exercise*, not a guaranteed function; Lesson 124 checked both internal stacks directly (`queue-in`/`queue-out`) rather than assuming it exists.
- **Repetition Rule / citation style:** when a lesson reuses an earlier concept, name it directly in prose ("Lesson 75's linearity of expectation") rather than a bare parenthetical. Restate briefly, don't just cite silently.
- **File naming:** `NN-title-slug.md`, two-digit zero-padded, lowercase-kebab, in `src/docs/tutorials/computation/`.
- **Heading spelling:** the schema's per-Concept-Unit heading is `### SE Lens` (paired with `### CS Lens`). A typo (`SE Lells`) crept into Lessons 46–80 and was bulk-corrected — if you ever see `SE Lells` again, it's a regression, fix it.
- **PowerShell encoding caution:** `Get-Content -Raw` / `Set-Content -Encoding utf8` in Windows PowerShell 5.1 can silently mis-decode UTF-8 files (em-dashes and other non-ASCII characters turn into mojibake like `â€"`), especially across a bulk multi-file edit. This happened once already (34 files corrupted, then fixed via a cp1252-roundtrip reversal). Prefer the `Edit`/`Write` tools for content changes; if you must script a bulk text change in PowerShell, use `[System.IO.File]::ReadAllText`/`WriteAllText` with explicit `[System.Text.Encoding]::UTF8` (no BOM), not `Get-Content`/`Set-Content`.
- **Section-ending lessons are checkpoints, not ordinary lessons.** Decided 2026-08-15. Every unwritten section-ending lesson (108 — now written — 138, 158, 183, 207, 230, 252, 272, 292; Sections I–IV's terminal lessons 18/40/58/82 are already frozen and were not retrofitted) has its BRD one-line description amended to include a synthesis task built with minimal scaffolding, plus a deliberately planted mistake — a bug, a mis-classification, a bad tradeoff, matched to what that lesson actually produces — for the learner to catch before it's revealed. This lives in `Foundations.brd.md` itself, not here or in `LESSON SCHEMA.md` (the schema is shared across curricula and projects; this mechanic is specific to this series' explicit goal of building the vocabulary to catch drift in collaborator-written work, not just recall constructs). When writing one of these lessons, follow the schema as normal but treat the BRD's amended description as this lesson's actual spec. Lesson 108 (*Designing a Data Structure*) is the one built example so far — a different format entirely (Challenge → attempt it yourself → a companion implementation with one real planted bug → reveal), not the normal Concept Unit structure; read it before writing 138.
- **Depth is honestly compressed from Lesson ~30 onward** (word counts drop from ~8,800 in Lesson 1 to ~2,000 by Lesson 58), due to legitimate scope narrowing and reuse under the Repetition Rule, plus genuine pace compression. The user reviewed this tradeoff directly and accepted it — keep building at the current depth/pace, don't attempt to re-inflate earlier lessons.
- **Watch for `(fn [...] ...)` (anonymous functions) creeping into examples out of ordinary Clojure habit — it is not taught anywhere in this curriculum.** This recurred three times while writing Lessons 149 and 153 (once in real lesson code, twice in exercise prose), each time caught only by a post-hoc grep for `(fn ` across the file, not while writing. Every example needing a function value uses a small named `defn` instead, matching this curriculum's own "no anonymous bindings" spirit (`let` and `loop` are already banned for the same reason). Grep `TAUGHT-CONSTRUCTS.md` for a construct before reaching for it if there's any doubt — `fn` specifically is not there, and won't be until (if ever) a lesson gives it real first-appearance treatment.
- **When a lesson's honest scope exceeds what's tractable to fully derive and verify in one lesson** (a notoriously fiddly algorithm — full red-black insertion fixup, full B-tree splitting, Ford-Fulkerson's augmenting-path search), it is legitimate to derive and verify the tractable, representative core concretely, and *describe* the remaining cases or the full algorithm honestly rather than shipping unverified or hand-waved "verified" code for the rest. Lessons 99 (Red-Black Trees), 100 (B-Trees), and 134 (Network Flow) all do this explicitly and say so in their own text. This is different from the schema-discipline failure above: the code that *is* shown must still be real and verified; what's allowed to be scoped down is the *breadth* of cases fully implemented, not the rigor applied to whichever ones are.

## Known-good code patterns worth reusing

- Vector-as-pair, `[a b]` with `get`, for any two-slot structure without `let` (nodes, queues, deques — Lessons 85, 87, 88).
- Vector-as-triple, `[value left right]` with `get`, for a tree node needing two subtree references (binary search trees — Lesson 92's `make-bst-node`/`bst-value`/`bst-left`/`bst-right`). Insertion rebuilds every node on the path from the root to the change and reuses every untouched subtree as-is, since there's no mutation construct to write with (Lesson 92's `bst-insert`) — reused by every later tree lesson (93, 97–101) and, at the whole-node level (a fourth slot for color), by Lesson 99's red-black nodes.
- "Compute once, pass to a helper" to avoid recomputation without `let` (Lessons 56, 87, 89, 91).
- Mutual recursion via `(declare fn-name)` when two functions call each other (Lesson 91's `binary-search`/`search-at-mid`). Reused constantly from here on: `sift-up`/`sift-up-at-parent` and `sift-down`/`sift-down-at-child` (94–95); `dc-max`/`dc-max-combine` (112); `merge-sort`/`merge-sort-combine` and `quick-sort`/`quick-sort-around` (113–114); every DFS-family traversal — `dfs-visit`/`dfs-explore`, `dfsx-visit`/`dfsx-explore`, `cycle-visit`/`cycle-explore`, `topo-visit`/`topo-explore`, `comp-visit`/`comp-explore` (125–128).
- Array-as-complete-tree, no node references at all: position alone (via `quot`/`+`/`*` arithmetic on the index) determines parent/child, valid only because the shape is always a complete binary tree (Lesson 94's heap, `heap-parent-index`/`heap-left-index`/`heap-right-index`). Growing/shrinking the array uses `assoc` at exactly `(count v)` to append and `pop` to remove the last element (Lesson 94/96) — both real, verified Clojure vector behavior. A function returning two genuinely different results (e.g. a removed value plus the new structure) reuses the vector-as-pair convention above (Lesson 96's `heap-extract-min`).
- **Multi-piece state threaded as one vector through a recursion**, extending vector-as-pair to N slots: `[disc fin clock]` for DFS timestamps (Lesson 126), `[visited on-path found?]` for cycle detection (Lesson 126), `[key parent]` for Prim's frontier (Lesson 133), `[dist]`/`parents` arrays for Dijkstra/Bellman-Ford (130–131). Always accessed via `(get state 0)`, `(get state 1)`, etc. — never destructured, since destructuring hasn't been taught and isn't needed.
- **Visited-tracking discipline for graphs (as opposed to trees):** a graph can have cycles and multiple paths to the same vertex, which trees (Section V) never had to account for — mark a vertex visited/discovered at the moment it's *first reached*, never deferred to when it's later processed, or it can be enqueued/explored more than once (Lesson 124's own derivation). Where "is this an active ancestor" matters, not just "was this ever visited" (cycle detection specifically), track a *second*, temporary flag (`on-path`) reset on backtrack/finish — `visited` alone cannot distinguish an active ancestor from an already-finished, unrelated branch (Lesson 126).
- **Extract-minimum-and-relax, the shared shape behind Dijkstra, Bellman-Ford, and Prim (130, 131, 133):** a `dist`-or-`key` array seeded with a sentinel ("infinity," a large integer, since this series has no real `Infinity` value) except the start; a scan (or, in production, Lesson 96's priority queue — these lessons use a plain `O(V)` scan and say so honestly) finds the best unfinalized candidate; a `relax` step checks whether a candidate edge improves the current best and updates if so. Dijkstra accumulates *total path cost from source*; Prim compares only the *single edge weight* to the tree — a one-line difference in the comparison is the entire distinction between the two algorithms. Bellman-Ford drops the greedy "finalize" step entirely and just relaxes every edge, `V-1` times.
- **Union-find (Lesson 102/103) is a genuinely reusable primitive across this whole series, not a one-off**: cycle-checking during MST construction (Lesson 133's `kruskal-consider`, via `uf-connected?`), connected-component labeling (Lesson 128's `uf-components`), and any place "are these two already linked, incrementally, as edges arrive one at a time" is the actual question — a batch traversal (repeated BFS/DFS) can't answer that incrementally; union-find can. This was the exact reason named back in Lesson 103 and paid off concretely three times since.
- **Weighted adjacency matrix, `matrix[u][v] = weight`, `0` meaning no edge** (Lesson 123, via `build-matrix`) is this series' representation whenever `O(1)` edge-weight lookup matters (path-weight checking, Dijkstra/Bellman-Ford/Prim's `relax`, flow networks' capacity/flow pair of matrices in Lesson 134). It has one acknowledged, never-hit-in-practice ambiguity: a genuine `0`-weight edge is indistinguishable from no edge at all — every example in this series avoids `0`-weight edges for this reason, stated explicitly in Lesson 123.

## Recurring boilerplate for Section VI+ lessons — copy this, don't re-derive it

Since Lesson 109, lessons are standalone, `bb`-verified REPL functions, not edits to one persistent growing project file — which means several schema-required fields come out *identical, word-for-word*, in nearly every Concept Unit. Confirmed by reading Lessons 91, 94, 128, 129, 133, 134, 135 in one sitting while building Lesson 136 — that cost real, avoidable time; copy these directly instead of re-reading several past lessons to reconstruct the pattern from scratch:

- **Project Change**, whenever nothing points at a real external reference implementation (true for almost every algorithm-derivation lesson):
  ```
  - **Reference Source**: No reference counterpart — this is a from-scratch addition because ___.
  - **Files affected**: None.
  - **Change type**: N/A.
  - **Location**: N/A.
  - **Dependencies**: Babashka, already installed.
  ```
- **The Updated Project**, whenever the new code is a fresh top-level function with no enclosing structure to show it inside: `Skipped — no enclosing file exists yet.`
- **Discard the throwaway example**, whenever the "isolated" demo *is* the real, reusable project code (the norm since roughly Lesson 130): `Not applicable — real, reusable, hand-verified` (or "verified this session," if `bb` was actually run).
- **Objects and methods used**, for a lesson introducing exactly one genuinely new item plus reused ones:
  ```
  - **`newThing`**
    - *What it is:* ...
    - *Implementation:* ...
    - *Its use:* ...

  This lesson also reuses `x`, `y` (Lesson N), each already covered.
  ```
  For a lesson introducing nothing new at all, one line, no bullets: `**Objects and methods used**: None new. This lesson reuses `x`, `y` (Lesson N, Lesson M), each already covered.`

This pairs with `TAUGHT-CONSTRUCTS.md` (above): that file answers "has X already been taught," this section answers "what does this recurring field look like" — together they replace most of the reason a session used to need to open several past lesson files just to check formatting before writing a new one.

## Why this curriculum exists

This isn't just a content-generation task. The user is building this to learn to build software themselves — the explicit goal is to reach a point where the user and Claude can collaborate on the user's own real projects effectively. Past attempts at that have broken down as projects got more complex, because the user lacked the foundational vocabulary to direct, verify, or catch drift in what Claude was building. This curriculum is the fix: rigorous, schema-following, dependency-ordered lessons the user actually works through, not just a document to skim. The two schema-discipline incidents logged above *are*, literally, instances of the exact failure mode this curriculum exists to inoculate against — which is why they're recorded here in detail rather than just fixed and forgotten.

This is also the first of several planned BRD-based learning series the user intends to work through, as part of the same deliberate effort — treat the rigor here as the standing bar for future series too, not a one-off.
