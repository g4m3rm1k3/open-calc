## Terms used in this lesson

- **Compilation unit** — the complete real set of `.ts` files `tsc`
  actually checks and compiles together, in one real pass. It exists
  because real files reference each other — `app.ts` imports from
  `data.ts` and `types.ts` — and a change in one can affect whether
  another still type-checks; `tsc`, given this project's own
  `tsconfig.json` with no `"include"`/`"files"` restricting its scope,
  treats *every* real `.ts` file in `code/05-html-css/Data/` as one
  single real compilation unit, not several independent ones.
- **`noEmitOnError`** — a real TypeScript compiler option; `true`
  tells `tsc` to withhold *all* real compiled output for the current
  compilation unit if even one real error was reported anywhere in it.
  It exists because `tsc`'s own real default behavior — described
  below — doesn't do this on its own.
- **Exit code** — a real, small integer a command-line program returns
  when it finishes, read by whatever ran it (a real shell, a real CI
  system) to decide whether it succeeded. It exists so a real, external
  process — not a human reading terminal text — can automatically tell
  success from failure; `tsc`'s own real, nonzero exit code, this
  lesson's own second unit shows, is genuine, actionable signal only
  once something is actually built to check it.

## Concept Unit: An Error Isn't a Wall Unless Something Makes It One

### The Problem

`tsc` reported a real, specific error for this lesson's own previous
unit's own broken call. Nothing in that unit ever actually confirmed
whether the resulting, real `.js` file was ever produced — the
previous unit only ran `tsc --noEmit`, which never writes real output
in the first place, by design. What happens if the identical real,
broken file is compiled *without* `--noEmit`?

> **Stop and try it yourself first:** Given that a real compiler
> error is, definitionally, a real problem `tsc` found — would you
> expect `tsc`, left to its own real, default behavior, to simply
> refuse to produce any real output at all when one exists? Or is that
> real behavior something a project has to ask for, explicitly?

### SE Lens

The principle is **a tool's own default behavior is not the same

point, inside `tsc` itself, rather than trusting a separate, later real
