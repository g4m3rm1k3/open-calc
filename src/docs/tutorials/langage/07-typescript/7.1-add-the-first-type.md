## Terms used in this lesson

- **Type annotation** — a piece of syntax, written by a human, that
  states a value's type explicitly: `const dataUrl: string = "data.json"`,
  the `: string` part. It exists so a human can *assert* a type the
  compiler either can't work out on its own, or one the human wants
  enforced even though the compiler could have guessed correctly anyway.
- **Type inference** — TypeScript working out a value's real type on its
  own, from the value's own literal shape or from a function's own real
  return expression, with no annotation written anywhere. It exists so a
  typed language doesn't force a human to write `: number` on every
  single `const x = 3;` in a whole real project — most values, most of
  the time, need no annotation at all for the compiler to already know
  their real type.
- **Strict mode** (TypeScript's own `"strict": true` compiler option) —
  a single real compiler switch that turns on a whole real bundle of
  stricter checks at once (including, most consequentially for later
  lessons in this phase, `strictNullChecks` — treating `null` and
  `undefined` as real, distinct values a type must explicitly allow,
  not silently permitted everywhere). It exists because TypeScript,
  by design, ships those stricter checks turned *off* by default, for
  backward compatibility with code written before they existed; a new
  project has no such compatibility burden, so turning them all on
  together, once, at the very start, is the real, standard, current
  recommendation.
- **`devDependency`** — one of two real categories npm sorts a
  project's own dependencies into inside `package.json`, the other
  being a plain `dependency`. A `devDependency` is needed only to
  *build* or *check* this project — TypeScript itself is the exact real
  example this lesson adds — never needed by the finished thing a
  browser actually loads. A plain `dependency` would be code the
  finished, running page itself needs at runtime; this project has none
  yet.
- **Semantic-versioning caret range** (the `^` in `"typescript":
  "^7.0.2"`) — a real version-range syntax `npm` writes into
  `package.json` automatically: `^7.0.2` means "any real, published
  version compatible with `7.0.2`" — in real semantic-versioning terms,
  any `7.x.y` at or above `7.0.2`, but never `8.0.0`, since a version's
  first number is reserved, by convention, for changes that are allowed
  to break existing code.
- **Type erasure** — the real, provable fact, demonstrated later in
  this lesson by comparing `data.ts`'s real source against its own real
  compiled output, that every type annotation TypeScript ever checks is
  gone by the time real, runnable JavaScript exists — a browser, or
  Node, never sees a single `: string` anywhere; type checking is a
  real, separate step that happens once, before the program ever runs,
  and leaves no trace in what actually executes.
- **Module** — reappearing from Lesson 6.10's own real ES module split:
  a single real `.js` (here, `.ts`) file whose own top-level `export`
  and `import` statements are the only real way its own values become
  visible to, or borrow visibility from, any other file. `data.ts`
  remains this project's own real module boundary around its network
  logic, unchanged in shape by this lesson — only in file extension.
- **`async`/`await`** — reappearing from Lesson 6.8's own real rewrite:
  a real pair of keywords marking a function (`async`) as one that can
  pause without blocking its own caller, and marking a specific
  expression inside it (`await`) as the exact point where that pause
  happens, resuming only once the awaited value's own real work
  finishes. `fetchEntries`'s own real `async function` declaration and
  its own real `await fetch(dataUrl)` are untouched by this lesson,
  carried over from `data.js` unchanged.
- **Template literal** — reappearing from Lesson 6.7's own real
  introduction: a backtick-delimited string, `` `Request failed:
  ${response.status}` ``, allowing a real expression (`response.status`)
  to be embedded directly inside the string via `${...}`, evaluated and
  converted to text at the moment the template literal itself runs.
- **`Promise`** — reappearing from Lesson 6.8's own real explanation: a
  real, built-in JavaScript object representing a value that doesn't
  exist yet but will, eventually, either succeed with a real result or
  fail with a real error. Every real `async function` — `fetchEntries`
  included — always returns one, whether or not its own source code
  ever writes the word `Promise`; this lesson's own real, run output
  proves TypeScript already knows this, unasked, by inferring
  `fetchEntries`'s own return type as `Promise<any>` before this lesson
  writes a single annotation anywhere.
