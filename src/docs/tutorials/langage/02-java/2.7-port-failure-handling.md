# Lesson 2.7: Refuse, Then Decide, Then Ask What Java Requires — Port Failure Handling

**What you will build.** `Service` gains a new method, `reset()`, that sets
its run count back to `0` — except when there's nothing to reset: calling
`reset()` on a `Service` that has never run **throws** a real exception,
`IllegalStateException("Cannot reset a service that has never run.")`,
refusing to proceed. `Program.java` proves both directions for real:
calling `reset()` on the original `service` (which has run twice)
succeeds; calling it on a brand-new, never-run `Service` first crashes the
whole program with a genuine, unhandled exception, then — once wrapped in
a **`try`/`catch`** block — is caught, logged, and the program finishes
cleanly instead. This much is a direct, faithful port of C# Lesson
1.10 — Java's `throw`, `try`, and `catch` keywords work close enough to
C#'s own that the mechanism itself needs almost no adaptation. But
curriculum's own title for this lesson says "compare," not just "port,"
because Java's exceptions carry a real, structural distinction C#'s never
had to: **checked exceptions**. C# has exactly one kind of exception —
throw it, and the compiler never requires anything else of the code around
it. Java has two: **unchecked** exceptions (like this lesson's own
`IllegalStateException`), which behave exactly like C#'s; and **checked**
exceptions, which the compiler refuses to let a method throw at all unless
that method either handles them or explicitly declares, in its own
signature, that it might. This lesson's third unit proves that distinction
directly, with a real compile error neither this curriculum's C# Phase nor
Java's own unchecked exceptions have ever produced before.

**What you need to know first.** From **Lesson 2.4 — Port Composition**:
the real project at `code/02-java/Service/`, real, unhandled
`NullPointerException`s, stack traces, and the JVM's own default crash
behavior. From **Lesson 2.3**: `private`, `public`, encapsulation. From
**Lesson 2.2**: `class`, `object`, `method`, `void`, `new`, member access
(`.`). From **Lesson 2.1**: `System.out.println`, `javac`/`java`. From
**C# Lesson 1.10 — Refuse, Then Decide**, this lesson's own reference
source: `if` statement, comparison operator, `throw`, `try`/`catch`,
deciding where failure belongs, and the exact reference code being
ported, read fresh this session from `code/01-csharp/Service/` at git
commit `333990c`. From the curriculum's own stated assumptions: Python's
`if`/`elif`/`else`, `==`, and `try:`/`except SomeError:` — this lesson
leans on that prior conceptual familiarity while still giving Java's own
version of each a full, real first-appearance treatment, per this
schema's own standing rule that a familiar idea in a new language is not
the same knowledge as the syntax itself.

## Terms used in this lesson

- **`if` statement (Java)** — a control-flow statement that runs the
  statements inside its block only when a given condition evaluates to
  `true`. The identical underlying idea C# Lesson 1.10 named, met here in
  Java's own, nearly identical syntax — parentheses around the condition,
  braces around the body, no colon, no indentation-as-structure.
- **comparison operator (`==`) (Java)** — tests whether two values are
  equal, producing `true` or `false`. Reappearing in spirit from C#
  Lesson 1.10; this project's first Java use of it — `runCount == 0`.
- **`throw` statement (Java)** — deliberately raises an exception,
  immediately ending the normal flow of whatever method it's in. The
  identical underlying mechanism C# Lesson 1.10 named for C#'s own
  `throw`.
- **`try`/`catch` (Java)** — a `try` block contains code that might throw;
  a `catch` block names a specific exception type and runs only if a
  matching exception was thrown inside the `try` block. The identical
  underlying mechanism C# Lesson 1.10 named.
- **unchecked exception** — an exception type that Java's compiler places
  no requirements on at all: any method may throw one, or call a method
  that might throw one, with no `throws` declaration and no `try`/`catch`
  required anywhere, ever. Every exception type extending
  `java.lang.RuntimeException` (including `RuntimeException` itself) is
  unchecked. This is the *only* kind of exception C# has at all — C#
  never distinguishes checked from unchecked, which is exactly why this
  term never appeared anywhere in this curriculum's own C# Phase.
- **checked exception** — a real, Java-only category of exception the
  compiler actively enforces handling for: any exception type extending
  `java.lang.Exception` *without* extending `RuntimeException` is
  checked, and a method that might throw one must either handle it with
  its own `try`/`catch`, or declare it explicitly in its own signature
  with a `throws` clause — proven, in this lesson's third unit, with a
  real compile error when neither is done. A hard concept, getting full
  CS Lens treatment below, with no C# counterpart to port from at all.
- **`throws` clause** — a keyword appended to a method's own declaration,
  naming one or more checked exception types that method might throw
  without handling itself, which is what lets that method compile despite
  not catching them — the obligation to handle the exception is passed up
  to whatever calls this method instead.
- **exception, unhandled exception, stack trace, runtime error** — all
  reappearing from Lesson 2.4, restated in full: an exception is an
  object representing something that went wrong while a program was
  running; unhandled means nothing in the program caught it, so the JVM
  prints a description and a stack trace, then ends the program at the
  exact point it occurred.
- **field, class, block (`{ }`), `void`, call syntax (`( )`), `var`,
  `new`, member access (`.`), assignment operator (`=`), string literal,
  semicolon (`;`), `int`, `public`, `private`, `this`** — all reappearing
  from Lessons 2.1–2.6, unchanged in meaning, all still present in
  `Service.java`, `Program.java`, and this lesson's isolated lab.

## Objects and methods used

- **`IllegalStateException`**
  - *What it is:* a real, unchecked exception type from Java's own
    standard library, representing a method call that's invalid given the
    object's *current state* — the direct Java counterpart to C#'s own
    `InvalidOperationException`, both in meaning and in requiring no
    special compiler-enforced handling.
  - *Implementation:* `public class IllegalStateException extends
    RuntimeException`, in the `java.lang` package (imported automatically
    into every Java file, needing no explicit `import` statement, the
    same package `String`, `System`, and `Object` all live in); declares a
    constructor accepting a `String` message, among others.
  - *Its use:* `Service.reset()` throws exactly this type when `runCount`
    is already `0`.
  - *Type:* a class — extending `RuntimeException`, which makes it
    **unchecked**: no `throws` declaration and no `try`/`catch` are
    required anywhere for code that throws or calls something that throws
    it.
  - *Responsibility:* carry a description of what invalid-state condition
    occurred, retrievable later via `getMessage()`.
  - *Depends on:* the message string passed to its constructor.
  - *Connects to:* thrown by `Service.reset()`; caught by `Program.main`'s
    `catch (IllegalStateException ex)` clause.
  - *Shape:* a real class from Java's own standard library, used here the
    same way `System` has been all along — genuine, inspectable code this
    project didn't write but depends on directly.

- **`IllegalStateException(String)` — the constructor**
  - *What it is:* the specific constructor `Service.reset()` calls to
    create the exception it throws.
  - *Implementation:* a `public` constructor accepting one `String`
    parameter.
  - *Its use:* `new IllegalStateException("Cannot reset a service that has
    never run.")`.
  - *Type:* an instance constructor.
  - *Responsibility:* store the message it's given so it's retrievable
    later.
  - *Depends on:* the `String` argument passed to it.
  - *Connects to:* called by `Service.reset()`'s own `throw` statement.
  - *Shape:* the exact point where a plain string becomes a real,
    throwable exception object.

- **`Throwable.getMessage()`** (inherited by `IllegalStateException`)
  - *What it is:* a real instance method, defined on `java.lang.Throwable`
    — the actual base class every exception in Java, checked or
    unchecked, ultimately extends — and inherited by every specific
    exception type.
  - *Implementation:* `public String getMessage()`, returning the message
    string the exception was constructed with. Unlike C#'s own `Message`
    (a property, reappearing in spirit from Lesson 2.3's own getter
    discussion), Java's version is an ordinary method, called with
    parentheses — `ex.getMessage()`, not `ex.getMessage` — the same real
    divergence this curriculum's own Lesson 2.3 already proved for
    `Service.getRunCount()` versus C#'s `RunCount` property.
  - *Its use:* read inside `Program.main`'s `catch` block —
    `logger.log(ex.getMessage());`.
  - *Type:* a `public` instance method.
  - *Responsibility:* hand back the exact message string the exception was
    constructed with.
  - *Depends on:* the exception object it's called on.
  - *Connects to:* called by `Program.main`'s `catch` block; ultimately
    passed to `logger.log`.
  - *Shape:* the seam where a caught exception's own information becomes
    available to the code that caught it.

- **`Service.reset()`**
  - *What it is:* this lesson's own new method — the operation that can
    fail.
  - *Implementation:* `public void reset() { if (runCount == 0) { throw
    new IllegalStateException("Cannot reset a service that has never
    run."); } runCount = 0; logger.log("Service has been reset."); }` —
    `code/02-java/Service/Service.java`.
  - *Its use:* called twice in `Program.main` — once successfully, on
    `service` (`getRunCount()` was `2`), once unsuccessfully, on a fresh
    `Service` that never called `run()`.
  - *Type:* an instance method, returning `void`.
  - *Responsibility:* set `runCount` back to `0` and report that via
    `logger` — but only when doing so is actually meaningful; refuse
    otherwise.
  - *Depends on:* an already-constructed `Service` object; `logger`, to
    report a successful reset.
  - *Connects to:* called by `Program.main`; reads and writes `runCount`;
    calls `logger.log` on success; throws `IllegalStateException` on
    failure, caught (or not) by whatever called it.
  - *Shape:* this project's first method whose contract includes a
    documented way to fail, not only a documented way to succeed.

- **`Service`, `Service.run()`, `Service.getRunCount()`,
  `Service(Logger)`** — all reappearing unchanged from Lessons 2.2–2.5,
  now sitting alongside `Service`'s own new `reset()` method.

- **`System`, `System.out`, `PrintStream.println(int)`** — reappearing
  unchanged from Lessons 2.1–2.6; this lesson's code prints
  `service.getRunCount()`'s own `int` value one more time, after a
  successful reset.

## Concept Unit: `if` and `throw` — Refusing an Invalid Operation

### The Problem

`Service` can count how many times it's run and report on it, but it has
no way to reset that count back to zero. Adding a `reset()` method seems
simple — until asking what `reset()` should do on a `Service` that has
never run at all.

> **Stop and think, before reading on:** you already know Python's `if
> value == 0:` and `raise ValueError("message")`. Given that every
> construct in this project's Java code so far has needed its own
> explicit braces and parentheses, what do you predict Java's own `if`
> and "raise an error" syntax actually looks like? And given `new
> Service(logger)` already showed you object creation using parentheses
> for constructor arguments, what shape do you expect for creating and
> immediately signaling an error object in one step?

### The Real Project Change

- **Reference Source:** `code/01-csharp/Service/Service.cs` and
  `Program.cs` at commit `333990c` — C# Lesson 1.10's own closing state,
  read fresh via `git show`:
  ```csharp

  {
      if (runCount == 0)
      {

  a Java equivalent that doesn't exist under that exact name.
- **Files affected:** modified — `code/02-java/Service/Service.java` and
  `code/02-java/Service/Program.java`.
- **Change type:** add.
- **Location:** a new method inside `Service`'s block; two new blocks
  appended to the end of `main`.
- **Dependencies:** `Service`'s existing `runCount` field and `logger`
  collaborator.

## Concept Unit: `try`/`catch` — Deciding Where Failure Belongs

### The Problem

`neverRun.reset()` crashes the whole program. `Program.java`, in this
project, would rather notice the problem, log it, and keep going. Nothing

> **Stop and think, before reading on:** you already know Python's `try:`

## Concept Unit: Checked vs. Unchecked — Java's Real Exception Hierarchy

### The Problem

`Service.reset()`'s own declaration, `public void reset()`, never
mentions `IllegalStateException` anywhere — no special keyword, nothing
in its signature warning a caller this method might throw. C# Lesson 1.10
never had to ask whether that was always true, because C# has exactly one
kind of exception, with no distinction like this at all. Java's own
curriculum title for this lesson says "compare" for a reason: is *every*
Java exception this easy to throw with no declaration required, or is
`IllegalStateException` a specific kind that happens to get a pass?

> **Stop and think, before reading on:** every exception this project has
> thrown or caught so far — Lesson 2.4's own `NullPointerException`, this
> lesson's own `IllegalStateException` — required no special declaration
> anywhere. Given that Java is generally stricter about compiler-enforced
> rules than C# has been throughout this entire curriculum (recall Lesson
> 2.3's own real, tested `private`-access compile errors, or this
> lesson's own `if`/`throw` syntax needing explicit braces Python never
> asks for), does it seem plausible that Java lets *every* exception
> through with zero compiler involvement — or does "Java tends to enforce
> more at compile time than C#" suggest there might be a category of
> exception this project simply hasn't met yet?

### The Real Project Change

- **Reference Source:** no reference counterpart — this unit inspects a
  real, Java-only language feature with no C# equivalent to port; C#
  Lesson 1.10 never needed to ask this question, because C#'s own
  exceptions don't raise it.

public class Checker {
    public void check() throws ServiceUnavailableException {
        throw new ServiceUnavailableException("Service is unavailable.");

        checker.check();

                     ^

        Checker checker = new Checker();

        try {
            checker.check();
        } catch (ServiceUnavailableException ex) {
            System.out.println(ex.getMessage());

}
```

### Mechanical Walkthrough

Enumerating the new syntactic elements from this unit's own lab, in
order:

- **`extends Exception`** — declares `ServiceUnavailableException` as a
  subclass of `java.lang.Exception`, Java's own real base class for
  checked exceptions. `Exception` itself extends `Throwable`, the
  ultimate ancestor of everything throwable in Java.
- **`super(message)`** — a call, inside this exception's own constructor,
  to its own superclass's constructor — `Exception(String)` — passing the
  message along so `getMessage()` (reappearing from earlier in this
  lesson) works correctly once inherited.
- **`throws ServiceUnavailableException`** — the **`throws` clause**,
  appended to `check`'s own declaration, naming the checked exception this
  method might throw without handling itself. This is not a `throw`
  statement (which actually raises an exception, at a specific line);
  `throws` is a declaration, appearing only in a method's own signature,
  naming a possibility rather than causing anything to happen.

### CS Lens

The checked/unchecked distinction is a real instance of **compile-time
contract enforcement** — the compiler treating "this operation can fail
this specific way" as part of a method's own public contract, checkable
before the program ever runs, rather than leaving it as documentation a
caller might never read:

```
Also recognized in: a function's own type signature in a statically
typed functional language declaring exactly which effects it can
perform, a database migration tool refusing to apply a migration
whose own declared dependencies haven't run yet, a shipping label
required by law to declare hazardous contents before a package can be
accepted for transport
```

### SE Lens

C#'s own choice — exactly one kind of exception, with no compiler
enforcement of handling at all — was deliberately not the path Java took.
Java's own designers chose checked exceptions specifically so a method's
own signature could honestly document every *recoverable*, expected
failure mode a caller genuinely needs to plan for — a network call that
might fail, a file that might not exist — forcing that possibility into
the open rather than leaving it as a comment a caller might never read.
The real cost, widely felt in real Java code and worth naming honestly
rather than presented as an unqualified win: checked exceptions propagate
through every intermediate method in a call chain, exactly as this unit's
own lab just proved, which means a change deep inside a call chain — a
new checked exception added to some low-level method — can force
`throws` clauses to be added or `try`/`catch` blocks written in every
method between there and wherever it's finally handled, a real,
sometimes disproportionate maintenance cost. `IllegalStateException`'s own
choice to extend `RuntimeException` instead — the choice this lesson's
own `Service.reset()` inherited by using it — is itself a real, common
judgment call in Java API design: `RuntimeException` (and its subtypes)
are reserved, by convention, for failures representing a programming
mistake or an invalid *precondition*, like calling `reset()` on a
`Service` that was never run — situations a caller could and should have
prevented by checking first, rather than genuinely unpredictable external
failures a caller has no way to avoid in advance.
