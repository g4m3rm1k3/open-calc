# Lesson 2.1: From Source Text to Bytecode to a Running Process — Recreate the Executable

**What you will build.** A brand-new Java project, `code/02-java/Service/` — the
seed of Phase 2's port of the small system Phase 1 built in C# — that does
exactly what the C# project did at the moment Lesson 1.1's own closing commit
was made: print `Service is running.` to the terminal, and nothing else.
Phase 2's own framing is a deliberate port, not a new project: the same
architecture, rebuilt in a different language and a different runtime, so the
differences between them become visible instead of assumed. This first lesson
only recreates that one-line bootstrap — not the full `Service`/`ILogger`/
`LastValue<T>` system Phase 1 eventually grew across eleven more lessons;
porting that starts in Lesson 2.2. The transferable problem underneath this
one line is the same shape Lesson 1.1 asked for C#, with different answers:
what, if anything, has to exist before a `.java` file can run at all; where a
Java program's execution actually begins; and what "build" means for a
language whose compiled output isn't one project-wide assembly, the way C#'s
was, but something else entirely — a separate compiled file per class, run by
a virtual machine instead of loaded directly by the operating system.

**What you need to know first.** From Phase 1, Lesson 1.1's own answers to
these same three questions, asked there for C#: that a compiled language
needs a real, separate translation step turning source text into a runnable
form, distinct from just running the source directly the way Python does;
that a program's execution begins at one specific, agreed-upon entry point,
not "wherever the interpreter happens to start reading"; and that a build
tool's job is to translate source into something runnable, a distinct
capability from actually running it. Also reused directly: Lesson 0.1's
`git init`, `git add`, and `git commit -m "<message>"`, used again in this
lesson's own closing commit. Nothing about Java's actual syntax is assumed —
the curriculum's own stated assumptions name only "more than one line" of
prior Java exposure, not working knowledge, so every construct below is
treated as genuinely new, per the Repetition Rule, regardless of how closely
it resembles something C# already covered.

## Terms used in this lesson

- **JDK (Java Development Kit)** — the installed toolchain bundle providing
  `javac`, `java`, and the standard class library together, the same role the
  .NET SDK played for C# in Lesson 1.1. It exists because "a Java compiler"
  and "a Java runtime" are two distinct programs, not one, and something has
  to bundle them, plus the standard library both depend on, into one
  installable unit.
- **JVM (Java Virtual Machine)** — the runtime program that actually executes
  a Java program, by reading compiled **bytecode** (below) and either
  interpreting it directly or compiling it further, on the fly, into the real
  CPU's native instructions. It exists so compiled Java code isn't tied to one
  specific CPU architecture or operating system the way a C or C++ binary is:
  the same compiled output runs anywhere a JVM exists, because the JVM — not
  the original source — is what actually varies per platform.
- **bytecode** — the instruction format `javac` compiles Java source into: not
  the real CPU's native machine instructions, and not human-readable text, but
  a fixed, documented instruction set the JVM itself understands. It's the
  actual "compiled form" of a Java program — the JVM's own machine language,
  one level of translation short of whatever a real CPU executes.
- **`.class` file** — the real file `javac` writes to disk, holding one
  class's compiled bytecode plus metadata (its name, its superclass, its
  members) the JVM needs to load and run it. Unlike C#'s single project-wide
  `Service.dll`, Java compiles one `.class` file per class — this lesson's one
  class produces exactly one `.class` file, but a project with ten classes
  would produce ten.
- **classpath** — the list of locations (folders, or `.jar` archives) the
  `java` command searches to find compiled `.class` files by name. It exists
  because "run the class named `Program`" doesn't say *where* to look for
  `Program.class`, and something has to define that search path; when no
  classpath is given explicitly, it defaults to the current directory, which
  is the only case this lesson needs.
- **class (declaration)** — a keyword and construct declaring a named type: a
  blueprint bundling data and behavior together, exactly the same underlying
  idea Lesson 1.2 will eventually name in C#'s own terms, but Java's own
  syntax and rules for it are being met here for the first time in this
  curriculum and get their own full, real treatment rather than a reused
  definition. Every Java program is built entirely out of classes — there is
  no equivalent to C#'s top-level statements that lets code exist outside one.
- **access modifier** — a keyword controlling which other code is allowed to
  see or use a class, method, or field. `public`, used throughout this
  lesson's code, is one specific access modifier: it exists to let some code
  be part of a program's externally usable surface while other code stays
  hidden as an internal detail — the same underlying problem C#'s own access
  modifiers solve, met here in Java's own syntax.
- **`static` (modifier)** — a modifier on a method or field meaning it belongs
  to the class itself, not to any particular instance of it, and can be
  called or read without ever creating one. It exists because some
  operations — like "where does this program start running" — don't
  conceptually belong to any one object; they belong to the class as a whole,
  or don't need an object at all.
- **`void` (return type)** — a keyword used in place of a real return type,
  meaning a method performs an action but hands nothing back to its caller.
  It exists because every method declaration needs *some* stated return
  type, and a method whose entire job is a side effect (printing a line, in
  this lesson's case) still needs a way to say, explicitly, "nothing comes
  back."
- **method** — a named, callable block of code associated with a class,
  taking zero or more parameters and returning a value or `void`. The same
  underlying idea as a C# method, met here in Java's own declaration syntax —
  a return type, a name, a parenthesized parameter list, and a body in
  braces — for the first time in this curriculum.
- **array type (`[]`)** — a type modifier meaning "a fixed-size, ordered
  sequence of values of this type," written by appending `[]` after the
  element type. This is the first appearance of arrays anywhere in this
  curriculum; C# Phase 1 never introduced them. An array is a genuinely
  different construct from `LastValue<T>`'s single stored value: it holds a
  whole indexed sequence, not one item.
- **command-line arguments** — the real-world values a program receives from
  however it was launched, beyond the program's own name — for example, the
  `--verbose` in `some-program --verbose`. This lesson's code declares a
  parameter for them (`String[] args`) without reading it, because the
  parameter is part of a fixed contract explained in the next unit, not
  something this lesson's own logic happens to need yet.
- **compilation unit / filename-matches-class-name rule** — a real, load-
  bearing Java rule: a source file containing a `public` class must be named
  *exactly* after that class, with a `.java` extension — `Program.java` for
  `class Program`, capitalization included. It exists so `javac`, and anyone
  else reading the project, can locate a given public class's source by name
  alone, without opening every file to check what it contains.
- **default (unnamed) package** — the namespace a class belongs to when its
  source file declares no explicit `package` statement. It's a real,
  legal Java state, used here as a deliberate simplification for this
  lesson's single-file project — not a hidden production practice worth
  imitating once a project grows past one file, which this lesson makes clear
  honestly, in the SE Lens below.
- **statement (Java)** — one complete instruction the JVM carries out before
  moving to the next one, the same underlying idea as a C# statement, met
  here in Java's own grammar, which — like C#'s — needs an explicit
  terminator rather than relying on line breaks the way Python does.
- **semicolon (`;`) as a statement terminator** — the character ending a Java
  statement, for the identical reason C# needs one: Java's grammar allows a
  single statement to span multiple lines or several statements to share one
  line, so whitespace alone can't mark where one statement ends and the next
  begins.
- **string literal (Java)** — text typed directly into source code, delimited
  by double quotes (`"..."`), the same surface syntax as C#'s own string
  literals. Underneath, though, a Java string literal is a real instance of
  the `String` class (below) — Java has no unboxed, class-free "just text"
  primitive the way `int` or `boolean` are primitives; every string, literal
  or not, is an object.

## Objects and methods used

- **`Program`**
  - *What it is:* the class this lesson defines to hold the program's entry
    point — this lesson's own subject, not a supporting class from
    elsewhere.
  - *Implementation:* `public class Program { ... }`, declared with no
    `extends` clause. Java gives every class with no explicit superclass an
    implicit one anyway: `java.lang.Object`, confirmed for real below rather
    than asserted from memory.
  - *Its use:* this is the one class this lesson's entire project consists
    of — the container the entry point method has to live inside, since Java
    has no equivalent to C#'s top-level statements letting code exist outside
    any class at all.
  - *Type:* a `public` top-level class — a blueprint, not a running thing by
    itself; nothing in this lesson ever writes `new Program()`.
  - *Responsibility:* hold this program's single entry point method and,
    later in Phase 2 as this project grows, whatever other startup logic the
    program needs before handing control to the rest of the system — for
    this lesson, that charter is satisfied by exactly one method.
  - *Depends on:* nothing at construction time — it's never constructed by
    this project's own code at all in this lesson.
  - *Connects to:* invoked by the JVM itself, not by any other class in this
    project; internally, its `main` method calls `System.out.println`.
  - *Shape:* the outermost public entry surface of this entire program — the
    seam between "the JVM decided to start this process" and "this project's
    own code begins running."

- **`main`**
  - *What it is:* the specific method the JVM looks for, by exact name and
    exact signature, to begin executing a class as a program — this lesson's
    other main subject.
  - *Implementation:* `public static void main(String[] args)` — a `public`,
    `static` method, returning `void`, taking one parameter: an array of
    `String`. This exact shape is not a convention this project chose; it's
    the one signature the JVM's own launcher recognizes. A method named
    `main` with any other signature — a different parameter type, a non-
    `void` return, missing `static` — is not this entry point at all, just an
    ordinary method the JVM would never call on its own.
  - *Its use:* this is where `java Program`'s execution actually begins —
    the direct Java counterpart to what Lesson 1.1's top-level statements did
    implicitly, made fully explicit here instead.
  - *Type:* a `public static` method — callable without ever constructing a
    `Program` instance, which is exactly how the JVM calls it: it never
    constructs one either.
  - *Responsibility:* serve as the single, agreed-upon place the JVM hands
    control to this program's own code, and, for this lesson, print the
    program's one observable line before returning.
  - *Depends on:* the `args` array, supplied by the JVM itself from the real
    command line this program was launched with — not read or used by this
    lesson's own body yet, but real and present regardless.
  - *Connects to:* called exactly once, by the JVM launcher, never by any
    code inside this project; it calls `System.out.println` in its own body.
  - *Shape:* the exact instruction the JVM executes first — everything this
    program will ever do starts as a statement inside this method or
    something it calls.

- **`System`**
  - *What it is:* a class in Java's standard library (`java.lang.System`)
    exposing system-level facilities: standard input/output/error streams,
    environment access, and a handful of other platform-level operations.
  - *Implementation:* declared `public final class System` — `final` meaning
    no other class is allowed to subclass it. Unlike C#'s `Console`, Java has
    no `static class` modifier for a top-level class at all; `System`
    achieves "no instances" a different way — by declaring a `private`
    constructor, so no code outside the class itself, not even this project,
    is permitted to write `new System()`.
  - *Its use:* this lesson's code reaches into it for exactly one thing —
    its `out` field, below — to get access to standard output.
  - *Type:* a `final` class exposing only `static` members; not instantiable
    by any code outside its own file.
  - *Responsibility:* give a running Java program access to process-level
    facilities the JVM manages on its behalf — standard streams among them —
    without exposing the operating system's own raw handles directly.
  - *Depends on:* the JVM having already wired up the real OS-level standard
    streams before any of this project's code runs, the same underlying
    dependency Lesson 1.1's `Console` had on the OS's stdout handle.
  - *Connects to:* called directly by `Program.main`; internally, its `out`
    field already holds a live, ready-to-use stream object by the time any
    Java code gets to run at all.
  - *Shape:* a public standard-library surface at the outer boundary between
    this program's own code and the process it's running inside of.

- **`System.out`**
  - *What it is:* a field on `System` — not a method call — holding the
    process's standard output stream as a ready-made object.
  - *Implementation:* declared `public static final PrintStream out`: a
    `public` field, `static` (reached through the class, not an instance),
    and `final` (the field itself is never reassigned to point at a
    different stream after startup). Its declared type, `PrintStream`, is a
    real class with its own members — this is exactly the case this schema's
    own "compound type" rule requires showing the real shape of, below,
    rather than only describing it in prose.
  - *Its use:* this lesson's code reads this field to get the object its
    next call, `.println(...)`, is actually invoked on.
  - *Type:* a `public static final` field — read directly off the class,
    never off an instance, and its own value never changes after the JVM
    sets it up at startup.
  - *Responsibility:* hold a single, shared, already-open `PrintStream`
    connected to the process's real standard output, so any code anywhere in
    a running JVM can reach it the same way, without first having to obtain
    or construct one.
  - *Depends on:* the JVM's own startup sequence, which sets this field
    before any application code — including `Program.main` — ever runs.
  - *Connects to:* read by `Program.main`; the object it holds is what
    `.println` (below) is actually called on.
  - *Shape:* a public, standard-library-owned handle sitting at the same I/O
    boundary `System` itself sits at — the field through which this lesson's
    code actually reaches that boundary.

  `PrintStream`'s real declared shape — the members that make it a compound
  type worth showing, not just describing, per this schema's own rule — has
  more than one `println` overload, one per common argument type, each
  documented in Java's own public `java.io.PrintStream` API reference:

  ```java
  public void println()
  public void println(boolean x)
  public void println(char x)
  public void println(int x)
  public void println(long x)
  public void println(float x)
  public void println(double x)
  public void println(char[] x)
  public void println(String x)
  public void println(Object x)
  ```

  This lesson's code calls exactly one of these — `println(String)`, below —
  but seeing the full set here matters: it shows `println` isn't one method
  that happens to accept text, but a whole family of overloads Java's
  compiler chooses between based on the argument's real type, the same
  overload-resolution idea C# also uses for `Console.WriteLine`'s own several
  overloads in Lesson 1.1.

- **`PrintStream.println(String)`**
  - *What it is:* the specific overload, from the family shown above, that
    writes a `String` to the stream followed by a line terminator.
  - *Implementation:* `public void println(String x)` — an **instance**
    method (no `static`), meaning it has to be called *on* a `PrintStream`
    object, never on the class `PrintStream` itself. This is confirmed as
    real, not assumed, in the Mechanical Walkthrough below, using the actual
    compiled bytecode.
  - *Its use:* this is the exact call this lesson's code makes to produce its
    one observable result — the direct Java counterpart to Lesson 1.1's
    `Console.WriteLine` call.
  - *Type:* a `public` instance method, called on the object `System.out`
    holds — never `static`, unlike C#'s `Console.WriteLine`, which was a
    `static` method on a `static`-only class. This is a real, structural
    difference between the two languages' otherwise near-identical "print a
    line" call, not just a naming difference.
  - *Responsibility:* append its `String` argument to the stream's output,
    followed by a platform-appropriate line terminator, so each call's
    output lands on its own line — the same charter Lesson 1.1's
    `Console.WriteLine` had, on a different kind of object.
  - *Depends on:* the `String` argument passed in, and the `PrintStream`
    instance it's called on — here, always the one `System.out` holds.
  - *Connects to:* called by `Program.main`, its only caller in this
    project; it writes, in turn, through `PrintStream`'s own internal
    buffering into the OS's real stdout stream.
  - *Shape:* the exact edge of the public API boundary this lesson's code
    crosses to produce anything a human can see — identical in role to
    Lesson 1.1's own `Console.WriteLine`, just reached through an instance
    instead of a static class.

  Its contract is documented in Java's own public `java.io.PrintStream` API
  reference; its real implementation is genuine source in the OpenJDK
  project, reachable the same way any IDE's go-to-definition would reach it.
  It isn't shown here because the real body ultimately funnels into
  synchronized, buffered byte-writing machinery several layers deep — not a
  short, illuminating read for this lesson — but nothing about it is hidden;
  it's ordinary code, written by people, sitting in a real, public file.

### Everything else in the file, not this lesson's subject but still explained

- **`String`**
  - *What it is:* Java's standard library class representing text —
    `java.lang.String` — appearing in this lesson's code only as the element
    type of the `main` method's array parameter, `String[] args`.
  - *Implementation:* `public final class String` — `final`, so, like
    `System`, it cannot be subclassed. Every Java string literal, including
    `"Service is running."` in this lesson's own code, is a real instance of
    this exact class.
  - *Its use:* named here only because it appears in `main`'s required
    signature — this lesson's code never constructs, reads, or calls a
    method on any `String` value directly by name; `args` itself is never
    touched.
  - *Type:* a `final` class — an ordinary reference type, not a primitive
    like `int` or `boolean`.
  - *Responsibility:* represent an immutable sequence of characters — once
    created, a given `String` object's contents never change.
  - *Depends on:* nothing from this project; it's part of the standard
    library the JDK ships.
  - *Connects to:* named in `main`'s parameter type; no code in this lesson
    calls any of its own methods.
  - *Shape:* a standard-library data type sitting at the JVM's own process
    boundary — it's the type the JVM itself uses to hand command-line
    arguments to a running program.

## Concept Unit: The Project

### The Problem

Right now, `code/02-java/` doesn't exist. There is no Java anywhere in this
curriculum yet. Lesson 1.1 needed a real project file — `Service.csproj` — to
exist before C#'s compiler would build anything at all. Does Java need
something equivalent before a `.java` file can be compiled and run?

> **Stop and think, before reading on:** you just finished twelve lessons of
> C#, where a project always meant a folder plus a `.csproj` build-recipe
> file — nothing built without one. Given that Java is also a compiled
> language, do you expect it to need a comparable manifest file before a
> single source file can be compiled? Or, given that a Java program's whole
> job here is just "print one line," might the language be willing to treat
> one bare `.java` file, sitting alone with nothing else next to it, as
> already enough? What's the smallest thing you'd guess `javac` actually
> requires to exist on disk before it will do anything at all?

### Introduce the Concept in Isolation

A single Java source file, `Program.java`, was written by hand in a throwaway
folder, `Scratch1`, inside the session's own scratch directory — never inside
this curriculum's tracked project tree — with nothing else placed alongside
it:

```java
public class Program {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}
```

Real directory listing, before doing anything else:

```
Program.java
```

Compiled for real, with no manifest, no build tool, and no flags beyond the
filename itself:

```
javac Program.java
```

Real output: none at all — `javac` prints nothing on success, only on
warnings or errors. Its exit code, checked directly, was `0`, confirming
success without any printed confirmation. Real directory listing immediately
after:

```
Program.class
Program.java
```

This proves the concept concretely: nothing but the one `.java` file existed
beforehand, and `javac` needed nothing else — no manifest, no separate
project file, no build tool — to produce a real compiled output,
`Program.class`. This is called **javac**: the Java compiler, one of the
core tools the **JDK** bundles, translating Java source into a `.class`
file. Where Lesson 1.1's `Service.csproj` had to exist *before* `dotnet new`
would create anything runnable, Java's smallest possible "project" is simply
one correctly named source file — nothing to scaffold, nothing to configure,
because there's nothing yet in this lesson's scope (like an external
dependency, or more than one source file) that a manifest would actually need
to record.

### Mechanical Walkthrough

- **`public` (on `class Program`)** — the **access modifier** making this
  class visible outside its own file; without it, Java's default
  ("package-private") visibility would still let this single-file program
  compile and run, but `public` is what the filename-matching rule, below,
  actually requires of a class it applies to.
- **`class Program`** — a **class declaration**, naming the type this whole
  file defines. Because this class is `public`, the **filename-matches-
  class-name rule** applies: the file must be named exactly `Program.java`,
  which it is — a real requirement, not a style convention, that `javac`
  enforces by refusing to compile a mismatched pair.
- **`{` / `}` (class body)** — already-established block-delimiter syntax
  from C#; the same idea, unchanged, applied here to a class body instead of
  a method or statement block.
- **no `package` statement** — the file declares no package at the top,
  which is what puts `Program` in Java's **default (unnamed) package**. This
  is real, present-by-omission behavior, not something skipped or assumed —
  named explicitly here rather than left silent.

### CS Lens

Requiring a manifest before anything can build — C#'s own choice, in Lesson
1.1 — versus letting one correctly named source file already be a complete,
buildable unit — Java's choice, here — is a real instance of **convention
over configuration**: relying on an agreed-upon rule (a file's name must
match its public class) to make an entire category of explicit configuration
unnecessary.

```
Also recognized in: Ruby on Rails' folder-name-implies-behavior
conventions, Python's __init__.py marking a package with no extra
manifest per file, Go's one-package-per-directory rule, Maven's
"convention over configuration" tagline for its own default project
layout
```

Every one of these trades an explicit declaration for an agreed-upon rule the
tooling already expects — less to write, at the cost of the rule itself
being fixed rather than freely chosen.

### SE Lens

The alternative not chosen here — the one C# actually did choose — is an
explicit manifest file naming exactly what to build and how. That
alternative's real payoff, visible the moment a project needs more than one
source file or an external dependency: a `.csproj` (or, for a larger Java
project, a `pom.xml` or `build.gradle`) gives one place recording exactly
what's needed, instead of leaving it implicit in file names and folder
placement. The real cost paid by Java's manifest-free approach, honestly:
it works cleanly right up until a project needs something a bare filename
convention can't express — a dependency on another library, a specific
target Java version, packaging instructions for distribution — at which
point real Java projects reach for Maven or Gradle after all, tools this
curriculum hasn't introduced and doesn't need yet, because nothing in Phase
2's own scope requires them. This lesson's own project is deliberately kept
in the zone where that tradeoff hasn't come due.

### Commands Needed

- **`javac Program.java`** — `javac` is the Java compiler; its one argument
  here is the source file to compile. Success looks like *no output at all*
  and an exit code of `0` — a real, worth-naming difference from `dotnet
  build`'s own verbose "Build succeeded" report in Lesson 1.1. Failure would
  print a real compiler error naming the file, line, and problem instead.

### Run It

Already run, for real, this session — the compile command's own real output
(none) and the real resulting `Program.class` file, both shown above, **are**
this unit's run. The compiled program itself hasn't been executed yet;
that's the second unit's problem to solve.

### Connect to What Came Before

This is Lesson 2.1's very first concept unit — there is no earlier unit in
this lesson to connect back to. What it establishes is the ground everything
else in this lesson stands on: a real, minimal, buildable Java source file,
on disk, with nothing else required around it — the direct answer to the

## Concept Unit: The Entry Point — `public static void main(String[] args)`

### The Problem

`Program.class` now exists, compiled successfully, but nothing has actually
been *run* yet. In C#, Lesson 1.1 discovered that a file's own top-level
statements, left unwrapped, already act as the entry point — no explicit
method needed. Java has no top-level statements at all; every line of Java
code has to live inside some method, which has to live inside some class.
Given that, what decides *which* method, out of however many a class might
have, is the one the JVM actually calls first?

> **Stop and think, before reading on:** C#'s top-level statements let
> Lesson 1.1 skip writing any method at all — the file's own statements just
> ran, top to bottom. Java's `Program.java`, as written in the previous
> unit, already has exactly one method: `main`. Given that Java requires

  public Program();
    Code:
         0: aload_0
         1: invokespecial #1                  // Method java/lang/Object."<init>":()V

         8: return

```

This is real, direct proof, not a description trusted on faith, of two
separate facts:

1. `getstatic ... Field java/lang/System.out` — reading `System.out` really

   a static field), not a method call at all — confirming the `Implementation`
   claim, above, that `out` is a field.
2. `invokevirtual ... Method java/io/PrintStream.println` — the actual call
   to `println` uses `invokevirtual`, the JVM's bytecode instruction for
   calling an **instance** method, dispatched on a real object at runtime —
   never `invokestatic`, the instruction a call to a truly static method
   like `Console.WriteLine` would compile to. This is the real, compiled-
   code proof that `println` is an instance method, called *on* the
   `PrintStream` object `System.out` holds, not a static method called
   directly on a class the way C#'s `Console.WriteLine` was.

Named plainly: this two-step shape — a static field access, `System.out`,
followed by an instance method call on the object it holds, `.println(...)`
— is Java's own answer to "print a line," genuinely different underneath
from C#'s single static call, even though both read almost identically on
the page.

`git init` creates the **repository** — `code/02-java/Service/.git/` — that
gives this brand-new Java project a history at all, exactly as Lesson 1.1
established for `code/01-csharp/Service/`, and Lesson 0.1 before that for
`code/00-git-workflow/`. `git add .` moves every current file into the
staging area, except the one path just excluded by the new `.gitignore`:
`Program.class`, the same build-output reasoning Lesson 1.1 already applied
to C#'s own `bin/`/`obj/` — a compiled `.class` file is entirely regenerable
from source with one `javac` command, so committing it would record noise a
teammate gets nothing from and can rebuild instantly anyway. Running `git
status` before committing inspects exactly what's about to be recorded:

```
git status
```

Real output:

```
On branch master

No commits yet

Changes to be committed:
  (use "git rm --cached <file>..." to unstage)
	new file:   .gitignore
	new file:   Program.java
```

Exactly two files — the `.gitignore` just written, and `Program.java` from
the first unit. `Program.class` did not make it in. Then the meaningful
commit message — stating *why* this change exists, not restating the diff
itself:

```
git commit -m "Program prints one observable line on run"
```

Real output:

```
[master (root-commit) 0177976] Program prints one observable line on run
 2 files changed, 6 insertions(+)

`code/02-java/Service/` now has its own real history, its own real compiled
bytecode, and its own real, single observable line — printing the exact
same message C# Lesson 1.1 first produced, through a genuinely different
build tool, a genuinely different entry-point mechanism, and a genuinely
different (proven, not assumed) shape of method call underneath. This is the
smallest possible foundation the rest of Phase 2 ports the rest of `Service`
onto, starting with Lesson 2.2's own `Service` class itself.
