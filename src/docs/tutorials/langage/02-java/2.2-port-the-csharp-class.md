# Lesson 2.2: Giving Behavior a Home — Port the C# Class

**What you will build.** `code/02-java/Service/` still prints exactly one
line, `Service is running.`, when it runs — but by the end of this lesson
that line no longer comes from a bare statement sitting directly inside
`main`. It comes from calling a method on a real, constructed object of a
new class named `Service`, declared in its own file, `Service.java` —
Java's own version of exactly the move C# Lesson 1.2 made for `Service.cs`.
This lesson only ports that much: an empty class, one method, one object
creation, and the constructor question that comes with it — not the fields,
encapsulation, or injected dependency Phase 1 built in later lessons, which
Lesson 2.2's own later Java counterparts (2.3 onward) will port in their own
turn. The five ideas underneath this move are the same five C# Lesson 1.2
named — a **class** gives behavior a named place to exist; an **object** is
what has to come into being, for real, before that behavior can run; an
**instance** names the relationship between that object and the class it
came from; a **method** is behavior belonging to a class instead of floating
free; a **constructor** is the guaranteed step that already runs the instant
an object is born, whether or not anyone wrote one by hand — but Java's own
syntax, compilation model, and even naming conventions answer each of them a
little differently, and those differences are this lesson's real subject.

**What you need to know first.** From **Lesson 2.1 — Recreate the
Executable**: the real project at `code/02-java/Service/`, its `Program`
class and `public static void main(String[] args)` entry point, `System`,
`System.out`, and `PrintStream.println(String)`, the `javac`/`java`
build/run cycle, and the real, disassembled-bytecode proof that `javac`
silently supplies a public no-arg constructor for a class that declares
none, and that constructor calls `java.lang.Object`'s own constructor —
reused directly in this lesson, and, per the Repetition Rule below, each one
explained again here in full rather than assumed remembered. From **C#
Lesson 1.2 — Giving Behavior a Home**, this lesson's own reference source:
the same five concepts named above, and the exact reference code being
ported, read fresh this session from `code/01-csharp/Service/` at git commit
`b9e470b` — C# Lesson 1.2's own closing state, not the project's current,
further-evolved files. From the curriculum's own stated assumptions: enough
basic Python object-oriented experience to have already written a class, a
constructor, and `self.name = name` — leaned on here only to contrast with
what Java does differently, the same way C# Lesson 1.2 used it, never to
assume Java's own syntax is already known.

## Terms used in this lesson

- **class (Java)** — a keyword and declaration introducing a new named
  blueprint: a description of what any object made from it will contain and
  be able to do, without itself being a running thing. The same underlying
  idea C# Lesson 1.2 named for C#'s own `class` keyword, met here in Java's
  own declaration syntax for the first time in this curriculum — Lesson
  2.1's `Program` class was already real Java `class` syntax, but this is
  the first lesson to explain the keyword's own meaning rather than just use
  it.
- **block (`{ }`)** — a pair of curly braces marking where a body begins and
  ends. Already established in Lesson 2.1 for a class body and a method
  body; this lesson nests them the same way C# Lesson 1.2 did — a method's
  own block sitting inside a class's own block.
- **access modifier `public`** — a keyword controlling which other code is
  allowed to see and use the thing it's attached to; already defined in
  Lesson 2.1 for `Program` and `main`. Reappearing here on `Service` itself
  and, later in this lesson, on `Service`'s own method and constructor —
  the same underlying visibility idea, applied to new declarations.
- **instance method** — a method that runs *on* a specific object rather
  than on the class as a whole; calling one requires an actual object to
  call it through (`service.run()`), unlike a `static` method such as
  `main` (reappearing from Lesson 2.1), which the JVM calls with no object
  involved at all. The same underlying idea C# Lesson 1.2 named for
  `Service.Run()`, ported here to `Service.run()`.
- **`void`** — a method's declared return type, meaning "this method hands
  no value back to whatever called it." Already defined in Lesson 2.1 for
  `main`'s own return type; reappearing here on `Service`'s new method.
- **object** — a concrete, real thing that exists while a program runs,
  created from a class's blueprint, with its own existence independent of
  any other object made from the same class. The same underlying idea C#
  Lesson 1.2 named for C#'s own objects — Java's objects work identically at
  this level of description; what differs, covered later in this lesson, is
  only the syntax for creating and reaching one.
- **instance** — the specific relationship between one particular object and
  the class it was created from: this object *is an instance of* `Service`.
  The same distinction "a car" has from "the specific car parked in this
  driveway right now," met here for Java's own objects for the first time.
- **`new` (Java)** — the operator that creates a new object from a class,
  running that class's constructor and producing a usable reference to the
  freshly created object. The identical surface syntax to C#'s own `new`
  operator, already met once, briefly, in this lesson's own reference
  source; this is the first time this curriculum's Java code actually uses
  it, so it gets its own full treatment here rather than an assumed
  carry-over from C#.
- **constructor (Java)** — a special method sharing its class's exact name,
  declaring no return type at all — not even `void` — that runs
  automatically, exactly once, at the moment `new` creates an object, before
  any other method can be called on it. The same underlying idea C# Lesson
  1.2 named for C#'s own constructors, met here in Java's own syntax, which
  turns out to be nearly identical: same-name-as-class, no return type,
  same automatic timing.
- **default constructor (Java)** — the specific parameterless constructor
  the Java compiler automatically supplies for any class that declares no
  constructor of its own — already proven real, with actual disassembled
  bytecode, in Lesson 2.1, for the `Program` class specifically. This
  lesson proves the identical fact again, now for `Service`, per the
  Repetition Rule below, rather than treating Lesson 2.1's proof as
  sufficient to skip re-explaining it here.
- **`var` (Java)** — a keyword letting a local variable's declared type be
  inferred by the compiler from whatever is assigned to it, instead of the
  author writing the type out by hand. The identical surface syntax and
  behavior to C#'s own `var`, already used once in this lesson's own
  reference source — but a genuinely separate language feature underneath,
  not literally the same mechanism just because it looks and behaves the
  same: Java's `var` was added to the language only in Java 10 (2018),
  roughly sixteen years after Java 1.0, as `javac -version`'s own `25.0.2`
  output (Lesson 2.1) already implies a much newer version than that.
- **assignment operator (`=`)** — reappearing from the general idea already
  familiar from Python, JavaScript, and C# (Lesson 1.2's own reference
  source); its first appearance in this curriculum's actual Java code,
  storing a genuinely new kind of value here: a reference to an object,
  rather than a plain number or string.
- **local variable** — a named storage location declared inside a method,
  existing only for as long as that method is running. This curriculum's
  first Java variable of any kind — Lesson 2.1's `main` method declared no
  variables at all, only a parameter.
- **object reference** — the actual value a variable of a class type holds
  in Java: not the object's data laid out inline, but a reference pointing
  at an object living elsewhere, so copying the variable copies the
  reference, not the object itself. The same underlying fact C# Lesson 1.2
  named for C#'s own reference types — Java draws this line even more
  simply than C# does: every non-primitive type in Java (every `class`,
  without exception) works this way, where C# additionally offers `struct`
  for defining custom value types, a distinction this curriculum has not
  needed and still doesn't need here.
- **member access (`.`)** — reappearing from Lesson 2.1, where it reached
  into `System` (a class) and a `PrintStream` instance held in a field. Here
  it reaches into a `Service` instance this project's own code constructed
  itself, for the first time — the same operator, the same underlying
  meaning, now used on this project's own object instead of only a
  standard-library one.
- **string literal (Java)** — reappearing from Lesson 2.1: text delimited by
  double quotes, a real `String` instance underneath, unchanged here.
- **semicolon (`;`) as a statement terminator** — reappearing from Lesson
  2.1, needed for the identical structural reason.
- **call syntax (`( )`)** — reappearing from Lesson 2.1, where it only ever
  invoked a method (`println(...)`). This lesson adds a constructor call
  (`new Service()`) and an instance method call (`service.run()`) to that
  same parenthesized syntax.
- **javac's implicit compilation of referenced sources** — a real, tested
  behavior of the Java compiler: given one `.java` file to compile, `javac`
  automatically locates and compiles any other source file, in the same
  directory, that the given file's code actually references — but *only*
  when it's actually referenced, not merely present nearby. This is Java's
  own answer to the same underlying problem C# Lesson 1.2's "SDK-style
  project / implicit file globbing" solved differently: C#'s SDK compiles
  *every* `.cs` file anywhere under the project folder, unconditionally,
  whether it's used or not; `javac`, given a single file, follows real
  dependencies outward from that file instead — a structurally different
  mechanism arriving at a similar convenience, proven for real, both ways,
  in this lesson's own isolated lab, not assumed to work like C#'s version.

## Objects and methods used

- **`Service`**
  - *What it is:* this project's own first Java class — a blueprint
    describing what a "service" object contains and can do, not itself a
    running thing. The direct Java counterpart to C# Lesson 1.2's own
    `Service` class.
  - *Implementation:* `public class Service { public void run() { ... } }`,
    declared in the new file `code/02-java/Service/Service.java`. No fields
    yet — that's a later Java lesson's own subject, porting C# Lesson 1.3 —
    and no explicitly written constructor, this lesson's own fourth unit.
  - *Its use:* gives this Java project's own behavior an actual, named,
    structural home instead of a bare statement directly inside `main` — the
    seed this curriculum's Phase 2 plan says becomes a full port of the C#
    `Service` architecture across the rest of this phase.
  - *Type:* a `public` top-level class — an instantiable blueprint;
    `new Service()` is both legal and, from this lesson onward, exactly how
    this project uses it.
  - *Responsibility:* right now, exactly one thing — running and printing
    this project's status line, via `run()`. Nothing else yet.
  - *Depends on:* nothing yet — no fields, and, per this lesson's fourth
    unit, no explicitly written constructor either.
  - *Connects to:* created and called by `Program.main`, its only caller
    right now; it in turn calls `System.out.println` to produce output.
  - *Shape:* this project's first real internal building block —
    `Program.java` is no longer the entire program by itself; it now
    depends on a distinct class sitting in its own file.

- **`Service.run()`**
  - *What it is:* an instance method belonging to `Service`, holding the
    exact behavior that is currently this whole project's point — the
    direct Java counterpart to C# Lesson 1.2's own `Service.Run()`.
  - *Implementation:* `public void run() { System.out.println("Service is
    running."); }` — a `public`, non-`static` method, returning `void`,
    taking no parameters. Named `run`, lowercase, not `Run` — a deliberate
    adaptation, not a typo, explained in this lesson's second Concept Unit.
  - *Its use:* this is where Lesson 2.1's original single statement now
    actually lives, moved out of `main` and into a named, callable piece of
    behavior that belongs to the `Service` class.
  - *Type:* an instance method — requires an actual `Service` object to
    call it through (`service.run()`); there is no way to call it on the
    class itself.
  - *Responsibility:* produce this project's one observable result by
    calling `System.out.println`, exactly once per call.
  - *Depends on:* an already-constructed `Service` object to be called on;
    `System.out`, to actually perform the printing.
  - *Connects to:* called by `Program.main` immediately after `new
    Service()` constructs the object it's called on; it calls
    `System.out.println` in turn.
  - *Shape:* an internal implementation detail of `Service` — `Program.java`
    doesn't need to know *how* `run()` produces its output, only that
    calling it does.

- **`Service()` — the compiler-supplied default constructor**
  - *What it is:* the specific constructor that actually runs every time
    `new Service()` executes, even though `Service.java` never declares one
    — the direct Java counterpart to Lesson 2.1's own proof of this exact
    fact for `Program`.
  - *Implementation:* not written anywhere in this project's own source.
    Per the Java Language Specification, a class with no declared
    constructor is automatically given one, equivalent to a hand-written
    `public Service() { }` — a real, callable member the compiler adds to
    the compiled class. Confirmed again for real, specifically for
    `Service` and not only assumed to generalize from Lesson 2.1's proof
    about `Program`, in this lesson's fourth unit, below.
  - *Its use:* this is what actually runs, silently, the instant
    `new Service()` executes in this lesson's third unit — before `run()`
    is ever reached.
  - *Type:* an instance constructor — a special method sharing its class's
    exact name, with no return type at all, not even `void`.
  - *Responsibility:* right now, nothing beyond letting the object come
    into existence at all — there is no field to initialize yet.
  - *Depends on:* nothing — a parameterless constructor needs no arguments.
  - *Connects to:* called directly by the `new Service()` expression in
    `Program.main`, before control ever reaches `.run()` on the next line —
    confirmed for real via disassembled bytecode in this lesson's closing
    unit, showing the exact `invokespecial` instruction.
  - *Shape:* an invisible-but-real piece of the class's compiled shape —
    present in the compiled `Service.class` even though absent from
    `Service.java`'s own source text.

- **`System`**
  - *What it is:* a class in Java's standard library (`java.lang.System`)
    exposing system-level facilities, including the standard output stream
    this lesson's code reaches through.
  - *Implementation:* declared `public final class System` — `final`,
    so no other class may subclass it — with a `private` constructor,
    Java's own way of preventing any code, including this project, from
    ever writing `new System()`.
  - *Its use:* reused, unchanged, from Lesson 2.1: this lesson's code still
    reaches into it for its `out` field to get access to standard output —
    now called from inside `Service.run()` instead of directly inside
    `main`.
  - *Type:* a `final` class exposing only `static` members; not
    instantiable by any code outside its own file.
  - *Responsibility:* give a running Java program access to process-level
    facilities the JVM manages on its behalf, standard streams among them.
  - *Depends on:* the JVM having already wired up the real OS-level
    standard streams before any of this project's code runs.
  - *Connects to:* called directly by `Service.run()` now, rather than by
    `Program.main` directly as in Lesson 2.1; its `out` field already holds
    a live, ready-to-use stream object by the time any Java code runs.
  - *Shape:* still a public standard-library surface at the outer boundary
    of this program — unchanged from Lesson 2.1; only the calling location
    moved.

- **`System.out`**
  - *What it is:* a field on `System`, holding the process's standard
    output stream as a ready-made object — unchanged from Lesson 2.1.
  - *Implementation:* `public static final PrintStream out` — `public`,
    `static` (reached through the class, not an instance), and `final`
    (never reassigned after startup).
  - *Its use:* read for the same reason as Lesson 2.1: this lesson's code
    needs the `PrintStream` object it holds to actually reach `println`.
  - *Type:* a `public static final` field.
  - *Responsibility:* hold a single, shared, already-open `PrintStream`
    connected to the process's real standard output.
  - *Depends on:* the JVM's own startup sequence, which sets this field
    before any application code runs.
  - *Connects to:* read by `Service.run()` now, rather than `Program.main`
    directly; the object it holds is what `.println` is called on.
  - *Shape:* still the same public, standard-library-owned handle at the
    I/O boundary, now reached from a different, deeper call site.

- **`PrintStream.println(String)`**
  - *What it is:* the overload, from `PrintStream`'s own family of
    `println` overloads (shown in full in Lesson 2.1), that writes a
    `String` to the stream followed by a line terminator.
  - *Implementation:* `public void println(String x)` — an **instance**
    method, confirmed in Lesson 2.1 via real disassembled bytecode
    (`invokevirtual`, never `invokestatic`) to genuinely be an instance
    call, not a static one, unlike C#'s own `Console.WriteLine`.
  - *Its use:* still the exact call producing this project's one
    observable result — now made from inside `Service.run()` instead of
    directly inside `main`.
  - *Type:* a `public` instance method, called on the object `System.out`
    holds.
  - *Responsibility:* append its `String` argument to the stream's output,
    followed by a line terminator.
  - *Depends on:* the `String` argument passed in, and the `PrintStream`
    instance it's called on.
  - *Connects to:* called now by `Service.run()` — a real instance method,
    itself called by `Program.main` through the `service` object — rather
    than being called directly by `main`, as in Lesson 2.1. The call chain
    grew by one real link, the same structural change C# Lesson 1.2 made to
    its own call chain.
  - *Shape:* still the exact edge of the public API boundary this project's
    code crosses to produce anything observable.

## Concept Unit: The Class — A Blueprint, Not a Running Thing

### The Problem

`code/02-java/Service/Program.java` currently contains exactly one
statement inside `main`: `System.out.println("Service is running.");`.
This curriculum's own plan says Phase 2 ports the rest of C#'s `Service`
architecture across the next several Java lessons — fields, encapsulation,
an injected dependency, an interface with two implementations, generics,
failure handling. None of that has anywhere to live inside a single
statement sitting directly in `main`. Where is any of it supposed to go?

> **Stop and think, before reading on:** C# Lesson 1.2 answered this exact
> question for C# with one keyword, `class`, and the general idea is
> already familiar from Python's own `class` keyword too. Given that Java

> before `main` could exist inside it at all, what do you predict declaring
> a *second* class looks like? Does it need to live inside `Program`

### Introduce the Concept in Isolation

A throwaway project, `Scratch2`, was created fresh in this session's own
scratch directory — never inside `code/02-java/`. Two files were written by
hand: `Program.java`, an untouched copy of Lesson 2.1's own boilerplate, and
`Greeter.java`, a new, empty class:

```java
// Program.java
public class Program {
    public static void main(String[] args) {
        System.out.println("Hello, World!");
    }
}

// Greeter.java
public class Greeter {
}
```

Compiled for real, naming only `Program.java` on the command line — never
`Greeter.java`:

```
javac Program.java
```

Real output: none (exit code `0`). Real directory listing immediately
after:

```
Greeter.java
Program.class
Program.java
```

No `Greeter.class` — `javac` never compiled `Greeter.java` at all, even
though it sits right there in the same folder. Run for real:

```
java Program
```

Real output:

```
Hello, World!
```

This is exactly what the real `Service.java` above is doing, isolated: an
empty class was added to a working program, and both the compiled output
and the running program's behavior stayed completely unaffected. This
proves two things at once. First, the same fact C# Lesson 1.2 proved for
C#: **declaring a class doesn't execute anything by itself** — a class is a
blueprint, sitting inert until something actually creates one. Second, a
genuinely Java-specific fact, worth naming plainly as its own concept:
**javac only compiles what it can prove is actually needed.** C#'s SDK,
back in Lesson 1.2, compiled *every* `.cs` file in the project folder
unconditionally — an unused `Greeter.cs` would have been compiled right
alongside everything else. Java's `javac`, given one file, doesn't scan the
whole folder at all; it only follows real references outward from the file
it was actually told to compile, and `Program.java` doesn't reference
`Greeter` anywhere yet, so `javac` had no reason to touch it.

`Scratch2` is kept alive rather than deleted immediately — the Verification
Rule's batching guidance is to run related throwaway checks together — and
will be reused for the next three concept units in this lesson.

### CS Lens

A class is a concrete example of **abstraction over structure**: it names a
*category* of thing (`Service`) separately from any particular thing that
category describes:

```
Also recognized in: a database table's schema, a factory's
assembly-line specification, a cookie cutter versus the cookies it
produces, a species classification versus any one living member of
that species
```

Separately, `javac`'s own reference-following behavior, just proven above,
is a real instance of **lazy evaluation of dependencies** — doing work only
for what's actually reachable from a stated starting point, rather than
eagerly processing everything that happens to be nearby:

```
Also recognized in: a build tool only rebuilding files whose
dependencies actually changed, a garbage collector only tracing
objects reachable from program roots, a module bundler's own
tree-shaking, a spreadsheet only recalculating cells whose inputs
changed
```

### SE Lens

The alternative not chosen here is what Lesson 2.1's entire program already
was: one class, one method, no separate named pieces of behavior. That
alternative works for exactly one thing happening once. It stops working
the moment a project needs more than one related piece of behavior — which
is exactly why C# Lesson 1.2 made the identical move for identical reasons.
The real cost paid here, worth stating honestly, mirrors what C# Lesson 1.2
already found: an empty class is more ceremony than an empty file needed to
contain zero behavior. Java's own version of that cost has a second layer
C#'s didn't: because `javac`'s compilation is reference-driven rather than
folder-wide, an unused class like this one doesn't even get compiled yet —
it's not just inert, it's not even *built* until something in the project
actually reaches for it, a genuinely different failure mode than C#'s own
"compiled but unused" state from Lesson 1.2's first unit.

## Concept Unit: The Method — Behavior That Belongs to the Blueprint

### The Problem

`Service` now exists as an empty blueprint. `Program.java`'s `main` method
still holds the project's entire real behavior, unchanged:
`System.out.println("Service is running.");`. If that line is ever going to
be something `Service` itself can do, it has to move somewhere. Where,
specifically, inside `Service`'s empty braces, does a runnable piece of
behavior actually go — and does adding it there change whether `javac` even
notices `Service` exists yet?

> **Stop and think, before reading on:** Lesson 2.1 already showed you
> exactly what a method declaration looks like — `main` itself. Given that
