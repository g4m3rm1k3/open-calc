# Lesson 2.5: Naming What Several Classes Can Do — Port the Interface

**What you will build.** `Service` currently depends on one concrete class,
`Logger`, and nothing else could ever take its place without changing
`Service`'s own field and constructor type. This lesson extracts a
`Logger` **interface** — a signature with no body, naming only *that*
something can `log(String message)`, never *how* — renames the old
concrete `Logger` class to `ConsoleLogger` (an **implementation** of that
interface), and adds a second, genuinely different implementation,
`LoudLogger`. Then, in this lesson's third act, `Program.java`'s
construction line swaps from `ConsoleLogger` to `LoudLogger`, and
`Service.java` is proven, with a real, empty `git diff`, to need zero
changes to make that true. This lesson ports two C# lessons — 1.7 and
1.8 — into one, the same combining move Lessons 2.3 and 2.4 already made.
Along the way, this lesson surfaces a genuinely Java-specific fact worth
its own real proof: unlike C#, which prefixes every interface name with
`I` (`ILogger`, distinct from any concrete `Logger`), Java's own real
convention gives the *plain* name to the interface — the same pattern
`List`, `Map`, and `Runnable` all follow in Java's own standard library —
which means `Service.java`'s field and constructor, already just reading
`Logger`, need **no text change at all** the moment `Logger` stops naming
a concrete class and starts naming an interface instead. **Polymorphism**
— the same call, genuinely different real behavior, depending only on
which concrete object stands behind an interface-typed reference — gets
proven here with a real, running comparison, exactly as C# Lesson 1.7
proved it, and exactly as real, in Java's own syntax.

**What you need to know first.** From **Lesson 2.4 — Port Composition**:
the real project at `code/02-java/Service/`, `Service`'s hand-written
constructor, `dependency`, `constructor injection`, and `this`. From
**Lesson 2.3**: `private`, `public`, encapsulation, getter methods. From
**Lesson 2.2**: `class`, `object`, `instance`, `method`, `constructor`,
`new`, `var`, member access (`.`). From **Lesson 2.1**:
`System.out.println`, `javac`/`java`. From **C# Lesson 1.7 — Naming What
Several Classes Can Do** and **C# Lesson 1.8 — The Payoff**, this lesson's

## Terms used in this lesson

- **interface (Java)** — a named declaration listing one or more method
  signatures — a name, parameter types, a return type — with no bodies at
  all, describing *what* something can do without saying *how*. A hard
  concept, getting full CS Lens treatment below — the identical principle
  C# Lesson 1.7 named for C#'s own interfaces, met here in Java's own
  syntax, which turns out to need one fewer keyword than C#'s own version:
  a class *implements* an interface with the word `implements`, not a bare
  colon.
- **implementation (Java)** — a class that provides real, working bodies
  for every method an interface declares. `ConsoleLogger` and `LoudLogger`
  are both implementations of `Logger` this lesson — two separate classes,
  each providing a genuinely different real body for the identical `log`
  signature.
- **polymorphism** — literally "many forms": the same method call,
  written once, producing genuinely different real behavior depending on
  which concrete object actually receives it at runtime. A hard concept,
  getting full CS Lens treatment below — the identical idea C# Lesson 1.7
  named, proven here again in Java's own syntax.
- **`implements`** — the keyword a class declaration uses to state that it
  provides real bodies for everything a named interface declares:
  `public class ConsoleLogger implements Logger` reads as "`ConsoleLogger`
  *is a* `Logger`" — a genuine **"is-a" relationship** (reappearing from
  Lesson 2.4, where it was only named in passing to contrast with
  "has-a"). This is Java's own direct counterpart to C#'s `: ILogger`
  syntax — a real keyword instead of a colon, but the identical underlying
  declaration.
- **Java's plain-name interface convention** — a real, widely followed
  naming convention this lesson's own code follows, worth naming
  explicitly because it's a genuine, worth-teaching-honestly divergence
  from C#'s own convention: where C# prefixes an interface name with a
  capital `I` (`ILogger`, distinct from any concrete `Logger`), idiomatic
  Java gives the *plain*, unprefixed name to the interface itself — the
  same pattern `java.util.List`, `java.util.Map`, and `java.lang.Runnable`
  all follow, none of them spelled with an `I` prefix. This lesson's own
  interface is named plainly `Logger`, which means the class that used to
  own that name has to be renamed — `ConsoleLogger`, this lesson's own
  first unit.
- **dependency, constructor injection, `this`** — reappearing from Lesson
  2.4, unchanged in meaning: `Service` still receives its logging
  dependency through its constructor; `this.logger = logger;` still
  disambiguates the parameter from the field. What changes this lesson is
  only the *kind* of type that dependency is — an interface instead of a
  concrete class — not the injection mechanism itself.
- **field, private, class, block (`{ }`), `void`, call syntax (`( )`),
  `var`, `new`, member access (`.`), assignment operator (`=`), string
  literal, semicolon (`;`), `int`, `public`, parameter, argument** — all
  reappearing from Lessons 2.1–2.4, unchanged in meaning, all still
  present in `Service.java`, the interface and its implementations, and
  this lesson's isolated lab.

## Concept Unit: The Interface — Naming What Multiple Classes Can Do

### The Problem

`Service`'s constructor currently declares `public Service(Logger
logger)`, where `Logger` names one specific, concrete class. Nothing else,
no matter how similar, could ever be passed in without `Service`'s own
source code changing to accept it. If a second, genuinely different way of
logging needs to exist someday, is `Service` really supposed to grow a
second constructor, or an `if` statement choosing between them, every
single time a new option appears?

> **Stop and think, before reading on:** in Python, you never declare
> ahead of time that a class provides some particular set of methods — any
> object with a `.log(message)` method just works anywhere a `.log(message)`
> call is made, with nothing checked before the program runs. Given that
> Java is strict about types everywhere else in this project so far —
> every field, every parameter, every return type has always been spelled
> out explicitly — what do you predict Java requires before a parameter
> can accept "anything with a `log(String)` method," rather than one
> single named class? And, thinking back to Lesson 2.2's own real, tested
> finding that Java's naming convention never prefixes anything the way
> C#'s `RunCount` did — what do you predict Java's own naming convention
> looks like for an interface specifically, given C#'s own choice was to
> prefix every one with a capital `I`?

### Introduce the Concept in Isolation

A throwaway project, `Scratch5`, was created fresh in this session's own
scratch directory. An interface, `Greeter`, was declared with one method
signature, and one class, `QuietGreeter`, was written to implement it:

```java
public interface Greeter {
    void greet(String name);
}

public class QuietGreeter implements Greeter {
    public void greet(String name) {
        System.out.println(name);
    }
}

public class Program {
    public static void main(String[] args) {
        Greeter greeter1 = new QuietGreeter();
        greeter1.greet("Ada");
    }
}
```

Compiled and run for real:

```
javac Program.java
java Program
```

Real output:

```
Ada
```

This is exactly what the real `Logger`/`ConsoleLogger` pair above is
doing, isolated: a variable, `greeter1`, is declared with the *interface*
as its type, `Greeter`, not the concrete class — yet it holds a real
`QuietGreeter` object, and calling `.greet("Ada")` through it runs
`QuietGreeter`'s own real code. This proves the concept named in this
lesson's Header: an **interface** describes *what* something can do —
here, "accept a `String name` and `greet` with it" — with no body of its
own at all; an **implementation** — `QuietGreeter` — is what actually
supplies that body.

`Scratch5` is kept alive rather than deleted immediately — the next
concept unit in this lesson still needs it.

### CS Lens

An interface is a concrete example of **programming to an abstraction** —
depending on *what* something can do rather than on any one specific class
that happens to do it:

```
Also recognized in: a wall power outlet accepting any appliance with a
matching plug, a USB port accepting any device that speaks the USB
protocol, a shipping container standard letting any compliant
container be loaded onto any compliant ship or truck, a job posting
describing required skills rather than naming one specific acceptable

```

### SE Lens

The alternative not chosen here is exactly what Lesson 2.4 already left in
place: `Service` depending directly on the concrete `Logger` class. That
alternative is simpler to write, and was entirely appropriate right up
until a second, genuinely different logging behavior became worth having.
The real cost paid here: one extra file, and one extra level of
indirection — `logger.log(...)` now resolves to *whichever* class actually
implements `Logger`, decided at runtime. Worth stating plainly, as its own
real tradeoff, separate from the interface concept itself: Java's own
naming convention — giving the interface the plain name rather than
prefixing it — has a real cost C#'s `I`-prefix convention avoids: renaming
the *old* concrete class becomes mandatory the moment the interface needs
to exist at all, since two declarations can't share one name in the same
package. C#'s `ILogger`/`Logger` pair could, in principle, have kept the
concrete class's name completely untouched; Java's `Logger`/`ConsoleLogger`
pair cannot — the rename this unit performs is not optional the way it
would be under C#'s own convention.

None new — `javac`/`java`, reappearing, used here to confirm an

  as a valid `Logger` implementation at all.
- **`System.out.println("!!!"); System.out.println(message);
  System.out.println("!!!");`** — three separate calls, reappearing from
  Lesson 2.1, run in sequence, producing three separate lines of output
  per call to `log`, in contrast to `ConsoleLogger.log`'s own single call.
