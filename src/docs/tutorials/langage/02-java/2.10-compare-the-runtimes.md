## Terms used in this lesson

- **CLR (Common Language Runtime)** — C#'s own managed runtime, the
  direct counterpart to Java's JVM, named explicitly here for the first
  time in this curriculum even though it's been running every C# example
  since Lesson 1.1: the layer that loads compiled C# assemblies, manages
  memory (including garbage collection), and executes the program.
- **JVM (Java Virtual Machine)** — reappearing, in full, from Lesson 2.1:
  the runtime program executing Java bytecode, either interpreting it
  directly or compiling frequently-run code further, on the fly, into
  native instructions.
- **managed runtime** — the general category both the CLR and the JVM
  belong to: a runtime that manages memory and execution on the running
  program's behalf — allocating objects, reclaiming ones no longer
  reachable, and enforcing safety guarantees like array-bounds and
  `null`-reference checks — as opposed to an unmanaged runtime (C or C++,
  reached later in this curriculum's own Phase 4), where a program
  manages its own memory directly.
- **garbage collection** — the managed runtime's own automatic process for
  reclaiming memory occupied by objects no reference anywhere in the
  running program can reach anymore. Both the CLR and the JVM perform it;
  neither this curriculum's C# Phase nor its Java Phase has ever written
  an explicit `free`, `delete`, or equivalent anywhere in either
  `Service`'s own source.
- **is-a via interface implementation, vs. is-a via class inheritance** —
  reappearing, in full, from C# Lesson 1.12: a precise distinction this
  project's own Java code makes real too — `public class ConsoleLogger
  implements Logger` genuinely is a form of "is-a," but it is *interface*
  implementation, not *class* inheritance. Nowhere in either language's
  version of this project does one class extend another class.
- **composition vs. inheritance** — reappearing, in full, from C# Lesson
  1.12: composition builds a class out of other objects it holds a
  reference to (`Service` has-a `Logger`); inheritance builds a class by
  extending another class's own implementation. This project, in both
  languages, uses the first exclusively.

## Concept Unit: Why Each Abstraction Exists, in Java's Own Terms

### The Problem

A reader who only ever saw this project one lesson at a time might be able

able to say *why* it's shaped that way. Recognizing syntax and
understanding a design are not the same skill.

### The Real Project Change

- **Reference Source:** no reference counterpart — this unit reviews
  reasoning already given, in full, across Lessons 2.1–2.9's own SE Lens
  sections.
- **Files affected:** none.
- **Change type:** none (inspection only).
- **Location:** every SE Lens section in Lessons 2.1 through 2.9.
- **Dependencies:** all of Lessons 2.1 through 2.9.

### Every Abstraction, and the Problem It Actually Solves

- **`class`, entry point, JVM (Lesson 2.1)** — gives behavior an actual
  named home, requiring more ceremony than C#'s own top-level statements
  in exchange for one, fixed, JVM-recognized entry contract instead of a
  compiler-synthesized one.
- **Objects, constructors (Lesson 2.2)** — the identical mechanism C#
  already established, met in Java's own syntax; `javac`'s
  reference-driven compilation, a genuinely different model from C#'s
  own whole-folder globbing, proven real by a class that stayed
  uncompiled until something actually referenced it.
- **Encapsulation, getter methods (Lesson 2.3)** — guarantees `Service`'s
  own state can only change through code allowed to change it, the
  identical goal C#'s own `private` and `property` serve — reached here
  through an ordinary method rather than a dedicated language construct,
  a real, provable cost at every call site (`service.getRunCount()`, not
  `service.RunCount`).
- **Composition, `"has-a"`, constructor injection (Lesson 2.4)** — splits
  `Service`'s unrelated jobs into separate, focused classes, then moves
  responsibility for *creating* the dependency to whatever code
  constructs `Service` — the identical reasoning C# Lesson 1.5/1.6 gave,
  proven here to carry a real, sharper risk: the identical shadowing bug
  produces zero compiler warning in Java, where C# gives three.
- **Interfaces, implementation, polymorphism (Lesson 2.5)** — names *what*
  a dependency can do separately from *which* concrete class does it —
  the only reason the swap from `ConsoleLogger` to `LoudLogger` was
  possible with a real, empty `git diff` proving `Service.java` needed
  zero changes, a genuinely stronger proof than C#'s own version of this
  same lesson.
- **Generics, type erasure (Lesson 2.6)** — lets `LastValue<T>` and
  `Describer.describe` work correctly across multiple types without
  duplication, deliberately built with zero relationship to `Service` or
  `Logger` — and proven, with real disassembled bytecode, to be a
  genuinely different runtime mechanism than C#'s own reified generics,
  not merely different syntax for the identical thing.
- **Exceptions, `throw`/`try`/`catch`, checked vs. unchecked (Lesson
  2.7)** — lets `Service.reset()` refuse an invalid operation while
  leaving the decision of what to do about that refusal to the caller —
  the identical reasoning C# Lesson 1.10 gave — while surfacing a whole
  real category, checked exceptions, that C# has no equivalent of at all.
- **Collection interfaces (Lesson 2.8)** — lets `Service` remember more
  than one thing at once, using the identical interface/implementation
  pattern Lesson 2.5 already established, now recognized inside Java's
  own standard library rather than code this project wrote.
- **Reference semantics (Lesson 2.9)** — not a new capability `Service`
  gained, but a deeper understanding of what its own fields had been
  doing the whole time — one that directly caught and fixed a real,
  live defect (`getHistory()`'s own leaked reference) no earlier lesson
  in either language ever needed to find, because no earlier lesson's own
  code had this exact shape of exposure.

### Composition vs. Inheritance, Answered Directly — Again, in Java

This project uses composition — `Service` has-a `Logger` — everywhere it
needs one class to rely on another. It uses interface implementation —
`ConsoleLogger` is-a `Logger`, `LoudLogger` is-a `Logger` — everywhere it
needs multiple classes to satisfy the same contract. It uses **class
inheritance — one class extending another class's own implementation —
nowhere at all**, the identical fact C# Lesson 1.12 already established
for C#'s own version of this project. `extends` appears exactly nowhere
in this project's own source targeting another concrete class — only
`implements`, targeting an interface. This is the same real,
deliberate design fact in both languages, not a coincidence of porting: a
project this scale never needed one class to inherit another's concrete
implementation to solve any problem it actually had.

## Concept Unit: C# CLR vs. Java JVM — Every Real Divergence, Side by Side

### The Problem

this phase's own nine lessons already found and proved, for real, a long

underneath that identical shape. Nobody has yet gathered that list into
one place.

- **Reference Source:** every real comparison below cites the specific
  lesson, and the specific real evidence, that lesson already produced —
  nothing here is a new claim; every one is a consolidated restatement of
  something already proven with a real compile error, a real
  disassembly, or a real run.
- **Files affected:** none.
- **Change type:** none (inspection only).
- **Location:** every lesson in this phase, and their C# counterparts.
- **Dependencies:** all of Lessons 2.1 through 2.9, and C# Lessons 1.1

### The Comparison, Assembled from What This Phase Already Proved

**CLR vs. JVM, and compilation.** C#'s `Service.csproj` is a required
manifest, without which `dotnet new` produces nothing runnable at all
(Lesson 2.1's own reference source, C# Lesson 1.1). Java needs no
manifest whatsoever — one correctly named `.java` file is already a
complete, buildable unit, proven by a real, empty `javac` success with no
project file anywhere (Lesson 2.1). Underneath that, C#'s SDK compiles
*every* `.cs` file in the project folder unconditionally; Java's `javac`,
given one file, only compiles what it can prove is actually referenced —
proven by a real, empty `Greeter.class`-less directory listing until
`Greeter` was actually referenced (Lesson 2.2). Both `Service.dll` and
`Program.class` are intermediate forms a managed runtime loads and runs,
never raw machine code directly — but the JVM interprets or JIT-compiles
*bytecode*, a real, separate representation `javap` can disassemble
directly (Lesson 2.1's own real `getstatic`/`invokevirtual` evidence),
where the CLR's own comparable intermediate form was never disassembled
in this curriculum's own C# Phase.

**Garbage collection.** Neither this project's C# version nor its Java
version has ever written an explicit deallocation anywhere. Both
`Service()`'s own compiler-supplied constructors — proven real via
`javap` for Java (Lesson 2.1/2.2), cited from the C# language
specification for C# (C# Lesson 1.2) — rely on their own managed runtime
to allocate the object's memory and, eventually, reclaim it once nothing
references it anymore. Neither runtime's own collector was directly
observed running in this curriculum — this is a real, shared property of
both languages' managed model, not a divergence, worth stating plainly as
exactly that: a place these two runtimes agree, not one where they
differ.

**Object references.** C#'s own reference types work identically to
Java's in the one respect both curricula's own Lesson 1.2/2.2-equivalent
already established: assigning one variable to another copies the
reference, not the object. Lesson 2.9 proved this directly for Java, for
the first time in either language's own curriculum, with a real `list2 =
list1; list2.add(...)` mutation visible through both names, and a real
`==` comparison distinguishing identity from `.equals(...)`'s own content
comparison — C# Lesson 1.2 only ever asserted reference semantics in
prose, never proved them with a comparable real test.

**Properties vs. methods.** This is the single sharpest, most concretely
proven divergence this entire phase found. C#'s `property` is real,
dedicated language syntax — `public int RunCount { get { return
runCount; } }` — that keeps field-like call syntax (`service.RunCount`)
at every call site, even once the underlying storage becomes fully
encapsulated. Java has no equivalent construct at all: `Service.
getRunCount()` (Lesson 2.3) is an ordinary method, called with ordinary
parentheses, and Lesson 2.3's own real, tested proof showed the actual
cost this difference imposes — the exact moment `runCount` became
`private`, every caller's own source text had to change, from
`service.runCount` to `service.getRunCount()`, where C#'s own equivalent
lesson proved `Program.cs` never needed to change at all.

**Interfaces.** Both languages support declaring a contract with no
implementation and multiple classes satisfying it — `interface`/`:` in
C#, `interface`/`implements` in Java, proven functionally identical by
real, matching polymorphism demonstrations in both curricula (C# Lesson
1.7, Java Lesson 2.5). The one real, concrete difference this phase
found and proved: naming convention. C#'s own `I` prefix (`ILogger`) lets
the *interface* be named separately from any existing concrete class of
the same root name; Java's real convention gives the *plain* name to the
interface instead (`Logger`, matching `List`/`Map`/`Runnable` in the real
JDK, confirmed via `javap` in Lesson 2.8), which forced this project's
own pre-existing concrete `Logger` class to be renamed `ConsoleLogger` —
a real, structural consequence of the naming convention itself, not an
arbitrary choice, proven in Lesson 2.5.

**Generics.** This phase's own single largest, most thoroughly
disassembly-proven divergence. C#'s generics are **reified** — a real,
distinct runtime type per closed generic instantiation; Java's generics
are **erased** — proven directly, via real `javap` disassembly, that
`LastValue<Integer>` and `LastValue<String>` compile to the identical
`Ljava/lang/Object;`-typed bytecode, and via a real `getClass()`
comparison returning `true` for two differently-parameterized `LastValue`
objects (Lesson 2.6). A direct, real consequence: Java generics cannot be
parameterized with a primitive type at all — a real compile error, `error:
unexpected type ... required: reference, found: int` — where C#'s own
`LastValue<int>` compiled and ran directly, no wrapper type or boxing
required (Lesson 2.6).

**Exceptions.** Both languages share `throw`/`try`/`catch`, working
almost identically at the mechanism level — proven by a near-verbatim
port requiring no structural change at all (Lesson 2.7, C# Lesson 1.10).
The one real, structural divergence this phase found: Java's **checked
exceptions**, a whole real category — any type extending `Exception`
directly rather than `RuntimeException` — that the compiler actively
refuses to let a method throw without either handling it or declaring
`throws`, proven with a real compile error that also, proven separately,
propagates up an entire call chain until something actually handles it.
C# has no such category, and no such compiler enforcement, at all — every
C# exception behaves like Java's *unchecked* half only.

### CS Lens

Two runtimes implementing the identical high-level architectural pattern
while diverging in real, load-bearing ways underneath is itself a real
instance of **implementation-independent specification** — the same
underlying idea that a well-specified interface, protocol, or algorithm
can have multiple, genuinely different correct implementations:

```
Also recognized in: multiple compliant implementations of the same
network protocol (different web browsers all correctly implementing
HTTP), multiple SQL databases all correctly implementing the
relational model with genuinely different query planners underneath,
different countries' electrical grids all delivering usable power at
genuinely different voltages and frequencies
```

### SE Lens

The alternative this comparison implicitly argues against is treating "C#
and Java are basically the same language" as sufficient understanding for
working in either one. This phase's own real, repeated finding says
otherwise: syntax similarity (`class`, `interface`, `<T>`, `try`/`catch`,
