# Lesson 2.8: Remembering More Than One Thing — Collections Appear Naturally

**What you will build.** `Service` gains a new field, `history` — a real,
ordered collection remembering every status message it has ever produced,
not just how many times it ran. `Program.java` then walks that entire
history, printing each message in order, and tallies how many times each
distinct message actually occurred — `"Service is running."` twice,
`"Service has been reset."` once — using a second, genuinely different
kind of collection. This lesson has no C# reference source to port from at
all: Phase 1 never needed a collection, and this curriculum's own
Phase 2 plan says so explicitly. Where every lesson since 2.2 has started
from real, already-written C# code, this one starts from a real, honest
question this project's own growth finally forces: `Service` can currently
tell you *how many* times it ran, but not *what happened*, in order — a
single `int` genuinely cannot hold more than one thing. A **`List`** is
Java's own interface for an ordered, growable sequence of values — the
same interface/implementation split Lesson 2.5 already taught from
scratch, now met again in Java's own real standard library, not a
construct this curriculum wrote by hand. A **`Map`** is Java's own
interface for associating a value with a lookup key, used here to turn a
list of raw messages into a real answer to "how many times did each one
happen." Both are proven, not just described, including one hard
constraint neither `Console`/`System` nor any class this project has
written before ever imposed: `List` and `Map` need to be explicitly
imported before Java will recognize their names at all.

**What you need to know first.** From **Lesson 2.7 — Port Failure
Handling**: the real project at `code/02-java/Service/`, `Service`'s
`run()` and `reset()` methods, both of which this lesson's own new field
hooks into. From **Lesson 2.5 — Port the Interface**: `interface`,
`implementation`, `implements`, and the real, tested fact that Java's own
naming convention gives interfaces their plain name — the same pattern

## Terms used in this lesson

- **`import` statement** — a declaration, placed at the top of a `.java`
  file before any class declaration, naming a specific class or interface
  from another package that this file wants to refer to by its short
  name. This is this curriculum's first Java lesson needing one at all:
  every class used so far — `System`, `String`, `Object` — lives in
  `java.lang`, the one package the JVM makes available in every file
  automatically, with no `import` required. `List` and `Map` live in
  `java.util`, a different package, which is not automatic — proven, in
  this lesson's own isolated lab, with a real compile error when the
  import is left out.
- **`List<T>`** — a real interface in Java's standard library (`java.util.
  List`), naming the contract for an ordered, growable sequence of
  values: values keep the order they were added in, and the same value
  can appear more than once. Confirmed, in this lesson's own real,
  disassembled evidence, to genuinely be declared `public interface
  java.util.List<E>` — the identical kind of declaration this curriculum's
  own Lesson 2.5 taught from scratch for `Logger`, now met again in code
  this project didn't write.
- **`ArrayList<T>`** — a real class in Java's standard library (`java.util.
  ArrayList`), one concrete implementation of the `List` interface,
  backed internally by a resizable array. Confirmed, in this lesson's own
  real, disassembled evidence, to be declared `implements
  java.util.List<E>` — the identical relationship `ConsoleLogger` and
  `LoudLogger` already had to `Logger`.
- **diamond operator (`<>`)** — a real, legal shorthand letting a generic
  constructor's own type argument be inferred from the variable's already-
  declared type, rather than repeated: `List<String> history = new
  ArrayList<>();` infers `ArrayList<String>` from the left-hand side's own
  `List<String>`, without writing `String` a second time. Exists for the
  identical reason `var` does — removing repetition the compiler can
  already resolve on its own — but narrower: `<>` only ever fills in a
  type argument already implied by context, never an entire type the way
  `var` can.
- **`Map<K, V>`** — a real interface in Java's standard library
  (`java.util.Map`), naming the contract for associating each of a set of
  unique keys with exactly one value, and looking that value back up by
  key. Confirmed, in this lesson's own real, disassembled evidence, to
  genuinely be declared `public interface java.util.Map<K, V>`.
- **`HashMap<K, V>`** — a real class in Java's standard library
  (`java.util.HashMap`), one concrete implementation of the `Map`
  interface. Confirmed, in this lesson's own real, disassembled evidence,
  to be declared `implements java.util.Map<K, V>`. Its own iteration
  order is not guaranteed to match insertion order at all — proven, in
  this lesson's own isolated lab, by a real run whose actual printed
  order didn't match the order entries were added in.
- **enhanced for-loop (`for (T x : collection)`)** — a loop form iterating
  over every element of something iterable, in order, without an
  explicit index variable or a manually written stopping condition. This
  is this curriculum's first loop of any kind in Java — the first
  appearance of repeated execution driven by a collection's own contents
  rather than a single, fixed statement sequence.
- **collection interfaces** — the general term this lesson's own
  curriculum title names for the pattern `List` and `Map` both
  instantiate: a standard-library interface describing a general shape of
  data structure, with one or more real classes providing the actual
  storage and behavior behind it — the same interface/implementation
  split this curriculum's own Lesson 2.5 already taught from scratch, now
  recognized as the same real pattern Java's own standard library is
  built out of.
- **field, private, public, class, block (`{ }`), `void`, call syntax
  (`( )`), `var`, `new`, member access (`.`), assignment operator (`=`),
  string literal, semicolon (`;`), `int`** — all reappearing from Lessons
  2.1–2.7, unchanged in meaning, all still present in `Service.java`,
  `Program.java`, and this lesson's isolated lab.

- **`List<T>.add(T)`**
  - *What it is:* the real interface method appending a new element to the

  - *Type:* an interface method, real bodies supplied by whichever
    concrete `List` implementation is actually in use — `ArrayList`,

  - *Responsibility:* grow the collection by exactly one element, at the
    end, preserving every element already present in its original order.
  - *Depends on:* the element being added; an already-constructed `List`
    to call it on.
  - *Connects to:* called by `Service.run()` and `Service.reset()`.
  - *Shape:* the exact seam `Service`'s own internal state grows through
    this lesson.

- **`Map<String, Integer>`**
  - *What it is:* the declared type of a new local variable in
    `Program.main`, tallying how many times each distinct message
    occurred.
  - *Implementation:* `java.util.Map<K, V>`, confirmed via real
    disassembly, below, to be declared `public interface java.util.Map<K,
    V>`.
  - *Its use:* built fresh in `Program.main`, from `service.getHistory()`'s
    own contents, associating each distinct message `String` with an
    `Integer` count.
  - *Type:* an interface — not instantiable on its own.
  - *Responsibility:* declare the contract for key-to-value lookup,
    nothing more.
  - *Depends on:* nothing of its own.
  - *Connects to:* implemented by `HashMap`.
  - *Shape:* a second real collection interface, alongside `List`, proving
    this lesson's own pattern generalizes.

- **`HashMap<String, Integer>`**
  - *What it is:* the real, concrete class actually backing
    `Program.main`'s own `messageCounts` variable.
  - *Implementation:* `java.util.HashMap<K, V>`, confirmed via real
    disassembly, below, to be declared `public class java.util.HashMap<K,
    V> extends java.util.AbstractMap<K, V> implements java.util.Map<K,
    V>, ...`.
  - *Its use:* constructed fresh, empty, then filled by this lesson's own
    third unit.
  - *Type:* a class implementing `Map`.
  - *Responsibility:* actually store the key-value associations, and make
    them retrievable by key.
  - *Depends on:* nothing to construct.
  - *Connects to:* created directly in `Program.main`; filled via
    `getOrDefault`/`put`, read via `get`.
  - *Shape:* one concrete implementation of `Map`.

- **`Map<K, V>.getOrDefault(Object, V)`**
  - *What it is:* a real interface method reading a value by key, with a
    fallback for a key that isn't present yet.
  - *Implementation:* declared on `Map` as `V getOrDefault(Object key, V
    defaultValue)` — returns the value already stored for `key`, or
    `defaultValue` if no entry for `key` exists yet.
  - *Its use:* called once per message in `service.getHistory()`, reading
    that message's own running count so far, defaulting to `0` the first
    time any particular message is seen.
  - *Type:* an interface method.
  - *Responsibility:* avoid forcing the caller to check "does this key
    exist yet?" separately before reading it.
  - *Depends on:* the key being looked up; the fallback value to use if
    it's absent.
  - *Connects to:* called by `Program.main`, inside its own tally loop.
  - *Shape:* one half of the read/write pair this lesson's own tally
    logic is built from.

- **`Map<K, V>.put(K, V)`**
  - *What it is:* a real interface method storing (or replacing) the
    value associated with a key.
  - *Implementation:* declared on `Map` as `V put(K key, V value)`.
  - *Its use:* called once per message, storing that message's own
    updated count — the value `getOrDefault` just read, plus one.
  - *Type:* an interface method.
  - *Responsibility:* associate `key` with `value`, overwriting whatever
    was associated with that key before, if anything.
  - *Depends on:* the key and value being stored.
  - *Connects to:* called by `Program.main`.
  - *Shape:* the other half of the read/write pair this lesson's tally
    logic is built from.

- **`Map<K, V>.get(Object)`**
  - *What it is:* a real interface method reading a value by key, with no
    fallback.
  - *Implementation:* declared on `Map` as `V get(Object key)` — returns
    `null` if `key` has no entry, rather than a supplied default.
  - *Its use:* called twice at the very end of `Program.main`, reading
    back the two final tallies to print them.
  - *Type:* an interface method.
  - *Responsibility:* hand back whatever value is currently associated
    with `key`.
  - *Depends on:* the key being looked up.
  - *Connects to:* called by `Program.main`.
  - *Shape:* the simplest possible read from this lesson's own finished
    tally.

## Concept Unit: The `List` — Remembering Every Message, in Order

### The Problem

`Service.getRunCount()` can say *how many* times `run()` has executed, but
not *what actually happened*, in the order it happened. A single `int`
genuinely cannot hold more than one value at once — this project has never
needed to remember a whole sequence of anything before. If `Service`
needs to answer "what messages have you actually produced, in order?",
where does that answer live?

> **Stop and think, before reading on:** in Python, you'd just write
> `self.history = []` and call `self.history.append(message)` — no import,
> no type declared anywhere, and a Python `list` can already hold any
> number of items of any type. Given that every type this Java project
> has used so far — `String`, `Service`, `Logger` — needed no special
> declaration beyond its own name to use, what do you predict happens if
> a Java program tries to use `List` the exact same way, with nothing
> special done first? And given `String`, `System`, and `Object` have
> never needed anything like Python's own `import` statement anywhere in
> this curriculum's Java code, what do you predict is different about
> `List` specifically?

### The Real Project Change

- **Reference Source:** no reference counterpart — Phase 1 (C#) never
  needed a collection anywhere in its own twelve lessons; this is a
  genuinely new, from-scratch Java addition, matching this curriculum's
  own Phase 2 plan, which lists 2.8 as new content, not a port.
- **Files affected:** modified — `code/02-java/Service/Service.java`.
- **Change type:** add.
- **Location:** two new `import` lines at the top of the file; a new
  field inside `Service`'s block; one new statement each inside `run()`
  and `reset()`; a new getter method.
- **Dependencies:** `Service`'s existing `run()` and `reset()` methods

A `List` is a concrete instance of an **ordered, repeatable-element

just Java's own `List`:

```
Also recognized in: Python's own list, a shopping list where the
```

### SE Lens

The alternative not chosen here is exactly what `Service` already had:
tracking only a single `int` count, with no memory of individual events at
all. That alternative is cheaper — one field, no import, no collection —
and was entirely sufficient for every lesson up to this one. It stops
being sufficient the moment a real question needs an actual sequence of
past events, not just a tally: "what happened, and in what order?" has no
honest answer a bare `int` can ever give. The real cost paid here,
worth stating honestly: an unbounded `List`, growing by one element every
successful `run()` or `reset()`, holds onto memory for as long as the
`Service` object itself exists, with nothing in this lesson's own code
ever removing an old entry — a real, permanent memory cost this project's
own tiny scale never makes matter, but a genuine design question any real,
long-running service would eventually have to answer.

## Concept Unit: Iteration — The Enhanced For-Loop

### The Problem

`history` is being recorded correctly, but nothing has ever read it back.
This project has never needed a loop of any kind before — every method
call so far has run exactly once, in a fixed sequence `Program.main`
itself writes out line by line. Printing every message in `history`,
whatever its actual length turns out to be, can't be written as a fixed
sequence of individual `System.out.println` calls — the number of
messages isn't even known until the program actually runs.

> **Stop and think, before reading on:** you already know Python's `for
> message in history:`. Given that every construct in this project's Java
> code so far has needed explicit parentheses and braces where Python
> uses a colon and indentation, what do you predict Java's own loop over
> a `List`'s contents looks like? And given `List<String>`'s own type
> parameter already tells you every element is a `String`, what do you
> expect a Java loop needs to state explicitly about each element that
> Python's own `for` loop never has to?

### The Real Project Change

- **Reference Source:** no reference counterpart.
- **Files affected:** modified — `code/02-java/Service/Program.java`.
- **Change type:** add.
- **Location:** the end of `main`, after the existing `try`/`catch`
  block from Lesson 2.7.
- **Dependencies:** `Service.getHistory()`, from the previous unit.

  (reappearing) producing the `List<String>` actually being iterated.
  Unlike Python's `for message in history:`, which never states a type
  anywhere, Java requires `message`'s own type to be declared explicitly
  — here, `String`, matching `List<String>`'s own type argument exactly.
- **`{` ... `}` (the loop body)** — a block, reappearing, run once per
  element, with `message` bound to a different element each time.
- **`System.out.println(message);`** — reappearing, printing whichever
  element `message` is currently bound to.

### CS Lens

Iterating a collection's own contents, one element at a time, in order,
is a real instance of the **iterator pattern**:

```
Also recognized in: a playlist advancing to the next track without
needing to know how many tracks exist in total, a book's own table
of contents letting a reader visit each chapter in order without
memorizing page numbers ahead of time, a factory assembly line
processing each item that arrives without knowing in advance how many
items the shift will produce
```

### SE Lens

The alternative not chosen here is a manually indexed loop — a counter
variable, an explicit stopping condition checked against `history`'s own
size, and `history.get(i)` to reach each element by position. That
alternative genuinely works, and Java fully supports writing it that way.
The enhanced for-loop used here trades that explicit control away for
real, permanent safety: there's no index variable to get wrong, no
off-by-one boundary to miscalculate, and no way to accidentally skip or
repeat an element through a mistake in the loop's own bookkeeping. The
real cost: an enhanced for-loop alone gives no access to each element's
own position, which this lesson's own printing job never needed but a
different task legitimately might.

## Concept Unit: The `Map` — Tallying What Happened

### The Problem

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`Map<String, Integer>`** — the declared type: `Map`, the interface;
  `<String, Integer>`, two generic type arguments — reappearing from
  Lesson 2.6, but this project's first use of a type taking *two*
  parameters at once, `K` (the key type) and `V` (the value type),
  `String` and `Integer` respectively here. `Integer`, not `int` — the
  identical wrapper-type requirement Lesson 2.6 already proved for
  `LastValue<T>`; a `Map`'s own value type is a generic type parameter
  too, and generic type parameters can never be primitives.
- **`new HashMap<>()`** — `new` (reappearing), constructing a real
  `HashMap`, with the diamond operator inferring `<String, Integer>` from
  the left-hand side's own declared type.
- **`messageCounts.getOrDefault(message, 0)`** — member access
  (reappearing), calling `getOrDefault` with two arguments: the key to
  look up, and the fallback value to use if that key has no entry yet.
- **`int current = ...;`** — a local variable declaration (reappearing
  from Lesson 2.4), holding this iteration's own running count.
- **`messageCounts.put(message, current + 1);`** — member access,
  calling `put` with two arguments: the key, and its new value — the
  count just read, plus one, using the arithmetic addition operator
  reappearing from Lesson 2.3.
- **`messageCounts.get("Service is running.")`** — member access, this
  time calling `get`, which takes only a key and returns whatever value
  is currently stored for it.

### CS Lens

A `Map` is a concrete instance of **associative lookup** — retrieving a
value by a meaningful key rather than by position:

```
Also recognized in: a phone book looking up a number by name rather

a coat check retrieving a specific coat by the ticket number given for
it, a spreadsheet's VLOOKUP finding a row by a matching key column
```

### SE Lens

The alternative not chosen here is doing this same tally using two
parallel `List`s — one of distinct messages seen so far, one of matching
counts — and manually searching the first list for a message's own
position before updating the second. That alternative works, but every
single lookup costs real, linearly growing search time as the list of
distinct messages grows, and keeping the two lists in sync by hand is a
real, ongoing source of bugs a `Map` removes by design: one structure,
one key, one associated value, always in sync by construction. The real
cost paid in exchange, honestly stated: a `HashMap` gives up any ordering
guarantee at all, proven directly by this unit's own real, out-of-order
output — a real tradeoff against `List`'s own guaranteed order, not a
free upgrade.
