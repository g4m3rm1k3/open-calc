# Lesson 2.4: Who Creates the Dependency — Port Composition

**What you will build.** `Service`'s reporting job moves out into a new
class, `Logger`, exactly as C# Lesson 1.5 did — `Service` now *has-a*
`Logger` instead of printing directly. Then, exactly as C# Lesson 1.6 did,
that relationship gets rebuilt again: instead of `Service` constructing its
own `Logger` internally, `Service` receives one from outside, through its
constructor — this curriculum's first hand-written Java constructor. Along
the way, this lesson's first working attempt at that constructor contains
the identical real bug C# Lesson 1.6 hit — naming the parameter and the
field it's meant to fill identically — and Java's own version of that bug
turns out to be *more* dangerous than C#'s: it compiles with zero warnings
at all, not three, and only reveals itself as a real, unhandled
`NullPointerException` once the program actually runs. This lesson ports
two C# lessons at once, the same combining move Lesson 2.3 already made,
because Java's constructor mechanics, `this` keyword, and shadowing rule
turn out to be close enough to C#'s that splitting them across two lessons
would mean re-explaining the same handful of Java rules twice. A
**dependency** is any object another object needs to do its job;
**composition** is building a class out of other objects it relies on
rather than doing every job itself; the **"has-a"** relationship is that
reliance's specific shape; **constructor injection** is supplying a
dependency through the constructor rather than the object creating it
itself; and **`this`** is the keyword that makes injection safe the moment
a parameter and a field share a name.

**What you need to know first.** From **Lesson 2.3 — Port Encapsulated
State**: the real project at `code/02-java/Service/`, `Service`'s private
`runCount` field and public `getRunCount()` accessor, `private`, `public`,
encapsulation, and this curriculum's first real Java compile-time errors.
From **Lesson 2.2**: `class`, `object`, `instance`, `method`, `constructor`
(specifically, the *compiler-supplied default* constructor every class in
this project has relied on until now), `new`, `var`, member access (`.`),
the assignment operator (`=`). From **Lesson 2.1**: `System.out.println`,
`javac`/`java`. From **C# Lesson 1.5 — One Class, One Job** and **C#
Lesson 1.6 — Who Creates the Dependency**, this lesson's own reference
source: the same concepts named above, and the exact reference code being
ported, read fresh this session from `code/01-csharp/Service/` at git
commits `d29e808` (1.5's close) and `246dc7e` (1.6's close) — not the
project's current, further-evolved files. From the curriculum's own stated
assumptions: enough basic Python object-oriented experience to already
know what inheritance is, and to have written `def __init__(self, name):
self.name = name` — leaned on here only to contrast with what Java does
differently, particularly Python's mandatory, explicit `self` against
Java's implicit `this`.

## Terms used in this lesson

- **responsibility** — the specific job or set of related jobs a class is
  actually in charge of; the reason that class exists at all. The same
  underlying idea C# Lesson 1.5 named; Java's own version of the same
  problem — `Service` currently doing both counting and reporting inline —
  gets the identical treatment here.
- **composition** — building a class out of other objects it relies on to
  do part of its job, rather than trying to do every job itself. A hard
  concept, per the Repetition Rule getting full CS Lens treatment below
  rather than a one-line definition — the identical principle C# Lesson
  1.5 named, met here in Java's own syntax.
- **"has-a" relationship** — the specific shape composition takes: object
  A holds a reference to object B as one of its own members. Contrasts
  with an **"is-a" relationship** (inheritance) — already familiar from the
  curriculum's own Python assumptions. This lesson's own Java code uses
  "has-a" exclusively, exactly as C# Lesson 1.5 did.
- **collaborator** — a general term for an object another object depends
  on to do part of its own job. `Logger` is this lesson's own new
  collaborator for `Service` — the direct Java counterpart to C# Lesson
  1.5's own `Logger`.
- **field initializer (Java)** — an expression written directly at a
  field's own declaration, assigning it a starting value the moment its
  object is constructed, before that object's own constructor body ever
  runs. The identical underlying mechanism C# Lesson 1.5 named for C#'s own
  field initializers, met here in Java's identical syntax:
  `private Logger logger = new Logger();` is this lesson's first use of
  one — every field this project has declared before this lesson
  (`runCount`) relied on its type's own default value, `0`, instead.
- **dependency** — any object another object needs in order to do its job,
  that it does not — and, per this lesson's second half, should not —
  create for itself. The identical idea C# Lesson 1.6 named; `Logger` is
  `Service`'s dependency.
- **constructor injection** — supplying an object's dependency by passing
  it as a constructor argument, rather than the object constructing that
  dependency internally. A hard concept, getting full CS Lens treatment
  below — the identical technique C# Lesson 1.6 named, ported here into
  Java's own constructor syntax.
- **dependency inversion** — the underlying design principle constructor
  injection applies: instead of a class depending on *and* being
  responsible for creating its own dependencies, that responsibility is
  inverted, handed to whatever code creates the class. The identical
  principle C# Lesson 1.6 named.
- **constructor parameter (Java)** — a named placeholder a constructor
  declares for information it needs handed in, written inside its
  declaration's parentheses — the same general idea as a method parameter,
  now applied to a Java constructor for the first time in this curriculum.
- **`this` (Java)** — a keyword, usable inside any instance method or
  constructor, referring to the specific object that method or constructor
  is currently running on. The identical underlying idea C# Lesson 1.6
  named for C#'s own `this` — proven, in this lesson, to work identically
  in Java, resolving the identical shadowing problem the identical way.
- **shadowing (Java)** — when a parameter or local variable's name is
  identical to a field's name, making the field temporarily unreachable by
  its own bare name inside that scope. The identical rule C# Lesson 1.6
  named; Java's own scoping rules resolve names the identical way.
- **compile-time error, compiler warning** — reappearing from Lesson 2.3:
  an error stops the build; a warning doesn't. This lesson's own buggy
  constructor produces **zero** of either — a genuinely different, more
  dangerous outcome than C# Lesson 1.6's three real warnings, proven for
  real in this lesson's third unit.
- **runtime error** — an error only discovered while a program is actually
  executing, contrasted with a compile-time error, caught before a program
  ever runs. This lesson's own `NullPointerException` is this Java
  curriculum's first runtime error.
- **exception, unhandled exception** — an exception is an object
  representing something that went wrong while a program was running,
  thrown by code that detects the problem. "Unhandled" means nothing in
  the program catches it, so the JVM's own default behavior takes over:
  printing a description of what went wrong, plus a stack trace, and
  ending the program immediately.
- **`NullPointerException`** — the specific exception the JVM throws when
  code tries to call a method or access a member *through* a reference
  that doesn't actually point to any object — Java's own name for the
  identical situation C# calls a `NullReferenceException`. Since Java 14,
  a `NullPointerException`'s own message names the exact null expression
  responsible — proven for real in this lesson, a genuinely more specific
  default message than C#'s own generic "Object reference not set to an
  instance of an object."
- **stack trace (Java)** — the ordered list of method calls active at the
  moment an unhandled exception occurred, printed as part of its own
  default output. The identical underlying idea C# Lesson 1.6 named for
  C#'s own stack traces.
- **`String.valueOf(Object)` and `null` text conversion** — a real, tested
  Java-specific fact this lesson's own isolated lab surfaces: printing a
  `null` `String` through `println(String)` prints the literal four-
  character text `null`, not a blank line — genuinely different from C#'s
  `Console.WriteLine(null)`, which prints only a blank line. Named here as
  its own term because it's a real, observable divergence, not merely
  incidental to the lesson's main subject.
- **parameter, argument** — reappearing from Lesson 2.1 (`main`'s own
  `args` parameter): still a named placeholder a member declares for
  information from outside, and the actual value supplied to fill it.
- **field, private, class, block (`{ }`), `void`, call syntax (`( )`),
  `var`, `new`, member access (`.`), assignment operator (`=`), string
  literal, semicolon (`;`), `int`, `public`** — all reappearing from
  Lessons 2.1–2.3, unchanged in meaning, all still present in
  `Service.java`, `Logger.java`, `Program.java`, and this lesson's
  isolated lab.

## Objects and methods used

- **`Service`**
  - *What it is:* this project's own class, now genuinely decoupled from
    how its own dependency gets created.
  - *Implementation:* by this lesson's end, `public class Service {
    private int runCount; private Logger logger; public Service(Logger
    logger) { this.logger = logger; } public int getRunCount() { return
    runCount; } public void run() { runCount = runCount + 1;
    logger.log("Service is running."); } }`, in
    `code/02-java/Service/Service.java`.
  - *Its use:* now requires a `Logger` to be handed in at construction —
    `new Service()` alone, which worked in every previous lesson, no
    longer compiles at all, since this class now declares a constructor
    requiring an argument.
  - *Type:* a class — unchanged.
  - *Responsibility:* unchanged from Lesson 2.3 — running and counting its
    own runs. New this lesson: no longer responsible for *creating* its
    own `Logger`, only for using whichever one it's given.
  - *Depends on:* a `Logger` object, supplied at construction — for the
    first time, a real, explicit constructor argument.
  - *Connects to:* created by `Program.main`, which must now also create
    the `Logger` it hands over; internally calls `logger.log` from
    `run()`.
  - *Shape:* unchanged as this project's first internal building block —
    now wired to its collaborator from outside rather than wiring itself.

- **`Service.run()`**
  - *What it is:* the instance method holding this project's core
    behavior.
  - *Implementation:* `public void run() { runCount = runCount + 1;
    logger.log("Service is running."); }` — character-for-character
    identical to Lesson 2.3's version except calling `logger.log` in place
    of `System.out.println` directly.
  - *Its use:* updates the count, then reports through whichever `Logger`
    this specific `Service` was constructed with.
  - *Type:* an instance method — unchanged.
  - *Responsibility:* update `runCount`, then produce the status report by
    delegating to `logger`.
  - *Depends on:* an already-constructed `Service` object whose `logger`
    field is genuinely set (this lesson's whole point); `Logger`, to
    report.
  - *Connects to:* called by `Program.main`, twice; reads and writes
    `runCount`; calls `logger.log`, the specific `Logger` object passed in
    at construction.
  - *Shape:* unchanged — an internal implementation detail.

- **`Service(Logger)` — the constructor**
  - *What it is:* this lesson's own new class member, and this entire Java
    curriculum's first explicitly hand-written constructor.
  - *Implementation:* `public Service(Logger logger) { this.logger =
    logger; }` — a `public` instance constructor, declaring one
    constructor parameter, `logger`, of type `Logger`.
  - *Its use:* runs the moment `new Service(logger)` executes in
    `Program.main`, storing the `Logger` handed in so `run()` can reach it
    later.
  - *Type:* an instance constructor — a special method sharing its class's
    exact name, with no return type at all, not even `void`.
  - *Responsibility:* accept a `Logger` from whatever code is constructing
    this `Service`, and store it on the object so every later call to
    `run()` can reach it — nothing more.
  - *Depends on:* a `Logger` object, supplied as an argument.
  - *Connects to:* called directly by `Program.main`'s `new Service(logger)`
    expression; assigns its own `logger` parameter to `this.logger`.
  - *Shape:* the exact seam this lesson is about — where a dependency
    crosses from outside code into this object's own internal state, once,
    at construction.

  One consequence of this constructor's existence, worth stating plainly:
  because `Service` now declares a constructor of its own, `javac` no
  longer supplies the parameterless default constructor Lessons 2.1
  through 2.3 relied on — per the same rule already proven, real, for
  `Program` and `Service` in Lesson 2.2, a class only receives one
  automatically when it declares *none* of its own. `new Service()`, which
  compiled in every previous lesson, no longer compiles at all;
  `new Service(logger)` is now the only way to construct one.

- **`Logger`**
  - *What it is:* this lesson's own new class — the collaborator `Service`
    relies on to report its status — the direct Java counterpart to C#
    Lesson 1.5's own `Logger`.
  - *Implementation:* `public class Logger { public void log(String
    message) { System.out.println(message); } }` — a new file,
    `code/02-java/Service/Logger.java`. No fields, no explicit
    constructor.
  - *Its use:* gives this project a single, focused place responsible for
    turning a message into visible output.
  - *Type:* a class — instantiable, exactly like `Service`.
  - *Responsibility:* accept a message and make it visible, via
    `System.out`. Nothing about counting or running is any part of this
    class's job.
  - *Depends on:* nothing to construct.
  - *Connects to:* created once, by `Program.main`, and handed to
    `Service`'s constructor — a single shared object, not two independent
    ones.
  - *Shape:* a second internal building block, deliberately designed with
    no dependency on `Service` at all — proven, this lesson, by using it
    completely independently.

- **`Logger.log(String)`**
  - *What it is:* the one method this lesson's new class exists to
    provide.
  - *Implementation:* `public void log(String message) {
    System.out.println(message); }` — a `public`, non-`static` instance
    method, returning `void`, taking one `String` parameter.
  - *Its use:* called by `Service.run()` in place of a direct
    `System.out.println` call, and, from this lesson's second unit
    onward, called directly by `Program.main` on that exact same shared
    object.
  - *Type:* an instance method.
  - *Responsibility:* forward its `message` argument to
    `System.out.println`, unchanged — this method's entire job.
  - *Depends on:* an already-constructed `Logger` object (though, since
    `Logger` has no fields, any two `Logger` objects behave identically);
    the `message` string; `System.out`.
  - *Connects to:* called by `Service.run()` on `Service`'s own injected
    `logger`; called directly by `Program.main` on that same object; calls
    `System.out.println` in turn.
  - *Shape:* a small, focused public API surface — this project's own
    second class exposing exactly one thing.

- **`Logger()` — the compiler-supplied default constructor**
  - *What it is:* reappearing, applied to a second class this time: the
    same mechanism Lessons 2.1–2.3 already established for `Program` and
    `Service`, now equally true for `Logger`.
  - *Implementation:* not written anywhere in `Logger.java`'s own source;
    per the Java Language Specification, automatically supplied.
  - *Its use:* runs every time `new Logger()` executes — once inside
    `Service`'s own field initializer in this lesson's first unit, and, in
    this lesson's second unit, once more, completely separately, inside
    `Program.main`'s own standalone `Logger` creation.
  - *Type:* an instance constructor.
  - *Responsibility:* letting a `Logger` object come into existence,
    nothing more.
  - *Depends on:* nothing.
  - *Connects to:* called by `Service`'s field initializer (first unit),
    and later by `Program.main` directly (second unit onward).
  - *Shape:* a real, compiled member absent from `Logger.java`'s own
    source text.

- **`System`, `System.out`, `PrintStream.println(String)`** — all
  reappearing unchanged from Lessons 2.1–2.3, now called from inside
  `Logger.log` rather than directly from `Service.run()` or `main`.

### Everything else in the file, not this lesson's subject but still explained

- **`String`** — Java's standard library text class, unchanged from
  Lessons 2.1–2.3; this lesson's own new code passes real, non-literal
  `String` values into `Logger.log` for the first time, rather than a

## Concept Unit: Composition — Giving Service a Collaborator

### The Problem

Look at `Service.run()`, exactly as Lesson 2.3 left it: `runCount =
runCount + 1; System.out.println("Service is running.");`. The first
statement updates a count — pure bookkeeping. The second produces a
human-readable report — pure output. These are two genuinely different
jobs, written inline, in the same method, as if they were naturally one
thing.

> **Stop and think, before reading on:** `Service.run()` already relies on
> `System` — a class this project didn't write, that `Service` reaches out
> to whenever it needs to print something. Given that `Service` already
> trusts an entirely separate class to handle the mechanics of writing to
> the terminal, why would `Service` need to contain its *own*
> status-reporting logic at all, rather than relying on some other
> object — one this project *does* write, this time — the same way it
> already relies on `System`?

### The Real Project Change

- **Reference Source:** `code/01-csharp/Service/Service.cs` and
  `Logger.cs` at commit `d29e808` — C# Lesson 1.5's own closing state,
  read fresh via `git show d29e808:Service.cs` / `git show
  d29e808:Logger.cs`:
  ```csharp
  public class Service
  {
      private int runCount;
      private Logger logger = new Logger();

      public int RunCount
      {
          get { return runCount; }
      }

      public void Run()
      {
          runCount = runCount + 1;
          logger.Log("Service is running.");
      }
  }
  ```
  ```csharp
  public class Logger
  {
      public void Log(string message)
      {
          Console.WriteLine(message);
      }
  }
  ```
  This unit ports this exact shape, adapting only the method name to
  Java's own camelCase convention: `Log` becomes `log`, the identical
  naming adaptation Lesson 2.2 already made for `Run`/`run`.
- **Files affected:** created — `code/02-java/Service/Logger.java`;
  modified — `code/02-java/Service/Service.java`.
- **Change type:** add (a new class) and replace (`run()`'s second
  statement, plus a new field).
- **Location:** a new file alongside `Program.java`, `Service.java`; inside
  `Service`'s block, a new field alongside `runCount`, one changed line
  inside `run()`.
- **Dependencies:** the `Service` class and `runCount` field from Lesson
  2.3.

### Introduce the Concept in Isolation

A throwaway project, `Scratch4`, was created fresh in this session's own
scratch directory. A `Greeter` class was given a `Printer` collaborator,
the same shape as `Service` and `Logger`, and `Printer` was given an
explicit constructor with its own print statement, purely to make an
otherwise invisible moment observable:

```java
public class Printer {
    public Printer() {
        System.out.println("Printer constructed.");
    }

    public void print(String message) {
        System.out.println(message);
    }
}

public class Greeter {
    private Printer printer = new Printer();

    public void sayHello() {
        printer.print("Hello from Greeter.");
    }
}

public class Program {
    public static void main(String[] args) {
        Greeter greeter = new Greeter();
        System.out.println("Greeter object created.");
        greeter.sayHello();
    }
}
```

Compiled and run for real:

```
javac Program.java
java Program
```

Real output:

```
Printer constructed.
Greeter object created.
Hello from Greeter.
```

`Printer constructed.` prints *first* — before `Greeter object created.`,
sitting on the very next line of `Program.java`, right after `new
Greeter()`. This proves the concept named in this lesson's Header: a
**field initializer** — `private Printer printer = new Printer();` — runs
as part of constructing the *outer* object, before control returns to
whatever called `new Greeter()`. This is exactly what `Service`'s own
`private Logger logger = new Logger();` does: the moment `new Service()`
runs, a real `Logger` comes into existence too, automatically. And `Hello
from Greeter.` prints only once `sayHello()` runs, through
`printer.print(...)`, not through any direct call to `System.out` inside
`Greeter` at all — this is the concept named in this lesson's title:
`Greeter` **has-a** `Printer`, exactly the same shape as `Service` **has-a**
`Logger`.

`Scratch4` is kept alive — the next three concept units in this lesson all
still need it.

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`private Logger logger = new Logger();`** — a field declaration
  (`private`, reappearing; `Logger`, this field's declared type; `logger`,
  its name) followed immediately by a **field initializer**: `= new

  declaration, rather than leaving it at a type-specific default the way

- **`logger.log("Service is running.");`** — member access (`.`),

### CS Lens

Composition — building `Service` out of a `Logger` it relies on rather than
doing every job itself — is a real, named design principle:

```
Also recognized in: a car built from an engine, a transmission, and a
braking system rather than one undivided machine, a restaurant
kitchen organized into separate stations each responsible for one
part of a meal, an orchestra where each section plays its own part,
a computer built from a CPU, RAM, and storage as separate,
replaceable components
```

### SE Lens

The alternative not chosen is exactly what Lessons 2.1 through 2.3 already
built: all of `Service`'s behavior written directly inside `Service`
itself. That alternative isn't wrong for a class this small; it stops
being fine the moment either job grows — logging to a file instead of the
console, or formatting messages with timestamps, would otherwise have to
happen *inside* `Service`, risking breaking the counting logic every time,
simply because nothing kept them apart. Composition pays a real,
immediate cost for that future safety: a whole second file, a field, a
field initializer, and one extra method call, all to accomplish exactly
what one inline `System.out.println` already did.

None new — `javac`/`java`, reappearing, run here against `Scratch4` to
observe the real order two separate constructors actually run in.

## Concept Unit: Responsibility Boundaries — Proving the Split Is Real

### The Problem

`Logger` now exists as its own class, in its own file. But moving code
into a separate class doesn't, by itself, prove that class is genuinely
independent. Is `Logger` actually reusable, or does it just look that way
because nothing has tried to use it any other way yet?

> **Stop and think, before reading on:** `Logger` declares no fields, no
> constructor, and no method that mentions `Service` anywhere in its own
> source. Given what you already know about `new` — that any code able to
> see a class can create its own, completely separate instance of it —
> what do you predict happens if `Program.java` created a `Logger` of its
> own, with no `Service` involved at all?

## Concept Unit: The Constructor Parameter — Where the Bug Hides

### The Problem

`Service` currently builds its own `Logger` via a field initializer —
nothing outside `Service` gets any say in that. To let a caller supply a
specific `Logger` instead, `Service` needs to actually *accept* one from
outside. Nothing in this Java curriculum has ever written a constructor
with a parameter before — every constructor so far has been the
compiler's own silent, empty, parameterless one.

> **Stop and think, before reading on:** you already know Python's `def
> __init__(self, name): self.name = name`. Given that Java's field is
> simply named `logger` with no required prefix at its own declaration
> (`private Logger logger;`), and a constructor parameter can be named
> anything at all, what do you predict happens if the constructor's own
> parameter is *also* just named `logger`, with nothing distinguishing it
> from the field? And given that Java's `javac` has already shown you real
> warnings for real mistakes (Lesson 2.3's own `private`-access errors), do
> you expect it to warn about this one too?

This proves the concept named in this lesson's Header: **shadowing**.
`printer = printer;` inside the constructor reads as "assign the parameter

field never gets touched, keeps its **default field value** for an object
reference — `null` — and the moment `sayHello()` tries to call

unhandled **`NullPointerException`**: this Java curriculum's first
**runtime error**. Its own message — `Cannot invoke "Printer.print(String)"
because "this.printer" is null` — names the exact null expression
responsible, a genuinely more specific default message than C#'s own
generic `Object reference not set to an instance of an object.`; Java has
supplied this level of detail in its default exception messages since Java
14. The **stack trace** beneath it names `Greeter.sayHello` first — where
the failure actually happened — then `Program.main`, the exact method
Lesson 2.1 already proved is this program's own entry point.

internally converts its argument through `String.valueOf(...)`, and

## Concept Unit: `this` — Completing the Injection

### The Problem

`logger`, inside `Service`'s own constructor, refers to the parameter, not
the field — proven, in the previous unit, by a real crash. Some way is
needed to say, unambiguously, "the field belonging to *this specific
object*," distinct from whatever local name happens to be sitting closer
in scope.

> **Stop and think, before reading on:** Python's `self` is a parameter
> you write out yourself, explicitly, as the first argument of every
> instance method. Given that Java instance methods and constructors never
> declare anything like that as an explicit parameter anywhere in this
> curriculum's code so far — no `self` has ever appeared in a `run()` or
> `log()` signature — do you predict Java has no equivalent concept at
> all, or one that's simply implicit, surfacing only when actually needed
> to resolve an ambiguity like this lesson's own?

### CS Lens

`this` is a concrete instance of **self-reference** — a running piece of
code having a way to refer to the specific object it's currently acting
on:

```
Also recognized in: Python's explicit self parameter, C#'s and C++'s
own this keyword, Kotlin's this, JavaScript's (more context-dependent)
this, a person filling out a form referring to "myself" rather than
repeating their own full name every time
```

### SE Lens

Python's alternative — an explicit `self` parameter, written out by hand
on every single instance method — was not chosen for Java, the same
choice C# already made. The tradeoff: Python's version is always visible,
right there in every method signature; Java's version stays out of the
way until a genuine ambiguity forces it to be written down. The real cost
of that choice, demonstrated directly by this lesson's own bug, and made
sharper by this lesson's own finding that Java's compiler gives zero
warning about it: because `this` is implicit rather than mandatory, it's
possible to write a constructor that *looks* complete without it,
compiles cleanly, and is silently or catastrophically wrong. Completing
this fix also completes this lesson's own larger point: `Logger` now
genuinely arrives from *outside* `Service`, via **constructor injection**,
rather than `Service` deciding for itself how to make one — **dependency
inversion**, made concrete. The real, provable benefit, visible in the
finished `Program.java`: this program now needs exactly one `Logger`, not
two, because the same object created once can be handed to `Service` *and*
used directly — something the previous lesson's design, `Service` quietly
building its own, could never have allowed.
