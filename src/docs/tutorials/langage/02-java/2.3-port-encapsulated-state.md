# Lesson 2.3: What an Object Remembers, and Who's Allowed to Change It — Port Encapsulated State

**What you will build.** `Service` gains real, per-object memory — a
`runCount` field counting how many times `run()` has been called — and then
that memory gets locked down: the field becomes `private`, and a public
`getRunCount()` method becomes the only way anything outside `Service` can
read it. `Program.java` ends up calling `service.run()` twice, then printing
`service.getRunCount()`, and gets `2` — proof the object remembered
something across two separate calls, and that nothing outside `Service` can
corrupt that memory directly. This lesson ports two C# lessons at once —
Lesson 1.3 (giving `Service` its first field) and Lesson 1.4 (encapsulating
it) — because Java's own answer to "controlled access to data" turns out to
be simple enough, and different enough from C#'s, that splitting it across
two separate lessons the way C# did would mean explaining the same Java
mechanism twice. A **field** is where an object's memory actually lives; a
field's current values are its **object state**; a **field**, like a
method, is an **instance member**, separate per object. **Encapsulation** is
the principle of bundling data with the only code allowed to change it;
`private` is Java's real, compiler-enforced way of shutting every other path
off. And where C#'s answer to "let outside code read, but not write" was a
dedicated language construct — a **property** — Java has no such construct
at all: its real, idiomatic answer is an ordinary method, conventionally
named `getX()`, and that difference is this lesson's own genuinely new
subject, not a detail to gloss past.

**What you need to know first.** From **Lesson 2.2 — Port the C# Class**:
the real project at `code/02-java/Service/`, its `Service` class and `run()`
method, `class`, `object`, `instance`, `method`, `constructor`, `new`, `var`,
local variables, object references, member access (`.`), the assignment
operator (`=`), and the access modifier `public` — all reused directly here
and, per the Repetition Rule below, explained again in full. From **Lesson
2.1**: `System`, `System.out`, `PrintStream.println`, and the `javac`/`java`
cycle, including real, disassembled-bytecode proof of how the JVM's default
field values and object construction actually work. From **C# Lesson 1.3 —
What an Object Remembers** and **C# Lesson 1.4 — Encapsulate the State**,
this lesson's own reference source: the same concepts named above, and the
exact reference code being ported, read fresh this session from
`code/01-csharp/Service/` at git commits `dc2af54` (Lesson 1.3's close) and
`fd69518` (Lesson 1.4's close) — not the project's current, further-evolved

## Terms used in this lesson

- **field (Java)** — a variable declared directly inside a class's own body,
  not inside any method, representing a piece of data every object made
  from that class will carry. The same underlying idea C# Lesson 1.3 named
  for C#'s own fields, met here in Java's identical declaration syntax — a
  type, a name, a semicolon, sitting at the class level rather than inside
  a method.
- **object state** — the actual, current values every one of an object's
  fields happens to hold at a given moment. The class only says *that* a
  field exists and what type it is; a specific object's state is whatever
  value that field actually holds on that one object, right now.
- **instance member** — anything declared inside a class that belongs to a
  particular object rather than to the class as a whole: an instance field
  (this lesson's subject) or a non-`static` method (`run()`, from Lesson
  2.2) are both instance members, contrasted with a `static` member, which
  belongs to the class itself with no object needed — `main`, reappearing
  from Lesson 2.1, is `static`.
- **default field value (Java)** — the specific, deterministic value a
  field automatically holds the moment its object is constructed, if
  nothing ever explicitly assigns it something else — `0` for `int`, the
  identical rule C# Lesson 1.3 already named for C#'s own fields. This
  lesson proves it again for real, for Java specifically, rather than
  assuming it carries over unverified.
- **`int` (Java)** — one of Java's built-in primitive types, representing a
  whole number with no fractional part. The first time this curriculum's
  Java code has actually declared something of this type.
- **arithmetic addition operator (`+`)** — combines two numeric values into
  their sum, producing a new value without changing either one on its own.
  The identical operator and behavior already met in C# Lesson 1.3, here in
  its first appearance in this curriculum's actual Java code.
- **access modifier `private` (Java)** — a keyword restricting a member's
  visibility to code written inside that same class only. The identical
  underlying idea C# Lesson 1.4 named for C#'s own `private`; Java's own
  version, proven in this lesson with real, differently-worded compiler
  errors than C#'s.
- **encapsulation** — the design principle of bundling a piece of data
  together with the only code allowed to read or change it, and
  deliberately restricting every other path to that data. The same
  principle C# Lesson 1.4 named; this lesson proves Java enforces it too,
  with its own real, compiler-checked wall.
- **getter method** — an ordinary, `public` instance method, conventionally
  named `getX()` for a field named `x`, whose entire body returns that
  field's current value. This is Java's own real answer to the problem C#
  solved with a dedicated `property` construct — not a special kind of
  class member at all, just an ordinary method, called with ordinary
  parentheses (`service.getRunCount()`), never with field-like syntax.
- **JavaBeans naming convention** — the real, widely followed Java
  convention this lesson's `getRunCount()` follows: an accessor method for
  a field named `x` (or, for a `boolean`, sometimes `isX()`) is named
  `getX()`, and, symmetrically, a method that sets it is named `setX(...)`.
  Nothing in the Java language itself enforces this naming — unlike C#'s
  `get`/`set` accessor keywords, which are real, reserved syntax the
  compiler recognizes — but a large amount of real Java tooling (IDEs,
  serialization libraries, UI frameworks) specifically looks for methods
  named this way, which is why this lesson follows it rather than
  inventing its own name.
- **compile-time error (Java)** — an error the compiler itself detects and
  refuses to build past, before the program ever executes. The identical
  underlying idea C# Lesson 1.4 named for C#'s own compile-time errors,
  proven again here with Java's own real error text and format.
- **`class`, block (`{ }`), access modifier `public`, `void`, call syntax
  (`( )`), `var`, `new`, string literal, semicolon (`;`), member access
  (`.`)** — all reappearing from Lessons 2.1 and 2.2, unchanged in meaning,
  all still present in `Service.java` and this lesson's isolated lab.

  - *Responsibility:* running and printing the status line (unchanged from

  - *Depends on:* nothing external — still no constructor needed; this

  - *Shape:* still this project's first internal building block; now
    carrying real, protected data, not just behavior.

- **`Service.run()`**
  - *What it is:* the instance method holding this project's core
    behavior, now with a side effect on the object's own state as well as
    the console.
  - *Implementation:* `public void run() { runCount = runCount + 1;
    System.out.println("Service is running."); }` — still `public`,
    non-`static`, returning `void`, taking no parameters; one new statement
    added before the unchanged `println` call.
  - *Its use:* every call now does two things instead of one: updates
    `runCount`, then prints, in that order.
  - *Type:* an instance method — unchanged.
  - *Responsibility:* grew this lesson — no longer just "produce the status
    line," but "produce the status line *and* keep an accurate count."
  - *Depends on:* an already-constructed `Service` object; `System.out`, to
    print.
  - *Connects to:* called by `Program.main`, twice; reads and writes its
    own object's `runCount` field directly, from inside the class, where
    `private` imposes no restriction at all.
  - *Shape:* unchanged — still an internal implementation detail.

- **`Service.getRunCount()`**
  - *What it is:* this lesson's own new class member — the public,
    read-only door into `Service`'s otherwise-private run count. This
    lesson's own genuinely new subject, not a supporting or reappearing
    member.
  - *Implementation:* `public int getRunCount() { return runCount; }` — a
    perfectly ordinary `public` instance method, returning `int`, taking no
    parameters. There is no special "property" syntax anywhere in this
    declaration; it is, structurally, the exact same shape as `run()`
    itself — `public`, a return type, a name, empty parentheses, a block —
    just returning a value instead of returning `void`.
  - *Its use:* this is exactly what lets `Program.main` keep reading the
    run count once `runCount` itself becomes `private`, this lesson's third
    unit — but, unlike C#'s property, only through an explicit method call,
    never through field-like syntax.
  - *Type:* a `public` instance method — not a distinct kind of class
    member the way C#'s property was; Java has no such distinct kind at
    all.
  - *Responsibility:* hand back `runCount`'s current value to any code that
    calls `getRunCount()`. Unlike C#'s read-only property, there is no
    compiler concept of "this member permits reading but not writing" —
    write access is blocked simply because no method named `setRunCount`
    exists anywhere, proven for real in this lesson's fourth unit.
  - *Depends on:* the private `runCount` field it reads from.
  - *Connects to:* called by `Program.main`'s own
    `System.out.println(service.getRunCount())`; internally reads
    `runCount`, which only `run()` itself ever writes to.
  - *Shape:* the exact seam this lesson is about — the public-facing
    boundary of `Service`'s otherwise-private state, reached through an
    ordinary method call rather than any special syntax.

- **`Service()` — the compiler-supplied default constructor**
  - *What it is:* reappearing, unchanged, from Lessons 2.1 and 2.2: the
    constructor that runs every time `new Service()` executes, still never
    written anywhere in `Service.java`'s own source.
  - *Implementation:* unchanged — still equivalent to an empty `public
    Service() { }`. One precise addition, worth stating now that a field
    actually exists: `runCount`'s starting value of `0` is not something
    this constructor's own body sets — a newly allocated Java object's
    fields are zeroed out as part of allocating its memory, before any
    constructor body, including this one, ever runs. This constructor's
    own job hasn't grown just because `Service` now has a field.
  - *Its use:* still what silently runs the instant `new Service()`
    executes, before either call to `.run()`.
  - *Type:* an instance constructor — unchanged.
  - *Responsibility:* unchanged from Lessons 2.1–2.2 — letting the object
    come into existence, nothing more. Explicitly *not* responsible for
    `runCount` starting at `0`.
  - *Depends on:* nothing — still parameterless.
  - *Connects to:* still called directly by `new Service()`, before either
    call to `.run()`.
  - *Shape:* unchanged — a real, compiled member absent from the source
    text.

- **`System`, `System.out`, `PrintStream.println(String)`** — all
  reappearing unchanged from Lessons 2.1–2.2: `System` is the `final`,
  private-constructor standard-library class exposing process-level
  facilities; `System.out` is its `public static final PrintStream` field
  holding the live standard-output stream; `println(String)` is the real

  established for these three in Lessons 2.1 and 2.2 still applies
  unchanged; only the calling location — now inside `run()`, exactly as
  since Lesson 2.2 — stays the same this lesson too.

## Concept Unit: The Field — Where Object State Lives

### The Problem

Every call to `Service.run()` right now does exactly the same thing,
because nothing inside `Service` remembers anything between one call and
the next. How many times has this service actually run? Right now, nothing
in this project can answer that.

> **Stop and think, before reading on:** in Python, you'd write `self.count
> = 0` inside `__init__`, then update it inside a later method, and it
> would still be there next time. Lesson 2.2 already showed that a *local*
> variable (`var service`, inside `main`) dies the moment `main` finishes.
> Given that `run()`'s own body is exactly this kind of statement sequence
> too, would declaring a variable *inside* `run()` solve this problem, or
> just recreate the same "gone when the method ends" issue? If not inside
> the method, where else, syntactically, is there room to declare something
> in a class you've only ever seen with two things inside its braces:
> nothing (Lesson 2.2's first unit) and then a method (its second)?

### The Real Project Change

- **Reference Source:** `code/01-csharp/Service/Service.cs` and
  `Program.cs` at commit `dc2af54` — C# Lesson 1.3's own closing state,
  read fresh via `git show dc2af54:Service.cs` / `git show
  dc2af54:Program.cs`:
  ```csharp
  public class Service
  {
      public int RunCount;

      public void Run()
      {
          RunCount = RunCount + 1;
          Console.WriteLine("Service is running.");
      }
  }
  ```
  ```csharp
  var service = new Service();
  service.Run();
  service.Run();
  Console.WriteLine(service.RunCount);
  ```
  This unit ports this exact shape — one field, one increment line, two
  calls, one read — with one immediate naming difference: Java's own field
  is spelled `runCount`, lowercase, from the very start, never `RunCount`.
  C#'s convention capitalizes a `public` member; Java's convention
  capitalizes only class names — every field and method, `public` or not,
  stays lowercase-first, camelCase.
- **Files affected:** modified — `code/02-java/Service/Service.java` and
  `code/02-java/Service/Program.java`.
- **Change type:** add.
- **Location:** inside `Service`'s block, a new field alongside `run()`,

  statements appended inside `main`, after the existing two.
- **Dependencies:** the `Service` class and `run()` method from Lesson 2.2.

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above:

- **`public`** — the access modifier, reappearing from Lesson 2.2, now
  applied to a field: any code able to see a `Service` object is allowed to
  read or write `runCount` directly — which is exactly what `Program.java`'s
  new sixth line does.
- **`int`** — the field's declared type, stating `runCount` can only ever
  hold a whole number.
- **`runCount`** — the field's own name, lowercase throughout — unlike C#'s
  `RunCount`, Java's own naming convention never capitalizes a field
  regardless of its access level.
- **`;`** — the semicolon ending the field declaration, reappearing.

And inside `run()`'s own updated body:

- **`runCount`** (on the left of `=`) — a **field** access with no `.` and
  no object name at all — because this reference sits *inside* one of
  `Service`'s own methods, Java already knows this means "the `runCount`
  belonging to whichever `Service` object `run()` is currently running on,"
  the identical rule C# Lesson 1.3 already established for its own
  unqualified field references.
- **`=`** — the assignment operator, reappearing, storing a new value into
  `runCount`.
- **`runCount + 1`** — the arithmetic addition operator: reads `runCount`'s
  current value, adds `1`, and produces a new value — it does not, by
  itself, change `runCount`; that only happens because this sits on the
  right of the `=` just described.
- **`;`** — the semicolon ending this statement.

And in the updated `Program.java`, the line that finally makes `runCount`
observable:

- **`service.run();`** (the second call) — reappearing, character for
  character, from Lesson 2.2's own use; running it a second time is what
  gives `runCount` a second chance to change.
- **`System.out.println(service.runCount)`** — **member access** (`.`),
  reaching for a **field** this time instead of calling a method —
  `service.runCount` produces the `int` currently stored on this specific
  object, no code run to produce it. That `int` becomes `println`'s
  argument — the same overload family shown in full in Lesson 2.1, here
  automatically selecting `println(int)` rather than `println(String)`
  because the value handed to it is an `int`.
- **`;`** — the semicolon ending this statement.

### SE Lens

The alternative not chosen is tracking this count somewhere else entirely —
a separate variable in `Program.java`, incremented by hand. That breaks the
moment a second `Service` needs its own count, or code outside `main`'s own
sight needs to update it. Keeping `runCount` as a field ties the count to
the exact object it counts, permanently. The real cost, stated honestly, is
the identical one C# Lesson 1.3 already named: `runCount` is `public`,
which means any code holding a `Service` can also set it directly —
`service.runCount = 9000;` compiles and runs without complaint, silently
corrupting the count. Nothing in this lesson's own code does that yet, but
nothing stops it either; that gap is this lesson's own third and fourth
units, not this one's. Also worth stating plainly: `Service` still doesn't
need an explicit constructor. A constructor becomes necessary the moment a
field's *correct* starting value differs from its type's own default —
`runCount` starting at `0` is exactly correct for a counter that hasn't
counted anything yet, so the compiler-supplied default constructor already
produces the right result.

## Concept Unit: Instance Members — Independent State Per Object

### The Problem

`runCount` clearly survives *between* two calls to `run()` on the same
`service` object. But this project has only ever created exactly one
`Service`. If a second one existed, would it start its own count at `0`
independently, or would incrementing one somehow affect the other?

> **Stop and think, before reading on:** in Python, `self.count` on one
> object and `self.count` on a second object of the same class are already
> known to be completely separate. Given that Java's `runCount` is declared
> exactly once, inside `Service`'s own body, and not once per object
> anywhere in the source text, what do you predict happens if two different
> `Service` objects exist at once? Does declaring a field once mean there's
> only ever one shared copy — or does something else happen the moment
> `new` is involved?

### SE Lens

The alternative this unit's own Socratic prompt raised — `runCount`
behaving like one value every `Service` shares — is a real, different Java
feature (a `static` field), not something this lesson's code could have
produced by accident. Java requires that exact keyword before a field
becomes shared; without it, a field is automatically per-instance, the
identical rule C# Lesson 1.3 already proved for its own `static` keyword.
The tradeoff: per-instance is the right default here, since counting runs
of *one specific service* is the whole point. This project has no second
real `Service` object anywhere in its tracked code yet — that stays true
until a later Java lesson gives it one — so, exactly as in C# Lesson 1.3,
this unit's proof lives entirely in the isolated lab.

## Concept Unit: The Access Modifier `private` — A Real, Enforced Boundary

## Concept Unit: The Getter Method — Java's Real Answer to a Property

### The Problem

`Service.runCount` is now unreachable from `Program.java` entirely — even
the legitimate read has stopped compiling. C# Lesson 1.4 solved this with a
`property`: a class member that looks like a field from the outside
(`service.RunCount`, no parentheses, no change to the caller at all) but is
secretly backed by real code. Does Java have an equivalent dedicated
construct — or does it solve the identical problem a genuinely different
way?

> **Stop and think, before reading on:** you've now seen exactly two access
> modifiers, `public` (everything open) and `private` (everything closed)
> — both all-or-nothing. What's actually needed here is narrower: allow
> reading, block writing. Given that every method you've written in this
> curriculum's Java code so far — `main`, `run`, `increment` — has been an
> ordinary method with a name and parentheses, and none of them have used
> any construct resembling C#'s `get`/`set` keywords, what do you predict
> Java's real answer looks like? Does it need special syntax at all, or
> could an ordinary method, one you already know exactly how to write,
> already solve this?

### The Real Project Change

- **Reference Source:** `code/01-csharp/Service/Service.cs` at commit
  `fd69518`, the same citation as the previous unit — its own answer to
  this exact problem:
  ```csharp
  private int runCount;

  public int RunCount
  {
      get { return runCount; }
  }
  ```
  This unit ports the *problem* and the *intent* — controlled, read-only
  access — but not the mechanism: Java has no `property` construct, no
  `get` keyword, and no capitalization-based rename the way C#'s own
  `runCount`/`RunCount` split required. Java's own real idiom, used here
  instead, is an ordinary method.
- **Files affected:** modified — `code/02-java/Service/Service.java` and
  `code/02-java/Service/Program.java`.
- **Change type:** add (a new method added to `Service`); replace (the
  read inside `Program.java` changes from field syntax to a method call).
- **Location:** `Service`'s block: a new method added directly after the
  field declaration from the previous unit; `Program.java`'s own final
  statement inside `main`.
- **Dependencies:** the private field from the previous unit.

### Introduce the Concept in Isolation

Still inside `Scratch3`, `Counter` gets the identical treatment: an


And `Program.java`, its reads switched to `getValue()`:

```java
public class Program {
    public static void main(String[] args) {
        Counter counter = new Counter();

        System.out.println(counter.getValue());
```

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above:

- **`public`** — the access modifier, reappearing, now on this new method:
  any code that can see a `Service` object can call `getRunCount()`.
- **`int`** — the method's declared return type — the type of value
  calling this method produces, the same `int` `runCount` itself holds.
- **`getRunCount`** — the method's own name, following the **JavaBeans
  naming convention**: `get` plus the field's own name, capitalized —
  `runCount` becomes `getRunCount`. Nothing in the Java language enforces
  this specific spelling; it's a real, load-bearing convention, not a
  keyword.
- **`()`** — the call syntax parentheses, reappearing, marking an empty
  parameter list — this method needs no information handed in to do its
  job.
- **`{ return runCount; }`** — the method's own block, containing one
  statement: `return`, handing back a value to the caller — the first time
  this curriculum's Java code has used `return` to produce a value rather
  than `void`'s "nothing to hand back" — followed by `runCount`, the
  private field being read from *inside* the class, exactly where
  `private` grants full access.
- **`service.getRunCount()`** (in `Program.java`) — member access,
  reappearing, now reaching a method rather than a field — genuinely
  different syntax at the call site than `service.runCount` was, unlike
  C#'s property, which kept the caller's own syntax completely unchanged.

### CS Lens

A getter method is still a concrete example of the general idea that **an
interface can hide its implementation** — from outside,
`service.getRunCount()`'s own body could be a single field read, a
computed value, or a network call, and the caller has no way to tell which:

```
Also recognized in: a car's speedometer needle giving no hint whether
it's driven by a mechanical cable or an electronic sensor, a getter
method in any object-oriented language hiding whatever computation
actually produces its return value, a REST API's JSON response giving
no hint whether a field was stored directly or computed on request
```

Separately, worth naming as its own recognition: Java's choice to solve
this with an *ordinary method* rather than a *dedicated language
construct* is itself a real instance of **minimality of language
features** — solving a new problem by reusing an existing, already-general
mechanism (methods) instead of adding a new kind of syntax purpose-built
for it:

```
Also recognized in: Lisp representing code itself as ordinary list
data rather than a separate syntax, Unix representing devices as
ordinary files rather than a special device-access API, Python
having no dedicated "constant" keyword and instead relying on naming
convention (ALL_CAPS) the same way Java's getter relies on naming
convention rather than dedicated syntax
```

### SE Lens

The alternative not chosen here is the one C# actually took: a dedicated
`property` construct, with real `get`/`set` keywords the compiler
specifically recognizes, letting a property preserve field-like syntax at
every call site. Java's own choice — an ordinary method — costs something
real, concrete, and already visible in this very unit: every caller's own
syntax has to change, from `service.runCount` to `service.getRunCount()`,
the moment a field becomes encapsulated. In a large, real codebase, that
cost compounds — turning any existing public field into a getter later
means finding and rewriting every call site, a mechanical but real burden
C#'s property design specifically avoids. What Java gains in exchange:
total uniformity. There is exactly one kind of callable member in Java —
the method — never a second, parallel kind of member with its own special
rules for how it's declared, called, or overridden. This lesson's own
`getRunCount()` is not a special case anywhere in the language's own
grammar; it's exactly as ordinary as `run()` itself, which is precisely why
no new syntax needed introducing to explain it at all.
