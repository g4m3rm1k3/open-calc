# Lesson 2.9: What a Variable Actually Holds — References Become Explicit

**What you will build.** No new feature — this lesson investigates what
this project's own variables have secretly been doing since Lesson 2.2,
and finds a real, live bug in doing so: `Service.getHistory()`, added last
lesson, hands back the *exact same* mutable `List` object `Service` itself
uses internally, meaning any code anywhere that calls `getHistory()` can
silently corrupt `Service`'s own recorded history with no method call into
`Service` at all — proven for real, against the actual tracked project,
before being fixed with a one-line change. This lesson has no C# reference
source to port from: Phase 1 never needed to investigate this, and this
curriculum's own Phase 2 plan lists it as new content, the same as Lesson
2.8. `int runCount` and `Logger logger` have sat right next to each other
in `Service`'s own field list since Lesson 2.4, and every assignment
involving either of them has behaved correctly the whole time — but for
two structurally different reasons this lesson makes explicit for the
first time: a primitive value like `int` is genuinely copied, in full,
every time it's assigned; an object reference like `Logger` or `List` is
never copied in that sense at all — only the reference itself is, leaving
both variables pointing at the identical object. **Object identity** — a
real, verifiable answer to "are these two references pointing at the
exact same object, or two different objects that merely look alike?" —
and the JVM's own **reference-driven, garbage-collected lifetime** for
every object this project has ever created, are this lesson's other real
subjects, both proven directly rather than only described.

## Terms used in this lesson

- **primitive type** — one of Java's eight built-in, non-object value
  types (`int`, among them — already used since Lesson 2.3 — plus
  `boolean`, `char`, `long`, `double`, `float`, `short`, `byte`), each
  holding its own actual value directly, with no object, no class, and no
  reference involved at all. A primitive variable's own storage *is* the
  value, in full.
- **reference type** — every type in Java that is *not* one of the eight
  primitives: every class (`Service`, `Logger`, `List`, `String`) and
  every interface. A reference-type variable never holds an object's data
  directly; it holds a reference — a real, JVM-managed pointer to where
  the actual object lives — so the variable's own storage is the size of
  a reference, regardless of how large the object it points to actually
  is.
- **copy-by-value** — what happens when a primitive is assigned to
  another variable, or passed as an argument: the actual value is
  duplicated, in full, into the new location, and the two copies are
  afterward completely independent — changing one never affects the
  other. Proven, in this lesson's own isolated lab, with a real `int`.
- **reference sharing** (sometimes loosely called "copy-by-reference," a
  phrase this lesson deliberately avoids as imprecise — see this unit's
  own SE Lens) — what happens when a reference-type variable is assigned
  to another variable, or passed as an argument: the *reference itself*
  is copied, but both copies still point at the identical single object —
  there is still only ever one real object, now reachable through two
  independent variable names, and mutating it through either name is
  visible through both.
- **object identity** — the real, verifiable fact of whether two
  reference-type variables point at the exact same object in memory, as
  opposed to two separate objects that merely happen to hold equal
  content. Tested in Java with `==`, when applied to two reference-type
  operands — a genuinely different meaning than `==` on two primitives,
  named explicitly in this lesson's own Objects and methods section
  below.
- **`.equals(Object)`** — the real, ordinary instance method every Java
  object inherits, by default, from `Object` — and which many classes,
  including `List`, override with their own, more useful definition —
  answering "is this object *equal in content* to that one?" rather than
  "is this the literal same object?" This is a genuinely different
  question than `==` asks, proven directly in this lesson's own isolated
  lab.
- **JVM-managed lifetime** — the real fact, already relied on implicitly
  since this project's very first `new Service()` call in Lesson 2.2, but
  never named directly until now: every object this project creates lives
  in memory the JVM itself manages, for exactly as long as at least one
  live reference still points to it, with no explicit `free`, `delete`,
  or equivalent ever written anywhere in this project's own code. Once no
  reference anywhere in the running program can reach an object anymore,
  it becomes eligible for the JVM's own garbage collector to reclaim,
  automatically, at a time this project's own code never controls or
  observes directly.
- **defensive copy** — a real, deliberate technique this lesson's own
  third unit applies: returning a brand-new object holding the same
  content, rather than the original, internally-held object itself,
  specifically to prevent the kind of external mutation this lesson's own
  real, tracked project turns out to have been vulnerable to.
- **field, private, public, class, block (`{ }`), `void`, call syntax
  (`( )`), `var`, `new`, member access (`.`), assignment operator (`=`),
  string literal, semicolon (`;`), `int`, `List<T>`, `ArrayList<T>`** —
  all reappearing from Lessons 2.1–2.8, unchanged in meaning, all still
  present in `Service.java` and this lesson's isolated lab.

## Objects and methods used

- **`==` (on reference types)**
  - *What it is:* the equality operator, reappearing in spirit from
    Lesson 2.7's own use on `int` (`runCount == 0`), but this lesson's
    first use of it on two reference-type operands — a genuinely
    different comparison underneath, even though the symbol is identical.
  - *Implementation:* built into the Java language itself, not a method
    call; on two reference-type operands, it compares the two references
    themselves — are they pointing at the identical object? — never the
    objects' own content.
  - *Its use:* this lesson's own direct proof of **object identity** —
    two separately constructed `List`s holding identical content compare
    `false`; the same `List` reached through two different variable
    names compares `true`.
  - *Type:* a language operator, not a method.
  - *Responsibility:* answer "are these the same object?", nothing about
    content.
  - *Depends on:* the two reference values being compared.
  - *Connects to:* used directly in this lesson's isolated lab and against
    the real, tracked project.
  - *Shape:* the exact tool this lesson uses to make object identity, an
    otherwise invisible fact about a running program's memory, directly
    observable.

- **`List<T>.equals(Object)`**
  - *What it is:* `List`'s own real, overridden implementation of the
    `equals` method every object inherits from `Object`, comparing two
    `List`s by content rather than by identity.
  - *Implementation:* declared on the `List` interface itself, requiring
    every implementation to define equality as: same size, and every
    element, in the same order, itself equal — a real, documented
    contract, not left to each implementing class's own discretion.
  - *Its use:* this lesson's own direct contrast against `==`: two
    separately constructed `List`s holding the identical sequence of
    elements compare `true` via `.equals(...)`, even while comparing
    `false` via `==`.
  - *Type:* an interface method, with a real, binding contract.
  - *Responsibility:* answer "do these two `List`s hold the same
    content?", regardless of whether they're the same object.
  - *Depends on:* the `List` it's called on; the other `List` (or any
    `Object`) it's compared against.
  - *Connects to:* called directly in this lesson's own isolated lab.
  - *Shape:* the exact counterpart to `==`, answering a genuinely
    different question with the identical two operands.

- **`Service.getHistory()`**
  - *What it is:* the getter method added in Lesson 2.8, this lesson's
    own real subject — found, in this lesson's third unit, to leak a
    live, mutable reference to `Service`'s own internal state, then
    fixed.
  - *Implementation:* before this lesson: `public List<String>
    getHistory() { return history; }` — returning the field itself,
    directly. After this lesson:
    `public List<String> getHistory() { return new ArrayList<>(history);
    }` — returning a **defensive copy** instead.
  - *Its use:* called by `Program.main`'s own iteration and tally logic,
    unaffected by this lesson's fix; also called, in this lesson's own
    diagnostic proof, by code specifically testing whether external
    mutation reaches `Service`'s own real state.
  - *Type:* a `public` instance method.
  - *Responsibility:* before this lesson, unintentionally: hand out
    `Service`'s own actual, mutable internal storage to anyone who asks.
    After this lesson, correctly: hand out a faithful, independent copy
    of `Service`'s own history, at the moment of the call, that cannot be
    used to alter `Service`'s own real state afterward.
  - *Depends on:* `Service`'s own `history` field.
  - *Connects to:* called by `Program.main`; internally reads `history`.
  - *Shape:* this lesson's own real, concrete example of the difference
    between a reference-type return value that's safe to hand out and one
    that isn't.

## Concept Unit: Primitive vs. Reference — Copying a Value vs. Copying a Reference

### The Problem

`Service`'s own fields include `runCount`, an `int`, and `logger`, a
`Logger`. Both have been assigned, read, and passed around since Lesson
2.4 with no problems at all — but has anything in this project ever

assumed they work the same underlying way because assigning either one
looks identical on the page (`x = y;`, either way)?

> **Stop and think, before reading on:** in Python, you already know that
> `a = [1, 2, 3]; b = a; b.append(4)` leaves `a` holding `[1, 2, 3, 4]`

> time than Python ever does, also changes something about *this*
> specific behavior?

### Introduce the Concept in Isolation

A throwaway project, `Scratch9`, was created fresh in this session's own
scratch directory:

```java
int a = 5;
int b = a;
b = 10;
System.out.println(a);
System.out.println(b);
```

Compiled and run for real:

```
javac Program.java
java Program
```

Real output:

```
5
10
```

`a` stays `5` even after `b` — assigned from `a` one line earlier — is
changed to `10`. This proves **copy-by-value**: `int b = a;` copied
`a`'s actual value, `5`, into `b`'s own separate storage; `b = 10;`
afterward only ever touches `b`'s own copy.

Then, the identical shape of code, using a `List` instead:

```java
List<String> list1 = new ArrayList<>();
list1.add("x");
List<String> list2 = list1;
list2.add("y");
System.out.println(list1.size());
System.out.println(list2.size());
System.out.println(list1 == list2);
```

Real output:

```
2
2
true
```

`list2.add("y")` was the only `add` call made through the `list2` name —
and `list1.size()` still reports `2`, the identical growth. This proves
**reference sharing**: `List<String> list2 = list1;` did not create a
second, independent list the way `int b = a;` created a second,
independent number — it copied the *reference*, leaving both `list1` and
`list2` pointing at the exact same single `ArrayList` object. `list1 ==
list2` reporting `true` confirms it directly.

`Scratch9` is kept alive rather than deleted immediately — the next two
concept units in this lesson still need it.

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`int a = 5;`** — a local variable declaration (reappearing from
  Lesson 2.4), `a`'s type a **primitive type**, `int`, holding the value
  `5` directly, in its own storage.
- **`int b = a;`** — a second declaration, `b`, also `int`, initialized by
  reading `a`'s current value — `5` — and copying that value, in full,
  into `b`'s own separate storage. After this line, `a` and `b` are two
  completely independent `5`s.
- **`b = 10;`** — the assignment operator, reappearing, overwriting `b`'s
  own storage with `10`. `a`'s own storage is a different location
  entirely, and this line has no way to reach it.

And, in the `List` version:

- **`List<String> list2 = list1;`** — a declaration whose right-hand side
  is not `new ArrayList<>()` — no fresh object is created here at all —
  just a plain variable read, `list1`, copying *its* value into `list2`.
  For a **reference type**, a variable's own "value" is a reference, not
  an object, which is exactly why this copies a reference, not an object.
- **`list2.add("y");`** — member access, reappearing, calling `add`
  through `list2` — but since `list2` and `list1` hold the identical
  reference, this reaches the exact same underlying `ArrayList` either
  name would reach.

### CS Lens

The distinction between copy-by-value and reference sharing is a real
instance of **indirection** — a variable holding not the thing itself,
but a pointer to where the thing actually lives:

```
Also recognized in: a house's street address versus the house itself
(copying the address doesn't build a second house; two pieces of mail
addressed to the identical address reach the identical building), a
library's card catalog entry pointing at a book's shelf location
rather than containing the book's full text, a shared document link
where every person with the link edits the identical file, not their
own separate copy
```

### SE Lens

Java's own choice — primitives genuinely copied by value, every object
reached only through a reference — was not the only possible design; some
languages copy everything by value unless told otherwise, and others
reference everything, even small numbers, uniformly. Java's own split
exists for a real, practical reason: a primitive `int` is small, fixed in
size, and cheap to copy in full every time; an object like a `List` might
hold an unbounded amount of data, and copying its *entire contents* every
single time a variable is merely assigned or passed to a method would be
a real, often unnecessary cost. Reference sharing avoids that cost — at
the price this lesson's own third unit is about to make concrete: any
code holding a reference to a mutable object can change that object,
visibly, for every other piece of code holding the identical reference,
whether that's actually intended or not.

The distinction between identity and equality is a real, foundational
idea wherever "the same" needs a precise definition:


### SE Lens

The alternative not chosen — `==` comparing content by default, the way
it does for Java's own primitives — would make identity itself
impossible to test directly at all without some other mechanism.
Java's own choice keeps `==` doing one honest, simple, and fast thing for

comparison to `.equals(...)`, which each class defines for itself, only
where it actually makes sense (some classes never override it at all,
inheriting `Object`'s own default, which — worth stating honestly — falls

ever be equal by being identical). The real cost, worth remembering

content comparison the way it would work for two Java `int`s or Python
values generally, is a real, common source of bugs — this lesson's own
first real output, `false` for two `"x"`-holding lists, is exactly the
kind of surprising result that mistake produces.

## Concept Unit: The Real Leak — `Service.getHistory()` Exposes a Live Reference

### The Problem

way `list2 = list1` did in this lesson's own first unit. This is a real
**encapsulation** gap, in the sense Lesson 2.3 already established that
term: `history` is declared `private`, and every direct field access is
correctly blocked — but `getHistory()` itself, a legitimate `public`
method, was quietly reopening that same door by handing out the live
object instead of information about it.

Fixed, and re-verified for real, with a second throwaway file,
`ServiceTest.java`, against the corrected `Service.java`:

```java
var copy1 = service.getHistory();
var copy2 = service.getHistory();
System.out.println(copy1 == copy2);
System.out.println(copy1.equals(copy2));

copy1.add("Injected from outside Service entirely.");
System.out.println("service history size after external mutation: " + service.getHistory().size());
```

Real output:

```
Service is running.
false
true
service history size after external mutation: 1
```

`copy1 == copy2` is now `false` — the fixed `getHistory()` constructs a
genuinely new `ArrayList` on every single call, so two separate calls
never return the identical object anymore. `copy1.equals(copy2)` is still
`true` — both copies hold identical content, at that moment. And the
size stays `1` after `copy1.add(...)` — the leak is closed: mutating a
copy can no longer touch `Service`'s own real internal state at all.

### Mechanical Walkthrough

Enumerating the one changed element in the New Code block above:

- **`new ArrayList<>(history)`** — a real, additional constructor
  `ArrayList` provides beyond the empty one already used since Lesson
  2.8: one accepting an existing collection and copying every one of its
  elements, in order, into a brand-new, independent `ArrayList`. This is
  a **defensive copy**: the returned list starts out `.equals(...)` to
  `history` at the moment of the call, but is never the identical object,
  and never will be — `history`'s own future growth, from later calls to
  `run()` or `reset()`, has no way to reach a copy already handed out.

### CS Lens

Returning a defensive copy instead of an internal, mutable reference is a
real instance of **preserving encapsulation across a return boundary** —
the same underlying idea `private`, from Lesson 2.3, already established
for direct field access, now applied to what a `public` method is allowed
to hand back:

```
Also recognized in: a museum displaying a replica while the original
artwork stays secured in controlled storage, a company sharing a
financial summary rather than direct access to its live accounting
ledger, a photocopy of a signed document handed to a third party
instead of the only original
```

### SE Lens

The alternative not chosen — returning `history` directly, exactly as
Lesson 2.8 originally wrote it — is not always wrong: it's cheaper, one
less object allocated per call, and perfectly safe *if* every single
caller, forever, is trusted never to mutate what it gets back. That
assumption is fragile in exactly the way this unit's own real diagnostic
just proved: nothing in Java's own type system distinguishes "a `List`
you may only read" from "a `List` you're free to mutate" — `List<String>`
is the identical declared type either way, so a caller has no compiler-
enforced signal telling it `getHistory()`'s own result is off-limits to
mutate. The real cost of the fix, honestly: every call to `getHistory()`
now allocates a brand-new `ArrayList` and copies every element into it,
real, measurable work this project's own tiny scale never makes matter,
but a genuine tradeoff a much larger, more frequently called version of
this same method would have to weigh — an immutable, read-only wrapper
(Java's own `List.copyOf(...)`, or `Collections.unmodifiableList(...)`)
is a real alternative fix worth knowing exists, trading the copy's own
allocation cost for a thinner, still-safe wrapper — a choice this lesson
doesn't need to make, but a future one reusing this exact pattern might.
