# Lesson 2.6: One Body, Many Types, One Real Runtime Shape — Compare C# and Java Generics

**What you will build.** Two small, new, standalone additions to this Java
project, ported from C# Lesson 1.9: `LastValue<T>`, a class that remembers
one value of *any* type — used once holding a whole number (`Service`'s
own run count) and once holding a `String` status message — and
`Describer`, an ordinary, non-generic class whose one method,
`<T> void describe(T value)`, is itself generic. Neither addition touches
`Service`, `Logger`, or either logger implementation at all — this lesson
is purely additive, exactly as C#'s own version was. But porting this
particular lesson surfaces two genuinely different, real facts about
Java's generics that this curriculum's own C# Phase never had to confront:
Java generics cannot be parameterized with a primitive type at all — where
C# wrote `LastValue<int>` directly, Java needs the wrapper type,
`LastValue<Integer>`, bridged to and from `int` by **autoboxing** — and
Java's generics are **erased** at compile time, not **reified** the way
C#'s are: `LastValue<Integer>` and `LastValue<String>` compile down to the
exact same runtime class, `LastValue`, with `T` replaced by `Object`
everywhere in the actual bytecode. This lesson's curriculum title says
"compare," not just "port," specifically because of this: the same
surface idea, `<T>`, hides a genuinely different runtime reality
underneath, and this lesson proves that difference with real, disassembled
bytecode rather than asserting it.

**What you need to know first.** From **Lesson 2.5 — Port the Interface**:
the real project at `code/02-java/Service/`, `interface`, `implementation`.
From **Lesson 2.4**: `parameter`, `argument`. From **Lesson 2.3**: `field`,
`int`, default field value. From **Lesson 2.2**: `class`, `object`,
`instance`, `method`, `new`, `var`, member access (`.`). From **Lesson
2.1**: `System.out.println`, `javac`/`java`, and real, disassembled-
bytecode evidence gathering with `javap`. From **C# Lesson 1.9 — One Body,
Many Types**, this lesson's own reference source: `generic type
parameter`, `generic class`, `generic method`, and the exact reference
code being ported, read fresh this session from `code/01-csharp/Service/`
at git commit `55d7c6d`. From the curriculum's own stated assumptions:
enough Python experience to know that Python functions and classes never
need to declare what type of value they'll receive at all — this lesson
leans on that contrast to explain *why* a compiled, statically typed
language needs an explicit mechanism for "the same code, many types," when
Python simply never asks the question.

## Terms used in this lesson

- **generic type parameter (Java)** — a placeholder name, conventionally a
  single capital letter like `T`, standing in for a real type that isn't
  fixed until the generic class or method is actually used. The identical
  underlying idea C# Lesson 1.9 named for C#'s own type parameters, met
  here in Java's own, nearly identical `<T>` syntax.
- **generic class (Java)** — a class declared with one or more type
  parameters in angle brackets after its own name. `LastValue<T>` is this
  lesson's own generic class — the exact same compiled class produces a
  `LastValue<Integer>` object and a `LastValue<String>` object, each with
  its own `T` fixed differently at the source level, though — this
  lesson's own real subject — not at the compiled level.
- **generic method (Java)** — a method declaring its *own* type parameter,
  independent of whether the class it belongs to is generic at all.
  `Describer.describe` is this lesson's own generic method — `Describer`
  itself is an entirely ordinary, non-generic class.
- **generic method type-parameter placement** — a real, worth-naming
  syntax difference this lesson's own code surfaces directly: C#'s generic
  method syntax places `<T>` immediately after the method's own name
  (`void Describe<T>(T value)`); Java's places it *before* the return
  type instead (`<T> void describe(T value)`) — a real, structural
  difference in where the same declaration piece goes, not merely a
  stylistic one, confirmed by this lesson's own real, compiling code.
- **wrapper type** — a real, ordinary class in Java's standard library
  (`Integer`, `Double`, `Boolean`, and so on, one per primitive type)
  representing a primitive value as a genuine object, so it can be used
  anywhere an object reference is required — including as a generic type
  argument, which a bare primitive can never be. `Integer` is this
  lesson's own wrapper type, standing in for `int` wherever
  `LastValue<T>` needs a real reference type.
- **autoboxing / auto-unboxing** — the compiler-inserted, automatic
  conversion between a primitive value and its corresponding wrapper type,
  at the exact point one is needed where the other was supplied — proven,
  in this lesson, with real disassembled bytecode showing the actual
  `Integer.valueOf`/`intValue` calls the compiler inserts, invisible in
  the source text itself. It exists so a primitive `int` (fast, unboxed,
  no object overhead) can still be handed to code that only accepts object
  references, like a generic method or class, without the author writing
  the conversion by hand every time.
- **type erasure** — the real, defining fact about how Java implements
  generics: type parameters exist only during compilation, for the
  compiler's own type-checking; by the time source becomes bytecode, every
  occurrence of a type parameter is replaced — "erased" — with its bound
  (or, unconstrained, with `Object`). `LastValue<Integer>` and
  `LastValue<String>` are, at runtime, the exact same class, `LastValue`,
  with no trace of `Integer` or `String` anywhere in its own compiled
  shape. A hard concept, getting full CS Lens treatment below.
- **reified generics** — the alternative design this lesson's own CS/SE
  Lens contrasts type erasure against: a generic type parameter that
  genuinely exists at runtime, as real, inspectable information, rather
  than being erased at compile time. C#'s own generics are reified —
  `typeof(LastValue<int>)` and `typeof(LastValue<string>)`, in C#, really
  are two different runtime `Type` objects; this lesson's own real,
  disassembled-bytecode and `getClass()` evidence proves Java's own
  generics are not.
- **compiler-inserted cast** — a real type cast the compiler adds to
  compiled bytecode automatically, with nothing in the source text asking
  for it, needed specifically because type erasure leaves a generic
  method's own compiled return type as `Object` rather than whatever
  specific type the source-level generic signature promised. This lesson's
  own real, disassembled bytecode shows two of these, inserted at two
  different real call sites.
- **field, private, public, class, block (`{ }`), `void`, call syntax
  (`( )`), `var`, `new`, member access (`.`), assignment operator (`=`),
  string literal, semicolon (`;`), `int`** — all reappearing from Lessons
  2.1–2.5, unchanged in meaning, all still present in `LastValue.java`,
  `Describer.java`, and this lesson's isolated lab.

  - *What it is:* this lesson's own new generic method — the one member

  - *Implementation:* `public <T> void describe(T value) {
    System.out.println(value); }` — a `public`, non-`static`, generic
    method, declaring its own type parameter `T`, placed *before* the
    return type — Java's own real syntax, structurally different from C#'s
    own placement, named in this lesson's own Terms entry above.
  - *Its use:* called twice on the *same* `Describer` object this lesson —
    once with an `int` (auto-boxed to `Integer`), once with a `String`

  - *Type:* a generic instance method.
  - *Responsibility:* print whatever value it's handed, regardless of
    type.
  - *Depends on:* an already-constructed `Describer` object; the `value`

  - *Connects to:* called directly by `Program.main`; calls
    `System.out.println(Object)` internally.
  - *Shape:* proof that genericity belongs to individual methods, not only
    to whole classes.

- **`Integer.valueOf(int)`**
  - *What it is:* a real, `static` factory method on Java's `Integer`
    wrapper class, converting a primitive `int` into a boxed `Integer`
    object.
  - *Implementation:* `public static Integer valueOf(int i)` — documented
    in Java's own public `java.lang.Integer` API reference; this method's
    own real body caches and returns small `Integer` instances for a
    fixed range of values rather than always allocating a new one, an
    optimization detail this lesson doesn't depend on but is honestly
    worth naming as real, inspectable behavior rather than a black box.
  - *Its use:* this is the exact call the compiler inserts, automatically,
    at every point this lesson's source code hands a primitive `int`
    where a `LastValue<Integer>` or `describe`'s own `T` expects an
    object — confirmed via real disassembly below, not asserted.
  - *Type:* a `static` factory method.
  - *Responsibility:* produce a real `Integer` object wrapping the given
    primitive value.
  - *Depends on:* the `int` value passed in.
  - *Connects to:* inserted by the compiler at `lastCount.set(...)` and
    `describer.describe(...)`'s own real call sites; never written by
    this lesson's own source text.
  - *Shape:* the real, concrete mechanism standing behind the word
    **autoboxing** this lesson's Header names — not a language feature
    with no real implementation, but a genuine method call the compiler
    inserts on this project's behalf.

- **`Integer.intValue()`**
  - *What it is:* a real instance method on `Integer`, converting a boxed
    `Integer` back into its primitive `int` value.
  - *Implementation:* `public int intValue()` — documented in `Integer`'s
    own public API.
  - *Its use:* the exact call the compiler inserts, automatically, the
    moment a boxed `Integer` needs to become a plain `int` again — proven
    in this lesson's isolated lab, where a `Box<Integer>.get()` result is
    assigned directly into an `int` local variable.
  - *Type:* an instance method.
  - *Responsibility:* hand back the primitive value a specific `Integer`
    object wraps.
  - *Depends on:* an already-constructed `Integer` object.
  - *Connects to:* inserted by the compiler wherever auto-unboxing is
    needed.
  - *Shape:* the concrete mechanism standing behind **auto-unboxing**.

- **`Object.getClass()`**
  - *What it is:* a real, `public final` instance method every Java object
    inherits from `java.lang.Object`, returning that object's actual
    runtime class.
  - *Implementation:* `public final native Class<?> getClass()` — `final`,
    meaning no class may override it, and `native`, meaning its real body
    is implemented outside ordinary Java bytecode, in the JVM itself —
    named honestly here rather than glossed over, since this lesson's own
    "demystify, don't hand-wave" standard still applies even to a method
    whose implementation genuinely isn't Java source to read.
  - *Its use:* this lesson's own real, direct proof of type erasure: two
    `LastValue` objects, one built as `LastValue<Integer>` and one as
    `LastValue<String>`, calling `getClass()` on each and comparing the
    results with `==`.
  - *Type:* a `public final native` instance method — inherited, not
    declared anywhere in `LastValue`'s own source.
  - *Responsibility:* report exactly which real, compiled class produced
    this specific object, at runtime, with no ambiguity.
  - *Depends on:* nothing beyond the object it's called on.
  - *Connects to:* called directly against this lesson's own `LastValue`
    objects, in a throwaway diagnostic file, never part of the tracked
    project.
  - *Shape:* the exact tool this lesson uses to make an otherwise
    invisible runtime fact — erasure — directly, concretely observable.

## Concept Unit: The Generic Class — One Type Parameter, Many Types

### The Problem

Suppose this project wanted a small utility remembering "the last value of
something" — the last run count, say. Writing `LastIntValue` with a plain
`int` field would work, once. Remembering the last logged message too
would mean writing an entirely separate `LastStringValue` class, with an
identical shape, differing only in which one type each happens to use. Is
duplicating that shape once per type really the only option?

> **Stop and think, before reading on:** in Python, you'd just write one
> class with a plain `self.value = value` inside `set`, and it would
> already work for an `int`, a `str`, or anything else. Given that every
> field, parameter, and return type in this Java project's code so far has
> always named one specific, fixed type, what do you predict Java's own
> answer to "the same class, many types" looks like syntactically? And
> given this project's own `Service` class stores a plain `int` — never a
> capital-`I` `Integer` — anywhere in its own source, what do you predict
> happens if a generic class tries to use that same bare `int` as its own
> type argument?

A real, concrete compile-time refusal — `required: reference, found: int`
— naming the exact rule: a Java generic type argument must be a
**reference type**, and `int` is a primitive, never a reference type,
full stop. Fixed by using `Integer`, the **wrapper type** wrapping `int`:

```java
public class Program {
    public static void main(String[] args) {
        Box<Integer> intBox = new Box<Integer>();
        int plainInt = 42;
        intBox.set(plainInt);
        int backOut = intBox.get();
        System.out.println(backOut);

        Box<String> stringBox = new Box<String>();
        stringBox.set("hello");
        System.out.println(stringBox.get());
    }
}
```

Compiled and run for real:

```
javac Program.java
java Program
```

Real output:

```
42
hello
```

`intBox.set(plainInt)` compiles even though `plainInt` is a bare `int` and
`set` expects a `T` fixed to `Integer` — and `int backOut = intBox.get();`
compiles even though `get()` returns `Integer`, not `int` — because the
compiler inserts **autoboxing** and **auto-unboxing** conversions
automatically at both points, confirmed with real bytecode in this
lesson's third unit rather than only asserted here. This proves the
concept named in this lesson's Header: a **generic class** fixes its own
type parameter, `T`, once per object created from it, and, in Java
specifically, that fixed type must always be a reference type — a
`Box<Integer>`, never a `Box<int>`.

### CS Lens

Generics are a real instance of **parametric polymorphism** — writing one
piece of code that works correctly for many types, by treating the type
itself as something suppliable later, the same way a value can be:

```
Also recognized in: a shipping container sized and shaped identically
whether it holds furniture or electronics, a moving box labeled
simply "fragile contents" rather than one box design per item
category, a mail slot accepting any letter regardless of what's
actually written inside it
```

### SE Lens

The alternative not chosen here — a separate class per type,
`LastIntValue` and `LastStringValue` written by hand — was entirely
possible and would have worked. It fails to scale the moment a third type
is needed, each copy needing identical bug fixes applied by hand, forever.
A genuinely Java-specific cost, worth stating plainly and not glossed
over: this project's own `Service.getRunCount()` returns a plain,
primitive `int` — the fastest, simplest numeric representation the JVM
has — and every time that `int` needs to flow through a generic boundary
like `LastValue<T>`, it has to be boxed into a real `Integer` object
first, a genuine, measurable cost (a real heap allocation, in the general
case) C#'s own reified generics never impose, since C#'s own
`LastValue<int>` can hold a true, unboxed `int` directly. This project's
own scale never makes that cost matter, but it's a real, honest tradeoff
Java's own generic design carries permanently, not a hypothetical one.

## Concept Unit: The Generic Method — Genericity Without a Generic Class

### The Problem

`LastValue<T>` is generic at the *class* level — every member inside it
shares the one `T` fixed when the object was created. Can one *method*, on
an otherwise completely ordinary class, be generic on its own, accepting a
different type on every single call?

> **Stop and think, before reading on:** `LastValue<T>`'s own `<T>` sits
> right after the *class* name. Given that a method already has its own
> separate parameter list, distinct from whatever's declared at the class
> level, and given that Java's own method declarations always list a
> return type immediately before the method's name (`public void
> run()`, `public int getRunCount()`), where do you predict a method's
> *own* type parameter has to go, relative to that return type?

### The Real Project Change

- **Reference Source:** `code/01-csharp/Service/Describer.cs` and
  `Program.cs` at commit `55d7c6d`, read fresh via `git show`:
  ```csharp

  {
      public void Describe<T>(T value)
      {
          Console.WriteLine(value);
      }
  }
  ```
- **Files affected:** created — `code/02-java/Service/Describer.java`;
  modified — `code/02-java/Service/Program.java`.
- **Change type:** add.
- **Location:** a new file alongside the existing ones; two new lines
  appended to the end of `main`.

## Concept Unit: Type Erasure — Comparing Reified and Erased Generics

### The Problem

`LastValue<Integer>` and `LastValue<String>` both work correctly, proven
by two real runs. But do they actually exist, at runtime, as two
genuinely different things — the way two different concrete classes
would — or is something else going on underneath? This curriculum's own
Phase 1 never had to ask this question: C#'s own generics are **reified**,
meaning `LastValue<int>` and `LastValue<string>` really are distinct
runtime types in C#. Is the identical thing true in Java?

> **Stop and think, before reading on:** every method call so far in this
> lesson has compiled correctly, whether it was handed an `Integer` or a
> `String`. Given that `LastValue<T>`'s own compiled `.class` file has to
> be one single file on disk — there's only one `LastValue.java` — what do
> you predict that file actually contains, mechanically, if it has to
> correctly serve both an `Integer` version and a `String` version at
> once? Does the compiler somehow generate two separate, hidden versions
> of the class behind the scenes? Or does it do something else entirely?

   behave, at every call site, as if the erasure never happened.

Enumerating the real bytecode instructions shown above, in the order they

### CS Lens

Type erasure is a real, specific instance of **compile-time-only
abstraction** — a distinction that exists for the type-checker alone, and
is deliberately discarded before the artifact that actually runs is
produced:

```
Also recognized in: TypeScript's own type annotations, which vanish
entirely from the JavaScript a TypeScript compiler produces, C's own
function-like macros expanded away by the preprocessor before the real
compiler ever sees them, a spreadsheet's cell format (currency,
percentage) affecting only how a number displays, never the raw
numeric value actually stored underneath
```

Every one of these keeps some structure meaningful to a human, or to a
checking tool, while producing a final artifact that no longer carries
that structure at all.

### SE Lens

Java's own choice, type erasure, was not the only possible design — C#'s
own reified generics prove a real, working alternative exists. Java's
specific reason, real and historical rather than arbitrary: generics were
added to the Java language in Java 5 (2004), a full decade after Java 1.0
first shipped, and an enormous amount of pre-existing, already-compiled
Java code and already-running Java virtual machines needed to keep working
unchanged. Type erasure was chosen specifically because it lets generic
code compile down to bytecode that looks, to an old JVM, exactly like the
non-generic code that same JVM already knew how to run — the price paid
for that backward compatibility is everything this unit just proved:
`getClass()` can't distinguish `LastValue<Integer>` from
`LastValue<String>`, a primitive can never be a type argument (the
previous unit's own finding — a primitive can't be erased down to `Object`
the way a reference type can, since a primitive isn't a reference at
all), and every generic call site quietly carries extra, invisible casts
the source text never shows. C#'s own reified generics, introduced as part
of the language's original design for value-type generics rather than
retrofitted onto a decade-old runtime, avoid every one of these costs, at
the price of a real, different tradeoff of their own: a generic method's
own compiled code genuinely differs per type argument in C#, which is a
real cost this curriculum's own C# Phase 1 never had reason to name,
because nothing in it needed to.
