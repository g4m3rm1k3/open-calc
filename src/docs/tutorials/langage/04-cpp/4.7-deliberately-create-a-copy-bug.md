# Lesson 4.7: The Program That Prints Garbage and Then Stops

**What you will build:** `Service` gains a real, explicit copy
constructor and copy assignment operator — deep copies, each allocating
its own independent buffer — replacing the default, compiler-generated
versions Lesson 4.6 proved safe for a plain `int` but never tested
against `label`. Before writing the fix, this lesson does something no
earlier lesson in this curriculum has done: deliberately runs undefined
behavior, for real, against the actual pre-fix `Service` class, and
reports exactly what happened — real, corrupted terminal output and a
program that never reaches its own last line, captured across three
separate real runs, not simulated or described secondhand.

**What you need to know first:** Lesson 4.6 proved copy construction and
copy assignment are real, distinct, separately-hookable mechanisms, and
that the compiler's own default versions work correctly for a plain
`int` — deliberately never testing them against `label`. Lesson 4.5 gave
`Service` that real, owned resource. This lesson runs the exact
experiment Lesson 4.6 named and postponed.

## Terms used in this lesson

- **Shallow copy** — the default behavior of C++'s own compiler-
  generated copy constructor and copy assignment operator: every member
  is copied exactly as it's stored — for a pointer member like `label`,
  that means copying the *address* itself, producing two objects whose
  `label` members point at the identical real memory, not two
  independent buffers. It exists as the compiler's own only reasonable
  default — copying a member "as stored" is the one behavior the
  compiler can always generate correctly with no knowledge of what a
  pointer actually *means* to the class holding it.
- **Deep copy** — a copy constructor or assignment operator, written by
  hand, that allocates a genuinely new, independent resource and copies
  the *contents* the original resource holds, rather than the raw
  pointer to it. It exists as the real fix for exactly the failure this
  lesson proves: a class owning a resource has to say, explicitly, what
  "becoming a copy" really means for that resource, because the
  compiler's own default has no way to know.
- **Double-free** — calling a resource-releasing operation (here,
  `delete[]`) twice on the identical pointer. It exists, as a real,
  named failure mode, because C++'s own memory allocator has no way to
  know a second `delete[]` on an already-freed pointer is a mistake —
  the pointer's own bit pattern gives no indication it was already
  released, so the allocator either corrupts its own internal
  bookkeeping trying to free it again, or — this lesson's own real,
  observed result — detects the corruption and aborts the whole program.

### CS Lens

A double-free is a specific, real instance of a broader class of bugs:
operations that are only safe to perform once, performed more than once
because nothing in the program's own visible state records that the
first one already happened.

```
Also recognized in: closing the same file handle twice in C (a real,
well-known, near-identical failure); releasing the same lock twice in
concurrent code, leaving a mutex in a genuinely broken state;
`Files.delete()` called twice on the same path in Java (a real, though
far gentler, failure — an exception, not memory corruption, precisely
because Java's own managed runtime is what this whole phase exists to
contrast against)
```

### SE Lens

The principle this unit's own real evidence proves, plainly: **a
compiler cannot generate correct copying behavior for a resource it
knows nothing about the meaning of** — `label`'s own type, `char*`, is
indistinguishable, to the compiler generating a default copy
constructor, from any other `char*` that might merely be borrowing a
view into memory it doesn't own at all (a real, valid, common use of
`char*` this curriculum has not needed). The compiler's own default is
not a bug in the compiler — it is the only behavior it *can* generate
without being told more. The real, honest cost this whole lesson exists

own, warns a reader that copying it is unsafe — the failure is entirely

## Concept Unit: Deep Copying — Writing the Meaning the Compiler Couldn't Guess

### The Problem

`Service`'s own copy constructor and copy assignment operator both need
to do something the compiler's own default cannot: allocate a *new*
buffer, sized and filled to match the original, rather than copying
`label`'s own address.

> **Stop and try it yourself first:** Lesson 4.5's own real constructor
> already does exactly this — `new char[std::strlen(name) + 1]` followed
> by `std::strcpy(label, name)` — for a `const char* name` handed to it
> at construction. A copy constructor receives, instead, an existing
> `Service` object to copy from. Given that `other.label` (where
> `other` is the object being copied from) is itself a real, valid
> `char*` — the exact same type `name` already was — what would you
> predict the fix actually looks like, compared to the constructor
> Lesson 4.5 already wrote?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.h`:

```cpp
#include <iostream>
#include <cstring>

class Named {
public:
    char* label;

    Named(const char* name) {
        label = new char[std::strlen(name) + 1];
        std::strcpy(label, name);
    }

    Named(const Named& other) : label(nullptr) {
        label = new char[std::strlen(other.label) + 1];
        std::strcpy(label, other.label);
    }

    ~Named() {
        delete[] label;
    }
};

int main() {
    Named a("A");
    Named b = a;
    std::cout << (a.label == b.label) << std::endl;
    std::cout << a.label << std::endl;
    std::cout << b.label << std::endl;
}
```

Run this session (`verification/4.7/lab_deep_copy_fix.cpp`):

```

```

`a.label == b.label` is now `0` (false) — two genuinely different real
addresses — while both still correctly print `"A"`. This is called a
**deep copy**, per this lesson's own Terms entry: the buffer itself, not
just its address, was duplicated. The program ran to real completion
with no crash and exit code `0`, confirmed the same session.

### Mechanical Walkthrough

- **`Service(const Service& other) : runCount(other.runCount)`** — the
  copy constructor, per Lesson 4.6's own full treatment; the member
  initializer list, per Lesson 4.2's own full treatment, copies
  `runCount` directly (a plain `int`, exactly as safe here as it was in
  Lesson 4.6's own `Counter`).
- **`label = new char[std::strlen(other.label) + 1];`** and
  **`std::strcpy(label, other.label);`** — per Lesson 4.5's own full
  treatment of both calls: identical logic to the ordinary constructor,
  reading from `other.label` instead of an externally-supplied `const
  char* name` — the real fix, exactly matching this unit's own Socratic
  prompt's own predicted shape.
- **`Service& operator=(const Service& other)`** — the copy assignment
  operator, per Lesson 4.6's own full treatment.
- **`if (this != &other)`** — per Lesson 4.6's own treatment of `this`:
  compares the address of the current object against the address of
  `other`. This guards against **self-assignment** (`service =
  service;`, not exercised by this lesson's own real code, but a real,
  legal statement any caller could write) — without this check, `delete[]
  label;` would free the buffer, and the immediately following
  `std::strlen(other.label)` would then read from that same, just-freed
  buffer (because `other` and `this` would be the identical object),
  reproducing this lesson's own first unit's real corruption from a
  single line of ordinary-looking code.
- **`delete[] label;`** (inside `operator=`) — per Lesson 4.5's own
  treatment: releases whatever buffer this object already owned
  *before* replacing it — per this lesson's own second unit's opening
  problem, an assignment operator's own real job, distinct from a
  constructor's, is discarding old state safely first.
- **`return *this;`** — per Lesson 4.6's own treatment.
- **`Service copy = service;`** (`Program.cpp`) — now invokes this
  lesson's own new copy constructor, not the compiler's own old,
  dangerous default.
- **`copy.run()`**, followed by both `getRunCount()` reads — proves
  independent state for `runCount` (already expected, per Lesson 4.6)
  *and*, implicitly, that `copy`'s own destructor will not collide with
  `service`'s own, proven directly by this lesson's own real run
  completing cleanly, below.
