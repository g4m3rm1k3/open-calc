## Terms used in this lesson

- **Automatic storage** (reappearing from Lesson 4.3, given full
  treatment again) — memory whose own lifetime is tied directly to the
  scope that declared it, requiring no explicit allocation or release
  call — every `Service`, `Logger`, and local variable this whole phase
  has ever declared with no `new` anywhere has lived here.
- **Dynamic storage** (the heap) — memory explicitly requested at
  runtime, via `new` or `new[]`, whose own lifetime is governed by
  nothing but an explicit, matching `delete`/`delete[]` (or, since
  Lesson 4.9, a smart pointer's own automatic release) — never by scope
  alone. `label`'s own real buffer, since Lesson 4.5, has always lived
  here, regardless of how many scopes the `Service` object that owns it
  passes through.

## Concept Unit: Proving the Two Regions Are Actually Different

### The Problem

Every real address this phase has printed so far — `service`'s own
address (never actually printed directly until now), `label`'s own
address (Lessons 4.7 and 4.8) — has been shown in isolation, never
side by side. Are "the stack" and "the heap" genuinely two separate real
regions of memory on this machine, or merely a useful conceptual
distinction with no real, observable difference?

> **Stop and try it yourself first:** Lesson 4.5's own real address
> evidence and Lesson 4.7's own real address comparisons were both
> real, printed hexadecimal numbers — but neither lesson ever printed a
> stack address and a heap address side by side, in the same real run,
> to compare their actual numeric ranges. Given everything this phase
> has established about the stack being managed by scope alone and the
> heap being managed by explicit allocation, would you predict their
> real address ranges, on an actual running program, end up close
> together, or in genuinely different, far-apart regions?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.h`, shaped like a simplified
`Service` specifically to print every real address side by side:

```cpp
#include <iostream>
#include <memory>
#include <cstring>

class Probe {
public:
    int runCount;
    std::unique_ptr<char[]> label;

    Probe(const char* name) : runCount(0), label(new char[std::strlen(name) + 1]) {
        std::strcpy(label.get(), name);
    }
};

int main() {
    Probe stackObject("A");
    std::cout << "Probe itself (stack):      " << &stackObject << std::endl;
    std::cout << "Probe's own runCount (stack, inside the object): " << &stackObject.runCount << std::endl;
    std::cout << "Probe's own label buffer (heap):                " << static_cast<void*>(stackObject.label.get()) << std::endl;

    auto heapObject = std::make_unique<Probe>("B");
    std::cout << "A whole second Probe, itself allocated on the heap via new: " << heapObject.get() << std::endl;
}
```

Run this session (`verification/4.12/lab_stack_vs_heap_full.cpp`):

```
Probe itself (stack):      0x10c7dffc60
Probe's own runCount (stack, inside the object): 0x10c7dffc60
Probe's own label buffer (heap):                0x15405f32320
A whole second Probe, itself allocated on the heap via new: 0x15405f3d5f0
```

Real, direct, concrete proof: `stackObject`'s own address and its own
first member's address (`runCount`, sitting at the very start of the
object with no padding before it) are identical, `0x10c7dffc60` — per
this lesson's own **automatic storage** entry, this is real memory
belonging to `main`'s own stack frame. `label`'s own real buffer,
`0x15405f32320`, and a second, entirely separate `Probe` object,
constructed via `std::make_unique` directly on the heap,
`0x15405f3d5f0`, both sit in a genuinely different, far higher numeric
region than the stack address — real, direct evidence that **dynamic
storage**, per this lesson's own Terms entry, is not merely a different
*concept* from automatic storage; it is a different, real region of
this machine's own address space, confirmed by an actual run, not
assumed from a diagram.

### SE Lens

The principle this whole comparison makes concrete: **choosing where a
value lives is a real, consequential decision, not an implementation
detail a managed runtime quietly makes on a program's own behalf**.
Every prior phase's own object — every C# object, every Java object,
every Kotlin object — lived in exactly one place, a managed heap, with
no real alternative and no real choice for a programmer to make; this
whole C++ phase, by contrast, has required a real, deliberate decision
at every single point something was created: `Service` itself, always
automatic storage, tied to a scope; `label`, always dynamic storage,
because its own real size isn't known until runtime and its own real
lifetime needs to outlive any single expression. The real, honest
tradeoff, traced across this entire phase: automatic storage costs
nothing to allocate or release and is always safe from leaks (Lesson
4.3's and 4.4's own real, proven guarantee) but must fit a size known in
advance and cannot outlive its own declaring scope; dynamic storage can
be sized at runtime and outlive any single scope, but requires exactly
the real discipline Lessons 4.5 through 4.9 spent building — first by
hand, then delegated to `unique_ptr` and `shared_ptr` — to avoid leaking
or double-freeing it.
