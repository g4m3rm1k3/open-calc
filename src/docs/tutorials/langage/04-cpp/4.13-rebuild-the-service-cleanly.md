  `const char*` view of the string's own real characters, terminated by
  a real `'\0'` — the bridge between `std::string`'s own modern
  interface and the raw-`char*`-expecting code (`Logger::log`) this
  phase has used throughout.

## Concept Unit: `std::string` — The Tool This Phase Was Teaching Toward

### The Problem

`label`, since Lesson 4.5, has needed real, manual work at every real
touch point: `std::strlen` plus `new char[]` plus `std::strcpy` in the
constructor; `.get()` at every read; explicit copy and move logic
(Lessons 4.7, 4.8) before `unique_ptr` (Lesson 4.9) took over the
memory management specifically, still leaving `.get()` calls throughout.
Every one of those real, necessary lessons — Lessons 4.5 through 4.9 —
exists so this exact moment can ask a real question with real
understanding behind it: was any of that manual work actually necessary
for a dynamically-sized string, specifically, or was it teaching a
general skill using a case the standard library had already solved?

> **Stop and try it yourself first:** Lesson 4.9's own real, central
> claim was that `unique_ptr` already solves exclusive-resource-
> ownership correctly, once, so individual classes don't have to
> reinvent it. Given that a dynamically-sized, owned string is *also* a
> common enough real need that the standard library might reasonably
> have solved it once too — and given this lesson's own real,
> verified proof that `std::string`'s own move behavior already matches
> everything Lesson 4.8 built by hand — what real, remaining reason
> would `Service` have to keep managing `label` as a raw `char*` at
> all, wrapped or not?

### Mechanical Walkthrough

- **`std::string label;`** — a plain member, per Lesson 4.2's own full
  treatment of member declarations — no wrapper type needed at all;
  `std::string` already *is* an owning, RAII type, per this lesson's own
  Terms entry.
- **`Service(std::string name, ...)`** — takes `name` *by value*, a
  real, deliberate, idiomatic choice: when the caller already has a
  temporary (`Service("Order Processor", logger)`, this program's own
  real call sites), the `std::string` is constructed once, directly, and
  then moved into `label` with no extra copy at all; when a caller has
  an existing named `std::string` instead, exactly one real copy happens
  — either way, never more than the genuinely necessary minimum, without
  needing two separate overloads to express it.
- **`label(std::move(name))`** — the member initializer list, per Lesson
  4.2's own full treatment, using `std::move`, per Lesson 4.8's own full
  treatment, to transfer `name`'s own real characters into `label`
  rather than copying them a second, unnecessary time.
- **`logger(std::move(sharedLogger))`** — the identical real idiom
  applied to the `shared_ptr` parameter too — moving a `shared_ptr`
  avoids the real, extra atomic reference-count increment-then-decrement
  a plain copy would otherwise cost, real, if small, avoidable work this
  lesson's own earlier version (Lesson 4.10) never bothered to avoid.
- **`if (!label.empty())`** — `std::string::empty()`, a real, standard
  member function, replacing Lesson 4.9's own `if (label)` (a
  `unique_ptr`'s own boolean conversion) — the identical real *purpose*
  (detecting a moved-from object) expressed through `std::string`'s own
  interface instead.
- **`label.c_str()`** — per this lesson's own Objects-and-methods entry:
  the bridge between `std::string` and `Logger::log`'s own `const char*`
  parameter, replacing `unique_ptr`'s own `.get()`.

## Concept Unit: A Deliberate Choice, Stated Explicitly

### The Problem

`std::string`, unlike `unique_ptr`, has a real, working copy
constructor — nothing about `Service`'s own new representation forces
it to remain move-only the way Lesson 4.9's `unique_ptr` did. Should
`Service` become copyable again, now that nothing technically prevents
it?

> **Stop and try it yourself first:** Lesson 4.9's own real, cited
> evidence proved `unique_ptr`'s own copy constructor is `= delete`d,
> which is *why* `Service` became move-only there — a real, direct
> consequence of that specific member's own type, not a deliberate
> choice `Service` itself made on its own behalf. Given that
> `std::string` and `std::shared_ptr` — `Service`'s own only two real
> members besides a plain `int` — are *both* genuinely copyable, what
> real, remaining reason, if any, would `Service` have to still refuse
> copying, now that nothing about its own members forces that refusal
> anymore?

### Introduce the Concept in Isolation

No separate throwaway lab — this unit's own real subject is a design
decision about the real, committed `Service` itself, tested directly
against it.

Real, direct proof the decision still holds, once stated explicitly:

```cpp
Service(const Service&) = delete;
Service& operator=(const Service&) = delete;
```

```

```

The identical real refusal as Lesson 4.9 — but the compiler's own note

deliberate design statement: `Service` represents one real, running
thing, tied to its own real `Logger` and its own real run count; letting
two independent copies exist, each believing itself the sole
authoritative record of "this service's own history," would be a real,
conceptual bug even though nothing about `std::string` or `shared_ptr`
would make it a *memory-safety* one the way Lesson 4.7's own raw
`char*` bug was.

## Connect the Pieces
