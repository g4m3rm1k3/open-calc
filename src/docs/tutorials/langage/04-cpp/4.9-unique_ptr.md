answer to that exact maintenance burden, and, in getting there, proves —

## Terms used in this lesson

- **`std::unique_ptr<T>`** — a real, standard library class template
  that owns a single, dynamically-allocated object (or, with the
  `T[]` form this lesson uses, an array) exclusively — no other
  `unique_ptr` can ever point at the same real memory at the same time,
  a guarantee enforced by the type itself, not by convention. It exists
  to give exactly the ownership discipline Lessons 4.5 through 4.8 built
  by hand — one real owner, automatic release at the owner's own
  destruction — as a real, reusable type, rather than requiring every
  class that owns a resource to reinvent it.
- **Exclusive ownership** — the specific real guarantee `unique_ptr`
  makes and enforces: exactly one `unique_ptr` object ever owns a given
  resource at once. It exists as `unique_ptr`'s own entire reason for
  being, proven concretely below to be enforced by the compiler itself,
  not merely documented as an intended usage pattern.
- **`= default`** — written after a special member function's own
  declaration in place of a body, this tells the compiler to generate
  that specific function's own default implementation explicitly,
  rather than leaving it to decide on its own whether to generate one at
  all. It exists for exactly this lesson's own real situation: a
  function the compiler *could* generate correctly on its own, in
  principle, but won't, automatically, once a class has also declared
  certain other special member functions — proven concretely below.
- **The Rule of Special Member Functions** — the real, load-bearing C++
  rule governing exactly when the compiler will and won't automatically
  generate a constructor, destructor, copy constructor, copy assignment
  operator, move constructor, or move assignment operator on a class's
  own behalf: declaring any one of them changes what the compiler will
  generate for the others, in ways this lesson proves directly rather
  than merely states.

  - *Its use:* `Service`'s own new, sole way of owning `label`'s real

  - *Depends on:* The `unique_ptr` it's called on.
  - *Connects to:* Called by `Service`'s own constructor, `run()`, and

  - *Shape:* A public API surface.

## Concept Unit: `unique_ptr` — Exclusive Ownership, Enforced by the Type

### The Problem

`Service`'s own manual `new char[]` and matching `delete[]`, spread
across four separate special member functions since Lessons 4.5 through
4.8, all exist to enforce one real rule: exactly one owner, ever.
Does a real library type already exist that enforces that same rule
directly, removing the need to write it out by hand at all?

> **Stop and try it yourself first:** Lesson 4.7's own real, deleted-by-
> hand copy operations (`Service(const Service&) = delete;`, not
> actually written in this curriculum's own real code, but a real,
> valid way to have solved that lesson's own problem) would have
> refused copying outright. Given that `unique_ptr`'s own entire real
> purpose, per this lesson's own Terms entry, is exclusive ownership,
> what would you predict happens if a class holding a `unique_ptr`
> member is copied — does the *class* need to explicitly refuse

### SE Lens

The principle is **encoding a design decision once, in a reusable type,
instead of re-deriving it by hand in every class that needs it**.

## Concept Unit: A Real Trap — Keeping the Destructor Costs the Free Move

### The Problem

Lesson 4.8's own real destructor exists for one specific, real reason:
printing `"... destroyed."` — its own `delete[]` call is no longer
needed at all, since `unique_ptr`'s own destructor already does that
automatically. Removing `Service`'s own destructor entirely would be the
simplest possible fix — but this whole phase's own real, observable
output, since Lesson 4.4, has depended on that printed line. Does

> **Stop and try it yourself first:** This lesson's own first unit

Now the real trap, adding back exactly the one thing `Service` still
needs — a destructor, purely for its own printed message:

```cpp
class Named {
private:
    std::unique_ptr<char[]> label;

public:
    Named(const char* name) : label(new char[std::strlen(name) + 1]) {
        std::strcpy(label.get(), name);
    }

    ~Named() {
        if (label) {
            std::cout << label.get() << " destroyed." << std::endl;
        }
    }
};

int main() {
    Named a("A");
    Named b = std::move(a);
}
```

Attempting to compile this session
(`verification/4.9/lab_dtor_suppresses_move.cpp`):

```
lab_dtor_suppresses_move.cpp:24:26: error: use of deleted function 'Named::Named(const Named&)'
```

Real, direct proof of the trap: adding *only* a destructor — nothing
about copying or moving mentioned anywhere — silently suppressed the
compiler's own automatic move-constructor generation entirely.
`std::move(a)` then fell back to the *copy* constructor instead (the
only other candidate the compiler still considers), which is itself
deleted, per this lesson's own first unit. The destructor's own mere
presence changed what the compiler was willing to generate elsewhere —
this is the real, load-bearing content of this lesson's own Terms entry
for the Rule of Special Member Functions, proven directly rather than
recited.

The real fix — explicitly restoring what the destructor's own presence
suppressed:

```cpp
Named(Named&& other) = default;
Named& operator=(Named&& other) = default;

~Named() {
    if (label) {
        std::cout << label.get() << " destroyed." << std::endl;
    }
}
```

```

```

Real, direct proof the fix works: this compiles and runs correctly, and
only *one* `"destroyed"` line prints for the two real objects (`a` and
`b`) — `a`, moved-from, has an empty `unique_ptr` (per Lesson 4.5's own
real discovery from `char*`'s own null-check behavior, `unique_ptr`
itself is checkable in a boolean context, `if (label)`, true only when
it actually owns something), so its own destructor's guard correctly
skips the print; `b`'s own destructor runs normally.
