**What you need to know first:** Lesson 4.5 gave `Service` a real,

## Terms used in this lesson

- **Copy constructor** — a real, special constructor, called
  automatically whenever a new object is *initialized* from an existing
  one of the same type — `Counter b = a;`, this lesson's own real
  example, or `Counter b(a);`, an equivalent alternate syntax not used
  in this lesson's own real code. It exists as the specific, guaranteed
  moment C++ gives a class to decide, deliberately, what "becoming a
  copy of this other object" actually means, rather than leaving it
  undefined.
- **Copy assignment operator (`operator=`)** — a real, separate special
  member function, called whenever an *already-existing* object is
  assigned the value of another object of the same type —
  `c = a;`, this lesson's own real example, where `c` already exists
  before this line runs. It exists as a genuinely different moment from
  copy construction: an object being overwritten, potentially discarding
  whatever it already held, rather than an object coming into existence
  for the first time.
- **`this`** — inside any member function, an implicit pointer to the
  real object the function was called on. It exists because a member
  function's own body needs a way to refer to "the whole object I'm
  running on," not just its individual members by name — `*this`
  (dereferencing it) is how a member function returns or refers to the
  entire object itself, this lesson's own real, necessary use of it,
  inside `operator=`'s own body, to let assignment expressions chain
  (`a = b = c;`, not used in this lesson's own real code, but the real
  reason `operator=` returns a reference to `*this` rather than nothing
  at all).
- **Value semantics** — the general expectation that copying an object
  produces a second, fully independent object, where mutating one never
  affects the other. It exists as the default, intuitive behavior every
  plain value (an `int`, this lesson's own real proof) already has in
  every language this curriculum has taught, including C++'s own
  compiler-generated copy behavior for a class holding only plain values
  — proven correct, for exactly that case, this lesson; proven to break
  down the moment a class owns a raw resource instead, Lesson 4.7's own
  real subject.

## Concept Unit: The Copy Constructor — `Counter b = a;`

### The Problem

`Service`'s own runCount, per Lesson 4.5, is a plain `int`. If two
`Service` objects existed, mutating one's own `runCount` should never
affect the other — the same real expectation every prior phase's own
object already met, automatically, without ever needing to think about
it. Does C++ guarantee the identical result, or does copying an object
need something explicit written to make that true?

> **Stop and try it yourself first:** Lesson 4.2 already showed C++
> generates a default constructor's own real behavior only when a class
> writes no constructor of its own at all — the moment `Service` wrote
> its own real constructor, that automatic generation stopped. Given
> that pattern, what would you predict about copying: does C++ *always*
> generate some default way to copy an object, or does a class need to
> write its own copying logic explicitly the same way it needed to write
> its own regular constructor?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.h`:

```cpp
#include <iostream>

class Counter {
public:
    int count;

    Counter(int startingCount) : count(startingCount) {
    }
};

int main() {
    Counter a(5);
    Counter b = a;
    b.count = 99;
    std::cout << a.count << std::endl;
    std::cout << b.count << std::endl;
}
```

Run this session (`verification/4.6/lab_copy_constructor.cpp`):

```
5
99
```

`Counter b = a;` — real, direct proof C++ *does* generate a default way
to copy, with no copy-specific code written anywhere in `Counter` itself
— and it produces genuinely independent state: `b.count` was changed to
`99` afterward, and `a.count` still reports its own original `5`. This
automatic, per-member copy is called the **copy constructor**, per this
lesson's own Terms entry — real proof this general expectation, **value
semantics**, holds here without any extra work.

Now the same real question this unit's own Socratic prompt implicitly
raised — is anything actually *happening*, distinctly, at the moment
`Counter b = a;` runs, or is this indistinguishable from any other
initialization? A version with a real, explicit copy constructor,
printing its own name:

```cpp
Counter(const Counter& other) : count(other.count) {
    std::cout << "copy constructor" << std::endl;
}
```

Run this session, as part of a larger real experiment
(`verification/4.6/lab_which_fires.cpp`, its full real evidence in this
lesson's own next unit): `Counter b = a;` really does print `copy
constructor` — real, direct proof this is a genuine, distinct, callable
function, not merely a label for "whatever initialization normally
does."

### Mechanical Walkthrough

- **`Counter b = a;`** — despite the `=`, this is *not* assignment; per
  this lesson's own Terms entry, any declaration that initializes a new
  object from an existing one of the same type — this exact syntax
  included — invokes the copy constructor, never `operator=` (this
  unit's own next-unit real proof makes the distinction concrete).
- **`Counter(const Counter& other) : count(other.count) { ... }`** — a
  real, explicit copy constructor: its own parameter, `const Counter&
  other`, is a *reference* to the object being copied from (not yet
  given its own full treatment — a reference here behaves, for this
  lesson's own real purpose, as an alias for the original object,
  avoiding a redundant, recursive copy of `other` itself just to read
  from it), marked `const` so this constructor promises not to modify
  the object it's copying from. The member initializer list,
  `count(other.count)`, per Lesson 4.2's own full treatment, initializes
  `count` directly from `other`'s own real value.

### CS Lens

A language distinguishing "becoming a copy" from "being overwritten by a
copy" as two real, separately-hookable moments is a real, if narrow,
design choice most languages in this curriculum never needed to make.

```
Also recognized in: C++'s own operator-overloading system broadly (this
whole lesson's own second unit is a direct instance of it); very few
other languages taught in this curriculum expose an equivalent
construction/assignment split as two separately overridable real
mechanisms — Python's own `__init__` versus `__copy__`/`__deepcopy__`
(via the `copy` module) is the closest real analog, achieving a similar
real split through a different, library-based mechanism rather than a
core language feature
```

### SE Lens

The principle is **giving a class a real, guaranteed hook at the exact
moment copying happens, rather than leaving "what does copying this
object mean" implicit**. The real alternative — no such hook at all,
copying always meaning nothing more than "whatever the compiler
happens to do by default" — is exactly what every prior phase's own
managed language effectively provides, safely, because nothing owned in
those languages could ever be silently duplicated in a way that broke
anything. C++'s own real cost of offering this hook: a class that *needs*
custom copying behavior (Lesson 4.7's own real, upcoming subject) has to
actually write it, correctly, by hand — the compiler's own default,
proven safe here for a plain `int`, offers no warning at all when it
stops being safe for something else.

## Concept Unit: Copy Assignment — `c = a;`, on an Object That Already Exists

### The Problem

`c = a;`, where `c` already exists, *looks* like the identical operation
as `Counter b = a;` — the same `=`, the same right-hand object. Is it
actually the same real mechanism running twice, or something genuinely
different?

> **Stop and try it yourself first:** A copy constructor, per the
> previous unit, runs at the exact moment a *new* object comes into
> existence. `c = a;`, with `c` already fully constructed and holding
> its own real value before this line runs, is not a moment of
> construction at all. Given that, what real, different problem would a
> class's own copying logic need to solve here that construction never
> had to — specifically, what does `c` already have, before this line
> runs, that a brand-new object never does?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.h`, extending the previous
unit's own explicit `Counter`:

```cpp
#include <iostream>

class Counter {
public:
    int count;

    Counter(int startingCount) : count(startingCount) {
    }

    Counter(const Counter& other) : count(other.count) {
        std::cout << "copy constructor" << std::endl;
    }

    Counter& operator=(const Counter& other) {
        std::cout << "copy assignment" << std::endl;
        count = other.count;
        return *this;
    }
};

int main() {
    Counter a(5);
    Counter b = a;
    Counter c(1);
    c = a;
}
```

Run this session (`verification/4.6/lab_which_fires.cpp`):

```
copy constructor
copy assignment
```

Real, direct, unambiguous proof: `Counter b = a;` printed `copy
constructor`; `c = a;` — `c` already holding its own real value, `1`,
from its own prior, separate construction — printed `copy assignment`
instead. These are two genuinely different real functions, chosen
automatically based on whether the object receiving the value is being
created right now or already existed.

A second real proof — that `operator=`, like the copy constructor,
still produces genuinely independent state:

```cpp
int main() {
    Counter a(5);
    Counter c(1);
    c = a;
    c.count = 99;
    std::cout << a.count << std::endl;
    std::cout << c.count << std::endl;
}
```

Run this session (`verification/4.6/lab_copy_assignment.cpp`, using the
plain, default-generated `operator=` rather than the printing version
above — the identical real result either way):

```
5
99
```

The identical real proof as the previous unit's own copy constructor —
`a`'s own `count` is untouched by mutating `c` after the assignment.

### Mechanical Walkthrough

- **`Counter& operator=(const Counter& other)`** — a real, explicit
  copy assignment operator: `operator=` is the real function name this
  syntax overloads, per Lesson 4.1's own treatment of operator
  overloading (`operator<<`, there); its parameter, `const Counter&
  other`, is shaped identically to the copy constructor's own, for the
  identical reason. Its own return type, `Counter&` — a reference to a
  `Counter`, not a plain `Counter` — is what this lesson's own Terms
  entry for `this` exists to explain.
- **`count = other.count;`** — ordinary member assignment, already
  familiar syntax, copying `other`'s own current value into `count` —
  the real, distinguishing fact being *when* this runs (on an object
  that already exists, potentially already holding a real, different
  value being overwritten), not *how* the assignment itself works.
- **`return *this;`** — per this lesson's own Terms entry for `this`:
  `this` is a pointer to the real object `operator=` was called on;
  `*this` dereferences it, yielding the object itself, returned by
  reference so an expression like `c = a;` itself evaluates to `c`'s own
  new value — necessary for chained assignment (`x = y = z;`) to work at
  all, though this lesson's own real code never chains one.

### SE Lens

The principle is **an assignment operator's own real job is discarding
what an object already held, safely, before adopting new state** — a
genuinely different responsibility from a constructor's own job
(bringing a brand-new object into existence with nothing to discard).
This lesson's own real `Counter` never actually has anything worth
discarding (a plain `int` simply gets overwritten, no cleanup needed) —
the real, honest stakes of this distinction only become concrete once a
class owns something that *does* need real cleanup before being
overwritten, which is precisely `Service`'s own real situation since
Lesson 4.5, and precisely why this lesson's own real project code stays
untouched: writing a correct `operator=` for `Service` right now, before
seeing what goes wrong with the naive, compiler-generated version, would
skip past the actual lesson Lesson 4.7 exists to teach.
