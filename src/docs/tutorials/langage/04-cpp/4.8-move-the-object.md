# Lesson 4.8: Stealing the Buffer Instead of Copying It

**What you will build:** `Service` gains a move constructor and move
assignment operator — transferring `label`'s own real pointer directly
instead of allocating a new buffer and copying characters into it — plus
a real, necessary guard in the destructor, discovered along the way, not
planned in advance. `Program.cpp` gains a real `std::move` call, proving
the transfer for real. The transferable problem: Lesson 4.7's own fix
works, but pays a real, avoidable cost — allocation plus a full character
copy — every single time, even in the common real case where the
*original* object is about to be discarded anyway and nothing would
actually be lost by simply handing its buffer to the new object
directly.

**What you need to know first:** Lesson 4.7 gave `Service` a correct,
safe deep-copy constructor and assignment operator. This lesson assumes
both and builds a real, separate alternative alongside them, not a
replacement. Lesson 4.4's own real, guarded destructor is revisited here
too, once this lesson's own real experimentation surfaces a genuine new
requirement it didn't originally anticipate.

## Terms used in this lesson

- **Move constructor / move assignment operator** — a real, separate
  pair of special member functions (alongside the copy constructor and
  copy assignment operator, Lessons 4.6 and 4.7), invoked instead of
  copying when the object being taken from is one the compiler can tell
  is about to be discarded, or is explicitly marked as such. They exist
  to make "transfer ownership of a resource from one object to another"
  a real, distinct, cheaper operation than "duplicate the resource,"
  for exactly the case Lesson 4.7's own deep copy always pays full
  price for even when nothing would be lost by simply transferring
  instead.
- **Rvalue reference (`Type&&`)** — a reference type, distinct from the
  ordinary `Type&` reference already used in Lesson 4.6's own copy
  constructor, that can only bind to a real or explicitly-marked
  *temporary* value — one the compiler can be confident nothing else
  still needs afterward. It exists as the real, compile-time signal that
  lets the compiler choose the move constructor over the copy
  constructor: a function taking `Type&&` can only be called with
  something the caller has, one way or another, marked as safe to
  plunder.
- **`std::move`** — a real standard library function that does no
  actual moving itself — it *casts* its argument to an rvalue reference,
  telling the compiler "treat this named, ordinarily-still-usable value
  as if it were a temporary, safe to steal from." It exists because a
  named local variable, unlike a genuine temporary, is not automatically
  treated as moveable by the compiler (the compiler has no way to know,
  on its own, that a program won't use that name again) — `std::move` is
  how a programmer states that intent explicitly.
- **Moved-from state** — the real, required condition a move
  constructor or move assignment operator must leave its *source*
  object in: not necessarily holding any meaningful value anymore, but
  guaranteed safe to destroy and safe to assign a new value to. This
  lesson's own real experimentation discovers, rather than assumes, one
  specific, concrete way to fail this guarantee — and fixes it.

## Concept Unit: `&&` and `std::move` — Transferring, Not Duplicating

### The Problem

`Service copy = service;`, from Lesson 4.7, always allocates a new
buffer and copies every character — real, necessary work when `service`
itself needs to keep existing afterward, which it does in that exact
line. But a real, common situation is different: constructing a new
object directly *from* one that's about to be discarded regardless —
does C++ offer any way to skip the allocation and the character copy
entirely in that specific, real case?

> **Stop and try it yourself first:** Lesson 4.7's own copy constructor
> takes `const Service& other` — a reference to an object the
> constructor promises not to modify, because the original might still
> be needed by whoever called it. If a *different* constructor existed,
> one that was allowed to reach into `other` and actually change it —
> specifically, to steal its buffer and leave it empty — what real,
> different guarantee would the *caller* need to make, before the
> compiler could safely let that constructor run instead of the ordinary
> copy constructor?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.h`:

```cpp
#include <iostream>
#include <cstring>

class Named {
public:
    char* label;

    Named(const char* name) {
        label = new char[std::strlen(name) + 1];
        std::strcpy(label, name);
        std::cout << "constructed" << std::endl;
    }

    Named(const Named& other) : label(nullptr) {
        label = new char[std::strlen(other.label) + 1];
        std::strcpy(label, other.label);
        std::cout << "copy constructed" << std::endl;
    }

    Named(Named&& other) noexcept : label(other.label) {
        other.label = nullptr;
        std::cout << "move constructed" << std::endl;
    }
};

int main() {
    Named a("A");
    Named b = std::move(a);
    std::cout << "a.label is null: " << (a.label == nullptr) << std::endl;
    std::cout << b.label << std::endl;
}
```

### Mechanical Walkthrough

- **`Service(Service&& other) noexcept`** — per this lesson's own Terms
  entry for **rvalue reference**: `Service&&`, not `const Service&`
  (Lesson 4.7's own copy constructor's own parameter type) — this
  constructor is only ever selected when the argument is something the
  compiler (or an explicit `std::move`) has marked as safe to modify.
  `noexcept` — a real, new keyword, promising this constructor never
  throws an exception — is not just documentation: code elsewhere in the
  standard library (not exercised by this lesson's own real code) makes
  real, different, safety-related decisions based on whether a type's
  own move operations are marked `noexcept`, since a throwing move
  partway through could leave data in a genuinely unrecoverable state.
- **`: runCount(other.runCount), label(other.label)`** — the member
  initializer list, per Lesson 4.2's own treatment, now initializing two
  members from `other`'s own current real values — `label` copied as a
  plain pointer value here (an address, exactly like Lesson 4.7's own
  first unit's real "shallow copy" evidence) — the real, deliberate
  point of a move: this specific copy of the *address* is intentional
  and correct here, unlike the accidental shallow copy Lesson 4.7's own
  first unit proved unsafe, because this constructor's own body,
  immediately after, empties `other` out completely.
- **`other.label = nullptr;`** — per this lesson's own Terms entry for
  **moved-from state**: `other` no longer owns any real buffer at all —
  the two objects no longer share the identical address the way Lesson
  4.7's own broken shallow copy left them.
- **`other.runCount = 0;`** — resets the source's own count too,
  leaving `other` in a real, sensible, fully-valid `Service`-shaped
  state (an empty label and a zero count) — the real reason it's
  worth doing this and not merely leaving `runCount` whatever it
  happened to be: `other` still exists, and its own destructor will
  still run later; the more predictable its own state, the less
  surprising that eventual destruction is to reason about.

### CS Lens

Transferring ownership instead of duplicating, whenever the source no
longer needs what it held, is a real, recurring idea beyond just C++'s
own move semantics.

```
Also recognized in: Rust's own move semantics (this curriculum's own
later Phase 12) — the *default* behavior there, not an opt-in mechanism
a class has to write by hand the way C++ requires here; a bank transfer
moving funds from one account to another rather than duplicating the
money into both; a physical handoff of a single, non-duplicable object
(passing a book to someone, rather than photocopying it)
```

### SE Lens

The principle is **not paying for a guarantee (independence) the
situation doesn't actually need**. Lesson 4.7's own deep copy always
buys real independence — two fully separate buffers, safe no matter
what either object does afterward — a guarantee genuinely necessary when
both objects need to go on existing, and genuinely wasted when one is
about to be discarded regardless. Move semantics let a program state,
explicitly, which situation it's actually in, and pay only for what that
specific situation needs. The real cost: a class offering both real
options now has *four* separate special member functions
(copy-construct, copy-assign, move-construct, move-assign) that all
have to agree with each other about what a valid `Service` looks like —
a maintenance burden this lesson's own next unit finds a real, concrete
instance of, not hypothetically, but by actually testing it.

## Concept Unit: A Guarantee the First Unit's Own Lab Never Actually Tested

### The Problem

`Service`'s own destructor, unchanged since Lesson 4.4, unconditionally
prints `label` and calls `delete[] label`. A moved-from `Service`, per
this lesson's own first unit, has `label == nullptr`. `delete[]
nullptr` is real, well-defined, safe C++ — but is printing a null
pointer through `std::cout` equally safe?

> **Stop and try it yourself first:** This lesson's own first unit's own
> isolated `Named` lab never let its own moved-from `a` object actually
> get destroyed and printed — `main` simply ended right after proving
> `a.label` was `nullptr`. Given that `Service`'s own real destructor
> unconditionally tries to print `label`, what do you predict happens
> once a moved-from `Service` — one whose own `label` is genuinely
> `nullptr` — actually reaches the end of its own scope and its
> destructor runs for real?

checks for exactly this case and sets the stream's own `badbit` instead
of dereferencing a null pointer. But once `badbit` is set, *every*
subsequent insertion into that same stream — `std::cout`, this lesson's

no exception, until the stream is explicitly cleared (never done
anywhere in this lesson's own real code). This is a real, genuine
problem `Service`'s own current destructor is exposed to the moment a
moved-from object is destroyed: not a crash, but something arguably
worse for a real program — every observable output from that point
onward simply vanishes, silently.

- **`moved.run();`** and its own `getRunCount()` read — deliberately the
