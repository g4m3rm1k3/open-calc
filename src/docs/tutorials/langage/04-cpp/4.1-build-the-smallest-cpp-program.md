## Terms used in this lesson

- **Compilation** — the process of translating source code into a form
  a machine can actually execute, done once, ahead of time, by a
  separate program (the compiler) rather than interpreted or
  just-in-time translated while the program runs. It exists because
  translating source text into machine instructions is expensive work a
  program shouldn't have to redo every single time it starts.
- **Executable** — the real, standalone output file compilation
  produces: a file containing actual machine instructions the operating
  system can load directly into memory and run, with no separate
  runtime, virtual machine, or interpreter required to make sense of it.
  This is a real, concrete difference from every prior phase's own
  compiled output: `javac` and `kotlinc` both produce `.class`/`.jar`
  files holding JVM *bytecode* — a format only the JVM itself knows how
  to execute, requiring `java` to be invoked separately to run it at
  all; `g++`, this lesson's own compiler, produces a real `.exe` the
  operating system itself runs directly, the same way it runs any other
  program on the machine.
- **Preprocessor** — a real, separate, textual step that runs *before*
  actual compilation begins, processing lines starting with `#`
  (**preprocessor directives**) by literally rewriting the source file's
  own text — substituting, deleting, or inserting text — before the
  compiler proper ever sees the result. It exists because C++ inherited
  this mechanism directly from C, predating the more structured
  module/import systems every other language in this curriculum already
  has; `#include`, this lesson's own directive, is one specific
  preprocessor instruction, not a language keyword the compiler itself
  interprets.
- **`#include`** — a preprocessor directive that replaces its own line,
  verbatim, with the *entire real text content* of the named file. It
  exists because C++ (again, inherited from C) has no built-in way for
  one source file to know that a type or function declared in another
  file exists, other than literally pasting that file's own declarations
  in before compilation begins — unlike Java's `import` or Kotlin's own
  file-visibility rules, which resolve symbols against already-compiled
  metadata, `#include` resolves everything through raw, textual
  substitution, proven concretely below.
- **Header file (`<iostream>`)** — a file, conventionally ending `.h` or
  with no extension for the C++ standard library's own headers,
  containing declarations (not full implementations) meant to be
  `#include`d into other source files. `<iostream>`, this lesson's own
  header, declares the standard library's own input/output facilities —
  `std::cout` among them — without containing their full, compiled
  implementation, which is supplied separately by the standard library
  itself at the final linking step.
- **Namespace (`std::`)** — a named region grouping a set of names
  (types, functions, variables) so they don't collide with identically-
  named things declared elsewhere. `std` is the C++ standard library's
  own namespace; `std::cout` names `cout` specifically as the one
  declared inside `std`, distinguishing it from any other `cout` a
  program might otherwise declare itself. This exists because C++, unlike
  Java or Kotlin (where every standard library type already lives inside
  a real package a programmer explicitly imports), has no package system
  of its own for its standard library — namespaces are C++'s own
  mechanism for the identical underlying problem, name collision.
- **Stream insertion operator (`<<`)** — the same token used for
  bitwise left-shift on integers, *overloaded* (given a completely
  different, additional real meaning when its left operand is a stream
  type like `std::ostream`) to mean "write this value to this output
  stream." It exists so that writing output can be expressed as a short,
  chainable expression (`cout << a << b`) rather than a sequence of
  separate method calls — this lesson's own first real encounter, in
  this curriculum, with operator overloading: the identical symbol
  genuinely means two unrelated things depending on the types on either
  side of it, resolved entirely at compile time from those types.

## Objects and methods used

- **`std::cout`**
  - *What it is:* A real, single, global object representing the
    program's own standard output stream.
  - *Implementation:* Its real declaration, found this session in the
    actual header this machine's own compiler ships
    (`C:\mingw64\include\c++\16.2.0\iostream`, line 65):

    ```cpp
    extern ostream cout;		///< Linked to standard output
    ```

    `extern` means this line only *declares* that `cout` exists and
    names its type (`ostream`, itself a `typedef` for a real, heavily
    templated class this lesson does not need to open) — the object
    itself is actually constructed once, elsewhere, inside the
    standard library's own already-compiled code, which this program
    links against rather than compiles itself (this lesson's own
    Commands Needed, below, shows that link step actually happening).
    This is real, honest proof that `<iostream>`'s own `#include`
    supplies a *declaration* — "this exists, here's its type" — not a
    full implementation; the implementation itself lives in code this
    lesson's own compiler never even looks at.
  - *Its use:* The left operand of this lesson's own `<<` chain — every
    real, observable output this program produces flows through it.
  - *Type:* A global object of type `std::ostream` (an alias for
    `std::basic_ostream<char>`).
  - *Responsibility:* Buffering and eventually writing characters to the
    real, operating-system-level standard output stream.
  - *Depends on:* Nothing this program supplies — it is already
    constructed and connected to the real console before `main` itself
    ever starts running.
  - *Connects to:* The left-hand operand of `operator<<`, below; its own
    internal state is what `std::endl`, below, flushes.
  - *Shape:* A public API surface — the standard, global handle to a
    running C++ program's own standard output, analogous in role (not
    in mechanism) to Kotlin's `System.out` that `println` itself wrapped
    in Lesson 3.1.

- **`operator<<(ostream&, const char*)`**
  - *What it is:* A real, free (non-member) function overload of `<<`,
    specifically for writing a plain C-style string to an output stream.
  - *Implementation:* Declared, per this session's own real search of
    the same shipped header set
    (`C:\mingw64\include\c++\16.2.0\bits\ostream.tcc`, line 311), as:

    ```cpp
    template<typename _CharT, typename _Traits>
      basic_ostream<_CharT, _Traits>&
      operator<<(basic_ostream<_CharT, _Traits>& __out, const char* __s)
    ```

    Its real body (read in full this session, not reproduced here — long
    enough, with its own internal exception-safety handling, that
    showing it whole would bury the one fact that actually matters for
    this lesson) does one concrete thing worth stating plainly: it
    **returns a reference to the same stream it was given** (`__out`,
    typed as the same `basic_ostream<...>&` it received). That single
    fact is what makes `std::cout << "a" << "b"` legal at all: the first
    `<<` call evaluates to `std::cout` itself again, so the second `<<`
    has a real, valid left operand to work on, chained exactly the way
    this lesson's own real code (`... << "Service is running." <<
    std::endl`) relies on.
  - *Its use:* Called once in this lesson's own real code, writing
    `"Service is running."` — a `const char*` once the string literal
    decays to a pointer — to `std::cout`.
  - *Type:* A free function template, not a member of any class.
    Signature (as declared above): takes an `ostream&` and a `const
    char*`, returns `ostream&`.
  - *Responsibility:* Writing the given string's own characters to the
    given stream, character by character, and reporting failure through
    the stream's own state rather than a return value (its return value
    is always the stream itself, per above, never a success/failure
    flag).
  - *Depends on:* The stream it's writing to, and the string it's
    writing.
  - *Connects to:* Called with `std::cout` as its left operand; its own
    return value becomes the left operand of the next `<<` in the same
    chain, here `std::endl`'s own call.
  - *Shape:* A public API surface — part of the same standard library
    boundary `std::cout` itself belongs to.

- **`std::endl`**
  - *What it is:* A real function — a **stream manipulator** — that,
    when passed to `<<`, writes a newline and immediately flushes the
    stream's own internal buffer.
  - *Implementation:* Its real, complete body, found this session in
    `C:\mingw64\include\c++\16.2.0\ostream`, lines 69–72:

    ```cpp
    template<typename _CharT, typename _Traits>
      inline basic_ostream<_CharT, _Traits>&
      endl(basic_ostream<_CharT, _Traits>& __os)
      { return flush(__os.put(__os.widen('\n'))); }
    ```

    Short enough to explain in full, and it does exactly two real
    things: `__os.widen('\n')` converts the plain `'\n'` character to
    whatever character type the stream itself actually uses (relevant
    for wide-character streams, not this lesson's own `cout`, but real
    regardless), and `__os.put(...)` writes that one character; the
    *whole* result of that is then passed to `flush(...)`, which forces
    any buffered-but-not-yet-written output to actually reach the real
    output destination immediately, rather than waiting for the buffer
    to fill naturally. The real header comment directly above this
    function, quoted verbatim, states the actual tradeoff plainly:
    *"This manipulator is often mistakenly used when a simple newline is
    desired, leading to poor buffering performance."* — a plain `'\n'`
    character (not used in this lesson's own code, but real and
    available) writes a newline with no forced flush at all.
  - *Its use:* The final piece of this lesson's own `<<` chain, ending
    the printed line and ensuring it's actually visible immediately
    rather than sitting in a buffer.
  - *Type:* A free function template. Signature (as declared above):
    takes an `ostream&`, returns the same `ostream&`.
  - *Responsibility:* Writing a newline and forcing a flush — both, not
    just one; a plain `'\n'` does only the first.
  - *Depends on:* The stream it's called on.
  - *Connects to:* Called as the right-hand operand of the second `<<`
    in this lesson's own chain; itself calls `.put()` and `flush()` on
    the stream it's given.
  - *Shape:* A public API surface, the same standard library boundary as
    the other two entries above.

## Concept Unit: Compilation — A Real Pipeline, Not a Virtual Machine

### The Problem

Every prior phase's own build command — `dotnet run`, `javac` plus
`java`, `kotlinc` plus `java -jar` — ultimately produced something a
*separate* program (the CLR, the JVM) had to load and execute; none of
those compiled outputs could simply be handed to the operating system
and run on its own. Does C++'s own compiler, `g++`, work the same way —
producing an intermediate format some other program then executes — or
something genuinely different?

> **Stop and try it yourself first:** Lesson 3.3's own real, disassembled
> evidence (`javap -p Service.class`) showed that even Kotlin's own
> compiled output was real, inspectable JVM bytecode — not something the
> operating system itself could run directly; `java` always had to be
> invoked to interpret or JIT-compile it first. Given that C++ has no
> equivalent to `java` at all in this curriculum's own command history so
> far, what would you predict `g++`'s own compiled output actually is —
> another format needing its own separate runtime, or something the
> operating system can run on its own? And: if it's the latter, what do
> you think happens to `#include <iostream>`'s own declarations between
> source code and that final, runnable file — do they need to be
> *compiled into* the output at all, or handled some other way?

### Introduce the Concept in Isolation

Real, direct evidence — not throwaway code exactly, since there's no
new *language* construct to isolate yet, but a real, staged inspection

```

```

  verbatim, with the original `int main() { ... }` surviving, unchanged,
  at the very end.
- `-S` (compile to assembly): a real, human-readable 48-line assembly
  file, `out.s` — actual CPU instructions, in text form, not yet turned
  into raw binary.
- `-c` (compile to an object file): a real, 1,695-byte binary file,

This is the real, concrete answer to this unit's own Socratic prompt:
`#include <iostream>`'s own declarations are resolved almost entirely at
the *first* stage — preprocessing — by literally pasting real header
text into the source before **compilation** (this unit's own Terms
entry) even begins; the actual, compiled *implementations* those
declarations describe (the real code behind `std::cout`, `operator<<`,
`std::endl`) are supplied afterward, at a final step called **linking**
(joining this program's own compiled code together with the standard
library's own already-compiled code) — not shown as its own separate
`g++` flag above because `g++` performs it automatically as the last,
invisible step of the no-flag "full pipeline" command, producing the
one file, `Program.exe`, that needs nothing else to run.

**Ahead-of-time compilation to native machine code**, with no
intermediate virtual machine, is one real point on a spectrum every
language in this curriculum's own history so far has occupied


### SE Lens

The design principle is **trading a managed runtime's own conveniences
for direct control**. Every prior phase's own JVM or CLR provides real,
substantial services C++ programs get none of automatically: automatic
memory management (this whole phase's own real subject, starting Lesson
4.3), bytecode verification before running untrusted code, and a
runtime that can be updated independently of any program that depends on
it. C++'s own alternative — compile directly to the exact machine the
program will run on, with nothing standing between the compiled code and
the CPU — trades all of that away for the reverse: no runtime startup
cost, no background garbage collector ever pausing the program
unpredictably, and a compiled binary that needs nothing installed on the
machine it runs on beyond the operating system itself. Neither choice is
strictly better; this whole phase's own remaining twelve lessons exist
because the *cost* of C++'s own choice — a programmer, not a runtime,
now has to reason correctly about when memory is freed — is real and
substantial enough to need careful, dedicated teaching.

## Concept Unit: `#include` — Real Text, Not Magic

### The Problem

```cpp
int main() {
```

## Concept Unit: `int main()`, `std::cout`, and the Observable Line

### The Problem

With `#include <iostream>` in place, this lesson's own real code is
almost complete — `int main() { std::cout << "Service is running." <<
std::endl; }`. Every prior phase's own entry point returned nothing
observable (Kotlin's `fun main()`, Java's `void main`) — C++'s own
`main` is declared `int`. Does that return type actually have to be
supplied by the program itself, the way every other typed return in this
curriculum has required, or does `main` get special treatment?

> **Stop and try it yourself first:** In every language taught so far, a
> function declared to return a real value (Kotlin's own `fun
> getRunCount(): Int`, Lesson 3.2) has required an explicit `return`
> statement matching that type — leaving one out is a real compile
> error every time. `int main()` in C++ declares a real, non-`void`
> return type too. Given that this lesson's own real code, shown below,
> has no `return` statement anywhere in `main`'s own body at all, what
> do you predict happens: a compile error naming the missing `return`,
> the same as it would for any other `int`-returning function, or
> something else?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Program.cpp`:

```cpp
int main() {
}
```

Run this session (`verification/4.1/lab_empty_main.cpp`):

```
(compiles with no error; running it produces no output)
exit code: 0
```

This is the real, concrete answer: C++'s own language rules grant `main`
*specifically* — and only `main` — a real exemption every other
`int`-returning function does not get: reaching the closing `}` with no
`return` statement is treated as an implicit `return 0;`, proven here by
the real, observed exit code. No other function in C++ gets this

### SE Lens

The principle behind `main`'s own implicit-zero exemption is **matching
convention to the overwhelmingly common case**: the vast majority of
programs that don't fail simply want to signal ordinary success, and
requiring `return 0;` to be typed at the end of every single `main`
that never actually fails would be pure, repetitive ceremony with no
real information conveyed — a real, small instance of the same
"ceremony that carries no decision" idea Lesson 3.2's own SE Lens named
for Kotlin's constructor-parameter properties, applied here by C++'s own
language designers directly, rather than left to a library or a style
convention.
