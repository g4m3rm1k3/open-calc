# Lesson 4.10: The Object Two Services Genuinely Both Need

**What you will build:** `Logger.h` — a real, new class, logging a
message through a shared, single instance — and `Service`, gaining a
`std::shared_ptr<Logger>` member, constructed from a `Logger` two
separate `Service` instances genuinely share at once. `Program.cpp`
constructs one real `Logger` and two real `Service`s that both depend on
it, printing the real, live reference count at every real stage. The
transferable problem: every resource this whole phase has managed so
far — `label`, since Lesson 4.5 — has had exactly one real owner at a
time, exactly what `unique_ptr` was built for. A shared logging
destination, injected into more than one object at once, is genuinely
different — no single `Service` can honestly claim sole ownership of it,
because destroying it while another `Service` still depends on it would
be a real, live bug, not a hypothetical one.

**What you need to know first:** Lesson 4.9 replaced manual pointer
ownership with `unique_ptr`'s own real, exclusive-ownership guarantee.
This lesson finds the one real situation that guarantee cannot honestly
express, and reaches for `shared_ptr` instead — never as a default
choice, but because this lesson's own real scenario, unlike every prior
one in this phase, genuinely has more than one legitimate owner.

## Terms used in this lesson

- **`std::shared_ptr<T>`** — a real, standard library class template
  owning a resource *jointly*, alongside any number of other
  `shared_ptr` instances that were copied from one another (never
  independently constructed from the same raw pointer twice — this
  lesson's own real code only ever copies, never does that unsafe
  alternative). It exists for exactly the situation `unique_ptr` cannot
  express: a resource with more than one legitimate, simultaneous real
  owner, none of which should be the one to decide, alone, when it's
  safe to destroy.
- **Reference counting** — the real, live mechanism `shared_ptr` uses to
  know when its own resource is safe to destroy: a shared counter,
  incremented every time a `shared_ptr` is copied, decremented every
  time one is destroyed, with the real resource itself only destroyed
  once that counter reaches zero. It exists as the concrete answer to
  "who decides when a shared resource is really done being needed" —
  the count itself, not any single owner's own decision.
- **`std::make_shared<T>`** — a real, standard library function
  constructing a new `T` and a new `shared_ptr` owning it in one real
  step, more efficient than constructing a raw `T*` and handing it to a
  `shared_ptr`'s own constructor separately (it allocates the real
  object and its own reference-count bookkeeping together, in one
  allocation, rather than two). It exists as the real, recommended way
  to create a `shared_ptr`-owned object, the same real spirit as
  Lesson 4.5's own `new[]`, but for a single object rather than an
  array.
- **`use_count()`** — a real, live member function reporting exactly how
  many `shared_ptr` instances currently share ownership of the same
  resource — this lesson's own real, direct window into reference
  counting actually happening, not merely asserted.

## Concept Unit: A Resource Two Objects Genuinely Both Need at Once

### The Problem

Two real `Service` instances, this lesson's own real subject, both need
to log through the identical `Logger` — not because either one owns the
logging destination exclusively, but because logging to two *different*
loggers would defeat the entire point of a shared log. Does `unique_ptr`,
Lesson 4.9's own real answer to ownership, work for this?

> **Stop and try it yourself first:** Lesson 4.9's own real, cited proof
> showed `unique_ptr`'s own copy constructor is itself `= delete`d —
> genuinely, unconditionally refusing to be copied, by design. Given
> that two separate `Service` constructors, in this lesson's own real
> scenario, would each need their own real reference to the identical
> `Logger`, what happens if `Service`'s own constructor tried to accept
> a `unique_ptr<Logger>` parameter and simply copy it into each
> `Service`'s own member — is that even something the compiler will
> allow, given what Lesson 4.9 already proved?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.h`:

```cpp
#include <iostream>
#include <memory>

class Logger {
public:
    void log(const char* message) {
        std::cout << message << std::endl;
    }

    ~Logger() {
        std::cout << "Logger destroyed." << std::endl;
    }
};

int main() {
    auto logger = std::make_shared<Logger>();
    std::cout << logger.use_count() << std::endl;
    {
        auto a = logger;
        std::cout << logger.use_count() << std::endl;
        {
            auto b = logger;
            std::cout << logger.use_count() << std::endl;
        }
        std::cout << logger.use_count() << std::endl;
    }
    std::cout << logger.use_count() << std::endl;
}
```

Run this session (`verification/4.10/lab_shared_ptr_refcount.cpp`):

```
1
2
3
2
1
Logger destroyed.
```

Real, direct proof: `auto logger = std::make_shared<Logger>();` —
per this lesson's own Terms entry — creates one real `Logger` and one
`shared_ptr` owning it; `logger.use_count()`, per this lesson's own
Terms entry, reports `1`. `auto a = logger;` — an ordinary copy,
completely legal here (a real, direct contrast to Lesson 4.9's own
`unique_ptr`, whose identical syntax would have been a compile error) —
raises the count to `2`; `auto b = logger;`, nested one scope deeper,
raises it to `3`. As `b`, then `a`, each go out of scope, the count
falls back to `2`, then `1` — and the real `Logger` object itself is
only destroyed at the very end, when `logger` — the *last* real owner —
finally goes out of scope too. This whole mechanism — a live count,
incremented on copy, decremented on destruction, the resource itself
destroyed only once it reaches zero — is called **reference counting**,
per this lesson's own Terms entry, and this is called `shared_ptr`'s
own **shared ownership**.

### Mechanical Walkthrough

- **`std::shared_ptr<Logger> logger;`** (`Service.h`) — per this
  lesson's own Terms entry: a member, per Lesson 4.9's own full
  treatment of member declarations, holding shared ownership of a
  `Logger` rather than exclusive ownership of one.
- **`Service(const char* name, std::shared_ptr<Logger> sharedLogger)`**
  — the constructor's own real second parameter; taking it *by value*
  (a real, deliberate copy at the call boundary, not a reference) is
  what actually increments the reference count, per this unit's own
  real proof, at the exact moment a new `Service` is constructed.
- **`logger(sharedLogger)`** — the member initializer list, per Lesson
  4.2's own full treatment: copies the parameter's own `shared_ptr` into
  the member — a second real copy, this one specifically what makes
  `Service` itself a real, ongoing owner for as long as it exists.
- **`logger->log(label.get(), " destroyed.");`** and its own twin inside
  `run()` — `->`, real member access through a smart pointer,
  identical syntax to a raw pointer's own `->`, already familiar even

### CS Lens

Reference counting — a live, shared count deciding when a resource is
actually safe to release, rather than any single participant deciding
alone — is a real, foundational idea in systems that manage shared
resources.

```
Also recognized in: every real garbage collector this curriculum has
used (Java's JVM, Kotlin's own JVM, C#'s CLR) — all use some real form
of reachability or reference tracking internally, the exact same
underlying question ("is anything still using this"), automated at the
scale of an entire program rather than opted into per-resource the way
`shared_ptr` is; Python's own real CPython implementation, which uses
reference counting as its own primary memory-management mechanism,
directly, not merely as an analogy; a library book with a real waiting
list, only re-shelved once every current borrower has returned it
```

### SE Lens

The principle is **only reaching for shared ownership once single
ownership genuinely can't express the real situation** — this lesson's
own real, motivating scenario (a logger two `Service` instances
legitimately, simultaneously need) is not one `unique_ptr` could
represent honestly at all; forcing single ownership onto it would mean
one arbitrary `Service` "owning" the logger and the other merely
borrowing an unsafe raw reference to it, with no real guarantee it would
outlive its own use. The real, honest cost, proven directly rather than
merely asserted: `shared_ptr` is twice the size of `unique_ptr` (Lesson
4.9's own real evidence: `unique_ptr`, `8` bytes, identical to a raw
pointer; `shared_ptr`, `16` bytes — a second real pointer, to a shared
control block tracking the live count) — and every copy and destruction
of a `shared_ptr` does real, extra work updating that count, work
`unique_ptr` never has to do at all, because it never needs to ask
anyone else. That real cost is exactly why `shared_ptr` is not this
whole phase's own default answer to ownership — `unique_ptr`, per
Lesson 4.9, remains the right choice for every situation with one real
owner, which is most of them.
