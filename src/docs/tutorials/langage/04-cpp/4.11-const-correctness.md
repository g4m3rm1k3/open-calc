# Lesson 4.11: A Promise the Compiler Actually Checks, Twice Over

**What you will build:** `Service::getRunCount()` marked `const`, and a
real, new function, `printRunCount(const Service& service)`, that
inspects a `Service` without being able to modify it — proven, not
merely intended, by a real compile error along the way. The
transferable problem: `Service`, since Lesson 4.9, cannot be copied at
all — every prior phase's own equivalent function could simply accept a
value and let the language quietly duplicate it if needed. This lesson
finds the one real way C++ lets a function inspect an object it doesn't
own, without moving it, copying it, or accidentally being allowed to
change it.

**What you need to know first:** Lesson 4.9 made `Service` move-only —
this lesson assumes that real, load-bearing fact and finds its own
direct, necessary consequence for a function that merely wants to
*read* a `Service`. Lesson 4.2 established member functions and `this`;
this lesson finds a real, second real thing `this` can be, not yet
named.

## Terms used in this lesson

- **`const` (on a member function)** — written after a member function's
  own parameter list, this promises the function will not modify the
  object it's called on, and — proven directly below — the compiler
  checks that promise, refusing to compile the function's own body if it
  tries. It exists to let a function state, in its own signature, that
  it only reads, never writes — checkable by any caller without reading
  the function's own implementation.
- **`const` member function's real effect on `this`** — inside an
  ordinary member function, `this` (Lesson 4.6's own real, first
  treatment) has type `Service*`; inside a `const` member function, it
  has type `const Service*` instead — a real, different type, which is
  precisely why a `const` member function cannot assign to a member: the
  assignment would go through a pointer the compiler itself now treats
  as pointing at read-only data.
- **Reference to `const` (`const Type&`)** — a reference parameter,
  already familiar in shape from Lesson 4.6's own copy constructor,
  combined with `const`: the function receiving it promises not to
  modify the object referred to, and can therefore only call that
  object's own `const` member functions on it — proven directly below
  to be enforced, not advisory.

## Objects and methods used

- **`Service::getRunCount() const`** — reappearing from Lesson 4.2,
  given full treatment again with its own real, new `const` qualifier;
  not duplicated as a separate full entry here, since nothing about its

  this lesson's own first unit.
- **`printRunCount(const Service&)`** — this lesson's own real, new

## Concept Unit: `const` Member Functions — A Promise, Checked Twice

### The Problem

A function that wants to print a `Service`'s own run count, without
running it, resetting it, or changing anything about it, needs to read
`getRunCount()`. Since Lesson 4.9, `Service` cannot be copied — such a
function has no honest way to accept a `Service` by value at all
(proven directly in this lesson's own next unit). It needs a *reference*
instead — and, since it only reads, that reference should say so.

> **Stop and try it yourself first:** A function parameter typed
> `const Service&` promises, to its own caller, that the `Service`
> passed in won't be modified. Given that `getRunCount()`, as it stands
> since Lesson 4.2, has no `const` anywhere in its own declaration, what
> do you predict happens if code holding a `const Service&` tries to
> call it — does the *compiler* actually check that a function called
> through a `const` reference is itself safe to call that way, or is
> `const`, on a reference, only ever a documentation-level promise a
> reader has to trust?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.h`:

```cpp
#include <iostream>

class Counter {
private:
    int count;

public:
    Counter(int c) : count(c) {
    }

    int getCount() {
        return count;
    }
};

void describe(const Counter& counter) {
    std::cout << counter.getCount() << std::endl;
}

int main() {
    Counter c(5);
    describe(c);
}
```

Attempting to compile this session
(`verification/4.11/lab_const_ref_fails.cpp`):

```
lab_const_ref_fails.cpp: In function 'void describe(const Counter&)':
lab_const_ref_fails.cpp:17:34: error: passing 'const Counter' as 'this' argument discards qualifiers [-fpermissive]
    17 |     std::cout << counter.getCount() << std::endl;
       |                  ~~~~~~~~~~~~~~~~^~
lab_const_ref_fails.cpp:11:9: note:   in call to 'int Counter::getCount()'
```

Real, direct proof: `const`, on a reference, genuinely is checked by
the compiler, not merely advisory — the real error names exactly what's
wrong (`getCount()`'s own implicit `this` parameter would need to become
`const Counter*` to be called through `counter`, and nothing about
`getCount()`'s own declaration permits that).

The fix — adding `const` to the member function itself:

```cpp
int getCount() const {
    return count;
}
```

This compiles and runs, printing `5`, confirmed the same session.

Now the second real proof this unit's own Terms entry promises: `const`
doesn't just permit being *called* through a `const` reference — it
genuinely prevents the function's own body from mutating anything:

```cpp
int getCount() const {
    count = count + 1;
    return count;
}
```

Attempting to compile this session
(`verification/4.11/lab_const_cannot_mutate.cpp`):

```
lab_const_cannot_mutate.cpp: In member function 'int Counter::getCount() const':
lab_const_cannot_mutate.cpp:12:15: error: assignment of member 'Counter::count' in read-only object
   12 |         count = count + 1;
      |         ~~~~~~^~~~~~~~~~~
```

Real, direct proof, per this lesson's own Terms entry: inside a `const`
member function, `this`'s own real type becomes `const Counter*` — the
compiler genuinely treats `count`, reached through it, as read-only,
refusing the assignment outright.

### SE Lens

honest cost: every member function that's genuinely read-only needs
this one extra word, remembered and applied consistently, with no
compiler warning if it's simply forgotten on a function that happens to
never actually need to mutate anything — `const`-correctness, in real
C++ codebases, is a discipline a team has to actively maintain, not
something the language defaults into on its own.

## Concept Unit: `const Service&` — Not a Choice, a Requirement

### The Problem

`printRunCount`, a real, new function this lesson wants to build, needs
to inspect a `Service` without owning it, copying it, or moving it away
from whoever already holds it. Every prior phase's own equivalent
function could simply accept its parameter by value, trusting the
language to copy it if needed. Can `Service`'s own function do that too?

> **Stop and try it yourself first:** Lesson 4.9's own real, direct
> evidence already proved `unique_ptr`'s own copy constructor is `=
> delete`d, and that this propagates automatically to any class holding
> one — `Service` included. Given that, what do you predict happens if
> a function is declared to take a plain `Service` parameter — not a
> reference, not a pointer, just `Service` — and is then called with a
> real, existing `Service` object?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.h` but using the real,
committed `Service` class directly:

```cpp
#include "Service.h"

void printRunCount(Service service) {
    std::cout << service.getRunCount() << std::endl;
}

int main() {
    auto logger = std::make_shared<Logger>();
    Service a("A", logger);
    printRunCount(a);
}
```

Attempting to compile this session
(`verification/4.11/lab_by_value_fails.cpp`):

```
lab_by_value_fails.cpp: In function 'int main()':
lab_by_value_fails.cpp:10:18: error: use of deleted function 'Service::Service(const Service&)'
   10 |     printRunCount(a);
      |     ~~~~~~~~~~~~~^~~
Service.h:8:7: note: 'Service::Service(const Service&)' is implicitly declared as deleted because 'Service' declares a move constructor or move assignment operator
```

This is a genuinely stronger, more concrete real answer than this
unit's own Socratic prompt even asked for: the compiler's own error
message directly names the *reason* — Lesson 4.9's own real finding,
that declaring move operations implicitly deletes copy operations —
cited back at this exact call site. `const Service&`, for a function
like `printRunCount`, is not a style preference or a minor optimization
here — it is the *only* real way to pass a `Service` into a function
that merely wants to inspect it, since passing by value would require
exactly the copy Lesson 4.9 made impossible.

### SE Lens

signature interacting with `Service` has to be considered carefully —
does it need to inspect, or take real ownership — a genuine design

## Connect the Pieces

that a `const` reference genuinely restricts which member functions can
