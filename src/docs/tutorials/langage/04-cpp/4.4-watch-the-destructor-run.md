## Terms used in this lesson

- **Destructor (`~Service()`)** — a special member function, named
  identically to the class it belongs to but prefixed with `~`, taking
  no parameters and having no return type at all — the same real
  absence of a return type a constructor already has, per Lesson 4.2's
  own treatment. It exists as the one real, guaranteed point in a C++
  program where an object's own cleanup logic runs, called automatically
  by the compiler at the exact moment the object's own lifetime ends —
  proven, in this lesson, to be scope exit for every automatic-storage
  object built so far.
- **RAII (Resource Acquisition Is Initialization)** — the real, named
  design principle of tying a resource's own acquisition to an object's
  own construction, and that same resource's own release to the
  identical object's own destruction — so that simply having a valid
  object in scope *is*, by construction, the same thing as holding
  whatever it manages, with no separate step a programmer could forget.
  It exists because Lesson 4.3's own real guarantee (destruction happens
  automatically, deterministically, at scope exit) is only actually
  *useful* once real cleanup work is attached to that guaranteed moment
  — this lesson's own destructor does the smallest possible version of
  that (printing a line) specifically so the *pattern* itself is proven
  before Lesson 4.5 gives it something real to manage.

## Concept Unit: RAII — A Guarantee Strong Enough to Survive an Early Exit

### The Problem

Every real run so far has exited its own scope the simple way — falling
through to the closing `}` after every statement above it already ran.
Real programs routinely leave a scope some other way: an early `return`,
a `break`, an exception. If `~Service()`'s own guarantee only held for
the simple case, it would be a much weaker, less useful promise than
Lesson 4.3's own language-guarantee claim actually states.

> **Stop and try it yourself first:** Every prior phase's own
> `try`/`finally` (or Kotlin's own `try`/`catch`, Lesson 3.2) required a
> programmer to *explicitly* write cleanup code in a `finally` block if
> they wanted it to run regardless of how a function actually exited.
> Given that `~Service()`'s own destructor call is not written anywhere
> at any of this lesson's own real call sites — it fires purely because
> `service` existed and its scope ended — what would you predict happens
> if that same scope is exited early, through a `return` inside an
> `if`, before the closing `}` is ever reached by normal, top-to-bottom
> execution?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Program.cpp`:

```cpp
#include "Service.h"

void demo(bool early) {
    Service service;
    service.run();
    if (early) {
        std::cout << "Returning early." << std::endl;
        return;
    }
    std::cout << "Reached the end normally." << std::endl;
}

int main() {
    demo(true);
}
```

Run this session (`verification/4.4/lab_destructor_early_return.cpp`):

```
Service is running.
Returning early.
Service destroyed.
```

Real, direct proof: `demo`'s own early `return;` still triggered
`~Service()` — printed *after* "Returning early." (the statement
directly before `return;`) but *before* `demo` actually hands control
back to `main`. The destructor's own guarantee is tied to the real event
"this scope is being exited," by whatever real path that happens
through — not to "execution happened to reach the last written line."

A second, real question this same guarantee raises: what happens when
*more than one* object shares a scope? Throwaway code, unconnected to
`Program.cpp`, using a small, labeled stand-in class rather than
`Service` itself, specifically so each object's own construction and
destruction can be told apart in the printed output:

```cpp
#include <iostream>
#include <string>

class Labeled {
private:
    std::string name;

public:
    Labeled(std::string n) : name(n) {
        std::cout << name << " constructed." << std::endl;
    }

    ~Labeled() {
        std::cout << name << " destroyed." << std::endl;
    }
};

int main() {
    {
        Labeled first("first");
        Labeled second("second");
    }
}
```

Run this session (`verification/4.4/lab_reverse_order_named.cpp`):

```
first constructed.
second constructed.
second destroyed.
first destroyed.
```

Real, direct proof of a second guarantee: destruction happens in the
exact *reverse* order of construction — `second`, constructed last, is
destroyed first. This matters beyond curiosity: an object constructed
later in a scope has, by definition, only ever existed *alongside*
everything constructed before it, never the other way around — reverse
order guarantees nothing is ever destroyed while something that might
still depend on it is still alive, the same real ordering discipline a
stack itself (Lesson 4.12's own later, explicit subject) always
enforces.

### CS Lens

Reverse-order teardown, exactly mirroring construction order, is a real,
recognizable discipline beyond just C++'s own destructor sequencing.

```
Also recognized in: a call stack itself unwinding in exactly the reverse
order function calls were made (the most recently called function
always returns first — this curriculum's own later Lesson 4.12 makes
this exact connection explicit); undo/redo systems reversing operations
in the opposite order they were applied; database transactions rolling
back nested savepoints in reverse order; a stack-based memory allocator
(freeing the most recently allocated block first, by necessity, since
nothing else can be freed out of order without corrupting everything
above it)
```

### SE Lens

The principle is **a guarantee that only held for the easy case would
not actually be a guarantee** — the real value of RAII, per this
lesson's own Terms entry, depends entirely on destruction being reliable
*regardless* of how a scope is exited, proven directly by this unit's
own early-return lab; a resource-management pattern that only cleaned
up on the "normal" path would leave every early return, every thrown
exception (this whole phase's own later material, not directly proven
here, but resting on the identical real mechanism this unit already
proved), and every `break` out of a loop as a real, silent leak.
Reverse-order destruction is the second half of the same real
reliability: an object is never torn down while something constructed
after it — and therefore able to depend on it — might still be alive,
a real, structural safety property, not merely a stylistic convention.
