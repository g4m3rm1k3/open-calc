# Lesson 4.5: Giving `~Service()`'s Own Proven Guarantee Something Real to Do

**What you will build:** `Service` gains `label` — a heap-allocated,
owned C-string, given to it at construction and copied, not merely

still compile and run identically — the moment that stops being true is
exactly this lesson's own real subject.

**What you need to know first:** Lesson 4.4 proved destruction is
reliable, deterministic, and reverse-ordered. This lesson assumes all of

matter. Lesson 4.2 established the member initializer list; this lesson

below.

## Terms used in this lesson

- **`new[]` / `delete[]`** — the array forms of C++'s own dynamic
  memory operators: `new T[n]` allocates space for `n` values of type
  `T` on the heap (not automatic storage — its own lifetime is governed
  by nothing but an explicit, matching `delete[]`, never by scope alone)
  and returns a real pointer to the first one; `delete[]` releases
  memory a matching `new[]` allocated. They exist as C++'s own most
  direct, manual way to acquire memory whose size isn't known until
  runtime (here, a name of unknown length) and whose real lifetime needs
  to outlive the single expression that requested it.
- **Resource acquisition** — the real, specific act of a constructor
  obtaining something that must later be explicitly given back — memory,
  here; a file handle or a network connection in other real programs,
  not needed by this lesson's own code. It exists as the first half of
  RAII (Lesson 4.4's own Terms entry): the guarantee only means anything
  once a constructor actually acquires something real.
- **Ownership (as a class responsibility)** — the real, load-bearing
  claim that exactly one place in the program — here, the `Service`
  object holding `label` — is responsible for eventually releasing a
  given resource, and every other piece of code interacts with that
  resource only through the owning object, never by holding a
  competing, independent responsibility to free it too. It exists so
  that "who frees this" has exactly one real, unambiguous answer,
  provable by reading the class's own declaration rather than tracing
  every place the resource might be used.
- **`<cstring>`** — a real C++ standard header, inherited essentially
  unchanged from C's own `<string.h>`, declaring raw C-string functions
  operating on `char*` — `std::strlen` (real character count, not
  counting the terminating null) and `std::strcpy` (copies one
  C-string's own characters, including its terminator, into another
  buffer) among them. It exists because this lesson's own resource is a
  raw `char*`, not yet the real `std::string` class this curriculum has
  not needed until now — C++'s own more primitive, C-inherited string
  handling, used here deliberately to make the underlying memory
  operations fully visible rather than hidden behind a higher-level
  type.

## Objects and methods used

- **`std::strlen`**
  - *What it is:* A real, standard C++ function returning a C-string's
    own length — the number of characters before its terminating null,
    not counting the terminator itself.
  - *Implementation:* Declared in `<cstring>` (inherited from C's own
    `<string.h>`); its real implementation, in this machine's own
    shipped standard library, walks the given buffer one byte at a time
    until it finds the terminating `'\0'`.
  - *Its use:* Called once, in `Service`'s own constructor, to compute
    exactly how large a buffer `label` needs.
  - *Type:* A free function. Signature: `size_t strlen(const char* s)`.
  - *Responsibility:* Reporting one real number — nothing about
    allocation or copying.
  - *Depends on:* The given C-string actually being properly
    null-terminated; nothing else.
  - *Connects to:* Called by `Service`'s own constructor; its result is
    used to size the `new[]` call immediately after it.
  - *Shape:* A public API surface, part of the C++ standard library's
    own C-inherited string-handling boundary.

- **`std::strcpy`**
  - *What it is:* A real, standard C++ function copying one C-string's
    own characters, including its terminator, into a given destination
    buffer.
  - *Implementation:* Declared alongside `std::strlen` in `<cstring>`;
    copies byte by byte until it copies the source's own terminating
    `'\0'`, then stops.
  - *Its use:* Called once, in `Service`'s own constructor, to copy the
    given name's own real characters into `label`'s own newly-allocated
    buffer.
  - *Type:* A free function. Signature: `char* strcpy(char* dest, const
    char* src)`.
  - *Responsibility:* Copying characters — nothing about checking that
    `dest` is actually large enough to hold them, a real, well-known,
    genuine danger of this specific function this lesson's own code
    avoids only because `std::strlen`'s own result, plus one for the
    terminator, is what sized `label` immediately beforehand.
  - *Depends on:* A destination buffer already large enough — this
    lesson's own real code, not the function itself, is what guarantees
    that.
  - *Connects to:* Called by `Service`'s own constructor, immediately
    after the `new[]` call its own result sizes.
  - *Shape:* The same public API surface as `std::strlen`.

## Concept Unit: `new[]` — Acquiring a Real Resource, Proven Independent

### The Problem

`Service` needs a name — something to print instead of the fixed literal
every prior lesson has used. A fixed-size `char` array member
(`char label[50];`) could hold one, but would silently truncate or waste
space depending on the real name's own length, decided at compile time
with no way to know what a caller will actually pass. Does C++ offer a
way to size a buffer to the real, runtime-known length of whatever name
is actually given?

> **Stop and try it yourself first:** Every array this curriculum has
> used so far — Kotlin's own `List`, Java's own `List`, C#'s own
> collections — had a size determined at runtime, growing or shrinking
> as needed, with the underlying memory management handled entirely by
> a managed runtime. C++ has no such runtime here. Given that
> `std::strlen` can report a real name's own exact length at runtime,
> what would you predict C++'s own most direct way is to request *that
> exact amount* of memory, dynamically, at the moment it's actually
> needed — a fixed member array sized generously in advance, or
> something that asks for precisely the right amount, every time?

### Introduce the Concept in Isolation

unit's own Socratic prompt implicitly raises: does `label` actually hold
an *independent copy* of `name`'s own characters, or merely the same
pointer `name` itself was?

`n` was constructed, and `n.announce()` still reports `"Original"` — if
`Named`'s own constructor had merely stored `name`'s own pointer instead
of copying its characters into a real, separate buffer, this would have
printed `"Changed!!"` instead. `label` is a genuine, independently owned
copy, not an alias.

## Concept Unit: `delete[]` — Ownership as a Class's Own Responsibility

### The Problem

`label`'s own real memory, once acquired, needs to be released
eventually — real memory `new[]` allocates does not free itself, and
nothing in this curriculum's own C++ toolchain (proven, across this
whole phase, to have no garbage collector at all) reclaims it
automatically. Whose job is that?

> **Stop and try it yourself first:** Lesson 4.4's own real proof
> already established that `~Service()` runs automatically, exactly
> once, at the precise moment a `Service` object's own lifetime ends —
> proven for early returns and for multiple objects, in a real, reverse
> order. Given that `label` is a member of `Service` specifically, and
> nothing outside `Service` ever directly touches `label`'s own real
> pointer, what real, single place in this whole program would you
> choose to put the matching `delete[]` — and why would putting it
> anywhere else (inside `run()`, say, or inside `main` itself, after
> constructing `service`) be a real, worse choice?

### Mechanical Walkthrough

- **`std::cout << label << " destroyed." << std::endl;`** — reads
  `label` while it's still valid, *before* releasing it — order matters
  here specifically: `delete[]` on the next line would make `label` a
  real, dangling pointer, unsafe to read from at all.
- **`delete[] label;`** — per this lesson's own Terms entry: releases
  the exact real memory `new[]`, in the previous unit, allocated. The
  `[]` here is not decorative — it must match the `[]` the original
  `new[]` used; using plain `delete label;` (no brackets) on memory
  allocated with `new[]` is real, well-documented undefined behavior,
  not merely a style mismatch, though this lesson's own real code never
  triggers that specific mistake, having used the matching form
  correctly throughout.
- **`Service service("Order Processor");`** (`Program.cpp`) — per this
  lesson's own Terms entry for **ownership**: `service` alone now owns
  its own real, independent copy of `"Order Processor"`'s own
  characters; the string literal itself, per Lesson 4.1's own treatment,
  is a separate, compiler-managed `const char*` that this constructor
  only ever reads from, never stores a pointer to directly.

### SE Lens

The principle is **making "who is responsible for this" answerable by
reading one class's own declaration, not by tracing every place a raw
