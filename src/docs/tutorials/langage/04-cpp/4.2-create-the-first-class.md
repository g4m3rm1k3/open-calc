## Terms used in this lesson

- **`class`** — declares a new C++ type, bundling data (member
  variables) and behavior (member functions) together — the same
  general idea as Java's, C#'s, and Kotlin's own `class`, re-derived
  here for C++'s own real syntax, which groups member *visibility* under
  labeled sections rather than a modifier on each individual member.
- **Access specifier section (`private:` / `public:`)** — a label,
  followed by a colon, that sets the visibility of every member declared
  after it, until the next such label or the class's own closing brace.
  This exists as C++'s own real mechanism for the identical problem
  Java's, C#'s, and Kotlin's own per-member modifiers already solved —
  restricting which code can access a given member — expressed here as a
  *section* covering however many members follow it, rather than a
  keyword repeated on every single member individually.
- **Default class visibility** — a `class` whose members carry no
  explicit `private:`/`public:` label at all are `private` by default;
  this is a real, load-bearing C++ rule, not a convention, proven with a
  real compile error below. `struct` — a second, distinct keyword for
  declaring what is otherwise an identical kind of type — defaults to
  `public` instead; the *only* real difference between `class` and
  `struct` in C++ is this one default, also proven below.
- **Constructor** — a special member function, sharing its class's own
  name exactly and having no return type at all (not even `void`),
  automatically called once, by the compiler, whenever a new object of
  that class is created. It exists as the guaranteed place to put
  whatever setup logic a valid object of this class actually requires —
  the same real idea Java's, C#'s, and Kotlin's own constructors already
  serve, re-derived here for C++'s own real syntax.
- **Member initializer list** — the part of a constructor's own
  declaration, after a colon and before its own `{ }` body, naming each
  member being initialized and the value it starts with —
  `Service() : runCount(0) { }`, this lesson's own real example. It
  exists because C++ member variables are genuinely *constructed*, not
  merely assigned, the moment an object begins existing — the
  initializer list is where that real construction step happens;
  assigning a value inside the constructor's own `{ }` body instead (as
  this lesson's own throwaway lab, below, does for contrast) is a real,
  separate step that happens *after* the member has already been
  constructed with whatever its own default state is, not the same
  operation performed at a different time.
- **Member function** — a function declared inside a class, operating on
  a specific object of that class (accessed implicitly, without needing
  to be named — a genuinely different mechanism from every prior
  language's own explicit `this`, covered in full once this curriculum's
  own C++ material actually needs to name `this` directly, not yet in
  this lesson). This exists as the same general idea as every prior
  phase's own member/instance methods, re-derived here for C++'s own
  syntax, which — unlike Kotlin's own primary-constructor shorthand from
  Lesson 3.2 — declares member functions inside the class body exactly
  the way Java's and C#'s own methods already did.
- **Automatic storage (object construction with no `new`)** — declaring
  `Service service;` inside `main`, with no `new` anywhere, creates a
  real, fully-constructed `Service` object directly, owned by the local
  variable `service` itself, existing for exactly as long as the scope
  it was declared in. This is this lesson's own first, real encounter
  with a concept this whole phase's own next lesson (4.3) gives full,
  dedicated treatment to — named here only enough to explain why this
  lesson's own real code never writes `new Service()` the way every
  garbage-collected language in this curriculum always did.

(`verification/4.2/lab_double_include_fails.cpp`):

```
In file included from lab_double_include_fails.cpp:2:
NoGuard.h:1:7: error: redefinition of 'class Counter'
    1 | class Counter {
      |       ^~~~~~~
In file included from lab_double_include_fails.cpp:1:
NoGuard.h:1:7: note: previous definition of 'class Counter'
```

This is real, direct proof of Lesson 4.1's own claim about `#include`
being *literal* text substitution: including the same header twice
really did paste `class Counter { ... };` into the file twice,
producing a real "redefinition" error — the compiler has no built-in
awareness that both copies came from the same original file. This
specific problem never surfaced in Lesson 4.1 only because `<iostream>`
happened to be included exactly once there; any header, `<iostream>`
included, has this exact same real exposure the moment something
includes it more than once (directly, or indirectly through two other
headers that both include it).

The fix:

```cpp
// Guarded.h
#pragma once

class Counter {
public:
    int count;
};
```

Run this session (`verification/4.2/lab_double_include_fixed.cpp`,
including `Guarded.h` twice plus `<iostream>`):

```
7
```

`#pragma once`, placed as the very first real line of the header, tells
the preprocessor to skip pasting this exact file's own content in a
second time if it's already been included once during this same
compilation — proven here by the identical double-`#include` no longer
producing any error at all.


## Concept Unit: `class`, Access Sections, and a Default Nobody Asked For

### The Problem

`Service` needs a private `runCount` — the same real requirement every
prior phase's own first-class lesson had. Java's own Lesson 2.3 needed
its own dedicated lesson just to make a field `private`; C#'s own Lesson
1.4 needed one too. Does C++ need the same explicit ceremony, or does
declaring a `class` already default to something safer?

> **Stop and try it yourself first:** Every language taught in this
> curriculum so far has required a field to be explicitly marked
> `private` — omitting the modifier, in Java, C#, or Kotlin (Lesson
> 3.8's own real, disassembled proof), makes a member accessible more
> broadly than `private`, never less. Given C++'s own real history (it
> predates all three of those languages, and predates the now-common
> assumption that safe defaults matter more than backward compatibility
> with C, which has no access control at all), what would you guess a
> C++ `class` with *no* access specifier written at all actually does —
> follow the same "unmarked means more open" pattern every other
> language in this curriculum uses, or something else?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.h`:

```cpp
class Counter {
    int count;
};

int main() {
    Counter c;

}
```

```
lab_default_private_fails.cpp: In function 'int main()':
lab_default_private_fails.cpp:7:7: error: 'int Counter::count' is private within this context
    7 |     c.count = 5;
      |       ^~~~~
lab_default_private_fails.cpp:2:9: note: declared private here
```

This is the real, concrete, and genuinely surprising answer: with *no*

the same experiment, changing only the one keyword `class` to `struct`:

```cpp
};

```

```

```

Identical code otherwise, and `c.count = 5;` now compiles and runs
cleanly. This is the real, complete proof: `struct` and `class` in C++
declare the exact same kind of thing — both can have member functions,
constructors, and access sections identically — differing in exactly
one real respect, their **default class visibility**, per this lesson's
own Terms entry: `class` defaults every unlabeled member to `private`;
`struct` defaults every unlabeled member to `public`.

## Concept Unit: The Constructor — and Why Its Initializer List Isn't Just Assignment

### The Problem

`runCount`, as declared so far, has no starting value at all — reading
it before any explicit initialization is real, undefined behavior in
C++ (a fact this lesson does not need to trigger directly to take
seriously; every prior phase's own language — Java, C#, Kotlin — always
gave a numeric field a real, guaranteed default of `0` automatically,
none of which C++ does for a plain `int` member). `Service` needs a real
constructor to fix this. Every prior phase's own constructor set a field
by simple assignment inside its own body — does C++'s own constructor
work identically, or is there a real, different mechanism specifically
for this exact moment, an object's own very first initialization?

> **Stop and try it yourself first:** Lesson 3.2 (Kotlin) showed a
> constructor-parameter property collapsing field declaration,
> parameter, and assignment into one line — a real *shortcut* over
> Java's own three-piece pattern, but still fundamentally an
> *assignment* happening after the object already exists. If C++
> members are genuinely *constructed*, not just declared and later
> assigned, the moment an object begins existing — a real, different
> claim from every prior phase — what would you predict a constructor
> needs, syntactically, to participate in that construction directly,
> rather than only being able to change a value *after* the member
> already exists in some other, unspecified starting state?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.h`:

```cpp
#include <iostream>

class Counter {
private:
    int count;

public:
    Counter() : count(0) {
    }

    int getCount() {
        return count;
    }

    void increment() {
        count = count + 1;
    }
};

int main() {
    Counter counter;
    counter.increment();
    counter.increment();
    std::cout << counter.getCount() << std::endl;
}
```

Run this session (`verification/4.2/lab_class_ctor_init_list.cpp`):

```

```

`Counter() : count(0) { }` — a **constructor**, per this lesson's own
Terms entry: named identically to its class, `Counter`, with no return
type at all, not even `void`. The part after the colon and before the
`{ }` body, `count(0)`, is the **member initializer list**, per this
lesson's own Terms entry: it constructs `count` directly with the value
`0`, as part of the object's own real construction, before the
constructor's own (here, empty) body ever runs. Two real increments
later, `getCount()` correctly reports `2` — proof the member really did
start at a known, real `0`, not an unspecified value.
