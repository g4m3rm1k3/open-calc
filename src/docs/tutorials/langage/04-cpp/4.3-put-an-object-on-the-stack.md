# Lesson 4.3: A Name That Stops Existing at a Real, Written Character

**What you will build:** `Program.cpp`'s own `service` wrapped in an
explicit `{ }` block — the same real object as Lesson 4.2, now
constructed and used inside a scope smaller than `main` itself. The
transferable problem: every prior phase's own object lived until a
garbage collector, running on its own unpredictable schedule, eventually
noticed nothing referenced it anymore — Lesson 2.9 (Java) called this
"JVM-managed lifetime" directly. C++ has no such collector at all. This
lesson finds out what actually governs an object's own lifetime instead,
and proves the one piece of it that's directly provable without a tool
this curriculum hasn't built yet — leaving the other half honestly
promised to the very next lesson, not faked here.

**What you need to know first:** Lesson 4.2 built `Service` and
constructed one real instance with no `new` — this lesson explains what
that choice actually means for how long the object lives. Lesson 2.9
(Java) established that garbage-collected languages leave an object's
own destruction timing unspecified — reused here only as the real
contrast this lesson's own subject stands against, not re-derived in
full (Java's own GC mechanics are that lesson's own subject, not this
one's).

## Terms used in this lesson

- **Scope** — the specific region of source code, delimited by a pair of
  matching `{` and `}`, within which a name declared inside it is
  actually visible and usable. It exists as the basic unit C++ uses to
  answer two real, related questions at once: where can this name be
  used, and — this lesson's own real subject — for how long does the
  object it names actually exist.
- **Automatic storage duration** — the specific lifetime rule that
  applies to an ordinary local variable, declared with no `new` and no
  special keyword: the object begins existing at the point it's
  declared, and is guaranteed to stop existing at the closing `}` of the
  scope that declared it — automatically, with no explicit instruction
  from the program required to make it happen. This is the real, formal
  name for what Lesson 4.2's own `Service service;` already did without
  yet naming it.
- **Deterministic destruction** — the real guarantee that an
  automatic-storage object's own destruction happens at one specific,
  predictable point in the program's own execution — the exact moment
  control leaves its own scope — rather than at some later, unspecified
  time a separate process decides on its own schedule. This is a real,
  load-bearing C++ language guarantee, not an implementation detail that
  merely tends to happen this way; this lesson states it as exactly
  that — a defined rule, citable from the language's own specification —
  while being honest that this lesson's own tools cannot yet *observe*
  the actual moment it happens directly; Lesson 4.4 builds the one real
  mechanism (a destructor) that can.

## Concept Unit: `{ }` — Where a Name Actually Lives

### The Problem

Every prior phase's own variable — a Kotlin `val`, a Java local, a C#
local — was visible from the point it was declared until the end of the
enclosing method, with no smaller boundary a programmer could draw
inside that method on purpose. Does C++ offer anything more precise than
"visible for the rest of the function," the way `Service service;`
sitting directly inside `main`, per Lesson 4.2, currently is?

> **Stop and try it yourself first:** Every function body in this
> curriculum, in every language so far, has been wrapped in one pair of
> `{ }` — the function's own boundary, and nothing smaller. C++ reuses
> the identical `{` and `}` characters for a function body. Given that,
> what would you predict happens if a *second*, nested pair of `{ }` is
> written directly inside a function body, with no `if`, no loop, no
> function call — nothing but the braces themselves? Does C++ treat that
> as a real, meaningful boundary of its own, or as dead, purposeless
> syntax?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Program.cpp`:

```cpp
int main() {
    {
        int x = 5;
    }
    return x;
}
```

Attempting to compile this session
(`verification/4.3/lab_scope_out_of_bounds_fails.cpp`):

```
lab_scope_out_of_bounds_fails.cpp: In function 'int main()':
lab_scope_out_of_bounds_fails.cpp:5:12: error: 'x' was not declared in this scope
    5 |     return x;
      |            ^
```

Real, direct proof: a bare `{ }` with nothing else around it *is* a
real, meaningful boundary — `x`, declared inside it, genuinely does not
exist by the time `return x;` runs, one line after the closing `}`. This
is called a **scope**.

A second, complementary proof — that two *separate* scopes are
genuinely independent, not merely hidden from each other:

```cpp
#include <iostream>

int main() {
    {
        int x = 5;
        std::cout << x << std::endl;
    }
    {
        int x = 10;
        std::cout << x << std::endl;
    }
}
```

Run this session (`verification/4.3/lab_scope_independent_names.cpp`):

```
5
10
```

No "redeclaration" error at all, even though the identical name `x` is
declared twice — real proof that each `{ }` block's own `x` is a wholly
separate, independent entity, not the same binding persisting or
colliding across the two blocks.

### CS Lens

Lexical scoping — a name's own visibility determined by where it sits in
the source code's own written structure, not by the order operations
happen to run in at runtime — is a foundational idea nearly every
language in this curriculum already relies on, usually invisibly.

```
Also recognized in: every `if`/`for`/`while` block in C#, Java, and
Kotlin already narrows a variable's own visibility the identical way
(a loop variable declared in a `for` header is not visible after the
loop ends, in any of those three languages) — the real, new fact this
lesson adds is not lexical scoping itself, already implicitly used
throughout this whole curriculum, but that in C++ specifically, a
scope's own boundary is *also* an object-lifetime boundary, not merely a
name-visibility one
```

### SE Lens

The principle is **letting the same syntax a programmer already writes
for organization also carry a second, real, load-bearing meaning**. The
real alternative — some separate, dedicated syntax just for "the point
this object should be destroyed," distinct from ordinary block
structure — was not the choice C++ made; instead, the exact same braces
already used to group related statements together (a habit already
familiar from every prior language in this curriculum) do double duty
as the *only* thing that determines when automatic-storage objects are
destroyed. The real cost: a programmer has to actually think about where
their braces are, in a way no prior phase's own language ever required,
because moving a variable's own declaration one line up or down, or
adding a scope around a section of code purely for readability, now has
a second, real effect (this whole phase's own later lessons, starting
4.4, are exactly what happens once that second effect is deliberately
put to use).

## Concept Unit: Automatic Storage and the Promise This Lesson Can't Fully Prove Yet

### The Problem

`service`, per the previous unit, genuinely stops being a legal *name*
at line 9's own closing `}`. But a name becoming illegal to write is a
compile-time fact, proven directly, in the previous unit, with a real
compile error. Whether the real *object* itself — the actual memory
`service` occupied, and any real cleanup work `Service` might need done
— is also guaranteed to happen at that exact same point is a different,
runtime claim entirely, one this lesson has not yet proven directly.

> **Stop and try it yourself first:** Lesson 2.9 (Java) already
> established that a JVM-managed object's own destruction timing is
> genuinely unspecified — the garbage collector decides, on its own
> schedule, sometime after nothing references the object anymore, never
> at a fixed, predictable point a programmer can name in advance.
> Given that C++ has already been shown, across this whole phase, to
> reject every piece of "managed runtime" machinery every prior
> phase relied on (Lesson 4.1's own real evidence: a standalone
> executable, no JVM, no CLR) — what would you predict C++'s own answer
> is to "when, exactly, does an automatic-storage object's own real
> cleanup happen" — an equally unpredictable answer, or a real,
> fixed one?

### Introduce the Concept in Isolation

No new throwaway lab in this unit — the honest, real reason is stated
directly: proving *when* an object's own destruction actually happens,
as opposed to when its *name* stops being legal (already proven in the
previous unit), requires a way to make destruction itself produce some
real, observable effect — a printed line, a changed value, anything a
`Run It` step could show. C++ has exactly one real mechanism for that:
a **destructor**, a term this lesson has deliberately not yet defined.
Writing one now, only to prove this one specific fact, would mean
re-explaining it again in full one lesson later anyway, per the
Repetition Rule — worse, it would mean this lesson's own real subject
(automatic storage as a *language rule*) leaning on next lesson's own
real subject (destructors as the *tool* that makes it observable)
before that tool has been properly built. This gap is named honestly
here rather than papered over with an isolated lab that doesn't actually
prove the thing it claims to.

One real approach genuinely was attempted this session, and is recorded
honestly rather than silently discarded: constructing two `Service`
objects in two separate, sequential (not nested) scopes and comparing
their own real memory addresses, hoping to show the second object
reusing the first one's own storage as indirect proof it had genuinely
been reclaimed. Run for real
(`verification/4.3/lab_address_reuse.cpp`):

```
0x9dbdbffb9c
0x9dbdbffb98
```

The two addresses came back *different*, not reused — this session's
own prediction was wrong, caught by actually running it rather than
assumed. The real, honest explanation: without optimization enabled
(the default this whole curriculum has used throughout), this specific
compiler does not necessarily reuse the identical stack slot for two
non-overlapping local scopes inside the same function — a real,
compiler-specific detail about *how* stack space happens to be laid
out, not a statement about whether destruction itself really happened
at scope exit. This approach is abandoned as this lesson's own proof
mechanism specifically because it does not actually demonstrate the
real claim this unit is making, even though the addresses genuinely
were captured from a real, compiled, and run program.

### Discard the Throwaway Example

not because it failed to compile or run, but because, on reflection, it
never actually proved the claim it was built to prove, and keeping it in

### SE Lens

The principle is **a real guarantee is only actually useful once it's

alternative some other curriculum might choose — asserting "C++ objects
are destroyed deterministically" as a bare fact with no supporting
evidence at all, or worse, papering over the gap with the abandoned
address-reuse experiment presented as if it had actually worked — would
teach a reader to accept confident-sounding claims about invisible
behavior without ever seeing them checked, the exact habit this whole
curriculum's own schema (its own repeated insistence on pasted, real
output) exists to prevent. The real cost of being honest about this
gap instead: this lesson ends without its own most important claim
fully proven, which is uncomfortable, but true — and Lesson 4.4, next,
closes it for real.
