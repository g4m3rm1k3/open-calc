# Lesson 1.9: One Body, Many Types — Introduce a Generic Operation

**What you will build.** Two small, new, standalone additions to this
project: `LastValue<T>`, a class that remembers one value of *any* type —
used once holding an `int` (`service.RunCount`) and once holding a
`string` (a status message) — and `Describer`, an ordinary, non-generic
class whose one method, `Describe<T>(T value)`, is itself generic,
printing whatever value it's handed regardless of type. Neither addition
touches `Service`, `ILogger`, or either logger implementation at all — this
lesson is purely additive. A **generic type parameter** — `T`, in both
cases — is a placeholder standing in for a real type that isn't chosen
until the class or method is actually used; a **generic class** fixes that
placeholder once per object it creates; a **generic method** can accept a
different type on *every single call*, even without belonging to a
generic class at all. Both are proven, not just described: the exact same
compiled class body handles `int` and `string` without duplication,
without casting, and without ever being told in advance which one it
would be asked to hold.

**What you need to know first.** From **Lesson 1.7 — Naming What Several
Classes Can Do**: the real project at `code/01-csharp/Service/`,
`interface`, `implementation`. From **Lesson 1.5**: `parameter`,
`argument`. From **Lesson 1.4**: **compiler warning**, reappearing this
lesson in a genuinely new shape. From **Lesson 1.3**: `field`, `int`,
`default field value`. From **Lesson 1.2**: `class`, `object`, `instance`,
`method`, `new`, `var`, member access (`.`). From **Lesson 1.1**:
`Console`, `Console.WriteLine`, string literals. From the curriculum's own
stated assumptions: enough Python experience to know that Python
functions and classes never need to declare what type of value they'll
receive at all — this lesson leans on that contrast to explain *why* C#
needs an explicit mechanism for "the same code, many types," when Python
simply never asks the question.

## Terms used in this lesson

- **generic type parameter** — a placeholder name, conventionally a single
  capital letter like `T`, standing in for a real type that isn't fixed
  until the generic class or method is actually used. `LastValue<T>`'s
  own `T` is never `int` or `string` inside `LastValue`'s own source —
  it's only ever `T`, until something writes `LastValue<int>` or
  `LastValue<string>` and fixes it.
- **generic class** — a class declared with one or more type parameters
  in angle brackets after its own name, whose fields, method parameters,
  and return types can be written in terms of that placeholder instead of
  one fixed, specific type. `LastValue<T>` is this lesson's own generic
  class — the exact same compiled class produces a `LastValue<int>`
  object and a `LastValue<string>` object, each with its own `T` fixed
  differently.
- **generic method** — a method declaring its *own* type parameter,
  independent of whether the class it belongs to is generic at all.
  `Describer.Describe<T>` is this lesson's own generic method — `Describer`
  itself is an entirely ordinary, non-generic class, but `Describe`
  accepts a different type on every single call.
- **type parameter list (`<T>`)** and **type argument** — the angle-
  bracket syntax declaring a generic type parameter (`class LastValue<T>`,
  `void Describe<T>(...)`) and, separately, the syntax filling it in at
  actual use (`LastValue<int>`, `LastValue<string>`) — the same
  parameter/argument relationship Lesson 1.5 already established for
  method parameters and their arguments, now applied to *types* instead
  of *values*.
- **compiler warning** — reappearing from Lesson 1.4, in a genuinely new
  shape this lesson: `CS8618`, produced by the compiler's nullable-
  reference-type analysis noticing that `LastValue<T>`'s own field,
  `value`, has no guarantee of holding a non-null value the moment its
  constructor finishes — because `T` is unconstrained, the compiler
  can't rule out `T` being a reference type that might never actually be
  set. This is a warning, not an error; the build still succeeds, and the
  real, correct behavior this lesson proves is unaffected by it.
- **field, private, public, class, block (`{ }`), `void`, call syntax
  (`( )`), `var`, `new`, member access (`.`), assignment operator (`=`),
  string literal, semicolon (`;`), `int`** — all reappearing from Lessons
  1.1–1.7, unchanged in meaning, all still present in `LastValue.cs`,
  `Describer.cs`, and this lesson's isolated lab.

## Concept Unit: The Generic Class — One Type Parameter, Many Types

### The Problem

Suppose this project wanted a small utility remembering "the last value
of something" — the last run count, say. Writing `LastIntValue` with a
plain `int` field would work, once. Remembering the last logged message
too would mean writing an entirely separate `LastStringValue` class, with
an identical shape — a field, a `Set`, a `Get` — differing only in which
one type each happens to use. Is duplicating that shape once per type
really the only option, or is there a way to write it exactly once?

> **Stop and think, before reading on:** in Python, you'd just write one
> class with a plain `self.value = value` inside `Set`, and it would
> already work for an `int`, a `string`, or anything else — Python never
> asks what type `value` is ahead of time. Given that every field,
> parameter, and return type in this project's C# code so far has always
> named one specific, fixed type — never "whatever type, decided later"
> — what do you predict C#'s own answer to "the same class, many types"
> actually looks like syntactically? Would it need something new in the
> class's own declaration, not just inside its methods?

own scratch directory. A generic class, `Box<T>`, was written and used
first with `int`, then with `string`:

```csharp

Console.WriteLine(intBox.Get());

var stringBox = new Box<string>();
stringBox.Set("hello");
Console.WriteLine(stringBox.Get());

public class Box<T>
{
    private T value;

    public void Set(T newValue)
    {
        value = newValue;
    }

    public T Get()
    {
        return value;
    }
}
```

Run for real:

```
dotnet run
```

Real output:

```

42
hello
```

This is exactly what the real `LastValue<T>` above is doing, isolated:
one class, `Box<T>`, compiled once, produces two genuinely different
real objects — `Box<int>` and `Box<string>` — each correctly storing and
returning its own type, with no casting, no duplication, and no separate
class written per type. This proves the concept named in this lesson's
Header: a **generic class** fixes its own **generic type parameter**,
`T`, once per object created from it — `intBox`'s own `T` is `int`,
permanently, for as long as that object exists; `stringBox`'s own `T` is
`string`, just as permanently, for a completely different object. The
real `CS8618` **compiler warning** appears here for the same reason it
will against the real project: `T` carries no constraint telling the
compiler it's safe to leave `value` unset, so the compiler flags it
honestly — the build still succeeds, and `42` and `hello` still print
correctly regardless.

`ScratchH` is kept alive rather than deleted immediately — the next
concept unit in this lesson still needs it.

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`public`** — the access modifier, reappearing from Lesson 1.2.
- **`class`** — reappearing from Lesson 1.2, declaring a new blueprint.
- **`LastValue`** — the class's own name.
- **`<T>`** — the **type parameter list**: a single **generic type
  parameter**, `T`, in angle brackets directly after the class name. This
  is what makes `LastValue` a **generic class** rather than an ordinary
  one — every other class this project has declared so far has no angle
  brackets here at all.
- **`private T value;`** — a **field**, reappearing from Lesson 1.3, whose
  declared type is `T` itself rather than a fixed type like `int` or
  `string` — the field's actual type is only decided once a **type
  argument** fills `T` in, at the point `LastValue<int>` or
  `LastValue<string>` is written.
- **`public void Set(T newValue)`** — a method whose **parameter**,
  reappearing from Lesson 1.5, is typed `T` as well — whatever `T` turns
  out to be for a given object, that's what `Set` requires as its
  argument.
- **`value = newValue;`** — the assignment operator, reappearing from
  Lesson 1.2, storing the parameter into the field — ordinary assignment,
  completely unaffected by either side's type being generic rather than
  fixed.
- **`public T Get()`** — a method whose *return* type is `T` — the first
  time this project's code has declared a method returning something
  other than `void`, `int`, or a concrete class type.
- **`return value;`** — returns the field's current value, whatever `T`
  actually is for this specific object.

### CS Lens

Generics are a real instance of **parametric polymorphism** — writing one
piece of code that works correctly for many types, by treating the type
itself as something suppliable later, the same way a value can be:

```
Also recognized in: a shipping container sized and shaped identically
whether it holds furniture or electronics, a moving box labeled simply
"fragile contents" rather than one box design per item category, a
mail slot accepting any letter regardless of what's actually written
inside it, a spreadsheet cell formula that works identically whether
the cell above it contains a number or a date
```

Every one of these separates "the mechanism that holds or processes
something" from "what specifically is being held or processed" — the
mechanism stays fixed; what fills it varies freely.

### SE Lens

The alternative not chosen here — a separate class per type, `LastIntValue`
and `LastStringValue` written by hand — was entirely possible and would
have worked. It fails to scale the moment a third type is needed:
`LastBoolValue`, `LastDoubleValue`, and so on, each one an exact structural
copy of the last, differing only in one type name repeated throughout the
file. Every one of those copies would also need identical bug fixes
applied by hand, every time, forever. A generic class pays a real, one-
time cost — the `<T>` syntax itself, and the discipline of writing every
member in terms of `T` rather than one concrete type — in exchange for
that duplication never happening at all, no matter how many different
types this class eventually needs to hold.

## Concept Unit: The Generic Method — Genericity Without a Generic Class

### The Problem

`LastValue<T>` is generic at the *class* level — every single member
inside it shares the one `T` fixed when the object was created. Is that
the only shape genericity comes in, or can one *method*, on an otherwise
completely ordinary class, be generic on its own, accepting a different
type on every single call rather than being fixed once per object?

> **Stop and think, before reading on:** `LastValue<T>`'s own `<T>` sits
> right after the *class* name — every member inside automatically shares
> it. Given that a method already has its own separate parameter list in
> parentheses, distinct from whatever's declared at the class level, what
> do you predict happens if a method wants its *own* type parameter,
> completely independent of whether its enclosing class has any generics
> at all? Would the syntax need to change meaningfully, or would it look
> like a natural extension of what a method declaration already has?

### CS Lens

A generic method is the same **parametric polymorphism** already named in
the previous unit, scoped down to a single method rather than an entire
class — proof that the underlying idea doesn't require every member
around it to participate:

```
Also recognized in: a single vending-machine slot dispensing whatever
item was loaded into it, regardless of what other slots in the same
machine hold, a translator repeating a spoken sentence in a different
language each time, using the exact same process regardless of which
language is asked for that particular time, a single photocopier
button producing a copy of whatever document is currently loaded,
without the button itself needing to change per document
```

Every one of these keeps one mechanism fixed while what passes through it
on any given use varies completely.

### SE Lens

The alternative not chosen here would be writing `Describe` as an
ordinary, non-generic method accepting `object value` directly, with no
`<T>` anywhere. That alternative would actually compile and run
identically for this lesson's own two calls — `object` already accepts
anything. The real difference shows up the moment a caller wants the
method to give something *back*, typed correctly, rather than just
consuming a value and printing it: a hypothetical `T Echo<T>(T value) {
return value; }` genuinely needs its own generic type parameter to return
the *exact* type it was given — an `Echo(object value)` returning `object`
would force every caller to cast the result back to whatever it actually
was, silently losing the type information a generic method preserves
automatically. This lesson's own `Describe<T>` doesn't strictly need
genericity to do its one, narrow job — printing — but demonstrates the
mechanism cleanly precisely because it's simple enough to see clearly
before meeting a case where genericity is the only option, not merely the
more precise one.
