# Lesson 1.10: Refuse, Then Decide — Handle Failure

**What you will build.** `Service` gains a new method, `Reset()`, that sets
its run count back to `0` — except when there's nothing to reset:
calling `Reset()` on a `Service` that has never run **throws** a real
exception, `InvalidOperationException("Cannot reset a service that has
never run.")`, refusing to proceed. `Program.cs` proves both directions
for real: calling `Reset()` on the original `service` (which has run
twice) succeeds; calling it on a brand-new, never-run `Service` first
crashes the whole program with a genuine, unhandled exception, then —
once wrapped in a **`try`/`catch`** block — is caught, logged, and the
program finishes cleanly instead. This is this curriculum's first-ever
`if` statement and first-ever `==` comparison, despite the curriculum's
own Python assumptions already covering conditional logic conceptually —
new C# syntax earns its own real, first-appearance treatment regardless
of how familiar the underlying idea already is. **Throwing** an exception
is a piece of code refusing to continue and saying exactly why;
**catching** one is a *different* piece of code — usually the caller,
not the class that threw it — deciding what to actually do about that
refusal.

**What you need to know first.** From **Lesson 1.6 — Who Creates the
Dependency**: the real project at `code/01-csharp/Service/`, **runtime
error**, **`NullReferenceException`**, **unhandled exception**, and
**stack trace** — all reappearing this lesson, now applied to an exception
this project's own code throws on purpose, not one caused by a bug. From
**Lesson 1.4**: **compile-time error**, contrasted throughout this lesson
with the runtime failures it's actually about. From **Lesson 1.3**:
`field`, `int`. From **Lesson 1.2**: `class`, `object`, `method`, `void`,
`new`, member access (`.`). From **Lesson 1.1**: `Console`,
`Console.WriteLine`, string literals, semicolons. From the curriculum's
own stated assumptions: Python's `if`/`elif`/`else` and `==` — this
lesson leans on that prior conceptual familiarity while still giving
C#'s own version of both a full, real first-appearance treatment, per
this schema's own standing rule that a *familiar* idea in a *new*
language is not the same knowledge as the syntax itself.

## Terms used in this lesson

- **`if` statement** — a control-flow statement that runs the statements
  inside its block only when a given condition evaluates to `true`,
  skipping them entirely otherwise. This is this curriculum's first `if`
  anywhere in C#, despite `if` already being familiar from Python — the
  syntax itself (parentheses around the condition, braces around the
  body, no colon) is genuinely new, even though the underlying idea of
  "run this only if that's true" is not.
- **comparison operator (`==`)** — tests whether two values are equal,
  producing `true` or `false`. This project's first use of it —
  `runCount == 0` asks whether `runCount`'s current value is exactly
  zero. Distinct from the assignment operator `=` (reappearing from
  Lesson 1.2): `=` stores a value; `==` only ever tests one, never
  changing anything.
- **`throw` statement** — deliberately raises an exception, immediately
  ending the normal flow of whatever method it's in and handing control
  to the nearest enclosing `catch` block that matches the exception's
  type — or, if none exists anywhere up the call chain, ending the
  program entirely, exactly as Lesson 1.6's own bug-caused
  `NullReferenceException` did. `throw new InvalidOperationException
  ("Cannot reset a service that has never run.");` is this project's
  first *deliberate* use of it — a real, on-purpose refusal, not a
  symptom of a mistake.
- **`try`/`catch`** — a `try` block contains code that might throw; a
  `catch` block, immediately following it, names a specific exception
  type and runs only if an exception of that type (or a more specific
  one) was thrown somewhere inside the `try` block, intercepting it
  before it can end the program. This is this curriculum's first use of
  either keyword.
- **deciding where failure belongs** — not a language construct, but this
  lesson's own central design question: *which* piece of code should
  `throw`, and *which* should `catch`? This lesson's own answer:
  `Service` throws, because only `Service` knows whether resetting is
  actually valid right now; `Program.cs` catches, because only the
  caller — not `Service` itself — knows what should actually happen once
  that refusal is known (log it and continue, in this lesson's case).
- **exception, unhandled exception, stack trace, runtime error** — all
  reappearing from Lesson 1.6, restated in full: an exception is an
  object representing something that went wrong while a program was
  running; unhandled means nothing in the program caught it, so the
  runtime prints a description and ends the program at the exact point
  it occurred; a stack trace is the ordered list of method calls active
  at that moment; a runtime error is any failure only discoverable while
  the program is actually executing, as opposed to a **compile-time
  error** (Lesson 1.4), caught before the program ever runs at all. This
  lesson's own unhandled exception, in its first unit, is the second one
  this project has ever produced — the first, in Lesson 1.6, came from a
  real bug; this one comes from code working exactly as designed.
- **field, class, block (`{ }`), `void`, call syntax (`( )`), `var`,
  `new`, member access (`.`), assignment operator (`=`), string literal,
  semicolon (`;`), `int`, `public`, private, `this`** — all reappearing
  from Lessons 1.1–1.6, unchanged in meaning, all still present in
  `Service.cs`, `Program.cs`, and this lesson's isolated lab.

## Concept Unit: `if` and `throw` — Refusing an Invalid Operation

### The Problem

`Service` can count how many times it's run and report on it, but it has
no way to reset that count back to zero. Adding a `Reset()` method seems
simple — until asking what `Reset()` should do on a `Service` that has
never run at all. Resetting something that's already at zero isn't
*wrong*, exactly, but it isn't meaningful either — is silently doing
nothing the right answer, or should the method refuse outright and say
so?

> **Stop and think, before reading on:** you already know Python's `if
> value == 0:` tests a condition and runs an indented block only when
> it's true, and `raise ValueError("message")` deliberately signals a
> problem. Given that every construct in this project's C# code so far
> has needed its own explicit braces and parentheses — no bare colons,
> no indentation-as-structure — what do you predict C#'s own `if` and
> "raise an error" syntax actually looks like? And given `Console
> .WriteLine` already showed you a method call using parentheses for
> arguments, what shape do you expect for creating and immediately
> signaling an error object in one step?

### CS Lens

Throwing an exception the moment an operation's own preconditions aren't
met is a real instance of **failing fast** — refusing to proceed the
instant a problem is detected, rather than continuing on invalid ground
and failing later, somewhere harder to trace back to the real cause:

```
Also recognized in: a circuit breaker tripping the instant it detects
an electrical fault, rather than letting the fault continue and
possibly start a fire, a database refusing to commit a transaction
that violates a constraint, rather than silently storing corrupted
data, an elevator refusing to move if its doors aren't fully closed,
rather than moving anyway and creating a hazard, a compiler refusing
to produce an executable from code with a type error, rather than
guessing what was probably meant
```

Every one of these detects a real problem at the earliest possible
moment and stops, rather than letting bad conditions propagate further
and become harder to diagnose.

### SE Lens

The alternative not chosen here is having `Reset()` silently do nothing
when `runCount` is already `0` — no exception, no message, just a no-op.
That alternative avoids ever crashing the program, which sounds safer on
the surface. It hides a real problem instead of surfacing it: if calling
`Reset()` on a never-run `Service` was never supposed to happen, a silent
no-op means that mistake produces no evidence at all — nothing to notice,
nothing to fix, until its consequences show up somewhere else entirely,
disconnected from the actual cause. Throwing costs something real, paid
immediately and visible in this very unit: an unhandled exception crashes
the whole program, right now, with no recovery built yet. That cost is
temporary and deliberate — the next unit is what actually decides what to
do about it, rather than never finding out at all.

## Concept Unit: `try`/`catch` — Deciding Where Failure Belongs

### The Problem

`neverRun.Reset()` crashes the whole program. That might be exactly the
right behavior in some contexts — but `Program.cs`, in this project, would
rather notice the problem, log it, and keep going. Nothing about
`Service.Reset()` itself needs to change to make that possible — the
question is how the code that *calls* it can intercept the exception
before it ends the program.

> **Stop and think, before reading on:** you already know Python's `try:`
> / `except SomeError:` structure catches a specific kind of error and
> lets execution continue afterward. Given that `throw` and `if` both
> needed their own explicit braces and parentheses in the previous unit,
> what do you predict `try`/`catch` needs to name, explicitly, that
> Python's `except` clause also names — and where do you think that
> naming actually needs to go: around the *risky* call, or around the
> method that *contains* the risky call?

### The Real Project Change

- **Reference Source:** no reference counterpart — from-scratch addition.
- **Files affected:** modified — `code/01-csharp/Service/Program.cs`.
- **Change type:** replace (`neverRun.Reset();` wrapped in a `try`/`catch`
  block).
- **Location:** `Program.cs`'s final two lines, added in the previous
  unit.
- **Dependencies:** the crashing call from the previous unit.


Run for real:

```
dotnet run
```

Real output:

```
Cannot reset a counter that is already zero.
```

No crash this time, and no stack trace — just the exception's own
message, printed on purpose. This proves the concept named in this
unit's own title: a **`try`/`catch`** block intercepts an exception
before it can end the program, running its own `catch` body instead —
`Console.WriteLine(ex.Message);` here, `logger.Log(ex.Message);` in the

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`try`** — the keyword opening a block of code that might throw.
- **`{` ... `}` (the `try` block)** — a block, reappearing from Lesson
  1.2, containing exactly the one call that might fail: `neverRun
  .Reset();`.
- **`catch`** — the keyword introducing a handler for a specific
  exception type.
- **`(InvalidOperationException ex)`** — names the exact exception type
  this `catch` block handles, `InvalidOperationException`, and binds it
  to a local name, `ex`, so the block's own body can read the caught
  exception's properties. An exception of any *other* type thrown inside
  the `try` block would *not* be caught here, and would still crash the
  program — this `catch` is specific, not universal.
- **`{` ... `}` (the `catch` block)** — a block, reappearing, running
  only when a matching exception was actually thrown.
- **`logger.Log(ex.Message);`** — member access, reappearing, reading
  `ex`'s own `Message` property and passing it to `Service`'s existing
  `logger` collaborator — the exact same logging path every other message
  in this program already goes through.

### CS Lens

`try`/`catch` is the language-level mechanism behind **separation of
failure detection from failure response** — the code that discovers a
problem is not required to be the code that decides what to do about it:

```
Also recognized in: a smoke detector sounding an alarm without itself
deciding whether to call the fire department, evacuate the building, or
just open a window, a car's low-fuel light turning on without the car
itself choosing a gas station, an automated test reporting a failure
without itself deciding whether that failure blocks a deployment, a
customer service escalation being flagged as urgent by one system and
resolved by an entirely different team
```

Every one of these keeps "noticing something is wrong" and "deciding what
happens next" as genuinely separate responsibilities, handled by whoever
is actually positioned to make that decision well.

### SE Lens

**Deciding where failure belongs** is this lesson's own central design
question, and this unit's real code is the answer: `Service.Reset()`
*throws* — it is the only code that actually knows whether resetting is
valid right now, since only it has access to `runCount`. `Program.cs`
*catches* — it is the caller, and only the caller knows what should
actually happen once the refusal is known: log it and keep going, in this
program's case, though a different caller might choose to retry, ask a
user, or fail its own operation in turn. The alternative not chosen —
`Service.Reset()` catching its own exception internally and quietly
returning — was rejected specifically because that decision doesn't
belong to `Service`: `Service` doesn't know, and shouldn't need to know,
whether "someone tried to reset an unused service" is a bug worth
crashing over, a routine situation worth logging, or something a caller
needs to retry. The real cost of getting this placement wrong: catching
too early, inside `Service` itself, would hide information the caller
might genuinely need; catching too late, or not at all, is exactly the
unhandled crash the previous unit ended on.
