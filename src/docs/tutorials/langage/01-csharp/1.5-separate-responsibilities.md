# Lesson 1.5: One Class, One Job — Separate Responsibilities

**What you will build.** `Service` currently does two genuinely unrelated
things inside the same method: it counts how many times it's run, and it
produces a human-readable report of what happened. This lesson pulls the
second job out entirely, into a new class named `Logger`, which `Service`
now *has* rather than *is*. `Program.cs` still prints the exact same four
lines it did before — the refactor changes nothing about what the program
does, only how its work is divided up — and, new this lesson, also creates
a second, completely independent `Logger` of its own, proving the
extracted class has no hidden tie back to `Service` at all. The
transferable problem underneath this one small class is bigger than
logging specifically: a class that quietly does two unrelated jobs at
once has no single, coherent reason to exist, and every future change to
either job risks breaking the other one by accident, since nothing
separates them. **Responsibility** is what a class is actually in charge
of; **composition** is building a class out of other objects it relies on
rather than trying to do everything itself; and the **"has-a"**
relationship is the specific shape that reliance takes — `Service` *has a*
`Logger`, the same way it already *has a* `runCount` field, just one level
more structured.

**What you need to know first.** From **Lesson 1.4 — Who Is Allowed to
Change This**: the real project at `code/01-csharp/Service/`, its
`Service` class with a `private int runCount` field and a public, read-
only `RunCount` property, `private`, `public`, `encapsulation`, and
`property`. From **Lesson 1.3**: `field`, `object state`, `instance
member`, `int`, and the arithmetic `+` operator. From **Lesson 1.2**:
`class`, `object`, `instance`, `method`, `constructor`, `new`, `var`,
member access (`.`), and the assignment operator (`=`). From **Lesson
1.1**: `Console`, `Console.WriteLine`, string literals, semicolons, and
the `dotnet run` cycle. From the curriculum's own stated assumptions:
enough basic Python object-oriented experience to already know what
inheritance is (a class defined as a specialized *kind of* another
class) — this lesson leans on that only to contrast it with composition,
a genuinely different relationship this lesson's own code never uses
inheritance for at all.

## Terms used in this lesson

- **responsibility** — the specific job or set of related jobs a class is
  actually in charge of; the reason that class exists at all. It exists
  as a concept because a class with no clearly statable single
  responsibility tends, in practice, to keep absorbing more and more
  unrelated jobs over time, with nothing about its own design pushing
  back against that.
- **composition** — building a class out of other objects it relies on to
  do part of its job, rather than trying to do every job itself inside one
  class. This is a **hard concept** — a real, named design principle, not
  routine syntax — so it gets full CS Lens treatment, below, rather than a
  one-line definition. It exists because splitting unrelated
  responsibilities across separate, focused classes, and then wiring them
  together, tends to stay understandable and changeable far longer than
  one class trying to do everything.
- **"has-a" relationship** — the specific shape composition takes: object
  A holds a reference to object B as one of its own members, and relies
  on B to do part of A's job. Contrasts with an **"is-a" relationship**
  (inheritance — already familiar from the curriculum's own Python
  assumptions), where one class *is a specialized kind of* another. This
  lesson's own code uses "has-a" exclusively — `Service` *has a* `Logger`;
  nothing in this project is declared as *being* a specialized kind of
  anything else.
- **collaborator** — a general term for an object another object depends
  on to do part of its own job; this is exactly the fifth field — "Connects
  to" — that every Objects and methods entry in this curriculum's own
  Header format already tracks. `Logger` is this lesson's own new
  collaborator for `Service`; `Console` has quietly been a collaborator
  since Lesson 1.1, just never named as one until a project-owned
  collaborator (`Logger`) existed to contrast it with.
- **parameter** — a named placeholder a method declares for information it
  needs handed in from outside in order to do its job, written inside its
  declaration's parentheses. `Log(string message)`'s `message` is this
  project's first-ever method parameter that the project itself declared
  — `Run()`, this project's only other method until now, needed no
  information from outside at all, so it declared none. Contrasts with an
  **argument** — the actual value supplied at a specific call site to fill
  a parameter — `"Service is running."` is the argument `Service.Run()`
  supplies for `Log`'s `message` parameter; `"Program finished."` is a
  different argument for that exact same parameter, supplied from a
  different call site. Every parameter needs some argument supplied for
  it at every call, which is exactly why a `string` value has to exist
  before `Log` can be called at all — unlike `Run()`, which needs nothing
  supplied because it declares no parameters to fill.
- **field initializer** — an expression written directly at a field's own
  declaration, assigning it a starting value the moment its object is
  constructed, before that object's own constructor body (empty or not)
  ever runs. `private Logger logger = new Logger();` is this lesson's own
  first use of one — every field this project has declared before this
  lesson (`runCount`) relied on its type's own default value instead, `0`,
  needing no initializer at all.
- **`private`, encapsulation, property** — reappearing from Lesson 1.4,
  unchanged in meaning: `logger`, this lesson's own new field, is declared
  `private`, exactly like `runCount` already was, for the same reason —
  nothing outside `Service` has any business reaching in and replacing its
  collaborator directly. `RunCount`'s own read-only property, from Lesson
  1.4, is untouched by this lesson's changes.
- **`public`** — reappearing from Lesson 1.2, unchanged in meaning: still
  the access modifier granting visibility to any code that can see the
  type at all, applied in this lesson to `Logger`'s own class declaration
  and its `Log` method.
- **field, object state, instance member** — reappearing from Lesson 1.3:
  `logger`, like `runCount` before it, is a field, holds part of this
  specific `Service` object's own state, and is an instance member,
  belonging to whichever `Service` object it's read on.
- **class, block (`{ }`), `void`, call syntax (`( )`), `var`, `new`,
  member access (`.`), assignment operator (`=`), string literal,
  semicolon (`;`), `int`** — all reappearing from Lessons 1.1–1.3,
  unchanged in meaning, all still present in `Service.cs`, the new
  `Logger.cs`, and this lesson's isolated lab.

  - *Shape:* a small, focused public API surface — this project's own

- **`Logger()` — the compiler-supplied default constructor**

## Concept Unit: Composition — Giving Service a Collaborator

### The Problem

Look again at `Service.Run()`, exactly as Lesson 1.4 left it:
`runCount = runCount + 1; Console.WriteLine("Service is running.");`. That
first statement updates a count — pure bookkeeping, no output involved.
That second statement produces a human-readable report — pure output, no
counting logic involved. These are two genuinely different jobs, with
nothing about one requiring anything about the other, and yet both are
written inline, in the same method, inside the same class, as if they
were naturally one thing.

> **Stop and think, before reading on:** `Service.Run()` already relies on
> `Console` — a class this project didn't write, sitting in a completely
> separate file, that `Service` reaches out to whenever it needs to print
> something. Given that `Service` already trusts an entirely separate
> class to handle the actual mechanics of writing to the terminal, why
> would `Service` need to contain its *own* status-reporting logic at all,
> rather than relying on some other object — one this project *does*
> write, this time — the exact same way it already relies on `Console`?

### The Real Project Change

- **Reference Source:** no reference counterpart — from-scratch addition,
  same as every unit in this project so far.
- **Files affected:** created — `code/01-csharp/Service/Logger.cs`;
  modified — `code/01-csharp/Service/Service.cs`.
- **Change type:** add (a new class) and replace (`Service.Run()`'s second
  statement, plus a new field).
- **Location:** a new file alongside `Program.cs` and `Service.cs`; inside
  `Service`'s block, a new field alongside `runCount`, and one changed line
  inside `Run()`.
- **Dependencies:** the `Service` class and its `runCount` field from
  Lessons 1.3 and 1.4.

### Introduce the Concept in Isolation

A throwaway project, `ScratchD`, was scaffolded fresh in this session's own
scratch directory. A `Greeter` class was given a `Printer` collaborator,
the same shape as `Service` and `Logger`, and `Printer` was given an
explicit constructor with its own print statement — purely to make an
otherwise invisible moment observable:

```csharp
var greeter = new Greeter();
Console.WriteLine("Greeter object created.");
greeter.SayHello();

public class Greeter
{
    private Printer printer = new Printer();

    public void SayHello()
    {
        printer.Print("Hello from Greeter.");
    }
}

public class Printer
{
    public Printer()
    {
        Console.WriteLine("Printer constructed.");
    }

    public void Print(string message)
    {
        Console.WriteLine(message);
    }
}
```

Run for real:

```
dotnet run
```

Real output:

```
Printer constructed.
Greeter object created.
Hello from Greeter.
```

The real output's own ordering is the proof, made concrete step by step:

1. `var greeter = new Greeter();` — before this line finishes, `Greeter`'s
   own field initializer, `private Printer printer = new Printer();`,
   runs as part of constructing the `Greeter` object — which is exactly
   why `Printer constructed.` is already printed by the time this single
   line of `Program.cs` is done.
2. `Console.WriteLine("Greeter object created.");` — only runs after step
   1 has fully finished, which is why `Greeter object created.` prints
   second, never before the `Printer` that was constructed as a side
   effect of the line above it.
3. `greeter.SayHello();` — calls `printer.Print(...)` on the *already-
   existing* `Printer` step 1 created; `Hello from Greeter.` prints last,
   proving `SayHello()` never touches `Console` directly at all — the
   message reaches the terminal only by going through `printer`.

`Printer constructed.` prints *first* — before `Greeter object created.`,
which sits on the very next line of `Program.cs`, right after `new
Greeter()`. This proves the concept named in this lesson's Header: a
**field initializer** — `private Printer printer = new Printer();` — runs
as part of constructing the *outer* object, before control ever returns
to whatever called `new Greeter()` in the first place. This is exactly
what `Service`'s own `private Logger logger = new Logger();` does: the
moment `new Service()` runs in `Program.cs`, a real `Logger` object comes
into existence too, automatically, with nothing in `Program.cs` ever
writing `new Logger()` itself. And `Hello from Greeter.` — the message —
prints only once `SayHello()` actually runs, through `printer.Print(...)`,
not through any direct call to `Console` inside `Greeter` at all. This is
the concept named in this lesson's title: `Greeter` **has-a** `Printer`,
exactly the same shape as `Service` **has-a** `Logger`.

`ScratchD` is kept alive rather than deleted immediately — the next
concept unit in this lesson still needs it.

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`public`** — the access modifier, reappearing from Lesson 1.2, applied
  to this new class: any code that can see this project can see `Logger`.
- **`class`** — the keyword declaring `Logger` as a new blueprint,
  reappearing from Lesson 1.2.
- **`Logger`** — the class's own name, chosen for what it's responsible
  for: producing visible output for whatever message it's handed.
- **`{` ... `}` (class body)** — a **block**, reappearing from Lesson 1.2,
  containing this class's one member.
- **`public void Log(string message)`** — a method declaration: `public`
  (reappearing), `void` (reappearing from Lesson 1.2, meaning this method
  hands nothing back), `Log` (the method's own name), and `(string
  message)` — this project's first-ever method **parameter**: unlike
  `Run()`, which needs no information handed in, `Log` cannot do its job
  at all without being told *what* to print, so it declares a parameter,
  `message`, of type `string`, that the caller must supply an argument for
  every time it's called.
- **`{` ... `}` (method body)** — a second block, delimiting `Log`'s own
  body.
- **`Console.WriteLine(message);`** — the same static method call already
  fully explained in Lesson 1.1, now printing whatever string was passed
  into `message` rather than a literal written directly inside this
  method — the first time this project's own code has printed a value
  that arrived as a parameter rather than being typed directly into the
  call itself.

And, inside the updated `Service.cs`:

- **`private Logger logger = new Logger();`** — a field declaration
  (`private`, reappearing from Lesson 1.4; `Logger`, this field's declared
  type; `logger`, its name, lowercase per this project's own established
  naming convention) followed immediately by a **field initializer**: `=
  new Logger();`, an assignment operator and a `new` expression
  (both reappearing) supplying this field's starting value directly at
  its own declaration, rather than leaving it at some type-specific
  default the way `runCount`'s bare `private int runCount;` still does.
- **`logger.Log("Service is running.");`** — **member access** (`.`),
  reappearing from Lesson 1.2, reaching into `Service`'s own `logger`
  field to call `Log` on it, passing the exact string literal `Run()`
  used to pass directly to `Console.WriteLine` before this lesson.

### CS Lens

Composition — building `Service` out of a `Logger` it relies on, rather
than `Service` doing every job itself — is a real, named design principle,
worth carrying beyond this one project:

```
Also recognized in: a car built from an engine, a transmission, and a
braking system rather than one undivided machine, a restaurant kitchen
organized into separate stations (grill, salad, dessert) each
responsible for one part of a meal, an orchestra where each section
(strings, brass, percussion) plays its own part rather than one
musician attempting the entire score, a computer built from a CPU, RAM,
and storage as separate, replaceable components rather than one fused
unit
```

Every one of these builds something capable by combining several
narrower, focused parts — each part answerable for one job, connected
together rather than fused into one undifferentiated whole.

### SE Lens

The alternative not chosen here is exactly what Lessons 1.1 through 1.4
already built: all of `Service`'s behavior, including its reporting logic,
written directly inside `Service` itself. That alternative isn't wrong
for a class this small — a single `Console.WriteLine` call barely
justifies its own class. It stops being fine the moment either job grows:
if this project ever needed to log to a file instead of the console, or
format messages with timestamps, or count runs differently under some
condition, every one of those changes would have to happen *inside*
`Service`, risking breaking the other, unrelated job every time, simply
because nothing in the class's own structure kept them apart. Composition
pays a real, immediate cost for that future safety: a whole second file,
a field, a field initializer, and one extra method call, all to
accomplish exactly what one inline `Console.WriteLine` already did. That
cost is deliberately paid now, while the two responsibilities are still
small and easy to see clearly, rather than later, once `Run()` has grown
large enough that untangling them would mean rewriting code nobody
remembers the reasoning behind anymore.

### Connect to What Came Before

Lesson 1.4 left `Service` fully in charge of both counting and reporting,
bundled into one method. This unit splits that bundle in two, giving the
reporting half its own class and its own file, wired together through a
field initializer — proven, in the isolated lab, to run exactly when
`Service`'s own construction happens, and proven, against the real
project, to change nothing about what actually gets printed. One question
remains open: is `Logger` genuinely its own, independent thing now, or is
it still secretly tied to `Service` in some way that just happens not to
show yet? The next unit answers that directly.

## Concept Unit: Responsibility Boundaries — Proving the Split Is Real

### The Problem

`Logger` now exists as its own class, in its own file, with its own
single job. But moving code into a separate class doesn't, by itself,
prove that class is genuinely independent — it's possible to extract
something into "its own class" that still secretly assumes it's only
ever going to be used by the one caller that happens to use it today.
Is `Logger` actually reusable, or does it just look that way because
nothing has tried to use it any other way yet?

> **Stop and think, before reading on:** `Logger` declares no fields, no
> constructor, and no method that mentions `Service` anywhere in its own
> source. Given what you already know about creating objects with `new` —
> that any code able to see a class can create its own, completely
> separate instance of it — what do you predict would happen if
> `Program.cs` created a `Logger` of its own, with no `Service` involved
> at all? Would it work identically to `Service`'s own internal `Logger`,
> or would something about it depend on `Service` having created it first?

### The Real Project Change

- **Reference Source:** no reference counterpart — from-scratch addition.
- **Files affected:** modified — `code/01-csharp/Service/Program.cs`.
- **Change type:** add (two new statements, appended after the existing
  four).
- **Location:** the end of `Program.cs`, after the existing
  `Console.WriteLine(service.RunCount);` line.
- **Dependencies:** the `Logger` class from the previous unit.

### The New Code

```csharp
var logger = new Logger();
logger.Log("Program finished.");
```

The whole file, after this edit, with the two new lines marked:

`Printer constructed.` prints *twice* — once for `Greeter`'s own internal

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`var logger = new Logger();`** — a **local variable** declaration
  (`var`, reappearing from Lesson 1.2), assigned via the **assignment
  operator** (`=`, reappearing) the result of **`new Logger()`**
  (reappearing): a brand-new, independent `Logger` object, entirely
  separate from the one `Service`'s own field initializer already
  created. Nothing links this `logger` variable to `service`'s internal
  one at all — they are two different objects, occupying two different
  locations in memory, that simply happen to have been created from the
  same class.
- **`logger.Log("Program finished.");`** — **member access** (`.`),
  reappearing, calling `Log` on this new, standalone `Logger` object,
  passing a string literal that has nothing to do with anything `Service`
  reports.

### CS Lens

A class that can be created and used with no dependency on any *specific*
other object is exhibiting **loose coupling** — the general idea that two
pieces of a system should depend on each other only as much as their job
genuinely requires, and no more:

```
Also recognized in: a USB device working identically whether it's
plugged into a laptop, a desktop, or a game console, a replacement car
part manufactured to a standard specification rather than custom-fit to
one specific vehicle, a power outlet supplying electricity to any
appliance with a matching plug, regardless of which appliance the
building's electrician happened to be thinking about when it was wired
```

Every one of these works precisely because the thing being connected to
doesn't need to know, or care, exactly what's on the other end — only
that the interface between them is respected.

### SE Lens

The alternative not chosen here — though nothing in this lesson's own
code takes it — would be a `Logger` that somehow only works correctly when
created by `Service` specifically: perhaps a method that silently assumes
some `Service`-specific state exists, or a constructor that requires a
`Service` object be passed in even though nothing about logging actually
needs one. That alternative would look identical to this lesson's own
`Logger` from a quick glance at its declaration, and only reveal the
hidden coupling the moment someone tried to use it exactly the way this
unit just did — standalone. The real, ongoing cost of *not* checking this
honestly: a class that quietly assumes a specific caller can be reused in
name only; anyone who tries to use it differently discovers the hidden
assumption the hard way, usually well after the class has already been
used in several places. Proving independence now, while `Logger` is this
small and this easy to test by hand, costs one throwaway lab and two
lines in `Program.cs` — considerably cheaper than discovering the coupling
after Lesson 1.6 hands `Logger` to something else entirely.

usable anywhere a message needs reporting, with no hidden dependency on
`Service` or anything `Service` does.
