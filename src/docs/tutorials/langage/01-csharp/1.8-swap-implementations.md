# Lesson 1.8: The Payoff — Swap Implementations

**What you will build.** One line, in `Program.cs`: `ILogger logger = new
ConsoleLogger();` becomes `ILogger logger = new LoudLogger();`. Nothing
else changes — not `Service.cs`, not `ILogger.cs`, not `ConsoleLogger.cs`,
not `LoudLogger.cs` — and `git diff Service.cs` after the fact proves it
with an empty, zero-line output. Every previous lesson since 1.6 was
building toward exactly this moment: `Service` depends on `ILogger`, an
abstraction, not on any one concrete class, and swapping which concrete
class actually gets used is now something only `Program.cs` — the place
that decides which collaborator to construct — ever has to know about.
This lesson has almost no new syntax in it at all. Its entire subject is
proving, with a real diff and a real run, that everything built across
Lessons 1.5 through 1.7 actually pays off the way it was supposed to.

**What you need to know first.** From **Lesson 1.7 — Naming What Several
Classes Can Do**: the real project at `code/01-csharp/Service/`, the
`ILogger` interface, its two existing implementations `ConsoleLogger` and
`LoudLogger`, `interface`, `implementation`, and `polymorphism`. From
**Lesson 1.6**: `Service`'s constructor, `dependency`, `constructor
injection`, `this`. From **Lesson 1.5**: `composition`, `"has-a"`,
`responsibility`, and **loose coupling** — named there for the first
time, about to reappear as this lesson's own central point. From **Lesson
1.2**: `class`, `object`, `instance`, `new`, `var`. From the curriculum's
own stated assumptions: nothing new required beyond what Lessons 1.5–1.7
already leaned on.

## Terms used in this lesson

- **programming against an abstraction** — reappearing from Lesson 1.7,
  restated in full because this entire lesson is its practical
  consequence: writing code that depends on *what* something can do
  (`ILogger`'s one method, `Log(string message)`) rather than on any one
  specific class that happens to provide it. `Service`'s constructor,
  `public Service(ILogger logger)`, is this principle made concrete —
  it names the interface, never either concrete class.
- **loose coupling** — reappearing from Lesson 1.5, restated in full: the
  general idea that two pieces of a system should depend on each other
  only as much as their job genuinely requires, and no more. Lesson 1.5
  proved `Logger` had no hidden dependency on `Service`; this lesson
  proves the *reverse* direction too — `Service` has no hidden dependency
  on any one specific `ILogger` implementation either. Coupling this loose
  is exactly what makes today's swap a one-line change instead of a
  rewrite.
- **why the interface exists** — not a separate technical term, but this
  lesson's own framing question, answered directly by its own result:
  an interface exists so that the class depending on it can be handed a
  *different* real implementation later, without itself ever needing to
  change — precisely what this lesson's real diff proves happened.
- **`ILogger`, `ConsoleLogger`, `LoudLogger`, dependency, constructor
  injection, interface, implementation, polymorphism, `this`** — all
  reappearing from Lessons 1.6–1.7, unchanged in meaning; every one of
  them is exactly why this lesson's own change is possible at all with
  no new vocabulary required.

  - *What it is:* the overload of the same method accepting a whole

  - *Implementation:* `public static void WriteLine(int value)` — a

  - *Its use:* unchanged from every previous lesson — still prints

  - *Type:* a `static` method — one overload among several sharing the
    name `WriteLine`.
  - *Responsibility:* convert its `int` argument to its ordinary decimal

  - *Depends on:* the `int` value passed in.

## Concept Unit: The Swap — Proving Service Needs Zero Changes

### The Problem

`Program.cs` currently constructs a `ConsoleLogger` and hands it to
`Service`. Suppose this program's status reports need to be loud instead
— every previous lesson has already built `LoudLogger` and already proven
it satisfies `ILogger` exactly as well as `ConsoleLogger` does. How much
of `Service.cs` — the class actually doing the counting and reporting —
needs to change to make that switch happen?

> **Stop and think, before reading on:** `Service`'s constructor is
> declared `public Service(ILogger logger)` — naming the interface, never
> either concrete class, established back in Lesson 1.7. Given that
> `LoudLogger` already compiles as a valid `ILogger`, already proven in
> Lesson 1.7's own standalone test, what do you predict has to change
> inside `Service.cs` itself for `Service` to start using `LoudLogger`
> instead of `ConsoleLogger`? Anything at all? Or does changing which
> concrete object gets constructed somewhere else already fully suffice?

### The Real Project Change

- **Reference Source:** no reference counterpart — from-scratch addition,
  same as every unit in this project so far.
- **Files affected:** modified — `code/01-csharp/Service/Program.cs`
  only. `Service.cs`, `ILogger.cs`, `ConsoleLogger.cs`, and
  `LoudLogger.cs` are all untouched.
- **Change type:** replace (one line) plus remove (two now-redundant
  lines from Lesson 1.7's own standalone proof).
- **Location:** `Program.cs`'s first line, and its final two lines.
- **Dependencies:** `ILogger`, `ConsoleLogger`, and `LoudLogger`, all
  already real and already proven compatible as of Lesson 1.7.

### The New Code

```csharp
ILogger logger = new LoudLogger();
```

### The Updated Project

`Program.cs`, in full, with the one changed line marked and Lesson 1.7's
now-redundant standalone proof removed:

```csharp
1  ILogger logger = new LoudLogger();          // ← changed from ConsoleLogger
2  var service = new Service(logger);
3  service.Run();
4  service.Run();
5  Console.WriteLine(service.RunCount);
6
7  logger.Log("Program finished.");
```

Lesson 1.7's own final two lines — constructing a second, standalone
`LoudLogger` purely to prove it satisfied `ILogger` — are gone. That proof
already did its job; keeping it here now would be redundant, since
`Service` itself is about to demonstrate the exact same fact directly,
for real, as its own actual behavior rather than as a side demonstration.

### Introduce the Concept in Isolation

A throwaway project, `ScratchG`, was scaffolded fresh in this session's own
scratch directory, mirroring `Service`'s own shape directly: an interface,
two implementations, and a class receiving one of them through its
constructor.

```csharp
IPrinter printer = new QuietPrinter();
var greeter = new Greeter(printer);
greeter.SayHello();

public interface IPrinter
{
    void Print(string message);
}

public class QuietPrinter : IPrinter
{
    public void Print(string message)
    {
        Console.WriteLine(message);
    }
}

public class LoudPrinter : IPrinter
{
    public void Print(string message)
    {
        Console.WriteLine("!!!");
        Console.WriteLine(message);
        Console.WriteLine("!!!");
    }
}

public class Greeter
{
    private IPrinter printer;

    public Greeter(IPrinter printer)
    {
        this.printer = printer;
    }

    public void SayHello()
    {
        printer.Print("Hello from Greeter.");
    }
}
```

Run for real:

```
dotnet run
```

Real output:

```
Hello from Greeter.
```

Then, exactly one line was changed — the first — swapping `QuietPrinter`
for `LoudPrinter`, with `Greeter`'s entire class body left completely
untouched:

```csharp
IPrinter printer = new LoudPrinter();
```

Run for real:

```
dotnet run
```

Real output:

```
!!!
Hello from Greeter.
!!!
```

This is exactly what the real `Program.cs` change above is about to do:
one line changed, and `Greeter`'s own constructor, field, and `SayHello()`
method — never touched at all — produced genuinely different real
output anyway. This proves the concept this lesson's title names
directly: **swapping implementations** requires changing only the code
that decides which concrete object to construct, never the code that
merely depends on the interface.

`ScratchG` is discarded immediately — this lesson needs it for exactly
this one proof, not for anything further.

### CS Lens

This lesson's entire point is a direct, practical demonstration of
**programming against an abstraction** — code depending on *what*
something can do, never on any one specific class providing it:

```
Also recognized in: replacing a car's tires with a different brand
without redesigning the car, swapping a laptop's battery for a
higher-capacity one from a different manufacturer without modifying
the laptop itself, changing a web application's database provider
without rewriting the application code that queries it, upgrading a
building's light bulbs to a different brand without rewiring the
light fixtures
```

Every one of these swaps out one specific part for another compatible one,
leaving everything built around the *interface* — the socket, the plug,
the query language, the fixture — completely undisturbed.

### SE Lens

The alternative not chosen anywhere in this project's history — `Service`
depending directly on the concrete `ConsoleLogger` class, the way it did
before Lesson 1.7 — would have made this exact lesson impossible to write
as a one-line change. Swapping loggers under that design would mean
editing `Service.cs` itself, recompiling a class that has nothing
conceptually to do with *which* logger is chosen, and risking breaking
its own counting logic in the process of changing something completely
unrelated to counting. **Loose coupling** — Lesson 1.5's own term,
reappearing here as this lesson's entire payoff — is exactly what
prevented that: `Service` depends on `ILogger` only as much as its job
genuinely requires — being told to `Log` something — and not one bit
more. The real cost this design already paid, back in Lesson 1.7, was the
one-time overhead of writing the interface at all; today's lesson is
where that earlier cost is repaid, in full, as a one-line change instead
of a class rewrite.
