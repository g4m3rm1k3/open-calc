# Lesson 1.12: Reading the System You Built — Refactor the Architecture

**What you will do.** Nothing in `code/01-csharp/Service/` changes this
lesson. Every previous lesson in Phase 1 introduced one new piece of
language machinery and applied it to this project immediately; this
lesson introduces none, and instead reviews the complete, real system all

place instead of scattered across eleven separate SE Lens sections. The
curriculum's own milestone for this phase is the actual test: not "can
you recite what `interface` means," but "can you read this real system
and explain, correctly, what depends on what and why it's built that
way."

**What you need to know first.** Every lesson in this phase, 1.1 through
1.11 — this lesson assumes all of them, and reviews rather than reintroduces

## Terms used in this lesson

- **dependency graph** — a map of which classes and interfaces in a
  system require which others in order to work, and in which direction
  those requirements point. This project's own dependency graph is this
  lesson's first Concept Unit, drawn from the real, current state of
  every file in `code/01-csharp/Service/`, not reconstructed from memory
  of what each lesson intended.
- **"is-a" via interface implementation, vs. "is-a" via class
  inheritance** — a precise distinction this project's own code makes
  real: `public class ConsoleLogger : ILogger` genuinely is a form of
  "is-a" — `ConsoleLogger` *is an* `ILogger` — but it is *interface*
  implementation, not *class* inheritance. Nowhere in this project does
  one class extend another class (`class A : B` where `B` is itself a
  class, not an interface) — every relationship in this system is either
  "has-a" (composition) or "is-a-through-an-interface" (implementation),
  never "is-a-through-inheriting-another-class's-implementation."
- **composition vs. inheritance** — the curriculum's own explicit
  contrast for this lesson: composition builds a class out of other
  objects it holds a reference to (`Service` has-a `ILogger`);
  inheritance builds a class by extending another class's own
  implementation, inheriting its members directly. This project uses the
  first exclusively; the second appears nowhere in it at all — a real,
  deliberate absence worth stating honestly rather than glossed over,
  addressed fully in this lesson's second Concept Unit.

### CS Lens

A dependency graph is a real instance of a **directed graph** — nodes
(classes, interfaces) connected by directed edges (a `has-a` field, an
`implements` relationship, a constructor parameter) where the direction
matters: `Service` depends on `ILogger`, but `ILogger` has no idea
`Service` exists at all.

```
Also recognized in: a build system's own dependency graph deciding
compile order, a spreadsheet's cell-formula dependencies determining
recalculation order, a family tree (a directed graph of "parent of"
edges), a city's road network directions determining which streets
are one-way
```

Every one of these is the same underlying structure: things connected by
relationships that only make sense read in one specific direction.

### SE Lens

The alternative not chosen anywhere in this project — every class
reaching directly into every other class it might ever need, with no
interfaces and no injected dependencies — was never actually built here,
but it's worth naming as the honest baseline this project's real design
decisions were made *against*. That alternative's real cost, avoided by
every choice this graph reflects: a system where nothing can be swapped,
tested, or understood in isolation, because every class's own source
would need to change the moment any of its collaborators did. This
project's actual graph — `Service` depending on an interface, not a
concrete class; `LastValue<T>` and `Describer` depending on nothing at
all — is the direct, cumulative result of Lessons 1.5 through 1.9's own
decisions, visible now as one coherent shape rather than eleven separate
edits.

## Concept Unit: Why Each Abstraction Exists

### The Problem

A reader who only ever saw this project one lesson at a time might be
able to explain what `Service`'s constructor does, in isolation, without
being able to say *why* it's shaped that way rather than some simpler
alternative. Recognizing syntax and understanding a design are not the
same skill — this curriculum's own stated milestone for this phase is
specifically the second one, not the first.

### The Real Project Change

- **Reference Source:** no reference counterpart — this unit reviews
  reasoning already given, in full, across Lessons 1.2–1.11's own SE Lens
  sections; nothing here is a new justification, only a consolidated
  restatement.
- **Files affected:** none.
- **Change type:** none (inspection only).
- **Location:** every SE Lens section in Lessons 1.2 through 1.11.
- **Dependencies:** all of Lessons 1.2 through 1.11.

### Every Abstraction, and the Problem It Actually Solves

- **`class` (Lesson 1.2)** — gives behavior an actual named home, instead
  of loose top-level statements with no boundary between unrelated
  pieces of logic.
- **Fields and encapsulation (Lessons 1.3–1.4)** — give an object real
  memory (`runCount`), then guarantee that memory can only be changed
  through code that's actually allowed to change it (`private` plus a
  read-only `RunCount` property), rather than being directly overwritable
  by anything that can see the object at all.
- **Composition, `"has-a"` (Lesson 1.5)** — splits a class's unrelated
  jobs (counting vs. reporting) into separate, focused classes, connected
  by one holding a reference to the other, rather than one class trying
  to do both jobs itself.
- **Constructor injection, dependency inversion (Lesson 1.6)** — moves
  the responsibility for *creating* a dependency away from the class that
  *uses* it, to whatever code constructs that class — proven necessary
  the moment `Program.cs` needed to share one `Logger` between two
  different uses, which `Service` building its own could never have
  allowed.
- **Interfaces, implementation, polymorphism (Lesson 1.7)** — names *what*
  a dependency can do (`Log(string message)`) separately from *which*
  concrete class actually does it, which is the only reason Lesson 1.8's
  entire one-line swap was possible at all.
- **Loose coupling, programming against an abstraction (Lesson 1.8)** —
  not a new construct, but the actual, provable payoff of 1.5 through
  1.7's design choices: swapping `ConsoleLogger` for `LoudLogger` touched
  exactly one file, confirmed by a real, empty `git diff Service.cs`.
- **Generics (Lesson 1.9)** — lets one written class or method body work
  correctly across multiple types, without duplicating that body once per
  type — deliberately built with zero relationship to `Service` or
  `ILogger`, proving generics are a general capability, not something
  tied to this project's own specific classes.
- **Exceptions, throw/catch (Lesson 1.10)** — lets a class refuse an
  operation it knows is invalid (`Service.Reset()` on a never-run
  service) without silently doing nothing, while leaving the decision of
  *what to do about that refusal* to the caller, not the class that
  detected the problem.
- **`Task`/`async`/`await` (Lesson 1.11)** — lets a method pause partway
  through its own execution, waiting for something that takes real time,
  without blocking the thread it's running on — proven, not just
  claimed, by a real run showing a line print before either of two
  concurrent delays had finished.

### Composition vs. Inheritance, Answered Directly

This project uses composition — `Service` has-a `ILogger` — everywhere it
needs one class to rely on another. It uses interface implementation —
`ConsoleLogger` is-a `ILogger`, `LoudLogger` is-a `ILogger` — everywhere
it needs multiple classes to satisfy the same contract. It uses **class
inheritance — one class extending another class's own implementation —
nowhere at all.** No `class A : B` exists in this project where `B` is
itself a class rather than an interface. This is worth stating as a real,
deliberate fact rather than an oversight: every problem this phase
actually encountered — swapping loggers, giving `Service` a dependency,
handling failure, running asynchronously — was solved by *composing*
objects together or by multiple classes *implementing* a shared
interface, and none of them needed one class to inherit another's
concrete implementation to be solved. That absence is itself the
curriculum's own point: composition and interfaces cover a very large
fraction of real object-oriented design, and reaching for class
inheritance is a choice that needs its own specific justification, not a
default starting point.

### CS Lens

The general principle underneath every abstraction reviewed above is
**separation of concerns** — dividing a system so each piece has one
clear job, and the connections between pieces are as narrow as the actual
problem requires:

```
Also recognized in: a car's separate braking, steering, and engine
systems, each independently serviceable, a company's separate legal,
engineering, and sales departments, each with its own clear mandate, an
operating system's separation between user programs and kernel-level
hardware access, a plumbing system's separate supply and drainage
pipes, never sharing a single pipe for both jobs
```

Every abstraction this phase introduced is a specific technique for
achieving the same underlying goal: keep responsibilities separate enough
that any one of them can change without forcing every other one to
change too.

### SE Lens

The alternative this entire phase implicitly argued against, one lesson
at a time, is a single, undifferentiated `Service` class doing
everything itself — its own counting, its own printing, its own
dependency creation, all inline, with no interfaces, no injected
collaborators, and no separate classes at all. That alternative is not
hypothetical; it's exactly what `Service` actually was after Lesson 1.2,
before any of the following nine lessons existed. The real, cumulative
cost paid across this phase — nine additional files, one interface, one
generic class, one generic method, a try/catch block, and an async
method, where a single file could have held every line of actual logic —
bought this project real, demonstrated properties: a swappable logging
implementation (1.8's own empty diff), reusable generic utilities with no
project-specific coupling (1.9), and a documented, catchable failure mode
(1.10) that a single undifferentiated class would have made much harder
to isolate and reason about. Every one of these costs was paid
deliberately, one lesson at a time, each with its own specific, provable
justification — never as ceremony for its own sake.

### Connect to What Came Before

Every SE Lens section in Lessons 1.2 through 1.11 argued for exactly one
decision, in isolation, against one specific alternative. This unit is
the first to hold all of those arguments at once, side by side — and the
one new fact this review surfaces that no single earlier lesson stated on
its own: every one of those decisions used composition or interface
implementation, and none of them ever needed class inheritance to work.
