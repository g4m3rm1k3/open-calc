# Lesson 1.6: Who Creates the Dependency — Give the Service a Dependency

**What you will build.** `Service` gets its first hand-written constructor
— the first explicit constructor anywhere in this entire curriculum.
Instead of building its own `Logger` internally (Lesson 1.5's field
initializer), `Service` now receives one from outside, through its
constructor: `public Service(Logger logger) { this.logger = logger; }`.
`Program.cs` creates the one `Logger` this program uses and hands it to
`Service` explicitly — and, because it already has that `Logger` in hand,
reuses the exact same object for its own direct logging too, rather than
creating a second, redundant one the way Lesson 1.5 did. Along the way,
this lesson's first working attempt at that constructor contains a real,
common bug — naming the parameter and the field it's meant to fill
identically — and lets it actually crash the running program with a real
exception, before fixing it. A **dependency** is any object another object
needs in order to do its job; **constructor injection** is supplying that
dependency through the constructor rather than the object creating it
itself; and **`this`** is the keyword that makes the fix possible at all,
by naming "the specific object this code is currently running on,"
unambiguously, the moment a parameter and a field share a name.

**What you need to know first.** From **Lesson 1.5 — One Class, One
Job**: the real project at `code/01-csharp/Service/`, `Service`'s `has-a`
relationship with `Logger`, wired there via a field initializer,
`composition`, and `responsibility`. From **Lesson 1.4**: `private`,
`public`, `property`, `encapsulation`, and this curriculum's first real
compile-time errors. From **Lesson 1.3**: `field`, `object state`,
`instance member`, `int`. From **Lesson 1.2**: `class`, `object`,
`instance`, `method`, `constructor` (specifically, the *compiler-supplied
default* constructor every class in this project has relied on until
now), `new`, `var`, member access (`.`), the assignment operator (`=`).
From **Lesson 1.1**: `Console`, `Console.WriteLine`, string literals,
semicolons, and top-level statements. From the curriculum's own stated
assumptions: enough Python experience to have already written
`def __init__(self, name): self.name = name` — this lesson leans on that
prior exposure specifically to contrast Python's mandatory `self` with
C#'s optional-until-it-isn't `this`.

## Terms used in this lesson

- **dependency** — any object another object needs in order to do its
  job, that it does not — and, per this lesson, should not — create for
  itself. `Logger` is `Service`'s dependency: `Run()` cannot do its full
  job (updating the count *and* reporting it) without one.
- **constructor injection** — supplying an object's dependency by passing
  it as a constructor argument, rather than the object constructing that
  dependency internally (Lesson 1.5's own approach, now replaced). This is
  a **hard concept** — a real, named design technique — so it gets full
  CS Lens treatment below rather than a one-line definition. It exists so
  the *caller* of a class, not the class itself, decides exactly which
  concrete dependency gets used, without the class's own source code ever
  needing to change to accommodate a different one.
- **dependency inversion** — the underlying design principle constructor
  injection is one practical way to apply: instead of a class depending on
  *and* being responsible for creating its own dependencies, that
  responsibility is *inverted* — handed to whatever code creates the class
  in the first place. Before this lesson, `Service` depended on `Logger`
  *and* controlled exactly how one came into existence (`new Logger()`,
  hardcoded inside `Service` itself); after this lesson, `Service` still
  depends on `Logger`, but creating one is now entirely someone else's
  job.
- **constructor parameter** — a named placeholder a constructor declares
  for information it needs handed in in order to construct the object
  correctly, written inside its declaration's parentheses — the same
  general idea as a method parameter (Lesson 1.5's `Log(string message)`),
  now applied to a constructor for the first time in this project.
- **`this`** — a keyword, usable inside any instance method or
  constructor, referring to the *specific object* that method or
  constructor is currently running on. It exists because, the moment a
  parameter or local variable shares a name with one of the object's own
  fields, the parameter or local variable wins inside that scope — plain
  `logger` would refer to the constructor's own parameter, not the field —
  so `this.logger` is how the code says, explicitly, "the field belonging
  to this object," rather than "whatever `logger` means in the nearest
  enclosing scope."
- **shadowing** — when a parameter or local variable's name is identical
  to a field's name, making the field temporarily unreachable by its own
  bare name inside that scope — the parameter or variable "shadows" it.
  This is exactly what made this lesson's first constructor attempt fail:
  `logger = logger;`, with no `this`, reads as "assign the parameter to
  itself," touching the field not at all.
- **compiler warning `CS1717`** — reappearing in spirit from Lesson 1.4's
  general **compiler warning** entry, and worth naming by its specific
  code this time: `Assignment made to same variable; did you mean to
  assign something else?` — the C# compiler's own, built-in detector for
  exactly this lesson's bug, firing the moment an assignment's left and
  right sides are the literal same variable.
- **compile-time error** and **compiler warning** — reappearing from
  Lesson 1.4: an error stops the build; a warning doesn't. This lesson's
  buggy constructor produces three real warnings and zero errors — the
  build succeeds, which is exactly why the bug survives all the way to a
  crash at runtime instead of being caught before the program ever runs.
- **runtime error** — an error only discovered while a program is actually
  executing, contrasted with Lesson 1.4's compile-time errors, which are
  caught before a program ever runs at all. This lesson's own
  `NullReferenceException` is this curriculum's first runtime error: the
  build succeeds completely, and the program only fails once it actually
  reaches the specific line that depends on the bug.
- **exception** and **unhandled exception** — an exception is an object
  representing something that went wrong while a program was running,
  thrown by code that detects the problem. "Unhandled" means nothing in
  the program ever catches it — no mechanism for that exists yet in this
  curriculum's code (Lesson 1.10 is where handling one is finally taught)
  — so the runtime's own default behavior takes over: printing a
  description of what went wrong and ending the program immediately,
  right where the exception occurred.
- **`NullReferenceException`** — the specific exception .NET throws when
  code tries to call a method or access a member *through* a reference
  that doesn't actually point to any object — a `null` reference. This
  lesson's own buggy `logger` field, left `null` by the shadowing bug, is
  exactly this situation the moment `logger.Log(...)` tries to call
  `.Log` through it.
- **stack trace** — the ordered list of method calls that were active at
  the moment an unhandled exception occurred, printed as part of that
  exception's own default output, showing exactly which method the
  problem happened in and which method called that one, and so on,
  outward. This lesson's own stack trace names `Service.Run()` first —
  where the crash actually happened — then the top-level statements that
  called it.
- **parameter, argument** — reappearing from Lesson 1.5: still a named
  placeholder a member declares for information it needs from outside,
  and the actual value supplied to fill it at a specific call site. This
  lesson's constructor parameter, `logger`, is filled by whatever `Logger`
  argument `Program.cs` passes to `new Service(logger)`.
- **field, private, class, block (`{ }`), `void`, call syntax (`( )`),
  `var`, `new`, member access (`.`), assignment operator (`=`), string
  literal, semicolon (`;`), `int`, `public`** — all reappearing from
  Lessons 1.1–1.5, unchanged in meaning, all still present in
  `Service.cs`, `Program.cs`, and this lesson's isolated lab.

## Concept Unit: The Constructor Parameter — Where the Bug Hides

### The Problem

`Service` currently builds its own `Logger` the moment it's constructed,
via a field initializer — nothing outside `Service` gets any say in that
at all. To let a caller supply a specific `Logger` instead, `Service`
needs to actually *accept* one from outside. Nothing in this project has
ever written a constructor with a parameter before — every constructor
so far has been the compiler's own silent, empty, parameterless one.

> **Stop and think, before reading on:** you already know Python's
> `def __init__(self, name): self.name = name` — a parameter, `name`,
> assigned to an attribute of the exact same name, disambiguated only by
> `self.` in front of one of them. Given that C#'s field is simply named
> `logger` with no required prefix at its own declaration (`private Logger
> logger;`), and a constructor parameter can be named anything at all —
> what do you predict happens if the constructor's own parameter is *also*
> just named `logger`, with nothing distinguishing it from the field, the
> way Python's `self.` already distinguishes its own two `name`s?

### The Real Project Change

- **Reference Source:** no reference counterpart — from-scratch addition,
  same as every unit in this project so far.
- **Files affected:** modified — `code/01-csharp/Service/Service.cs` and
  `code/01-csharp/Service/Program.cs`.
- **Change type:** replace (the field initializer is removed; a
  constructor is added in its place) and replace (`Program.cs` now
  creates the `Logger` first and passes it in).
- **Location:** inside `Service`'s block, replacing the field initializer
  from Lesson 1.5 with a plain field declaration plus a new constructor;
  in `Program.cs`, reordering the first two lines.
- **Dependencies:** the `Service` and `Logger` classes from Lesson 1.5.

### Introduce the Concept in Isolation

A throwaway project, `ScratchE`, was scaffolded fresh in this session's own
scratch directory. A `Greeter` class was given a constructor accepting a
`name` parameter, matching its own field's name exactly:

```csharp
var greeter = new Greeter("Ada");
greeter.SayHello();

public class Greeter
{
    private string name;

    public Greeter(string name)
    {
        name = name;
    }

    public void SayHello()
    {
        Console.WriteLine(name);
    }
}
```

Run for real:

```
dotnet run
```

Real output:

```
Program.cs(8,12): warning CS8618: Non-nullable field 'name' must contain a non-null value when exiting constructor. Consider adding the 'required' modifier or declaring the field as nullable.
Program.cs(10,9): warning CS1717: Assignment made to same variable; did you mean to assign something else?
Program.cs(6,20): warning CS0649: Field 'Greeter.name' is never assigned to, and will always have its default value null

```

That trailing blank line is real, printed output, not a formatting
accident — capturing this run's raw standard-output bytes directly
confirmed exactly two characters: a carriage return and a line feed, the
line terminator alone, nothing else. This proves the concept named in
this lesson's Header: **shadowing**. `name = name;` inside the constructor
reads as "assign the parameter `name` to itself" — the parameter, not the
field, is what that bare word `name` refers to inside this exact scope,
because a constructor parameter shadows a field of the same name for the
whole body of that constructor. The field never gets touched at all, so
it keeps its **default field value** for a `string` — `null` — and
`Console.WriteLine(null)` prints only its line terminator, silently, with
no error of any kind. The C# compiler's own `CS1717` warning is a real,
built-in detector for exactly this mistake — `Assignment made to same
variable; did you mean to assign something else?` — though, notably, a
warning, not an error: the build still succeeds regardless.

`ScratchE` is kept alive rather than deleted immediately — the next
concept unit in this lesson still needs it.

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`public`** — the access modifier, reappearing from Lesson 1.2, applied
  here to a constructor rather than a class or method.
- **`Service`** (no return type before it) — the constructor's own name,
  reappearing in kind from Lesson 1.2's entry for the *implicit* default
  constructor, now written by hand for the first time.
- **`(Logger logger)`** — the **constructor parameter** list: `Logger`,
  the parameter's declared type; `logger`, its name — chosen, this time,
  deliberately identical to the field it's meant to fill, which is exactly
  what causes this unit's own bug.
- **`{` ... `}`** — the constructor's own block, reappearing from Lesson
  1.2.
- **`logger = logger;`** — the assignment operator, reappearing from
  Lesson 1.2, but this time both sides resolve to the *same* thing: the
  constructor's own parameter. Nothing here reaches the field at all.

### CS Lens

Shadowing — an inner name hiding an outer one of the same name for as long
as that inner scope lasts — is a general property of how names resolve in
nested scopes, not unique to constructors or even to C#:

```
Also recognized in: a Python function parameter with the same name as a
module-level variable, a JavaScript block-scoped `let` hiding an outer
variable of the same name, a loop variable reusing the name of a
variable declared just outside the loop, a nested function's own local
variable hiding a variable from its enclosing function
```

Every one of these resolves a name to whichever declaration is *closest*
to where it's used — which is exactly why a parameter, sitting right at
the top of a constructor's own scope, always wins over a field declared
elsewhere in the class, no matter how obviously the two were meant to
refer to the same thing.

### SE Lens

The alternative not chosen here — giving the parameter and the field
genuinely different names, such as `newLogger` — would sidestep this
entire bug without needing `this` at all. That alternative is completely
valid C#, and plenty of real code is written that way. It was not the
path taken in this lesson specifically because matching the parameter's
name to the field's is itself a widely used, deliberate convention — it
documents, at the call site and inside the constructor alike, exactly
which field a given parameter is *for* — and `this` is the language
feature that makes that convention safe to use rather than a recurring
trap. The real cost, demonstrated directly by this unit's own bug: naming
collisions like this one compile cleanly and, depending on what happens to
the un-set field afterward, can either fail *loudly*, the way this
lesson's real project is about to, or fail *silently*, the way this
unit's own lab just did — printing nothing wrong-looking at all, just an
empty line where a name should have been. A compiler warning is the only
thing standing between this mistake and a program that appears to work.

The real project crashes where the isolated lab merely printed a blank

## Concept Unit: `this` — Completing the Injection

### The Problem

`logger`, inside `Service`'s own constructor, refers to the parameter, not
the field — proven, in the previous unit, by a real crash. Some way is
needed to say, unambiguously, "the field belonging to *this specific
object*," distinct from whatever local name happens to be sitting closer
in scope.

> **Stop and think, before reading on:** Python's `self` is a parameter
> you write out yourself, by hand, as the first argument of every
> instance method — nothing works without it, and it's simply always
> there, explicitly, in every method signature you've ever written. Given
> that C# instance methods and constructors never declare anything like
> that as an explicit parameter anywhere in this curriculum's code so
> far — no `self` has ever appeared in a `Run()` or `Log()` signature —
> do you predict C# has no equivalent concept at all, or that it has one
> that's simply implicit, available without being declared, only surfacing
> in code the moment it's actually needed to resolve an ambiguity like
> this lesson's own?

### The Real Project Change

- **Reference Source:** no reference counterpart — from-scratch addition.
- **Files affected:** modified — `code/01-csharp/Service/Service.cs`.
- **Change type:** replace (one line, inside the constructor).
- **Location:** the constructor's own body, added in the previous unit.
- **Dependencies:** the buggy constructor from the previous unit.

this.logger = logger;

### Mechanical Walkthrough

Enumerating the one changed element in the New Code block above:

- **`this`** — a keyword referring to the current object — the specific
  `Greeter` (or, in the real project, `Service`) this exact constructor
  call is building. It requires no declaration and no parameter of its
  own; it's simply always available inside any instance method or
  constructor.
- **`.logger`** (or `.name`) — **member access** (`.`), reappearing from
  Lesson 1.2, this time reaching into `this` — the current object —
  rather than into some other named variable, to name its own `logger`
  field specifically, distinct from the identically-named parameter
  sitting in the same scope.

### CS Lens

`this` is a concrete instance of **self-reference** — a running piece of
code having a way to refer to the specific object it's currently acting
on, distinct from any other object of the same kind:

```
Also recognized in: Python's explicit `self` parameter, Java's and C++'s
own `this` keyword, Kotlin's `this`, JavaScript's (more context-
dependent) `this`, a person filling out a form referring to "myself"
rather than repeating their own full name every time
```

Every one of these gives running code a way to say "the specific thing
I'm currently part of," without that thing needing to be passed around
and renamed at every single step.

### SE Lens

Python's alternative — an explicit `self` parameter, written out by hand
on every single instance method — was not chosen for C#. The tradeoff:
Python's version is always visible, right there in every method
signature, with no implicit magic to explain; C#'s version stays out of
the way entirely until a genuine ambiguity — like this lesson's shadowing
— forces it to be written down. The real cost of C#'s choice, demonstrated
directly by this lesson's own bug: because `this` is implicit rather than
mandatory, it's possible to write a constructor that *looks* complete
without it, compiles, and is subtly wrong — exactly what happened here.
Completing this fix also completes this lesson's own larger point: `Logger`
now genuinely arrives from *outside* `Service`, via **constructor
injection**, rather than `Service` deciding for itself how to make one —
**dependency inversion**, made concrete. The real, provable benefit,
visible in the finished `Program.cs`: this program now needs exactly one
`Logger`, not two, because the same object created once can be handed to
`Service` *and* used directly, something Lesson 1.5's design — `Service`
quietly building its own — could never have allowed, since nothing outside
`Service` ever had a reference to the one *it* built.
