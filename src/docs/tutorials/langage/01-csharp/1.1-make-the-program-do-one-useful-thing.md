# Lesson 1.1: From Source Text to a Running Process — Make the Program Do One Useful Thing

**What you will build.** A brand-new C# console project named `Service` — the seed
of the small service architecture Phase 1 grows across the next eleven lessons —
that does exactly one observable thing: printing `Service is running.` to the
terminal when it runs. The transferable problem underneath that single line is
bigger than the line itself. In Python, a `.py` file is already a runnable
program the moment it exists — there is no separate step between writing the
text and the interpreter executing it. C# has no such shortcut. Before any of
this project's code can run, something has to exist that a compiler recognizes
as *a project*; something has to decide *where execution begins* inside that
project's files; and *translating* that written text into a runnable form has
to happen as a real, visible step triggered on purpose, not one the language
hides. What a project even is, where a program starts, and what a compiler's
build step actually does — those three problems are what this lesson is about.
Printing one line is just the smallest task that forces all three to become
real.

**What you need to know first.** Nothing from a prior C# lesson — this is the
first lesson of Phase 1, and Phase 1 does not continue any earlier project.
From the curriculum's own assumptions: enough command-line comfort to run
`cd`, `mkdir`, and an installer command like `pip install` without those being
explained again here; enough Python to know that a `.py` file's statements
already run top to bottom without any extra step; and, from **Lesson 0.1 —
Create the first repository**, the specific commands `git init`, `git add`,
and `git commit -m "<message>"`, reused only in this lesson's closing commit,
not anywhere in the C# code itself. No object-oriented concepts are assumed or
used — this lesson deliberately contains no class, so there is nothing from
Phase 0 or outside experience about objects to draw on yet.

## Terms used in this lesson

- **project** — a folder plus a build-recipe file that tells a compiler what
  kind of program to produce and what it needs to build it. It exists because,
  unlike a Python `.py` file that the interpreter just reads and runs, a
  compiled `.cs` file on its own doesn't tell any tool enough to turn it into
  a running program.
- **dotnet CLI** — the single command-line program (`dotnet`) that wraps the
  entire .NET SDK: scaffolding new projects, restoring dependencies,
  compiling, and running, all through one tool instead of several separate
  ones.
- **`dotnet new`** — the CLI subcommand that scaffolds a new project from a
  named template, so a project's starting files don't have to be typed by
  hand every time one is created.
- **console template** — the specific template name (`console`) passed to
  `dotnet new`, telling it to scaffold a runnable, text-only program rather
  than, say, a web project or a class library.
- **`-o` / `--output`** — a `dotnet new` flag naming the folder the new
  project's files are written into.
- **`-n` / `--name`** — a `dotnet new` flag naming the project itself (used
  for the generated `.csproj` file's name and the compiled assembly's name).
- **`.csproj` file (project file)** — the actual XML file that *is* a
  project's build recipe. Its presence, not any folder-naming convention, is
  what makes a folder "a project" as far as the build tooling is concerned.
- **SDK-style project** — the modern (2017-onward), deliberately minimal
  `.csproj` format, which inherits a large set of sensible default build rules
  from a named SDK instead of spelling every rule out by hand. The older
  format needed dozens of lines for even a trivial project, and almost none
  of that was ever actually specific to the project.
- **XML element** — a markup tag, like `<PropertyGroup>...</PropertyGroup>`,
  that names and contains a piece of structured data. `.csproj` files are
  written in XML because MSBuild (the build engine that reads them) needs a
  format it can parse unambiguously — the same reason config formats in
  general aren't just written as prose.
- **XML attribute** — a `name="value"` pair written inside an element's own
  opening tag, giving extra data about that specific element, as opposed to a
  child element nested inside it. `Sdk="Microsoft.NET.Sdk"` is an attribute on
  the `<Project>` element, not a separate element of its own.
- **`PropertyGroup`** — an XML element that groups a set of named build
  settings together, so a project file with many settings stays organized
  into logical clusters instead of one flat, undifferentiated list.
- **`OutputType`** — a build setting (an XML element inside `PropertyGroup`)
  telling the compiler what kind of binary to produce. Its value here, `Exe`,
  means "a program that can be launched directly," as opposed to `Library`,
  which would produce a `.dll` meant to be referenced by other code rather
  than run on its own.
- **`TargetFramework`** — a build setting naming which .NET version/runtime
  this project compiles against and is guaranteed to run on. It exists
  because .NET code isn't universally portable across every runtime version
  without this being pinned down somewhere explicit.
- **Target Framework Moniker (TFM)** — the short string format (like
  `net10.0`) .NET tooling uses to name a specific target framework/runtime
  version. It exists so build tools have one unambiguous, machine-parseable
  string to compare against, instead of a free-text version description a
  program would have to guess at.
- **`ImplicitUsings`** — a build setting that, when enabled, automatically
  inserts a small standard set of `using` directives (including one for the
  `System` namespace) into every file in the project, so the same handful of
  common namespaces don't have to be imported by hand in every single file.
- **namespace** — a named grouping of types that exists to prevent two
  unrelated pieces of code from accidentally defining a type with the same
  name. `Console` lives inside the `System` namespace, so its full name is,
  technically, `System.Console`.
- **`using` directive** — a statement (`using System;`) that imports a
  namespace's types into a file, so they can be referred to by their short
  name (`Console`) instead of their full qualified name (`System.Console`).
  `ImplicitUsings`, above, is what makes writing this by hand unnecessary in
  this project.
- **`Nullable`** (nullable reference types) — a build setting that turns on
  compiler-level tracking of whether a reference-type variable might be
  `null`, so the compiler can warn about a possible `null` before it causes a
  runtime crash, instead of the reader finding out the hard way, at runtime,
  the same way Python or JavaScript would.
- **restore** (NuGet restore) — a step `dotnet new` (and later `dotnet build`
  and `dotnet run`) performs automatically, resolving the project's full
  dependency graph — here, just the base SDK and runtime references — before
  the project is considered ready to build. It exists because a build tool
  can't safely compile against dependencies it hasn't first confirmed it can
  actually locate.
- **top-level statements** — a C# feature letting a file's own statements act
  directly as the program's starting sequence, with no explicit wrapping
  class or method required around them. It exists to remove ceremony for the
  common case of a small program, script, or — as here — a first lesson,
  where writing a full class-and-method wrapper before a single line of real
  logic would only be friction.
- **entry point** — the specific place a running program's execution actually
  begins. Every executable needs exactly one, because "run this program" is
  meaningless unless something has agreed where "the beginning" is.
- **statement** — one complete instruction the runtime carries out before
  moving to the next one; the basic unit a C# program's execution is built
  out of, one after another.
- **semicolon (`;`) as a statement terminator** — the character C# requires
  at the end of each statement. It exists because, unlike Python, where a
  newline marks the end of a statement, C#'s grammar allows a single
  statement to span multiple lines, or multiple statements to share one line,
  so whitespace alone can't mark where one statement ends and the next
  begins — the semicolon removes that ambiguity for the compiler.
- **string literal** — text typed directly into source code, delimited by
  double quotes (`"..."`). The same underlying idea as a Python or JavaScript
  string literal: fixed text data the program doesn't compute, just contains.
- **stdout (standard output)** — the specific output stream a running process
  writes ordinary text to, which a terminal displaying that process reads
  from and renders. It's the reason text printed by a program shows up in the
  same window that launched it.
- **build** — the act of turning written source text into a form something
  can actually execute. It exists as a distinct step in C# because, unlike
  Python's interpreter (which reads and executes source directly, line by
  line, on every run), a .NET program's source is translated once into a
  separate, already-executable artifact before it's ever run.
- **compile / compilation** — the specific translation the C# compiler
  performs, turning `.cs` source files into Intermediate Language (IL)
  instructions packaged into an assembly. "Build," above, is the overall
  step; "compile" is what's actually happening inside it.
- **assembly (the compiled `.dll`)** — the real file (`Service.dll`) that
  compilation produces: a package of compiled IL code plus metadata
  describing it, which the .NET runtime can load and execute. It's the
  concrete, inspectable artifact standing between "source text" and "a
  running process."
- **`dotnet build`** — the CLI subcommand that performs a build without
  running the result, producing the compiled assembly (and its supporting
  files) on disk and stopping there.
- **`dotnet run`** — the CLI subcommand that performs a build (skipping it if
  nothing has changed since the last one) and then immediately executes the
  freshly built assembly, as one combined step.
- **running a compiled assembly directly (`dotnet <path-to-dll>`)** — passing
  `dotnet` a path to an already-built `.dll` loads and executes that exact
  compiled assembly immediately, with no build step at all. It exists here as
  proof that "build" and "run" are genuinely two separate capabilities, not
  one indivisible action `dotnet run` merely happens to expose as two words.
- **repository** — the hidden `.git` folder and everything it tracks: a
  project's entire recorded history, able to reconstruct any previously
  committed state. A brand-new C# project has no history at all until one is
  created here, the same way `code/00-git-workflow/` needed one created for
  it back in Lesson 0.1.
- **staging area** — the place `git add` moves changes into before they're
  committed. It exists as a deliberate middle step so a commit can be built
  from exactly the changes intended, not automatically from everything
  currently different in the working tree.
- **`git init`** — the command that creates a brand-new, empty repository (an
  empty `.git` folder) in the current directory. Every repository starts as a
  real, explicit act of creating one — nothing is a repository by default.
- **`git add`** — the command that moves a file's current content into the
  staging area described above, marking it to be included in the next
  commit.
- **`git status`** — a command that shows the working tree's current state
  relative to the last commit: which files are new, modified, staged, or
  untracked. It exists as a way to see exactly what a commit is about to
  include before actually making it, rather than committing blind.
- **`git commit`** — the command that permanently records whatever is
  currently staged as a new point in the repository's history, alongside a
  message explaining why.
- **meaningful commit message** — a commit message that states *why* a
  change was made, not merely *what* changed (the diff itself already shows
  what changed). It exists so a repository's history stays useful to a future
  reader trying to understand a past decision, not just a log of timestamps.
- **`.gitignore`** — a file listing paths git should never track, even if
  they exist in the working tree. It exists because some files — `bin/` and
  `obj/` here — are entirely regenerable from source by re-running the
  build, and committing them would bloat the repository's history with
  content that carries no real information a teammate needs.

## Objects and methods used

- **`Console`**
  - *What it is:* a static class in the .NET base class library representing
    the current process's standard input, output, and error streams.
  - *Implementation:* declared as `public static class Console` in the
    `System` namespace, part of the shared .NET runtime libraries — not
    something this project wrote or owns.
  - *Its use:* this lesson calls it because printing to the terminal is the
    "one observable result" the whole lesson needs, and `Console` is .NET's
    built-in gateway to that terminal.
  - *Type:* a `static` class — a namespace-like container of static members,
    never instantiated. There is no `new Console()` anywhere, and none is
    possible.
  - *Responsibility:* exposes the process's standard input, output, and error
    streams, and provides static methods to read from and write to them
    (`WriteLine`, `Write`, `ReadLine`, and others), plus a handful of
    environment-level knobs, such as text color. Its full charter is "the
    process's connection to the console window it runs in," not merely "lets
    you print text."
  - *Depends on:* the operating system's own standard-stream handles for the
    running process, which the .NET runtime has already wired up before any
    of this project's code runs. `Console` does not need anything passed to
    it by this project's code to do its job.
  - *Connects to:* called directly by `Program.cs`'s top-level statements;
    underneath it, `Console` forwards writes to the OS's real stdout stream,
    which the terminal displaying this lesson's output is reading from.
  - *Shape:* a public API surface at the outer boundary of this program — the
    seam between "code running inside the .NET process" and "the terminal
    window a human is watching."

- **`Console.WriteLine(string?)`**
  - *What it is:* a method that writes a line of text to standard output,
    followed by a line terminator.
  - *Implementation:* `public static void WriteLine(string? value)` — a
    `static` method returning `void`, taking one `string?` (nullable string)
    parameter. This is one overload among several on `Console`; others accept
    an `int`, a `bool`, an `object`, or no argument at all, for a bare blank
    line.
  - *Its use:* this is the exact call this lesson's code makes to produce its
    one observable result.
  - *Type:* a `static` method — called on the class itself
    (`Console.WriteLine(...)`), never on an instance, because `Console` has
    no instances to call it on.
  - *Responsibility:* convert its argument to text (already text, in this
    lesson's case) and append it to the process's standard output stream,
    followed by a newline, so each call's output lands on its own line.
  - *Depends on:* the string argument passed in, and, indirectly, the same
    OS-level stdout handle `Console` itself depends on.
  - *Connects to:* called by this project's top-level statements — its only
    caller here — and it in turn writes through `Console`'s underlying
    stream machinery to the OS's stdout, which the terminal reads and
    displays.
  - *Shape:* the exact edge of the public API boundary this lesson's code
    crosses to produce anything a human can see. Everything before this call
    is invisible computation; this call is where it becomes observable.

  `Console.WriteLine`'s contract is documented in Microsoft's own public API
  reference for `System.Console`; its real implementation is genuine, current
  source in the `dotnet/runtime` repository, reachable in an IDE with
  go-to-definition, the same as any other library method used later in this
  curriculum. It isn't shown here because the real body is buried several
  layers deep in the console-stream machinery — not a short, illuminating
  read for a first lesson — but nothing about it is secret or unreachable;
  it's ordinary code, written by people, sitting in a real file.

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the file above, in order:

- **`<Project ...>` / `</Project>` (line 1, line 10)** — the root **XML
  element** of the whole file; every other element in the file is nested
  inside this one pair of tags. A `.csproj` file is required to have exactly
  one root element, the same way a well-formed document needs exactly one
  outermost container.
- **`Sdk="Microsoft.NET.Sdk"` (line 1)** — an **XML attribute** on the
  `<Project>` element, not a separate element. This is what makes the file an
  **SDK-style project**: it names which SDK's default build rules this
  project inherits, which is precisely why lines 2–9 can stay this short —
  a large body of ordinary build behavior (how to find `.cs` files, how to
  invoke the compiler, how to lay out `bin/`/`obj/`) is inherited from
  `Microsoft.NET.Sdk` rather than written out here.
- **`<PropertyGroup>` / `</PropertyGroup>` (line 3, line 8)** — a child
  **XML element**, nested inside `<Project>`, that groups the actual build
  settings together. A `.csproj` can have more than one `PropertyGroup`
  (for settings that only apply under certain conditions), but this project
  needs only one.
- **`<OutputType>Exe</OutputType>` (line 4)** — a build setting whose text
  content, `Exe`, tells the compiler to produce a directly runnable program.
  The alternative value, `Library`, would produce a `.dll` meant only to be
  referenced by other projects, never launched on its own — this project's
  entire point is to be launched, so `Exe` is what `dotnet new console`
  chose.
- **`<TargetFramework>net10.0</TargetFramework>` (line 5)** — a build
  setting whose text content, `net10.0`, is a **Target Framework Moniker**
  naming exactly which .NET version this project compiles against and is
  guaranteed to run on. It reads `net10.0` specifically because the .NET SDK
  actually installed on this machine, confirmed via `dotnet --version`, is
  `10.0.301` — `dotnet new` always targets whichever SDK generated the
  project, so this value is itself a small piece of real, environment-
  dependent output, not something guessable in advance without checking.
- **`<ImplicitUsings>enable</ImplicitUsings>` (line 6)** — a build setting
  turning on automatic insertion of a small standard set of `using`
  directives into every file in this project, including one for the
  `System` **namespace** — the namespace `Console` lives in. Because this is
  `enable`d, `Program.cs` (next unit) never has to write `using System;` by
  hand to reference `Console` by its short name.
- **`<Nullable>enable</Nullable>` (line 7)** — a build setting turning on
  the compiler's nullable-reference-type tracking: the compiler starts
  reasoning about whether a reference-type variable might be `null`, and
  warns before that possibility becomes a runtime crash. This project's own
  code doesn't yet do anything where that tracking is visible, but the
  setting is part of every project `dotnet new console` scaffolds by
  default, so it's real, present, and worth naming honestly rather than
  silently skipped.

### CS Lens

A `.csproj` file is **declarative configuration** describing *what* should be
built, read by a separate tool (MSBuild) that decides *how* — as opposed to
**imperative code**, like the `Console.WriteLine` call in the next unit,
which states *how* to do something, step by step, itself. This isn't unique
to .NET:

```
Also recognized in: package.json (Node.js), pom.xml (Maven/Java),
Cargo.toml (Rust), a Dockerfile's FROM/COPY/RUN instructions,
a CI pipeline's YAML config, HTML markup describing structure
versus the JavaScript that manipulates it
```

Every one of these hands a separate tool a description of *what* to do,
rather than code that does it directly — the tool is trusted to figure out
the *how*.

### SE Lens

The alternative not chosen here is a convention-based, file-less build: a
tool that just compiles whatever `.cs` files it finds in a folder, with no
separate manifest at all — closer to how a single Python script works. That
alternative doesn't scale past a single trivial file: the moment a project
needs a specific target framework, more than one source file, or (starting
several lessons from now) an external package dependency, *something* has to
record that information outside of any one source file, or every tool
touching this project would have to re-derive it by guessing. The real cost
paid for that, visible in this very unit, is ceremony: a project that does
nothing but print one line still needed a ten-line XML file to exist before
it could do even that.

## Concept Unit: The Entry Point — Top-Level Statements

### The Problem

The project from the previous unit exists, but nothing has actually been
*run* yet. `Program.cs`, sitting inside it right now, contains exactly one
line — the same boilerplate line every fresh `dotnet new console` project
starts with. In C, Java, or the "more than one line" of C++/Java/C# already
seen before this curriculum, running a program means the runtime looks for a
specific method — usually named `Main` — and calls it. Nothing that specific
has been written here at all.

> **Stop and think, before reading on:** if `Program.cs` were run right now,
> completely untouched, what do you predict would happen? Would it do
> nothing? Print an error demanding a `Main` method that doesn't exist? Or
> print something anyway — and if it printed something, what would that
> imply about where a C# program actually starts, given no explicit "starting
> method" appears anywhere in this one-line file?

### Introduce the Concept in Isolation

A second, separate throwaway project, `Scratch2`, was scaffolded fresh — not
reusing `Scratch1` — specifically to answer this with its boilerplate file
completely untouched:

```
dotnet new console -o Scratch2 -n Scratch2
```

Its real, unedited `Program.cs`:

```csharp
Console.WriteLine("Hello, World!");
```

Run for real, immediately, with no edits made:

```
dotnet run
```

Real output:

```
Hello, World!
```

This proves the concept directly: nothing was added, no `class`, no `Main`
method, nothing — and the program still ran, and still produced output. The
single statement already sitting in the file is, itself, where execution
begins. This is called **top-level statements**: a file's own statements,
written directly at the top level with no wrapping class or method, act as
the program's **entry point** — the specific place execution actually
begins — with no extra ceremony required.

### Mechanical Walkthrough

- **The absence of any `class` or `Main` declaration** — this is the

  every program to declare `class Program { static void Main(string[]
  args) { ... } }` around its logic; that requirement still exists in the
  language, but the compiler is willing to write the wrapping class and
  method itself when a file's statements are simply left at the top level,
  the way `dotnet new console` generated this one.
- **`Console.WriteLine("Hello, World!");`** — the one **statement** in this

### Execution-Order Note

There's no loop, branching, or state carried between steps in this single
statement — but it's still worth being explicit about what "top-level
statements act as the entry point" means for a file with *more than one*
statement, since the real project will have that shape again the moment the
next unit edits it. In the `Scratch1` throwaway project (still alive from
the previous unit), `Program.cs` was edited to two statements and run for
real:

1. `Console.WriteLine("First line.");` — runs to completion first: its text
   is written to standard output before control moves to the next line,
   because top-level statements execute strictly top to bottom, exactly
   like statements inside an ordinary method body.
2. `Console.WriteLine("Second line.");` — only begins after statement 1 has
   fully finished, which is why the real output below shows `First line.`
   before `Second line.`, never interleaved or reversed.

Real output, from the same `Scratch1` project reused from the previous unit:

```

Second line.
```

### CS Lens

An **entry point** — the one agreed-upon place a program's execution
begins — is not a C#-specific idea:

```
Also recognized in: C's int main(void), the JVM's public static void
main(String[] args), Python's if __name__ == "__main__": convention,
a CPU's reset vector pointing at the first instruction to execute on
power-on, an OS loader jumping to an ELF or PE file's declared entry
address
```

Every one of these is the same underlying agreement: "execution starts
*here*," stated somewhere a runtime or hardware can find it without having
to guess.

### SE Lens

The alternative not chosen for this specific file is the older, always-
explicit form: requiring `class Program { static void Main(...) { ... } }`
around every program's logic, no matter how small. That form is not gone —
it's still legal C#, and every class-based lesson later in this curriculum
will use it, because a program with more than a few lines benefits from an
explicit, visible entry point method. Top-level statements trade that
explicitness for less ceremony in the one place it costs the most: a
learner's very first working program, or a small script, where writing a
class and a method before a single real instruction would be friction with
no payoff yet. The real cost is a genuine language rule worth knowing
honestly: only one file in an entire project is allowed to contain top-level
statements — the moment this project grows a second source file with logic
at its own top level, the compiler will reject it, and that second file will
need an explicit method to live inside of instead.


lesson's single call doesn't have, but one worth remembering before reaching
for it that way later in this curriculum.

## Concept Unit: The Build/Run Cycle — `dotnet build` vs. `dotnet run`

### The Problem

`dotnet run` has now been used three times in this lesson without ever being
explained. Every one of those runs quietly did two things: turning source
text into something executable, and then executing it. Are those actually
one indivisible action, or two separate steps that only look fused together
because `dotnet run` happens to trigger both?

> **Stop and think, before reading on:** Python has nothing resembling this
> question — there is no separate "build Python" step before "run Python."
> Given that C# is compiled, what do you think actually exists, physically,
> as a file on disk, after a C# project has been built? And if that file
> already exists and is already runnable, do you think `dotnet run` would
> still recompile it every single time, even with nothing changed — or would
> it check first?

### Introduce the Concept in Isolation

Still inside the same throwaway `Scratch1` project, used one final time
before being discarded, its already-edited two-statement `Program.cs` was
compiled explicitly, without running it:

```
dotnet build
```

Real output:

```
  Determining projects to restore...
  All projects are up-to-date for restore.
  Scratch1 -> .../scratchpad/Scratch1/bin/Debug/net10.0/Scratch1.dll

Build succeeded.
    0 Warning(s)
    0 Error(s)

Time Elapsed 00:00:00.63
```

And the real resulting file on disk:

```
bin/Debug/net10.0/Scratch1.dll
```

Nothing printed `First line.` or `Second line.` — proving `dotnet build`, on
its own, translates source into a real, standalone file and stops, without
executing anything. Then, that exact compiled file was launched directly,
with no separate `dotnet run` involved at all:

```
dotnet bin/Debug/net10.0/Scratch1.dll
```

Real output:

```
First line.
Second line.
```

This proves the concept named in this unit's own title: **build** and **run**
are two genuinely separate capabilities. `dotnet build` performs
**compilation** — the C# compiler translating `.cs` source into Intermediate
Language packaged into an **assembly**, here `Scratch1.dll` — and stops.
Passing `dotnet` that exact `.dll` path loads and executes the already-
compiled assembly immediately, with no compilation step at all, proving the
assembly on disk really was a complete, independently runnable artifact all
along, not an illusion `dotnet run` was quietly recreating each time.

### Mechanical Walkthrough

- **`dotnet build`** — the CLI subcommand performing compilation only. Its
  real output above shows the compiler reporting where the resulting
  assembly was written (`Scratch1.dll`, inside `bin/Debug/net10.0/`), plus a
  warning/error count and elapsed time — this is what "build succeeded, and
  here is exactly what it produced" looks like, made visible rather than
  hidden.
- **`dotnet bin/Debug/net10.0/Scratch1.dll`** — `dotnet`, given a path to an
  already-compiled `.dll` instead of a subcommand name, loads and runs that
  exact assembly directly. No `.cs` file is read again, and no compiler runs
  again — everything needed to execute the program was already sitting
  inside the `.dll` produced by the previous command.

### CS Lens

Turning source text into a separately executable form before it ever runs is
**translation between representations** — the same shape of problem shows
up anywhere data is transformed from one encoding into another before use:

```
Also recognized in: any compiler's full pipeline (source → tokens →
AST → machine code), a JIT compiler translating bytecode to native
instructions the moment before it's needed, an image format
converter producing a .png from a .raw capture, a network protocol
serializing an in-memory object into bytes before sending it
```

Each of these produces a durable, inspectable intermediate artifact — an
assembly, a compiled binary, a file, a byte stream — standing between the
original form and whatever eventually consumes it.

### SE Lens

Python's alternative — no separate build step, just re-interpret the source
every time — was not chosen for C#. The real tradeoff: because C# is
compiled ahead of time, a whole category of errors (a missing semicolon, a
misspelled method name, a type mismatch) is caught by the compiler *before*
the program ever runs, rather than only being discovered mid-execution the
way an interpreted language might discover them. The cost is the translation
step itself — a real wait, however short, between writing code and seeing it
run, that Python's model never imposes. `dotnet run`'s existence is itself an
engineering answer to that cost: rather than making a learner type `dotnet
build` and then separately launch the result every time, it collapses the
two into one command for the overwhelmingly common case of "I just want to
see this run." The separation this unit just proved still real underneath
that convenience is a debt this lesson is deliberately not spending any more
time paying down: there is no reason yet, this early in the curriculum, to
use `dotnet build` on its own rather than `dotnet run` — that distinction
starts mattering once something later wants a build artifact without also
wanting to execute it, which hasn't happened yet in this curriculum's story.

- **`dotnet run`** — builds (if needed) and then immediately executes.
  Success looks like the program's own printed output appearing directly,
  with no separate build report shown unless something needed recompiling.
