# Lesson 1.2: Giving Behavior a Home — The First Class

**What you will build.** `code/01-csharp/Service/` still prints exactly one
line, `Service is running.`, when it runs — but by the end of this lesson
that line no longer comes from a bare top-level statement. It comes from
calling a method on a real, constructed object of a new class named
`Service`, declared in its own file, `Service.cs`. The transferable problem
underneath that move is bigger than the line itself: Lesson 1.1's whole
program was one instruction with no name, no boundary, and nowhere to grow.
This curriculum's own plan says `Service` becomes "a small service
architecture" across the next ten lessons — state, encapsulation, composed
responsibilities, injected dependencies, swappable implementations. None of
that has anywhere to live inside a single bare statement. A **class** is
what gives behavior an actual, named place to exist; an **object** is what
has to come into being, for real, at runtime, before that behavior can
actually run; an **instance** names the specific relationship between that
object and the class it came from; a **method** is behavior that belongs to
a class instead of floating free; and a **constructor** is the guaranteed,
automatic step that already runs the instant an object is born, whether or
not anyone wrote one by hand. Those five ideas are this lesson's actual
subject. Moving one string is just the smallest change that forces all five
to become real and necessary rather than abstract.

**What you need to know first.** From **Lesson 1.1 — From Source Text to a
Running Process**: the real project at `code/01-csharp/Service/`, its
`Service.csproj` (SDK-style, `net10.0`, `ImplicitUsings`/`Nullable` both
enabled), the fact that `Program.cs`'s one top-level statement *is* this
program's entry point with no `Main` method anywhere, the `Console` class
and its `static` `WriteLine(string?)` method, string literals, the
semicolon as a statement terminator, and the `dotnet build`/`dotnet run`
build/run cycle — all reused directly in this lesson's own code, and, per
the Repetition Rule below, each one explained again here in full rather
than assumed remembered. From the curriculum's own stated assumptions:
enough basic Python object-oriented experience to have already written a
class, a constructor, and `self.name = name` — this lesson leans on that
prior exposure only to contrast it with what C# does differently, never to
assume the C# syntax itself is already known.

## Terms used in this lesson

- **class** — a keyword and declaration introducing a new named blueprint:
  a description of what any object made from it will contain and be able
  to do, without itself being a running thing. It exists because Lesson
  1.1's program had no way to group related behavior under one name at
  all — a bare top-level statement has no boundary and nothing to attach a
  second, related piece of behavior to.
- **block (`{ }`)** — a pair of curly braces marking where a body begins
  and ends — here, a class's body. It exists because C#'s grammar is
  whitespace-insensitive: unlike Python, where indentation itself marks
  what's "inside" a class or function, C# needs an explicit character pair
  to mark that boundary, since whitespace alone carries no structural
  meaning in its grammar.
- **access modifier `public`** — a keyword controlling which other code is
  allowed to see and use the thing it's attached to; `public` is the least
  restrictive option, meaning "visible to any code that can see this type
  at all." It exists because, without some visibility control, every piece
  of code anywhere in a program could reach into and depend on every other
  piece's internal details directly, no matter how unrelated the two
  pieces are supposed to be — access modifiers let an author state what's
  meant to be depended on from outside versus what's just internal detail.
- **instance method** — a method that runs *on* a specific object rather
  than on the class as a whole; calling one requires an actual object to
  call it through (`service.Run()`), unlike a `static` method such as
  `Console.WriteLine` (reappearing from Lesson 1.1), which is called on
  the class itself with no object involved anywhere. It exists because
  most real behavior needs to act on *some particular* thing's own data —
  Lesson 1.3 makes this concrete the moment `Service` gets its first
  field — even though this lesson's own `Run()` doesn't yet touch any data
  of its own.
- **`void`** — a method's declared return type, meaning "this method hands
  no value back to whatever called it." It exists because every method
  declaration in C# must state some return type; `void` is the explicit,
  named way of saying "none," rather than a return type simply being
  omitted the way some languages allow.
- **object** — a concrete, real thing that exists while a program runs,
  created from a class's blueprint, occupying actual memory, with its own
  existence independent of any other object made from the same class. It
  exists because a class only describes what's *possible* — something
  still has to actually come into being at runtime for any of that
  possibility to become real, usable data a program can act on.
- **instance** — the specific relationship between one particular object
  and the class it was created from: this object *is an instance of*
  `Service`. It exists to distinguish "a `Service`" — the general kind of
  thing the class describes — from "this particular one, right here, that
  was just created" — the same distinction "a car" has from "the specific
  car parked in this driveway right now."
- **`new`** — the operator that creates a new object from a class, running
  that class's constructor and producing a usable reference to the
  freshly created object. It exists because bringing a new object into
  existence is a distinct, deliberate action a program has to trigger on
  purpose — nothing comes into being merely because a class was declared
  somewhere in a file.
- **constructor** — a special method sharing its class's exact name,
  declaring no return type at all — not even `void` — that runs
  automatically, exactly once, at the moment `new` creates an object,
  before any other method can be called on it. It exists because a newly
  created object needs some guaranteed, one-time opportunity to set itself
  up correctly before any other code can touch it; without one, a caller
  could accidentally start using an object that was never properly set up
  in the first place.
- **default constructor** — the specific parameterless constructor the C#
  compiler automatically supplies for any class that declares no
  constructor of its own. It exists because `new` always requires some
  constructor to run — rather than forcing every author to hand-write a
  do-nothing constructor for the common case of "there's nothing extra to
  set up yet," the compiler supplies one silently, with the same
  visibility as the class itself.
- **`var`** — a keyword letting a local variable's declared type be
  inferred by the compiler from whatever is assigned to it, instead of the
  author writing the type out by hand. It exists because a line like
  `Service service = new Service();` already states the type twice in one
  place — once as the declared type, again as what's being constructed —
  and `var` removes that repetition wherever the type is already obvious
  from the right-hand side of the assignment.
- **assignment operator (`=`)** — the operator storing whatever its
  right-hand side produces into the variable named on its left. It
  reappears here from the general idea already familiar from Python and
  JavaScript, but this is its first appearance in this curriculum's C#
  code — Lesson 1.1 never declared or assigned to a variable at all — and
  it's now storing a genuinely new kind of value: a reference to an
  object, rather than a plain number or string.
- **local variable** — a named storage location declared inside a method,
  or, as still applies in this lesson, inside a file's own top-level
  statements, existing only for as long as that statement sequence is
  running. This is this curriculum's first C# variable of any kind — worth
  naming plainly even though the general idea of "a variable" is already
  familiar from Python and JavaScript.
- **reference type** — a category of C# type — every `class` belongs to
  it — whose variables don't hold an object's data directly; they hold a
  reference pointing at an object living elsewhere, so copying the
  variable copies the reference, not the object itself. It matters the
  moment `service` is assigned `new Service()`: what actually sits inside
  the `service` variable is a pointer to that object, not the object's
  contents laid out inline. This lesson names that fact honestly without
  going further — Phase 4 of this curriculum (C++) is where value versus
  reference semantics gets confronted in full depth, once a language
  actually forces the distinction to matter for correctness.
- **member access (`.`)** — reappearing from Lesson 1.1: the dot operator,
  reaching into something to name one specific piece it contains. In
  Lesson 1.1 it reached into a `static` class (`Console.WriteLine`); here
  it reaches into an actual object instead (`service.Run()`) — the same
  operator, now used on a genuinely different kind of thing on its left.
- **string literal** — reappearing from Lesson 1.1: text typed directly
  into source code, delimited by double quotes, fixed data the program
  doesn't compute. It reappears unchanged here, inside `Service.Run()`'s
  own `Console.WriteLine("Service is running.");`.
- **semicolon (`;`) as a statement terminator** — reappearing from Lesson
  1.1: the character ending each statement, needed because C#'s grammar
  doesn't treat a line break as marking the end of a statement the way
  Python's does.
- **call syntax (`( )`)** — reappearing from Lesson 1.1: the parentheses
  invoking a method or constructor. Lesson 1.1 only ever showed this on a
  `static` call; this lesson adds a constructor call (`new Greeter()`) and
  an instance method call (`greeter.SayHello()`) to that same syntax.
- **SDK-style project / implicit file globbing** — extends Lesson 1.1's
  "SDK-style project" entry: part of the default build behavior this
  project's `.csproj` inherits from `Microsoft.NET.Sdk` is automatically
  compiling every `.cs` file found anywhere under the project's own
  folder, with no need to list each file individually inside the project
  file. This lesson is the first time this project has more than one
  source file, and nothing was added to `Service.csproj` to make the new
  one get compiled — proof this globbing behavior is real, not merely
  assumed to work.

## Objects and methods used

- **`Console`**
  - *What it is:* a static class in the .NET base class library
    representing the current process's standard input, output, and error
    streams.
  - *Implementation:* declared as `public static class Console` in the
    `System` namespace, part of the shared .NET runtime libraries — still
    not something this project wrote or owns.
  - *Its use:* called for the same reason as Lesson 1.1 — printing to the
    terminal is still the only way this program produces an observable
    result; only *where* that call now sits has changed.
  - *Type:* a `static` class — a namespace-like container of static
    members, never instantiated. There is still no `new Console()`
    anywhere, and none is possible.
  - *Responsibility:* exposes the process's standard input, output, and
    error streams, and provides static methods to read from and write to
    them (`WriteLine`, `Write`, `ReadLine`, and others), plus a handful of
    environment-level knobs such as text color. Its full charter is "the
    process's connection to the console window it runs in," not merely
    "lets you print text."
  - *Depends on:* the operating system's own standard-stream handles for
    the running process, already wired up by the .NET runtime before any
    of this project's code runs.
  - *Connects to:* called directly from inside `Service.Run()`'s own body
    now, rather than from `Program.cs`'s top-level statements directly as
    in Lesson 1.1; underneath it, `Console` still forwards writes to the
    OS's real stdout stream.
  - *Shape:* still a public API surface at the outer boundary of this
    program — unchanged from Lesson 1.1; only the calling location moved.

- **`Console.WriteLine(string?)`**
  - *What it is:* a method that writes a line of text to standard output,
    followed by a line terminator.
  - *Implementation:* `public static void WriteLine(string? value)` — a
    `static` method returning `void`, taking one `string?` (nullable
    string) parameter; one overload among several on `Console`.
  - *Its use:* still the exact call producing this project's one
    observable result — now made from inside `Service.Run()` instead of
    directly inside `Program.cs`.
  - *Type:* a `static` method, called on the class itself, never on an
    instance — unchanged from Lesson 1.1.
  - *Responsibility:* convert its argument to text and append it to the
    process's standard output stream, followed by a newline.
  - *Depends on:* the string argument passed in, and, indirectly, the
    OS-level stdout handle `Console` itself depends on.
  - *Connects to:* called now by `Service.Run()` — a real instance method,
    itself called by `Program.cs`'s top-level statements through the
    `service` object — rather than being called directly by top-level
    statements, as in Lesson 1.1. The call chain grew by one real link.
  - *Shape:* still the exact edge of the public API boundary this
    project's code crosses to produce anything observable.

- **`Service`**
  - *What it is:* this project's own first class — a blueprint describing
    what a "service" object contains and can do, not itself a running
    thing.
  - *Implementation:* `public class Service { public void Run() { ... } }`,
    declared in the new file `code/01-csharp/Service/Service.cs`. No
    fields yet (Lesson 1.3's own subject); no explicitly written
    constructor (this lesson's fourth unit).
  - *Its use:* gives this project's own behavior an actual, named,
    structural home instead of loose top-level statements — the seed this
    curriculum's own Phase 1 plan says will "gradually become a small
    service architecture" across the next ten lessons.
  - *Type:* a class — an instantiable blueprint, not `static` like
    `Console`; `new Service()` is both legal and, from this lesson onward,
    exactly how this project uses it.
  - *Responsibility:* right now, exactly one thing — running and printing
    this project's status line, via `Run()`. Nothing else yet; Lessons
    1.3 through 1.11 are what grow this responsibility further.
  - *Depends on:* nothing yet — no fields, and, per this lesson's fourth
    unit, no explicitly written constructor either.
  - *Connects to:* created and called by `Program.cs`'s top-level
    statements, its only caller right now; it in turn calls
    `Console.WriteLine` to produce output.
  - *Shape:* this project's first real internal building block —
    `Program.cs` is no longer the entire program by itself; it now depends
    on a distinct piece sitting in its own file.

- **`Service.Run()`**
  - *What it is:* an instance method belonging to `Service`, holding the
    exact behavior that is currently this whole project's point.
  - *Implementation:* `public void Run() { Console.WriteLine("Service is
    running."); }` — a `public`, non-`static` method, returning `void`,
    taking no parameters.
  - *Its use:* this is where Lesson 1.1's single statement now actually
    lives, moved out of `Program.cs` and into a named, callable piece of
    behavior that belongs to the `Service` class.
  - *Type:* an instance method — requires an actual `Service` object to
    call it through (`service.Run()`); there is no way to call it on the
    class itself the way `Console.WriteLine` is called on `Console`.
  - *Responsibility:* produce this project's one observable result by
    calling `Console.WriteLine`, exactly once per call.
  - *Depends on:* an already-constructed `Service` object to be called on;
    `Console`, to actually perform the printing.
  - *Connects to:* called by `Program.cs`'s top-level statements
    immediately after `new Service()` constructs the object it's called
    on; it calls `Console.WriteLine` in turn.
  - *Shape:* an internal implementation detail of `Service` —
    `Program.cs` doesn't need to know *how* `Run()` produces its output,
    only that calling it does.

- **`Service()` — the compiler-supplied default constructor**
  - *What it is:* the specific constructor that actually runs every time
    `new Service()` executes, even though `Service.cs` never declares one.
  - *Implementation:* not written anywhere in this project's own source.
    Per the C# language specification, a class with no declared instance
    constructor is automatically given one, equivalent to a hand-written
    `public Service() { }` — a real, callable member the compiler adds to
    the compiled class, not merely a fallback behavior invoked only when
    nothing else applies.
  - *Its use:* this is what actually ran, silently, the instant
    `new Service()` executed in this lesson's third unit — before `Run()`
    was ever reached.
  - *Type:* an instance constructor — a special method sharing its
    class's exact name, with no return type at all, not even `void`.
  - *Responsibility:* right now, nothing beyond letting the object come
    into existence at all — there is no field to initialize yet, so this
    constructor's entire current job is "exist, so `new` has something to
    call."
  - *Depends on:* nothing — a parameterless constructor needs no
    arguments, which is exactly why the compiler can supply one
    automatically with no guesswork about what it should do.
  - *Connects to:* called directly by the `new Service()` expression in
    `Program.cs`, before control ever reaches `.Run()` on the very next
    line.
  - *Shape:* an invisible-but-real piece of the class's compiled shape —
    present in the compiled `Service.dll` even though absent from
    `Service.cs`'s own source text.

## Concept Unit: The Class — A Blueprint, Not a Running Thing

### The Problem

`code/01-csharp/Service/Program.cs` currently contains exactly one
top-level statement: `Console.WriteLine("Service is running.");`. This
curriculum's own plan says `Service` is going to grow fields, encapsulated
state, a second collaborating class, an injected dependency, an interface
with two implementations, a generic operation, failure handling, and
asynchronous behavior — ten more lessons of real growth. A bare top-level
statement has no name, no boundary, and nothing to attach a second piece of
related behavior to. Where is any of that supposed to live?

> **Stop and think, before reading on:** you've already written a Python
> class — something with a name, containing methods, that you create
> instances of with `ClassName()`. Given that C# is the language whose
> `.csproj` you already inspected in Lesson 1.1 (an XML file with a `Sdk`
> attribute, `PropertyGroup` elements, and so on), do you expect declaring
> a class to need something equally ceremonial, or do you expect it to
> look close to what you already know from Python, just with different
> keywords? What do you think the actual C# keyword for "this is a class"
> is likely to be?

- **Location:** a new file, sitting directly alongside `Program.cs` and

### Introduce the Concept in Isolation

A throwaway project, `ScratchA`, was scaffolded fresh in this session's own
scratch directory — never inside `code/01-csharp/`:

```

```

```csharp

{
}
```

Run for real:

```

```

Real output:

```

```

This is exactly what `public class Service { }` above is doing, isolated:
an empty class was added to a working program, and the program's output
didn't change at all. This proves the concept directly — **declaring a
class** doesn't execute anything by itself. A class is a blueprint: a
named description of what instances of it *could* contain and do, sitting

and neither one has run a single line of its own code yet.

`ScratchA` is kept alive rather than deleted immediately — the Verification
Rule's batching guidance is to run related throwaway checks together
rather than one execution per concept — and will be reused for the next
three concept units in this lesson before it's finally discarded.

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`public`** — the **access modifier** on this class, stating that any
  code able to see this project at all is allowed to use `Service`.
  Nothing has actually depended on that visibility yet — `Program.cs`
  will, starting in the third unit of this lesson — but the declaration

- **`class`** — the keyword declaring that what follows is a **class**: a

- **`{` ... `}`** — the **block** delimiting this class's body. Right now
  the body is empty — nothing sits between the braces — which is exactly
  why running the program does nothing differently: there is, quite
  literally, nothing inside this blueprint yet for anything to do.

### CS Lens

A class is a concrete example of **abstraction over structure**: it names
a *category* of thing (`Service`) separately from any particular thing
that category describes, the same way a blueprint for a house names what
a house *of that design* would contain without being a house itself:

```
Also recognized in: a database table's schema (describes what any row
could contain, without being a row itself), a factory's assembly-line
specification, a cookie cutter versus the cookies it produces, a
species classification versus any one living member of that species
```

Every one of these separates "the description of a kind of thing" from
"an actual thing of that kind" — a class is C#'s version of that same
split.

### SE Lens

The alternative not chosen here is what Lesson 1.1's entire program
already was: everything expressed as loose top-level statements with no
named grouping at all. That alternative works for exactly one thing
happening once, which is all Lesson 1.1 needed. It stops working the
moment a project needs more than one related piece of behavior that
belongs together conceptually — nothing about bare statements says "these
five lines are all part of the same idea" the way wrapping them in one
named class does. The real cost paid here, visible in this very unit: an
empty class is genuinely more ceremony than an empty file needed to
contain zero behavior — three lines just to say "nothing is here yet."
That cost is worth it the moment a second, related piece of behavior needs
to join the first inside the same named thing — which is exactly what the
next unit does.

## Concept Unit: The Method — Behavior That Belongs to the Blueprint

### The Problem

`Service` now exists, but it's an empty blueprint — it describes nothing
and does nothing. `Program.cs` still holds the project's entire real
behavior, unchanged: `Console.WriteLine("Service is running.");`, sitting
outside `Service` entirely. If that line is ever going to be something
`Service` itself can do, rather than something `Program.cs` does *to* it
from outside, it has to move somewhere. Where, specifically, inside an
empty pair of braces, does a runnable piece of behavior actually go?

> **Stop and think, before reading on:** you already know a Python method
> is defined with `def`, indented inside a class body, and called as
> `instance.method_name()`. Given that C#'s class declaration you just saw
> uses `{` `}` instead of Python's indentation to mark what's inside a
> class, what do you predict a method *declaration* looks like sitting
> inside those braces — and given `Console.WriteLine` already showed you
> what a method *call* looks like, what do you think has to be different
> about writing one instead of just calling one?

### The Real Project Change

- **Reference Source:** no reference counterpart — from-scratch addition.
- **Files affected:** modified — `code/01-csharp/Service/Service.cs`.
- **Change type:** add (a method added inside the previously empty class

- **Location:** inside `Service`'s block, between the `{` and `}` the
  previous unit left empty.
- **Dependencies:** the empty `Service` class from the previous unit;

### Mechanical Walkthrough

Enumerating every distinct new syntactic element from the New Code block,
in order:

- **`public`** — the **access modifier** on this method, reappearing from
  the previous unit's use on the class itself. Here it states that any

- **`void`** — the method's declared return type, stating plainly that

- **`Run`** — the method's own name, chosen for what this project needs

- **`()`** — the **call syntax** parentheses, reappearing from Lesson 1.1,
  here marking a *declaration's* empty parameter list rather than a call's

  needs any information handed in from outside; Lesson 1.6 is where this
  project's own constructor first needs one.
- **`{` ... `}` (method body)** — a second **block**, this time delimiting
  `Run`'s own body rather than the class's — the same braces-as-boundary
  idea from the previous unit, now nested one level deeper: a method
  block sitting inside a class block.
- **`Console.WriteLine("Service is running.");`** — the exact statement

`Greeter constructed.` appears *before* `Hello from inside a method.`,
even though the source code only calls `greeter.SayHello()` explicitly —
nothing anywhere calls a method named `Greeter` by name. The real output's

1. `Console.WriteLine("Hello, World!");` — the file's own first top-level

   this is why `Hello, World!` is the first line of the real output above.
2. `new Greeter()` (evaluated while running `var greeter = new
   Greeter();`) — this is the exact moment the constructor written just

   `Greeter` anywhere; `new` itself is what triggers it, which is why
   `Greeter constructed.` appears in the real output despite no visible
   call to produce it.
3. `greeter.SayHello();` — only runs after step 2 has already finished and
   handed back a fully constructed object for `greeter` to hold; this is
   why `Hello from inside a method.` is the real output's last line, never
   first or interleaved with the other two.

method that runs automatically at the exact moment `new Greeter()`
executes, with no explicit call anywhere telling it to run, strictly
before any other method can be reached on that same object.

Now look back at every earlier run in this lesson's own units. `new

have produced a usable object in the first place. This is the **default
constructor**: the C# compiler automatically supplies a parameterless
constructor, equivalent to an empty `public Greeter() { }`, for any class

### CS Lens

A constructor is a real instance of **guaranteed initialization** —
ensuring some setup step cannot be skipped, forgotten, or reordered by
whoever creates an object:

```
Also recognized in: Python's __init__, Java's and C++'s same-named
constructors, a factory's mandatory quality-check step before a
product ships, a database's NOT NULL column default applying even
when an insert statement never mentions that column
```

Every one of these guarantees some setup happens whether or not the
caller remembers to ask for it — the constructor's whole reason for
existing is removing that reliance on memory.

### SE Lens

The alternative not chosen — for any class, in any language with
constructors — would be requiring every caller to remember to call some
separate `initialize()`-style method by hand after creating an object,
with nothing enforcing that it's ever actually called. That alternative is
a real, common bug source: an object left half set-up because some caller,
somewhere, forgot the second step. A constructor removes that risk
entirely by making initialization *part of* creation itself — `new` and
"run the constructor" are not two separate actions a caller can pull apart
or skip one half of. The cost paid here is narrower than it looks: right
now, `Service`'s compiler-supplied constructor does nothing beyond letting
the object exist, because there's no state yet to set up. That changes the
moment Lesson 1.3 gives `Service` its first field — the exact moment this
project needs to start writing an explicit constructor of its own, instead
of continuing to rely on the compiler's empty one.
