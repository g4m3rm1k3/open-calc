# Lesson 1.7: Naming What Several Classes Can Do — The Dependency Needs Multiple Implementations

**What you will build.** `Service` currently depends on one concrete class,
`Logger`, and nothing else could ever take its place without changing
`Service`'s own constructor signature. This lesson extracts an `ILogger`
**interface** — a signature with no body, naming only *that* something can
`Log(string message)`, never *how* — renames `Logger` to `ConsoleLogger`
(an **implementation** of that interface), and changes `Service`'s
constructor to accept `ILogger` instead of the concrete class. Then a
second, genuinely different implementation, `LoudLogger`, is added and
proven to satisfy the exact same interface while behaving completely
differently. `Service` itself never has to know which one it's holding —
it only ever calls `logger.Log(...)`, and whichever concrete object was
actually passed in decides what really happens. That — the same call,
genuinely different real behavior, depending only on which concrete
object stands behind an interface-typed reference — is **polymorphism**,
proven with a real, running comparison rather than just asserted.

**What you need to know first.** From **Lesson 1.6 — Who Creates the
Dependency**: the real project at `code/01-csharp/Service/`, `Service`'s
hand-written constructor, `dependency`, `constructor injection`, and
`this`. From **Lesson 1.5**: `composition`, `"has-a"`, `Logger`'s own
`Log(string message)` method, `parameter`/`argument`. From **Lesson
1.4**: `private`, `public`, `property`. From **Lesson 1.2**: `class`,
`object`, `instance`, `method`, `constructor`, `new`, `var`, member
access (`.`). From **Lesson 1.1**: `Console`, `Console.WriteLine`, string
literals. From the curriculum's own stated assumptions: enough Python
experience to know that Python doesn't require declaring an interface at
all before writing a class with a given method — this lesson leans on
that contrast to explain *why* C# requires the explicit declaration this
lesson introduces.

## Terms used in this lesson

- **interface** — a named declaration listing one or more method
  signatures — a name, parameter types, and a return type — with no
  bodies at all, describing *what* something can do without saying
  *how*. This is a **hard concept**, so it gets full CS Lens treatment
  below. It exists so code can depend on "anything that can `Log` a
  message," rather than on one specific class that happens to do so —
  `Service`'s constructor, before this lesson, could only ever accept the
  one concrete class `Logger`; after this lesson, it can accept *any*
  class that satisfies `ILogger`, with no further changes to `Service`'s
  own source ever required again.
- **implementation** — a class that provides real, working bodies for
  every method an interface declares, and is said to *implement* that
  interface. `ConsoleLogger` and `LoudLogger` are both implementations of
  `ILogger` this lesson — two separate classes, each providing a
  genuinely different real body for the identical `Log(string message)`
  signature.
- **polymorphism** — literally "many forms": the same method call,
  written once, producing genuinely different real behavior depending on
  which concrete object actually receives it at runtime. This is a
  **hard concept**, so it gets full CS Lens treatment below. It's what
  makes an interface useful in practice — not just that multiple classes
  *can* implement the same signature, but that code written against the
  interface never needs to know or care which one it's actually talking
  to.
- **interface implementation syntax (`: ILogger`)** — the colon after a
  class's own name in its declaration, followed by an interface name,
  stating that this class provides real bodies for everything that
  interface declares. `public class ConsoleLogger : ILogger` reads as
  "`ConsoleLogger` *is an* `ILogger`" — a genuine **"is-a" relationship**
  (reappearing from Lesson 1.5, where it was only named in passing to
  contrast with "has-a"; this is its first real use in this project's
  own code).
- **`I` prefix convention** — a naming convention, not a compiler rule,
  used throughout this project's code and extremely common in real C#:
  an interface's name starts with a capital `I`, distinguishing it at a
  glance from an ordinary class — `ILogger` versus `ConsoleLogger`.
  Nothing enforces this; it exists purely so a reader can tell interfaces
  and classes apart by name alone.
- **dependency, constructor injection, `this`** — reappearing from Lesson
  1.6, unchanged in meaning: `Service` still receives its logging
  dependency through its constructor; `this.logger = logger;` still
  disambiguates the parameter from the field. What changed this lesson is
  only the *type* of that dependency — `ILogger` instead of the concrete
  `Logger` — not the injection mechanism itself.
- **field, private, class, block (`{ }`), `void`, call syntax (`( )`),
  `var`, `new`, member access (`.`), assignment operator (`=`), string
  literal, semicolon (`;`), `int`, `public`, parameter, argument** — all
  reappearing from Lessons 1.1–1.6, unchanged in meaning, all still
  present in `Service.cs`, the interface and its implementations, and
  this lesson's isolated lab.

## Concept Unit: The Interface — Naming What Multiple Classes Can Do

### The Problem

`Service`'s constructor currently declares `public Service(Logger
logger)`. That signature only ever accepts the one, specific, concrete
class `Logger` — nothing else, no matter how similar, could ever be
passed in without `Service`'s own source code changing to accept it. If a
second, genuinely different way of logging needs to exist someday, is
`Service` really supposed to grow a second constructor, or an `if`
statement choosing between them, every single time a new option appears?

> **Stop and think, before reading on:** in Python, you never declare
> ahead of time that a class provides some particular set of methods —
> any object with a `.log(message)` method just works anywhere a
> `.log(message)` call is made, with nothing checked before the program
> runs. Given that C# is strict about types everywhere else in this
> project — every field, every parameter, every return type has always
> been spelled out explicitly — what do you predict C# requires before a
> parameter can accept "anything with a `Log(string)` method," rather
> than one single named class?

### Introduce the Concept in Isolation

A throwaway project, `ScratchF`, was scaffolded fresh in this session's own
scratch directory. An interface, `IGreeter`, was declared with one method
signature, and one class, `QuietGreeter`, was written to implement it:

```csharp
IGreeter greeter1 = new QuietGreeter();
greeter1.Greet("Ada");

public interface IGreeter
{
    void Greet(string name);
}

public class QuietGreeter : IGreeter
{
    public void Greet(string name)
    {
        Console.WriteLine(name);
    }
}
```

Run for real:

```
dotnet run
```

Real output:

```
Ada
```

This is exactly what the real `ILogger`/`ConsoleLogger` pair above is
doing, isolated: a variable, `greeter1`, is declared with the *interface*
as its type, `IGreeter`, not the concrete class — yet it holds a real
`QuietGreeter` object, and calling `.Greet("Ada")` through it runs
`QuietGreeter`'s own real code. This proves the concept named in this
lesson's Header: an **interface** describes *what* something can do —
here, "accept a `string name` and `Greet` with it" — with no body of its
own at all; an **implementation** — `QuietGreeter` — is what actually
supplies that body. `IGreeter greeter1 = new QuietGreeter();` compiles
specifically because `QuietGreeter` provides a real method matching
`IGreeter`'s own declared signature exactly.

`ScratchF` is kept alive rather than deleted immediately — the next
concept unit in this lesson still needs it.

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`public`** — the access modifier, reappearing from Lesson 1.2, here
  applied to an interface declaration for the first time.
- **`interface`** — the keyword declaring that what follows is an
  **interface** rather than a `class`: a contract with no bodies, not a
  blueprint for a runnable object.
- **`ILogger`** — the interface's own name, following the **`I` prefix
  convention** this lesson's Header names.
- **`{` ... `}`** — a **block**, reappearing from Lesson 1.2, this time
  containing an interface's member declarations rather than a class's
  real, runnable members.
- **`void Log(string message);`** — the interface's one member: `void`
  (reappearing from Lesson 1.2), `Log` (the method's name), `(string
  message)` (a **parameter**, reappearing from Lesson 1.5), and a
  **semicolon** ending the declaration directly — no `{ }` body at all,
  which is exactly what marks this as an interface member rather than a
  real method.

### CS Lens

An interface is a concrete example of **programming to an abstraction** —
depending on *what* something can do rather than on any one specific class
that happens to do it:

```
Also recognized in: a wall power outlet accepting any appliance with a
matching plug, regardless of what's actually inside the appliance, a
USB port accepting any device that speaks the USB protocol, a shipping
container standard letting any compliant container be loaded onto any
compliant ship or truck, a job posting describing required skills
rather than naming one specific acceptable candidate
```

Every one of these separates "the shape something must have" from "which
specific thing actually has that shape" — letting the shape stay fixed
while what satisfies it changes freely.

### SE Lens

The alternative not chosen here is exactly what Lesson 1.6 already left
in place: `Service` depending directly on the concrete `Logger` class.
That alternative is simpler to write — no extra file, no extra
declaration — and was entirely appropriate right up until a second,
genuinely different logging behavior became worth having. It stops being
appropriate the moment that happens: without an interface, adding a second
logging option would mean either modifying `Service`'s own constructor to
accept a second type, or writing conditional logic inside `Service`
choosing between concrete classes by hand — both of which make `Service`
grow every time logging grows, even though counting and reporting are
supposed to be `Service`'s only two concerns (Lesson 1.5's own point).
The real cost paid here: one extra file, and one extra level of
indirection — `logger.Log(...)` now resolves to *whichever* class
actually implements `ILogger`, decided at runtime, rather than being
knowable just by reading `Service`'s own source text alone.

## Concept Unit: Polymorphism — One Interface, Two Real Behaviors

### The Problem

`ILogger` currently has exactly one implementation, `ConsoleLogger`.
Nothing yet has actually demonstrated that a *second* class could satisfy
the same interface and behave differently — for all this project's own
code has shown so far, `ILogger` could just be an unnecessary layer of
naming around a single class that was never really going to have any
alternative.

> **Stop and think, before reading on:** `ILogger` declares exactly one
> method, `Log(string message)`, with no body. Given that any class at
> all can implement it as long as it provides a real body matching that
> exact signature, what do you predict happens if two *completely
> different* method bodies are written for two different classes, both
> declared `: ILogger`, and both are called the exact same way — through
> a variable or parameter typed as `ILogger`, not as either concrete
> class by name? Will the interface somehow force them to behave the
> same, or does each class remain free to do whatever it wants inside its
> own `Log` method?

### CS Lens

Polymorphism is the practical payoff of programming to an interface —
literally, "many forms," the same call site producing different real
behavior depending on what's actually behind it:

```
Also recognized in: pressing a car's accelerator pedal producing
different acceleration depending on the engine actually installed, a
universal remote's "power" button working identically across many
different television brands, calling .draw() on a shape in a drawing
program producing a circle, square, or triangle depending on which
shape object is actually selected, ordering "the daily special" at a
restaurant chain and receiving a genuinely different dish at each
location
```

Every one of these keeps the *interaction* fixed — the same button, the
same call, the same request — while the *actual behavior* varies
entirely based on what's really on the other end.

### SE Lens

The alternative not chosen here would be giving `LoudLogger` some
different method name entirely — `LogLoudly`, say — rather than
implementing `ILogger`'s exact `Log` signature. That alternative would
still let `LoudLogger` exist and work when called directly, exactly as
this unit's own `Program.cs` demonstration does — but it would make
`LoudLogger` *unusable* anywhere code expects an `ILogger`, including
`Service`'s own constructor, since `Service` only ever calls `.Log(...)`,
never `.LogLoudly(...)`. Matching the interface's exact signature is what
makes `LoudLogger` a genuine, interchangeable alternative to
`ConsoleLogger` rather than merely a similarly-named class that happens
to also print things. The real cost of this discipline: every
implementation is bound to the interface's exact signature forever, once
other code depends on that interface — changing `ILogger.Log`'s own
signature later would require updating every implementation in lockstep,
a real, recurring maintenance cost this project doesn't pay today only
because `ILogger` has exactly one method and no reason yet to change it.
