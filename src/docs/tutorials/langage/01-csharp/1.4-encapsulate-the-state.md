# Lesson 1.4: Who Is Allowed to Change This — Encapsulate the State

**What you will build.** `Service.RunCount`, which Lesson 1.3 left as a
plain `public` field, becomes a private field named `runCount` plus a
public property named `RunCount` that only allows reading it from outside
— never writing it directly. `Program.cs` doesn't change at all: it still
reads `service.RunCount` with the exact same syntax it always has. What
changes is that `service.RunCount = 9000;`, which Lesson 1.3 already
warned would silently corrupt the count, now fails to even *compile*. The
transferable problem underneath this one field is bigger than `RunCount`
itself: any object whose data can be reached and rewritten by anything
that can see it has no way to guarantee its own data stays correct — the
object itself has no say in the matter. **Encapsulation** is the
principle of bundling data together with the only code allowed to change
it, and deliberately shutting every other path off. **Access modifiers**
are how C# actually enforces that shutting-off, as a real, compiler-
checked wall, not a naming convention anyone could ignore. And a
**property** is the specific tool that lets an object expose *some*
controlled access — here, read-only — without exposing unrestricted
access to the field underneath it.

**What you need to know first.** From **Lesson 1.3 — What an Object
Remembers**: the real project at `code/01-csharp/Service/`, its `Service`
class, the `public int RunCount;` field it currently has and the exact
problem this lesson exists to fix (already named there: "nothing stops
[external code from setting `RunCount` directly], silently corrupting the
count"), `Run()`'s `runCount = runCount + 1;` increment logic, `int`, and
the arithmetic `+` operator. From **Lesson 1.2**: `class`, `object`,
`instance`, `method`, `constructor`, `new`, `var`, member access (`.`),
the assignment operator (`=`), and the access modifier `public`. From
**Lesson 1.1**: `Console`, `Console.WriteLine`, string literals,
semicolons, and the `dotnet run`/`dotnet build` cycle. From the
curriculum's own stated assumptions: enough Python experience to know that
a leading underscore (`self._value`) is only ever a *naming convention*
signaling "please don't touch this from outside" — Python's own
interpreter never actually stops anyone from touching it anyway. This
lesson leans on that specific fact to contrast it with what C# does
differently.

## Terms used in this lesson

- **access modifier `private`** — a keyword restricting a member's
  visibility to only the class it's declared inside — not even other code
  in the same project can see it, let alone code outside the project
  entirely. Contrasts directly with `public` (reappearing from Lesson
  1.2), which allows any code that can see the type at all to see the
  member too. It exists so a class can genuinely keep some of its own data
  or logic to itself, with that restriction actually enforced by the
  compiler rather than left as a hope.
- **encapsulation** — the design principle this whole lesson is about:
  bundling a piece of data together with the only code that's allowed to
  read or change it, and deliberately restricting every other path to that
  data. It exists because an object that anyone can freely rewrite from
  outside has no way to guarantee its own data ever stays correct — the
  object itself never gets a say in what happens to it.
- **property** — a class member that looks, from outside, exactly like a
  field — read with the same `.` syntax a field already uses — but is
  actually backed by real code that runs every time it's read (and,
  optionally, every time it's written) rather than being a plain storage
  location itself. It exists to let a class expose *controlled* access to
  its data — here, read-only — without forcing a caller to change how it
  reads that data at all.
- **get accessor (`get`)** — the specific block inside a property
  declaration that runs whenever that property is read from anywhere. It
  exists because a property, unlike a plain field, isn't itself a storage
  location — something has to actually run to decide what value to hand
  back, even when, as in this lesson, that "something" is as simple as
  returning a backing field's current value unchanged.
- **backing field** — the private field a property's own accessors
  actually read from and write to; the real storage location the property
  gives controlled access to. `runCount`, lowercase, is this lesson's own
  backing field for the public `RunCount` property.
- **compile-time error** — an error the compiler itself detects and
  refuses to build past, before the program is ever executed. It exists
  because some mistakes — like code trying to reach a `private` member
  from outside the class that owns it — are detectable just by reading
  the source text, with no need to ever actually run the program to
  discover them; catching them at this stage means they can never reach a
  user running the finished program at all. Contrasts with a *runtime*
  error — a mistake only discovered while the program is actually
  executing — which this curriculum doesn't cover until Lesson 1.10.
- **compiler warning** — a compiler diagnostic that, unlike an error, does
  *not* stop the build — the program still compiles and runs — but flags
  something the compiler considers suspicious enough to mention anyway,
  such as a field that's declared but never actually used for anything.
- **naming convention (`PascalCase` vs. `camelCase`)** — a stylistic, not
  compiler-enforced, choice this lesson's own code follows: `RunCount`
  (capital `R`) for the `public` property anything outside can see, and
  `runCount` (lowercase `r`) for the `private` field only `Service` itself
  can see. Nothing in the compiler requires this particular casing split;
  it exists purely so a reader can tell, at a glance, whether a name is
  meant to be seen from outside a class or not.
- **field, object state, instance member** — reappearing from Lesson 1.3:
  `runCount` is still a field — a variable declared inside a class's body,
  not any method — still holds this specific `Service` object's own
  state, and is still an instance member, belonging to whichever object
  it's read or written on. Everything Lesson 1.3 proved about persistence
  and independence still applies to it unchanged; only who's *allowed* to
  reach it changed this lesson.
- **`int`, arithmetic addition operator (`+`), assignment operator (`=`)**
  — all reappearing from Lesson 1.3, still doing exactly what they did
  there: `runCount = runCount + 1;`, inside `Run()`, is the identical
  statement Lesson 1.3 wrote, only renamed.
- **member access (`.`)** — reappearing from Lesson 1.2: still the dot
  operator reaching into an object to name a specific member. This
  lesson's whole point rides on a subtlety about it worth stating plainly:
  `service.RunCount` looks *identical*, character for character, whether
  `RunCount` is a plain field (Lesson 1.3) or a property (this lesson) —
  the dot operator doesn't reveal which one it's reaching into at all.
- **`class`, block (`{ }`), `void`, call syntax (`( )`), `var`, `new`,
  string literal, semicolon (`;`)** — all reappearing from Lessons 1.1 and
  1.2, unchanged in meaning, all still present in `Service.cs` and this
  lesson's isolated lab.

  - *Connects to:* read by `Program.cs`'s own `Console.WriteLine(service

  - *Depends on:* nothing — still parameterless.
  - *Connects to:* still called directly by `new Service()` in
    `Program.cs`, before either call to `.Run()`.
  - *Shape:* still a real, compiled member absent from `Service.cs`'s own
    source text.

## Concept Unit: The Access Modifier `private` — A Real, Enforced Boundary

### The Problem

Lesson 1.3 already named this problem out loud without fixing it:
`Service.RunCount` is `public`, which means any code holding a `Service`
object can assign it directly — `service.RunCount = 9000;` compiles and
runs today, silently replacing a real, accumulated count with a number
that has nothing to do with how many times `Run()` actually executed.
Nothing about `Run()`'s own logic is involved at all when that happens.

A quick, concrete look at exactly this shape of problem, on a throwaway
stand-in, makes it impossible to wave away as theoretical. A `Meter` class
with a public `Reading` field:

```csharp
var meter = new Meter();
meter.Reading = 100;
meter.Reading = -5;
Console.WriteLine(meter.Reading);

public class Meter
{
    public int Reading;
}
```

Run for real:

```
dotnet run
```

Real output:

```
-5
```

Nothing about `Meter` stopped this. `Reading` ends at `-5` — a value that
makes no sense for whatever a "meter reading" is supposed to represent —
because a `public` field can be set to literally anything, by anything
that can see it, with the class itself having no say in the matter at
all. `Service.RunCount`, sitting `public` in the real project right now,
has exactly this same exposure.

> **Stop and think, before reading on:** you already know that Python's
> leading-underscore convention (`self._value`) is *only* a convention —
> nothing in Python's own interpreter stops `obj._value = 9000` from
> working perfectly. Given that every access modifier you've seen in C# so
> far (`public`, on every class, method, and field in this project) has
> been written out explicitly, with nothing left to a reader's inference —
> do you predict C# treats a restricted-access declaration the same
> hands-off way Python does, or do you think the compiler might actually
> *enforce* it as a real rule, refusing to build code that violates it?

- **Reference Source:** no reference counterpart — from-scratch addition,
  same as every unit in this project so far.
- **Files affected:** modified — `code/01-csharp/Service/Service.cs`.
- **Change type:** replace (`public` becomes `private` on one line;
  nothing else in the file changes yet).
- **Location:** `RunCount`'s own field declaration, the first line inside
  `Service`'s block.
- **Dependencies:** the `RunCount` field from Lesson 1.3.

### The New Code


### Mechanical Walkthrough

Enumerating the one changed token in the New Code block above:

- **`private`** — the access modifier replacing `public` on this exact
  declaration. Unlike `public`, which lets any code that can see `Service`
  at all also see `RunCount`, `private` restricts visibility to code
  written *inside* `Service`'s own body — `Run()` qualifies; `Program.cs`,
  sitting outside the class entirely, does not, no matter that it's still
  part of the same project and even the same file's neighboring type.

### CS Lens

`private` is this lesson's concrete mechanism for **encapsulation** — the
design principle of bundling data together with the only code allowed to
touch it, and shutting every other path off, enforced here by the
compiler itself rather than left to hope or convention:

```
Also recognized in: a bank vault whose contents only bank employees
with the right key can reach (not just a sign asking customers not to
enter), a sealed medical record only clinical staff can open, a car's
locked engine bay versus its unlocked cabin, a factory machine's
internal wiring sealed behind a panel an operator is never expected to
open
```

Every one of these draws a real, enforced line between "freely reachable"
and "reachable only by the specific party responsible for it" — not a
polite request, an actual barrier.

### SE Lens

The alternative not chosen here is exactly what Lesson 1.3 already left in
place: a `public` field, with any restriction on how it's used left
entirely to a comment, a naming convention, or a teammate simply
remembering not to touch it — Python's own leading-underscore convention
is precisely this alternative, made explicit. That alternative costs
nothing to write and works fine as long as everyone touching the code
already knows and respects the informal rule. It fails the moment that
stops being true — a rushed change, a new contributor who never read the
comment, or, as this unit's own `Meter` demonstration showed, code that
compiles and runs while quietly doing exactly the wrong thing, with
nothing anywhere flagging that anything went wrong at all. `private`
converts "please don't" into "cannot, and the compiler will tell you
exactly where you tried." The real cost, paid immediately and visible in
this very unit: making `RunCount` `private` broke `Program.cs`'s own
`Console.WriteLine(service.RunCount);` line entirely — Lesson 1.3's
already-working project no longer builds at all, on purpose, until the
next unit gives external code a different, controlled way back in.

## Concept Unit: The Property — Restoring Read Access Without Restoring Write Access

### The Problem

`Service.RunCount` is now unreachable from `Program.cs` entirely — even
the read that was always meant to work has stopped compiling. Simply
making it `public` again would undo everything the previous unit just
proved. Is there a third option — something that looks like a field from
outside, so `Program.cs` doesn't have to change at all, but only ever lets
outside code *read* it, never write it?

> **Stop and think, before reading on:** you've now seen exactly two
> access modifiers, `public` (everything open) and `private` (everything
> closed) — both all-or-nothing about *every* kind of access at once.
> Given that what's actually needed here is narrower — allow reading,
> block writing — do you predict C# has some in-between keyword covering
> exactly that one combination, or do you think the real answer might be
> a completely different kind of class member altogether, one that only
> *looks* like a field from the outside but is secretly built from
> something else?

### The Real Project Change

- **Reference Source:** no reference counterpart — from-scratch addition.
- **Files affected:** modified — `code/01-csharp/Service/Service.cs`.
- **Change type:** replace (the private field is renamed and a property is
  added; `Run()`'s own reference to it is updated to match).
- **Location:** `Service`'s block: the field declaration from the
  previous unit, plus one new member added directly after it, plus the one
  line inside `Run()` that names this field.
- **Dependencies:** the private field from the previous unit.

### Introduce the Concept in Isolation

Still inside `ScratchC`, `Meter` gets the identical treatment: its field
renamed and made the backing store for a new, read-only property:

```csharp
var meter = new Meter();
Console.WriteLine(meter.Reading);

public class Meter
{
    private int reading;

    public int Reading
    {
        get { return reading; }
    }
}
```

Run for real:

```
dotnet run
```

Real output:

```
Program.cs(6,17): warning CS0649: Field 'Meter.reading' is never assigned to, and will always have its default value 0
0
```

This is exactly what the real `Service.cs` change above restores: reading
`meter.Reading` compiles and runs again, with no change at all to how the
caller reads it — the same `.` syntax as a plain field, now actually
running the `get` accessor's own code underneath. This is called a
**property**, proven rather than just defined: `Reading` isn't storage at
all anymore; it's a real accessor that happens to simply hand back
`reading`'s value, unchanged, whenever it's read. The real output is `0`
because nothing anywhere ever assigns `reading` in this throwaway lab —
which is also exactly why the compiler's own `CS0649` **compiler warning**
appears: a genuine, honest observation that this particular field's value
can never be anything but its Lesson 1.3-established **default field
value**, `0`, in this lab specifically. That warning doesn't stop the
build; `0` still prints right after it.

Then, exactly the corruption attempt this whole lesson opened with was
tried again — against the property this time, not the field:

```csharp
var meter = new Meter();

Console.WriteLine(meter.Reading);
```

Run for real:

```
dotnet run
```

Real output:

```
Program.cs(2,1): error CS0200: Property or indexer 'Meter.Reading' cannot be assigned to -- it is read only
Program.cs(7,17): warning CS0649: Field 'Meter.reading' is never assigned to, and will always have its default value 0

The build failed. Fix the build errors and run again.
```

A genuinely different real error than the previous unit's `CS0122` —
`CS0200` this time, "read only," not "inaccessible." This is the crux of
what **encapsulation** actually delivers here: `Reading` is fully visible
and readable from outside `Meter` — nothing about it is hidden, unlike the
previous unit's fully `private` field — and still, the compiler refuses to
let outside code write to it, for an entirely different, more specific
reason than a `private` member ever gives. Read access, restored;
write access, permanently blocked; `Program.cs`'s own legitimate read

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`private`** — the access modifier, reappearing from the previous
  unit, still restricting visibility to inside `Service` alone — now
  applied to the renamed backing field rather than the originally-named
  one.
- **`int`** — reappearing from Lesson 1.3, the field's declared type,
  unchanged.
- **`runCount`** — the field's new name, lowercase, following the
  **naming convention** this lesson's Header names: a `private` member
  spelled starting with a lowercase letter, distinguishing it at a glance
  from the `public` property below it.
- **`;`** — the semicolon ending the field declaration.
- **`public`** — the access modifier, reappearing, now applied to the new
  property: any code that can see a `Service` object can read `RunCount`.
- **`int`** — the property's own declared type — a property, like a
  field, states what type reading it produces; here, the same `int` the
  backing field holds.
- **`RunCount`** — the property's name, capitalized, per the same naming
  convention, and deliberately matching the old field's original name so
  that `service.RunCount` in `Program.cs` keeps meaning exactly what it
  always meant from the outside.
- **`{` ... `}` (the property's own block)** — a **block**, reappearing
  from Lesson 1.2, this time delimiting the property's own body — the set
  of accessors it declares — rather than a class's or method's body.
- **`get`** — the **get accessor** keyword, opening the specific block
  that runs whenever `RunCount` is read from anywhere. This property
  declares only this one accessor — no `set` accessor exists anywhere in
  this declaration, which is exactly why writing to it fails to compile,
  as the isolated lab's own `CS0200` error already proved.
- **`{ return runCount; }`** — the `get` accessor's own body: a single
  statement handing back the private field's current value. This is the
  entire logic this property runs on every read — simple here, but real,
  executable code nonetheless, not a passthrough the language provides for
  free.
- **`runCount = runCount + 1;`** (inside `Run()`) — the assignment and
  arithmetic addition operators, both reappearing from Lesson 1.3,
  unchanged in meaning, now targeting the renamed field. This line still
  compiles without any complaint about `private`, because it sits *inside*
  `Service`'s own body, exactly where `private` grants full access.

### CS Lens

A property is a concrete example of the general idea that **an interface
can hide its implementation** — from outside, `service.RunCount` gives no
indication whatsoever whether it's reaching a plain field or running real
code:

```
Also recognized in: a car's speedometer needle giving no hint whether
it's driven by a mechanical cable or an electronic sensor, a thermostat
display reading the same whether it's wired to an old mercury tube or a
digital chip, a vending machine's coin slot working identically whether
the machine validates coins mechanically or with a coin-recognition
circuit, a getter method in Java hiding whatever computation actually
produces its return value
```

Every one of these lets whatever's on the other side of an interaction
change completely without anyone relying on that interaction ever needing
to know or care.

### SE Lens

The alternative not chosen here is the one the previous unit's own ending
left open: staying fully `private`, with no property at all, and simply
accepting that `Program.cs` can no longer read `RunCount` either. That
alternative is more restrictive than this project actually needs — nothing
about this lesson's problem required blocking *reads*, only writes — and
would force `Program.cs` (or, worse, every piece of code anywhere that
legitimately just wants to know the count) to find some other, likely
messier way to learn it. The real cost paid here, worth stating honestly:
this property is more verbose than the field it replaces — five lines
where one used to be — for behavior that, right now, does nothing beyond
returning a value unchanged. Real, idiomatic C# usually shortens exactly
this shape using an **auto-implemented property**
(`public int RunCount { get; private set; }`), letting the compiler
generate the backing field itself rather than one being hand-written the
way `runCount` is here. This lesson deliberately wrote the backing field
by hand instead, so that the get accessor's own real, visible body — the
first time this curriculum has shown one — was fully inspectable rather
than resting on a hidden, compiler-generated field this lesson would then
have to separately prove exists, the same way Lesson 1.2 had to prove the
default constructor exists. The shorter, idiomatic form remains available
to reach for once this one is fully understood.
