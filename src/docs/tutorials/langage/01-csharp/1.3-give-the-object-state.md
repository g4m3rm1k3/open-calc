# Lesson 1.3: What an Object Remembers — Give the Object State

**What you will build.** `Service` gains its first real piece of memory: a
`RunCount` field that counts how many times `Run()` has actually been
called. `Program.cs` calls `Run()` twice in a row, then reads
`service.RunCount` directly, printing `2` — proof the object actually
remembered something across two separate method calls, not just within
one. The transferable problem underneath that single field is bigger than
counting: Lesson 1.2's `Service` could only ever do the same fixed thing,
every time, because nothing inside it could hold information from one
call to the next. A **field** is where that memory actually lives; the
values a field currently holds, at any given moment, are an object's
**object state**; and a field, like a method, is an **instance member** —
something belonging to a particular object, not to the class in general.
Those three ideas, plus a fourth one this lesson proves concretely rather
than just claims — that two different objects of the same class hold
*separate* copies of their own state — are this lesson's actual subject.

**What you need to know first.** From **Lesson 1.2 — Giving Behavior a
Home**: the real project at `code/01-csharp/Service/`, its `Service` class
and `Run()` method, `class`, `object`, `instance`, `method`, `constructor`,
`new`, `var`, local variables, reference types, member access (`.`), the
assignment operator (`=`), and the access modifier `public` — all reused
directly in this lesson's own code and, per the Repetition Rule below,
explained again here in full. From **Lesson 1.1**: `Console`,
`Console.WriteLine`, string literals, semicolons, and the `dotnet run`
cycle. From the curriculum's own stated assumptions: enough basic Python
object-oriented experience to have already written `self.count = 0` inside
an `__init__` and had it survive between calls to a later method — this
lesson leans on that prior experience only to contrast it with what C#
does differently (particularly around default values), never to assume
the C# syntax is already known.

## Terms used in this lesson

- **field** — a variable declared directly inside a class's own body, not
  inside any method, representing a piece of data every object made from
  that class will carry. It exists because a local variable declared
  inside `Run()` would be destroyed the instant `Run()` finishes — Lesson
  1.2's `var service` already showed that a local variable's lifetime is
  tied to the statement sequence it's declared in — and nothing about that
  changes for a variable declared inside a method body specifically. A
  field is declared at a different scope entirely — the class's own body —
  so that its lifetime is tied to the *object's* lifetime instead, letting
  it survive across as many separate method calls as that object exists
  for.
- **object state** — the actual, current values every one of an object's
  fields happens to hold at a given moment while a program runs. This is
  different from the class itself: `Service`'s declaration only says *that*
  a `RunCount` field exists and what type it is; a specific `Service`
  object's state is whatever number `RunCount` actually holds on that one
  object, right now, which changes over time as `Run()` is called.
- **instance member** — a general term covering anything declared inside a
  class that belongs to a particular object rather than to the class as a
  whole: an instance field (this lesson's own subject) or a non-`static`
  method (`Run()`, from Lesson 1.2) are both instance members. Contrasts
  with a `static` member, which belongs to the class itself with no object
  needed at all — `Console.WriteLine`, reappearing from Lesson 1.1, is a
  `static` method, never an instance member of anything this project owns.
- **default field value** — the specific, deterministic value a field
  automatically holds the moment its object is constructed, if nothing
  ever explicitly assigns it something else. It exists because an object
  has to start in *some* well-defined state the instant it's created —
  rather than leaving a freshly allocated field's contents as unpredictable
  leftover memory, the way some lower-level languages allow, C# guarantees
  a specific, fixed default per type: `0` for `int` (this lesson's own
  case), and, though not needed yet, `false` for `bool` and `null` for a
  reference type.
- **`int`** — one of C#'s built-in numeric types, representing a whole
  number with no fractional part. This is the first time this curriculum's
  C# code has actually declared something of this type; Lesson 1.1's
  Objects and methods section only ever mentioned `int` in passing, as one
  of `Console.WriteLine`'s other overloads, never as a type this project's
  own code used.
- **arithmetic addition operator (`+`)** — combines two numeric values into
  their sum, producing a new value without changing either one on its own.
  This is the first time this curriculum's C# code has used `+`
  arithmetically; the curriculum's own assumptions already take basic
  numeric addition for granted from Python, so what's actually new here is
  narrower: `RunCount + 1` by itself doesn't store anything anywhere — it
  only produces a value — which is exactly why the surrounding assignment
  operator, next, is still a separate, necessary part of the same
  statement.
- **assignment operator (`=`)** — reappearing from Lesson 1.2: the operator
  storing whatever its right-hand side produces into whatever is named on
  its left — a local variable there, a field here. `RunCount = RunCount +
  1;` only actually changes `RunCount` because of this operator; the `+`
  on its own, as just stated, produces a value and stops.
- **member access (`.`)** — reappearing from Lesson 1.2: the dot operator,
  reaching into an object to name one specific member it has. Lesson 1.2
  only ever reached in to call a method (`service.Run()`); this lesson
  reaches in to read a field's current value instead (`service.RunCount`)
  — the same operator, now used to read data rather than invoke behavior.
- **string literal** — reappearing from Lesson 1.1: text typed directly
  into source code, delimited by double quotes. `Service.Run()`'s own
  `Console.WriteLine("Service is running.");` still contains one, entirely
  unchanged since Lesson 1.2.
- **semicolon (`;`) as a statement terminator** — reappearing from Lesson
  1.1: the character ending each statement, still required because C#'s
  grammar doesn't treat a line break as the end of a statement.
- **`var`** — reappearing from Lesson 1.2: lets a local variable's type be
  inferred from whatever it's assigned, rather than written out by hand.
  Still used exactly as before, for `service` in `Program.cs`.
- **`new`** — reappearing from Lesson 1.2: the operator that creates an
  object from a class and runs that class's constructor. Still used
  exactly as before to create the one `Service` object this project has.
- **`class`, access modifier `public`, block (`{ }`), `void`, call syntax
  (`( )`)** — all reappearing from Lesson 1.2, unchanged in meaning, and
  all still present in `Service.cs`'s continued declaration and in this
  lesson's isolated lab.

  - *Type:* a class — unchanged in kind from Lesson 1.2.
  - *Responsibility:* running and printing this project's status line
    (unchanged from Lesson 1.2), plus, new this lesson, keeping track of
    how many times that's happened.
  - *Depends on:* nothing external yet — still no explicit constructor,
    and this lesson's field needs no constructor argument to start in a

  - *Connects to:* created and called by `Program.cs`; `Run()` in turn

  - *Its use:* every call to `Run()` now does two things instead of one:
    updates `RunCount`, then prints, in that order.
  - *Type:* an instance method — unchanged.
  - *Responsibility:* grew this lesson — no longer just "produce the
    status line," but "produce the status line *and* keep an accurate

  - *Depends on:* an already-constructed `Service` object to run against

  - *Connects to:* called by `Program.cs`, now twice in a row instead of

## Concept Unit: The Field — Where Object State Lives

### The Problem

Every call to `Service.Run()` right now does exactly the same thing,
because nothing inside `Service` remembers anything between one call and
the next. How many times has this service actually run since the program
started? Right now, nothing in this project can answer that — that
information doesn't exist anywhere yet, not even as a wrong answer.

> **Stop and think, before reading on:** in Python, you'd write
> `self.count = 0` inside `__init__`, then update `self.count` inside some
> later method, and it would still be there the next time that method
> runs. Given that Lesson 1.2 already showed you a *local* variable
> (`var service` in `Program.cs`) dies the moment its statement sequence
> finishes, and that `Run()`'s own body is exactly this kind of statement
> sequence — do you think declaring a variable *inside* `Run()` itself
> would solve this problem, or would it just recreate the exact same
> "gone when the method ends" issue `var service` already has? If not
> inside the method, where else, syntactically, is there even room to
> declare something in a class you've already seen has exactly two things
> inside its braces: nothing (Lesson 1.2's first unit) and then a method
> (Lesson 1.2's second unit)?

- **Reference Source:** no reference counterpart — from-scratch addition,
  same as every unit so far in this project.
- **Files affected:** modified — `code/01-csharp/Service/Service.cs` and
  `code/01-csharp/Service/Program.cs`.
- **Change type:** add.
- **Location:** inside `Service`'s block, a new field alongside `Run()`,
  plus one new line inside `Run()`'s own body; in `Program.cs`, two new

- **Dependencies:** the `Service` class and `Run()` method from Lesson


`Program.cs`'s job grew from "create a `Service` and run it once" to
"create a `Service`, run it twice, then report how many times it actually
ran" — read directly off the object's own field, through the same member
access `.` already used to call `Run()`, now reaching for data instead of
behavior.

### Introduce the Concept in Isolation

A throwaway project, `ScratchB`, was scaffolded fresh in this session's own
scratch directory:

```
dotnet new console -o ScratchB -n ScratchB
```

Its `Program.cs` starts with the smallest possible version — a field,
declared, never assigned anything, read immediately:

```csharp
var counter = new Counter();
Console.WriteLine(counter.Value);

public class Counter
{
    public int Value;
}
```

Run for real:

```
dotnet run
```

Real output:

```
0
```

This is exactly what the real `Service.cs` field declaration above is
doing, isolated, at its very first moment of existing: `Value`, just like
`RunCount`, was never explicitly assigned anything anywhere in this file,
and yet it already holds `0`, not garbage, not an error, and not nothing.
This proves the concept named earlier in this lesson's Header: a
**default field value** — every field a class declares is automatically
given a deterministic starting value the instant its object is
constructed, `0` for `int`, with no code anywhere responsible for setting
it.

Next, `Increment()` was added and called once:

```csharp
var counter = new Counter();
Console.WriteLine(counter.Value);
counter.Increment();
Console.WriteLine(counter.Value);

public class Counter
{
    public int Value;

    public void Increment()
    {
        Value = Value + 1;
    }
}
```

Run for real:

```
dotnet run
```

Real output:

```
0
1
```

Then `Increment()` was called a second time, with nothing else changed:

```csharp
var counter = new Counter();
Console.WriteLine(counter.Value);
counter.Increment();
Console.WriteLine(counter.Value);
counter.Increment();
Console.WriteLine(counter.Value);
```

Run for real:

```
dotnet run
```

Real output:

```
0
1
2
```

This is exactly what `RunCount`'s own increment line, shown in the real
project above, is doing: `Value` didn't reset back to `0` on the second
call, and it didn't jump straight to some fixed number either — it
carried `1` forward from the first call and added another `1` on top of
it. This is what a **field** actually is, proven rather than just defined:
a piece of storage that survives across separate calls to the same
method, on the same object, accumulating changes instead of starting over
each time.

`ScratchB` is kept alive rather than deleted immediately — the next
concept unit in this lesson still needs it.

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`public`** — the access modifier, reappearing from Lesson 1.2, now
  applied to a field rather than a class or method: any code able to see a
  `Service` object is allowed to read or write `RunCount` directly — which
  is exactly what `Program.cs`'s new fourth line does.
- **`int`** — the field's declared type, stating that `RunCount` can only
  ever hold a whole number, never text or any other kind of value. This is
  the first type this curriculum's C# code has actually declared,
  anywhere.
- **`RunCount`** — the field's own name, chosen to describe exactly what
  it tracks: how many times this object's `Run()` has executed.
- **`;`** — the semicolon ending the field declaration, reappearing from
  Lesson 1.1, playing the same role here as on any other statement: it
  tells the compiler this declaration is complete.

And, inside `Run()`'s own updated body:

- **`RunCount`** (on the left of `=`) — a **field** access with no `.`
  and no object name in front of it at all — unlike `service.RunCount` in
  `Program.cs`, which reaches in from *outside* the object, this reference
  sits *inside* one of `Service`'s own methods, so C# already knows,
  without being told again, that this means "the `RunCount` belonging to
  whichever `Service` object `Run()` is currently running on."
- **`=`** — the assignment operator, reappearing from Lesson 1.2, storing
  a new value into `RunCount`.
- **`RunCount + 1`** (on the right of `=`) — the arithmetic addition
  operator, reappearing generally from arithmetic already known from
  Python but appearing for the first time in this curriculum's C# code:
  reads `RunCount`'s current value, adds `1` to it, and produces a new
  value — it does not, by itself, change `RunCount` at all; that only
  happens because this expression sits on the right side of the `=` just
  described.
- **`;`** — the semicolon ending this statement.

And in the updated `Program.cs`, the one line that finally makes
`RunCount` observable:

- **`service.Run();`** (the second call) — reappearing, character for
  character, from Lesson 1.2's own first use of this exact statement;
  running it a second time is what actually gives `RunCount` a second
  chance to change, which the next line then reveals.
- **`Console.WriteLine(service.RunCount)`** — **member access** (`.`),
  reappearing from Lesson 1.2 but reaching for a **field** this time
  instead of calling a method — `service.RunCount` produces the `int`
  currently stored on this specific object, rather than running any code.
  That `int` becomes the argument to **`Console.WriteLine(int)`** — a
  different overload than the one `Run()` itself calls internally,
  selected automatically by the compiler because the value handed to it
  is an `int`, not a `string`; see this overload's own entry, above, for
  its exact signature.
- **`;`** — the semicolon ending this statement, the fourth and last one
  `Program.cs` now contains.

### CS Lens

A field is this lesson's concrete example of **encapsulated state** — data
that lives *inside* a structural unit, tied to that unit's own lifetime,
rather than floating free at some outer scope everything can reach:

```
Also recognized in: an odometer's mileage counter sealed inside the
instrument itself rather than tracked on a separate notepad, a thermostat's
own remembered target temperature, a bank account's balance stored on the
account record rather than recomputed from nothing on every inquiry,
a video game character's current health value
```

Every one of these ties a changing quantity to the specific thing it
describes, so that thing can be asked about its own condition at any
later moment without anything else having had to track it separately.

### SE Lens

The alternative not chosen here is tracking this count somewhere else
entirely — a separate variable in `Program.cs`, incremented by hand every
time `Run()` is called. That alternative works today, with exactly one
`Service` and exactly two calls to `Run()`, visible in one small file. It
breaks the moment either of those stops being true: a second `Service`
object would need its own separately-tracked variable with no
relationship enforced between "this variable" and "that object," and any
code calling `Run()` from somewhere `Program.cs` can't see would have no
way to update a variable that only exists inside `Program.cs`. Keeping
`RunCount` as a field on `Service` itself ties the count to the exact
object it's actually counting, permanently, no matter who calls `Run()`
or from where. The real cost, worth stating honestly rather than glossed
over: `RunCount` is `public`, which means any code holding a `Service`
object can also set it directly — `service.RunCount = 9000;` would
compile and run without complaint, silently corrupting the count without
ever calling `Run()` at all. Nothing in this lesson's own code does that,
but nothing stops it either; that gap is exactly Lesson 1.4's subject,
not this one's.

Also worth stating plainly, since Lesson 1.2 explicitly flagged an
explicit constructor as something `Service` would eventually need: it
still doesn't, yet. A constructor becomes necessary the moment a field's
*correct* starting value is something other than its type's own default —
`RunCount` starting at `0` is exactly the correct starting point for a
counter that's never yet counted anything, so the compiler-supplied
default constructor, unchanged since Lesson 1.2, already produces the
right result with no code written for it at all.

```csharp
var secondCounter = new Counter();

Console.WriteLine(counter.Value);
Console.WriteLine(secondCounter.Value);

public class Counter
{
    public int Value;

    public void Increment()
    {
        Value = Value + 1;
    }
}
```

```
dotnet run
```

Real output:

```

0
```

`counter`, incremented twice by the previous unit's lab, still holds `2`
— unaffected by anything that happens next. `secondCounter`, created
afterward from the exact same `Counter` class, starts at its own default
`0`, not `2` — proving the concept directly: this is what **instance
member** means for a field specifically. `Counter`'s source text declares
`Value` exactly once, but each object created by `new Counter()` gets its
own separate, independent copy of it — declaring a field describes what
every object of that class *will have*, not one single shared value every
object reaches into together.

### Mechanical Walkthrough

Enumerating the new syntactic elements in this unit's isolated lab, in
order — everything else in the file (`Value`, `Increment`, the class
declaration itself) is unchanged from the previous unit and already fully
explained there:

- **`var secondCounter = new Counter();`** — a second, independent call to
  **`new`**, reappearing from Lesson 1.2: each call to `new` allocates a
  brand-new object with its own memory, entirely separate from any object
  an earlier `new` call already produced. `secondCounter` and `counter`
  are two different objects, at two different locations in memory, even
  though both came from the identical `Counter` class.
- **`secondCounter.Value`** — member access, reappearing from Lesson 1.2,
  reaching into the second object specifically. This is the same operator
  as `counter.Value` two lines earlier, but the object to its left is a
  genuinely different object, which is exactly why the two reads produce
  different numbers.

### CS Lens

Each object carrying its own independent copy of a class's fields is
**instance-level state**, as opposed to state shared by every object of a
class at once:

```
Also recognized in: every car built from the same factory blueprint
having its own odometer reading, every bank account opened under the
same account-type template holding its own independent balance, every
browser tab running the same web page holding its own separate scroll
position, two instances of the same video game character each tracking
their own separate health value
```

Every one of these is the same underlying idea: a shared *description*
of what data something will carry, paired with each individual thing
holding its own actual copy of that data, never accidentally sharing it
with another instance of the same description.

### SE Lens

The alternative this unit's Socratic prompt deliberately raised —
`RunCount` behaving like a single shared value every `Service` object
reaches into together — is a real, different C# feature (a `static`
field), not something this lesson's code accidentally could have produced
by mistake. C# requires a `static` field to be declared with that exact
keyword; without it, a field is automatically per-instance, the behavior
this unit just proved. The tradeoff, stated honestly: per-instance fields
are the right default for `RunCount`, since counting runs of *one specific
service* is the entire point — a shared count across every `Service` this
project ever created would answer a different, less useful question
("how many times has *any* service run, ever?") that nothing in this
project currently needs answered. This project doesn't yet have a second
`Service` object anywhere in its real, tracked code — that stays true
until Lesson 1.5 gives `Service` a second, related object to collaborate
with — so this unit's proof necessarily lives entirely in the isolated
lab rather than in a second real `Service` this project has no actual use
for yet.

### Connect to What Came Before

The previous unit proved `RunCount` persists *across time* — two calls to
`Run()`, one object, an accumulating value. This unit proves the other
half of what "instance member" means: that same field also stays separate
*across objects* — two `Counter`s, two independent `Value`s, neither
affecting the other. Together, these two units are the full meaning of
**object state**: data that belongs to one specific object, persisting for
as long as that object exists, and never leaking into any other object of
the same class.
