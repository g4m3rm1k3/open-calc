# Lesson 1.11: Waiting Without Blocking — Make the Operation Asynchronous

**What you will build.** `Service` gains a third way to run: `RunAsync()`,
an **asynchronous** counterpart to `Run()` that simulates work taking real
time — `await Task.Delay(100)` — before updating the count and reporting,
exactly like `Run()` already does. `Program.cs` calls it twice, with
`await`, and the real output is identical in substance to a synchronous
call: the count still ends up right, the messages still print in order.
What's different is invisible in that output alone: while `RunAsync()`'s
own delay is pending, the thread that called it is never blocked, sitting
idle, waiting — proven, in this lesson's own isolated lab, by starting two
such delays *before* awaiting either one, and watching a line print
between "started" and "finished" that could only appear there if neither
call had blocked anything. A **`Task`** represents work that is either
still in progress or already done; **`async`** marks a method as one that
can pause and resume around that work; **`await`** is the specific point
where a method pauses — without freezing the thread it's running on —
until a `Task` finishes.

**What you need to know first.** From **Lesson 1.10 — Refuse, Then
Decide**: the real project at `code/01-csharp/Service/`, `Service`'s
`Run()` and `Reset()` methods. From **Lesson 1.6**: `this`, constructor
injection. From **Lesson 1.2**: `class`, `object`, `method`, `void`,
`new`, member access (`.`). From **Lesson 1.1**: `Console`,
`Console.WriteLine`, top-level statements, and `ImplicitUsings` — this
lesson's own new types, `Task` and everything needed to use it, are
reachable with no new `using` directive at all, for the same reason
`Console` always has been. From the curriculum's own stated assumptions:
nothing specific beyond ordinary sequential program reading — this
lesson's whole point is a kind of control flow genuinely different from
anything Python's basic assumptions already cover.

## Terms used in this lesson

- **`Task`** — a type representing a unit of asynchronous work that is
  either still running or has already finished. It exists because an
  operation that takes real time — a delay, a network call, reading a
  file — needs *something* to represent "this is in progress, check back
  or wait for it," distinct from the operation's own eventual result.
- **`async`** — a modifier on a method declaration, marking that method
  as one whose body can use `await`. It exists because `await`'s own
  pause-and-resume behavior needs the compiler to transform the method's
  body into something that can genuinely be suspended and resumed later,
  and `async` is what asks for that transformation.
- **`await`** — an operator, usable only inside an `async` method, that
  suspends that method's own execution until the `Task` it's applied to
  finishes — *without* blocking the thread the method is running on,
  which remains free to do other work in the meantime. This is the
  single most important distinction this lesson exists to prove: `await`
  is not the same as simply waiting in place.
- **asynchronous control flow** — the general shape of execution `async`
  and `await` produce: code written to read top-to-bottom, the same as
  any other method, while actually running in discontinuous pieces —
  everything before an `await` runs immediately; everything after it
  only runs once the awaited `Task` finishes, on whatever thread happens
  to resume it, not necessarily synchronously with everything before.
- **blocking vs. non-blocking** — a blocking wait ties up the thread doing
  the waiting, preventing it from doing anything else until the wait
  ends; a non-blocking wait — what `await` actually is — releases the
  thread to do other work while the underlying operation is still
  pending, and only resumes the original method once that operation
  finishes. This distinction is this lesson's own central subject,
  proven concretely in its second unit.
- **`class`, `object`, `method`, `void`, `new`, member access (`.`),
  assignment operator (`=`), string literal, semicolon (`;`), `public`,
  `this`** — all reappearing from Lessons 1.1–1.6, unchanged in meaning,
  all still present in `Service.cs`, `Program.cs`, and this lesson's
  isolated lab.

## Concept Unit: `Task`, `async`, and `await` — Declaring Work That Takes Time

### The Problem

`Run()` and `Reset()` both do their work immediately, synchronously —
nothing about either method's own shape allows for "this might take a
while, and the caller shouldn't have to sit frozen waiting for it." A
real service performing real work — a network call, a database write —
often genuinely does take real time. How does a method say, honestly,
"this will take a while, but calling me shouldn't lock up whatever called
me the entire time"?

> **Stop and think, before reading on:** you already know a Python
> function just runs, top to bottom, and the caller waits for it to
> return — there's no built-in notion in ordinary Python functions of
> "this might take a while, don't wait synchronously." Given that
> `Console.WriteLine` and every method in this project so far has
> returned instantly (or as close to instantly as this project's own
> work requires), what do you predict a method's *declaration* needs to
> say, up front, to signal "calling me might take real time, and here's
> how you'll know when I'm done"? Would that need a different return
> type than `void`, or could `void` already handle it?

### CS Lens

`async`/`await` is a real instance of **cooperative suspension** — a
piece of running code voluntarily pausing itself at a specific, chosen
point, rather than being forcibly interrupted from outside:

```
Also recognized in: a chess player who, mid-game, steps away to think
without giving up their seat or ending the game, a recipe step that
says "let the dough rise for an hour" — during which the cook is free
to do something else entirely, a phone call placed on hold, where the
caller keeps the line without the phone itself being tied up doing
nothing, a librarian placing a book request and moving on to help
another patron instead of waiting at the shelf for it to be found
```

Every one of these separates "waiting for something to finish" from
"being unable to do anything else in the meantime" — the two are not the
same thing, even though a synchronous, blocking wait makes them feel
identical.

### SE Lens

The alternative not chosen here is a **blocking** wait — code that
occupies its thread the entire time an operation is pending, doing
nothing else, the way a synchronous `Run()` already does for its own
(currently instant) work. That alternative is completely fine for work
that genuinely finishes immediately; it becomes a real problem the moment
an operation takes meaningfully long, because the thread doing the
waiting can't do anything else at all during that time — in a program
serving many callers at once, one blocked thread per waiting operation
adds up fast. `async`/`await` costs something real in exchange: a method
marked `async` doesn't run as one uninterrupted sequence of instructions
the way every other method in this project does — its body is
transformed by the compiler into something that can be paused and
resumed, which is exactly why the next unit's proof is necessary at all,
rather than obvious from reading the code alone.

## Concept Unit: Asynchronous Control Flow — Proving the Caller Isn't Blocked

### The Problem

`RunAsync()`'s own output looked identical to what a synchronous version
would produce — nothing in Unit 1's real output actually distinguished
"paused without blocking" from "just ran a little slower." Is `await`
genuinely different from a plain, blocking wait, or does it just look
different in the method declaration while behaving identically underneath?

> **Stop and think, before reading on:** if `await Task.Delay(100)`
> merely blocked the calling thread the same way a synchronous wait
> would, then starting *two* such delays back to back, before awaiting
> either one, should behave no differently than starting them one at a
> time — each one would have to finish before the next line could even
> run. Given that hypothesis, what real, observable evidence would prove
> it wrong? What would you expect to see printed, and in what order, if
> starting two delayed operations really doesn't block anything at all?

### Introduce the Concept in Isolation

Still inside `ScratchJ`, two `DoWorkAsync` calls were started — but not
awaited — one right after the other, with a line printed in between:

```csharp
var worker = new Worker();

var task1 = worker.DoWorkAsync("A");
var task2 = worker.DoWorkAsync("B");
Console.WriteLine("Both started");

await task1;
await task2;
Console.WriteLine("Both finished");

public class Worker
{
    public async Task DoWorkAsync(string name)
    {
        await Task.Delay(200);
        Console.WriteLine(name);
    }
}
```

Run for real, four times in a row, specifically to check whether the
result is the same every time:

```
dotnet run
```

Real output, run 1:

```
Both started
B
A
Both finished
```

Real output, run 2:

```
Both started
A
B
Both finished
```

Real output, runs 3 and 4: identical in shape to run 1 (`B` before `A`).

The real output's own ordering is the proof, made concrete step by step:

1. `worker.DoWorkAsync("A")` — called without `await`; this starts `A`'s
   own `200`ms delay, but does not pause `Program.cs`'s own execution at
   all, since nothing here awaits the `Task` it returns yet.
2. `worker.DoWorkAsync("B")` — called immediately after, for the same
   reason: `B`'s own delay starts too, while `A`'s is still pending.
3. `Console.WriteLine("Both started")` — runs *immediately*, before
   either delay has had time to finish, which is exactly why this line
   prints first in every single run: nothing before it ever blocked
   waiting for `A` or `B`.
4. `await task1;` then `await task2;` — only *now* does `Program.cs`
   actually pause, waiting for each `Task` in turn — but since both
   delays have been running concurrently since steps 1 and 2, this
   mostly waits for whichever hasn't already finished, not a fresh,
   sequential `200`ms wait for each.
5. `Console.WriteLine("Both finished")` — runs only once both `await`s
   above have resumed, which is exactly why it prints last, every time.

This proves the concept named in this unit's own title: `Both started`
printing before either `A` or `B` is real, direct evidence that calling
`DoWorkAsync` twice did not block `Program.cs` at all — a blocking wait
could never have let that line print first. The order `A`/`B` themselves
print in, by contrast, genuinely varies run to run — real, honest proof
that two concurrently-running tasks' relative finishing order isn't
something this lesson can promise, only that neither one blocked
anything while it ran.

### CS Lens

The distinction this unit proves — code that *looks* sequential but
doesn't *block* sequentially — is a real instance of **logical versus
physical execution order**: the order code is *written* in is not always
the order in which its effects on the outside world actually complete:

```
Also recognized in: a restaurant kitchen firing several dishes at once
for one table rather than cooking them one at a time in ticket order,
a web browser requesting several images for one page simultaneously
rather than waiting for each to finish downloading before requesting
the next, a project manager assigning several tasks to different team
members at once rather than waiting for each one to finish before
assigning the next, an orchestra conductor cueing multiple sections to
begin at once rather than waiting for one section to finish before
cueing the next
```

Every one of these separates "the order things were requested in" from
"the order they actually complete in" — the two only look identical when
nothing runs concurrently at all.

### SE Lens

The alternative this unit's own isolated lab could have taken —
`await worker.DoWorkAsync("A"); await worker.DoWorkAsync("B");`, awaiting
each immediately, the same pattern this project's own `Program.cs`
actually uses for `RunAsync()` — is not wrong. It's simply sequential:
each `200`ms delay genuinely waits its own full duration before the next
one even starts, taking roughly twice as long in total as the concurrent
version this unit demonstrated. This project's own two `RunAsync()`
calls are deliberately left sequential rather than concurrent, because
nothing about incrementing `runCount` twice benefits from happening at
the same time — doing so concurrently would risk both calls reading and
writing `runCount` at overlapping moments, a real problem this project
has no mechanism yet to guard against. The real lesson here: `async`/
`await` makes concurrency *possible*, but writing `await` immediately
after starting one operation, the way `Service`'s own code does, is a
perfectly valid, deliberate choice — not a missed opportunity — whenever
running things one at a time is actually what correctness requires.
