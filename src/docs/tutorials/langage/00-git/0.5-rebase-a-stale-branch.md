# Lesson 0.5: A Branch That Pretends It Started Later

**What you will build:** `add-goodbye-line` — a branch created back in Lesson 0.2 and never touched since — finally gets real work: two new commits, each adding a translated goodbye line to `hello.py`. Meanwhile `master` has kept moving without it, all the way through Lesson 0.4's merge commit and one commit further. Instead of merging the stale branch in as-is (which Lesson 0.3 and 0.4 already know how to do, and which would produce a second merge commit), this lesson makes `add-goodbye-line`'s two commits behave as though they had been written starting from `master`'s current tip all along — replayed there, one at a time, as brand-new commits with brand-new identities. The transferable problem: a branch that falls behind isn't just "old," it's built on an assumption — "this is what the world looked like when I started" — that's no longer true, and there are two different ways to reconcile that: combine the two realities as they actually happened (merge), or rewrite one branch's story as if it had happened later than it did (rebase).

**What you need to know first:** Lesson 0.1's commit and staging area. Lesson 0.2's branch and `git switch`. Lesson 0.3's `git merge` and the fast-forward case. Lesson 0.4's merge conflict, conflict markers, three-way merge, common ancestor, `HEAD`, and testing after resolution — this lesson's own conflict reuses every one of those ideas, just inside a different command.

**Terms used in this lesson**

- **rebase** — Taking every commit that exists on one branch but not on another, and replaying each of them, one at a time, as a brand-new commit on top of the second branch's current tip — instead of combining the two branches' histories with a merge commit. It exists because a merge commit records *both* realities (what the current branch had, what the incoming branch had) permanently, forever, in the history — which is honest, but leaves the project's history full of forks and rejoins. Rebase exists for the case where that honesty isn't wanted: where it's more useful for the history to read as if the branch's work had simply started later, from whatever `master` looks like *now*, than to preserve the fact that it didn't.
- **upstream** — Git's own name, in `git rebase`'s own usage, for the branch being rebased *onto* — the new foundation the current branch's commits get replayed on top of. It's the same role `master` played as the merge *target* in Lessons 0.3–0.4, just renamed, because rebase's own mental model isn't "combine two branches" (merge's model) but "move my branch's starting point" — and a starting point needs a name that isn't "target."
- **detached HEAD** — The state git puts the working tree into while a rebase is actually replaying commits: `HEAD` points directly at a specific commit instead of at a branch name, because the commit being built doesn't belong to any branch yet — it's provisional, waiting to see whether the whole replay succeeds. Only once every commit has been replayed does git move `add-goodbye-line` itself to point at the final result; until then, the label attached to each newly-created commit literally reads `detached HEAD`, not the branch's name, which is exactly what this lesson's own real output below shows.
- **linear history** — A commit history in which every commit has exactly one parent, with no merge commits anywhere in the chain — the shape `git log --graph` draws as a single straight line instead of forking and rejoining. It's not a property any individual commit has; it's a property of the whole sequence, and it's the specific thing rebasing a branch before merging it is capable of producing, which merging a stale branch directly is not.
- **merge conflict** — Reappearing from Lesson 0.4. The state git puts an operation into when two branches changed the exact same region of the exact same file in different ways, and has no rule for choosing between them — there, that operation was `git merge`; here, it's each individual commit being replayed during a rebase, which turns out to hit the identical problem for the identical reason.
- **conflict markers** — Reappearing from Lesson 0.4. The literal text — `<<<<<<< HEAD`, `=======`, `>>>>>>> <label>` — git writes directly into a conflicted file to show both disputed versions in place. This lesson's own conflict produces the same three-part structure inside `hello.py`, with one difference in the closing label explained where it appears below.
- **three-way merge** — Reappearing from Lesson 0.4. The algorithm that compares two versions of a file *against their common ancestor*, not just against each other, so git can tell "only one side changed this" (safe to combine automatically) from "both sides changed this differently" (a real conflict). `git rebase`, this lesson proves, runs this exact algorithm too — once per commit being replayed, not once for the whole operation the way `git merge` did.
- **common ancestor** — Reappearing from Lesson 0.4. The most recent commit two versions being compared both descend from — what a three-way merge measures every difference *against*. This lesson's conflict measures against a different common ancestor than Lesson 0.4's did, for reasons explained inside the first Concept Unit.
- **`HEAD`** — Reappearing from Lesson 0.4. Git's name for "the commit currently checked out." During Lesson 0.4's merge conflict it always meant "master's version" specifically, because `master` was the branch checked out. During this lesson's rebase, `HEAD` briefly means something else entirely — a *detached* commit, not a branch — which is exactly what the term above exists to name.
- **staging area / index** — Reappearing from Lessons 0.1 and 0.4. Git's intermediate structure between the working tree and the commit history. During this lesson's conflict, `git add` does the identical double duty it did in Lesson 0.4: stage the resolved content, and clear the path's unmerged flag — the one thing `git rebase --continue` checks before it will proceed to the next commit.
- **fast-forward** — Reappearing from Lesson 0.3 and 0.4. The case where the branch being merged in has no independent commits of its own relative to the current branch, so git can resolve the "merge" by just moving a pointer, with no new commit and no possibility of a conflict. This lesson's whole point is to *manufacture* this case for a branch that, at the start of the lesson, genuinely doesn't qualify for it yet.
- **merge commit** — Reappearing from Lesson 0.3 and 0.4. A commit with more than one parent, created when a merge can't be resolved by fast-forwarding. This lesson never produces one — that absence, deliberately engineered, is the entire outcome rebasing was for.

**Objects and methods used**

- **`git rebase <upstream>`**
  - *What it is:* A git subcommand that takes every commit reachable from the current branch but not from `<upstream>`, and replays each one, in order, as a new commit on top of `<upstream>`'s current tip.
  - *Implementation:* Invoked below as `git rebase master`, run while `add-goodbye-line` is checked out, with no flags — `master` is the upstream, the new foundation to replay onto.
  - *Its use:* This lesson's code reaches for it specifically because `add-goodbye-line` has two commits `master` doesn't have, and `master` has commits (all the way back through Lesson 0.4's merge, plus one more) that `add-goodbye-line` doesn't have — the exact shape of divergence a straight merge would resolve with a second merge commit, and rebase resolves differently.
  - *Type:* A `git` CLI subcommand — a write operation that creates brand-new commit objects; it does not modify any existing commit.
  - *Responsibility:* Identify the set of commits unique to the current branch (everything reachable from it but not from `<upstream>`); for each one, in the order it was originally committed, reapply that commit's actual content change against whatever the tree looks like so far (starting from `<upstream>`'s tip); if a given commit's change can't be applied automatically because the target region already changed differently, stop and hand the file to the person, in a conflicted state, exactly like `git merge` does; once every commit has been replayed successfully, move the current branch's pointer to the last new commit created.
  - *Depends on:* The current branch already checked out; the named upstream branch or commit; for each individual commit replay, a common ancestor between that commit's original parent and the tree being built so far.
  - *Connects to:* Called by the person at the terminal; reads the commit history built by earlier `git commit` calls on both branches; on success, creates new commit objects and moves the current branch's pointer to the last of them; on a per-commit failure, writes conflict markers into the affected file exactly as `git merge` would, and pauses, leaving `git status`, `git add`, and `git rebase --continue` to finish the job.
  - *Shape:* The same seam `git merge` operates on — where one branch's history meets another's — reached with a different intent: not "record that these two things happened independently," but "make it look like this branch's work started from where the other one is now."

- **`git status`**
  - *What it is:* Reappearing from Lesson 0.4. A read-only git subcommand that reports the current state of the working tree and staging area, without changing anything.
  - *Implementation:* Invoked with no arguments, mid-rebase, in the same spot Lesson 0.4 used it mid-merge.
  - *Its use:* Used here to confirm exactly what state the interrupted rebase left things in — and, more importantly, to show that its message is *not* the same message Lesson 0.4's mid-merge `git status` produced, which is the whole reason this term needed its own real look rather than an assumption that "conflict resolution" always reads identically.
  - *Type:* A read-only `git` CLI subcommand.
  - *Responsibility:* Compare the last commit, the index, and the working tree, and describe every difference in terms a person can act on — including, specifically, which git operation is currently in progress (a merge, or, as shown below, a rebase) and what command would move that operation forward.
  - *Depends on:* Nothing beyond an existing repository; it reads whatever state `git rebase` happens to have left behind at the moment it's run.
  - *Connects to:* Called by the person at the terminal; reads the index and working tree `git rebase` just modified; its output is what tells the reader whether `git add` still needs to run or whether the operation is ready to continue.
  - *Shape:* The same read-only diagnostic layer it was in Lesson 0.4 — never part of the history being built, only a window onto it, reused here to show that the window looks different depending on what's actually happening underneath.

- **`git add <file>`**
  - *What it is:* Reappearing from Lessons 0.1 and 0.4. A git subcommand that stages a file's current content into the index.
  - *Implementation:* Invoked below as `git add hello.py`, immediately after hand-editing the file to remove this lesson's own conflict markers — the identical call, syntactically, as Lesson 0.4's resolution step.
  - *Its use:* Same double duty as Lesson 0.4: stage the resolved content, and clear `hello.py`'s unmerged flag — except this time, that flag is being checked by `git rebase --continue`, not `git commit`.
  - *Type:* A `git` CLI subcommand — a write operation on the index only.
  - *Responsibility:* Copy the exact current bytes of the named path from the working tree into the index, and clear that path's unmerged status if it had one.
  - *Depends on:* A working-tree file at the given path; during a conflict, it depends on the conflicting operation having already put that path into the unmerged state.
  - *Connects to:* Called by the person at the terminal after hand-editing the file; reads the working tree; writes to the index; its effect is what the next command — here, `git rebase --continue` rather than `git commit` — checks before proceeding.
  - *Shape:* The same manual signal it was in Lesson 0.4 — the seam between "git flagged a problem" and "a human took responsibility for the fix" — reused here for a different operation to hand off to.

- **`git rebase --continue`**
  - *What it is:* A git subcommand — really the same `git rebase` command from above, invoked in its resumption mode — that proceeds with a paused rebase once every currently-unmerged path has been staged.
  - *Implementation:* Invoked below as `git rebase --continue`, with no other arguments, immediately after `git add hello.py`.
  - *Its use:* This is the step that actually finishes replaying the commit that just conflicted, and then keeps going — attempting every remaining commit in the sequence, not just the one that was paused.
  - *Type:* A `git` CLI subcommand — a write operation resuming an already-in-progress rebase.
  - *Responsibility:* Confirm no path is still marked unmerged; if clear, take whatever is currently staged, wrap it in a new commit carrying the paused commit's original author and message, and continue replaying every remaining commit in the sequence — stopping again, the same way, if any of the rest also conflicts.
  - *Depends on:* An in-progress rebase (the state `.git` was left in by the paused `git rebase master` above) and a fully-resolved index for the currently-conflicted path.
  - *Connects to:* Called by the person at the terminal; reads the index `git add` just staged; creates one or more new commit objects; on finishing every remaining commit, moves the branch pointer the same way a clean `git rebase` would have.
  - *Shape:* The rebase-specific counterpart to Lesson 0.4's plain `git commit` — where finishing a resolved merge conflict meant one ordinary commit, finishing a resolved rebase conflict means resuming a whole in-progress sequence, because a rebase is not one operation but a queue of them.

- **`git cat-file -p <object>`**
  - *What it is:* A git subcommand that reads any object out of git's own internal object store — by the exact SHA that identifies it — and prints its real, raw content in human-readable form.
  - *Implementation:* Invoked below twice, once as `git cat-file -p 0ba2c86` (the original, pre-rebase commit object) and once as `git cat-file -p 40fa2c0` (the new, post-rebase commit object) — one argument each time, the object's SHA.
  - *Its use:* This is the one command in this lesson that doesn't move the project forward at all — it exists purely to prove, by directly inspecting git's own stored data, that "rebase creates new commits" is a literal, physical fact about what's stored on disk, not just a description of the visible effect.
  - *Type:* A read-only `git` CLI subcommand — a direct window into git's object database, the same underlying storage every other command in this lesson writes to indirectly.
  - *Responsibility:* Given an object's SHA, look it up in git's object store and print its stored content in the format appropriate to that object's type — for a commit object specifically, its tree, its parent (or parents), its author, its committer, and its message, in that order.
  - *Depends on:* An object matching the given SHA already existing in the repository's object store — including an object no branch currently points at, as long as it hasn't been garbage-collected yet.
  - *Connects to:* Called by the person at the terminal; reads directly from the same object store every `git commit` and `git rebase` call in this lesson wrote to; its output is not consumed by any other command — it's read by the person, as evidence.
  - *Shape:* The lowest layer this curriculum has looked at yet — every other command in this and every prior Phase 0 lesson operates *through* git's porcelain (`commit`, `merge`, `rebase`); this one reaches straight into the plumbing underneath it.

**Everything else in the file, not this lesson's subject but still explained.**

- **`git switch`**
  - *What it is:* Reappearing from Lesson 0.2. A git subcommand that changes which branch is currently checked out.
  - *Implementation:* Invoked below as `git switch add-goodbye-line` and `git switch master`, plain switches with no `-c`, since both branches already exist from earlier lessons.
  - *Its use:* Moves between `add-goodbye-line` and `master` at every point in this lesson where the next command needs a different branch checked out.
  - *Type:* A `git` CLI subcommand — a write operation on `HEAD` and on the working tree's contents.
  - *Responsibility:* Given a branch name, replace the working tree's contents with that branch's committed content and update `HEAD` to point at it.
  - *Depends on:* A working tree clean enough relative to the branch being left that git won't have to silently overwrite anything.
  - *Connects to:* Called by the person at the terminal; writes to `HEAD`; every subsequent command in that terminal session then operates on whichever branch it just switched to.
  - *Shape:* The same foundation Lesson 0.2 built — one working tree standing in for many lines of history, one at a time — reused here purely as setup between this lesson's real steps.

- **`git commit`**
  - *What it is:* Reappearing from Lessons 0.1 and 0.4. A git subcommand that takes whatever is staged and permanently records it as a new commit.
  - *Implementation:* Invoked below three ways: `git commit -m "..."` for the new `CHANGELOG.md` file (an already-staged new file, no `-a` needed), and `git commit -am "..."` twice more, for the French and German goodbye lines on `add-goodbye-line` (stage-and-commit an already-tracked file's change in one step).
  - *Its use:* Builds the real divergence this lesson needs — one commit moving `master` forward, two commits moving `add-goodbye-line` forward, all before either branch knows anything about the other's new work.
  - *Type:* A `git` CLI subcommand — a write operation creating a new, single-parent commit in each case here (none of these three are merge commits).
  - *Responsibility:* Take the exact content currently staged, wrap it in a new commit with an author, a message, a timestamp, and a pointer back to the branch's current tip, and move the branch to point at that new commit.
  - *Depends on:* A staged change (via `-a` for already-tracked files, or an explicit `git add` for a new file like `CHANGELOG.md`) and a configured commit author.
  - *Connects to:* Called by the person at the terminal; reads the index; writes a new commit; moves the branch pointer; its result is what every `git log` and `git cat-file` call in this lesson later reads back.
  - *Shape:* The same permanent record-keeping step it's been since Lesson 0.1 — used here purely to set the stage for the rebase that's this lesson's actual subject.

- **`git log --oneline --graph --all`**
  - *What it is:* Reappearing from Lessons 0.3 and 0.4. A git subcommand that reads and displays commit history, drawing an ASCII graph of branch structure across every branch, not just the checked-out one.
  - *Implementation:* Invoked identically, several times below, at each point this lesson's history changes shape — before the rebase, mid-conflict is covered by `git status` instead, and after the rebase completes.
  - *Its use:* This is how the lesson makes the *shape* of divergence, and later the *shape* of a linear history, directly visible rather than described.
  - *Type:* A read-only `git` CLI subcommand.
  - *Responsibility:* Walk the commit graph from every branch tip (`--all`) and print each commit as one line (`--oneline`), with an ASCII graph (`--graph`) showing exactly how the branches fork and rejoin, or don't.
  - *Depends on:* An existing commit history; `--graph` specifically depends on more than one line of history existing, or it just prints a flat list.
  - *Connects to:* Called by the person at the terminal; reads the commits every `git commit` and `git rebase` call in this lesson created; its output is how the reader confirms what the history actually looks like, rather than trusting a description of it.
  - *Shape:* The same read-only reporting layer it's been since Lesson 0.3 — never part of the history itself, only a way of looking at it, which is exactly why it's the right tool for proving a *shape* changed.

- **`git branch`**
  - *What it is:* Reappearing from Lessons 0.2 and 0.4. A git subcommand that manages and reports on branch pointers.
  - *Implementation:* Invoked below two ways: `git branch -d add-goodbye-line` (delete the branch, only allowed because its commits are now reachable from `master`) and `git branch -v` (list every remaining branch with the commit it points at).
  - *Its use:* `-d` cleans up `add-goodbye-line` once its work is safely part of `master`. `-v` confirms only `master` remains, exactly as Lesson 0.4 confirmed its own cleanup.
  - *Type:* A `git` CLI subcommand — read-only with `-v`, a write operation on stored branch pointers with `-d`.
  - *Responsibility:* Track the set of named pointers into the commit graph; with `-d`, remove a pointer, but only after confirming every commit it points at is already reachable from some other branch.
  - *Depends on:* `-d` depends on the branch not being currently checked out, and its commits already being reachable elsewhere.
  - *Connects to:* Called by the person at the terminal; `-d` reads the commit graph to verify safety before deleting a pointer; `-v` reads the stored pointers directly.
  - *Shape:* Branch management sitting one layer above individual commits — Lesson 0.2's own subject, reused here only for cleanup and confirmation.

- **`python <file>`**
  - *What it is:* Reappearing from Lessons 0.1 and 0.4. The Python interpreter, run directly against a source file.
  - *Implementation:* Invoked below as `python hello.py`, no flags.
  - *Its use:* The same **testing after resolution** practice Lesson 0.4 established — proving the final, rebased `hello.py` actually behaves as intended, not just that git considers the history clean.
  - *Type:* An external CLI program — not a git subcommand, not part of this project's own code.
  - *Responsibility:* Parse the given source and execute it top to bottom, printing whatever the code's own `print(...)` calls produce.
  - *Depends on:* A syntactically valid `.py` file.
  - *Connects to:* Called by the person at the terminal; reads the exact file content the completed rebase and fast-forward merge left behind; its output is the only thing in this lesson that speaks to whether the final file is *correct*, not just *committed*.
  - *Shape:* Sits entirely outside git, same as in Lesson 0.4 — the boundary between "the repository's history is in an agreed-upon state" and "the code that state represents actually does the right thing."

None of these are opaque magic. Every git subcommand above is documented, in full, by git itself — `git help <subcommand>` prints its real, official manual page on any machine with git installed, mirrored at git-scm.com. `git cat-file` specifically is how this lesson checks its own claims directly against git's real stored data rather than taking a description of git's internals on faith.

## Setting Up: A Branch That Fell Behind Gets Real Work

Lesson 0.4 left the real project — `code/00-git-workflow/` — on `master`, at commit `e4a118e`, with `hello.py` reading:

```python
print("Hello, recoverable history.")
print("Goodbye, for now, see you soon.")
```

`add-goodbye-line`, created back in Lesson 0.2, still points at `5ee4c4f` — the commit both `warmer-goodbye` and `formal-goodbye` originally branched from, before either of them existed. It's never diverged from `master` in its own right; it's just been sitting there, unmoved, while three more commits happened without it. Its own copy of `hello.py`, inspected directly:

```
$ git show add-goodbye-line:hello.py
print("Hello, recoverable history.")
print("Goodbye, for now.")
```

Line 2 here — `"Goodbye, for now."` — is the *original* wording, from before `warmer-goodbye` and `formal-goodbye` ever rewrote it. `master`'s current line 2 is `"Goodbye, for now, see you soon."` This difference is not something this lesson introduces on purpose; it's simply what "fell behind" already means for this branch, and it becomes relevant later.

First, `master` gets one more commit of its own — real, independent project work that happens to occur while `add-goodbye-line` is still sitting idle, the same way real projects keep moving while a stale branch waits:

```
$ git switch master
Switched to branch 'master'
$ printf '# Changelog\n\n0.4: resolved the goodbye-line conflict between warmer-goodbye and formal-goodbye, kept the warmer phrasing.\n' > CHANGELOG.md
$ git add CHANGELOG.md
$ git commit -m "Log the goodbye-line conflict resolution in CHANGELOG"
warning: in the working copy of 'CHANGELOG.md', LF will be replaced by CRLF the next time Git touches it
[master ce52fbd] Log the goodbye-line conflict resolution in CHANGELOG
 1 file changed, 3 insertions(+)
 create mode 100644 CHANGELOG.md
```

`git commit`, explained in full above, records `CHANGELOG.md` as a brand-new file. `master` now sits at `ce52fbd`, one commit past where Lesson 0.4 left it. This commit doesn't touch `hello.py` at all — that matters later, when this lesson's own conflict is explained.

Now `add-goodbye-line` finally gets the work its name has promised since Lesson 0.2 — two more translated goodbye lines, one commit each:

```
$ git switch add-goodbye-line
Switched to branch 'add-goodbye-line'
$ printf 'print("Hello, recoverable history.")\nprint("Goodbye, for now.")\nprint("Au revoir!")\n' > hello.py
$ git commit -am "Add a French goodbye"
warning: in the working copy of 'hello.py', LF will be replaced by CRLF the next time Git touches it
[add-goodbye-line 0ba2c86] Add a French goodbye
 1 file changed, 1 insertion(+)
$ printf 'print("Hello, recoverable history.")\nprint("Goodbye, for now.")\nprint("Au revoir!")\nprint("Auf Wiedersehen!")\n' > hello.py
$ git commit -am "Add a German goodbye"
warning: in the working copy of 'hello.py', LF will be replaced by CRLF the next time Git touches it
[add-goodbye-line b73b07f] Add a German goodbye
 1 file changed, 1 insertion(+)
```

Both commits build directly on `add-goodbye-line`'s *own* stale copy of `hello.py` — line 2 still reads the original `"Goodbye, for now."` in both of them, because neither commit touches that line; they only add lines after it.

The real shape of the divergence is now visible directly:

```
$ git log --oneline --graph --all
* b73b07f Add a German goodbye
* 0ba2c86 Add a French goodbye
| * ce52fbd Log the goodbye-line conflict resolution in CHANGELOG
| *   e4a118e Merge formal-goodbye into master, keep the warmer goodbye phrasing
| |\
| | * 9b01ea8 Make the goodbye line more formal
| |/
|/|
| * 6da3aab Make the goodbye line warmer
|/
* 5ee4c4f Add a goodbye line to hello.py
* b63f930 Add hello.py, the first runnable script
```

Two commits below `5ee4c4f` belong only to `add-goodbye-line`. Four commits above it — `6da3aab`, `9b01ea8`, `e4a118e`, `ce52fbd` — belong only to `master`. This is a different shape than Lesson 0.4's divergence: there, two branches forked from the same point and neither had moved past the other. Here, both sides have moved, in completely different directions, from the same common ancestor. Merging `add-goodbye-line` into `master` right now, the way Lessons 0.3–0.4 already know how, would need a second merge commit — there's no way for `master`'s pointer to just slide forward, because `add-goodbye-line` has real commits `master` doesn't have.

Before reading on: given what `git merge` already does with two branches that have each moved independently — is there any way to bring `add-goodbye-line`'s two commits into `master` *without* creating a merge commit? What would have to be true about `add-goodbye-line`'s commits for a fast-forward to become possible again, given that it isn't possible right now?

## Concept Unit: Replaying Commits — `git rebase`

### The Problem

`add-goodbye-line` has two real commits `master` doesn't have. `master` has four real commits `add-goodbye-line` doesn't have. A fast-forward needs one side to have *nothing* the other side lacks — and right now, neither side qualifies. Lesson 0.3 and 0.4 already showed the merge-commit answer to this shape of problem. This lesson asks a different question: instead of accepting that `add-goodbye-line`'s two commits happened while `master` was somewhere else, is there a way to make it *as if* they'd been written starting from wherever `master` is *right now*?

### Project Change

- **Reference Source:** No reference counterpart — Phase 0 teaches the engineering workflow itself, not a port of the `Service`/`Data` reference project.
- **Files affected:** `code/00-git-workflow/hello.py` (modified by the rebase attempt itself, not by hand).
- **Change type:** The command below is a `git rebase` invocation, not a hand-written code change.
- **Location:** Run from `add-goodbye-line`, immediately after Setting Up, with `master` as the upstream.
- **Dependencies:** The divergent history built in Setting Up, above — `add-goodbye-line` at `b73b07f`, `master` at `ce52fbd`, both descended from `5ee4c4f`.

### The New Code

```
$ git rebase master
```

### The Updated Project

This doesn't produce a clean result the way the isolated lab below eventually will. Git reports exactly where it got stuck:

### Mechanical Walkthrough

- **`git rebase master`** — Explained in full above. - **`Auto-merging hello.py`** — Git's own label for attempting the automatic part of a three-way merge before discovering it can't finish. - **`CONFLICT (content): Merge conflict in hello.py`** — The identical message shape Lesson 0.4 produced from `git merge`, for the identical underlying reason: `0ba2c86`'s diff touches text close enough to where `master`'s independent change to line 2 already landed that git can't cleanly place both without asking. - **`hint: ... "git add/rm <conflicted_files>", then run "git rebase --continue"`** — This is the first concrete sign that finishing this conflict won't look like Lesson 0.4's ending. - **`git status`'s output** — Explained in full above. Its very first line, `interactive rebase in progress; onto ce52fbd`, is new vocabulary: git's rebase machinery is always driven by the same internal sequencer — a literal todo list of commits to pick, one per line — whether or not the `-i` flag was ever typed. - **`Last command done` / `Next command to do`** — Direct proof of the sequencer just named: git is tracking this rebase as a queue, currently paused after item 1 of 2, with item 2 still pending. Nothing about this queue is hidden — `git status` is reading it and printing it back verbatim.

Here, the label is a *specific commit's own SHA and message* — because rebase isn't merging in a branch as a unit, it's replaying one individual commit at a time, and this conflict belongs to exactly one of them, not to `add-goodbye-line` as a whole.

### CS Lens

**Rebase vs. merge** is the hard concept this whole lesson is built around, worth stating plainly and by name: both commands solve the identical underlying problem — "bring another branch's work into mine" — but they choose opposite answers to what the resulting history should *say happened*. `git merge` (Lessons 0.3–0.4) preserves both realities exactly as they occurred, forking and rejoining, at the cost of a merge commit recording that a decision had to be made. `git rebase` discards the fact that the two branches ever diverged at all — it rewrites one side's story as a straight line starting from wherever the other side currently is, at the cost of every replayed commit becoming a brand-new object, unrelated, as far as git's own bookkeeping is concerned, to the commit it replaced.

Also recognized in: database migration tools that let you replay a set of pending changesets against wherever the schema currently stands rather than merging schema branches; event-sourcing systems that rebuild current state by replaying a log of events in order; CPU speculative execution reissuing instructions after discovering a branch prediction was wrong, discarding the wrongly-speculated results and recomputing from the correct point; other version-control systems (Mercurial's `histedit`, Fossil's `amend`) that offer this same replay-vs-merge choice under different names.

### SE Lens

The alternative not chosen here is simply merging `add-goodbye-line` into `master` as-is, the same way Lesson 0.4 merged `formal-goodbye` — accepting a second merge commit and moving on. The tradeoff is real and has a name in wide use: the **golden rule of rebase** — never rebase commits that have already been shared with anyone else. Rebasing replaces commits with new ones that share no identity with the originals; if another person had already pulled `0ba2c86` and `b73b07f` before this rebase ran, their copy of history would now permanently disagree with this one, and reconciling the two would be far more painful than the merge commit this rebase avoided. `add-goodbye-line` is safe to rebase specifically because it's local-only — nothing has ever pushed it anywhere, a fact this lesson is relying on rather than proving, since Phase 0 hasn't introduced a remote yet. The benefit being bought here — a history readable as one straight line instead of a fork — becomes directly useful in Lesson 0.6, where finding a bug means walking backward through history one commit at a time; a straight line is unambiguous to walk, a history full of merge commits is not.

- **`git add hello.py`** — Explained in full above. Stages the resolved content and clears `hello.py`'s unmerged flag, identical to Lesson 0.4's own resolution step.
- **`git rebase --continue`** — Explained in full above. First, it takes the currently-staged content and wraps it in a brand-new commit — `[detached HEAD 40fa2c0] Add a French goodbye`. Note **`detached HEAD`**, defined above, appearing directly in git's own output: this new commit doesn't belong to `add-goodbye-line` yet, or to any branch — it's provisional, exactly as the term describes. The message `Add a French goodbye` is preserved from the *original* commit, `0ba2c86` — `git rebase --continue` reuses the paused commit's author and message; only its parent and its resulting tree change.
- **`Rebasing (2/2)Successfully rebased and updated refs/heads/add-goodbye-line.`** — After finishing the paused commit, `git rebase --continue` didn't stop — it moved straight on to the second queued commit, `b73b07f` ("Add a German goodbye"), attempted it, and this time it applied with no conflict at all: its own change (adding a fourth line) doesn't touch line 2, the region that conflicted the first time, so the three-way merge here has nothing to argue about. - **The final `git log --graph --all`** — Explained in full above. Compare this to Setting Up's own graph: there, `add-goodbye-line`'s two commits sat on a separate line, forked from `5ee4c4f`, never touching `master`'s line at all. Here, there is exactly one line, start to finish, with `add-goodbye-line`'s two commits sitting directly on top of `master`'s own tip. This is a **linear history** — every commit shown has exactly one parent, and there is no merge commit anywhere in this graph, unlike Lesson 0.4's `e4a118e`, which still sits partway down this same log with its own two parents intact.

**Why history changes — direct proof, not just a description.** The claim that `40fa2c0` is a genuinely different commit from `0ba2c86` — not the same commit relocated — is exactly the kind of hidden-behavior claim that needs verification, not a confident sentence. Both objects still exist in git's own object store and can be read directly:

```

parent 5ee4c4f9865235267f56166caa2b2060276059d6
author Learner <learner@example.com> 1787413326 -0400

$ git cat-file -p 40fa2c0
tree 7507f8b86d7f828294f59fd855bc4dfb0f3a24e8
parent ce52fbdf126db13683e5a47ce8a497732c50ddf5
author Learner <learner@example.com> 1787413326 -0400
committer Learner <learner@example.com> 1787413350 -0400

Add a French goodbye
```

The message is byte-for-byte identical: `Add a French goodbye`. The author line — who originally wrote the change, and when — is identical too, because `git rebase --continue` deliberately preserves it. But the **`parent`** field is completely different (`5ee4c4f...` versus `ce52fbdf...`), matching exactly what changed: the old commit's parent was `add-goodbye-line`'s stale starting point, the new commit's parent is `master`'s current tip. The **`tree`** field — the actual snapshot of every file's content at this commit — is also different, because the resolved content (`master`'s line 2 plus the new French line) differs from what the original, unresolved commit tried to apply. And the **`committer`** timestamp is later than the **`author`** timestamp on the new commit specifically, while they matched exactly on the old one — proof that this commit was *created* just now, during this rebase, even though it claims the same original authorship.

Git identifies every commit by hashing this exact object content — tree, parent, author, committer, message, all of it. Change any one field, and the hash is completely different, unrelated-looking, even when the message is word-for-word the same. This is why "rebase creates new commits" isn't a metaphor: `0ba2c86` and `40fa2c0` are two distinct objects, permanently, both sitting in git's object store right now — one simply isn't reachable from any branch anymore.

Not a new algorithm from the previous unit's three-way merge — `--continue` is the same replay mechanism, resumed. Resolving costs the one extra step of actually looking at both sides and deciding, in exchange for keeping the work and actually finishing what the rebase was for.

The second commit, `"Add a German goodbye,"` replayed right behind it with no conflict at all, since nothing about it touched the region that had just been contested.

What came out the other side was a straight line: `add-goodbye-line`'s tip now sat directly on top of `master`'s, with `master`'s old tip as a direct ancestor — the one condition a fast-forward has always needed, engineered on purpose rather than arrived at by accident. `git merge add-goodbye-line` moved `master`'s pointer forward with no new commit at all; `git branch -d` removed the now-redundant name; and `python hello.py`, run for real, printed `"Au revoir!"` exactly where it belonged — the fourth line of a file whose history now reads as if it had never diverged, even though, for two commits and one real conflict, it genuinely had.
