# Lesson 0.3: The Two Lines of History Rejoin

**What you will build** — `master` and `add-goodbye-line`, the two branches
Lesson 0.2 deliberately kept apart, combined back into one: `master`
gaining `add-goodbye-line`'s commit, in the cheapest way git can possibly
do that. The working feature is small on purpose, same as every lesson in
this phase: one command, one branch pointer moved. The transferable
problem this lesson is actually about is bigger than that one command:
given two branches that both trace back to a shared point, how does git
decide whether combining them can be as simple as moving a pointer
forward, versus requiring git to build something genuinely new — and what
exactly does that decision depend on?

**What you need to know first** — Lesson 0.1 (repository, working tree,
staging area, commit, root commit, commit hash, meaningful commit message,
`git init`/`status`/`add`/`commit`/`log`) and Lesson 0.2 (branch, HEAD,
`git switch`, isolated work, `git branch`), specifically the exact state
Lesson 0.2 left `code/00-git-workflow/` in: `master` holding one commit
(`b63f93074bd274e384f5d1bb4f3a01f3ecb141a7`, `hello.py` one line) and
`add-goodbye-line` holding two (`b63f930` and, one further,
`5ee4c4f9865235267f56166caa2b2060276059d6`, `hello.py` two lines),
currently checked out on `master`.

**Terms used in this lesson**

- **Merge base (common ancestor)** — the most recent commit that two
  branches both descend from: the exact point where their histories split
  apart. It exists because combining two branches requires a starting
  point to measure each one's changes *against* — without knowing where
  they last agreed, there's no way to tell what either branch actually
  added on its own, only what each currently contains in total.
- **Fast-forward** — the specific outcome `git merge` produces when the
  branch being merged into hasn't moved since the branch being merged in
  last diverged from it — meaning the current branch's own tip is an
  ancestor of the incoming branch's tip. In that exact case, git doesn't
  need to combine anything at all: it can simply move the current branch's
  pointer forward to match. It exists as a distinct, *named* outcome
  because it's the cheapest thing `git merge` can possibly do, and git
  says so explicitly in its own output, so whoever ran the command knows
  precisely which of two possible outcomes just happened.
- **Merge commit** — the other outcome, produced when the current branch's
  tip is *not* an ancestor of the incoming branch — meaning both branches
  gained commits of their own since they last agreed. A fast-forward is
  impossible here: moving the pointer to match the incoming branch would
  silently throw away whatever the current branch had gained on its own.
  Instead git builds a brand-new commit with **two** parents — one
  pointing at each branch's previous tip — permanently recording that this
  specific combination happened.
- **Merge strategy** — the specific algorithm git uses internally to
  decide how to combine two divergent branches' changes into one when
  building a merge commit. It exists as a named, swappable concept
  because "combine these two sets of changes automatically" is a real
  algorithmic problem with more than one possible solution; git names
  whichever one it used directly in its own output rather than treating
  the combination as an unexplained black box. This lesson's own real run
  used **`ort`** — Ostensibly Recursive's Twin, git's current default
  strategy, and the direct successor to an older one named `recursive`.
- **DAG (directed acyclic graph)** — a graph whose connections each point
  in one direction, arranged so that following those directions can never
  lead back to a starting point. It exists as the precise name for the
  shape a repository's commit history actually has: every commit points
  backward at its own parent (or, starting with this lesson, parents), and
  no chain of those backward-pointing links can ever loop back on itself.
- **Branch** *(reappearing from Lesson 0.2, full treatment)* — a movable,
  named pointer to a specific commit, not a copy of any files. It exists
  so a repository can hold more than one independent line of work at
  once, each pointing at its own tip commit. This lesson is about exactly
  two of them, `master` and `add-goodbye-line`, becoming one again.
- **HEAD** *(reappearing)* — git's record of which branch is currently
  checked out, the thing that actually moves when a branch is switched.
  It matters here because `git merge` always merges *into* whichever
  branch HEAD currently points at — the same branch every command in this
  lesson reports as `On branch master`.
- **Isolated work** *(reappearing)* — the engineering idea Lesson 0.2
  proved directly: a commit made on one branch changes only that branch's
  own pointer, leaving every other branch's history completely unaffected
  until something later deliberately combines them. This lesson is that
  deliberate combination — the direct payoff of everything Lesson 0.2 set
  up and proved.
- **Line-ending conversion (LF / CRLF)** *(reappearing from Lessons 0.1 and
  0.2)* — LF (a single `\n` character) is the line ending git's own stored
  objects always use internally; CRLF (the two characters `\r\n`) is what
  Windows text editors and tools typically write to disk. This lesson's
  own lab reproduces the same warning again, on files being staged for the
  very first time in a fresh scratch repository.

**Objects and methods used**

- **`git merge`**
  - *What it is:* The command that combines another branch's history into
    the branch currently checked out.
  - *Implementation:* `git merge <branch>` — merges `<branch>` into
    whichever branch HEAD currently points at. Its behavior forks into
    exactly two shapes depending on the two branches' merge base: if the
    current branch's tip is an ancestor of `<branch>`'s tip, it
    fast-forwards, printing `Updating <old-hash>..<new-hash>` followed by
    `Fast-forward` and a one-line summary of what changed; otherwise it
    constructs a new commit with two parents, printing `Merge made by the
    '<strategy>' strategy.` followed by that same one-line summary, and —
    unless told otherwise with `-m` or
    `--no-edit` — opens a text editor for that new commit's message.
  - *Its use:* This lesson's central action — the one command that takes
    two branches Lesson 0.2 deliberately kept apart and actually combines
    them, in both of the distinct ways this lesson exists to show.
  - *Type:* A subcommand of `git`, exactly like `git init`, `git status`,
    `git add`, `git commit`, `git log`, `git branch`, and `git switch`
    before it — a standalone CLI executable, not a class or object
    system.
  - *Responsibility:* Given a target branch name, determine that branch's
    relationship to the current one by computing their merge base, and
    then either move the current branch's pointer forward (a fast-forward)
    or construct an entirely new commit recording both histories (a merge
    commit) — whichever the merge base makes correct — updating the
    working tree to match the result either way.
  - *Depends on:* An already-initialized repository; the named branch
    already existing; the working tree having no uncommitted changes that
    would be overwritten by the merge's result.
  - *Connects to:* Reads both branches' entire commit history (via their
    recorded parent pointers) to compute their merge base; writes either a
    moved branch pointer or a brand-new commit object — the same kind of
    object `git commit` writes, except this one can record two parents
    instead of one. Every `git log` call run afterward reflects whichever
    outcome it produced.
  - *Shape:* The actual recombination boundary this entire lesson exists
    to reach — the direct counterpart to Lesson 0.2's `git branch` and
    `git switch`, which only ever pulled history apart. This is the first
    command in the curriculum that brings two separated lines back
    together.

**Everything else in the file, not this lesson's subject but still
explained**

- **`git status`**
  - *What it is:* A read-only inspection command that reports the current
    relationship between the working tree, the staging area, and the most
    recent commit.
  - *Implementation:* `git status`, with no required arguments. It prints
    the current branch name (read from HEAD), then either `nothing to
    commit, working tree clean` or a list of files under headings
    depending on what it finds.
  - *Its use:* Run at the very start of this lesson's real-project unit,
    to make visible, before merging anything, that `master` really is
    exactly where Lesson 0.2 left it — clean, with nothing uncommitted
    that a merge could conflict with.
  - *Type:* A subcommand of `git`; a read-only query, never a mutation.
  - *Responsibility:* Compare the working tree's actual files, whatever is
    currently staged, and the most recent commit against each other, and
    report every difference found.
  - *Depends on:* An already-initialized repository; reads the working
    tree's files, the staging area's contents, and HEAD's current branch.
  - *Connects to:* Called here before `git merge`, specifically to confirm
    the working tree is clean — a real precondition `git merge` itself
    depends on. Nothing downstream reads its output.
  - *Shape:* A diagnostic tool sitting outside the actual commit history,
    unchanged from Lessons 0.1 and 0.2 — running it never changes anything
    `git log` will later show.
- **`git add`**
  - *What it is:* The command that copies a change from the working tree
    into the staging area.
  - *Implementation:* `git add <pathspec>...` — this lesson's lab calls it
    as `git add master-notes.txt`, the same single-file form every prior
    lesson used.
  - *Its use:* This lesson's bridge, inside the isolated lab, between "a
    new file exists on disk" and "the next commit will actually include
    it" — the exact step needed to manufacture a real, independent commit
    on the lab's own `master`.
  - *Type:* A subcommand of `git`; a mutating command — it changes the
    staging area's contents, never the working tree's files or the
    repository's committed history.
  - *Responsibility:* Copy the current content of exactly the file(s)
    named into the staging area, replacing whatever that area held for
    those specific files before.
  - *Depends on:* The working tree's current file content for whatever
    pathspec is given; an already-initialized repository.
  - *Connects to:* Reads from the working tree; writes into the staging
    area that `git commit`, next, reads from.
  - *Shape:* The boundary between "editing files" and "building a commit,"
    identical to its role in every prior lesson — reused here specifically
    to build the commit that will make this lesson's second branch
    genuinely diverge.
- **`git commit`**
  - *What it is:* The command that permanently records whatever is
    currently staged as a new, addressable snapshot in the repository's
    history.
  - *Implementation:* `git commit -m "<message>"`. Every commit this
    lesson's lab makes is a non-root commit, so its success output starts
    `[<branch> <hash>]`, without the `(root-commit)` marker — each one has
    a parent to link back to.
  - *Its use:* The step that turns `master-notes.txt`'s existence in the
    lab's working tree into a real, permanent commit on the lab's
    `master` — the exact commit that makes `master` diverge from the
    feature branch instead of staying still.
  - *Type:* A subcommand of `git`; a mutating command that writes into the
    repository's *permanent* history, rather than the staging area or the
    working tree.
  - *Responsibility:* Take exactly what's currently staged, package it
    together with the message, an author, a timestamp, and a reference to
    the branch's current tip as this new commit's parent, compute the new
    commit's content-derived hash, and move the current branch's pointer
    forward to it.
  - *Depends on:* Something actually staged; a configured author name and
    email; the message text supplied via `-m`.
  - *Connects to:* Reads from the staging area `git add` just filled;
    writes a new entry `git log` can then display; moves the current
    branch's pointer forward — in this lesson's lab, specifically
    `master`'s own pointer, independently of whatever `add-third-line`'s
    pointer is doing.
  - *Shape:* The actual history-creation boundary, unchanged from every
    prior lesson — what's different here is *why* it's being run: not to
    build ordinary progress, but to deliberately manufacture the exact
    divergence this lesson's second unit needs to demonstrate.
- **`git log`**
  - *What it is:* A read-only command that prints the commit history
    reachable from the currently checked-out branch's tip, most recent
    commit first.
  - *Implementation:* `git log`, with no required arguments. For each
    commit it finds by walking backward through recorded parents, it
    prints the full hash, author, date, and message — and, new in this
    lesson's real output, a `Merge:` line naming **both** parent hashes
    for any commit that has two.
  - *Its use:* Run after every merge in this lesson, as direct,
    independent proof of exactly what each merge actually produced: an
    unchanged commit count for a fast-forward, or one brand-new commit
    with two recorded parents for a merge commit.
  - *Type:* A subcommand of `git`; read-only, exactly like `git status`.
  - *Responsibility:* Starting from whatever branch HEAD currently points
    at, walk backward through each commit's recorded parent (or, for a
    merge commit, both recorded parents), and print every commit's
    metadata along the way, newest first.
  - *Depends on:* At least one commit reachable from the current branch;
    HEAD, to know which branch's history to walk.
  - *Connects to:* Reads whatever `git commit` or `git merge` most
    recently wrote on the current branch. This lesson is the first place
    its own output can show a commit with more than one parent.
  - *Shape:* The read side of the repository's permanent history — in this
    lesson specifically, the tool that turns "a merge happened" from a
    claim into something independently checkable.
- **`cat`**
  - *What it is:* A standard Unix command, available here through Git
    Bash, that prints a file's entire contents to standard output.
  - *Implementation:* `cat <file>` — called in this lesson as `cat
    hello.py`, `cat .git/refs/heads/master`, `cat lab.txt`, and `cat
    master-notes.txt`, each with no flags.
  - *Its use:* This lesson's concrete, independent proof, run repeatedly:
    not "git says the merge worked," but the literal file content and the
    literal branch-pointer file, read directly, showing exactly what each
    merge actually left behind.
  - *Type:* A standalone external program, entirely unrelated to git.
  - *Responsibility:* Read the named file's entire contents and write them,
    unmodified, to standard output — nothing else; no awareness of git,
    branches, or version control at all.
  - *Depends on:* The file named existing, readable, at the given path.
  - *Connects to:* Reads whatever `git merge` (or, for the `refs/heads`
    files, git's own internal bookkeeping) most recently left on disk —
    the tool this lesson keeps reaching for specifically because it reads
    independently of anything git itself reports.
  - *Shape:* A verification tool sitting entirely outside git, included
    here for the same reason it mattered in Lessons 0.1 and 0.2: proof,
    not a repeated claim from the same system being tested.

## Concept Unit: The Merge

### The Problem

Right now, `code/00-git-workflow/` has exactly the state Lesson 0.2 left
it in: `master` holds one commit, `add-goodbye-line` holds two — the same
one `master` has, plus one more. Lesson 0.2 spent its entire third unit
proving those two branches are genuinely isolated: a commit made on
`add-goodbye-line` changed nothing about `master`. That isolation was the
point *then*. Now it's a problem: the second line in `hello.py` is real,
finished work, sitting on a branch that `master` — the project's actual
main line — still knows nothing about. Isolation was supposed to be
temporary, a safe place to make the change; nothing yet has actually
brought it back.

*Pause and try:* Lesson 0.2 proved a commit made on `add-goodbye-line`
never touched `master` — so right now, `add-goodbye-line`'s own history
includes everything `master` has, plus exactly one more commit on top.
Given that, if you were git and someone asked you to make `master` reflect
`add-goodbye-line`'s work, would you actually need to build anything new,
or could you get away with just changing where `master`'s pointer points?
What's the absolute cheapest thing git could do here that would still
leave `master` reflecting both commits? And if that shortcut has a name,
what do you think it might be called?

### CS Lens

A fast-forward is a specific case of **convergence requiring no actual
reconciliation**: when two things that were tracking the same underlying
sequence never actually disagreed — one simply stopped advancing while
the other kept going — bringing them back in sync needs nothing more than
letting the one that stopped catch up.

```
Also recognized in: a database read replica advancing its replayed log
position when it hasn't fallen behind in any conflicting way, a CDN edge
node adopting a newer cached version when there's exactly one valid
successor, a package lockfile bumping to a newer pinned commit when
nothing else competes for that same slot, a state machine advancing along
the one single transition its current state actually defines
```

Every one of those systems reaches the same shortcut for the same reason:
when there was never more than one valid "next" state to reach, arriving
at it is just movement, not negotiation.

### SE Lens

The alternative git did not choose here, as the *default*: always
creating a merge commit, even when a fast-forward is possible — a real,
existing option, invoked as `git merge --no-ff`, not used by this lesson.
`--no-ff`'s real benefit: the permanent history would then always show
that `add-goodbye-line` existed as its own branch, even after being
merged — a fact a fast-forward, by design, throws away. Once this unit's
merge finishes, `git log` on `master` looks exactly as if
`"Goodbye, for now."` had been committed directly on `master` all along;
nothing in that history says a separate branch was ever involved. The
real cost of the alternative: `--no-ff` would add a merge commit — and
therefore a small branch and rejoin in the history graph — even for cases
exactly like this one, where nothing actually needed reconciling. Git's
default keeps history as simple as possible whenever nothing does, at the
cost of losing the "a branch happened here" marker once it's merged. This
project is not carrying any debt from that choice yet — nothing so far
has depended on being able to tell, after the fact, that
`add-goodbye-line` once existed as its own branch.

### Commands Needed

- **`git merge`** — used here with one argument, the branch name, no

  then `Fast-forward`, then a one-line summary of what changed. Failure
  (not encountered
  in this lesson's real run) would occur if the named branch doesn't

## Concept Unit: The Merge Commit

### The Problem

The previous unit's merge only worked as a simple pointer-move because
`master` had not gained any commits of its own since `add-goodbye-line`
branched off — `master`'s own tip was already an ancestor of
`add-goodbye-line`'s tip, which is exactly what let git skip building
anything. That precondition won't always hold. If `master` had gained its
own, independent commit before the merge — something with no relationship
to `add-goodbye-line`'s work at all — would `git merge` still be able to
just move a pointer forward? And if it can't, what does it have to build
instead?

*Pause and try:* Suppose `master` gained a brand-new commit, completely
unrelated to anything on a feature branch, before that feature branch got
merged in. Could git still just move `master`'s pointer forward to match
the feature branch's tip? If it did, what would happen to `master`'s own
new commit — would it survive, or would moving the pointer past it lose
it? Given that both branches would then hold a commit the other doesn't
have, what do you think would have to exist, that didn't exist a moment
before, for both of those commits to end up recorded together afterward?

### Project Change

- **Reference Source:** No reference counterpart — from-scratch, same as
  every unit in this Git phase.

- **`git commit -m "Add master-only note"`** — given full treatment above

  `[master 268ebfc]` names the branch that moved and the new commit's

  `add-third-line` has no idea it exists.
- **`git merge add-third-line`** — given full treatment above under
  Objects and methods used, in this call reaching its *other* possible
  outcome: the merge base of `master` (now at `268ebfc`) and
  `add-third-line` (at `7ff2403`) is `52dd03e` — the commit both branched
  from — and neither branch's tip is an ancestor of the other's. A
  fast-forward is impossible; git has to build something new.
- **`--no-edit`** — a flag on `git merge`, new in this lesson: it tells
  git to accept the automatically-generated merge commit message (`Merge
  branch 'add-third-line'`) without opening a text editor to let the
  message be rewritten. `git merge` only opens an editor at all when it's
  about to create a genuine merge commit — never for a fast-forward, which
  is exactly why the previous unit's merge never needed this flag. A
  script running commands non-interactively, as this lesson's lab does,
  has no editor to open at all; `--no-edit` sidesteps that entirely by
  accepting the default message outright, rather than the command
  stalling with nothing to interact with.

Real output of the merge itself:

```
$ git merge add-third-line --no-edit
Merge made by the 'ort' strategy.
 lab.txt | 1 +
 1 file changed, 1 insertion(+)
```

`Merge made by the '<strategy>' strategy.` replaces the previous unit's
`Fast-forward` line entirely — a different sentence, for a genuinely
different outcome. `ort` is the name of the specific algorithm git used
to combine the two branches' changes — Git's current default merge
strategy, and the direct successor to an older one named `recursive`.
Naming it here matters for the same reason `Fast-forward` was named
explicitly: this is a real decision git made, inspectable and nameable,
not an unexplained "it just merged."

### CS Lens

A merge commit is a specific case of a **join point in a directed
acyclic graph**: a single node with more than one incoming edge, sitting
at the exact place where two independently-progressing paths reconverge
into one. Until this unit, every commit in this curriculum's history had
exactly one parent — a straight line. `ed028a0` is the first node in this
project's history with two, the first point where that history stopped
being a line and became a real **DAG**.

```
Also recognized in: a build system's fan-in step that waits on several
independent upstream tasks before proceeding, a distributed database's
multi-master replication reconciling two independently-written histories,
a spreadsheet's data-consolidation step combining two independently-edited
copies, a project-management tool's dependency chart showing one task that
can't start until several unrelated ones finish
```

Every one of those systems needs the same thing a merge commit provides:
a single point that can honestly say "this depended on more than one
thing," rather than forcing a multi-parent reality into a structure that
can only ever record one predecessor at a time.

### SE Lens

The alternative git did not choose here, as the default: refusing to
merge at all unless a fast-forward is possible, forcing every divergent
branch to be rebased first — a real, existing option, invoked as `git
merge --ff-only`, which would have made this exact command fail outright
rather than build a merge commit. `git rebase`, the tool that would then
be needed to make a fast-forward possible again, isn't covered until
Lesson 0.5. Its real benefit: history would always stay a perfectly
straight line, exactly like the previous unit's, with no branching or
rejoining ever visible in `git log` at all. Its real cost: rebasing
rewrites a branch's own commits — computing new hashes for content that
already had permanent ones — which becomes a genuinely serious problem
the moment a branch has been shared with anyone else (a topic this
curriculum hasn't reached yet, but real all the same). Git's actual
default — permitting merge commits — never has to touch `add-third-line`'s
own commits at all; `7ff2403` above is the exact same hash it always was,
untouched by the merge that combined it with `master`. The cost of that
choice is a history graph that branches and rejoins instead of reading as
one flat line — precisely the shape `git log`'s own `Merge:` line just
made visible and inspectable, not hidden.

### Connect to What Came Before

The previous unit's merge only had to move a pointer because `master`
never gained a commit of its own. This unit answered the question that
unit's own closing line left open: what happens when it does. The answer
was git's other outcome — a merge commit, with two recorded parents,
combining both branches' independent work into one without discarding
either. Together, these two units are `git merge`'s entire behavior: one
command, one decision (is the current branch's tip an ancestor of the
incoming branch's?), and exactly two possible results.

## Connect the Pieces

Trace `master`'s own pointer and `hello.py`'s content through this
lesson's real unit, then the lab's contrasting one, start to finish:

1. Before this lesson, `master` held one commit (`b63f930`) and
   `add-goodbye-line` held two (`b63f930`, then `5ee4c4f`) — exactly the

2. `git merge add-goodbye-line`, run on `master`, computed the two

   path: it moved `master`'s pointer forward to `5ee4c4f` without
   creating anything new. `.git/refs/heads/master`, read directly, now
   holds the exact same hash `add-goodbye-line`'s own pointer file already
   held.
3. `cat hello.py` and `git log`, both run on `master`, confirmed the
   result independently of git's own merge message: both lines, both
   commits, identical to what `add-goodbye-line` already had. This is a
   **fast-forward** — proven, not asserted, by the fact that nothing new
   was ever created.
4. The following unit asked what would happen if `master` had *not*
   stayed still, and answered it entirely inside the disposable
   `_lab_scratch/`: a commit manufactured directly on the lab's `master`,
   independent of anything on a feature branch, made a fast-forward
   impossible. `git merge`'s other outcome followed: a **merge commit**,
   `ed028a0`, recording two parents at once — the first commit in this
   entire curriculum with more than one, and the first point this
   project's history stopped being a straight line and became a real

One repository proving the cheap case, one disposable lab proving the
expensive one. Together: `git merge`'s complete behavior, both outcomes it
can produce, and exactly what decides which one happens — the merge
base, and whether either branch moved past it alone. Lesson 0.4's
conflict is what happens when a merge commit's automatic combination
*can't* resolve cleanly — when both branches changed the exact same

`add-third-line`'s own edit to `lab.txt` deliberately avoided this
lesson. Lesson 0.5's rebase, and Lesson 0.6's `git bisect`, both depend on
exactly this same commit-and-parent structure — now, for the first time,
