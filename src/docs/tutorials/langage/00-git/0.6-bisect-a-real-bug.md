# Lesson 0.6: Binary Search Through History

**Build:** Bisect a Real Bug

## What you will build

Several ordinary-looking commits land on `master` in `code/00-git-workflow/`
— a small refactor and a few new lines added to `hello.py` — and somewhere
in the middle of them, unnoticed at the time, one commit breaks the script.
By the time anyone runs `hello.py` again, it crashes, and nothing about the
crash says which of the several intervening commits caused it. You'll use
`git bisect` to answer that question by testing a handful of commits instead
of reading every diff by eye, then read the guilty commit as evidence to
understand and fix it. The transferable problem underneath the git mechanics
is **binary search**: a general strategy for finding one boundary inside an
ordered sequence by repeatedly checking the middle of whatever range is
still uncertain, applicable to a sorted array, a phone book, or — as this
lesson shows — a sequence of commits.

## Terms used in this lesson

- **regression** — a bug that appears in code that previously worked
  correctly, introduced by some later change rather than present from the
  very start. Naming it matters because it reframes the debugging question:
  not "what's wrong with this code" but "what changed since it last
  worked" — exactly the question `git bisect` exists to answer mechanically
  instead of by memory or guesswork.
- **index assignment** — the syntax `sequence[i] = value`, which replaces
  whatever element is currently stored at position `i` in an existing
  sequence. It requires position `i` to already exist; Python's list
  assignment is defined as "overwrite an existing slot," never "extend the
  list to make room," which is exactly the gap this lesson's bug falls
  into.
- **`IndexError`** — Python's built-in exception, raised when code tries to
  read or assign a sequence index outside that sequence's current valid
  range (`0` through `len(sequence) - 1`). It exists so that reaching past
  the end of a list fails immediately and loudly, at the exact line
  responsible, instead of silently doing something the programmer didn't
  intend.
- **traceback** — the report Python prints when an exception propagates all
  the way up without being caught anywhere: the chain of source lines that
  were executing at the moment of failure, ending with the exception's type
  and message. It exists so a crash points directly at its own cause
  instead of leaving a reader to guess where things went wrong.
- **exit code** — the integer a program hands back to whatever launched it
  when it finishes running. By convention, `0` means "finished
  successfully" and any nonzero value means "something went wrong." This
  lesson depends on it directly: it's what turns "does this version of the
  script work?" from a judgment call into a fact a tool — or a person
  running one command — can check without reading any output at all.
- **binary search** — a strategy for finding one specific boundary inside
  an ordered sequence by repeatedly checking the middle of whatever range
  is still uncertain, then discarding the half that cannot contain the
  answer, rather than checking every element in order from the start. It
  exists because checking one midpoint eliminates half of the remaining
  possibilities in a single step, so the number of checks needed grows far
  more slowly than the size of the thing being searched.
- **bisectable (history)** — a property a sequence of commits has when
  "good" and "bad" don't interleave arbitrarily: every commit before the
  bug is good, every commit from the bug onward is bad, with no good
  commits reappearing later in between. Binary search is only a valid way
  to search a sequence that has exactly one such boundary; a history where
  the bug randomly appears and disappears across unrelated commits has no
  single boundary for the halving to converge on, and bisecting it would
  give a wrong or meaningless answer.
- **commit** *(reappearing from Lesson 0.1)* — a saved, permanent snapshot
  of the project's entire tracked state at one moment, identified by its
  own hash, carrying a message describing what changed and why. This
  lesson depends on commits being genuinely separable, individually
  testable units, because `git bisect` treats each one as a single yes/no
  data point — "does the project work at exactly this snapshot" — never
  looking at any partial state in between two commits.
- **commit hash (SHA)** *(reappearing)* — the long hexadecimal identifier
  git computes from a commit's own content (its snapshot, message, parent,
  author, and timestamp), used to name that exact commit unambiguously.
  This lesson uses real ones — `d4a36eb`, `ceceb58`, and others — as the
  literal arguments handed to `git bisect good` and `git bisect bad`, and
  as the identifier `git bisect` itself ultimately reports as the culprit.
- **working tree** *(reappearing)* — the actual files on disk in the
  project directory, exactly as they currently exist; the place edits
  happen before anything is staged or committed. Every commit `git bisect`
  checks out for testing changes nothing but the working tree — commit
  history itself is never touched — which is exactly what makes testing
  each candidate commit safe to do over and over.
- **staging area (the index)** *(reappearing)* — git's holding area
  between the working tree and a commit. `git add` copies a file's current
  content into it, and `git commit` snapshots whatever the staging area
  currently holds, never a live view of whatever the working tree happens
  to contain at commit time. This distinction is why staging and
  committing are two separate steps rather than one.
- **`HEAD`** *(reappearing)* — git's name for "the commit currently
  checked out." `git bisect bad` with no argument marks `HEAD`; every
  commit `git bisect` checks out during its search moves what `HEAD`
  points to, without moving any branch pointer, which is why the search
  can hop between arbitrary commits without disturbing `master` itself.
- **checkout** *(reappearing)* — the act of updating the working tree to
  match a specific commit or branch, and moving `HEAD` to point there.
  Every commit `git bisect` selects to test gets checked out this same way
  — the identical mechanism `git checkout` performs directly, just invoked
  automatically by `git bisect` on a commit it computed, rather than one a
  person named by hand.
- **branch** *(reappearing)* — a movable, named pointer to a commit — most
  relevantly here, `master`, which stays pointing at the same commit
  throughout this entire lesson's bisect search. `git bisect`'s repeated
  checkouts move `HEAD` alone, never `master` itself, which is exactly why
  bisecting doesn't disturb ordinary branch-based work in progress.
- **parent (commit)** *(reappearing)* — the commit a given commit was
  created on top of; each commit's own parent link is what lets git
  reconstruct history as an ordered chain of snapshots rather than an
  unordered pile of them. `git show`'s diff output and `git commit`'s own
  snapshot are both defined relative to exactly this link.

## Objects and methods used

- **`list.append(x)`**
  - *What it is:* A built-in method on Python's `list` type — the ordinary
    way to grow a list by one element without touching any element already
    in it.
  - *Implementation:* `list.append(object) -> None` — an instance method,
    called as `some_list.append(value)`; mutates `some_list` in place and
    always returns `None`.
  - *Its use:* This lesson's eventual fix calls
    `goodbyes.append("Sayonara!")` to add the missing goodbye correctly,
    replacing the index-assignment line that caused the crash.
  - *Type:* An instance method defined on the built-in `list` class.
  - *Responsibility:* Extend the list by exactly one element, placed
    immediately after whatever the current last element is, regardless of
    how many elements the list already holds.
  - *Depends on:* The list instance it's called on, and the one value being
    added.
  - *Connects to:* Called directly by this lesson's fixed `hello.py`;
    internally, CPython's own list implementation may reallocate its
    backing array to make room, but nothing in this lesson's code observes
    that detail directly.
  - *Shape:* A public method on a standard-library built-in type — the
    outermost, most stable kind of API surface Python offers.

- **`git bisect start`**
  - *What it is:* The git subcommand that begins a bisect session — it puts
    the repository into a special "bisecting" state and prepares to receive
    good/bad judgments.
  - *Implementation:* `git bisect start [<bad> [<good>...]]` — invoked with
    no arguments in this lesson; git records that a bisect session is now
    active.
  - *Its use:* The first command run to begin locating the commit that
    broke `hello.py`.
  - *Type:* A git subcommand — one mode of the `git bisect` command family.
  - *Responsibility:* Initialize bisect's internal state — an empty set of
    known-good and known-bad commits — and record which branch or commit
    the repository was on before starting, so `git bisect reset` can return
    there later.
  - *Depends on:* A git repository with commit history to search; nothing
    else at this point.
  - *Connects to:* Every subsequent `git bisect good`/`git bisect bad` in
    the same session adds to the state this command created; `git bisect
    reset` reads that same state to know where to return.
  - *Shape:* An entry point into a stateful, multi-command git workflow —
    not a single self-contained operation the way `git log` is.

- **`git bisect bad [<rev>]`**
  - *What it is:* Tells git that a specific commit — or, with no argument,
    whatever commit is currently checked out — fails the thing being
    tested.
  - *Implementation:* `git bisect bad [<rev>]` — with no `<rev>`, marks
    `HEAD`; with one, marks that commit instead.
  - *Its use:* First marks the repository's current tip as bad, since the
    crash is happening right now; later, marks a specific commit `git
    bisect` checked out for testing, once running `hello.py` there also
    crashes.
  - *Type:* A git subcommand — a mode of `git bisect`.
  - *Responsibility:* Record one commit as a known failing point, and, once
    at least one good commit is also known, trigger git to compute and
    check out the midpoint of the remaining uncertain range.
  - *Depends on:* An active bisect session, and either an explicit `<rev>`
    or a current checkout to use as the default.
  - *Connects to:* Feeds directly into git's own internal binary-search
    logic, which reads every recorded good/bad judgment to decide which
    commit to check out next.
  - *Shape:* One half of the two-sided input — `good`/`bad` — that drives
    bisect's search; a data point supplied by whoever is running the
    tests, not computed by git itself.

- **`git bisect good <rev>`**
  - *What it is:* Tells git that a specific commit passes the thing being
    tested — the mirror image of `git bisect bad`.
  - *Implementation:* `git bisect good [<rev>]` — same argument shape as
    `bad`.
  - *Its use:* First marks Lesson 0.5's known-working endpoint (`d4a36eb`)
    as the far boundary of the search; later, marks each checked-out commit
    that still runs `hello.py` cleanly.
  - *Type:* A git subcommand — a mode of `git bisect`.
  - *Responsibility:* Record one commit as a known-working point, and,
    combined with the recorded bad commit, narrow the range of commits git
    still needs to check.
  - *Depends on:* An active bisect session and a commit reference.
  - *Connects to:* The same internal search logic as `git bisect bad`;
    together, one `good` and one `bad` commit define the exact range binary
    search operates over.
  - *Shape:* The other half of the two-sided input driving bisect's search.

- **`git bisect reset`**
  - *What it is:* Ends the bisect session and returns the repository to the
    branch or commit it was on before `git bisect start`.
  - *Implementation:* `git bisect reset [<commit>]` — with no argument,
    returns to the pre-bisect position `git bisect start` recorded.
  - *Its use:* Run immediately after git announces the first bad commit, to
    leave the bisecting state and get back to `master` so the fix can be
    written and committed normally.
  - *Type:* A git subcommand — a mode of `git bisect`.
  - *Responsibility:* Discard bisect's internal state and check out
    whatever branch or commit was active before the session started.
  - *Depends on:* The "before" position `git bisect start` recorded.
  - *Connects to:* Closes the session opened by `git bisect start`; nothing
    after this point is still "inside" a bisect.
  - *Shape:* The symmetrical closing operation to `git bisect start` —
    every bisect session this lesson's workflow expects to end with one.

- **`git show <rev>`**
  - *What it is:* Displays a specific commit — its metadata (author, date,
    message) and the diff it introduced relative to its parent.
  - *Implementation:* `git show <rev>` — `<rev>` is any commit reference,
    including the hash `git bisect` just reported.
  - *Its use:* After bisect names `ceceb58` as the first bad commit, `git
    show ceceb58` is what actually reveals the one changed line
    (`goodbyes[5] = "Sayonara!"`) — the evidence the commit provides once
    you know which one to look at.
  - *Type:* A git subcommand.
  - *Responsibility:* Render one commit's full content — message plus diff
    — for a human to read, without changing the repository's checked-out
    state.
  - *Depends on:* A valid commit reference.
  - *Connects to:* Consumes the exact hash `git bisect`'s final "is the
    first bad commit" output supplies; produces the diff a person then
    reasons about to understand and fix the bug.
  - *Shape:* A read-only inspection command — the same category as `git
    log`, safe to run at any time with no effect on the working tree.

**Everything else in the file, not this lesson's subject but still
explained:**

- **`git add <path>`** *(reappearing)*
  - *What it is:* Stages a file's current content, marking it to be
    included in the next commit.
  - *Implementation:* `git add <path>` — copies the named file's current
    working-tree content into git's staging area (the index).
  - *Its use:* Run before every commit in this lesson's setup history,
    exactly as in every earlier lesson — staging `hello.py` or
    `CHANGELOG.md` before committing whatever changed.
  - *Type:* A git subcommand.
  - *Responsibility:* Copy a file's exact current content into the staging
    area, so the next commit captures precisely that version — no more, no
    less.
  - *Depends on:* A file that exists in the working tree.
  - *Connects to:* Feeds directly into `git commit`, which snapshots
    whatever is currently staged, not whatever the working tree happens to
    contain at commit time.
  - *Shape:* The staging boundary between "edited on disk" and "recorded in
    history."

- **`git commit -m "<message>"`** *(reappearing)*
  - *What it is:* Creates a new commit from whatever is currently staged,
    carrying the given message.
  - *Implementation:* `git commit -m <message>` — the `-m` flag supplies
    the commit message inline instead of opening an editor.
  - *Its use:* Used to create every one of this lesson's six new commits —
    the four setup commits, the unrelated changelog commit, and the final
    fix.
  - *Type:* A git subcommand.
  - *Responsibility:* Package the staging area's current content into a
    new, permanent, hash-identified snapshot, with the given message and
    the current commit as its parent.
  - *Depends on:* Staged content (via `git add`) and a message string.
  - *Connects to:* Produces exactly the kind of object `git bisect
    good`/`git bisect bad` will later judge, one at a time.
  - *Shape:* The actual history-writing operation — everything else in
    this lesson's workflow either reads history (`git show`, `git log`) or
    searches it (`git bisect`); this is what creates it.

- **`git log --oneline`** *(reappearing)*
  - *What it is:* Lists commits, most recent first, one line each — short
    hash plus subject line.
  - *Implementation:* `git log --oneline` — `--oneline` compresses each
    commit's normal multi-line display down to `<short-hash> <subject>`.
  - *Its use:* Used throughout this lesson's setup to confirm the real
    commit history after building it, and to locate the exact hash
    (`d4a36eb`) to hand to `git bisect good`.
  - *Type:* A git subcommand.
  - *Responsibility:* Render the commit graph as a compact, human-scannable
    list.
  - *Depends on:* Existing commit history.
  - *Connects to:* Supplies the hashes fed into `git bisect good`/`git
    bisect bad`, and the hash `git show` later inspects.
  - *Shape:* A read-only inspection command, the same category as `git
    show`.

## Concept Unit: The trap in list index assignment

### The Problem

Before building the buggy history, it's worth understanding the exact shape
the bug will take, because the shape of the bug is what makes bisecting it
useful in the first place — a bug that crashes immediately and
unambiguously is much easier to test for than a bug where "did that work?"
requires careful eyeballing. Python's `list` has two different ways to
attach a new element to it, and they behave differently at the boundary of
the list's current length.

Given a list `["red", "green", "blue"]` (three elements, valid indices `0`,
`1`, `2`): what would you *expect* `colors[3] = "yellow"` to do, based on
what you already know about how indexing works for reading a list element?
What about `colors.append("yellow")` — does it need to know the list's
current length at all? If you're not sure `colors[3] = "yellow"` is safe,
what's the actual worst case you'd guess could happen?

### The New Code

```python
colors = ["red", "green", "blue"]
colors.append("yellow")
print(colors)

colors[4] = "purple"
```

### Run it

```
$ python index_assignment_lab.py
['red', 'green', 'blue', 'yellow']
Traceback (most recent call last):
  File ".../index_assignment_lab.py", line 5, in <module>
    colors[4] = "purple"
    ~~~~~~^^^
IndexError: list assignment index out of range
```

`colors.append("yellow")` succeeded without needing to know the list's
current length — it grew the list from three elements to four, and printing
it confirms `['red', 'green', 'blue', 'yellow']`. `colors[4] = "purple"`
then failed immediately: after the append, `colors` has four elements, at
valid indices `0` through `3`. Index `4` is one past the last valid index,
and **`index assignment`** — the `sequence[i] = value` syntax — only ever
overwrites a slot that already exists; it never extends the sequence to
make room for a new one. Reaching for an index that doesn't exist yet
raises **`IndexError`**, Python's built-in exception for exactly this
situation, and the interpreter prints a **traceback**: the file, line
number, and the source line itself (`colors[4] = "purple"`, with `^^^`
marking the exact subexpression that failed), ending with the exception's
name and message. This proves the two operations are not interchangeable:
`append` always succeeds by growing the list to fit; index assignment only
ever succeeds when the target index already exists.

### Discard it

`index_assignment_lab.py` is deleted now that both behaviors are confirmed.
It never becomes part of `code/00-git-workflow/` — it existed only to prove,
in isolation, exactly what `colors[4] = "purple"` does and doesn't do,
before meeting the real bug below.

### Mechanical walkthrough

Enumerating the one new element on line 10, in order:

- `goodbyes` — a read of the same list built on lines 3–9, now holding five
  string elements at indices `0` through `4`.
- `[5]` — an index expression. Applied to a read (`goodbyes[5]` alone), this
  would raise `IndexError` for the same reason; applied here as the target
  of an assignment, it's **index assignment**, requiring position `5` to
  already hold a value it can overwrite.
- `=` — assignment. On its own, ordinary assignment; combined with the
  index expression to its left, it forms the specific `sequence[i] = value`
  shape that only ever replaces an existing slot.
- `"Sayonara!"` — a string literal, the value being assigned.

This is exactly the shape `index_assignment_lab.py` isolated a moment ago:
`colors[4] = "purple"` on a four-element list failed the same way, for the
same reason. Here the list has five elements (valid indices `0`–`4`), and
index `5` is one past the end — the same off-by-one gap, reached the same
way.

### CS lens

An off-by-one boundary error — code that's correct everywhere except
exactly at an edge, here "one past the last valid index" — is a genuinely
recurring category of bug, not specific to Python or to this script.

```
Also recognized in: fencepost errors in loop bounds ("for i in
range(n)" vs "range(n + 1)"), buffer overruns in C when a write
reaches one byte past an allocated block, off-by-one errors in
pagination logic (page * size vs (page - 1) * size), and array-
index-out-of-bounds crashes in nearly every language with fixed-
size or fixed-length sequences.
```

### SE lens

Python's design choice here — raising `IndexError` immediately rather than
silently growing the list to fit — is not the only reasonable choice a
language could make. JavaScript's arrays make the opposite choice:
`arr[4] = "x"` on a three-element array silently grows the array to length
five, leaving the gap in between as empty slots, with no error at all. The
tradeoff is real in both directions: Python's choice means this exact bug
fails loudly, at the exact line and moment responsible, which is what made
it possible to write a script (`git bisect`, next) that can test for it
mechanically at all. JavaScript's permissive choice means a similar typo
would silently produce a sparse array with a gap in it, and the resulting
bug would surface later, somewhere else, in a form much harder to trace
back to its actual cause. Python accepts more immediate failures in
exchange for failures that are easier to locate; this is exactly the
tradeoff between failing fast and failing permissively, and it's a design
decision every language with mutable sequences has to make one way or the
other.

## Concept Unit: Binary search — searching without reading

### The Problem

Five commits sit between the last known-good state and the current,
known-bad state: the loop refactor, the Italian goodbye, the Portuguese
goodbye, the Japanese goodbye, and the changelog note. Exactly one of them
is the actual cause. Checking all five, one at a time, from oldest to
newest, would work — but with five commits it's not obviously faster than
just reading each diff. What if there were fifty commits instead of five?
Reading fifty diffs by eye, trying to spot which one looks suspicious,
doesn't scale, and "looks suspicious" isn't even reliable — the actual
culprit here (`goodbyes[5] = "Sayonara!"`) looks exactly as safe as the
Italian and Portuguese additions did.

Suppose, instead of reading diffs, you could only ask one question,
repeatedly: "does the script work at this specific point in history?" —
yes or no, nothing else. Given that you know the very first commit in the
range is good and the very last is bad, and that once it breaks it stays
broken (this history is **bisectable**), which single commit would you test
*first* to eliminate the largest possible number of remaining candidates
with just that one answer? Would testing the very next commit after the
known-good one narrow things down as much as testing one further in?

### The New Code

```python
history = ["good"] * 9 + ["bad"] * 7  # 16 items, index 9 is the first "bad" one


def check(i):
    return history[i]


# Linear scan: check every index from the start until the first "bad" one.
linear_checks = 0
i = 0
while check(i) != "bad":
    linear_checks += 1
    i += 1
linear_checks += 1  # the check that finally found "bad"
print("Linear scan: first bad index", i, "-", linear_checks, "checks")

# Binary search: repeatedly check the midpoint of the remaining range.
low, high = 0, len(history) - 1
binary_checks = 0

while low < high:
    mid = (low + high) // 2
    binary_checks += 1
    if check(mid) == "bad":
        high = mid
    else:
        low = mid + 1

print("Binary search: first bad index", low, "-", binary_checks, "checks")
```

### Run it

```
$ python binary_search_lab.py
Linear scan: first bad index 9 - 10 checks
Binary search: first bad index 9 - 4 checks
```

Both strategies find the same, correct answer — the first bad index is `9`
— but the linear scan needed 10 checks (indices `0` through `9`, one at a
time) while the halving strategy needed only 4. Tracing the halving
strategy's own checks, over a 16-item range where the boundary sits at
index `9`:

1. `low = 0, high = 15` — the full range is uncertain. `mid = (0 + 15) // 2
   = 7`. `check(7)` reads `"good"` (index `7` is less than the boundary at
   `9`), so every index from `0` to `7` is now known-good; `low` moves to
   `8`, discarding those eight indices from further consideration.
2. `low = 8, high = 15` — `mid = (8 + 15) // 2 = 11`. `check(11)` reads
   `"bad"` (index `11` is past the boundary), so the boundary is now known
   to sit at or before `11`; `high` moves to `11`, discarding indices `12`
   through `15`.
3. `low = 8, high = 11` — `mid = (8 + 11) // 2 = 9`. `check(9)` reads
   `"bad"` — this is exactly the boundary itself; `high` moves to `9`.
4. `low = 8, high = 9` — `mid = (8 + 9) // 2 = 8`. `check(8)` reads
   `"good"`; `low` moves to `9`, meeting `high`. `low < high` is now false,
   so the loop ends with `low` equal to `9` — the first bad index — found
   in exactly four checks.

Each check discarded roughly half of whatever range remained uncertain,
regardless of which half turned out to hold the boundary. This is called
**binary search**: repeatedly testing the midpoint of an uncertain range
and discarding the half that cannot contain the answer, rather than
checking every candidate in order.

### Discard it

`code/00-git-workflow/` — the numbers `16` and `9` were chosen only to make
the halving pattern easy to trace by hand; the real search that follows

### SE lens

The alternative not chosen here is a linear walkthrough: `git log -p` from
`f74a70a` back to `d4a36eb`, reading every diff in order until the
suspicious one turns up. With five commits, that's plausible; with fifty or
five hundred, it stops being practical, and — as this exact bug already
demonstrated — "suspicious-looking" isn't a reliable signal anyway, since
`goodbyes[5] = "Sayonara!"` reads exactly as safely as the two commits next
to it. Binary search trades reading for testing: instead of judging code by
eye, each step asks one mechanical yes/no question and halves the remaining
range regardless of the answer.

That trade has a real cost this lesson's setup was deliberately built to
satisfy: bisect's search is only valid over a **bisectable** history — one
where "good" and "bad" don't interleave. If some intervening commit had
briefly fixed the crash and a later one reintroduced it, testing the
midpoint could land on either side of either boundary and mislead the
search, since binary search assumes exactly one boundary exists to
converge on. Maintaining that property — never letting a broken state
mask a later regression, never letting history flip back and forth between
working and broken — is a real, ongoing cost bisect's usefulness depends
on, not something it guarantees for free.

### SE lens

The alternative to `.append()` here isn't only "use a different method" —
it's a real design tradeoff about where bookkeeping responsibility lives.
`goodbyes[5] = "Sayonara!"` requires whoever writes that line to correctly
track the list's exact current length by hand, entirely outside the list
itself; get that number wrong by even one, in either direction, and the
line either crashes (too high) or silently overwrites an existing goodbye
instead of adding a new one (a valid-but-wrong index, no crash at all,
which would be a much harder mistake to catch). `.append()` delegates that
bookkeeping to the list's own implementation, which always knows its own
current length with certainty. The cost this project was already paying,
one commit before the fix: manual index tracking is fragile exactly when
a list keeps growing across separate, individually ordinary-looking
changes — which is precisely the situation three commits in this lesson's
own history walked into.
