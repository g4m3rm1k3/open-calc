# Lesson 0.1: Recoverable History From the First Line

**What you will build** — A folder that starts as nothing (not even a git
repository) and ends as a real, initialized repository holding one committed
file: a tiny runnable Python script, `hello.py`. The working feature is small
on purpose — one file, one commit. The transferable problem this lesson is
actually about is bigger than that one file: how does a project go from
"just files sitting in a folder" to "a project with permanent, recoverable
history," and what does git actually create, store, and move between three
distinct states — the working tree, the staging area, and the repository's
history — to make that true?

**What you need to know first** — Nothing. This is Lesson 0.1, the first
lesson in the curriculum.

**Terms used in this lesson**

- **Repository** — the persistent, on-disk record of a project's entire
  history, existing alongside (not instead of) the project's actual files.
  Without something whose whole job is remembering, editing a file and
  saving over it destroys the previous version permanently — a repository
  is the thing that exists specifically so that doesn't happen.
- **`.git` directory** — the real, physical folder git creates to hold a
  repository's stored history, its configuration, and its bookkeeping. It
  exists so "repository" isn't an abstract idea — it's an actual folder you
  can open, right alongside the files you're editing.
- **Working tree** — the files you can currently see and edit on disk, in
  their present-moment state. This has to be named and understood as its
  own thing because it is not the same thing as the repository's history —
  a file can be sitting in the working tree, fully edited, with the
  repository knowing nothing about that edit yet.
- **Untracked** — the specific state a brand-new file starts in: it exists
  in the working tree, git can see it's there, but git has never been told
  to include it in anything. This name matters because it's the exact word
  `git status` uses, and it means "git is not yet watching this," not "git
  is confused by this."
- **Staging area (the index)** — a holding area, distinct from both the
  working tree and the repository's history, where changes are placed
  right before they become permanent. It exists so a commit can be built
  out of exactly the changes intended, rather than automatically including
  every single edit currently sitting in the working tree.
- **Commit** — a permanent, addressable snapshot of the project, recorded
  into the repository's history. This is the actual unit "recoverable
  history" is made of — each one is a fixed point that can always be
  returned to, later, exactly as it was.
- **Root commit** — the very first commit a repository ever has, the one
  with no earlier commit before it. It gets its own name because every
  later history operation this curriculum will eventually use (including
  `git bisect` in Lesson 0.6) has to walk backward through history until it
  hits this exact point and can't go any further.
- **Commit hash (SHA)** — the long hexadecimal identifier — for example
  `b63f93074bd274e384f5d1bb4f3a01f3ecb141a7` — that git computes from a
  commit's exact content and permanently assigns to it as its name. This is
  what actually makes a commit "recoverable" in a precise sense: it's a
  unique, content-derived address, not a label a person assigned by hand,
  so two different commits can never accidentally share one.
- **Meaningful commit message** — the short, human-written text attached to
  a commit, stating *why* a change was made, not merely restating what
  changed. The hash gives a commit a permanent address; the message is the
  only part of a commit that tells a future reader — including the same
  person, months later — why that snapshot exists at all. An address with
  no explanation is only half of "recoverable."
- **Branch** *(flagged here; fully explained in Lesson 0.2, "Make a feature
  branch")* — a movable, named pointer to a specific commit, used to track
  one independent line of work. This lesson only needs the minimum: a
  freshly initialized repository already has one, named `master` on this
  machine by default, and every command in this lesson will print that name
  without this lesson ever being about branches. It's flagged rather than
  silently left unexplained because it's genuinely unavoidable — it's
  sitting in every single piece of real output this lesson shows.
- **Line-ending conversion (LF / CRLF)** — LF (a single `\n` character) is
  the line ending git's own stored objects always use internally; CRLF (the
  two characters `\r\n`) is what Windows text editors and tools typically
  write to disk. This term exists to explain a real warning this lesson's
  own verified run produced — not a bug, but git noticing the difference
  between what it stores and what Windows will write back into the working
  tree.

**Objects and methods used**

- **`git init`**
  - *What it is:* A one-time setup command that turns an ordinary folder
    into a git repository.
  - *Implementation:* `git init [<directory>]` — with no argument, it
    initializes the current directory. It creates a `.git` subdirectory
    containing everything needed to start recording history there: an
    initially empty store for future commits, and default configuration.
  - *Its use:* This lesson's very first command. Nothing else git offers
    works until a folder has actually become a repository.
  - *Type:* A subcommand of the `git` program — a standalone CLI
    executable, not a class or an object system.
  - *Responsibility:* Create the `.git` directory and everything inside it
    needed for git to track history in this folder from this point
    forward — and nothing else. It does not look at, stage, or touch any
    file that might already exist in the folder.
  - *Depends on:* A filesystem location to create `.git` in — the current
    directory, by default. Nothing else; it's the one command in this
    lesson that can run with zero prior repository state.
  - *Connects to:* Every other command in this lesson — `git status`,
    `git add`, `git commit`, `git log` — depends on `.git` already
    existing. `git init` is what makes every one of them possible.
  - *Shape:* The boundary between "just a folder" and "a git repository" —
    a one-time setup step, not part of the ordinary edit/stage/commit cycle
    that follows it.
- **`git status`**
  - *What it is:* A read-only inspection command that reports the current
    relationship between the working tree, the staging area, and the most
    recent commit.
  - *Implementation:* `git status`, with no required arguments. It prints
    the current branch name, then lists files under one or more headings —
    staged ("Changes to be committed"), modified-but-unstaged, or
    untracked — depending on what it finds.
  - *Its use:* Run repeatedly in this lesson specifically to make the
    otherwise invisible state changes — working tree → staged →
    committed — visible before and after each command that causes one.
  - *Type:* A subcommand of `git`; a read-only query, never a mutation — it
    reports on state, it never changes any.
  - *Responsibility:* Compare three things against each other — the
    working tree's actual files, whatever is currently staged, and the
    most recent commit — and report every difference it finds, sorted into
    which of those three states it currently lives in.
  - *Depends on:* An already-initialized repository (a `.git` directory
    has to exist); reads the working tree's files and the staging area's
    contents to build its report.
  - *Connects to:* Called before `git add` (to see what's untracked or
    modified) and after it (to confirm what actually got staged). Nothing
    downstream reads its output — it exists purely to inform whoever runs
    it.
  - *Shape:* A diagnostic tool sitting outside the actual commit history —
    running it never changes anything `git log` will later show.
- **`git add`**
  - *What it is:* The command that moves a change from the working tree
    into the staging area.
  - *Implementation:* `git add <pathspec>...` — for example, `git add
    hello.py`. It also accepts `.` to mean "everything changed in the
    current directory," though this lesson stages one named file
    deliberately.
  - *Its use:* This lesson's third Concept Unit — the exact step that turns
    "a file git merely notices exists" into "a file git will include in
    the next commit."
  - *Type:* A subcommand of `git`; a mutating command — it changes the
    staging area's contents, but it never touches the working tree's files
    or the repository's committed history.
  - *Responsibility:* Copy the current content of exactly the file(s)
    named into the staging area, replacing whatever that area held for
    those specific files before.
  - *Depends on:* The working tree's current file content for whatever
    pathspec is given; an already-initialized repository.
  - *Connects to:* Reads from the working tree; writes into the staging
    area that `git commit` reads from next. It is the only bridge between
    those two states — nothing else moves a change from one to the other.
  - *Shape:* The boundary between "editing files" and "building a commit."
    Everything staged here, and only what's staged here, is what the next
    `git commit` will actually record.
- **`git commit`**
  - *What it is:* The command that permanently records whatever is
    currently staged as a new, addressable snapshot in the repository's
    history.
  - *Implementation:* `git commit -m "<message>"` — the `-m` flag supplies
    the commit message directly on the command line; without it, git opens
    a text editor instead and waits for one to be typed and saved. It
    produces a new commit object identified by a SHA-1 hash, containing the
    currently staged content and, for every commit after the first, a
    reference back to the previous commit as its parent.
  - *Its use:* This lesson's actual destination — the moment "recoverable
    history" stops being a claim and becomes a checkable fact about this
    exact folder.
  - *Type:* A subcommand of `git`; a mutating command, and the only one of
    the four covered so far that writes into the repository's *permanent*
    history, rather than the staging area or the working tree.
  - *Responsibility:* Take exactly what's currently staged, package it
    together with the message, an author, and a timestamp into a new
    commit object, compute that object's content-derived hash, and record
    it as the new tip of the current branch.
  - *Depends on:* Something actually staged — an empty staging area
    produces "nothing to commit" instead; a configured author name and
    email; the message text supplied via `-m`.
  - *Connects to:* Reads from the staging area `git add` just filled;
    writes a new entry that `git log` can then display; moves the current
    branch's pointer (`master`) forward to point at the commit it just
    created.
  - *Shape:* The actual history-creation boundary. Everything before this
    point — working tree, staging — is provisional and can be freely
    changed. Everything after it is a permanent, addressable point in
    history.
- **`git log`**
  - *What it is:* A read-only command that prints the commit history of the
    current branch, most recent commit first.
  - *Implementation:* `git log`, with no required arguments. For each
    commit it finds, it prints the full hash, the author's name and email,
    the commit date, and the commit message.
  - *Its use:* This lesson's own proof step — the concrete evidence that a
    real, permanent, inspectable commit now exists in this folder.
  - *Type:* A subcommand of `git`; read-only, exactly like `git status`.
  - *Responsibility:* Starting from the current branch's tip, walk
    backward through each commit's recorded parent, and print every
    commit's recorded metadata along the way, newest first.
  - *Depends on:* At least one commit already existing; an
    already-initialized repository.
  - *Connects to:* Reads the commit object `git commit` just created. This
    is the first command in the lesson whose output is history that will
    still exist, unchanged, in every later lesson in this phase — including
    Lesson 0.6's `git bisect`, which walks exactly this same chain.
  - *Shape:* The read side of the repository's permanent history — the
    direct counterpart to `git commit`'s write side.

**Everything else in the file, not this lesson's subject but still
explained**

- **`print(...)`**
  - *What it is:* Python's built-in function for writing text to standard
    output.
  - *Implementation:* `print(*objects, sep=' ', end='\n', ...)` — a
    built-in function, not a method on any object this lesson defines.
    Called here as `print("Hello, recoverable history.")`, with a single
    positional string argument.
  - *Its use:* Gives `hello.py` one observable, runnable effect, so the
    file being committed is a real, working script instead of an empty
    placeholder.
  - *Type:* A built-in free function, part of Python's `builtins` — not a
    class, and not a method that requires an object to call it on.
  - *Responsibility:* Convert its argument(s) to text and write that text,
    followed by a newline, to the program's standard output stream.
  - *Depends on:* The value(s) passed as arguments. Nothing about git or
    this lesson's repository.
  - *Connects to:* Called once, directly, at the top level of `hello.py`;
    nothing calls it in turn — it's a leaf call whose only effect is the
    line printed to the terminal when the script runs.
  - *Shape:* Ordinary language-level output, entirely outside git's own
    concerns — included here only because it's what makes `hello.py` an
    actual runnable program rather than an empty file with nothing to
    commit.

## Concept Unit: The Repository

### The Problem

Right now, nothing in this project remembers anything. If a file gets
edited, saved, then edited again, the earlier version isn't stored
anywhere — it's just gone, overwritten on disk. There is currently no
folder, database, or mechanism anywhere that keeps track of what a file
looked like a moment ago, let alone a full history of every change ever
made. Before commits, staging, or any of git's vocabulary can mean
anything, something has to physically exist whose entire job is
remembering — a place separate from the files themselves, where their past
states can actually live.

need to exist alongside them? If you ran a single setup command inside an
empty folder to turn on that remembering, what do you think that command
would actually create — a new file sitting next to your others, a new
subfolder, or something else entirely? And what do you expect happens if
you run that exact setup command a second time in the same folder — does it
start over from nothing, or does it recognize the folder is already set up?

### Mechanical Walkthrough

The New Code above is a single line: `git init`. Enumerated in order:

- **`git`** — the name of the program being invoked. This is not a git
  concept at all; it's the operating system locating and running an
  executable named `git`, the same as running any other command-line
  program.
- **`init`** — the subcommand argument telling the `git` program which of
  its many operations to perform. `git` itself does nothing by default; it
  requires a subcommand (`init`, `status`, `add`, `commit`, `log`, and many
  others not used in this lesson) to know what to do.

That's the entire line — two tokens, a program name and a subcommand. What
it *does*, mechanically: `git init`, per its real documented behavior (see
`git help init`, or git's own public documentation, for the full contract),
creates a `.git` subdirectory in the current folder if one doesn't already
exist, and populates it with an empty store, ready to hold commits once
they start being made, plus a default configuration file. Running it again in a folder that's already a
repository is explicitly documented as safe — it re-initializes
non-destructively, leaving existing history untouched, which is the direct
answer to this unit's third *Pause and try* question above.

### CS Lens

A repository is, at its core, an **append-only log**: a repository accumulates history by adding
new commits, and existing commits are never edited or erased once
recorded — only added to. This is a genuinely reusable idea, not specific
to git:

```
Also recognized in: database write-ahead logs, event-sourcing systems,
accounting ledgers (mistakes get a correcting entry, not an erasure),
audit logs, blockchain ledgers
```

Every one of those systems makes the same trade for the same reason: once
something is recorded, changing the record itself would destroy the very
thing that makes it trustworthy as history. A repository's `.git` directory
is this idea, applied to source code.

### SE Lens

The alternative to a real repository is the folder-copying approach many
people reach for instinctively — manually duplicating a project folder as
`project-backup`, `project-backup-2`, `project-final`, and so on, before
making a risky change. That approach requires zero setup and zero new
vocabulary, which is its entire appeal. Its real cost only shows up later:
there's no way to see *what specifically* changed between `project-backup`
and `project-backup-2` without manually comparing every file by eye, no way
to know *why* a given copy was made, and the number of copies grows without
bound the longer a project lives. `git init`'s upfront cost — a `.git`
folder, a small amount of new vocabulary, one command to run before editing
starts — is a deliberate trade: pay a small, one-time setup cost now, in
exchange for git computing and storing exactly what changed, and why (once
messages are involved), automatically, for as long as the project exists.
This project is not yet carrying any debt from this choice — there's
nothing in a fresh `.git` directory that costs anything until it starts
accumulating real history, which is exactly what the next three Concept
Units begin doing.

## Concept Unit: The Working Tree

### The Problem

A `hello.py` file is about to exist in this folder, sitting right next to
the `.git` directory the previous unit just created. But "sitting in the
folder" and "known to git" are not automatically the same thing — git
doesn't watch a folder continuously and record every save the instant it
happens. So the moment a new file is created, there's a real question: does
git know about it yet, and if it doesn't, what state is that file actually
in from git's point of view — invisible to git entirely, or visible but
deliberately not part of history yet?

### CS Lens

The three-state model this unit is naming — a file changes from "not
tracked" to "tracked, changed" to "recorded" — is a specific instance of a
much more general pattern: a **pipeline with distinct, named stages**, where
something has to pass through an earlier stage before it can enter a later
one, and its current stage is always inspectable rather than hidden.

```
Also recognized in: a compiler's source → intermediate representation →
final binary pipeline, a CI/CD pipeline's working branch → build → deploy
stages, an image editor's canvas → layer → flattened-export stages, an
HTTP request's received → validated → processed states
```

In every one of those systems, the point of naming the intermediate stages
explicitly — rather than treating "input" and "output" as the only two
states that matter — is the same reason `git status` exists: so that
something partway through the pipeline is never a mystery, only ever a
specific, nameable, inspectable state.

### SE Lens

An alternative design git did not choose: some version-control and
auto-save tools (many cloud document editors, for instance) track every
single keystroke or save automatically, with no separate "working tree"
state distinct from "recorded" at all — the moment something changes on
disk, it's already part of history. That design removes the entire
category of question this unit exists to answer ("is this file tracked
yet?") because there's no gap between editing and recording to ask about.
The real cost of that convenience: the author loses the ability to make
several related edits and have them show up as one deliberate,
after-the-fact decision about what "this version" means — every keystroke
becomes its own permanent, unfiltered data point. Git's working-tree state
is the deliberate opposite trade: files can be edited freely, saved
repeatedly, left half-finished, or abandoned entirely, and none of that
touches the repository's history at all until something later (staging,
covered next) explicitly says otherwise.

  varies by what it finds, but always starts with `On branch <name>`; there
  is no failure mode for this specific command short of running it outside
  any repository at all, which is not the case here.

## Concept Unit: Staging

### The Problem

`hello.py` currently exists only in the working tree — the previous unit's
`git status` output said so directly: "untracked," "nothing added to

in the working tree, there would be no way to commit *some* of the changes
in a folder while leaving others out — every edit currently on disk would
have to become part of the next commit, whether or not that's actually
what was intended. Before a commit can happen, there needs to be a way to
explicitly choose which changes are about to become permanent.

### CS Lens

Staging is a specific case of a **buffer standing between two systems that
operate at different granularities** — the working tree changes constantly,
one save at a time, while a commit is meant to represent one deliberate,
coherent unit of change; the staging area is what lets many small edits
accumulate before being grouped into that one unit.

```
Also recognized in: a shopping cart before checkout, a database
transaction's uncommitted writes before COMMIT, a print spooler holding
jobs before they actually print, a pull request holding commits before
they're merged
```

Every one of those examples separates "things that have happened" from
"things that are now final" by exactly one buffering step — never zero
(which would make every small change permanent immediately, as the
previous unit's SE Lens described some auto-save tools doing) and never
more than one (which would just relocate the same question to a different
boundary).

### SE Lens

The alternative git did not choose: commit directly from the working tree
with no separate staging step at all — some other version-control tools
lean this way, committing everything currently changed with a single
command. That removes one command from the everyday cycle (`git add` would
simply not exist) and removes one entire concept a newcomer has to learn.
Its real cost: there would be no way to commit *only* `hello.py` if a
second, unrelated, half-finished file also happened to be sitting in the
same working tree at the same moment — every commit would necessarily
include everything currently edited, whether or not it was actually meant
to be part of that particular snapshot. Git's staging area is the
deliberate trade of one extra command and one extra concept, in exchange
for every commit being exactly what its author intended it to be, no more
and no less — a cost this project is not yet carrying any debt from, since
`code/00-git-workflow/` currently has exactly one file to stage in the
first place.

## Concept Unit: The Commit

### The Problem

`hello.py` is staged — `git status` confirmed it's sitting under "Changes
to be committed." But staged is still not the same as **recorded**: this
folder's repository still has zero commits, meaning if the machine
vanished right now, nothing about `hello.py` would actually be recoverable
from git's history, because no history exists yet. Something has to take
whatever is currently staged and turn it into an actual, permanent entry in
the repository — and whatever that entry is, it needs a way to be found
again later, and a way to say, in words, why it exists.

found again later — a name you'd choose yourself, or something git
generates?

- **`git`** — the name of the program being invoked, exactly as in every
  prior unit: the operating system locating and running the `git`
  executable, regardless of which subcommand follows it.
- **`commit`** — the subcommand selecting git's commit-creation operation,
  given full treatment in this lesson's Header under Objects and methods
  used: it packages whatever is currently staged, together with a message,
  author, and timestamp, into a new commit object, computes that object's
  content-derived hash, and records it as the new tip of the current
  branch.
- **`-m`** — a flag supplying the commit message directly on the command
  line, rather than opening a separate text editor and waiting for one to
  be typed and saved there. Without `-m`, `git commit` would stop and open
  an editor instead of proceeding immediately.
- **`"Add hello.py, the first runnable script"`** — the message text
  itself, a plain quoted string. This is where the **meaningful commit
  message** term this lesson's Header defines actually gets applied: the
  message doesn't just restate the diff ("added a file") — it names *what*
  was added and *why it matters to the project at this point* ("the first
  runnable script"), which is exactly the information a hash alone could
  never carry. A message like `"update"` or `"fix"` would technically
  satisfy `-m`'s syntax identically, and git would accept it without
  complaint — the difference is entirely about what a future reader,
  including the same person months later, can actually learn from it.

Second, `git log`, enumerated:

- **`git`** — the name of the program being invoked, exactly as in every
  prior unit and in the `git commit` line just above: the operating system

  subcommand follows it.
- **`log`** — the subcommand selecting git's history-listing operation,
  given full treatment in this lesson's Header under Objects and methods
  used: starting from the current branch's tip, it walks backward through

  the way.

### CS Lens

The commit hash is this lesson's clearest example of **content-addressable
storage**: an object's own name is derived from its content, rather than
assigned by a person or a counter. Change the content even slightly, and
the hash changes completely — which is exactly why two different commits
can never collide on the same address, and why a hash, once computed,
proves the content really is what it claims to be.

```
Also recognized in: Docker image layers (each identified by a SHA256 hash
of its own contents), IPFS, package-manager integrity hashes (npm's
package-lock.json, pip's hash-checking mode), deduplicating backup tools
like restic and borg, Merkle trees underlying blockchains
```

Every one of those systems reaches for the same trick for the same reason:
a name that's computed from content, rather than chosen by hand, can be
independently verified by anyone who has the content — which is precisely
what let `git log` above confirm the commit was real, without needing to
trust `git commit`'s own report of success.

### SE Lens

The alternative git did not choose: commits with no required message at
all, or an automatically generated one (a timestamp, an incrementing
number). That would remove the one moment in this entire lesson where a
human has to stop and articulate, in their own words, why a change
happened — and it would make `-m` unnecessary, simplifying the command.
Its real cost, stated by this lesson's own **meaningful commit message**
term: a hash alone is an address, not an explanation. A history made of
nothing but timestamps is technically just as "recoverable" in the literal
sense — every past state is still there, still checkable-out — but
practically much less useful, because nothing in it says why any particular
point in that history matters more than the point next to it. Requiring
`-m`'s argument is git putting a small amount of friction — one flag, one
short string — directly in the path of every single commit, specifically
because the alternative's convenience would come at the cost of the
project's history actually being *readable* later, not just present.
