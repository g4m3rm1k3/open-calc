# Lesson 0.4: The Merge Git Refuses to Guess

**What you will build:** Two branches will each rewrite the same line of `hello.py` differently, and merging them for real will force git to stop and ask you to decide. You'll cause that conflict on purpose, read exactly what git leaves behind in the file, resolve it by hand, close out the merge commit, and then actually run the resolved script to prove your resolution works — not just that it looks clean. The transferable problem: automatic merging has a hard boundary. Git can silently combine two changes that touch different things, but the moment two branches touch the *exact same content* differently, there's no rule that tells git which one you meant — and a conflict that "resolves cleanly" (no markers left, commit succeeds) is not proof that what you typed is correct.

**What you need to know first:** Lesson 0.1's repository, working tree, staging area/index, and `git commit`. Lesson 0.2's branch and `git switch`. Lesson 0.3's `git merge` and the fast-forward case specifically — this lesson is where merging stops being that simple case.

**Terms used in this lesson**

- **merge conflict** — The state git puts a merge into when two branches changed the exact same region of the exact same file in different ways, and git has no rule for choosing between them. It exists because git's automatic merging only works by assuming non-overlapping changes are safe to combine; the moment that assumption breaks, silently picking a side would mean discarding someone's real work without telling them, so git stops and hands the decision to a person instead.
- **conflict markers** — The literal text git writes directly into a conflicted file — `<<<<<<< HEAD`, a divider `=======`, and `>>>>>>> <branch-name>` — to show both versions of the disputed content side by side, in place, inside the actual file. They exist so the person resolving the conflict can see exactly what each side wanted without having to go look it up separately in each branch's history.
- **three-way merge** — The algorithm `git merge` actually runs: instead of comparing just the two branch tips, it also finds their most recent common ancestor commit and compares both tips *against that ancestor*. This is what lets git tell the difference between "only one side changed this line" (safe to take automatically) and "both sides changed this line differently" (a real conflict) — a plain two-way diff between the tips alone couldn't make that distinction, because it would have no way to know which side actually changed anything.
- **common ancestor** — The most recent commit that both branches being merged share in their history — the point they diverged from. It's what a three-way merge measures both branches' changes *against*; without it, git would have no way to know whether a difference between two branch tips means "one side changed it" or "the other side changed it," since either explanation would look identical from the tips alone.
- **HEAD** — Git's name for "the commit currently checked out" — normally a pointer to whatever branch you're on, which itself points at a commit. During a conflict, the conflict markers label one side `HEAD` specifically because that's always *your current branch's* version, as opposed to the incoming branch's version, which gets labeled by name instead.
- **working tree** — The actual files on disk in the project folder, reappearing from Lesson 0.1. It exists because git's committed history isn't directly editable — you edit the working tree, then explicitly choose what to record from it via the index and a commit. This lesson's conflict markers get written directly into the working tree's copy of `hello.py`, not into any commit.
- **staging area / index** — Git's intermediate structure between the working tree and the commit history, reappearing from Lesson 0.1. Normally it just holds "what will go into the next commit." During a conflict it does double duty: it also tracks, per file, whether that file's conflict has been marked resolved yet — the exact flag `git add` clears and `git commit` checks before it will finish a merge.
- **fast-forward** — The case, reappearing from Lesson 0.3, where the branch being merged in is simply ahead of the current branch with no independent commits of its own — so git can resolve the "merge" by just moving the current branch's pointer forward, with no new commit and no possibility of a conflict. This lesson uses it once, for `warmer-goodbye`, specifically so the *next* merge — `formal-goodbye` — has something to actually conflict with.
- **merge commit** — A commit with more than one parent, reappearing from Lesson 0.3, created when a merge can't be resolved by fast-forwarding. Lesson 0.3's merge commit only ever existed in an isolated lab, since the real project's actual merge there was a fast-forward; this lesson is the first time the real project itself produces one, and the first time that merge commit exists specifically *because* a conflict had to be resolved by hand first.
- **unmerged path** — Git's status label for a file that `git merge` touched but couldn't fully resolve — the specific state `git status` reports as "both modified" mid-conflict, and the specific flag `git add` clears once the reader has resolved that path.
- **testing after resolution** — Actually running the resolved code, rather than trusting git's own bookkeeping (a clean `git status`, a successful `git commit`) as proof the resolution is correct. It exists because git's own checks only ever verify that a file is well-formed enough to commit — never that its content does what was intended — so it's the one step in a conflict's whole lifecycle that can catch a resolution that's clean but wrong.
- **CRLF / LF line-ending normalization** — A warning git prints ("LF will be replaced by CRLF...") whenever it's about to write a file to disk on a system, like Windows, whose default text convention (CRLF, carriage-return-then-linefeed) differs from what's stored in the commit (LF, linefeed only). It isn't an error and doesn't affect anything in this lesson; it appears on the very first commit below and on every commit after that for the same reason, so it's explained once, here, and not repeated at every later appearance.

**Objects and methods used**

- **`git merge`**
  - *What it is:* A git subcommand that combines the commit history of another branch into the branch you currently have checked out.
  - *Implementation:* Invoked as `git merge warmer-goodbye` (fast-forward case) and `git merge formal-goodbye` (conflict case) — no flags, just a branch name argument. It compares the current branch's tip, the target branch's tip, and their common ancestor commit — a three-way comparison.
  - *Its use:* This lesson's code reaches for it twice: once to bring in a change git can apply without any decision (fast-forward), and once to bring in a change git cannot resolve alone (the conflict).
  - *Type:* A `git` CLI subcommand — a free operation on the repository's stored branch pointers and the working tree, not a method on any object the reader constructed.
  - *Responsibility:* Given a target branch, determine whether the current branch already contains everything the target has (in which case just move the pointer forward), or whether the two branches have independent commits that need combining into a new commit — and, when combining, apply every change automatically except where both branches touched the identical region of the identical file, in which case stop and leave the working tree in a conflicted state instead of guessing.
  - *Depends on:* The current branch already checked out via `git switch`, the named target branch, and — for anything past a fast-forward — a common ancestor commit reachable from both.
  - *Connects to:* Called by the person at the terminal; reads the commit history built by earlier `git commit` calls; on success it either moves the branch pointer (fast-forward) or leaves the tree ready for a later `git commit` to record a merge commit; on failure it writes conflict markers directly into the affected file's working-tree copy and marks that path unmerged, for `git status` and `git add` to report on and act on next.
  - *Shape:* The seam between two independent lines of a project's history and the one line the reader is actually working on — the exact boundary Lesson 0.3 first crossed with a single, uncomplicated fast-forward, and the boundary this lesson pushes past into the case that requires human judgment.

- **`git status`**
  - *What it is:* A git subcommand that reports the current state of the working tree and staging area relative to the last commit, without changing anything.
  - *Implementation:* Invoked with no arguments, `git status`, at two different moments below — once mid-conflict, once after resolving it — reporting a different message each time because the underlying state changed.
  - *Its use:* This lesson uses it as the primary way to ask git "what do you need from me right now" — first to confirm a conflict exists and which file it's in, then to confirm the resolution was accepted.
  - *Type:* A read-only `git` CLI subcommand — it inspects state and never writes to history or the working tree.
  - *Responsibility:* Compare the last commit, the index, and the working tree, and describe every difference between them in terms a person can act on — untracked files, staged changes, unstaged changes, and, specifically relevant here, any path still marked unmerged because a conflict hasn't been resolved yet.
  - *Depends on:* Nothing beyond an existing repository; it reads whatever state `git merge` and `git add` happen to have left behind at the moment it's run.
  - *Connects to:* Called by the person at the terminal; reads the index and working tree that `git merge` just modified; its output ("both modified: hello.py," later "All conflicts fixed but you are still merging") is what tells the reader whether `git add` still needs to run or whether `git commit` is what's left.
  - *Shape:* A read-only diagnostic layer between the reader and the repository's real internal state — never itself part of the history being built, only a window onto it.

- **`git add`**
  - *What it is:* A git subcommand that stages a file's current content into the index, marking it ready for the next commit. Already used in Lesson 0.1 for ordinary staging.
  - *Implementation:* Invoked as `git add hello.py`, the file's real path as its only argument, called immediately after hand-editing the file to remove the conflict markers.
  - *Its use:* This lesson reaches for it in a role Lesson 0.1 didn't need: during a conflict, this exact command is also how the reader tells git "I've made my decision on this file," not just "stage my edit."
  - *Type:* A `git` CLI subcommand — a write operation on the index only; it does not touch the commit history and does not touch the working tree's own file contents.
  - *Responsibility:* Copy the exact current bytes of the named path from the working tree into the index — and, specifically during a conflict, clear that path's unmerged status, which is the one and only signal git uses to decide whether `git commit` is allowed to close out a merge.
  - *Depends on:* A working-tree file at the given path; during a conflict, it depends on `git merge` having already put that path into the unmerged state.
  - *Connects to:* Called by the person at the terminal, after they've hand-edited the file; reads the working tree's current file content; writes to the index; its effect is what `git status` reports next and what `git commit` checks before it will allow the merge to finish.
  - *Shape:* The one explicit, manual signal in the whole conflict workflow — the seam between "git has flagged a problem" and "a human has taken responsibility for the fix," placed deliberately so nothing about resolution is ever inferred automatically.

- **`git commit`**
  - *What it is:* A git subcommand that takes whatever is currently staged in the index and permanently records it as a new commit in the repository's history. First used in Lesson 0.1 for a single-parent commit; used again here to close out a merge, which produces a commit with two parents instead of one.
  - *Implementation:* Invoked two ways below: `git commit -am "message"` (stage every already-tracked file's changes and commit in one step — the ordinary case, used while setting up the two diverging branches) and `git commit -m "message"` with no `-a` (the merge-closing case, since `git add hello.py` already staged the resolution explicitly).
  - *Its use:* In the setup below it's the same everyday commit from Lessons 0.1–0.3. Inside the second Concept Unit, it's the command that actually finishes the merge — until it runs, git still considers the merge in progress.
  - *Type:* A `git` CLI subcommand — a write operation that creates a new, permanent commit in the repository's history.
  - *Responsibility:* Take the exact content currently recorded in the index, wrap it in a new commit with an author, a message, a timestamp, and a pointer back to whatever commit(s) it's built on top of — one parent for an ordinary commit, two parents when it's closing a merge — and move the current branch to point at that new commit.
  - *Depends on:* A fully-resolved index (during a conflict, every previously-unmerged path must already be re-added via `git add`); a configured commit author (already set up in an earlier lesson, since every commit in this project shows `Learner <learner@example.com>`).
  - *Connects to:* Called by the person at the terminal; reads the index `git add` just wrote to; during a merge, also reads git's own record of which commit is being merged in, so it knows to record two parents instead of one; writes a new commit and moves the branch pointer; its result is what `git log` and `git branch -v` report afterward.
  - *Shape:* The actual permanent record-keeping step — everything before it (`git merge` failing, hand-editing the file, `git add`) is preparation; this is the one command that makes the resolution part of the project's real, shared history.

**Everything else in the file, not this lesson's subject but still explained.**

- **`git switch`**
  - *What it is:* A git subcommand that changes which branch is currently checked out, and — with `-c` — creates a new branch at the same time. Already used in Lesson 0.2.
  - *Implementation:* Invoked as `git switch -c warmer-goodbye` and `git switch -c formal-goodbye` (create-and-switch, both starting from master's current commit) and as plain `git switch master` (switch only, no creation).
  - *Its use:* Used twice below to create the two branches that are about to diverge, and to move back to master between them so both branches start from the exact same commit.
  - *Type:* A `git` CLI subcommand — a write operation on the stored branch pointers (with `-c`) and on the working tree (it rewrites the working tree's files to match whatever branch you switch to).
  - *Responsibility:* Given a branch name, replace the working tree's contents with that branch's committed content and update `HEAD` to point at that branch; with `-c`, first create the named branch pointing at the current commit, then do the switch.
  - *Depends on:* A clean working tree relative to the branch being left (git refuses to switch over uncommitted changes it would have to overwrite) and, for `-c`, a branch name that doesn't already exist.
  - *Connects to:* Called by the person at the terminal; writes to `HEAD` and, with `-c`, to git's stored branch pointers; every subsequent command in that terminal session (`git commit`, `git merge`) then operates on whichever branch it just switched to.
  - *Shape:* The mechanism that lets one working tree represent many different lines of history, one at a time — already the foundation of Lesson 0.2's whole lesson, reused here purely as setup, not as this lesson's own subject.

- **`git log`**
  - *What it is:* A git subcommand that reads and displays the repository's commit history. Already used in Lesson 0.3.
  - *Implementation:* Invoked two ways below: `git log --oneline --graph --all` (a compact, one-line-per-commit view with an ASCII graph of branch structure, across every branch, not just the checked-out one) and `git log -1 --format=full HEAD` (the single most recent commit on the current branch, in git's "full" format, which — unlike the default format — prints a separate `Merge:` line listing every parent when a commit has more than one).
  - *Its use:* The `--graph --all` form is how this lesson makes the actual shape of the divergence visible — two branches forking from the same commit, then rejoining. The `-1 --format=full` form is what proves, in real inspectable text, that the resulting commit has two parents instead of one.
  - *Type:* A read-only `git` CLI subcommand.
  - *Responsibility:* Walk the commit graph starting from whatever the given arguments specify (`--all` meaning every branch tip, or `HEAD` meaning just the current branch) and print each commit's metadata in the requested format, including every parent a commit has, not just the first.
  - *Depends on:* An existing commit history; `--graph` specifically depends on there being more than one line of history to draw, or it just prints a flat list.
  - *Connects to:* Called by the person at the terminal; reads the commits `git commit` created; its output is how the reader confirms what actually happened, rather than trusting a description of it.
  - *Shape:* A read-only reporting layer over the same commit graph `git merge` and `git commit` build — never part of the history itself, only a way of looking at it.

- **`git branch`**
  - *What it is:* A git subcommand that manages branch pointers — listing them, and, with the right flag, deleting them. Already used in Lesson 0.2.
  - *Implementation:* Invoked three ways below: `git branch --show-current` (print just the name of the currently checked-out branch, used inside the throwaway labs so they don't hard-code a branch name that might not match this machine's git configuration), `git branch -d warmer-goodbye formal-goodbye` (delete both branches, only allowed because git can confirm every commit on them is already reachable from another branch), and `git branch -v` (list every branch with the commit each one currently points at).
  - *Its use:* `--show-current` keeps the isolated labs honest about what branch they're actually on. `-d` cleans up the two branches once their work is safely part of `master`'s history. `-v` is how this lesson confirms that cleanup actually happened.
  - *Type:* A `git` CLI subcommand — read-only with `--show-current`/`-v`, a write operation on the stored branch pointers with `-d`.
  - *Responsibility:* Track the set of named pointers into the commit graph; report on them in whatever detail the flags ask for; and, with `-d`, remove a pointer — but only after confirming every commit it points at is already reachable from some other branch, so `-d` can never silently discard commits the way deleting a pointer by hand could.
  - *Depends on:* `-d` depends on the branch not being the currently checked-out one, and on its commits already being merged elsewhere; `--show-current` depends on `HEAD` actually pointing at a named branch rather than a specific commit directly.
  - *Connects to:* Called by the person at the terminal; `-d` reads the commit graph `git merge`/`git commit` built to verify safety before deleting a pointer; `-v` and `--show-current` just read the stored pointers directly.
  - *Shape:* Branch management sitting one layer above individual commits — Lesson 0.2's own subject, reused here only as setup and cleanup.

- **`python`**
  - *What it is:* The Python interpreter — the external program that reads a `.py` file and actually executes it. Already used in Lesson 0.1 to run `hello.py` for the first time.
  - *Implementation:* Invoked two ways below: `python hello.py` (run a file directly) and, in the throwaway lab, `python -c "from calc import combine; print(combine(2, 3))"` (run a short program passed directly as a string via `-c`, importing a function from a file in the current directory and calling it).
  - *Its use:* This is "testing after resolution" made literal — the one command in this lesson that proves the resolved file's actual behavior, as opposed to git's own checks, which only ever look at whether the file's *text* is well-formed enough to commit.
  - *Type:* An external CLI program, not a git subcommand and not part of this project's own code — a free-standing executable this lesson's code depends on but didn't write.
  - *Responsibility:* Parse the given source and execute it top to bottom, printing whatever the code's own `print(...)` calls produce, or — with `-c`, after importing — whatever the called function actually returns when run.
  - *Depends on:* A syntactically valid `.py` file (or string, for `-c`) and, for `-c`'s import, a matching filename in the current directory (`calc.py`, defining `combine`).
  - *Connects to:* Called by the person at the terminal; reads the exact file content `git add`/`git commit` just finished resolving and recording; its output is the only thing in this lesson that speaks to whether the merge is *correct*, not just *complete*.
  - *Shape:* Sits entirely outside git — the boundary between "the repository's history is in a clean, agreed-upon state" (git's job) and "the code that state represents actually does the right thing" (never git's job at all).

None of these are opaque magic — every git subcommand above is documented, in full, by git itself: `git help <subcommand>` (for example, `git help merge`) prints its real, official manual page on any machine with git installed, and the same content is mirrored at git-scm.com's own documentation. Nothing about `git merge` halting on a conflict, or `git add` clearing an unmerged flag, is a secret behavior — it's all in git's own public contract for these commands, checkable directly rather than taken on faith.

## Setting Up: Two Branches Touch the Same Line

Lesson 0.3 left the real project — `code/00-git-workflow/` — on `master`, at commit `5ee4c4f`, with `hello.py` reading:

```python
print("Hello, recoverable history.")
print("Goodbye, for now.")
```

The `add-goodbye-line` branch from Lessons 0.2–0.3 points at that same commit and stays untouched for the rest of this lesson — it's not part of what diverges here.

To get a real conflict, two branches need to change the *same line* differently, starting from the *same commit*. Both branches below are created from `master` while it's still at `5ee4c4f`, before either one commits anything — that's what guarantees they share a common ancestor and haven't already diverged from each other in some other way.

```
$ git switch -c warmer-goodbye
Switched to a new branch 'warmer-goodbye'
```

`git switch -c warmer-goodbye` — a `git switch` call, explained in full above — creates a new branch named `warmer-goodbye` pointing at the current commit (`5ee4c4f`) and checks it out in one step, updating `HEAD` to point at it.

The file is edited by hand to read:

```python
print("Hello, recoverable history.")
print("Goodbye, for now, see you soon.")
```

and committed:

```
$ git commit -am "Make the goodbye line warmer"
warning: in the working copy of 'hello.py', LF will be replaced by CRLF the next time Git touches it
[warmer-goodbye 6da3aab] Make the goodbye line warmer
 1 file changed, 1 insertion(+), 1 deletion(-)
```

`git commit -am "..."` — a `git commit` call, explained in full above — stages the change to the already-tracked `hello.py` and records it in one step, producing commit `6da3aab` on `warmer-goodbye`. The `warning: ... LF will be replaced by CRLF ...` line is git's CRLF/LF line-ending normalization warning, explained above; it's harmless and will reappear on every commit below without further comment.

Switching back to `master` (still at `5ee4c4f` — nothing has touched it) and branching again from there:

```
$ git switch master
Switched to branch 'master'
$ git switch -c formal-goodbye
Switched to a new branch 'formal-goodbye'
```

The same file, edited differently this time:

```python
print("Hello, recoverable history.")
print("Goodbye for now.")
```

```
$ git commit -am "Make the goodbye line more formal"
warning: in the working copy of 'hello.py', LF will be replaced by CRLF the next time Git touches it
[formal-goodbye 9b01ea8] Make the goodbye line more formal
 1 file changed, 1 insertion(+), 1 deletion(-)
```

`formal-goodbye` now has its own commit, `9b01ea8`, changed from the *same* ancestor line but in a different direction. The real shape of this can be seen directly:

```
$ git log --oneline --graph --all
* 9b01ea8 Make the goodbye line more formal
| * 6da3aab Make the goodbye line warmer
|/
* 5ee4c4f Add a goodbye line to hello.py
* b63f930 Add hello.py, the first runnable script
```

`git log --oneline --graph --all` — explained in full above — draws exactly this: one commit (`5ee4c4f`) with two separate lines coming out of it, each ending in its own commit. Neither branch has merged into the other yet.

`master` itself is still sitting at `5ee4c4f`, one step behind both of them. Bringing `warmer-goodbye` in first is a fast-forward — a case already taught in Lesson 0.3 — because `master` hasn't moved since `warmer-goodbye` branched off, so git can just slide `master`'s pointer forward to `6da3aab` with nothing to combine:

```
$ git switch master
Switched to branch 'master'
$ git merge warmer-goodbye
Updating 5ee4c4f..6da3aab
Fast-forward
 hello.py | 2 +-
 1 file changed, 1 insertion(+), 1 deletion(-)
```

`master` is now at `6da3aab` — the same commit as `warmer-goodbye`. That's the setup this lesson needed: `master` has now moved *past* `5ee4c4f`, along a path `formal-goodbye` never took. The next merge is where the two branches' conflicting edits to the same line finally meet.

## Concept Unit: A Merge Conflict and Its Markers

### The Problem

`master` and `formal-goodbye` both trace back to the same commit, `5ee4c4f`, where line 2 of `hello.py` read `print("Goodbye, for now.")`. Since then, `master` (by way of the `warmer-goodbye` fast-forward) changed that line to `print("Goodbye, for now, see you soon.")`, and `formal-goodbye` changed it, independently, to `print("Goodbye for now.")`. Both are real, committed changes to the exact same line, and they say different things.

Lesson 0.3 showed `git merge` combining two branches automatically, without ever needing to ask a question, because the fast-forward case has nothing to combine — one side just hadn't moved. This is a different shape of problem entirely.

Before reading on: given what `git merge` did in Lesson 0.3 — resolving things on its own, silently — what do you think it does when there's no way to resolve things silently? Does it have any basis for picking `master`'s wording over `formal-goodbye`'s, or the reverse? If it can't pick, what are its actual options: guess anyway, refuse to merge at all, or something in between?

### Project Change

- **Reference Source:** No reference counterpart — Phase 0 teaches the engineering workflow itself, not a port of the `Service`/`Data` reference project.
- **Files affected:** `code/00-git-workflow/hello.py` (modified by the merge attempt itself, not by hand).
- **Change type:** The command below is a `git merge` invocation, not a hand-written code change — its effect on `hello.py` is written by git, not typed by the reader.
- **Location:** Run from `master`, immediately after the fast-forward above, with `formal-goodbye` as the merge target.
- **Dependencies:** The divergent history built in Setting Up, above — specifically, `master` at `6da3aab` and `formal-goodbye` at `9b01ea8`, both descended from the same `5ee4c4f`.

### The New Code

```
$ git merge formal-goodbye
```

### The Updated Project

This command doesn't produce a new commit the way the merges in Lesson 0.3 did. Instead, git reports what happened and leaves `hello.py` in a new, unfinished state:

```
Auto-merging hello.py
CONFLICT (content): Merge conflict in hello.py
Automatic merge failed; fix conflicts and then commit the result.
```

`git status` confirms exactly what's outstanding:

```
$ git status
On branch master
You have unmerged paths.
  (fix conflicts and run "git commit")
  (use "git merge --abort" to abort the merge)

Unmerged paths:
  (use "git add <file>..." to mark resolution)
	both modified:   hello.py

no changes added to commit (use "git add" and/or "git commit -a")
```

And `hello.py` itself, opened directly, now reads:

```
1  print("Hello, recoverable history.")
2  <<<<<<< HEAD
3  print("Goodbye, for now, see you soon.")
4  =======
5  print("Goodbye for now.")
6  >>>>>>> formal-goodbye
```

Line 1 is untouched — neither branch changed it, so git carried it through with no ambiguity at all. Lines 2–6 are new: git has stopped mid-merge, right at the one place it couldn't resolve on its own, and written both contested versions directly into the working file instead of picking one.

### Mechanical Walkthrough

Enumerating the file's new content, in order:

- **`<<<<<<< HEAD`** (line 2) — Conflict markers, explained in full above. This exact three-part syntax (`<<<<<<<`, `=======`, `>>>>>>>`) is what git writes into a file the moment it detects a merge conflict; it isn't valid Python, isn't meant to stay, and exists purely as a temporary, in-place display of the disagreement. `HEAD`, the term explained above, labels this side specifically because it's always the branch that was already checked out — `master` — as opposed to the branch being merged in.
- **`print("Goodbye, for now, see you soon.")`** (line 3) — `master`'s current version of the line, taken from commit `6da3aab` (by way of the `warmer-goodbye` fast-forward). This is exactly the content `master` already had before the merge was attempted; git hasn't altered it, only wrapped it in markers.
- **`=======`** (line 4) — The divider between the two sides. There's no branch name attached to it because its only job is separating `HEAD`'s version from the incoming version — it doesn't itself represent either side's content.
- **`print("Goodbye for now.")`** (line 5) — `formal-goodbye`'s version of the same line, taken from commit `9b01ea8`. This is the content being merged *in*, shown exactly as that branch committed it.
- **`>>>>>>> formal-goodbye`** (line 6) — The closing marker, labeled with the actual branch name being merged in. This is how a reader tells the two sides apart when there's more than one conflict in a larger project: `HEAD` always means "whatever I already had," and the name after `>>>>>>>` always means "whatever I'm merging in," no matter which branch happens to be checked out at the time.

None of this is git *inventing* new content. Every character on lines 3 and 5 is copied verbatim from a real commit that already exists (`6da3aab` and `9b01ea8`); the markers are the only thing git added, and their entire job is labeling, not deciding.

This is only possible because of the **three-way merge**, the hard concept explained in full above: git didn't just compare `master`'s `hello.py` to `formal-goodbye`'s `hello.py` and notice they differ — a plain two-way diff would show a difference on line 2 but have no way to know *why*. By also comparing both against their **common ancestor**, `5ee4c4f`, git can tell that line 2 in the ancestor read `print("Goodbye, for now.")`, and that *both* branches changed it away from that, in different directions. That's the specific condition — both sides changed the same region relative to the ancestor — that produces a **merge conflict**, rather than git silently picking whichever version happened to be scanned first.

Also recognized in: Subversion's and Mercurial's own conflict-marker formats (different syntax, same three-way idea), collaborative document editors reconciling two people's offline edits to the same paragraph, database systems using optimistic concurrency control that reject a write when the row changed underneath it, and any config-management tool that merges two people's edits to the same file (Kubernetes manifests, Terraform state) and has to decide whether they're compatible.

### CS Lens

Already covered above, alongside the walkthrough: the **three-way merge** is the specific algorithm at work, and it's a hard concept worth naming again here on its own — comparing two branch tips *against their common ancestor*, not just against each other, is what turns "these two files differ" into "these two files changed the same thing differently," which is the only condition that actually triggers a conflict.

### SE Lens

The alternative git doesn't take is auto-resolving conflicts with a heuristic — "last commit wins," or "prefer the branch being merged in," or some kind of automatic text-blending. Some tools do attempt exactly that. The tradeoff is real: an automatic guess would mean `git merge` never stops and never costs the developer a manual step, but it would also mean one side's real, intentional work could get silently discarded without anyone noticing until much later — a wrong guess here doesn't fail loudly, it just quietly ships the wrong wording (or, in a codebase instead of a greeting, the wrong logic). Git's designers chose to make the failure loud and manual instead: a conflict halts the merge entirely, and nothing moves forward until a person looks at both sides. The cost is exactly the extra step this lesson is walking through; the benefit is that no change is ever silently lost. This project isn't carrying any debt from that choice yet — the cost only shows up as friction, not as a defect, and only when conflicts are frequent enough to feel expensive, which two people's first real conflict isn't.

### Commands Needed

- `git merge <branch>` — no flags, one argument, the branch to bring in. Run from the branch you want to merge *into* (here, `master`, checked out via `git switch master` beforehand). A `CONFLICT (content): Merge conflict in <file>` line means it stopped and needs manual resolution; no such line means it either fast-forwarded or wrote a merge commit on its own.
- `git status` — no arguments. `both modified: <file>` under "Unmerged paths" is the signal a conflict is still open.

### Mechanical Walkthrough

- **`git add hello.py`** — Explained in full above. Here it does two things at once: it stages the exact rewritten content shown above (the ordinary staging behavior from Lesson 0.1), and — because `hello.py` was flagged unmerged by `git merge` — it also clears that unmerged status. The `warning: ... LF will be replaced by CRLF ...` line is the same CRLF/LF normalization warning explained during Setting Up; it isn't new information here.
- **`git status`** — Explained in full above. Its message changed from "You have unmerged paths" to **"All conflicts fixed but you are still merging"** — real, direct proof that `git add` did more than ordinary staging: git is explicitly distinguishing "the conflict is resolved" from "the merge is finished," and stating outright that one more step, `git commit`, is still required.
- **`git commit -m "..."`** — Explained in full above, in its merge-closing role specifically: called with no `-a` flag, because there's nothing untracked or unstaged left to sweep in — `git add hello.py` already staged the only file that needed it. Because this commit runs while a merge is in progress, git records it with two parents instead of one, rather than the ordinary single-parent commit Lessons 0.1–0.3 always produced.

That two-parent claim isn't something to take on faith — it's inspectable directly:

```
Author: Learner <learner@example.com>
Commit: Learner <learner@example.com>

    Merge formal-goodbye into master, keep the warmer goodbye phrasing
```

The `Merge: 6da3aab 9b01ea8` line is `git log`'s `--format=full` output — explained in full above — printing every parent a commit has, not just the first. `6da3aab` is exactly the commit `master` pointed at going into this merge (by way of the `warmer-goodbye` fast-forward); `9b01ea8` is exactly `formal-goodbye`'s commit. This is the same **merge commit** concept Lesson 0.3 only ever demonstrated in an isolated lab — a real commit, in the real project, with two parents instead of one, because the history genuinely needed combining rather than just moving a pointer.

The full shape of the history confirms it:

```
|/
```

### Isolated Lab: Closing Out a Resolved Conflict

The Concept Isolation Rule still applies here — `git add` and `git commit`'s conflict-closing roles are their own new concept, distinct from the conflict-detection Unit A already isolated, and they deserve their own dedicated demonstration rather than only ever appearing for the first time inside `hello.py`'s real resolution above.

### CS Lens

Not a distinct algorithmic concept from Unit A's three-way merge — resolving is the human half of the same process the machine started. Worth restating plainly, though: the **staging area / index**, explained in full above, is doing real conceptual work here beyond its ordinary "what goes in the next commit" role — it's also git's only record of *which specific paths* still need a decision, which is exactly what lets `git commit` refuse to finish the merge while any path remains unresolved.

### SE Lens

The alternative not taken here is inferring resolution automatically — for instance, treating "no conflict markers remain in the file" as proof enough that it's resolved, with no explicit `git add` required. That would save exactly one command. The tradeoff: a file can legitimately contain the literal text `<<<<<<<` or `>>>>>>>` as real data (a file that itself documents git conflict markers, for instance), which would break a marker-scanning approach in either direction — falsely claiming a real conflict is resolved, or falsely refusing to accept a file that never had one. Requiring an explicit `git add` sidesteps that entirely: it's not scanning file content for anything, it's just a direct, unambiguous statement from a person, decoupled from whatever the file happens to contain. The cost is one extra command per conflicted file, paid every time, in exchange for never depending on a heuristic that could be wrong.

### Commands Needed

- `git add <file>` — one argument, the resolved file's path. On a conflicted path, this both stages the content and clears the unmerged flag; `git status` immediately afterward is how to confirm it worked.
- `git commit -m "<message>"` — during an active merge, this needs no `-a` (whatever was conflicted was already explicitly staged) and produces a commit with as many parents as branches were being merged — two, in every case this lesson covers.

### CS Lens

This is a hard concept, not routine syntax: the gap between **syntactic validity** (does this parse, does this commit cleanly) and **semantic correctness** (does this do what was intended) — worth naming as its own idea, separate from the three-way-merge mechanics of the earlier two units.

Also recognized in: a type checker that accepts code with correct types but wrong logic, a compiler that accepts code that builds but crashes at runtime, a database migration that applies without error but corrupts data semantics, a Kubernetes manifest or Terraform plan that parses and applies cleanly but produces the wrong running configuration, and — one level up from all of these — any code review that checks "does this look right" without ever running it.

### SE Lens

The alternative not taken here is trusting git's own success signals — a clean `git status`, a successful `git commit` — as sufficient proof the merge is correct, and skipping the run entirely. The tradeoff is speed against safety: skipping the run is faster in the moment and correct *most* of the time, since most conflicts really are resolved thoughtfully. But git's own conflict system, by design, only ever checks for the *absence of markers* — it has no way to know whether the remaining content is right, because it has no idea what "right" means for this project. That's a real, honest limitation of this lesson's current workflow, not a hypothetical one: nothing here is a substitute for an actual automated test suite that could catch this kind of mistake without a person remembering to run the file by hand every time — Phase 0 hasn't introduced automated testing yet, so "testing after resolution" right now means exactly what it did in this unit: running the script and reading the output yourself.
