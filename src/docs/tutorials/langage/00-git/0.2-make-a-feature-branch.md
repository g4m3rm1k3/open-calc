# Lesson 0.2: A Second Line of History That Doesn't Touch the First

**What you will build** — A second, independent line of history added to the
same repository Lesson 0.1 created: a new branch, `add-goodbye-line`,
holding one small change to `hello.py` — a second `print(...)` line —
committed entirely separately from `master`. The working feature is small
on purpose, same as Lesson 0.1: one branch, one commit. The transferable
problem this lesson is actually about is bigger than that one line: how
does a single repository let two different versions of the same file exist
at the same time without either one silently overwriting or being
overwritten by the other, and what has to move, inside git, for a person to
freely switch between them?

**What you need to know first** — Lesson 0.1, specifically the repository
it left behind at `code/00-git-workflow/`: already holding one commit (the
root commit, hash `b63f93074bd274e384f5d1bb4f3a01f3ecb141a7`, message "Add
hello.py, the first runnable script") on a branch named `master`, with
`hello.py` containing exactly one line, `print("Hello, recoverable
history.")`. This lesson also reuses, at full treatment below, Lesson 0.1's
`git status`, `git add`, `git commit`, and `git log`, and the working tree /
staging area / commit / repository vocabulary those commands depend on.

**Terms used in this lesson**

- **Branch** *(flagged in Lesson 0.1, fully explained here)* — a movable,
  named pointer to a specific commit, not a copy of any files. It exists so
  a repository can hold more than one independent line of work at once:
  each branch points at its own tip commit, and creating one costs nothing
  more than writing a new pointer — no files are duplicated, no history is
  copied. Lesson 0.1 already showed one branch, `master`, in every command's
  output without ever naming it as a concept; this lesson is where that
  deferral gets paid off.
- **HEAD** — git's record of which branch is currently checked out; the
  thing that actually moves when a branch is switched. It exists because
  a repository can hold many branches at once, but a working tree can only
  ever reflect one of them at a time — HEAD is git's answer to "which one,
  right now?" Every command this lesson runs that reports "On branch
  `<name>`" is reading HEAD to know what to print.
- **`git checkout` (the older branch-switching command)** — the command
  `git switch`, introduced in this lesson, replaced for the specific job of
  moving between branches. `checkout` still exists in current git and still
  works for this purpose, but it was long overloaded with a second,
  unrelated job — restoring individual files to an earlier version — with
  no way to tell, from the command name alone, which job a given invocation
  meant. `git switch` (for branches) and `git restore` (for files) were
  added later specifically to split that one overloaded command into two
  named ones. This term exists so that `git checkout <branch>`, encountered
  in older tutorials or existing codebases, is recognized as the same idea
  under a different, older name — not a different concept.
- **Line-ending conversion (LF / CRLF)** *(reappearing from Lesson 0.1)* —
  LF (a single `\n` character) is the line ending git's own stored objects
  always use internally; CRLF (the two characters `\r\n`) is what Windows
  text editors and tools typically write to disk. This lesson's own real
  run reproduces the same warning Lesson 0.1 first explained, this time on
  a file that already existed and is merely being modified, not created —
  proof the conversion isn't a one-time, first-commit-only event, but
  something git checks on every `git add` of content it hasn't stored in
  that exact form before.
- **Isolated work** — the engineering idea this lesson exists to prove, not
  just define: a commit made on one branch has no effect on any other
  branch's history until something later (a merge, not covered until
  Lesson 0.3) explicitly combines them. It exists so that experimenting,
  risking breakage, or trying something that might not work never has to
  put a project's known-good line of history at risk — the cost of a
  mistake is contained to the branch it was made on.

**Objects and methods used**

- **`git branch`**
  - *What it is:* The command that creates a new branch, or, called with no
    arguments, lists every branch that already exists.
  - *Implementation:* `git branch <name>` creates a new branch named
    `<name>`, pointing at whatever commit HEAD currently points to, and does
    **not** move HEAD to it — the newly created branch is not checked out.
    `git branch`, with no arguments, prints one line per existing branch,
    prefixing the currently checked-out one with `* ` and a space, every
    other one with two plain spaces.
  - *Its use:* This lesson's first command — the exact step that turns "one
    line of history" into "two independent lines of history that both
    exist, right now, in this same repository."
  - *Type:* A subcommand of the `git` program, exactly like `git init`,
    `git status`, `git add`, `git commit`, and `git log` before it — a
    standalone CLI executable, not a class or object system.
  - *Responsibility:* Create a new named pointer at HEAD's current commit
    when given a name, or report every branch pointer that currently exists
    and which one HEAD refers to when given none — and nothing else. It
    never changes the working tree, the staging area, or which branch is
    checked out.
  - *Depends on:* An already-initialized repository with at least one
    commit — a brand-new repository with zero commits has no commit for a
    new branch to point at, so `git branch <name>` fails in that state.
  - *Connects to:* Reads HEAD to know which commit a new branch should point
    at; writes a new entry that `git branch` (list form) and `git switch`
    can both then see. `git switch`, this lesson's next unit, is the only
    command that turns a branch this command created into the one actually
    checked out.
  - *Shape:* The boundary between "one line of history" and "more than
    one" — a one-time creation step per branch, not part of the ordinary
    edit/stage/commit cycle Lesson 0.1 already established.
- **`git switch`**
  - *What it is:* The command that changes which branch is checked out —
    moving HEAD to point at a different branch, and updating the working
    tree to match that branch's tip commit.
  - *Implementation:* `git switch <branch-name>` — for example, `git switch
    add-goodbye-line`. On success it prints `Switched to branch
    '<branch-name>'` and nothing else. It requires `<branch-name>` to
    already exist (created by `git branch`, in this lesson) and requires
    the working tree to have no changes that would be overwritten by the
    switch.
  - *Its use:* This lesson's second command — the step that actually moves
    work onto the branch the previous unit created, so anything committed
    next lands on that branch instead of `master`.
  - *Type:* A subcommand of `git`; a mutating command — it changes HEAD and
    the working tree's file contents, but it never creates a commit, stages
    anything, or deletes any branch.
  - *Responsibility:* Point HEAD at the named branch instead of whatever it
    pointed at before, and rewrite every tracked file in the working tree
    to match the content that branch's tip commit recorded for it — nothing
    about the repository's actual commit history changes.
  - *Depends on:* A branch with the given name already existing (this
    lesson's previous unit, `git branch`, creates it); a working tree with
    no uncommitted changes that would conflict with files the target
    branch's tip records differently.
  - *Connects to:* Reads the branch pointer `git branch` created; writes to
    both HEAD and every tracked file in the working tree. Every command run
    after it — `git status`, `git add`, `git commit`, `git log` — reports on
    whichever branch it just switched to, since they all read HEAD to know
    where they currently stand.
  - *Shape:* The boundary between "a branch exists" and "a branch is the
    one currently being worked on" — the actual point where isolated work,
    this lesson's closing idea, becomes possible to demonstrate at all.

**Everything else in the file, not this lesson's subject but still
explained**

- **`git status`**
  - *What it is:* A read-only inspection command that reports the current
    relationship between the working tree, the staging area, and the most
    recent commit.
  - *Implementation:* `git status`, with no required arguments. It prints
    the current branch name (read from HEAD), then lists files under
    headings depending on what it finds — untracked, staged ("Changes to be
    committed"), or, appearing for the first time in this lesson, modified
    but not yet staged ("Changes not staged for commit").
  - *Its use:* Run in this lesson's third unit to make visible, before
    staging anything, that editing `hello.py` on a branch produced exactly
    one specific, named state — not a guess about what "probably" happened.
  - *Type:* A subcommand of `git`; a read-only query, never a mutation.
  - *Responsibility:* Compare the working tree's actual files, whatever is
    currently staged, and the most recent commit against each other, and
    report every difference found, sorted by which of those states it
    currently reflects.
  - *Depends on:* An already-initialized repository; reads the working
    tree's files, the staging area's contents, and HEAD's current branch to
    build its report.
  - *Connects to:* Called after `git switch` (to see what changed relative
    to the newly checked-out branch) and before `git add` (to confirm what
    is about to be staged). Nothing downstream reads its output — it exists
    purely to inform whoever runs it.
  - *Shape:* A diagnostic tool sitting outside the actual commit history,
    exactly as in Lesson 0.1 — running it never changes anything `git log`
    will later show.
- **`git add`**
  - *What it is:* The command that copies a change from the working tree
    into the staging area.
  - *Implementation:* `git add <pathspec>...` — this lesson calls it as
    `git add hello.py`, the same single-file form Lesson 0.1 used.
  - *Its use:* This lesson's bridge between "the file on disk now has two
    lines" and "the next commit will actually include that second line."
  - *Type:* A subcommand of `git`; a mutating command — it changes the
    staging area's contents, never the working tree's files or the
    repository's committed history.
  - *Responsibility:* Copy the current content of exactly the file(s) named
    into the staging area, replacing whatever that area held for those
    specific files before.
  - *Depends on:* The working tree's current file content for whatever
    pathspec is given; an already-initialized repository.
  - *Connects to:* Reads from the working tree; writes into the staging
    area that `git commit`, next, reads from. It is the only bridge between
    those two states.
  - *Shape:* The boundary between "editing files" and "building a commit,"
    identical to its role in Lesson 0.1 — reused here on a different
    branch, not a different mechanism.
- **`git commit`**
  - *What it is:* The command that permanently records whatever is
    currently staged as a new, addressable snapshot in the repository's
    history.
  - *Implementation:* `git commit -m "<message>"`. This lesson's commit is
    the repository's **second** commit, not its root commit — its success
    output therefore starts `[<branch> <hash>]`, without the
    `(root-commit)` marker Lesson 0.1's very first commit printed, because
    this one has a parent commit (the root commit) to link back to.
  - *Its use:* This lesson's actual destination for Unit 3 — the moment the
    second line added to `hello.py` stops being an uncommitted edit and
    becomes a real, permanent, hash-addressed entry in history, on its own
    branch.
  - *Type:* A subcommand of `git`; a mutating command, and the only one
    covered so far that writes into the repository's *permanent* history,
    rather than the staging area or the working tree.
  - *Responsibility:* Take exactly what's currently staged, package it
    together with the message, an author, a timestamp, and a reference to
    the branch's current tip as this new commit's parent, compute the new
    commit's content-derived hash, and move the current branch's pointer
    forward to it.
  - *Depends on:* Something actually staged; a configured author name and
    email (already set, `--local`, in this repository since Lesson 0.1); the
    message text supplied via `-m`.
  - *Connects to:* Reads from the staging area `git add` just filled;
    writes a new entry `git log` can then display; moves the *current*
    branch's pointer forward — specifically `add-goodbye-line`'s pointer in
    this lesson, leaving `master`'s pointer exactly where Lesson 0.1 left
    it.
  - *Shape:* The actual history-creation boundary, unchanged from Lesson
    0.1 — what's new in this lesson is *which* branch's pointer moves when
    it runs.
- **`git log`**
  - *What it is:* A read-only command that prints the commit history
    reachable from the currently checked-out branch's tip, most recent
    commit first.
  - *Implementation:* `git log`, with no required arguments. For each
    commit it finds by walking backward through recorded parents, it
    prints the full hash, the author's name and email, the commit date, and
    the commit message.
  - *Its use:* Run twice in this lesson's third unit — once on
    `add-goodbye-line` to prove the new commit exists there, and once again
    after switching back to `master` to prove, independently, that it does
    *not* exist there.
  - *Type:* A subcommand of `git`; read-only, exactly like `git status`.
  - *Responsibility:* Starting from whatever branch HEAD currently points
    at, walk backward through each commit's recorded parent, and print
    every commit's recorded metadata along the way, newest first — stopping
    only when a commit with no parent (a root commit) is reached.
  - *Depends on:* At least one commit reachable from the current branch;
    an already-initialized repository; HEAD, to know which branch's history
    to walk.
  - *Connects to:* Reads whatever commit `git commit` most recently created
    on the current branch. This lesson is the first place its output
    actually *differs* depending on which branch it's run from — Lesson
    0.1 only ever had one branch to show.
  - *Shape:* The read side of the repository's permanent history, unchanged
    in mechanism from Lesson 0.1 — its output changing between branches in
    this lesson is what makes isolated work directly observable rather
    than merely claimed.
- **`print(...)`**
  - *What it is:* Python's built-in function for writing text to standard
    output.
  - *Implementation:* `print(*objects, sep=' ', end='\n', ...)` — a
    built-in function. `hello.py` now calls it twice: once with
    `"Hello, recoverable history."` (from Lesson 0.1, unchanged), and once,
    new in this lesson, with `"Goodbye, for now."`.
  - *Its use:* The second call is this lesson's actual observable change —
    the concrete, one-line difference that exists on `add-goodbye-line` and
    nowhere else, until a future lesson merges it.
  - *Type:* A built-in free function, part of Python's `builtins` — not a
    class, and not a method requiring an object to call it on.
  - *Responsibility:* Convert its argument(s) to text and write that text,
    followed by a newline, to the program's standard output stream —
    identical responsibility on both calls; only the argument differs.
  - *Depends on:* The value(s) passed as arguments. Nothing about git or
    which branch is currently checked out.
  - *Connects to:* Both calls sit at the top level of `hello.py`, one after
    the other; nothing calls either of them in turn — each is a leaf call
    whose only effect is the line it prints when the script runs.
  - *Shape:* Ordinary language-level output, entirely outside git's own
    concerns — unchanged from Lesson 0.1, just called a second time.
- **`cat`**
  - *What it is:* A standard Unix command, available here through Git
    Bash, that prints a file's entire contents to standard output.
  - *Implementation:* `cat <file>` — this lesson calls it as `cat
    hello.py`, with no flags.
  - *Its use:* The concrete, independent proof this lesson's third unit
    needs: not "git says master is unaffected," but the literal file
    content on `master`, read directly, showing only the original one
    line.
  - *Type:* A standalone external program, entirely unrelated to git — the
    operating system (via Git Bash's Unix-like environment) locating and
    running an executable named `cat`, the same mechanism by which `git`
    itself gets run.
  - *Responsibility:* Read the named file's entire contents and write them,
    unmodified, to standard output — nothing else; it has no awareness of
    git, branches, or version control at all.
  - *Depends on:* The file named existing, readable, at the given path in
    the current working tree.
  - *Connects to:* Reads whatever `git switch`, run immediately before it,
    left on disk for `hello.py` — it is the tool this lesson reaches for
    specifically because it reads the working tree directly, independent of
    anything git itself reports.
  - *Shape:* A verification tool sitting entirely outside git, included
    here for the same reason `git log`'s independent read-only check
    mattered in Lesson 0.1: proof, not a repeated claim from the same
    system being tested.

## Concept Unit: The Branch

### The Problem

Right now, `code/00-git-workflow/`'s entire history is one straight line:
a single commit, on a single branch, `master`. Suppose a small change is
wanted — adding a second line to `hello.py` — but there's no guarantee yet
that it's the right change, or that it won't need to be abandoned partway
through. If it were committed directly onto `master`, and it turned out to
be wrong, `master` — the one line of history everything else in this
project depends on — would carry that mistake permanently, unless it were
somehow undone after the fact. Before any risky change is made, there needs
to be a way to try it somewhere that isn't `master`, without duplicating
the entire project to do so.

called, based on the vocabulary Lesson 0.1 already used? And once created,
do you expect your very next command to automatically happen "inside" that
new place, or would you expect a separate step to actually move there?

### Mechanical Walkthrough

The New Code above is one line: `git branch add-goodbye-line`. Enumerated
in order:

- **`git`** — the name of the program being invoked. Not a git concept at
  all, exactly as in every unit of Lesson 0.1: the operating system
  locating and running an executable named `git`.
- **`branch`** — the subcommand argument selecting git's branch-management
  operation, given full treatment above under Objects and methods used: in
  this form (a name follows it), it creates a new branch pointer at

- **`add-goodbye-line`** — the argument naming the new branch. Not a git
  concept — a plain identifier, chosen here (as opposed to something
  generic like `branch1`) so that anyone listing branches later can tell

  the identical reasoning a commit message earns its own real content
  instead of a placeholder like `"update"`, just applied to a branch's name
  instead of a commit's message.

### CS Lens

A branch is a specific case of **indirection through a mutable
pointer**: instead of a commit hash being written down directly wherever
"the current state of this line of work" needs to be referenced, a named
pointer sits in between, and that pointer can be moved to reference a
different commit later without anything that used the *name* needing to
change.

```
Also recognized in: a DNS record pointing a domain name at a changing IP
address, a database's "latest" symlink pointing at whichever backup file is
newest, a compiler's vtable pointing at whichever method implementation
actually applies, an operating system's symbolic link
```

Every one of those systems makes the same trade for the same reason: fixing
a name to point at something that can itself change means everything that
uses the name stays correct automatically, without having to be updated
every time the underlying thing does.

### SE Lens

The alternative to branching that Lesson 0.1's own SE Lens already
named as a bad instinct — manually copying the whole project folder
(`project-v2`, `project-experiment`) before trying something risky —
applies here with an extra cost specific to git: a folder copy has no
shared history with the original at all. Two independently copied folders
can never be recombined by git into one project's history later; whatever
value came from the experiment has to be manually re-applied, by hand, back
into the real project. A branch's upfront cost — one command, one new name
to choose — buys something a folder copy cannot: a *real* shared ancestor
(the commit both `master` and `add-goodbye-line` currently point at) that a
future merge (Lesson 0.3) can use to combine the two lines back into one,
automatically, without anyone manually re-typing the change. This project
is not yet carrying any debt from this choice — a freshly created branch
costs nothing until something is actually committed on it, which is
exactly what this lesson's third unit does next.

### Commands Needed

- **`git branch`** — used here with one argument, the new branch's name.
  Run from inside the repository, with at least one existing commit.
  Success output for the create form is nothing at all; the list form

  line per branch, current one prefixed `* `. Failure (not encountered in
  this lesson's real run) would occur if run in a repository with zero
  commits, or if a branch with the given name already exists.

## Concept Unit: Switching Branches

### The Problem

`add-goodbye-line` now exists, but the previous unit's own `git branch`
listing still showed `master` marked with `* ` — HEAD, the record of which
branch is currently checked out, never moved. If `hello.py` were edited and
committed right now, without anything else happening first, that commit
would land on whichever branch HEAD still points to — `master` — exactly
the outcome the previous unit's branch was created to avoid. Creating a
branch and actually working on it are two different steps.

*Pause and try:* Given that `git branch` only created a pointer without

you've encountered in other tools (an IDE switching between open files, a
TV switching between channels)? Once that command runs, what do you expect
`git status`'s first line — `On branch <name>` — to say afterward, compared
to what it said before? And what do you think happens to `hello.py`'s
actual content on disk the moment that switch happens, given that `master`
and `add-goodbye-line` currently point at the exact same commit?

- **Change type:** Configure — HEAD is repointed; no new commit, no file

- **Dependencies:** The branch `add-goodbye-line` must already exist (the

### CS Lens

Switching branches is the direct counterpart to the previous unit's
indirection idea: if a branch is a mutable pointer, HEAD is **a pointer to
whichever pointer is currently active** — a second layer of indirection,
letting "the branch I'm working on" itself be swapped without any single,
fixed name ever needing to change.

```
Also recognized in: a text editor's "active tab" among several open files,
a video game's active save slot among several saves, a multi-user
system's "current user" session pointer, a build system's active
configuration profile among several defined ones
```

Every one of those systems separates "the things that exist" from "the one
currently in focus" using exactly this same second layer — a pointer whose
whole job is remembering which of several equally real options is the
active one right now.

### SE Lens

The alternative git did not choose here: requiring every command to name
which branch it operates on explicitly (`git commit --branch
add-goodbye-line -m "..."` on every single command), rather than having an
implicit "current" branch at all. That would remove the entire category of
mistake this unit's own *Pause and try* question raised — accidentally
committing to the wrong branch because HEAD was left somewhere unintended
— since there would be no ambient state to get wrong. Its real cost: every
single git command, for the entire rest of this curriculum, would need an
explicit branch argument, even when working on one branch for hours at a
time is the overwhelmingly common case. HEAD's implicit, ambient "current
branch" is the deliberate trade: one extra, easy-to-forget state to keep
track of (a real cost — forgetting to switch before committing is a common
real-world mistake), in exchange for every ordinary command staying as
short as Lesson 0.1 already showed it.

### CS Lens

Isolated work is a direct application of the CS Lens both prior units
already named: because a branch is a movable pointer (Unit 1) and HEAD
determines which one is currently active (Unit 2), a commit — which only
ever moves the *current* branch's pointer — physically cannot affect any
pointer it isn't currently attached to. This specific consequence, several
independent lines of history coexisting in one system without interfering,
is itself a recognizable pattern:

```
Also recognized in: a database's isolated transactions (changes in one
transaction are invisible to others until committed), a filesystem's
copy-on-write snapshots, a programming language's separate call stacks for
separate threads, parallel universes in a version-controlled configuration
system (separate environments — staging, production — that don't affect
each other until a deliberate promotion step)
```

Every one of those systems draws the same boundary for the same reason:
work that might be wrong, incomplete, or still in progress needs a
container whose boundaries are enforced by the system itself, not by the
person doing the work remembering to be careful.

### SE Lens

The alternative already named in Unit 1's own SE Lens — committing directly
to `master` and hoping nothing breaks — has a cost this unit can now state
precisely, having actually proven what a branch avoids: if `"Goodbye, for
now."` had turned out to be wrong, or unfinished, or needed to be
abandoned, undoing it on `master` would mean rewriting or reverting

landed on `add-goodbye-line` instead, abandoning it costs nothing more than
deleting that one branch (a command this curriculum doesn't need yet);
`master` was never at risk in the first place. This is the actual payoff of
every command this lesson has run: one extra branch, one extra switch, in
exchange for `master` never having to absorb a mistake before it's ready
to.
