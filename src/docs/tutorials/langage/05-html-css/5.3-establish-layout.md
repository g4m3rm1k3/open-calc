## Terms used in this lesson

- **Stylesheet** — a real, separate file holding CSS rules, kept apart
  from the HTML document it styles. It exists so that a page's own
  structure (this project's own `index.html`) and a page's own
  appearance (this lesson's own new `styles.css`) can be authored,
  read, and changed independently of one another — the same real
  separation of concerns Lesson 5.1 already named for `<header>`,
  `<main>`, and `<footer>`, applied here to structure versus appearance
  at the level of whole files instead of individual elements.
- **CSS rule** — one real, complete instruction inside a stylesheet:
  a **selector** naming which real element(s) it applies to, followed
  by a **declaration block** — one or more real property/value pairs,
  wrapped in curly braces — stating what should change about them. This
  lesson's own real file is nothing more than three of these, one after
  another.
- **Selector** — the part of a CSS rule naming which real elements a
  declaration block applies to. This lesson's own real selectors,
  `body` and `main`, are both real, plain **element type selectors** —
  the simplest kind, matching every real element in the document with
  that exact tag name.
- **Declaration** — one real property/value pair inside a CSS rule's own
  declaration block (`margin: 0;`, one real example from this lesson's
  own code), ended by a semicolon. It exists as CSS's own basic unit of
  "change one specific thing" — a rule is really just a named target
  plus a real list of these.
- **`display` property (`flex` value)** — a real CSS property
  controlling how a real element and its own direct children
  participate in layout at all. MDN's own documentation, fetched and
  quoted this session, states the specific value this lesson's own code
  uses plainly: "To create a flex container, set the area's `display`
  property to `flex`. When we do this, the direct children of that
  container become **flex items**." It exists because a browser has to
  be told, explicitly, which of several real layout algorithms to use
  for a given element's own children — flexbox, this lesson's own real
  choice, is one of several real options CSS provides.
- **Flex container / flex item** — per this lesson's own Terms entry
  for **`display` property**: a **flex container** is any real element
  with `display: flex` set on it; its own direct children automatically
  become real **flex items**, arranged along that container's own real
  layout algorithm rather than the ordinary, default document flow every
  element has used until now.
- **Main axis / `flex-direction` property** — per MDN's own
  documentation, fetched and quoted this session: "The main axis is
  defined by `flex-direction`, which has four possible values: `row`,
  `row-reverse`, `column`, `column-reverse`." It exists because a flex
  container needs one real, explicit direction to arrange its own
  children along — this lesson's own real code chooses `column`, per
  that same documentation, meaning "the main axis will run in the
  **block direction**, from the top of the page to the bottom" — the
  literal, real reason `<header>`, `<main>`, and `<footer>` end up
  stacked vertically rather than side by side.
- **`vh` unit (viewport height)** — a real, relative CSS length unit,
  distinct from a fixed unit like `px`. MDN's own documentation, fetched
  and quoted this session, states its exact real meaning: "`1vh` is 1%
  of the viewport height. For example, if the viewport height is
  `300px`, then a value of `70vh` on a property will be `210px`." It
  exists because a fixed pixel height could never account for how tall
  an actual browser window really is on a given real device; `vh`
  recomputes itself against whatever the real viewport's own current
  height happens to be.
- **`flex-grow` (the `flex: 1` shorthand)** — a real CSS property
  controlling how a flex item shares any real, leftover space along its
  own container's main axis. MDN's own documentation, fetched and
  quoted this session, states its real mechanism directly: "With the
  `flex-grow` property set to a positive integer, if there is available
  space, the flex item can grow along the main axis from its
  `flex-basis`." This lesson's own real code uses the `flex` shorthand,
  which MDN's own documentation states "allows you to set the three
  values in this order — `flex-grow`, `flex-shrink`, `flex-basis`" —
  `flex: 1`, this lesson's own real value, sets only the first of the
  three, leaving the other two at their own real, sensible defaults.

so, deliberately, exactly the way this unit's own real, direct
screenshot contrast proved `<header>` and `<footer>` staying their own
natural size while only `<main>`, the one element actually given `flex:
1`, grew to fill the rest. The real alternative not chosen: flexbox
could instead have divided leftover space evenly among every flex item
by default, the way, for a real contrasting example, three equal-width
table columns often do without anyone asking for that specifically.
The real cost that alternative would have introduced here: `<header>`
and `<footer>`, both real, short, fixed-content regions with no real
reason to grow at all, would have been stretched to consume a third of
the page's own real leftover space each, visually wrong for what they
actually are — real, deliberate, per-item control, this lesson's own
`flex: 1` demonstrates directly, is exactly what avoids that.
