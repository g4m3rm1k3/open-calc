## Terms used in this lesson

- **Element** — the basic structural unit of HTML: a named, possibly-
  nested unit of content, normally written as a start tag and a matching
  end tag with content between them (`<title>Data</title>`), or, for a
  small, fixed set of **void elements** that can never contain content,
  a single tag with no matching end tag at all (`<meta charset="UTF-8">`,
  used exactly this way later in this lesson). It exists because HTML
  describes *structure*, not a sequence of instructions to execute —
  every element names what its content *is*, not what to *do* with it,
  the same underlying idea Java's and Kotlin's own class declarations
  (Lessons 2.2, 3.2) named a *shape* rather than a sequence of steps,
  applied here to markup instead of a running program.
- **Attribute** — a name/value pair written inside an element's own
  opening tag (`lang="en"`, `charset="UTF-8"`, both used in this
  lesson), supplying extra information about that specific element
  without changing what kind of element it is. It exists because an
  element's own name alone is rarely enough information — `<html>` alone
  says nothing about *which* human language the document is written in;
  `<meta>` alone says nothing about *which* character encoding to use.
  Both gaps are filled by an attribute, below.
- **Document Type Declaration (`<!DOCTYPE html>`)** — a required,
  special, non-element instruction that must be the very first thing in
  a real HTML file, before even whitespace. It exists, historically, to
  let a browser decide how strictly to interpret a given page — this
  lesson's own first Concept Unit proves, with a real fetched
  specification quote and a real observed run, exactly what that
  decision actually is and why it still matters today.
- **Quirks mode / standards mode (`document.compatMode`)** — the two
  real, distinct rendering strategies a browser chooses between for
  every page it loads: **standards mode** (reported as the literal
  string `"CSS1Compat"`) follows the modern CSS and layout specification
  exactly; **quirks mode** (reported as `"BackCompat"`) deliberately
  reproduces specific, real layout bugs from Netscape Navigator 4 and
  Internet Explorer 5, on purpose, so that pages written for those
  browsers in the 1990s don't visually break in a modern one. It exists
  because, per this lesson's own first Concept Unit, the choice between
  the two is not cosmetic — it changes real box-model and layout
  behavior a page's own CSS (starting Lesson 5.3) silently depends on.
- **`lang` attribute** — a global attribute (usable on any element, most
  commonly placed on `<html>` itself) declaring which human language an
  element's own text content is written in, as a short standardized code
  (`en` for English). It exists so that software consuming the page —
  most concretely, screen-reading software for blind and low-vision
  users — knows which language's pronunciation rules to apply, rather
  than guessing or defaulting to whatever language the software itself
  happens to be configured for.
- **Paragraph element (`<p>`)** — a block-level element grouping one
  real unit of running, human-readable text. It appears once in this
  lesson's own second Concept Unit, inside a throwaway lab file, purely
  as ordinary filler content proving that lab's own real point (about
  `<html>`/`<head>`/`<body>`, not about `<p>` itself) — included here
  regardless, per the Vocabulary Extraction Rule, because it's real text
  shown in a real lab code block, not because this lesson teaches it as
  its own subject.
- **Root element (`<html>`)** — the single element every other real
  element in an HTML document nests inside, with no exception; per this
  lesson's own second Concept Unit, a real, guaranteed fact about every
  parsed HTML document, not merely a strong convention authors happen to
  follow. It exists to give the document exactly one top-level container
  a language attribute, or any other document-wide attribute, can be
  attached to.
- **`<head>` element** — the direct child of `<html>` holding the
  document's own *metadata*: information *about* the document (its
  title, its character encoding) that is not itself part of what a
  reader sees rendered on the page. It exists to give metadata a
  dedicated home, structurally separate from the actual visible content
  in `<body>`, below — the same underlying split as a file's own
  metadata (a "last modified" timestamp, an author field) being kept
  separate from the file's actual content.
- **`<body>` element** — the direct child of `<html>`, and its only other
  real child besides `<head>`, holding every element a reader actually
  sees rendered on the page. It exists as the direct counterpart to
  `<head>`: everything genuinely part of the page's own visible content
  lives here and nowhere else.
- **Character encoding** — the real, specific mapping a piece of
  software uses to translate a sequence of raw bytes on disk into actual
  displayed characters. It exists because text is never stored as
  letters themselves — only as numbers — and more than one real,
  incompatible mapping from number to letter has existed historically
  (UTF-8 and ISO-8859-1, both used directly in this lesson's own real
  lab, disagree on what many of the same byte sequences mean).
- **Mojibake** — the real, established term for text rendered as visibly
  garbled, wrong characters because the encoding used to *decode* it
  didn't match the encoding actually used to *write* it in the first
  place. This lesson's own third Concept Unit produces real mojibake on
  purpose, deliberately mismatching the two, to prove character encoding
  is a real, load-bearing decision rather than an invisible detail that
  always sorts itself out.
- **`<title>` element** — a required child of `<head>` giving the
  document a name used in a browser's own tab, in bookmarks, and by
  search engines and screen readers — but, per this lesson's own third
  Concept Unit, never rendered anywhere inside the visible page itself,
  a real, proven contrast with the heading element covered later in this
  same lesson.
- **Semantic element / semantic HTML** — an element whose *name itself*
  conveys real meaning about the kind of content it holds (`<header>`,
  `<main>`, `<footer>`, all covered in this lesson's own fourth Concept
  Unit), as opposed to a generic container element (`<div>`, not used
  anywhere in this lesson) that conveys no meaning at all beyond "a
  box." It exists so that software other than a human eyeball — a
  screen reader, a search engine crawler, a browser extension — can
  understand a page's own real structure without any styling or visual
  layout being present at all, proven directly by this lesson's own
  final screenshot.
- **Landmark (ARIA landmark role)** — a real, standardized category
  (`banner`, `main`, `contentinfo`, among others defined by the
  Accessibility Rich Internet Applications, or ARIA, specification)
  that assistive technology uses to let a user jump directly to a named
  region of a page, the same way a sighted reader's eye jumps straight
  to a page's own header or footer without reading everything in
  between. It exists because, without it, a screen reader user would
  otherwise have to listen through an entire page's own content
  linearly, start to finish, with no way to skip directly to "the main
  content" or "the page footer" the way a sighted user already can just
  by looking.
- **`<header>` element** — per this lesson's own fourth Concept Unit, an
  element representing introductory content for whatever it's placed
  in — most commonly, when placed directly in `<body>` the way this
  lesson's own real code does, the page's own title or branding region.
- **`<main>` element** — per this lesson's own fourth Concept Unit, the
  element representing a document's own primary, central content — the
  one real region a reader or piece of software should treat as "the
  actual point of this page," distinct from navigation, branding, or
  closing material.
- **`<footer>` element** — per this lesson's own fourth Concept Unit, an
  element representing closing content for whatever it's placed in —
  when placed directly in `<body>`, the page's own closing or
  supplementary material.
- **Heading element (`<h1>`–`<h6>`) / document outline** — per this
  lesson's own fifth and final Concept Unit, six distinct elements
  (only `<h1>` actually used in this lesson) whose *number* — not any
  nesting in the markup itself — tells a browser or screen reader how
  deep, in an inferred outline of the whole document, a given heading
  sits. It exists to give a document a real, navigable table of contents
  a reader never has to build by hand.

## Concept Unit: The Document Type Declaration

### The Problem

Every prior phase's own compiler — `g++`, `javac`, `kotlinc`, the C#
compiler `dotnet` drives — refuses outright to produce anything at all
from source code it considers malformed; Lesson 4.1's own real,
observed proof was a hard compile error the moment `std::cout` was used
without its required `#include`. A browser parsing an HTML file behaves
nothing like this: it always produces *something* on screen, even from
badly broken markup, because the real web has always been full of
badly broken markup a browser cannot simply refuse to show. Given that,
how does a browser decide *how* to interpret a page whose markup might
be anywhere from perfectly modern to decades old and badly malformed —
does it pick one single, fixed interpretation for everything, or does
it decide differently per page?

> **Stop and try it yourself first:** Real websites written in the
> 1990s, before any of today's CSS layout rules existed, still have to
> load correctly in a browser built decades later — and real websites
> written *today*, following the current specification exactly, also
> have to load correctly in that same browser. If a single piece of
> information sat at the very top of a page, before anything else, and
> a browser used it to decide "treat this page the old way" versus
> "treat this page the modern way" — what would you, as a browser
> vendor, want that piece of information to look like? And: given that
> most 1990s-era pages were never rewritten and never will be, what do
> you predict a browser does with a page that has *no* such marker at
> the top at all — modern rules, old rules, or something else entirely?

### Introduce the Concept in Isolation

The real, fetched specification text answers this unit's own Socratic

incorrect or missing doctype causes the browser to set the document to
**quirks mode** — this lesson's own Terms entry, above. MDN's own guide

> "In the old days of the web, pages were typically written in two
> versions: One for Netscape Navigator, and one for Microsoft Internet
> Explorer. When the web standards were made at W3C, browsers could not
> just start using them, as doing so would break most existing sites on
> the web. Browsers therefore introduced two modes to treat new
> standards compliant sites differently from old legacy sites."

And, naming the exact real value this lesson's own doctype line
produces:

> "The doctype shown in the example, `<!doctype html>`, is the simplest
> possible, and the one recommended by current HTML standards... all
> existing browsers today will use no-quirks mode for this doctype."

lesson's own Objects-and-methods note above) confirmed this exact,
documented contract directly, using `document.compatMode` — a real,
standard JavaScript property reporting a page's own real, internal
rendering-mode decision as one of two exact string values:

```
lab_doctype_with.html    → compatMode=CSS1Compat
lab_doctype_without.html → compatMode=BackCompat
```

`CSS1Compat` is standards mode's own real reported name (a historical
name, referring to CSS Level 1, kept unchanged ever since for backward
compatibility with code already checking for it); `BackCompat` is
quirks mode's own real reported name. This is real, observed,
first-hand confirmation — not just the cited specification text alone —
that this lesson's own one-line addition is the exact, documented
decision point, matching the real values MDN's own page (fetched and
quoted above) states directly. This is called the **quirks mode /
standards mode** decision, and it is a real, permanent, still-relevant
fact about every HTML page on the modern web, not a historical curiosity
— every page this whole curriculum builds from this lesson forward

### Mechanical Walkthrough

- **`<!`** — the two-character sequence that begins a **markup
  declaration** rather than an ordinary element's own opening tag; no
  other construct in this lesson's own real code starts this way,
  marking the doctype as a genuinely different kind of thing from every
  element that follows it.
- **`DOCTYPE`** — the declaration's own keyword, case-insensitive in
  real HTML (unlike XML's own stricter, case-sensitive equivalent), per
  this lesson's own Terms entry: the literal word a browser's own
  parser checks for at the very start of a file to decide whether a
  doctype is present at all.
- **`html`** — the doctype's own single argument, naming which real
  document type is being declared. This lesson's own version — bare
  `html`, with nothing else after it — is deliberately the shortest
  legal form the current HTML Living Standard defines; older doctypes
  (HTML 4.01's own, or XHTML's own) were real, much longer strings
  naming a specific external Document Type Definition file, not used
  anywhere in this lesson because the modern, short form is what every
  current specification recommends, per this unit's own quoted MDN
  text.
- **`>`** — closes the declaration; per this unit's own Terms entry for
  **Document Type Declaration**, this line is not an element and has no
  matching closing tag of its own the way `<title>...</title>`, seen
  later in this lesson, does.

### CS Lens

**A short, mandatory marker at the very start of a file, used to decide
how everything after it should be interpreted**, is a real, recurring
pattern well beyond HTML's own doctype.

```
Also recognized in: a shebang line (`#!/usr/bin/env python3`) telling a
Unix shell which interpreter should run the rest of a script file; PNG's
own fixed 8-byte file signature, letting an image decoder recognize the
format before reading anything else; HTTP's own request line naming a
protocol version (`HTTP/1.1`) the server uses to decide which rules
govern the rest of the exchange; XML's own `<?xml version="1.0"?>`
processing instruction, doing structurally the same job HTML's own
doctype does, for a different format
```

### SE Lens

The design principle is the **robustness principle** — often stated as
"be conservative in what you send, be liberal in what you accept."
Browser vendors had a real, available alternative: refuse to render any
page that didn't strictly conform to the current specification, the
same way `g++` refuses malformed C++. This was tried for real — XHTML,
a real, stricter HTML variant from the early 2000s, mandated exactly
that: a well-formedness error meant the page didn't render *at all*.
XHTML's own strict mode lost, in practice, precisely because ordinary
authors produced malformed markup constantly, and a browser that
refused to show a page for a stray unclosed tag was a browser nobody
wanted to use. The real, ongoing cost of the *permissive* choice HTML5
actually made: every browser engine has to implement — and keep
identical to every other browser engine — quirks mode's own specific,
frozen-in-time rendering bugs, forever, so that a decision made for
Netscape Navigator 4 in the 1990s still constrains what a browser
released this year is allowed to do differently.

## Concept Unit: The Root Element and the Guaranteed Two-Part Split

### The Problem

A real HTML file is really just a sequence of characters in a text
file — nothing forces an author to actually write a well-formed tree of
nested elements at all. Given that a browser still has to hand some
program (later in this curriculum, JavaScript, via the DOM) a real,
navigable tree structure no matter what the author actually typed, what
happens if an author's own real file is missing pieces of that
structure — does the browser fail, the way `g++` failed on a missing
`#include` in Lesson 4.1, or does something else happen?

> **Stop and try it yourself first:** Suppose a real file contained only
> a `<title>` and a single paragraph of text, with no `<html>`, no
> `<head>`, and no `<body>` written anywhere by hand — the doctype from

> internal tree actually looks like after loading a file like that — a
> broken or incomplete tree missing those three elements, or a complete
> one anyway? If it's complete anyway, where do you think the missing
> pieces come from?

### SE Lens

The principle, again, is the **robustness principle** from this
lesson's own previous unit, applied here to structure instead of
rendering mode — and this unit's own real project change shows the
other side of the same tradeoff deliberately: even though the browser
*would* supply `<html>`, `<head>`, and `<body>` automatically, per this
unit's own real, proven lab, this lesson's own real project writes all

source: the previous unit's own lab file gave no visual indication
anywhere that a `<head>` and `<body>` genuinely exist in the resulting
tree, which is confusing for exactly the same reason an implicit
`return 0;` at the end of C++'s own `main` (Lesson 4.1) was: correct,
but silent, and silent is a real cost when a human — not just a parser —
is the one reading the file. Writing the structure explicitly costs six
extra real lines and gains an unambiguous, self-documenting file every
future lesson in this phase can keep extending without confusion about
what already exists.
