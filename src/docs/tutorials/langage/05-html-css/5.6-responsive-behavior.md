## Terms used in this lesson

- **`display` property (`flex` value)** — per Lesson 5.3's own Terms
  entry, restated here in full: turns an element into a real flex
  container, its own direct children becoming real flex items. This
  lesson's own real code applies it to `<main>` for the first time —
  Lessons 5.3 and 5.4 already used it on `<body>` and `<section>`, but
  `<main>` itself, until now, has only ever used a plain `flex: 1` to
  describe its own relationship to its *parent*, never `display: flex`
  to control its own *children*.
- **`gap` property** — per Lesson 5.4's own Terms entry, restated here
  in full: real, consistent space between a flex container's own real
  children. This lesson's own real code applies it to `<main>` for the
  first time, spacing its own two real sibling sections.
- **Child combinator (`>`)** — a real CSS selector combinator matching
  only an element's own **direct** children, not any more distantly
  nested descendant. MDN's own documentation, fetched and quoted this
  session, states the real, exact contrast this lesson's own code
  depends on: "It matches only those elements matched by the second
  selector that are the direct children of elements matched by the
  first" — stricter, per that same documentation, than the **descendant
  combinator** Lesson 5.5 already used for `.detail article`, which
  "matches all elements matched by the second selector for which there
  exists an ancestor element matched by the first selector, regardless
  of the number of 'hops' up the DOM."
- **Media query** — a real, conditional block of CSS, applied only when
  a stated real condition about the browser or device is true. MDN's
  own documentation, fetched and quoted this session, states its real
  purpose directly: "Media queries allow you to apply CSS styles
  depending on a device's media type... or other features or
  characteristics such as... browser viewport width." It exists because
  every real CSS rule this project has written so far applies
  unconditionally, everywhere, regardless of how large or small the
  real browser window actually is — this lesson's own real problem
  needs a rule that doesn't.
- **Viewport** — the real, visible area of a web page inside the actual
  browser window, excluding the browser's own toolbars and other
  chrome. This lesson's own real media query checks this exact real
  measurement.
- **Breakpoint (`min-width`)** — the real, specific viewport width at
  which a media query's own conditional CSS starts applying. MDN's own
  documentation, fetched and quoted this session, states the real
  mechanism directly: "this CSS will apply styles only if your
  browser's viewport width is equal to or narrower than" a stated
  value, for `max-width`; this lesson's own real code uses `min-width`
  instead, applying its own CSS only once the real viewport is *at
  least* as wide as the chosen breakpoint.
- **Mobile-first** — a real, deliberate CSS authoring order: writing a
  page's own base, unconditional CSS for the narrowest real viewport
  first, then adding wider-viewport CSS inside `min-width` media
  queries layered on top, rather than the reverse. This lesson's own
  real code follows this order directly: every rule this project has
  written before this lesson already applies correctly at a narrow real
  viewport with no media query needed at all, and this lesson's own new
  rule only adds behavior for wider ones.

## Concept Unit: The Media Query — Conditional CSS

### The Problem

The previous unit's own real screenshot proved cards stretch
uncomfortably wide on a real, wide window — but simply shrinking every
card to a fixed, small width would create the identical real problem
in reverse on that same wide window: a narrow column of content

detail) could instead fill productively, side by side, if only there
were real room for both. Given that this project's own real CSS, as it
stands, has no way to say "do this, but only when the window is wide
enough" — what real mechanism would need to exist for that condition to
be expressible in CSS at all?

> **Stop and try it yourself first:** This lesson's own Terms entry for
> **Mobile-first** already states the real order this lesson's own code
> follows: base CSS for a narrow real viewport first, wider-viewport
> CSS layered on afterward. Given that the previous unit's own real,
> narrow screenshot (375 pixels) already looks correct with zero new
> code, and only the real, wide screenshot (1300 pixels) showed a real
> problem, does this lesson's own real fix need to change what happens
> at narrow widths at all, or only add new behavior for wide ones?

### The New Code

```css
@media (min-width: 700px) {
  main {
    display: flex;
    gap: 1rem;
  }

  main > section {
    flex: 1;
  }
}
```

### Mechanical Walkthrough

- **`@media`** — per this lesson's own Terms entry for **Media query**:
  opens a real, conditional block; every real rule inside its own curly
  braces applies only when the stated condition, next, is true.
- **`(min-width: 700px)`** — per this lesson's own Terms entry for
  **Breakpoint**: the real, stated condition — "the real viewport is at
  least 700 real pixels wide" — chosen here specifically because 700
  pixels is comfortably wider than a real phone-sized viewport (the
  375-pixel screenshot above) while still narrower than the real,
  1300-pixel window the previous unit's own screenshot already proved
  needs a real fix.
- **`main { display: flex; gap: 1rem; }`** — per this lesson's own Terms
  entries for **`display` property** and **`gap` property**, both
  restated here in full: turns `<main>` into a real flex container for
  the first time, its own two direct children (the list `<section>` and
  the detail `<section>`) becoming real flex items, spaced by one real
  `gap` unit — this real declaration block only exists inside the media
  query, so it has zero real effect below the 700-pixel breakpoint,
  matching the real, unchanged narrow screenshot above.
- **`main > section`** — per this lesson's own Terms entry for **Child
  combinator**: matches only a real `<section>` that is `<main>`'s own
  **direct** child — both real sections this project has (the list and
  the detail view) qualify, since neither is nested inside the other.
  This is a real, deliberate contrast with Lesson 5.5's own `.detail
  article`, which used a **descendant** combinator (a plain space)
  instead — the correct real choice there, since `<article>` was never
  a *direct* child of `.detail`'s own class name specifically, only of
  the `<section>` carrying it; here, `<section>` genuinely is `<main>`'s
  own direct child, so the *stricter*, more specific real combinator is
  both correct and preferred, per this lesson's own real, explained
  reasoning rather than habit.
- **`flex: 1;`** — per Lesson 5.3's own Terms entry for **`flex-grow`**,
  restated here in full: applied to both real sections equally, this
  real declaration divides `<main>`'s own leftover real space evenly
  between them, the real, concrete reason the wide screenshot above
  shows two roughly equal-width columns rather than one wide and one
  narrow.
