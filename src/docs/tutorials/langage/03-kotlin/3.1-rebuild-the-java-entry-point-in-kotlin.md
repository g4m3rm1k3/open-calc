# Lesson 3.1: A Variable That Declares Its Own Intent (Rebuilding the Java Entry Point in Kotlin)

**What you will build:** A Kotlin source file, `Program.kt`, whose `fun main()`
prints two observable lines — "Service is running." followed by "Service is
running again." — by declaring one local variable and changing its value in
between the two prints. This is the Kotlin port of the very first Java
commit in `code/02-java/Service/`, which did the same two-observable-lines
job by literal repetition rather than reassignment. The transferable
problems this lesson is actually about: (1) Kotlin does not require a
program's starting point to live inside a class at all — `fun` alone,
sitting directly in a file, is enough — and (2) every local binding in
Kotlin has to say, at the moment it's created, whether the compiler should
ever let its value change. Java's own `var` never asked that question; this
lesson finds out what Kotlin asks instead, and why.

**What you need to know first:** Lesson 2.1 (`code/02-java/Service` commit
`0177976`) established the idea of an entry point — a method a language's
own toolchain recognizes and calls first, without the program ever calling
it directly — using Java's `public static void main(String[] args)`
wrapped inside a `public class Program`. Lesson 1.1 established the same
idea for C#. This lesson assumes only that general idea (a designated
starting method, found and invoked by the toolchain, not by any line of
the program's own code) and the basic terminal fluency already built across
Lessons 0.1–2.1 (compiling a source file, then running the compiled
result) — not any specific Java or C# syntax, which this lesson re-derives
for Kotlin from scratch, in full, below.

## Terms used in this lesson

- **Top-level declaration** — a function, property, or other declaration
  written directly in a source file, not nested inside any class, object,
  or interface. Kotlin allows this; Java and C# (before C# 9's own
  top-level-statements feature) require every method to live inside some
  class. This exists because not every routine genuinely belongs to an
  object — Kotlin's designers treated "must be inside a class" as
  ceremony the language shouldn't force when nothing about the routine is
  actually object-shaped.
- **`fun`** — the keyword that declares a function in Kotlin, at top level
  or inside a class. It exists as Kotlin's single, uniform way to
  introduce a function regardless of where that function lives — the same
  keyword names a top-level function, a class's member function, and (as
  later lessons in this phase will show) an extension function.
- **`main`** — not a keyword, but a *recognized name*: when a Kotlin file
  compiles to a JVM program, the compiler looks for a function literally
  named `main` (either top-level, taking no arguments or a single
  `Array<String>`, or — for older Kotlin versions — as a certain
  `@JvmStatic` member) and wires the JVM's own program-launch mechanism to
  call it first. This exists so a Kotlin program has exactly one
  unambiguous place execution begins, the same problem Java's own `main`
  convention and C#'s own `Main` convention both solve, just spelled with
  a lowercase `m` here because Kotlin's own naming convention lowercases
  function names uniformly, entry point included.
- **Function body block (`{ }`)** — the pair of braces delimiting the
  statements that run when a function is called. It exists to give the
  compiler an unambiguous start and end for "everything this function
  does," the same job curly braces do in Java and C#, which this lesson's
  code reuses verbatim.
- **String literal (`"..."`)** — text written directly in source code,
  delimited by double quotes, that the compiler turns into a real string
  value with no computation needed to produce it. It exists so a program
  can name a fixed piece of text without building it at runtime.
  Kotlin's double-quoted literal syntax is the same syntax Java and C#
  already use for this; nothing about it is new here except that it is
  being read again, in full, per the Repetition Rule this curriculum
  follows.
- **`val`** — a keyword that declares a *read-only* local binding (or,
  outside a function, a read-only property): once a `val` is assigned a
  value, the compiler refuses to compile any later statement that tries
  to assign it a different one. It exists to let a programmer state, in
  the declaration itself, a promise the compiler will actually enforce —
  "this name will never point at anything else after this line" — rather
  than that promise living only as an unenforced comment or convention.
- **Assignment operator (`=`)** — the operator that gives a variable or
  property its value, evaluated right-to-left: the expression on the
  right is evaluated first, and its result becomes what the name on the
  left refers to. It exists as the basic mechanism by which any binding —
  `val` or `var` — actually acquires a value in the first place; without
  it, a declaration would just be a name with no content.
- **Type inference** — the compiler working out a value's type from the
  expression assigned to it, without the programmer writing the type out
  by hand. It exists so a programmer isn't forced to restate information
  the compiler can already see for itself — `"Service is running."` is
  unambiguously a `String`; writing `val message: String = "Service is
  running."` would say that twice. Kotlin infers a type for *every*
  declaration that omits an explicit one, whether the binding is `val` or
  `var` — inference and mutability are two separate, independent
  questions the compiler answers about the same declaration, which
  matters directly below when comparing this to Java's own `var`.
- **`var`** — a keyword that declares a *reassignable* local binding (or
  property): after a `var` is first assigned a value, a later statement
  may assign it a different one, and the compiler allows it. It exists as
  `val`'s counterpart — the explicit way to say "this name's value is
  expected to change over its lifetime," the same enforced promise `val`
  makes, just the opposite promise.
- **Reassignment** — a later assignment statement that gives an
  *already-declared* variable a new value, using its name and `=` again
  with no `val`/`var` keyword in front (a keyword there would instead
  declare a brand-new binding). It exists as the mechanism `var` actually
  permits and `val` actually forbids — the concept both keywords are
  ultimately arguing about.
- **Java's `var`** (reappearing from Lesson 2.2, given full treatment
  again here) — Java's own `var` (introduced in Java 10) is *only* a
  type-inference instruction to the compiler: writing `var service = new
  Service(logger);` instead of `Service service = new Service(logger);`
  tells the compiler to work out `service`'s type from the right-hand
  side, exactly like Kotlin's own inference above. Java's `var` says
  nothing whatsoever about whether `service` can later be reassigned — a
  Java local declared with `var` can always be reassigned unless it is
  *also* separately marked `final`, the same rule that governs every
  other Java local variable. One keyword, one question answered
  (inference); mutability is a wholly separate, optional add-on
  (`final`) that most Java code never bothers to write. This is the exact
  point this lesson's own Socratic prompts, below, ask the reader to
  reason through before being told the answer.
- **Compiler diagnostic (compile-time error)** — a message the compiler
  produces instead of a compiled program, when the source code violates a
  rule the compiler enforces before any code ever runs. It exists as the
  mechanism that makes a rule like "`val` cannot be reassigned" a real,
  checked guarantee rather than a style preference — the difference this
  lesson's second Concept Unit exists to prove with a real, pasted error,
  not just assert in prose.

## Objects and methods used

- **`println`**
  - *What it is:* A top-level function in Kotlin's standard library that
    writes a value's text representation to standard output, followed by
    a line separator.
  - *Implementation:* Real source, fetched this session from
    `libraries/stdlib/jvm/src/kotlin/io/Console.kt` in the JetBrains/kotlin
    repository at tag `v2.4.10` (the exact version this lesson's `kotlinc
    -version` reported):

    ```kotlin
    public actual inline fun println(message: Any?) {
        System.out.println(message)
    }
    ```

    This is the overload that resolves for this lesson's calls — Kotlin's
    stdlib also declares dedicated `println` overloads for `Int`, `Long`,
    `Byte`, `Short`, `Char`, `Boolean`, `Float`, `Double`, and `CharArray`,
    but none for `String`, so a `String` argument (this lesson's only
    argument type) resolves to the `Any?`-typed overload shown above. It
    is marked `inline`, meaning the compiler substitutes this function's
    own body directly at every call site instead of emitting a real
    method call — so `println(message)` becomes, after compilation,
    exactly the same bytecode as writing `System.out.println(message)` by
    hand. There is no hidden mechanism between Kotlin's `println` and
    Java's own `System.out.println`; this *is* it.
  - *Its use:* This lesson's only way to produce an observable result —
    every version of "Service is running." this lesson prints, in every
    Concept Unit, goes through this one function.
  - *Type:* A top-level (not a member of any class), `public`, `inline`
    function. Signature: `fun println(message: Any?): Unit`.
  - *Responsibility:* Converting any value (or `null`) to its text form
    and writing that text, followed by a newline, to the process's
    standard output stream — nothing more; it does not format, does not
    buffer beyond what `System.out` itself buffers, does not validate its
    argument.
  - *Depends on:* `System.out` — a `java.io.PrintStream` the JVM sets up
    before any Kotlin or Java code runs, wired to the process's real
    standard output.
  - *Connects to:* Called directly by this lesson's own `main` function,
    once per Concept Unit's real code; calls `System.out.println` in
    turn, which is Java standard library code, not this lesson's own.
    Nothing calls `println` *for* this lesson's code — it is a leaf call,
    the last step before output leaves the program.
  - *Shape:* A public API surface — the boundary between this lesson's own
    code and the JVM's standard output stream.

## Concept Unit: The Class-less Entry Point

### The Problem

Java's own entry point has needed a class just to hold it — Java's
`Program` class in Lesson 2.1, wrapping a single `main` method that does
the actual work, because Java requires every method, without exception,
to live inside some class. (C#'s own `Program.cs` — checked fresh this
session via `git show`, its very first commit — has never actually had
one: `code/01-csharp/Service` used C#'s own top-level-statements feature,
which lets a `.cs` file's own statements run directly with no `class
Program`/`static void Main` wrapper at all, from its very first real
commit onward. C# only *requires* that wrapper if a project's own
`.csproj` doesn't opt into top-level statements — this curriculum's own
C# project already opted in, before Lesson 3.1 was ever written.)
Porting Java's exact first commit (`code/02-java/Service/Program.java`
at commit `0177976`, quoted in full below) into Kotlin raises an
immediate, concrete question: does Kotlin need Java's own wrapping
class, or was it only ever there because Java specifically requires it —
with C#'s own real history already suggesting the answer might be
"only Java"?

> **Stop and try it yourself first:** Java requires *every* method,
> without exception, to be declared inside some class or interface — a
> method cannot exist "loose" in a `.java` file. Does that same
> requirement sound like something the *language* is enforcing, or
> something the *problem* (printing one line) actually needs? If Kotlin
> turned out to allow a function with no enclosing class at all, what
> would you expect the resulting file to look like — try sketching it
> before reading on. And: if there's no class, what part of the file
> would a Kotlin compiler have to search for by *name* alone (rather than
> by "the method inside class `Program`") to know where the program
> starts?

### Mechanical Walkthrough

Enumerating every distinct syntactic element in the New Code block above,
in order:

- **`fun`** — declares a function. This is the *first* appearance, in
  this curriculum's own Kotlin code, of a function declaration written
  with no enclosing class at all — matching Java's own `main`, which
  always sat inside a class body, per Java's own language rule requiring
  it universally. `fun` here is written directly in the file, at the
  outermost level a Kotlin file has — this is exactly the **top-level
  declaration** concept, above: Kotlin does not require an object to own
  a function before that function can exist, because not every routine
  represents behavior belonging to some object. A print statement that
  runs once at startup is a genuine example of behavior with no natural
  owning object — forcing it into a class, the way Java does, doesn't describe anything
  true about the problem; it's a rule Java's own compiler imposes
  regardless of whether the code's actual shape wants a class.
- **`main`** — the function's name. Nothing about the *word* `main` is
  special to the Kotlin *language* — it is not a keyword, and a function
  named `main` declared somewhere other than as this file's real entry
  point is just an ordinary function. What makes it special is
  toolchain-level convention: when `kotlinc` compiles a `.kt` file to a
  JVM class and that file contains a top-level function literally named
  `main`, the compiler generates a real `public static void main(String[]
  args)` method on the file's synthetic class (visible, later in this
  same unit's Commands step, as `ProgramKt.main`) and the JVM launches
  that generated method exactly the way it would launch a hand-written
  Java `main`. Kotlin did not invent a new entry-point mechanism here —
  it reuses the JVM's own, and generates the Java-shaped method the JVM
  already knows how to find.
- **`()`** — an empty parameter list. This lesson's `main` takes no
  parameters at all — Kotlin permits `fun main()` with zero parameters,
  unlike Java, which requires `String[] args` to be present in its `main`
  signature even when the program never reads it (as Java's own
  `Program.java`, quoted above, never does). Kotlin also accepts `fun
  main(args: Array<String>)` when command-line arguments are actually
  needed; this lesson's program never reads any, so the empty-parameter
  form is both valid and the honest choice — writing an unused parameter
  only to satisfy the language would be exactly the kind of ceremony this
  phase's own "less ceremony" framing is about removing.
- **`{` ... `}`** — the function body block. Identical in purpose to the
  same braces in every C# and Java method body already written in this
  curriculum: they mark where the function's statements begin and end.
  Kotlin reuses this exact C-family block syntax rather than inventing
  its own.
- **`println(...)`** — a call to the `println` function, given its own
  full Objects-and-methods entry above (its real implementation, its
  responsibility, and its connection to `System.out.println`).
- **`"Service is running."`** — a string literal, described in Terms
  above: fixed text the compiler turns directly into a `String` value,
  with no runtime computation needed to produce it. It is the exact same
  text Java's own `Program.java` (quoted in Project Change, above) prints
  — the literal itself needed no translation between languages; only the
  surrounding syntax did.

### CS Lens

A function that exists without belonging to any object is not a Kotlin
invention — it is Kotlin choosing *not* to force object-orientation onto
code that isn't actually shaped like an object's behavior, an idea far
older than Kotlin itself and present in most languages that don't
mandate pure OOP.

```
Also recognized in: Python's bare `def` functions and its
`if __name__ == "__main__":` convention, JavaScript/Node's module-level
code with no enclosing class required, Go's package-level `func`
declarations, Rust's free functions declared outside any `impl` block,
C's own functions (which were never inside anything to begin with)
```

### SE Lens

The design principle here is **not forcing an abstraction where the
problem doesn't have one**. Java's alternative — mandatory class
membership for every method — was a real, deliberate design decision made
for Java specifically (every piece of code visibly belongs to some class,
which simplifies reasoning about where behavior lives, and matches Java's
own "everything is an object" philosophy consistently). The tradeoff Java
accepts is exactly what this Concept Unit's Reference Source shows: a
program whose entire real behavior is "print one line" still has to
manufacture a `Program` class to hold it, and every reader has to look
*through* that class to find the one line that matters. Kotlin's
alternative accepts a different cost: behavior can now live in two
places — top-level or class-member — so a reader has to know both
possibilities exist before source code can be located with confidence.
Kotlin's own designers judged that cost worth paying because so much real
code (utility functions, entry points, small standalone operations) never
had a natural owning object to begin with; forcing one, in their
judgment, added a class to search through without adding any real
information.

### Commands Needed

- `kotlinc Program.kt -include-runtime -d Service.jar` — invokes the
  Kotlin compiler (`kotlinc`) on `Program.kt`. `-include-runtime` bundles
  the small Kotlin standard-library classes the compiled program needs
  (like the real `println` shown above) directly into the output jar, so
  the result can run with nothing but a plain JVM — without this flag,
  running the jar would fail unless Kotlin's runtime jars were separately
  placed on the classpath. `-d Service.jar` names the output file.
  Success looks like: no output at all — a clean compile prints nothing,
  the same convention Java's own `javac` uses.
- `java -jar Service.jar` — runs the compiled program the ordinary JVM
  way, since `-include-runtime` already bundled everything the jar's
  manifest needs to be self-contained and directly executable.

## Concept Unit: `val` — A Promise the Compiler Checks

### The Problem

The line `println("Service is running.")` repeats the same literal text
directly inside the call. If this program later needed to print that same
message a second time — which, as the header's own "What you will build"
already previews, it will, in the very next Concept Unit — writing the
literal out twice would mean two separate places that both have to be kept
in sync by hand. Naming the value once and reusing the name is the obvious
fix.

> **Stop and try it yourself first:** In basic Python (which the header's
> own Assumptions this whole curriculum work from say you already know),
> writing `message = "Service is running."` creates a name that can
> always be reassigned later — Python enforces no restriction at all.
> Given that Kotlin has already shown, in the unit just finished, that it
> is willing to enforce real rules the compiler checks (unlike a
> convention or a comment), what would you guess a *read-only* named
> value looks like in Kotlin — a keyword before the name, the same as
> `fun` sat before a function's name? And once you've named a value, what
> do you predict happens if the code tries to give that same name a
> second value later — does Kotlin allow it silently, warn about it, or
> refuse to compile?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Program.kt`, demonstrating only `val`:

```kotlin
fun main() {
    val greeting = "Hello, val."
    println(greeting)
}
```

Run this session (`verification/3.1/lab_val.kt`):

```
Hello, val.
```

This proves `val` can be declared, given a value with `=`, and read back
by name — nothing about `val` prevents *using* the value, only changing
it, which the next real, run proof below demonstrates directly. This
read-only kind of local binding is called a **`val`**.

Now the enforcement claim itself, proven rather than asserted — a second
throwaway file that tries to reassign a `val`:

```kotlin
fun main() {
    val greeting = "Hello, val."
    greeting = "Goodbye, val."
    println(greeting)
}
```

Attempting to compile this file this session
(`verification/3.1/lab_val_reassign_fails.kt`) with the exact same
`kotlinc` invocation used for every other file in this lesson:

```
lab_val_reassign_fails.kt:3:5: error: 'val' cannot be reassigned.
    greeting = "Goodbye, val."
    ^^^^^^^^
```

This is a real **compiler diagnostic**, not a guess about what Kotlin
"probably" does — the compiler refuses to produce a program at all. The
promise `val` makes is not a style convention a reader has to trust; it's
a rule the compiler checks before the code can even run.

### Mechanical Walkthrough

- **`val`** — declares `message` as a read-only local binding, per the
  Terms entry above and the real compiler proof just shown: once line 2
  runs, no later line in this function is allowed to give `message` a
  different value, and the compiler — not a linter, not a convention —
  is what enforces that.
- **`message`** — the chosen name for this binding. Naming it is what
  makes reuse possible at all; an unnamed literal, as in the previous
  unit, can only ever be used once, at the exact place it's written.
- **`=`** — the assignment operator, per its Terms entry above: the
  right-hand string literal is evaluated (trivially — a literal evaluates
  to itself) and that value becomes what `message` refers to.
- **`"Service is running."`** — the same string literal already explained
  in the previous unit's walkthrough, given here in full again per the
  Repetition Rule: fixed text the compiler turns directly into a `String`
  value.
- **(no explicit type)** — neither `val message` nor anything after it
  names a type directly; **type inference**, per its Terms entry above,
  is what the compiler is doing here. Because the right-hand side is
  unambiguously a `String` literal, the compiler infers `message`'s type
  as `String` without it ever being written — equivalent, in effect, to
  writing `val message: String = "Service is running."` by hand, just
  without the redundant restatement.
- **`println(message)`** — a call to the same `println`, given its full
  Objects-and-methods entry above, now passed a *name* instead of a
  literal. Because `message`'s inferred type is `String`, and Kotlin's
  stdlib declares no `println` overload specific to `String`, this call
  resolves to the exact same `println(message: Any?)` overload the
  previous unit's literal-argument call resolved to — passing a named
  `String` through a variable changes nothing about which overload runs
  or what it does.

### SE Lens

The principle here is **naming as documentation the compiler can verify**.
The alternative — leaving the literal inline, as Java's own first commit
did — costs nothing when a value is used exactly once, which is exactly
why Java's original commit didn't bother naming it. The real cost that
naming avoids only shows up once a value needs to be *reused*, which is
precisely the situation the next Concept Unit creates on purpose. Naming
it here, one unit ahead of that need, means the next unit can focus
entirely on `var` itself rather than also having to introduce naming as a
new idea at the same time — a real, deliberate sequencing choice, not
free of cost (this unit's own code technically does no more than the
previous unit already did; the payoff arrives one unit later).

## Concept Unit: `var` — and Why It Isn't Java's `var`

### The Problem

The program now needs to print a *second*, different line — "Service is
running again." — right after the first, using the same `message` name
rather than introducing a second one (introducing `message2` or similar
would just recreate the duplication problem the previous unit's naming
was meant to solve). But `message` is a `val`: the previous unit's own
real, pasted compiler error already proved that reassigning a `val` is
refused. Something has to change about how `message` is declared before
it can be given a second value.

> **Stop and try it yourself first:** Given that `val` is the read-only
> option, what do you predict the reassignable option is spelled as in
> Kotlin — is it likely to be a completely unrelated word, or something
> that pairs naturally with `val` the way `true`/`false` or `if`/`else`
> pair? Now the harder question, the one this lesson's own header framed
> from the start: Java's `var` (already fully re-explained in this
> lesson's Terms, above) lets the compiler infer a type and says nothing
> about mutability — a Java `var` local can always be reassigned. If
> Kotlin's `val`/`var` split is real and enforced (which the previous
   unit already proved with a real compiler error), does that mean
> Kotlin's `var` is doing *the same job* as Java's `var`, or a
> *narrower* one? Try stating, in one sentence, exactly what Java's `var`
> promises and exactly what you'd expect Kotlin's `var` to promise,
> before reading on.

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Program.kt`, demonstrating only `var`:

```kotlin
fun main() {
    var greeting = "Hello, var."
    println(greeting)
    greeting = "Goodbye, var."
    println(greeting)
}
```

Run this session (`verification/3.1/lab_var.kt`):

```
Hello, var.
Goodbye, var.
```

Two real, distinct lines of output, from the same `greeting` name printed
twice with a reassignment in between — proof that a `var`-declared local
accepts a second assignment that an identically-shaped `val` declaration,
per the previous unit's own real compiler error, refuses outright. This
reassignable kind of local binding is called a **`var`**.

### Mechanical Walkthrough

- **`var`** (line 2, replacing `val`) — declares `message` as a
  reassignable local binding, per its Terms entry above. Changing this
  one word is what makes line 4's reassignment legal at all; with `val`
  still in place, line 4 would fail to compile with the exact same
  `'val' cannot be reassigned` error the previous unit's own throwaway
  lab already produced for real — this program's own line 4 is, in
  effect, the previous unit's failing lab turned into something that's
  now allowed to succeed, by changing exactly one keyword.
- **`"Service is running."`** (line 2) — the same string literal already
  explained twice above, given full treatment again here per the
  Repetition Rule: fixed text becoming a `String` value with no runtime
  computation.
- **`println(message)`** (line 3) — the same `println` call already
  explained in full in this lesson's Objects-and-methods section and in
  the previous unit's walkthrough, reading `message`'s first value.
- **`message = "Service is running again."`** (line 4) — a
  **reassignment**, per its Terms entry above: no `val` or `var` keyword
  appears here, because this statement is not declaring a new binding —
  it's giving the *already-declared* `message` a new value. The
  right-hand literal `"Service is running again."` is a string literal,
  the same construct as before, evaluated to itself and assigned via the
  same `=` operator already explained in the previous unit — the only
  genuinely new element on this line is the absence of `var`/`val`, which
  is precisely what makes it a reassignment rather than a declaration.
- **`println(message)`** (line 5) — the same `println` call, a third
  time in this lesson, reading `message`'s *second* value. Because
  `message` is the same binding both times — not a new one — this call
  observes whatever the most recent assignment left behind, which is
  exactly what reassignment means: the name doesn't change, what it
  refers to does.

The sequence across lines 2 through 5 is straightforward enough — two
plain reassignment-then-print steps with no loop, no recursion, and no
branching — that a full `Iteration N:` execution trace would restate the
same two lines twice over with no new information; the walkthrough above,
read top to bottom, already *is* the trace: `message` holds "Service is
running." through lines 2–3, then holds "Service is running again."
through lines 4–5, because line 4's reassignment is the only place either
value changes.

### CS Lens

Separating "can this be inferred" from "can this be reassigned" into two
independent questions the compiler answers separately about the same
declaration — rather than one keyword (Java's `var`) answering only the
first and leaving the second as an unenforced, optional add-on (`final`)
— is a real instance of a broader idea: making an implicit assumption
into an explicit, checked one.

```
Also recognized in: `const` vs `let` in JavaScript (a nearly identical
split to Kotlin's val/var, arguably its direct inspiration), C++'s
`const` qualifier layered onto any declaration rather than replacing the
type, Rust's variables being immutable *by default* unless explicitly
marked `mut` (the same two questions, with the default flipped), Python's
complete absence of this enforcement at the language level (a real,
different design choice this list makes concrete by contrast, not a
missing feature to feel bad about)
```

### SE Lens

The design principle is the same one named in the previous unit's SE
Lens, applied to a different decision: **stating intent where the
compiler can check it**, rather than leaving intent to a comment,
a naming convention, or a reader's trust. The alternative Kotlin's
designers didn't choose is Java's own approach: one keyword (`var`) that
answers only "what type is this," with mutability left as a separate,
rarely-used, opt-in modifier (`final`) that most real Java code skips —
meaning the overwhelming majority of Java locals declared with `var` are
reassignable by default, whether or not the code ever actually reassigns
them, and a reader has no way to tell which is true without reading the
rest of the method by hand. Kotlin's split moves that same default:
choosing `val` or `var` is not optional the way `final` is in Java — a
Kotlin declaration has to pick one — so the *default* case (idiomatic
Kotlin style strongly prefers `val` unless reassignment is genuinely
needed) actively documents "this will not change," checked by the same
compiler that already refused to compile this lesson's own throwaway
reassignment lab. The real cost: a Kotlin author has to make this decision
at every single declaration, every time, rather than deferring it the way
Java's `var` plus optional `final` allows. Kotlin's designers judged that
small, repeated cost worth paying for a promise the compiler can actually
enforce, rather than one that lives only in a reader's assumptions.
