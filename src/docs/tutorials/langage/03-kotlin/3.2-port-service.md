# Lesson 3.2: A Constructor Parameter That Is Also a Field

**What you will build:** `code/03-kotlin/Service/Service.kt` and
`Logger.kt` — a Kotlin `Service` class holding a run count and a
constructor-injected `Logger`, with a `run()` that logs and counts, and a
`reset()` that fails loudly (a real, caught exception) when called before
`run()` ever has. `Program.kt` is rewritten to build a real `Logger` and
`Service`, exercise both the success and failure paths of `reset()`, and
print the results. This directly ports four real Java commits
(`366bed6`, `71d927d`, `b35d9aa`, `ece5221` — all read fresh this
session from `code/02-java/Service`) into one Kotlin lesson. The
transferable problem: Java's `Service`, at this point in its own history,
needed a separate field declaration, a constructor with a body that
copies a parameter into that field, and a separate getter method just to
expose one number — four separate pieces of ceremony for one idea
("this class holds a `Logger` and a run count"). This lesson finds out
how much of that ceremony Kotlin's class syntax actually requires.

**What you need to know first:** Lesson 3.1 established `fun`, `val`,
`var`, and the class-less top-level entry point. Lesson 2.2 (Java) and
Lesson 1.2 (C#) established what a class, an object, a constructor, and a
method fundamentally are — this lesson assumes that general shape
(a blueprint; an object as a real instance of it; a constructor as the
special routine that builds one; a method as behavior attached to it) and
re-derives Kotlin's own syntax for all four from scratch, below, per the
Repetition Rule. Lesson 2.4 (Java) established constructor injection —
handing a dependency to an object through its constructor rather than
letting the object construct its own dependency — which this lesson's
third Concept Unit re-derives for Kotlin in full. Lesson 2.7 (Java)
established `throw`/`catch` for a real failure case, re-derived for
Kotlin in this lesson's fourth Concept Unit.

## Terms used in this lesson

- **Primary constructor** — the constructor declared directly in a
  Kotlin class's own header, in parentheses right after the class name,
  rather than as a separate block of code inside the class body the way
  Java and C# both require. It exists because a constructor that does
  nothing but accept parameters and store them is Kotlin's single most
  common case — the language gives that exact case a shorthand instead
  of demanding the same three-line pattern (field, constructor
  signature, constructor body) be written out by hand every time.
- **Constructor-parameter property (`val`/`var` in a primary
  constructor)** — writing `val` or `var` directly in front of a primary
  constructor parameter, which does two things in one declaration: it
  declares the constructor parameter, *and* it declares a property on the
  class holding that parameter's value, automatically initialized from
  it. It exists to collapse Java's separate field-declaration-plus-
  constructor-body pattern (a field, then a constructor whose only job is
  copying its parameter into that field) into the single line where the
  dependency is already being named.
- **`private` (reappearing, given full treatment again)** — an access
  modifier restricting where a member can be referenced from: a
  `private` member is visible only inside the class that declares it,
  the same restriction Java's and C#'s own `private` already enforce.
  Kotlin reuses this exact word and this exact meaning; nothing about
  its behavior changes here, only where it can now be written (directly
  on a constructor parameter, not only on a body-level field).
- **`return`** — a statement that ends a function immediately and
  supplies the value the function call evaluates to. It exists because a
  function that promises a result (declared with a return type, below)
  needs an explicit point in its body where that result is actually
  produced and handed back to whoever called it; without it, the
  function would have no way to communicate its answer.
- **Explicit return type (`: Int`)** — a type written after a function's
  parameter list, separated by a colon, naming what that function's
  `return` statement must produce. It exists so both the compiler and a
  reader know, from the function's own signature, what kind of value a
  call to it evaluates to — without reading the function's body at all.
- **`Int`** — Kotlin's own integer type, first explicit type this
  curriculum's Kotlin code has written out by name. Unlike Java, where a
  programmer must choose between a raw primitive `int` (never `null`,
  stored directly, cheap) and a boxed `Integer` object (nullable,
  allocated on the heap, usable as a generic type argument) — two
  genuinely different types a Java programmer has to reason about and
  convert between by hand — Kotlin exposes exactly one type, `Int`, for
  a whole number in this range, and the compiler itself decides,
  invisibly, whether to compile a given `Int` down to the JVM's raw
  primitive `int` or box it into a real `java.lang.Integer` object,
  based on where it's used (a plain local variable compiles to a
  primitive; an `Int` stored in a generic collection like `List<Int>`
  gets boxed automatically). This exists so a Kotlin programmer reasons
  about one type, `Int`, and lets the compiler handle the primitive/boxed
  distinction Java forces onto the programmer directly.
- **Composition (reappearing from Lesson 2.4/1.5, given full treatment
  again)** — one object holding a reference to another object as part of
  its own state, so it can call on that other object to do part of its
  job, rather than doing everything itself. It exists because a single
  class trying to do every job itself (logging, counting, and whatever
  else) becomes harder to change and harder to test than several small
  classes, each with one job, that call on each other.
- **Constructor injection (reappearing from Lesson 2.4/1.6, given full
  treatment again)** — supplying an object's dependency (here,
  `Service`'s `Logger`) as a constructor parameter at the moment the
  object is created, rather than having the object construct its own
  dependency internally. It exists so the *caller* decides which
  concrete dependency an object gets, which is exactly what makes
  swapping one implementation for another (a later lesson's own subject)
  possible without changing the class that depends on it.
- **`if` (reappearing, given full treatment again)** — a conditional
  statement that runs its block only when the parenthesized condition
  evaluates to `true`. Kotlin's `if` syntax is character-for-character
  identical to Java's and C#'s here; the only thing new about this
  lesson's use of it is the specific condition being checked.
- **`==` (reappearing, given full treatment again)** — the equality
  comparison operator. For `Int` values specifically (this lesson's only
  use of it), it compares the two numeric values directly, the same as
  Java's `==` does for the primitive `int` it compiles `Int` down to in
  this context — there is no boxed-reference-comparison subtlety here,
  because a plain local `Int` compiles to a primitive, per the `Int`
  entry above.
- **`throw` (reappearing, given full treatment again)** — a statement
  that immediately abandons the function's normal execution and hands a
  real exception object up to whatever calling code is prepared to catch
  it — or, if nothing catches it, up through every calling frame until
  the program itself terminates. Kotlin's `throw` is syntactically
  identical to Java's and C#'s.
- **`try`/`catch` (reappearing, given full treatment again)** — `try`
  marks a block of code whose exceptions should be intercepted rather
  than left to propagate further; `catch` names the exception type to
  intercept and runs its own block when a thrown exception matches. One
  real, genuinely new fact about Kotlin specifically, not shared with
  Java: **Kotlin has no checked exceptions at all.** Java forces a method
  that can throw certain exception types (subclasses of `Exception` that
  aren't `RuntimeException`) to either catch them or declare them with
  `throws`, checked by the compiler; Kotlin enforces none of this — every
  exception in Kotlin behaves the way only `RuntimeException` does in
  Java, catchable if a `catch` block happens to be written, never
  required. `IllegalStateException` (this lesson's own exception, given
  its own full entry below) happens to already be unchecked in Java too,
  so this particular lesson's own code would compile in Java without any
  `throws` declaration either way — but the *rule itself* is a real
  difference worth stating plainly rather than leaving it to be
  discovered by surprise in a lesson that actually depends on it.

## Objects and methods used

- **`println`** (reappearing from Lesson 3.1, given full treatment
  again)
  - *What it is:* Kotlin's standard-library top-level function that
    writes a value's text representation to standard output.
  - *Implementation:* `public actual inline fun println(message: Any?) {
    System.out.println(message) }` — real source, already fetched and
    verified in Lesson 3.1 from `libraries/stdlib/jvm/src/kotlin/io/Console.kt`
    at tag `v2.4.10`, unchanged since.
  - *Its use:* Called inside `Logger.log`, this lesson's own new home for
    the exact `System.out.println` call Java's `Logger` class used
    directly.
  - *Type:* Top-level, `public`, `inline` function. Signature: `fun
    println(message: Any?): Unit`.
  - *Responsibility:* Converting any value to text and writing it,
    followed by a newline, to standard output.
  - *Depends on:* `System.out`, a `java.io.PrintStream` set up by the JVM.
  - *Connects to:* Called by `Logger.log`, this lesson's own new caller;
    calls `System.out.println` in turn.
  - *Shape:* A public API surface between this lesson's code and the
    JVM's standard output.

- **`IllegalStateException`**
  - *What it is:* A real exception type representing "an object was
    asked to do something its current internal state doesn't allow" —
    the exact situation `reset()` is in when `runCount` is still `0`.
  - *Implementation:* Confirmed for real this session by throwing and
    catching one, then printing `ex.toString()` and
    `ex::class.java.name` (`verification/3.2/check_exception_type.kt`):
    both printed `java.lang.IllegalStateException`, proving Kotlin's
    `IllegalStateException` is not a separate Kotlin-only class — it is
    a real `typealias` for Java's own `java.lang.IllegalStateException`,
    the identical class Java's `Service.reset()` (Reference Source,
    below) already threw. Its real constructor used here,
    `IllegalStateException(message: String)`, stores that string so a
    later `.message` read (a nullable `String?` — the subject of Lesson
    3.5, not used yet in this lesson) or `.toString()` call
    (used here, always non-`null`) can retrieve it.
  - *Its use:* Thrown by `Service.reset()` when `runCount == 0`; caught
    in `Program.kt` around the `neverRun.reset()` call, to prove the
    failure path really runs rather than crashing the whole program.
  - *Type:* A class (a real, instantiable object type — `throw
    IllegalStateException("...")` creates a genuine instance of it, the
    same as constructing any other object), extending `RuntimeException`.
  - *Responsibility:* Carrying a description of *why* an operation was
    refused, from the point it was thrown up to whatever `catch` block
    is prepared to handle it.
  - *Depends on:* A `String` message, supplied at construction.
  - *Connects to:* Constructed and thrown inside `Service.reset()`;
    caught inside `Program.kt`'s `try`/`catch`, whose own `catch` block
    calls `.toString()` on it (below) to produce something loggable.
  - *Shape:* A boundary type — the actual data crossing from `Service`'s
    own internal failure back out to whatever code called `reset()`.

- **`Any.toString()`**
  - *What it is:* A member function every Kotlin object has, inherited
    from `Any` (Kotlin's own root type — every class, `IllegalStateException`
    included, is an `Any` whether it says so or not), producing a
    `String` description of the object.
  - *Implementation:* `Any`'s own default `toString()` (declared in
    Kotlin's stdlib as `public open fun toString(): String`) returns a
    generic `ClassName@hashcode`-shaped string; `Throwable` (an ancestor
    of `IllegalStateException`, inherited from Java's own
    `java.lang.Throwable`) overrides it to return the class's fully
    qualified name followed by `: ` and the exception's own message —
    exactly the real, verified output `java.lang.IllegalStateException:
    Cannot reset a service that has never run.` this lesson's own real
    run below produces.
  - *Its use:* Called on the caught exception, in `Program.kt`, to turn
    it into a real `String` that can be concatenated and logged, without
    touching the still-not-yet-taught nullable `.message` property.
  - *Type:* An open (overridable) instance member function on `Any`,
    Kotlin's universal root type. Signature: `open fun toString():
    String`.
  - *Responsibility:* Producing a text representation of the object it's
    called on — for a plain object, a generic identity string; for a
    `Throwable`, its own type name plus message, per the override above.
  - *Depends on:* Nothing beyond the object it's called on (`this`).
  - *Connects to:* Called directly by `Program.kt`'s `catch` block; its
    result is concatenated with a literal `String` via `+` and passed to
    `Logger.log`.
  - *Shape:* A public API surface — the standard, universal way any
    Kotlin value can be turned into displayable text.

## Concept Unit: A Class Whose Constructor Parameter Is Already a Field

### The Problem

Java's own `Service`, at the point this lesson ports it from (commit
`b35d9aa`), needs three separate pieces just to hold one `Logger`
dependency: a field declaration (`private Logger logger;`), a constructor
signature naming the parameter (`public Service(Logger logger)`), and a
constructor body copying that parameter into the field
(`this.logger = logger;`). Three lines, one idea: "this object holds the
`Logger` it was given." Does Kotlin's class syntax need all three, or was
Java's `this.logger = logger;` line only ever there because Java has no
shorter way to say it?

> **Stop and try it yourself first:** Look again at `this.logger =
> logger;` — what is that line actually *doing* that isn't already fully
> determined by the field's declared type and the constructor
> parameter's declared type being the same (`Logger`, in both cases)?
> If a language's compiler could see, just from the constructor's own
> signature, that a parameter and a field share a name and a type, what
> work would still be genuinely left for a programmer to write by hand?
> Given that Lesson 3.1 already showed `val`/`var` can appear on an
> ordinary local declaration, what do you predict happens if `val` is
> written *inside a constructor's own parentheses*, right in front of a
> parameter name, instead of on a separate line?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.kt`:

```kotlin
class Greeter(private val name: String) {
    fun greet() {
        println("Hello, " + name + ".")
    }
}

fun main() {
    val greeter = Greeter("Kotlin")
    greeter.greet()
}
```

Run this session (`verification/3.2/lab_class_ctor_member.kt`):

```
Hello, Kotlin.
```

This proves three things at once: `Greeter("Kotlin")` really did
construct a real object with no separate field declaration and no
constructor body anywhere in the class — the single `private val name:
String` inside the parentheses was enough; `greet()`, a genuine **member
function** (a function declared inside a class body, called on a real
instance via `.`), can read `name` directly, proving it truly became a
property of the object, not just a parameter that vanished after
construction; and `Greeter("Kotlin")` built the object with no `new`
keyword anywhere — Kotlin removes `new` entirely, since a constructor
call is already unambiguous from the type name being called like a
function. This whole shorthand — a `val`/`var` written directly in a
primary constructor's parameter list — is called a **constructor-
parameter property**.

### Mechanical Walkthrough

- **`class Service(...)`** — declares `Service` as a class, the same
  blueprint concept already established in Lesson 2.2 (Java) and Lesson
  1.2 (C#): a description of what every `Service` object will have and
  can do, not a running thing itself — no `Service` object exists until
  something calls its constructor.
- **`private`** — per its Terms entry above, restricts `logger`'s
  visibility to inside `Service` itself; code outside this class cannot
  read `logger` directly.
- **`val`** — per Lesson 3.1's own full treatment, makes this
  particular property read-only: once `Service` is constructed, nothing
  can ever point `logger` at a different `Logger` instance.
- **`logger: Logger`** — the constructor parameter's own name and type.
  Because `val` precedes it, this single piece of syntax is doing what
  Java's `b35d9aa` needed a field declaration, a constructor parameter,
  *and* a constructor body assignment to do — per the constructor-
  parameter property Terms entry above.
- **`fun run()`** — a member function, per Lesson 3.1's own treatment of
  `fun` (there, top-level; here, declared inside a class body instead,
  which is the only thing that makes it a *member* rather than a
  top-level function — the keyword itself doesn't change).
- **`logger.log("Service is running.")`** — a call to `Logger.log`, `.`
  used to reach a member function on the object `logger` refers to, the
  same dot-member-access syntax Java and C# both already use.

### CS Lens

Constructor-parameter properties are a specific instance of a broader
idea: **letting the compiler synthesize boilerplate the programmer would
otherwise write by hand**, when that boilerplate follows a fixed,
predictable shape (here: "this parameter becomes this field, verbatim,
every time").

```
Also recognized in: C# 12's own primary constructors (a very similar
shorthand, added to C# after this curriculum's own Phase 1 was written
against an earlier version), Python's `@dataclass` generating `__init__`
from field declarations, Lombok's `@AllArgsConstructor` annotation
generating the same Java constructor body Service's own history shows
being written by hand, TypeScript's constructor-parameter property
shorthand (`constructor(private name: string)`) — a near-identical
feature in a completely different language family
```

### SE Lens

The principle is **removing ceremony that carries no decision**. Writing
`private Logger logger;` and then `this.logger = logger;` in Java asks
the programmer to make the same choice twice — the field's type and the
parameter's type must already match for the assignment to type-check —
so there is no real decision being expressed in that second line, only
required repetition. The alternative Kotlin didn't choose here is Java's
own: keep field declaration, constructor signature, and constructor body
as three independent things a programmer could, in principle, make
diverge (a field of one type, a constructor accepting a different one,
manually converted) — a flexibility this lesson's own `Service` never
actually uses. The real cost of Kotlin's shorthand: it only covers the
common case where a constructor parameter becomes a property with no
transformation in between; the moment real logic needs to run before a
parameter becomes a property (validating it, transforming it), Kotlin
falls back to an explicit constructor body (`init { ... }`), which this
lesson's own `Service` never needs and so never shows.

## Concept Unit: State and a Java-Shaped Getter (On Purpose)

### The Problem

`Service` needs to track how many times `run()` has been called and let
outside code read that count — the same problem Java's own `71d927d`
solved with a private field plus a public `getRunCount()` method. This
unit ports that exact shape into Kotlin deliberately, using an explicit
getter method rather than Kotlin's own more concise property syntax —
Kotlin's shorter option is real, and it's coming, but not yet: this
lesson's own job is showing the class port working *at all* first; the
next lesson's entire job is replacing exactly this getter method with
something more concise, and that lesson needs a real getter method here
to replace.

> **Stop and try it yourself first:** A private field plus a public
> method that only returns it, unchanged, is a pattern this curriculum
> has already seen in both C# (before properties were introduced) and
> Java. Nothing about Kotlin's own syntax so far — `class`, `fun`,
> `val`, `var`, constructor-parameter properties — has stopped a
> programmer from writing that exact same pattern by hand in Kotlin too.
> Try writing, on paper or in your head, what a direct, line-for-line
> Kotlin translation of Java's `private int runCount;` plus `public int
> getRunCount() { return runCount; }` would look like, using only the
> `fun`/`val`/`var` syntax already established, before reading on.

### Mechanical Walkthrough

- **`private var runCount: Int = 0`** — a body-level property (declared
  directly in the class body, not in the primary constructor's
  parentheses the way `logger` was in the previous unit — a real,
  different declaration site for a property, used here because
  `runCount` isn't supplied from outside; it starts at a fixed value the
  class decides for itself). `private`, per its Terms entry, restricts
  it to inside `Service`. `var`, per Lesson 3.1's own treatment, makes it
  reassignable — necessary, since `run()` changes it. `: Int`, per its
  own Terms entry above, explicitly names the type here rather than
  relying on inference, because `= 0` alone would already let the
  compiler infer `Int` — the explicit annotation is written for the
  same reason Java's own `private int runCount;` writes `int` explicitly:
  a field's type is part of the class's own contract, worth stating
  plainly rather than leaving to whatever the initializer happens to
  imply.
- **`fun getRunCount(): Int`** — a member function, per the previous
  unit's own treatment of `fun`, now with an explicit return type,
  per its own Terms entry above: `: Int` after the parameter list states
  that calling `getRunCount()` produces an `Int`, before a reader ever
  looks at the body to confirm it.
- **`return runCount`** — a `return` statement, per its own Terms entry
  above: ends `getRunCount()` immediately and hands `runCount`'s current
  value back to whoever called it.
- **`runCount = runCount + 1`** (inside `run()`, now meaningful with the
  field this unit adds) — a reassignment, per Lesson 3.1's own full
  treatment: reads `runCount`'s current value, adds `1`, and assigns the
  result back into the same binding.

### SE Lens

## Concept Unit: `reset()` — Kotlin's Exceptions Are Java's Exceptions

### The Problem

`Service` needs a `reset()` that refuses to run if `run()` has never been
called — the same real failure case Java's own `ece5221` introduced,
throwing `IllegalStateException` and catching it back in `Program.java`.
Does Kotlin need a different exception mechanism, a different exception
type, or does it reuse Java's own outright?

> **Stop and try it yourself first:** Kotlin compiles to the same JVM
> bytecode Java does, and this curriculum's own Java lessons already
> used a real class named `IllegalStateException`, sitting in Java's own
> standard library. Given that Kotlin code and Java code both ultimately
> run on the identical JVM, what would you predict happens if Kotlin
> source code writes `throw IllegalStateException(...)` — does Kotlin
> need to define its own, separate exception class with the same name,
> or could it simply reuse the real Java one directly? What real,
> verifiable way could you check which of those two is actually true,
> rather than guessing?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.kt`:

```kotlin
fun mightFail(shouldFail: Boolean) {
    if (shouldFail) {
        throw IllegalStateException("it failed")
    }
}

fun main() {
    try {
        mightFail(true)
    } catch (ex: IllegalStateException) {
        println("caught: " + ex.toString())
    }
}
```

Run this session (`verification/3.2/lab_exception.kt`):

```
caught: java.lang.IllegalStateException: it failed
```

The printed text itself is the proof the Socratic prompt above asked for:
`ex.toString()` printed `java.lang.IllegalStateException`, not
`kotlin.IllegalStateException` or anything else — this is the real,
fully-qualified Java class name. A second, more direct check, run this
same session (`verification/3.2/check_exception_type.kt`), confirms it
further: printing `ex::class.java.name` (the exception's own real,
runtime Java class name, not just its `toString()`) printed the identical
`java.lang.IllegalStateException`. Kotlin's `IllegalStateException` is a
real `typealias` for Java's own `java.lang.IllegalStateException` — not a
lookalike, not a wrapper, the exact same class Java's `ece5221` already
threw.

### Mechanical Walkthrough

- **`fun reset()`** — a member function, per this lesson's own repeated
  treatment of `fun`, with no parameters and no return type — Kotlin
  infers `Unit` (its own equivalent of "no return value," which a later
  lesson gives full treatment to on its own first genuinely relevant
  appearance) when no `: Type` is written and no `return` inside the
  body ever supplies a value.
- **`if (runCount == 0)`** — per the Terms entries above for `if` and
  `==`: checks whether `runCount`'s current value is exactly `0`, the
  same condition Java's own `ece5221` checks.
- **`throw IllegalStateException(...)`** — per this unit's own Objects-
  and-methods entry for `IllegalStateException`, above: constructs a
  real `java.lang.IllegalStateException` (no `new` keyword, per this
  lesson's first unit) and immediately hands it to `throw`, per its own
  Terms entry, abandoning `reset()`'s normal execution.
- **`runCount = 0`** and **`logger.log("Service has been reset.")`**
  (lines 18–19, reached only when the `if` above did *not* throw) — a
  reassignment and a method call, both already given full treatment
  earlier in this lesson.
- **`val logger = Logger()`** and **`val service = Service(logger)`**
  (`Program.kt` lines 2–3) — object construction with no `new`, per this
  lesson's first unit, now for real project types rather than the
  throwaway `Greeter`.
- **`service.run()`** (lines 4–5, called twice) — the same member
  function call syntax already explained; called twice in a row so
  `getRunCount()` (line 6) has something other than `0` to report.
- **`val neverRun = Service(logger)`** (line 13) — a *second*, distinct
  `Service` instance, sharing the same `logger` reference but with its
  own independent `runCount` (starting at `0`, per that property's own
  initializer) — proving `runCount` is per-object state, not something
  shared across every `Service`.
- **`try { neverRun.reset() } catch (ex: IllegalStateException) { ... }`**
  — per the Terms entry for `try`/`catch` above: attempts `reset()` on
  the never-run `neverRun`, and when it throws (because its own
  `runCount` really is still `0`), the `catch` block runs instead of the
  exception propagating further and ending the program.
- **`ex.toString()`** — per this unit's own Objects-and-methods entry for
  `Any.toString()`: called on the caught exception, producing the real
  `String` `"java.lang.IllegalStateException: Cannot reset a service
  that has never run."`, confirmed by this lesson's own real run below.
- **`"Caught expected failure: " + ex.toString()`** — string
  concatenation via `+`, already used in this lesson's first Concept
  Unit's own isolated lab, joining a literal with `ex.toString()`'s
  result into one `String` for `logger.log`.

### SE Lens

The principle is **reusing an existing, well-understood guarantee instead
of inventing a parallel one**. Kotlin's designers could have defined
their own exception hierarchy from scratch, disconnected from Java's —
instead, Kotlin exception types are, wherever a Java equivalent already
exists, the *exact same* JVM classes, proven directly by this unit's own
real evidence. The real, deliberate tradeoff Kotlin does make, though, is
dropping Java's checked-exception enforcement entirely (per this lesson's
own Terms entry for `try`/`catch`) — Kotlin's designers judged that Java's
compiler-enforced `throws` declarations, in practice, too often produced
either overly broad `throws Exception` escape hatches or empty
catch-and-ignore blocks written just to satisfy the compiler, rather than
code that actually handled failure meaningfully — a real, debated
language-design decision this curriculum can now state plainly, backed by
a real class this lesson's own program actually throws and catches.
