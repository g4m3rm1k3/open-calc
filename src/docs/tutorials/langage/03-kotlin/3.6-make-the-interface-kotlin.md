# Lesson 3.6: The Type a `var` Infers Is Narrower Than You Think

**What you will build:** `Logger.kt` becomes a real Kotlin `interface`;
`ConsoleLogger.kt` and `LoudLogger.kt` become its two real
implementations; `Service` keeps depending on `Logger` by name, unchanged;
and `Program.kt` swaps in `LoudLogger`, with one deliberate, explicit
type annotation this lesson exists to justify. This directly ports Java
commit `38f2915`. The transferable problem: Lesson 3.2 built `Logger` as
a plain concrete class specifically because that was Java's own real
history too — a concrete dependency, extracted into an interface only
once a second implementation was genuinely needed. That need arrives now.
Along the way, a real, separate problem surfaces: when Kotlin infers a
type from `LoudLogger()`, what type does it actually infer — `Logger`,
the abstraction the rest of this program should be programmed against, or
`LoudLogger`, the one concrete class sitting on the right of `=`?

**What you need to know first:** Lesson 2.5 (Java) and Lesson 1.7/1.8
(C#) established what an interface is and why swapping implementations
matters — this lesson assumes that motivation and re-derives Kotlin's own
syntax for it from scratch. Lesson 3.2 built `Logger` as a concrete class
and `Service`'s own constructor-injected dependency on it — unchanged by
this lesson, since `Service`'s own code never names `Logger`'s concrete
shape, only its `log(String)` member. Lesson 3.1 established Kotlin's own
type inference for `val`/`var`, reused here to prove a real, narrower
consequence of it.

## Terms used in this lesson

- **`interface`** — a declaration naming a set of members (here, one:
  `log(message: String)`) with no implementation of its own, that a
  class can promise to provide by declaring itself as implementing it.
  It exists to let code (here, `Service`'s own constructor parameter)
  depend on "something that can log a message," without depending on
  *which* concrete way of logging it gets, at all.
- **`: Logger`** (in a class header, e.g. `class ConsoleLogger : Logger`)
  — Kotlin's syntax for declaring that a class implements an interface
  (or extends a class — the same colon covers both, unlike Java, which
  uses separate keywords, `implements` and `extends`). It exists as
  Kotlin's single, uniform way to state an inheritance relationship,
  regardless of whether what follows the colon is an interface or a
  class.
- **`override`** — a required modifier on a member function that
  provides a real implementation for something an interface (or a
  parent class) only declared. It exists so that, reading a function
  signature alone, it's immediately visible that this function is
  fulfilling an existing contract rather than introducing a brand-new
  one — unlike Java, where `@Override` is only an optional, advisory
  annotation the compiler checks but never requires.
- **Inferred type narrowing** — when a `val`/`var`'s type is inferred
  (per Lesson 3.1's own treatment) from an expression whose own type is
  more specific than the abstraction a programmer actually intends to
  program against, the inferred type is that more specific one, not the
  broader one — even when the more specific type happens to implement a
  broader interface. It exists as a direct, unavoidable consequence of
  how type inference itself works (per Lesson 3.1: the compiler infers
  from what the expression's own type actually is, not from what a
  programmer meant), not a special rule of its own — this lesson's own
  first Concept Unit exists specifically to make that consequence
  concrete and provable, since it's easy to overlook until it actually
  causes a real compile error.

## Objects and methods used

- **`Logger.log`** (reappearing from Lesson 3.2, given full treatment
  again, now as an interface member rather than a concrete method)
  - *What it is:* The one member `Logger` declares — a function taking
    a message and producing no return value.
  - *Implementation:* No body at all in `Logger.kt` itself anymore — an
    interface member with no default body is purely a contract; its two
    real bodies now live in `ConsoleLogger.log` (a direct `println`) and
    `LoudLogger.log` (three `println` calls, with `"!!!"` markers before
    and after), both quoted in full in this lesson's own Reference
    Source below.
  - *Its use:* Called by `Service`'s own `run()` and `reset()`, unchanged
    by this lesson — `Service` was already written, in Lesson 3.2,
    against `Logger`'s own name and signature, never against either
    concrete class, which is exactly what makes this lesson's own swap
    possible with zero changes to `Service.kt` itself.
  - *Type:* An abstract instance member of an `interface` (Lesson 3.2's
    `Logger` had this as a concrete, `println`-bodied method instead —
    this lesson replaces that body with a bare signature, per its own
    Project Change below). Signature: `fun log(message: String): Unit`.
  - *Responsibility:* Recording or displaying a message — the *how* is
    entirely left to whichever class implements it; `Logger` itself
    guarantees only that some way of doing so exists.
  - *Depends on:* Nothing at the interface level; each real
    implementation depends on whatever it needs internally
    (`println`, for both of this lesson's own two implementations).
  - *Connects to:* Called by `Service`; implemented by `ConsoleLogger`
    and `LoudLogger`.
  - *Shape:* A public API surface — the seam between `Service` and
    whatever concrete logging behavior a caller decides to inject.

## Concept Unit: `interface` — One Contract, Two Real Implementations

### The Problem

`Service`'s own `Logger` dependency, since Lesson 3.2, has been a single
concrete class — every `Service` gets the exact same logging behavior,
whichever `Logger` instance happens to be passed in. Java's own real
history (commit `38f2915`, this unit's own Reference Source) hit the same
wall: a second, genuinely different way of logging (`LoudLogger`, wrapping
every message in `"!!!"`) was needed, and a single concrete `Logger`
class has no room for two different bodies of the same method. Does
`Service`'s own code need to change to make room for a second
implementation, or does something else need to change instead?

> **Stop and try it yourself first:** `Service`'s own constructor,
> unchanged since Lesson 3.2, is `Service(private val logger: Logger)`
> — it already names `Logger` as a *type*, not as a specific object.
> Given that Kotlin's constructor-parameter properties (Lesson 3.2's own
> treatment) only ever care about a parameter's declared *type*, not
> which concrete class actually satisfies it at any given call site,
> what would have to change about `Logger` itself — not about `Service`
> — to let two genuinely different classes both count as a valid
> `Logger`?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Logger.kt`:

```kotlin
interface Shape {
    fun area(): Double
}

class Square(private val side: Double) : Shape {
    override fun area(): Double {
        return side * side
    }
}

class Circle(private val radius: Double) : Shape {
    override fun area(): Double {
        return 3.14159 * radius * radius
    }
}

fun main() {
    val shapes: List<Shape> = listOf(Square(2.0), Circle(2.0))
    for (shape in shapes) {
        println(shape.area())
    }
}
```

Run this session (`verification/3.6/lab_interface.kt`):

```
4.0
12.56636
```

`Shape` declares one member, `area()`, with no body — an **`interface`**,
per this lesson's own Terms entry. `Square` and `Circle` each declare
`: Shape` (per this lesson's own Terms entry for that syntax) and each
supply their own, genuinely different `override fun area()` (per this
lesson's own Terms entry for `override`) — real proof that a single
`List<Shape>` can hold genuinely different concrete objects, each
responding to the identical `.area()` call with its own real logic:
`4.0` (a `2.0`-sided square) and `12.56636` (a `2.0`-radius circle),
computed by two entirely different formulas, called through the exact
same interface member.

### Mechanical Walkthrough

- **`interface Logger`** — per this lesson's own Terms entry: declares
  `Logger` as a contract, not a concrete, instantiable class — `Logger()`
  (constructing a bare `Logger` directly, the way Lesson 3.2's own code
  once did) is no longer valid Kotlin at all once `Logger` becomes an
  interface; only a class that implements it can be constructed.
- **`fun log(message: String)`** (inside `Logger`) — a function
  signature with no body — legal specifically because it sits inside an
  `interface`; the identical bare signature inside a `class` would be a
  real compile error (a class member needs a body unless the class
  itself is declared `abstract`, not covered by this lesson).
- **`class ConsoleLogger : Logger`** — per this lesson's own Terms entry
  for `:` in a class header: declares `ConsoleLogger` as implementing
  `Logger`. Because `Logger` is an interface with one unfulfilled member,
  `ConsoleLogger` is now *required*, by the compiler, to provide a real
  `log` — omitting it would be a real compile error naming exactly which
  member is missing.
- **`override fun log(message: String) { println(message) }`** — the
  same `println` call already given full treatment, now inside a
  function marked `override`, per this lesson's own Terms entry:
  required here because `log` already exists as a name on `Logger`
  itself; without `override`, the compiler would refuse to compile this
  as a genuinely new, unrelated function with the same name as an
  existing interface member.
- **`class LoudLogger : Logger`** and its own `override fun log(...)`
  body — the identical pattern, with three `println` calls instead of
  one, each already given full treatment.

### CS Lens

One name, `log`, dispatching to genuinely different real behavior
depending on which concrete object it's called on — decided at runtime,
not at the point the code calling it was written — is **polymorphism**,
already given full treatment in Lesson 2.5 (Java) and Lesson 1.7 (C#),
restated here in full per the Repetition Rule: the same real idea,
proven again, this time in Kotlin's own interface syntax.

```
Also recognized in: every GUI framework's own event-handler interfaces
(a `ClickListener` interface, implemented differently by every widget
that reacts to clicks differently), a plugin system where a host program
calls one fixed interface method and each plugin supplies its own real
behavior, a strategy-pattern sort comparator (the same `compare` call,
a different real ordering depending on which comparator object is
passed)
```

### SE Lens

The principle — **programming against an abstraction, not a concrete
implementation** — was already fully stated in Lesson 1.8 (C#) and
Lesson 2.5 (Java); this lesson's own real contribution is proving,
concretely, that Kotlin's own version of the same idea costs nothing
extra to set up: `Service`'s constructor needed zero changes, because it
was already written against `Logger` by name, never against `Logger`'s
own (now former) concrete body. The alternative not chosen — keeping
`Logger` a concrete class and adding a `LoudLogger` that somehow extends
it, overriding its behavior — would have worked too (Kotlin classes can
extend other classes, not covered by this lesson), but would have tied
every future logger to `Logger`'s own original implementation, even parts
a new logger has no interest in reusing; an interface guarantees nothing
beyond the contract itself, which is exactly the loose coupling this
whole idea, across three languages now, has consistently been for.

## Concept Unit: What Type Does `val logger = LoudLogger()` Actually Infer?

### The Problem

`Program.kt` needs to construct a real `LoudLogger` and pass it to
`Service`. The obvious code — `val logger = LoudLogger()`, following
every other Kotlin construction so far in this curriculum — relies on
type inference, per Lesson 3.1's own treatment. But Lesson 3.1's own
treatment only ever said the compiler infers a value's type from its
initializer's own type — it never asked *which* type that is when the
initializer's own type sits inside an interface hierarchy at all. Is the
inferred type of `LoudLogger()` `Logger`, the abstraction, or
`LoudLogger`, the exact concrete class being constructed?

> **Stop and try it yourself first:** Per Lesson 3.1's own full
> treatment of type inference, the compiler works out a value's type
> "from the expression assigned to it" — not from any broader context
> about how that value might be used later. `LoudLogger()` is, as an
> expression, a call to `LoudLogger`'s own constructor — its own type,
> unambiguously, is `LoudLogger`. Given that, and given nothing in `val
> logger = LoudLogger()` mentions `Logger` (the interface) anywhere at
> all, what would you predict `logger`'s own inferred type actually is?
> Now: this curriculum's own real, verified reference source
> (`Program.java` at commit `38f2915`, quoted in this unit's own Project
> Change below) writes `Logger logger = new LoudLogger();` — explicitly
> typing the Java local as the *interface*, not letting even Java's own
> `var` infer it. Given everything Lesson 1.8 and Lesson 2.5 already
> established about why programming against an abstraction matters, why
> might the very same reference source *not* have written `var logger =
> new LoudLogger();`, the way it did for `service` one line later?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Program.kt`:

```kotlin
interface Greeter {
    fun greet()
}

class LoudGreeter : Greeter {
    override fun greet() {
        println("HELLO")
    }
}

class QuietGreeter : Greeter {
    override fun greet() {
        println("hello")
    }
}

fun main() {
    var inferred = LoudGreeter()
    inferred = QuietGreeter()
    inferred.greet()
}
```

Attempting to compile this session
(`verification/3.6/lab_type_inference_pitfall.kt`):

```
lab_type_inference_pitfall.kt:19:14: error: assignment type mismatch: actual type is 'QuietGreeter', but 'LoudGreeter' was expected.
    inferred = QuietGreeter()
             ^
```

This is the real, concrete proof this unit's own Socratic prompt was
asking for: `inferred`'s own type was inferred as `LoudGreeter` — not
`Greeter` — exactly per Lesson 3.1's own rule (the compiler infers from
the expression's own type, `LoudGreeter()`, with no awareness that a
broader `Greeter` interface exists at all). Reassigning `inferred` to a
different, unrelated implementation of the same interface (`QuietGreeter`)
is a real, provable type error, even though both classes are equally
valid `Greeter`s.

Now the fix — one explicit type annotation:

```kotlin
fun main() {
    var explicit: Greeter = LoudGreeter()
    explicit = QuietGreeter()
    explicit.greet()
}
```

Run this session (`verification/3.6/lab_type_inference_fixed.kt`):

```
hello
```

`explicit`'s own type is now `Greeter`, stated directly rather than
inferred — reassigning it to any real `Greeter` implementation, `Loud` or
`Quiet`, compiles and runs correctly, printing `QuietGreeter`'s own real
`"hello"`.

### SE Lens

The principle is **not trusting inference to encode a design decision it
was never told about**. Type inference, per Lesson 3.1's own SE Lens,
exists to avoid restating information the compiler can already see — but
"this should be treated as a `Logger`, not specifically a `LoudLogger`"
is not information the compiler can see from `LoudLogger()` alone; it's
a real decision about how the rest of the program should be allowed to
use this value, and the real reference source this lesson ports from
already made that decision explicit, in Java, one line before choosing
*not* to make the identical decision for `service` (which genuinely has
no broader abstraction it needs to be treated as here). The real,
honest cost: an explicit type annotation is one small piece of the exact
ceremony this whole phase's own "less ceremony" framing has been
removing everywhere else — a reader has to know *why* this one
declaration bucks that trend, which is precisely what this unit's own
extended Socratic prompt and worked proof exist to make legible, rather
than leaving `: Logger` looking like an arbitrary, unexplained exception
to Kotlin's own usual inference-first style.

## Connect the Pieces

concrete class, holding exactly one real implementation. This lesson's
