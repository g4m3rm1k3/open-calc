# Lesson 3.5: A Value the Compiler Won't Let You Pretend Is There

**What you will build:** `Program.kt` gains a real message tally —
counting how many times each logged message appears in `service.history`
— ported from `Program.java`'s own `Map<String, Integer>` block, plus one
new, genuinely null-returning check: the first entry of `neverRun`'s own
history (a `Service` whose `reset()` always fails before ever running,
built back in Lesson 3.2), which is really, truly empty. The transferable
problem: Java's `Map.get(key)` returns a plain `Integer` — nullable at
runtime if the key is missing, but the *type* never says so, so nothing
stops a program from using the result as if it's always there until it
crashes. Kotlin's `Map.get` returns `Int?`, and the compiler refuses to
compile code that uses it as a plain `Int` without first proving, one way
or another, what happens if it's missing.

**What you need to know first:** Lesson 2.8 (Java) established `Map` and
iteration over a collection, reused here without re-deriving the general
idea (only Kotlin's own specific syntax gets full treatment below).
Lesson 3.2 built `neverRun`, the `Service` instance whose `reset()`
always throws — its own empty `history`, never touched by this lesson's
earlier code, is what makes this lesson's own null case real rather than
invented. Lesson 3.2 also left `ex.message` deliberately unused,
noting this lesson as where it would be handled properly — that promise
is kept in this lesson's own first Concept Unit.

## Terms used in this lesson

- **Nullable type (`Type?`)** — a type name followed by `?`, meaning "a
  reference to a `Type`, or the absence of one (`null`)." It exists so
  that "this value might not exist" is stated in the type itself, and
  therefore checked everywhere that type is used, rather than living only
  in a comment or a programmer's memory of which methods can return
  `null`.
- **`?`** — the character that turns an ordinary type into its nullable
  counterpart. Every type in Kotlin that omits it — `Int`, `String`,
  `Service`, all of this curriculum's own Kotlin code so far — is
  guaranteed, by the compiler, to never hold `null`; no Kotlin code
  anywhere can pass `null` where a non-nullable type is expected without
  the compiler refusing to compile it. This is real, checked, and
  different from Java, where every reference type (never primitives, but
  every object type) can hold `null` regardless of whether a programmer
  intended that.
- **Elvis operator (`?:`)** — a binary operator: `left ?: right`
  evaluates to `left` if `left` is not `null`, or to `right` otherwise.
  It exists as the concise way to supply a fallback for a nullable value
  in a single expression, turning a `Type?` into a real, guaranteed
  `Type` on the spot.
- **Safe call (`?.`)** — a variant of ordinary member access (`.`) that
  only actually calls the member if the receiver isn't `null`; if the
  receiver *is* `null`, the whole expression evaluates to `null` instead
  of throwing. It exists so a chain like `maybeNull?.someProperty` can be
  written directly, without a separate `if (maybeNull != null)` check
  wrapping it first.
- **`firstOrNull()`** (a Term here because it's the source of this
  lesson's own genuinely-empty nullable case, though its full
  Objects-and-methods treatment is below) — a real stdlib function
  returning a collection's first element, or `null` if the collection has
  none. It exists as the null-safe counterpart to a plain `first()`
  (which throws if the collection is empty) — this lesson's own use of
  it is deliberately against a collection known, for real, to sometimes
  be empty.

## Objects and methods used

- **`Map<K, V>.get` / `map[key]`** (reappearing from Java Lesson 2.8's
  own `Map.get`, given full treatment again)
  - *What it is:* The operation that retrieves the value associated with
    a given key in a map, if one exists.
  - *Implementation:* Kotlin's own `Map<K, V>` interface declares `get`
    with a genuinely different signature than Java's: `operator fun
    get(key: K): V?` — nullable, always, regardless of what `V` itself
    is. Kotlin's `[]` indexing syntax (`messageCounts["..."]`) is real
    operator-overload syntax calling this exact `get` function; nothing
    magic happens for the bracket syntax specifically — it's the same
    `get` a direct `messageCounts.get("...")` call would reach, per this
    lesson's own real, verified compile errors below, which apply
    identically either way.
  - *Its use:* Reading each real message's own tally, and — deliberately
    — reading `neverRun`'s history in this lesson's second unit through
    the related `firstOrNull()`, below, rather than `get` directly.
  - *Type:* An `operator` instance member function on `Map<K, V>`.
    Signature: `operator fun get(key: K): V?`.
  - *Responsibility:* Looking up one key's associated value, reporting
    its absence as `null` rather than throwing or silently defaulting.
  - *Depends on:* The map itself and the key being looked up.
  - *Connects to:* Called directly by `Program.kt`'s own tally-reading
    code; its `V?` result flows directly into this lesson's own Elvis
    operator.
  - *Shape:* A public API surface — the standard way any Kotlin code
    reads a map.

- **`MutableMap<K, V>.getOrDefault` / `.put`** (reappearing from Java
  Lesson 2.8, given full treatment again)
  - *What it is:* `getOrDefault(key, default)` reads a key's value or
    returns a supplied fallback if absent — already returning a plain,
    non-nullable `V` (the fallback itself guarantees a value exists
    either way, so the type system needs no `?` here). `put(key, value)`
    stores a value under a key, replacing any previous one.
  - *Implementation:* Both are real methods `kotlin.collections.MutableMap`
    inherits, ultimately, from the same real `java.util.Map` contract
    Java's own `HashMap` already implements — Kotlin's `mutableMapOf<K,
    V>()` (this lesson's own map constructor, used in the same spirit as
    Lesson 3.3's own `mutableListOf`) builds a real `java.util.LinkedHashMap`
    underneath.
  - *Its use:* Building `messageCounts` from `service.history`, one
    entry at a time, exactly mirroring Java's own `getOrDefault`/`put`
    pair from `Program.java`.
  - *Type:* Instance member functions on `MutableMap<K, V>`. Signatures:
    `fun getOrDefault(key: K, defaultValue: V): V`, `fun put(key: K,
    value: V): V?` (returning the previous value for that key, or
    `null` if there wasn't one — a return value this lesson's own code
    never uses).
  - *Responsibility:* `getOrDefault` guarantees a usable value with no
    nullability at the call site; `put` records a new key/value pair,
    overwriting whatever was there.
  - *Depends on:* The map itself; `getOrDefault` also needs a fallback
    value, `put` needs both a key and a value.
  - *Connects to:* Both called inside `Program.kt`'s own tally-building
    loop, once per history entry.
  - *Shape:* A public API surface for building up map state incrementally.

- **`Iterable<T>.firstOrNull()`**
  - *What it is:* A real stdlib extension function returning a
    collection's first element, or `null` if it has none.
  - *Implementation:* Declared, per Kotlin's own real convention for
    functions extending an existing type without modifying it, as `fun
    <T> Iterable<T>.firstOrNull(): T?` — internally, it checks whether
    the underlying collection is a `Collection` and reads index `0` if
    non-empty (via an internal iterator otherwise), returning `null`
    immediately if there is nothing to read at all. This lesson does not
    write a function shaped like this itself — doing so is this whole
    phase's own Lesson 3.7 — but calling one someone else already wrote,
    the way this lesson does, needs no knowledge of how that mechanism
    works internally.
  - *Its use:* Reading `neverRun.history`'s own first entry — genuinely
    `null`, this session's own real run below proves, since `neverRun`'s
    `reset()` always throws before ever appending anything.
  - *Type:* A function extending `Iterable<T>`. Signature: `fun <T>
    Iterable<T>.firstOrNull(): T?`.
  - *Responsibility:* Reporting a collection's first element without ever
    throwing for an empty one — the plain `first()` this lesson does not
    use throws `NoSuchElementException` instead.
  - *Depends on:* The collection it's called on.
  - *Connects to:* Called on `neverRun.history` (itself a call to
    `Service`'s own custom getter, per Lesson 3.3); its `T?` result flows
    into this lesson's own safe call.
  - *Shape:* A public API surface, part of Kotlin's own standard
    collection operations.

## Concept Unit: `Map.get` Returns `Int?`, and the Elvis Operator

### The Problem

`Program.java`'s own final `Map<String, Integer>` block tallies how many
times each message in `service.getHistory()` appears, then prints two
specific counts by key. Porting the tally-building loop itself is
straightforward — `getOrDefault`/`put` port almost verbatim. But reading
a specific count back out — `messageCounts.get("Service is running.")`
in Java — is where this lesson's own real problem shows up. Java's own
`Map<String, Integer>.get` returns a plain `Integer`, which is `null` at
runtime if the key is missing, but nothing in its *type* says so —
`Integer` looks the same whether or not `null` is a real possibility. Does
Kotlin's own `Map.get` behave the same way?

> **Stop and try it yourself first:** Every key `Program.java`'s own
> code actually reads (`"Service is running."`, `"Service has been
> reset."`) really is present in the tally, by construction — this
> specific program never actually triggers Java's own missing-key `null`
> case. Given that, is Java's `Integer`-typed, nullable-at-runtime return
> from `Map.get` a real problem *for this specific program*, or only a
> latent one? Now, suppose this program wanted one more number: the
> *total* of both counts added together. Given what Lesson 3.4's own
> `Int` Terms entry already said about Kotlin never silently converting
> or ignoring type mismatches, what do you predict happens if Kotlin's
> `Map<String, Int>.get` returns something other than a plain `Int` —
> and two such results are added together with `+`?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Program.kt`:

```kotlin
fun main() {
    val counts = mutableMapOf<String, Int>()
    counts["a"] = 3
    counts["b"] = 4
    val total = counts["a"] + counts["b"]
    println(total)
}
```

Attempting to compile this session
(`verification/3.5/lab_null_arithmetic_fails.kt`):

```
lab_null_arithmetic_fails.kt:5:29: error: operator call is prohibited on a nullable receiver of type 'Int?'. Use '?.'-qualified call instead.
    val total = counts["a"] + counts["b"]
                            ^
lab_null_arithmetic_fails.kt:5:31: error: argument type mismatch: actual type is 'Int?', but 'Int' was expected.
    val total = counts["a"] + counts["b"]
                              ^^^^^^^^^^^
```

Two real compiler errors — both keys `"a"` and `"b"` really are present
in `counts`, exactly like `Program.java`'s own real, always-present keys,
and Kotlin's compiler still refuses to compile the arithmetic. This is
the concrete, provable answer to the Socratic prompt above: Kotlin's
`Map<K, V>.get`, per this lesson's own Objects-and-methods entry, returns
`V?` — here, **`Int?`**, a **nullable type**, per this lesson's own Terms
entry — *unconditionally*, regardless of whether a specific call site
happens to know its key is always present. The compiler has no way to
verify "this specific key is always there" from the map's own type
alone, so it applies the same rule to every `get` call, universally.

Now the fix:

```kotlin
fun main() {
    val counts = mutableMapOf<String, Int>()
    counts["a"] = 3
    counts["b"] = 4
    val total = (counts["a"] ?: 0) + (counts["b"] ?: 0)
    println(total)
    val missing = counts["z"] ?: 0
    println(missing)
}
```

Run this session (`verification/3.5/lab_elvis_fix.kt`):

```
7
0
```

`(counts["a"] ?: 0)` — the **Elvis operator**, per this lesson's own
Terms entry — evaluates to `counts["a"]`'s own real value (`3`) since it
isn't `null`, producing a genuine, non-nullable `Int` the compiler now
accepts inside `+`. `counts["z"] ?: 0`, for a key that truly doesn't
exist, evaluates to the right-hand `0` instead — real, verified proof the
fallback branch works too, not just the "value present" branch.

### CS Lens

Making "this value might not exist" part of the type itself — so the
compiler, not the programmer's memory or discipline, is what catches a
missing check — is a real, substantial idea usually called **null
safety**.

```
Also recognized in: Swift's own Optional type (`Int?`, nearly identical
syntax and behavior to Kotlin's), Rust's `Option<T>` (no dedicated `?`
type syntax, but the same core idea: absence stated in the type, not
left implicit), TypeScript's `strictNullChecks` mode (opt-in, unlike
Kotlin's always-on default), Haskell's `Maybe` type (one of this whole
family's own oldest, most direct ancestors)
```

### SE Lens

The principle is **moving a whole class of runtime failure to compile
time**. Java's alternative — every reference type nullable, unless a
programmer manually adds an external annotation (`@Nullable`) that
nothing in the language itself enforces — was Java's own original design,
made before null-safety-by-default was common practice; the real cost
Java pays for it, industry-wide and well-documented, is the
`NullPointerException`, a failure that only ever surfaces at runtime,
often far from wherever the actual missing check was. Kotlin's tradeoff:
every value's nullability is a real, binding decision at the point it's
declared or returned, checked everywhere it's used — the real cost is
this lesson's own opening error, a compile failure a programmer has to
actively resolve (with `?:`, `?.`, or an explicit non-null assertion)
before the program will build at all, even when — as `ex.message` in
this exact program shows — the `null` case never actually happens at
runtime. Kotlin's designers judged that cost worth paying because the
alternative (Java's own, real, frequently-hit `NullPointerException`) is
worse: a failure caught by every single build, always, is cheaper in
aggregate than one caught only by whichever runs happen to hit the
missing case.

## Concept Unit: Safe Calls — `neverRun`'s Genuinely Empty History

### The Problem

`neverRun`, built back in Lesson 3.2, is a `Service` whose only `reset()`
call always throws — its own `history` (Lesson 3.3's own computed
property) has never had anything appended to it, because both
`run()`'s own append and `reset()`'s own append happen only *after* each
method's own logic succeeds, and `neverRun` has never called `run()` at
all. Reading `neverRun.history`'s own first entry needs
**`firstOrNull()`**, per this lesson's own Terms entry — but this
lesson's own previous unit only showed a nullable value being read
directly (`?:`); what happens when code wants to call a *member* — a
property, a method — on a value that might itself be `null`, not just
read the value directly?

> **Stop and try it yourself first:** `firstOrNull()` returns `String?`
> — a `String`, or `null`. If code wanted to know that string's own
> `.length`, ordinary member access (`someString.length`) works fine when
> `someString` is a genuine, non-`null` `String` — but `neverRun.history`
> really does have zero entries, so `firstOrNull()` here will really
> return `null`. Given everything this lesson has already shown about
> Kotlin refusing operations on nullable values without a resolution in
> place, what do you predict happens if plain `.length` is called
> directly on a `String?` that might be `null`? And, given `?:`'s own
> shape from the previous unit (a fallback for a nullable *value*), what
> different shape would you guess a fallback needs when the thing that
> might be missing is the *receiver of a member access*, not a value
> being used directly?

### Mechanical Walkthrough

- **`neverRun.history`** — property access, per Lesson 3.3's own
  treatment, reading `neverRun`'s own independent `history` — per Lesson
  3.2's own walkthrough of `neverRun`'s construction, a genuinely
  separate `Service` instance from `service`, with its own,
  never-appended-to `mutableHistory`.
- **`.firstOrNull()`** — per this lesson's own Objects-and-methods entry:
  called on `neverRun.history`'s own real, empty `List<String>`, per its
  own real implementation, returning `null` because there is no first
  element to return.
- **`val firstEverEntry = ...`** — `val`, per Lesson 3.1's own treatment,
  binding the result; its inferred type is `String?`, per `firstOrNull`'s
  own declared return type, not `String` — the compiler already knows,
  from `firstOrNull`'s own signature, that this value might be absent.
- **`firstEverEntry?.length`** — the **safe call**, per this lesson's own
  Terms entry, proven in isolation moments ago: because `firstEverEntry`
  really is `null` in this exact run, `.length` (a real property on
  `String`, reporting its character count) is never evaluated, and this
  whole sub-expression becomes `null`.
- **`?: -1`** — the **Elvis operator**, reappearing from this lesson's
  own first unit, given full treatment again: since the left side is
  `null`, the whole expression evaluates to `-1`, a plain, deliberately
  out-of-range sentinel (a real string's own length can never be
  negative) marking "there was nothing here at all," rather than `0`
  (which would be ambiguous with a real, zero-length string).

### SE Lens

The principle is the same **making absence a checked, first-class case**
idea named in this lesson's first unit, now applied at the point of
*member access* rather than *value use* — the real difference `?.`
specifically addresses. The alternative not chosen here — reading
`neverRun.history.first()` (no `OrNull`, which throws
`NoSuchElementException` on an empty collection rather than returning
`null`) — would have been a real, valid design too, one this program
deliberately avoids: it would turn "the history happens to be empty," a
genuinely normal state for a `Service` that's never successfully run,
into a thrown exception, the same weight this curriculum's own Lesson
3.2 already gave to `reset()`'s own genuine misuse. `firstOrNull()` plus
a safe call treats "empty" as an expected, ordinary outcome instead —
the real, honest choice for a value that legitimately might not be
there, as opposed to one that represents something having actually gone
wrong.
