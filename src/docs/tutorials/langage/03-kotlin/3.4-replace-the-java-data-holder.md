# Lesson 3.4: Two Objects That Hold the Same Number, and Are Not Equal

**What you will build:** `code/03-kotlin/Service/LastValue.kt` — a Kotlin
port of Java's `LastValue<T>`, rebuilt as a `data class` instead of a
plain class with `set`/`get` methods, and `Program.kt` updated to use it
to hold the service's own run count and a finished-message. The
transferable problem is a real, deliberately-proven bug in Java's own
`LastValue<T>`: two instances holding the identical value are not
`.equals()`, and printing one shows meaningless identity text instead of
the value it holds — proven for real, this session, against Java's own
compiled class, not assumed. This lesson finds out how much of that bug
is inherent to "a class that holds one value," and how much of it Kotlin
removes for free with one keyword.

**What you need to know first:** Lesson 3.2 established Kotlin's class
and constructor syntax; Lesson 3.3 established Kotlin's property syntax.
This lesson assumes both and re-derives, from scratch, what `data`
changes about a class declaration that already uses them. Lesson 2.6
(Java) and Lesson 1.9 (C#) established generic type parameters (`<T>`),
reused here without re-teaching the general idea, though Kotlin's own
generic syntax gets full treatment on its own first appearance below,
per the Repetition Rule.

## Terms used in this lesson

- **`data class`** — a class declaration prefixed with the `data`
  modifier, instructing the compiler to automatically generate real
  `equals()`, `hashCode()`, `toString()`, `copy()`, and `componentN()`
  functions from the properties declared in its primary constructor. It
  exists because a class whose entire purpose is holding a fixed set of
  values — not behavior, not identity, just data — needs those five
  functions to behave consistently almost every time, in a way that's
  fully determined by which properties the class holds; writing all five
  by hand, correctly, for every such class is repetitive and easy to get
  subtly wrong (forgetting to update `equals()` after adding a new
  field is a real, common bug in hand-written Java).
- **Structural equality (`equals()`/`==`)** — two objects being
  "equal" because their *contents* match, as opposed to being the exact
  same object in memory. It exists as the more useful default for data:
  two separate `Point(1, 2)` objects usually should be treated as the
  same point, even though they are two distinct objects taking up two
  distinct locations in memory.
- **Referential equality (`===`)** — Kotlin's own separate operator
  asking "are these two names referring to the *exact same object* in
  memory," regardless of whether their contents happen to match. It
  exists because Kotlin needs a way to ask that second, different
  question once `==` itself has been redefined (by `data class`, or by a
  hand-written `equals()` override) to mean structural comparison
  instead — a real difference from Java, where `==` on objects *always*
  means referential comparison and `.equals()` is the only way to opt
  into structural comparison; Kotlin's `==` calls `.equals()` under the
  hood for any type that defines one, meaning `==` itself changes
  meaning depending on the type, and `===` exists specifically to still
  be able to ask the referential question when needed.
- **`copy()`** — a real, generated function every `data class` receives,
  producing a new instance with the same property values as the
  original, except for whichever properties are explicitly passed as
  named arguments. It exists to make working with *immutable* data
  practical: rather than mutating an object in place (which this
  lesson's own `LastValue` deliberately no longer allows, per its own
  Project Change below), `copy()` produces a distinct object representing
  "the same data, except this one thing changed" — the object the
  earlier value was never itself modified to become.
- **Destructuring declaration (`val (v) = ...`)** — a single declaration
  that pulls one or more properties out of an object into their own
  separate named variables in one statement, by position rather than by
  name. It exists as a convenience for exactly the shape a `data class`
  already guarantees: because its generated `componentN()` functions
  return its properties in primary-constructor order, `val (v) =
  wrapper` can pull `value` straight out without writing
  `wrapper.value` at all.

## Objects and methods used

- **`Any.equals(other: Any?)`, `Any.hashCode()`, `Any.toString()`**
  (`toString()` reappearing from Lesson 3.2, given full treatment again)
  - *What it is:* Three open (overridable) member functions every
    Kotlin class inherits from `Any`, Kotlin's universal root type.
  - *Implementation:* `Any`'s own defaults — unless overridden —
    implement all three by object *identity*: `equals` compares whether
    two references point at the same real object; `hashCode` derives
    from that same identity; `toString` (already shown to compile down
    to Java's own `Object.toString()` behavior in this lesson's real
    Java proof below) produces a `ClassName@hexHashcode`-shaped string.
    A `data class`, per its own Terms entry above, generates real
    overrides of all three, based on its primary-constructor properties,
    instead of inheriting `Any`'s identity-based defaults.
  - *Its use:* This lesson's entire subject is the difference between the
    inherited defaults (proven, for real, to misbehave for a
    single-value holder) and the `data class`-generated overrides.
  - *Type:* Open instance member functions on `Any`. Signatures: `open
    fun equals(other: Any?): Boolean`, `open fun hashCode(): Int`, `open
    fun toString(): String`.
  - *Responsibility:* `equals` answers "should this object be treated as
    the same as that one"; `hashCode` produces an `Int` consistent with
    `equals` (equal objects must produce equal hash codes — a real
    contract, not just a convention, that hash-based collections like
    `HashMap` depend on to work correctly at all); `toString` produces
    a human-readable text representation.
  - *Depends on:* Nothing beyond the object itself (and, for `equals`,
    the other object being compared against).
  - *Connects to:* `==` (structural equality, per its own Terms entry
    above) calls `equals` under the hood; `println` (already given full
    treatment) calls `toString`.
  - *Shape:* A public API surface every Kotlin object exposes, whether a
    class overrides it or accepts `Any`'s own defaults.

## Concept Unit: The Problem, Proven — and `data class` Fixing It

### The Problem

Java's own `LastValue<T>` (`code/02-java/Service/LastValue.java`,
quoted in full in this unit's own Project Change, below) is a plain
class with a private field and `set`/`get` methods — the same shape
Lesson 3.2's own `Service` started with, before Lesson 3.3 replaced it.
But `LastValue` was never revisited in Java the way `Service` was — it
never gained a real `equals()`, `hashCode()`, or `toString()` override at
all. Does that actually matter for how this program uses it?

> **Stop and try it yourself first:** `Program.java`'s own real code
> constructs a `LastValue<Integer>`, calls `.set(...)` once, and reads it
> back with `.get()` once — it never compares two `LastValue` instances
> to each other, and never prints one directly. Given that, does the
> missing `equals()`/`toString()` override actually cause a bug in *this*
> program today — or is it a latent problem, real but not yet triggered?
> If you constructed two separate `LastValue<Integer>` objects and set
> both to hold `5`, what would you *want* `a.equals(b)` to return — and
> what do you predict Java's own, unmodified `Object.equals()` (which
> `LastValue` never overrides) actually returns instead?

### Introduce the Concept in Isolation

First, the real proof, in Java itself — not a throwaway Kotlin lab yet,
because the problem being proven belongs to the Reference Source, not to
Kotlin:

```java
LastValue<Integer> a = new LastValue<>();
a.set(5);
LastValue<Integer> b = new LastValue<>();
b.set(5);
System.out.println(a.equals(b));
System.out.println(a);
```

Run this session, against the real, unmodified `LastValue.java`
(`verification/3.4/CheckJavaLastValue.java` and
`verification/3.4/LastValue.java`, a verbatim copy of the real file):

```
false
LastValue@7ad041f3
```

Both real: `a.equals(b)` is `false`, even though both objects hold the
identical value `5` — Java's own default `Object.equals()`, which
`LastValue` never overrides, compares by reference identity, not
content. And printing `a` directly shows `LastValue@7ad041f3` — the
default `Object.toString()` shape (a class name, `@`, and the object's
identity hash in hexadecimal — the exact hex digits are not predictable
in advance and will differ on a different run; only this *shape* is
guaranteed), never the value `5` it actually holds. This is called
**referential equality** deciding the outcome where **structural
equality** — comparing the two objects' actual contents — is what a
reader would reasonably expect from something named `LastValue`.

Now, the same experiment, in a *plain* (non-`data`) Kotlin class, to
prove this isn't a Java-only problem waiting to be automatically fixed
just by porting the language:

```kotlin
class PlainBox<T>(var value: T)

fun main() {
    val a = PlainBox(5)
    val b = PlainBox(5)
    println(a == b)
    println(a)
}
```

Run this session (`verification/3.4/lab_plain_class_problem.kt`):

```
false
PlainBox@70dea4e
```

The identical real problem, reproduced in Kotlin: `a == b` is `false`
(Kotlin's `==` calls `equals()` under the hood, per this lesson's own
Terms entry, and `PlainBox` inherits the same identity-based default
`Any.equals()` Java's `Object.equals()` already gave `LastValue`), and
`println(a)` shows the same `ClassName@hex` shape, not the value `5`.

Now the fix — the exact same class, with one word added:

```kotlin
data class DataBox<T>(val value: T)

fun main() {
    val c = DataBox(5)
    val d = DataBox(5)
    println(c == d)
    println(c)
}
```

Run this session (`verification/3.4/lab_data_class_fix.kt`):

```
true
DataBox(value=5)
```

`c == d` is now `true` — the compiler-generated `equals()`, per this
lesson's own Objects-and-methods entry above, compares `value` directly
rather than object identity. And `println(c)` shows `DataBox(value=5)` —
the compiler-generated `toString()`, showing the class name and every
primary-constructor property by name and value, not an opaque hash. This
whole automatic generation — real `equals()`, `hashCode()`, and
`toString()`, derived from a class's own primary-constructor properties
— is what the **`data class`** modifier turns on.

- **`data class LastValue<T>(val value: T)`** — `data`, per this

### CS Lens

Generating `equals`/`hashCode`/`toString` from a fixed, declared set of
fields — rather than requiring them hand-written, and rather than
defaulting to identity — is a specific, real instance of **value types**:
treating an object as meaningful *because of what it holds*, not because
of *where it lives in memory*.

```
Also recognized in: Java's own `record` (added in Java 16, after this
curriculum's own Java phase was written against an earlier baseline —
the exact same generated-equals/hashCode/toString idea, arriving in Java
itself years after Kotlin's `data class`), Python's `@dataclass`
decorator, C#'s `record` types, Scala's `case class` (one of `data
class`'s own direct historical influences)
```

### SE Lens

The principle is **making the common case require no manual, error-prone
repetition**. The alternative not chosen — writing `equals()`,
`hashCode()`, and `toString()` by hand for every small data-holding class
— is exactly what Java's own `LastValue` shows the real cost of: not a
class that got it *wrong*, but a class where nobody ever got around to
writing it *at all*, because doing so by hand for every such class in a
real codebase is tedious enough that it's routinely skipped, exactly the
way this lesson's own real, pasted Java output proves happened here. The
real, honest limit of `data class`: it only knows how to generate these
functions from primary-constructor properties — a class holding
meaningful state *outside* its primary constructor (a body-level `var`
that isn't part of the constructor) is silently excluded from
`equals()`/`hashCode()`/`toString()`'s own generated logic, a real,
easy-to-miss gap `LastValue` itself never hits (its only real state
*is* its one constructor property) but a more complex `data class` could.

## Concept Unit: `copy()` — Changing One Field of an Immutable Object

### The Problem

`LastValue`'s own `value` is a `val` — per this lesson's first unit,
deliberately immutable, unlike Java's mutable original. If a later part
of a program needed "the same `LastValue`, except holding a different
number," mutation (Java's own `.set(...)`) isn't available anymore. Is
there a real, idiomatic way to get a changed version of an immutable
`data class` instance without hand-writing a whole new constructor call
naming every property again — especially once a `data class` has more
than one property, where re-typing every unchanged one just to change one
would be exactly the kind of repetition this whole lesson has been
removing?

> **Stop and try it yourself first:** `LastValue<T>` only has one
> property, so "construct a new one with a different value" is just
> `LastValue(newValue)` — no real problem yet. But imagine a `data class
> Point(val x: Int, val y: Int)` instead, and a need to move a point one
> step to the right, keeping `y` the same. Writing `Point(oldPoint.x + 1,
> oldPoint.y)` works, but re-states `y` even though it never changes.
> Given that a `data class` already knows, from its own primary
> constructor, every property's name and current value, what would you
> guess a generated function for "construct a copy, but let me override
> just some of the properties by name" looks like at the call site?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `LastValue.kt`:

```kotlin
data class Wrapper<T>(val value: T)

fun main() {
    val c = Wrapper(5)
    val d = Wrapper(5)
    println(c === d)

    val e = c.copy(value = 10)
    println(e)
    println(e == c)

    val (v) = c
    println(v)
}
```

Run this session (`verification/3.4/lab_data_class_copy_destructure.kt`):

```
false
Wrapper(value=10)
false
5
```

`c === d` — per this lesson's own Terms entry for **referential
equality** — is `false`: even though `c` and `d` hold the identical
value `5` (and, per this lesson's first unit, `c == d` would be `true`,
proven there for the equivalent `DataBox`), they are two genuinely
distinct objects in memory, which `===` and only `===` is able to
detect. `e = c.copy(value = 10)` produced a real, new `Wrapper` —
printed as `Wrapper(value=10)`, using the same generated `toString()`
from this lesson's first unit — and `e == c` is `false`, since `copy()`
built an object holding a genuinely *different* value than `c` still
holds; `c` itself was never modified (it couldn't be — `value` is a
`val`). Finally, `val (v) = c` — a **destructuring declaration**, per
this lesson's own Terms entry — pulled `c`'s own `value` out into a
freshly-declared `v`, printed as `5`, using the compiler-generated
`component1()` a `data class` provides for exactly this purpose (a class
with more than one primary-constructor property generates
`component1()`, `component2()`, and so on, one per property, in
declaration order — `Wrapper` has only one, so only `component1()` was
available to `val (v) = c` here).

### Mechanical Walkthrough

- **`c === d`** — the **referential equality** operator, per this
  lesson's own Terms entry: compares whether `c` and `d` refer to the
  same real object in memory, unaffected by whatever `equals()` a class
  defines or generates.
- **`c.copy(value = 10)`** — a call to the **`copy()`** function, per its
  own Terms entry: `value = 10` is a *named argument* (reappearing
  language capability — passing an argument by the parameter's own name
  rather than by position, already implicitly available anywhere Kotlin
  accepts function calls, first given a real, deliberate use here),
  overriding just the `value` property; since `Wrapper` has only one
  property, this call is equivalent to `Wrapper(10)` — the payoff of
  named-argument `copy()` grows with classes holding more properties
  than this lesson's own single-property example needs to show.
- **`e == c`** — structural equality, per this lesson's first unit's own
  full treatment, now comparing two objects with genuinely different
  `value`s, correctly reporting `false`.
- **`val (v) = c`** — a **destructuring declaration**, per its own Terms
  entry: calls `c.component1()` (generated by `data class`, unused by
  name anywhere else in this lesson) and binds its result to a
  freshly-declared `v`.

### SE Lens

The principle is **immutability paired with cheap, explicit change** —
rather than mutating an object in place (Java's own `LastValue.set(...)`,
which leaves no record that a change happened, and which is unsafe to
share across concurrent code without further precaution), `copy()`
produces a distinct new object, leaving the original genuinely untouched.
The real tradeoff: every "change" now allocates a new object rather than
reusing the existing one — for `LastValue`, a single-field wrapper, this
cost is negligible; for a `data class` with many properties updated
frequently in a hot loop, the repeated allocation is a real, measurable
cost an experienced Kotlin programmer has to weigh against the safety
this pattern buys.

## Connect the Pieces

Tracing `LastValue` through this lesson: it began as a real, proven bug —
Java's own `LastValue<Integer>`, two instances holding the identical `5`,
reporting `false` for `.equals()` and printing an opaque identity hash
instead of the value `5` it actually holds, both facts pasted from a real
run against the genuine, unmodified Java source, not assumed. A plain
Kotlin port, with no `data` keyword, was shown to inherit the exact same
problem — proving the fix that follows comes specifically from `data`,
not from the language switch alone. Adding `data` produced a real,
disassembly-free but still fully verified fix: structural `equals()`,
a readable `toString()`, and, proven against a stand-in, `copy()` and
destructuring, both generated the same way. `Program.kt` now holds the
service's run count and a finished-message in two real `LastValue`
instances, immutable by design, sidestepping a nullable-type question
this curriculum has deliberately saved for its own dedicated lesson.

**Next lesson (3.5):** `Program.java`'s own `Map<String, Integer>`
message tally gets ported — and, for the first time in this Kotlin
phase, a real, natural `null` shows up: Kotlin's own `Map.get` returns a
value that might not be there, and the compiler refuses to let the
program pretend otherwise.
