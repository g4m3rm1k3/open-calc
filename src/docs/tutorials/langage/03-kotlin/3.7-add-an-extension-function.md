# Lesson 3.7: A Function Added to a Type That Never Knew About It

**What you will build:** `Describer.kt` — no longer a class at all, but a
single generic function, `fun <T> T.describe()`, callable on any value as
if it were a real member. `Program.kt` calls `service.runCount.describe()`
and `"Program finished.".describe()` directly, replacing Java's own
`Describer` object and its `.describe(value)` calls. The transferable
problem: Java's `Describer` (`code/02-java/Service/Describer.java`) is a
whole class whose only real job is one generic method that does nothing
with `this` at all — it never touches its own state, because it has
none. This lesson finds out what happens to that "operation with no real
home" once the language doesn't require a class to hold it, and — the
real, deliberately surprising part — proves that the result, despite
looking exactly like a method call at every call site, does not behave
like a real inherited or overridden method at all.

**What you need to know first:** Lesson 3.6 established Kotlin
interfaces and real polymorphism — a call resolved, at runtime, to
whichever concrete implementation the actual object is. This lesson's
own second Concept Unit deliberately contrasts against that, proving
extension functions resolve a different way entirely. Lesson 3.1
established generic type parameters were already reused (Lesson 3.4's
own `LastValue<T>`) — this lesson's own `<T>` is the same idea, applied
to a function rather than a class.

## Terms used in this lesson

- **Extension function** — a function declared as `fun
  ReceiverType.functionName(...)`, letting it be called with the same
  dot syntax as a real member of `ReceiverType` (`someValue.functionName()`),
  without `ReceiverType`'s own declaration ever being touched or even
  being something the extension's own author has access to modify. It
  exists so a useful operation on an existing type doesn't have to
  either become a real member of that type (impossible for a type from
  a library, and unwanted here, where `Int` and `String` are both
  built-in types nobody should be modifying) or live in some awkwardly
  separate utility class whose name a caller has to remember and import.
- **Receiver** — the value an extension function is called on — the
  part before the dot (`service.runCount` in
  `service.runCount.describe()`). It exists as this lesson's own name
  for "the thing the extension function is extending," referenced inside
  the function's own body as `this`, the same way an ordinary member
  function's body refers to the object it was called on.
- **Static dispatch (for extension functions specifically)** — which
  extension function actually runs, when more than one same-named
  extension exists across a type hierarchy, is decided at compile time,
  from the *declared* (static) type of the expression the extension is
  called on — never from the object's own real, runtime type. It exists
  as a direct, unavoidable consequence of how extension functions are
  actually implemented (proven in this lesson's own second unit,
  below): an extension function is not stored anywhere on the type it
  extends at all; the compiler resolves `x.functionName()` to a specific,
  ordinary function call by looking at `x`'s own declared type, the same
  way it resolves any other overloaded function call — never by asking
  the real object, at runtime, "which version of this do you actually
  have."

## Concept Unit: `fun <T> T.describe()` — A Method with No Class

### The Problem

Java's own `Describer` (`code/02-java/Service/Describer.java`, quoted in
full in this unit's own Project Change, below) is a real class — but its
one method, `describe`, never reads or writes any field, because
`Describer` has none. It exists purely to hold one operation, because
Java requires every method to live inside some class (Lesson 3.1's own
opening problem, restated here for a different kind of function). Kotlin
already removed that requirement for `main` itself, back in Lesson 3.1 —
does the same freedom extend to a function meant to operate *on* an
existing value, the way `describe(value)` does?

> **Stop and try it yourself first:** Lesson 3.1's own top-level `fun
> main()` had no receiver at all — it was called by the toolchain
> itself, with nothing before a dot. `Describer.describe(value)`, by
> contrast, is always called *on* something (`service.getRunCount()`,
> `"Program finished."`) — the value being described is central to what
> the call even means. Given that Kotlin already lets a function live
> at the top level of a file with no enclosing class, what would you
> guess happens if a function's own name, in its declaration, is
> prefixed with a *type* and a dot — `Int.something()` — rather than
> left bare? What might calling such a function then look like at the
> call site, compared to `Describer().describe(value)`?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Describer.kt`:

```kotlin
fun Int.doubled(): Int {
    return this * 2
}

fun main() {
    val x = 5
    println(x.doubled())
}
```

Run this session (`verification/3.7/lab_extension_function.kt`):

```

```

`x.doubled()` — ordinary member-call syntax, dot and all — really did
call `doubled()`, even though `Int` (a built-in Kotlin type this lesson's
own code has no ability to edit the declaration of) was never modified to
add it. Inside `doubled`'s own body, `this` refers to `x` itself — per
this lesson's own Terms entry, the **receiver** — the same way `this`
inside a real member function refers to the object the member was called
on. This whole mechanism — a function declared as `Type.functionName()`,
callable with dot syntax on any value of that type — is called an
**extension function**.

### CS Lens

Adding real, callable behavior to an existing type without modifying
that type's own original declaration — and without wrapping it in a new
type either — is a specific, real idea usually discussed under **open/
closed extensibility**: a type can be extended with new operations
without being reopened or subclassed.

```
Also recognized in: C#'s own extension methods (`public static class
Ext { public static int Doubled(this int x) => x * 2; }` — a
near-identical feature, predating Kotlin's own by several years and one
of its own real, acknowledged influences), Swift's own `extension`
declarations, JavaScript's own (now largely discouraged) practice of
adding methods directly onto `Array.prototype` or similar built-in
prototypes — the same underlying goal, achieved through a much less safe
mechanism
```

### SE Lens

The principle is **not forcing state onto an operation that has none**.
Java's `Describer` needed to be a class specifically because Java's own
rule (every method lives in a class) left no other option — but a class
with no fields at all is a real, honest signal that "class" was never
the right shape for this operation to begin with; it's a class only in
the sense Java's own syntax demanded one, not in the sense that anything
about `describe`'s own behavior benefits from object identity, state, or
inheritance. Extension functions let the code say exactly what's true:
this is a free-standing operation, parameterized by the value it acts
on, needing no home of its own. The real cost, deferred to this lesson's
own next unit: because an extension function is not a real member of the
type it extends, it cannot participate in the same runtime polymorphism
a real member — or a real interface implementation, per Lesson 3.6 — can.

## Concept Unit: Why an Extension Function Isn't Real Inheritance

### The Problem

Lesson 3.6 proved real polymorphism for real: a `Logger`-typed variable
holding a `LoudLogger` object called `LoudLogger`'s own real
`log`, decided at runtime from the object's own actual type, not its
declared one. `describe`, from this lesson's own first unit, looks
identical at every call site — dot syntax, no visible difference from a
real member call. If a second, more specific `describe` existed for a
narrower type, would calling it through a variable declared as the
broader type behave the same way Lesson 3.6's own `Logger` did — resolved
from the real object — or differently?

> **Stop and try it yourself first:** Lesson 3.6's own real, disassembled
> evidence (`Service.class`, back in Lesson 3.3) proved that ordinary
> Kotlin member calls compile down to real, callable methods on the
> object's own class. An extension function, by contrast — per this
> lesson's first unit's own Objects-and-methods entry — is declared as a
> free-standing, top-level function, not a member of the type it
> extends at all. Given that a type's own real methods (and interface
> implementations) are what Lesson 3.6's polymorphism actually depends
> on, and an extension function is never one of those — what do you
> predict happens if two different extension functions, with the
> identical name, are declared for a class and its subclass, and one is
> called through a variable declared as the *parent* type but holding a
> real *child* object?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Describer.kt`:

```kotlin
open class Animal
class Dog : Animal()

fun Animal.describeKind(): String = "an animal"
fun Dog.describeKind(): String = "a dog"

fun main() {
    val a: Animal = Dog()
    println(a.describeKind())
    val d: Dog = Dog()
    println(d.describeKind())
}
```

Run this session (`verification/3.7/lab_extension_static_dispatch.kt`):

```
an animal
a dog
```

This is the real, provable answer: `a`'s *declared* type is `Animal`,
even though the real object stored in it is a `Dog` (`Dog()`
constructed on the right, per Lesson 3.6's own subtype-construction
pattern). `a.describeKind()` prints `"an animal"` — the `Animal`
extension ran, not the `Dog` one — decided entirely from `a`'s own
declared type, with the real object's own actual type never consulted at
all. `d`, declared directly as `Dog`, prints `"a dog"` as expected. This
is called **static dispatch**, per this lesson's own Terms entry — the
opposite of Lesson 3.6's own real, proven dynamic dispatch, where
`Logger`-typed code calling `log()` genuinely did run whichever concrete
class's override the real object actually was, every time.

### Mechanical Walkthrough

- **`open class Animal`** — `open`, a modifier (not covered in earlier
  lessons, since no earlier Kotlin lesson needed a class to be
  subclassed) permitting a class to be extended by another class at all;
  Kotlin classes are non-extendable by default, unlike Java's, where
  every class can be subclassed unless explicitly marked `final` — the
  reverse default. `Animal` needs `open` specifically because `Dog`, on
  the next line, extends it.
- **`class Dog : Animal()`** — `:`, per Lesson 3.6's own treatment
  (the same colon syntax covering both interface implementation and
  class extension); `Animal()` here calls `Animal`'s own (default,
  no-argument) constructor as part of `Dog`'s own construction — real
  class inheritance, not interface implementation, the one genuinely new
  piece of syntax this isolated lab needs that this lesson's own real
  project code does not.
- **`fun Animal.describeKind(): String = "an animal"`** and **`fun
  Dog.describeKind(): String = "a dog"`** — two separate extension
  functions, per this lesson's first unit's own treatment, sharing a
  name but declared on two different receiver types.
- **`val a: Animal = Dog()`** — an explicit type annotation, reappearing
  from Lesson 3.6's own treatment: `a`'s declared type is `Animal`,
  deliberately, even though the constructed object is a real `Dog`.
- **`a.describeKind()`** — resolved, per this unit's own real proof,
  from `a`'s declared type (`Animal`), not from the real object's actual
  type (`Dog`) — the concrete evidence for **static dispatch**, per this
  lesson's own Terms entry.

### CS Lens

Static dispatch versus dynamic dispatch — deciding which code runs at
compile time, from a declared type, versus at runtime, from an object's
real type — is a foundational distinction in how every object-oriented
language actually works underneath its own syntax.

```
Also recognized in: C++'s own non-virtual methods (statically dispatched
by default, exactly like Kotlin extension functions) versus its `virtual`
methods (dynamically dispatched, exactly like Kotlin's own real interface
members from Lesson 3.6); C#'s extension methods (statically dispatched,
for the identical underlying reason as Kotlin's); Java's own static
method overloading, resolved at compile time from a variable's declared
type, contrasted with its instance method overriding, resolved at
runtime — the same two-category split, inside one single language
```

### SE Lens

The principle is **the same mechanism cannot honestly promise both
convenience and polymorphism at once, and Kotlin is explicit about which
one extension functions chose**. The alternative — making extension
functions dynamically dispatched, the way real interface members are —
was not available to Kotlin's own designers without also requiring every
extendable type to somehow know, in advance, about every extension
function anyone might ever write against it, which defeats the entire
purpose (adding behavior to a type *without* modifying it). The real,
honest tradeoff, proven concretely by this unit's own real run: an
extension function is the right tool for an operation that doesn't need
to vary by the receiver's own real subtype (exactly `describe`'s own
real situation — it does the same one thing, `println(this)`, regardless
of what `T` turns out to be); it is the *wrong* tool the moment different
subtypes genuinely need to behave differently when a specific operation
is called on them, which is precisely what Lesson 3.6's own real
interface members exist for instead.
