# Lesson 3.3: A Getter Method That Was Never Really a Method

**What you will build:** `Service.kt`'s `getRunCount()` method —
deliberately left Java-shaped in Lesson 3.2 — replaced with a real Kotlin
property, publicly readable but privately settable. `Service` also gains
`history`, a computed property returning a defensive copy of its run
history, replacing Java's own `getHistory()` shape from
`code/02-java/Service/Service.java`. The transferable problem: Lesson
3.2's own `getRunCount()` compiled and worked, but no working Kotlin
programmer would write it that way — this lesson finds out exactly what
Kotlin's own idiom looks like instead, and proves, by disassembling the
real compiled class, that the concise version isn't hiding anything the
verbose version had.

**What you need to know first:** Lesson 3.2 built `Service.kt` with a
private `runCount` field and a public `getRunCount()` method returning
it, on purpose, so this lesson would have real boilerplate to replace.
Lesson 2.3 (Java) and Lesson 1.4 (C#) already established *why*
encapsulation matters (letting outside code read a value without letting
it write one) — this lesson assumes that motivation and re-derives
Kotlin's own mechanism for it from scratch. Lesson 2.8 (Java) established
`List` and iteration, reused here for `history`'s own backing collection.

## Terms used in this lesson

- **Property** — in Kotlin, a `val`/`var` declaration is never *just* a
  field the way a bare Java field is — it is always, source-level,
  backed by a real getter (and, for `var`, a real setter too), even when
  neither is written by hand. It exists so that "read this value" and
  "write this value" can always be intercepted with real logic later
  without ever having to change how calling code accesses it — Java code
  that starts as a plain public field and later needs validation logic
  has to change every caller from `obj.field` to `obj.getField()`; Kotlin
  code calling `obj.field` never has to change, because it was already
  calling a getter, whether or not one was visibly written.
- **`private set`** — written directly after a `var` property's own
  declaration, this restricts *only the setter* to `private`, while
  leaving the property's own declared visibility (here, the class's
  default, `public`) governing the getter. It exists so a property can be
  freely *read* from outside the class while still only being *written*
  from inside it — exactly the shape Java's `private` field plus public
  getter, no public setter, already achieves, spelled here as one small
  modifier instead of two separate declarations.
- **Custom getter (`get() = ...`)** — writing a property's own `get()`
  block explicitly, rather than accepting the default one Kotlin
  generates automatically, so that reading the property runs real code
  and produces a *computed* result instead of simply returning a stored
  field. It exists for exactly this lesson's own `history`: the value
  handed back on each read (a defensive copy) is not the same object as
  whatever is stored internally, so the default "just return the field"
  getter would be the wrong behavior.
- **`List<T>` vs `MutableList<T>`** — Kotlin splits what Java's single
  `List<T>` interface does into two separate interfaces: `List<T>`
  declares only read operations (`size`, `get`, iteration — no `add`, no
  `remove`), and `MutableList<T>` extends it, adding the mutating ones.
  This exists to let the *type itself*, checked by the compiler, state
  whether code holding a reference is allowed to mutate what it points
  at — Java's own single `List<T>` interface always declares `add`/
  `remove`, whether or not a given caller should be allowed to use them;
  the immutability of a Java list returned as "read-only" is only a
  runtime convention (or a `UnsupportedOperationException` if the
  specific implementation enforces it), never something the *type*
  itself rules out at compile time the way Kotlin's split does.
- **`mutableListOf<T>()`** (a Term here because it produces the type just
  described, not because it's the call this lesson gives full
  Objects-and-methods treatment to below) — the way to obtain a fresh,
  empty `MutableList<T>`, used as `history`'s own real backing storage.

## Objects and methods used

- **`mutableListOf`**
  - *What it is:* A top-level Kotlin stdlib function producing a new,
    empty `MutableList<T>`.
  - *Implementation:* Real source, fetched this session from
    `libraries/stdlib/src/kotlin/collections/Collections.kt` at tag
    `v2.4.10`:

    ```kotlin
    public inline fun <T> mutableListOf(): MutableList<T> = ArrayList()
    ```

    It is `inline`, per Lesson 3.1's own treatment of that modifier, and
    its entire real implementation is a real `java.util.ArrayList` —
    confirmed independently this session by disassembling the real,
    compiled `Service.class` (`verification/3.3/output.txt`): the
    generated field backing `mutableHistory` is declared, in real JVM
    bytecode, as plain `java.util.List` — proving `MutableList<T>` is a
    Kotlin-compiler-only distinction layered on top of the same real
    `java.util` collection types Java already uses, not a separate
    runtime type.
  - *Its use:* Creates `Service`'s own private `mutableHistory` backing
    list.
  - *Type:* Top-level, `public`, `inline`, generic function. Signature:
    `fun <T> mutableListOf(): MutableList<T>`.
  - *Responsibility:* Producing one fresh, empty, mutable list — nothing
    about sizing, nothing about the elements it will eventually hold.
  - *Depends on:* Nothing; it takes no arguments in this lesson's call
    (a separate, `vararg`-accepting overload exists for
    non-empty initial contents, not used here).
  - *Connects to:* Called once, in `Service`'s own property initializer,
    to build `mutableHistory`; the `MutableList<T>` it returns is then
    read and written by `run()`, `reset()`, and `history`'s own getter.
  - *Shape:* A public API surface — the standard way Kotlin code obtains
    a real, empty mutable collection.

- **`ArrayList(Collection<E>)`** (reappearing from Java Lesson 2.8's own
  `new ArrayList<>(history)`, given full treatment again)
  - *What it is:* A real constructor on `java.util.ArrayList`, accepting
    an existing collection and copying its elements into a brand-new
    list.
  - *Implementation:* This is Java's own real `java.util.ArrayList`
    class — Kotlin does not define its own competing `ArrayList`; it
    reuses this one directly, the same class `mutableListOf`'s own real
    implementation, above, already constructs.
  - *Its use:* Called inside `history`'s own custom getter, on every
    read, to hand back a brand-new list holding a snapshot of whatever
    `mutableHistory` contains *at that exact moment* — never the same
    object as `mutableHistory` itself.
  - *Type:* An instance constructor. Signature (the overload resolved
    here): `ArrayList(c: Collection<out E>)`.
  - *Responsibility:* Building a new, independent list whose initial
    contents are copied from an existing collection, at the moment of
    construction only — it establishes no ongoing connection to the
    original collection afterward.
  - *Depends on:* An existing `Collection` to copy from — here,
    `mutableHistory`.
  - *Connects to:* Called by `history`'s own getter; its result is what
    every caller of `service.history` actually receives.
  - *Shape:* The defensive-copy boundary between `Service`'s own private,
    mutable state and whatever code reads `history` from outside.

## Concept Unit: `private set` — A Property with a Restricted Setter

### The Problem

Lesson 3.2's own `getRunCount()` works, but it's a method a working
Kotlin programmer would never write by hand — `private var runCount:
Int` plus a separate `fun getRunCount(): Int { return runCount }` is
exactly the three-piece Java pattern this whole phase's own "less
ceremony" framing exists to remove. Given that every `val`/`var`
declaration in Kotlin is already, per this lesson's own Terms entry, a
real property with a real getter generated automatically — what is
`getRunCount()` actually doing that Kotlin doesn't already do for free?

> **Stop and try it yourself first:** If `var runCount: Int = 0` already
> generates a real, public `getRunCount()`-equivalent getter
> automatically (this lesson's own Terms entry for **property** already
> says so), what would happen if `Service`'s `getRunCount()` method were
> simply deleted, and every caller wrote `service.runCount` instead of
> `service.getRunCount()`? Would that alone be enough — or is there a
> second problem `getRunCount()` was *also* solving, one that a bare
> `var runCount: Int = 0` wouldn't, on its own, still solve? (Hint: what
> could outside code do to `service.runCount` today, if `runCount` were
> simply a public `var` with no method wrapping it at all?)

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.kt`:

```kotlin
class Counter {
    var count: Int = 0
        private set

    fun increment() {
        count = count + 1
    }
}

fun main() {
    val counter = Counter()

    counter.increment()

```

```

```

`counter.count` — no parentheses, no `get` prefix — read `count`'s real
value directly, proving property access syntax works even though `count`
is declared with an explicit `private set`. The real proof this Concept
Unit's own Socratic prompt was asking for comes from disassembling the
real compiled class (`javap -p`, run this session against this exact
lab — see `verification/3.3/output.txt`):

```
public final class Counter {
  private int count;
  public Counter();
  public final int getCount();
  public final void increment();
}
```

Two things this proves: first, `counter.count` really did compile down
to a call on a real, generated `getCount()` method — Kotlin's property
syntax is not a special case the JVM understands; it's ordinary
getter-method bytecode, generated for the reader instead of typed by
hand. Second — and this is the answer to the Socratic prompt above —
`-p` shows *private* members too, and there is no `setCount` method
anywhere in this output, not even a private one: because `private set`
means the setter is only ever used inside `Counter` itself (inside
`increment()`), the compiler writes directly to the private field there
rather than generating a callable method for it at all. A plain public
`var count: Int = 0`, with no `private set`, would have generated both
`getCount()` *and* a real public `setCount(int)` — which is exactly what
this unit's Socratic prompt was pointing at: a bare public `var` would
let outside code write `counter.count = 999` directly, something
`private set` genuinely, additionally prevents, beyond what property
syntax alone provides.

### CS Lens

Property syntax that always desugars to real accessor methods — so that
switching from a stored value to computed logic never requires changing
any caller — is a specific, real instance of a broader idea: the
**uniform access principle**, the design rule that a client of some data
shouldn't be able to tell, or need to care, whether that data is stored
directly or computed on demand.

```
Also recognized in: C#'s own properties (`public int Count { get; private
set; }`, near-identical to this lesson's own Kotlin syntax), Python's
`@property` decorator turning a method into attribute-style access,
Eiffel's own uniform access principle (the design rule's original,
named source, predating all of the above)
```

### SE Lens

The principle is the same **stating intent where the compiler can check
it** idea Lesson 3.1 named for `val`/`var`, applied again here at a
different granularity: `private set` states, in the property's own
declaration, "outside code may read this but never write it" — checked
by the compiler, not left as a convention a reader has to trust by
noticing there's no public setter method anywhere. The alternative not
chosen — Lesson 3.2's own deliberately-Java-shaped version — costs three
extra, disconnected lines (a separate field, a separate method signature,
a separate method body) to express a single idea a property declaration
plus one modifier now expresses in two. The real, honest tradeoff: `var
runCount: Int = 0` with `private set` still requires a reader to know
Kotlin's own property/accessor model to correctly predict that
`getRunCount()`-equivalent behavior exists at all — a Java programmer
seeing bare `runCount: Int` for the first time has no visual cue, the way
an explicit `getRunCount()` method name would have given one, that a
method call (not raw field access) is actually happening underneath.

## Concept Unit: `history` — A Getter That Computes Instead of Stores

### The Problem

Java's own `Service.java`, at its final commit (`75787fe`), has a
`getHistory()` that doesn't just return a field — it returns `new
ArrayList<>(history)`, a fresh copy, specifically so outside code can
never mutate `Service`'s own private history list by holding onto
whatever `getHistory()` handed back. A bare Kotlin property — even one
with `private set`, per the previous unit — only controls *whether*
outside code can reassign the property to point at a different list
entirely; it does nothing to stop outside code from calling `.add(...)`
on the *same* list object a plain getter handed back. Does Kotlin's
property syntax have room for a getter that does real work on every
read, the way Java's own hand-written `getHistory()` method already
does?

> **Stop and try it yourself first:** So far, every `val`/`var` property
> in this curriculum's Kotlin code has looked like `var name: Type =
> initialValue` — a fixed value, assigned once, read back unchanged.
> Given that the previous unit's own disassembly already proved a
> property's getter compiles into a real, ordinary method, is there any
> real reason a property's *getter* couldn't run arbitrary code — a
> calculation, a copy, anything a normal method body could do — every
> time it's read, rather than just returning a stored field? If so, what
> syntax would you guess replaces the implicit `= initialValue` a stored
> property writes, given that a *computed* property has no single fixed
> value to store in the first place?

### Introduce the Concept in Isolation

Throwaway code, unconnected to `Service.kt`:

```kotlin
class Box {
    private val items = mutableListOf<String>()

    val snapshot: List<String>
        get() = ArrayList(items)

    fun add(item: String) {
        items.add(item)
    }
}

fun main() {
    val box = Box()
    box.add("first")
    val copy = box.snapshot
    box.add("second")
    println(copy)
    println(box.snapshot)
}
```

Run this session (`verification/3.3/lab_computed_getter.kt`):

```
[first]
[first, second]
```

This proves exactly the defensive-copy behavior Java's own `getHistory()`
was written for: `copy` was taken (via `box.snapshot`) right after adding
only `"first"`, and printing it *after* a second item was added still
shows only `[first]` — because `copy` is a real, independent `ArrayList`,
already fully built at the moment it was read, with no ongoing connection
back to `items`. Reading `box.snapshot` a second time, after the second
`add`, computes a *brand-new* copy reflecting the current state —
`[first, second]`. A property whose `get()` block is written explicitly,
running real code on every read instead of returning a fixed stored
value, is called a **custom getter**.

### SE Lens

The principle is **encapsulation enforced at the type level, not just by
convention**. Java's `getHistory()` achieves the identical real
guarantee — a caller can never mutate `Service`'s own internal history —
but only because the method's *body* happens to copy; nothing in Java's
own `List<String>` return type stops a future edit from changing
`return new ArrayList<>(history);` to `return history;` by accident,
silently breaking the guarantee with no compiler warning at all. Kotlin's
`List<String>` return type, backed by this lesson's own real, verified
compile error, makes a whole *category* of that mistake impossible to
reintroduce silently: even if a future edit to `history`'s own getter
returned `mutableHistory` directly instead of a copy, any caller trying
to call `.add(...)` on the result would still fail to compile, because
the declared return type is `List<String>`, not `MutableList<String>` —
the type itself, not just this one getter's own current implementation,
is what a caller's guarantee actually rests on. The real cost: Kotlin's
List/MutableList split is a distinction that exists nowhere in Java,
meaning porting *back* the other direction (Kotlin calling into existing
Java collection code) requires knowing that Java's own `List<T>` doesn't
carry this same compile-time promise — a real seam this curriculum's own
Lesson 3.8 (comparing all three languages) will have real material to

Tracing `runCount` and `history` through this lesson: `runCount` began
Lesson 3.2 as a private field with a separate, hand-written getter

units together replaced every piece of Java-shaped boilerplate Lesson 3.2
deliberately left behind, without changing one line of `run()` or
