```kotlin
// Service.kt
class Service(private val logger: Logger) {
    var runCount: Int = 0
        private set

    private val mutableHistory = mutableListOf<String>()

    val history: List<String>
        get() = ArrayList(mutableHistory)

    fun run() {
        runCount = runCount + 1
        logger.log("Service is running.")
        mutableHistory.add("Service is running.")
    }

    fun reset() {
        if (runCount == 0) {
            throw IllegalStateException("Cannot reset a service that has never run.")
        }

        runCount = 0
        logger.log("Service has been reset.")
        mutableHistory.add("Service has been reset.")
    }
}
```

```kotlin
// LastValue.kt
data class LastValue<T>(val value: T)
```

```kotlin
// Describer.kt
fun <T> T.describe() {
    println(this)
}
```

```kotlin
// Program.kt
fun main() {
    val logger: Logger = LoudLogger()
    val service = Service(logger)
    service.run()
    service.run()
    println(service.runCount)

    logger.log("Program finished.")

    val lastCount = LastValue(service.runCount)
    println(lastCount.value)

    val lastMessage = LastValue("Program finished.")
    println(lastMessage.value)

    service.runCount.describe()
    "Program finished.".describe()

    service.reset()
    println(service.runCount)

    val neverRun = Service(logger)
    try {
        neverRun.reset()
    } catch (ex: IllegalStateException) {
        logger.log(ex.message ?: "Unknown error")
    }

    println(service.history)

    val messageCounts = mutableMapOf<String, Int>()
    for (message in service.history) {
        val current = messageCounts.getOrDefault(message, 0)
        messageCounts.put(message, current + 1)
    }

    println(messageCounts["Service is running."] ?: 0)
    println(messageCounts["Service has been reset."] ?: 0)

    val total = (messageCounts["Service is running."] ?: 0) + (messageCounts["Service has been reset."] ?: 0)
    println(total)

    val firstEverEntry = neverRun.history.firstOrNull()
    println(firstEverEntry?.length ?: -1)
}
```

## Concept Unit: Why Each Abstraction Exists, in Kotlin's Own Terms

**Real Project Change: none (inspection only).**

Every SE Lens conclusion from this phase, in one place:

- **`val`/`var` (Lesson 3.1):** stating mutability intent where the
  compiler checks it, rather than leaving it to Java's own `var` (which
  answers only "what type is this," never "can this change") plus an
  optional, rarely-used `final`.
- **Constructor-parameter properties (Lesson 3.2):** removing ceremony
  that carries no real decision — a field, a constructor parameter, and
  a constructor-body assignment, collapsed into one declaration, proven
  by disassembly (Lesson 3.3) to compile to the identical real
  `getRunCount()`-shaped bytecode a hand-written Java getter would.
  Kotlin's exceptions, in the same lesson, were proven — not assumed —
  to be Java's own real `java.lang` classes, reused directly rather than
  reinvented.
- **Properties with `private set` and custom getters (Lesson 3.3):** the
  uniform access principle — a caller can never tell, or need to care,
  whether `service.runCount` reads a stored field or `service.history`
  computes a fresh defensive copy on every read; both look identical at
  the call site, proven by real disassembly to both compile to genuine
  getter methods either way.
- **`data class` (Lesson 3.4):** value types — proven, against a real,
  pasted bug in Java's own unmodified `LastValue` (two equal-valued
  instances reporting `false` for `.equals()`), that generating
  `equals`/`hashCode`/`toString`/`copy`/`componentN` from a class's own
  declared properties removes an entire category of "nobody got around
  to writing this" bug, not just a style preference.
- **Nullable types, `?:`, `?.` (Lesson 3.5):** moving a real category of
  runtime failure (Java's own `NullPointerException`) to compile time —
  proven with two real, pasted compiler errors (arithmetic on `Int?`;
  member access on `String?`) that Kotlin refuses to compile the unsafe
  version at all, then proven again that the safe versions produce
  correct real output for both the branch that never triggers
  (`ex.message`, `Map.get` on always-present keys) and the branch that
  genuinely does (`neverRun.history.firstOrNull()`, proven empty for
  real).
- **`interface`, real polymorphism (Lesson 3.6):** programming against
  an abstraction — `Service` needed zero changes to accept a second,
  behaviorally different `Logger`, proven by an isolated `Shape`/
  `Square`/`Circle` lab that the same call dispatches to genuinely
  different real code depending on the real object, decided at runtime.
  The same lesson also proved a real, separate pitfall: `var`/`val`
  infers a value's *concrete* type, not whichever interface it happens
  to implement — proven with a real compile error, and resolved the
  same way the real Java-derived reference source already, independently,
  chose to resolve it.
- **Extension functions (Lesson 3.7):** not forcing state onto an
  operation that has none — `Describer`, a Java class with no fields at
  all, ported to a single free function. The same lesson also proved a
  real, honest limit: unlike Lesson 3.6's own real polymorphism,
  extension functions resolve statically, from a variable's *declared*
  type, never from the real object's own type — proven with a real,
  isolated counter-example (`Animal`/`Dog`), not merely asserted.

**One structural fact, confirmed true a second time:** every real
dependency in this phase's own graph, above, is either composition
(`Service` holding a `Logger`) or interface implementation
(`ConsoleLogger`/`LoudLogger` implementing `Logger`) — real class
inheritance (`class X : Y()`, extending a concrete class) appears
*nowhere* in this phase's own real, committed project code. The one
place it appeared at all was Lesson 3.7's own isolated, explicitly
discarded `Animal`/`Dog` lab, built solely to prove a fact about
extension-function dispatch and never connected to `Service` or any real
project file. The same "composition and interfaces everywhere, class
inheritance nowhere" fact Lesson 2.10 established for Java is confirmed,
independently, true of this Kotlin port too.

## Concept Unit: C# → Java → Kotlin — Every Real Divergence, Side by Side

**Real Project Change: none (inspection only).** Every C# claim below
was checked fresh this session by reading the real files in
`code/01-csharp/Service` (`git log --oneline`, `git show`, and one real
compile-and-run check, `verification/3.8/check_csharp_nullable/`, for
the one claim that genuinely needed fresh execution rather than reading
already-tracked code); every Java claim was already proven in Lesson
2.10 and is restated here, not re-derived.

- **Entry point.** C#'s own `code/01-csharp/Service/Program.cs`, checked
  fresh this session via `git show` of its very first real commit
  (`5a43116`), has *never* had a wrapping class at all — it used C#'s
  own top-level-statements feature (opted into by its own `.csproj`)
  from the very first line of this whole curriculum's own C# project.
  Java requires a wrapping class *unconditionally* — Lesson 3.1's own
  real port had to correct an earlier draft of this exact lesson that
  claimed otherwise before this session double-checked the real C#
  source. Kotlin, per Lesson 3.1, needs no wrapping class either, using
  `fun main()` directly — closer, on this specific point, to C#'s own
  modern style than to Java's.
- **Classes.** All three declare a class body with `{ }`. Real,
  verified difference in default visibility when no modifier is
  written: Kotlin's default is `public` (Lesson 3.8's own disassembly,
  above: a plain `class NoModifier` compiled to real `public final
  class NoModifier` bytecode); Java's own default (no modifier) is
  package-private, established as part of Java's own access-modifier
  material; C#'s own default for a top-level class is `internal`, not
  `public` — three genuinely different silent defaults across all three
  languages for the exact same "write nothing" starting point.
- **Constructors.** C#'s `Service` (`code/01-csharp/Service/Service.cs`,
  read fresh this session) uses a separate constructor body assigning
  `this.logger = logger;`, identical in shape to Java's own — neither
  language has Kotlin's constructor-parameter-property shorthand
  (Lesson 3.2), which collapsed that same three-piece pattern (field,
  constructor signature, constructor body) into one line, `private val
  logger: Logger`, in the primary constructor itself.
- **Interfaces.** C#'s own interface is named `ILogger`
  (`code/01-csharp/Service/ILogger.cs`) — the `I`-prefix is a real,
  long-standing C# naming *convention*, not a language requirement;
  Java's and Kotlin's own interfaces are both named plainly, `Logger`,
  with no such convention in either language's own idiomatic style.
  All three languages express "this class implements that interface"
  with real, if differently-spelled, syntax: C#'s `: ILogger`
  (identical colon syntax to Kotlin's own `: Logger`, coincidentally),
  Java's `implements Logger`.
- **Properties.** This is this whole comparison's own sharpest three-way
  divergence. C#'s `Service.RunCount` (`code/01-csharp/Service/Service.cs`)
  is a real, native C# property — `public int RunCount { get { return
  runCount; } }` — get-only, with no setter written at all, expressed as
  a first-class language feature, the same general idea as Kotlin's own
  `private set`, though C#'s own syntax makes the getter's own body
  explicit rather than defaulting one in automatically. Java has *no*
  native property syntax whatsoever — Lesson 2.3's own `getRunCount()`
  method is Java's only real option, a real, permanent language gap
  Kotlin's own Lesson 3.3 exists specifically to *not* need. Kotlin's
  own `var runCount: Int = 0` with `private set` sits between the two:
  a real property, like C#'s, but with an *implicit* default getter
  unless a custom one is written (Lesson 3.3's own `history`), where C#
  requires the getter's own body to be written even for the trivial
  case shown here.
- **Generics.** All three use near-identical `<T>` angle-bracket
  declaration syntax — the one place this whole comparison finds
  genuine, close continuity rather than divergence. The real difference
  is what each language's own `LastValue<T>` chose to *do* with it: C#'s
  (`code/01-csharp/Service/LastValue.cs`) and Java's are both mutable,
  `Set`/`set` plus `Get`/`get` methods, exactly mirroring each other;
  Kotlin's own Lesson 3.4 deliberately diverged into an immutable `data
  class LastValue<T>(val value: T)`, a real, stated choice (avoiding a
  premature nullable-type forward-reference), not a language
  requirement — nothing about Kotlin's own generics forced immutability
  here.
- **Nullability.** C#'s own `.csproj` (`code/01-csharp/Service/Service.csproj`,
  read fresh this session) has `<Nullable>enable</Nullable>` turned on —
  modern C#'s own compile-time null-safety system, annotating reference
  types as nullable (`string?`) or not, checked by the compiler,
  genuinely closer in spirit to Kotlin's own system (Lesson 3.5) than to
  Java's complete absence of one. But real, verified evidence from this
  session (`grep -n '?' *.cs` inside `code/01-csharp/Service` returned no
  matches at all) shows this specific reference project never actually
  *exercises* that feature anywhere in its own real code — the setting
  is on, but no `?` appears in any real `.cs` file. A direct, fresh check
  this session (`verification/3.8/check_csharp_nullable/`, a real,
  compiled and run C# program) confirms `Exception.Message` itself is
  annotated non-nullable in modern .NET — `string safe = ex.Message;`
  compiles with zero nullable warnings under `<Nullable>enable</Nullable>`
  — the same real value Kotlin's own `Throwable.message` (Lesson 3.2,
  Lesson 3.5) is `String?` for. Java, with no compile-time nullability
  system at all, is the real outlier of the three: every reference type
  is silently nullable everywhere, checked by nothing.
- **Type inference.** C#'s own `var service = new Service(logger);`
  (`code/01-csharp/Service/Program.cs`) and Java's own `var service =
  new Service(logger);` (Lesson 2.2) both infer a value's *concrete*
  type from its initializer — the identical real behavior Lesson 3.6
  proved for Kotlin's own `val`/`var`. All three languages' own
  reference sources independently made the *identical* real choice at
  the identical spot: C#'s own `Program.cs` writes `ILogger logger = new
  LoudLogger();` — explicit, not `var` — one line before its own `var
  service = ...`; this curriculum's Kotlin port (Lesson 3.6) made the
  same choice, for the same reason, after independently re-deriving it.
- **Runtime.** C# runs on the CLR, Java and Kotlin both compile to real
  JVM bytecode — proven, this whole phase, by real `javap` disassembly
  (Lessons 3.3 and 3.8) showing genuine, ordinary JVM classes and
  methods underneath every piece of Kotlin syntax this phase used,
  interoperable with Java's own classes directly (Kotlin's own
  `IllegalStateException`, proven in Lesson 3.2 to be a real `typealias`
  for `java.lang.IllegalStateException`, not a separate class).

**Real, honest arithmetic.** C# has 11 real commits across its own 12
lessons (1.12, its own pure review, has none); Java has 9 across 10
(2.10, likewise); this Kotlin phase has 7 across 7 real-code lessons
(3.1 through 3.7 — 3.8, this lesson, adds an eighth lesson with none).
Kotlin's own count is the smallest of the three, and by more than a
one-lesson difference alone: Lesson 3.2 alone folded four separate real
Java-lesson-equivalents (extracting `Service` as its own class,
encapsulating its state behind a getter, injecting its `Logger`
dependency, and adding `reset()`'s own failure handling — four separate
Java commits, `366bed6`, `71d927d`, `b35d9aa`, and `ece5221`) into one
single Kotlin commit, a real degree of compression beyond what Java
itself achieved relative to C#. Lesson 3.3 (the properties refactor) has
no C# or Java commit counterpart at all — it exists only because Kotlin
itself has something worth refactoring *into*. And, matching Java's own
already-stated plan, this Kotlin phase never ported C#'s own
`RunAsync`/`Task`/`await` (C#'s own commit `10702f3`) at all — Kotlin's
own asynchronous model, coroutines, is this whole curriculum's own later
Phase 10 subject, not Phase 3's. None of this is a weaker port — it's
the same real "approximately the same architecture" this curriculum has
named as its own goal since Java's own Lesson 2.10, now confirmed a
second time, with the actual mechanism (constructor-parameter properties
collapsing several Java-shaped steps into one) named plainly rather than
left as an unexplained smaller number.

This whole phase ported the identical nine-step architecture — an entry
point, a stateful service, an injected logging dependency with two real
implementations, a generic value holder, a generic print operation, a

precisely where Kotlin sits relative to C# and Java on every axis this

enabled-if-unused nullability), sometimes doing alone what neither older

independently arriving at the identical decision all three reference
sources made on their own (typing `logger` as the interface, not letting
