## Terms used in this lesson

- **Promise** (full, real treatment, deferred from Lesson 6.7) — per
  MDN's own documentation, fetched and quoted this session, "the
  `Promise` object represents the eventual completion (or failure) of an
  asynchronous operation and its resulting value." A Promise is always
  in exactly one of three real states, per that same documentation:
  **pending** ("initial state, neither fulfilled nor rejected"),
  **fulfilled** ("the operation was completed successfully"), or
  **rejected** ("the operation failed"). `fetch("data.json")`'s own
  real return value, since Lesson 6.7, starts pending and becomes
  fulfilled once the real response actually arrives.
- **`async` function** — a real function, declared with the keyword
  `async` directly before `function`, that's always allowed to use
  `await` inside its own body. Per MDN's own documentation, fetched and
  quoted this session, such a function "always return[s] a promise" —
  even one that never explicitly builds one itself.
- **`await`** — a real operator, usable only inside an `async`
  function, that pauses that function's own execution until a given
  Promise settles, then evaluates to its real, fulfilled value directly.
  Per MDN's own documentation, fetched and quoted this session, "the
  `await` expression never blocks the main thread and only defers
  execution of code that actually depends on the result" — meaning only
  the `async` function itself pauses; every other real code in the page
  keeps running normally in the meantime.

### Introduce the Concept in Isolation

This is exactly what `async`/`await` control flow looks like, isolated
here in a real, throwaway lab (`verification/6.8/lab_async.js`),
deliberately kept free of any real network request, run this session:

```js
function delay(value) {
  return Promise.resolve(value);
}

async function run() {
  console.log("start");
  const result = await delay("done");
  console.log(result);
}

run();
console.log("after calling run()");
```

Real output, from a real `node lab_async.js` run this session, saved in
`verification/6.8/run_output.txt`:

```
start
after calling run()
done
```

This is the real, concrete answer to this unit's own Socratic prompt —
and the order is genuinely worth tracing step by step, since it's the
real crux of what "doesn't block the main thread" actually means:

1. `run();` — calling an `async` function runs its own body immediately,
   synchronously, up to its first real `await`; `console.log("start")`
   runs right away, printing `start`.
2. `const result = await delay("done");` — `delay("done")` returns an
   already-fulfilled real Promise (`Promise.resolve` never actually
   waits at all), but `await`, per this lesson's own Terms entry, still
   pauses `run`'s own execution here and hands control back to whatever
   called `run()`, rather than continuing immediately, even though the
   value is technically already available.
3. `console.log("after calling run()");` — this line sits directly
   after `run();` in the real, top-level, synchronous code, and now
   runs next, printing `after calling run()`, *before* `run`'s own
   body ever resumes — real, direct proof that calling an `async`
   function doesn't block whatever comes after it.
4. Only once all of that real, synchronous code has finished does
   `run`'s own paused body resume, `result` finally receiving `"done"`,
   and `console.log(result)` printing it last.

Applied directly to this lesson's own real project, the identical real
pause-and-resume behavior is what lets `loadEntries()`'s own body read
top-to-bottom while `entryList`'s own real click handlers (Lesson 6.5,
Lesson 6.6) keep working normally the entire time `fetch`'s own real
request is still pending.
