## Terms used in this lesson

- **`this`** — per MDN's own documentation, fetched and quoted this
  session, "the `this` keyword refers to the context where a piece of
  code, such as a function's body, is supposed to run." For an ordinary
  method, that context is decided fresh, every single call, by *how* the
  method is actually invoked — never by where it was written.
- **Call-site binding** — the real rule, per that same MDN
  documentation, that a regular function's own `this` is set based on
  how it's invoked: written as `object.method()`, `this` becomes
  `object`; written as a bare function call, `this` becomes something
  else entirely — `undefined` in strict mode (this project's own real
  context, since Lesson 6.10's own real ES modules are always strict),
  or, for a real DOM event listener specifically, the element the
  listener is attached to.
- **Method** — a real function stored as a property of an object,
  callable as `object.methodName()`. `selection.select`, this lesson's
  own real addition, is this project's first.

### CS Lens

**A value resolved by the calling context rather than fixed at
definition time**, is a real, recurring idea beyond JavaScript's own
`this`.

```
Also recognized in: Python's own explicit `self` parameter, which,
unlike JavaScript's implicit `this`, must be written by hand on every
method — a real, deliberate design choice trading this exact real
confusion for extra typing; a C++ `this` pointer (this whole
curriculum's own Phase 4), resolved similarly at the call site, though
C++ makes calling a member function without an object a compile-time
error rather than a real runtime surprise; dynamic scope generally
(Lesson 6.5's own SE Lens already named it as JavaScript's real

```

### SE Lens

The principle is **binding must be considered wherever a method is
handed off, not just where it's called normally** — `counter.increment
()` is safe; the instant that same method is passed somewhere else *as
a value* (assigned to a variable, passed as a callback), its own real
connection to `counter` is gone unless something explicit preserves it.
The real alternative some other languages choose: bind a method
permanently to its own object the moment it's declared, so it can never
be called any other way (this whole curriculum's own C#, Java, and
Kotlin phases all work this way for an ordinary instance method). The
real, concrete cost of JavaScript's own real, different choice — `this`
decided fresh at every call, never fixed — is exactly this unit's own
real, thrown error: real flexibility (the same real function usable with
a genuinely different `this` depending on how it's called) traded for a
real, easy-to-hit footgun the instant a method is extracted without
that flexibility actually being wanted.

### Introduce the Concept in Isolation

This lesson's own real proof is two separate, real runs against the
actual project — the safe version, already shown correct above, and a
deliberately broken one, built and run specifically to fail. A real,
deliberately broken copy
(`verification/6.11/lab_broken_app.js`) changes exactly one real line:

```js
// Deliberately broken: passes the method reference directly instead
// of article.addEventListener("click", () => selection.select(article, entry));
article.addEventListener("click", selection.select);
```

A real, synthetic click against this broken variant, run this session
with `--enable-logging=stderr` to capture the browser's own real
console, saved in `verification/6.11/run_output.txt`:

```
Uncaught TypeError: Cannot read properties of undefined (reading 'add')
```

Tracing exactly why, one real step at a time:

1. `article.addEventListener("click", selection.select);` — this real
   call hands the browser a bare reference to the `select` function
   itself, with no memory of `selection` attached to it at all — the
   identical real problem this lesson's own previous unit already
   isolated with `extracted`.
2. A real click fires; the browser calls the listener as
   `selection.select.call(clickedElement, event)` — per this lesson's
   own real Terms entry for **call-site binding**, a DOM event listener
   is always called with `this` set to the element it's attached to,
   and with exactly one real argument, the `Event` object.
3. Inside `select`, `this` is therefore the clicked `<article>` element
   — not `selection` — and the function's own first parameter,
   *written* as `article`, is actually bound to the real `Event` object,
   since only one real argument was ever passed; the function's own
   second parameter, `entry`, is `undefined`.
4. `if (this.article)` — `this` (the clicked element) has no real
   `.article` property yet; this check correctly, if accidentally,
   evaluates to false, and is skipped.
5. `this.article = article;` — sets a new, real `.article` property
   directly on the clicked DOM element, assigning it the real `Event`
   object (since that's what the parameter named `article` actually
   holds here, per step 3) — legal JavaScript, silently wrong, and not
   yet an error.
6. `this.article.classList.add("selected");` — `this.article` is now
   the real `Event` object just assigned; `Event` objects have no real
   `.classList` property, so `this.article.classList` evaluates to
   `undefined`, and calling `.add` on that is exactly what throws —
   `Cannot read properties of undefined (reading 'add')`, the identical
   real error captured above.

This is the real, concrete answer to this unit's own Socratic prompt:
passing `selection.select` directly causes *two* real, independent
problems at once, not one — `this` resolves to the wrong object (the
clicked element, not `selection`), and the function's own real
parameters receive the wrong real values entirely (the click's own
`Event`, not the intended `article` and `entry`) — because
`addEventListener` always calls a listener with its own fixed, one-
argument calling convention, regardless of how many parameters the
listener itself declares.

The real, committed project avoids both problems the same way it always
has, since Lesson 6.1: the arrow function `article.addEventListener
("click", () => { ... })` is what `addEventListener` actually calls —
and its own body doesn't read `this` at all, it calls `selection.select
(article, entry)` using real, explicit method-call syntax, with `this`
correctly set to `selection` and both real arguments passed exactly as
intended, regardless of anything `addEventListener` itself does with
`this` or with its own single `event` argument.
