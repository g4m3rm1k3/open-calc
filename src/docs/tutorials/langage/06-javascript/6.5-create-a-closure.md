## Terms used in this lesson

- **Lexical scope** — the real rule, fixed the moment code is written
  (not when it runs), that determines which outer variables a function
  can see: a function can read any variable declared in whichever block
  or function it was itself written inside, no matter how deeply nested,
  and no matter when it's actually called.
- **Closure** — a real function that keeps real, working access to
  variables from the scope it was defined in, even after that outer
  scope has already finished running. This lesson's own new click
  handler, defined inside `createEntryElement`, is one: it keeps real
  access to that specific call's own `entry` parameter, indefinitely,
  long after `createEntryElement` itself has already returned.

## Objects and methods used

- **`document.title`** (reappearing use of `document`, first fully
  explained in Lesson 6.1)
  *What it is:* a real, writable property of `document` holding the

  *Implementation:* a plain string property; reading it returns the

  *Its use:* this lesson's own real click handler assigns to it

  knew specifically which record it belonged to.
  - *Type:* an instance property, defined on `Document`.
  - *Responsibility:* hold, and let script both read and replace, the
    real text the browser shows for this page's own title.
  - *Depends on:* being read or assigned on `document`, this project's
    own single, real global page object, already explained in full in
    Lesson 6.1.
  - *Connects to:* assigned here inside a closure created by
    `createEntryElement`; its own real effect is directly, visibly

    immediately next, gives this exact same closure a real, substantial

## Concept Unit: A Function Can Read What Surrounds It

### The Problem

Every function this project has written so far — `createEntryElement`,
`renderEntries`, Lesson 6.1's own click handler — only ever reads values
handed to it directly: a parameter, or a value read fresh off `entries`
or `entryList` at the moment it runs. None of them has yet read a value
that belongs to neither its own parameters nor the global top level —
specifically, a value that belongs to some *other*, enclosing function.
Given that this lesson's own real goal is a click handler, defined
*inside* `createEntryElement`, that needs to know that same call's own
`entry` — not a parameter of the handler itself, since `addEventListener
`'s own real handler signature never passes it one — what real rule
would let that inner function read `entry` at all?

> **Stop and try it yourself first:** Every function this project has
> declared so far is written directly at the top level of `app.js` —
> nothing has ever been *nested*, one function's own body containing
> another function's own declaration. Given that JavaScript allows a
> function to be declared anywhere an expression is allowed, including
> directly inside another function's own body, what would you predict
> happens if that inner function's own code mentions a name it never
> declared itself, and never received as its own parameter, but which
> *is* a parameter of the outer function it's nested inside?

### CS Lens

**A function's own ability to reference names from the environment it
was defined in, resolved by where code is written rather than how it's
later called**, is a real, foundational programming-language idea well
beyond this one function.

```
Also recognized in: nested function or nested class definitions in
Python or Java, each able to reference their own enclosing scope's
names; a mathematical function's own free variables, bound by the
context a formula is written within rather than by how it's later
evaluated; block-scoped variables in C++ or C# (this whole curriculum's
own Phase 1 and Phase 4), visible to any nested block written inside

```

### SE Lens

The principle is **scope determined by source structure, not by call
history** — a reader can always determine what `greet` can see by
reading where it's written, without ever having to trace who calls it or
when. The real alternative some languages historically chose (and some
still support in restricted forms) is **dynamic scope**, where a
function sees whatever variables happen to be in scope at the *call
site*, not the definition site. The real, concrete cost dynamic scope
would introduce here: `greet`'s own behavior would then depend on
*where it's called from*, not just on its own source code — reading
`greet`'s own definition alone would no longer be enough to know what it
does, since the exact same call could read a completely different real
`greeting`, or none at all, depending on what happened to be in scope at
each individual call site.

### Introduce the Concept in Isolation

This is exactly what a closure surviving its own outer function's return
looks like, isolated here in a real, throwaway lab
(`verification/6.5/lab_closure.js`), run this session:

```js
function makeGreeter(name) {
  return () => console.log(`Hello, ${name}`);
}

const greetAlice = makeGreeter("Alice");
const greetBob = makeGreeter("Bob");

greetAlice();
greetBob();
```

Real output, from a real `node lab_closure.js` run this session, saved
in `verification/6.5/run_output.txt`:


This is the real, concrete answer to this unit's own Socratic prompt:
each call to `makeGreeter` gets its own, separate, real `name`
parameter, and the arrow function it returns keeps real, working access
to that *specific* call's own `name` — proven directly by `greetAlice`
and `greetBob` printing two genuinely different real values, long after
both calls to `makeGreeter` have already returned. This is called a
**closure**: a function that carries its own defining scope along with
it, wherever it goes, for as long as it exists.

### CS Lens

**A function bundled together with a live reference to its own defining
environment, able to outlive that environment's own normal lifetime**,
is a real, foundational idea well beyond this one click handler.

```
Also recognized in: a real callback registered with any asynchronous
API in any language — a C# delegate or Java lambda capturing local
variables from its own enclosing method (this whole curriculum's own
Phase 1 and Phase 2); a generator or iterator object, which resumes
exactly where it left off, remembering its own local state between
calls; a partially-applied function in functional programming (this

```

### SE Lens

The principle is **state carried implicitly, through scope, rather than
passed explicitly, through parameters** — this lesson's own click
handler never receives `entry` as an argument from `addEventListener`
(which only ever hands a real `Event` object to its own callback); it
already has it, closed over from `createEntryElement`'s own call. The
real alternative not chosen: attach `entry.id` to the DOM instead (via
`data-entry-id`, per Lesson 5.8, already present) and have the click
handler read it back out of the clicked element at the moment it runs,
looking the matching record back up in `entries` by that id. The real,
concrete cost that alternative would introduce: every real click handler
in this project would need real, extra lookup logic — reading an
attribute back off the DOM, then searching `entries` for a match — for a
value this lesson's own closure already has, directly, for free,
without ever touching the DOM again after the element was first built.
This lesson's own real approach is simpler specifically *because*
JavaScript's own closures make it simpler; the SE Lens honestly worth
naming here is that this convenience has a real limit — Lesson 6.10,
still ahead in this phase, revisits exactly this same closed-over `entry`
once this project's own data starts coming from a real network response
that can change after the fact, at which point a closure's own frozen
snapshot and the DOM's own live `data-entry-id` stop being
interchangeable.
