## Terms used in this lesson

- **Dynamic typing** — a real language design where a variable's own
  type is neither declared nor checked before the program runs; any
  variable can hold any kind of value, and can be reassigned to a
  genuinely different kind of value later. JavaScript, this whole
  phase's own real language, works this way — proven directly, this
  session, in this lesson's own first Concept Unit.
- **Static typing** — a real language design, reappearing from this
  whole curriculum's own Phase 1 and Phase 2, where a variable's own
  type is fixed at compile time, and the compiler refuses to compile a
  program that ever assigns a mismatched value to it. C# and Java both

- **Effectively final** — per Oracle's own official Java tutorial,
  fetched and quoted this session, "a variable or parameter whose value
  is never changed after it is initialized." Java's own real,
  compiler-enforced rule: "a lambda expression can only access local

### Three Languages, One Question: Can a Closure Mutate What It Captured?

**JavaScript: yes**, already proven for real by this whole phase.
Lesson 6.6's own real `let selectedArticle` (its real successor,
`selection.article`, Lesson 6.11) is read *and reassigned* inside a real
closure, on every real click — proven, this session and Lesson 6.6's
own session, by a real, two-click verification showing selection
correctly moving from one record to another.

**Java: no — a real, compiler-enforced refusal.** Per Oracle's own
official tutorial, fetched and quoted this session, attempting the
identical real thing — a lambda reassigning a captured local variable —
produces a real, specific compile error: `"Local variable z defined in
an enclosing scope must be final or effectively final."` A Java lambda
may *read* a captured local variable, exactly as JavaScript's closures
do, but may never reassign one — the identical real capability Lesson
6.6's own entire real design depends on is, in Java, a compile-time
error, not a runtime choice.

**C#: yes — proven directly by Microsoft's own official documentation's
own real, executed example**, fetched and quoted this session: a real
C# lambda, `updateCapturedLocalVariable = x => { j = x; ... }`,
genuinely reassigns a captured local variable `j`, and that
documentation's own real, shown output confirms it: `j` reads `0`
before the lambda runs, and `10` after — real, direct proof C#'s own
closures behave like JavaScript's here, not like Java's.

### CS Lens

**Whether a captured variable is a real, live reference a closure can
mutate, or a real, frozen snapshot a closure can only read**, is a real,
consequential closure-design choice beyond any one of these three
languages.

```
Also recognized in: Python's own closures, which — like Java — cannot
reassign a captured outer variable without an explicit `nonlocal`
declaration; Swift's own closures, which, like JavaScript and C#, can
freely mutate captured variables by default; Rust's own closures (this
whole curriculum's own Phase 12, still many phases ahead), where the
choice is made explicit and enforced by the type system itself — a
closure is either `Fn` (read-only capture), `FnMut` (mutable capture),
or `FnOnce`, decided by what the closure's own body actually does
```

### SE Lens

The principle is **whether a language trusts closures to safely mutate
shared state, or refuses to compile a program that tries**. JavaScript
and C# both trust the author; Java refuses outright, at compile time,
before the mistake this refusal is designed to prevent (a lambda
silently capturing a *stale* copy of a variable that's since changed, or
several lambdas racing to mutate the same one unpredictably) can ever
happen at all. The real, concrete cost of Java's own stricter real rule:
Lesson 6.6's own real design — one shared `let` variable, mutated by
every closure that needs it — has no direct real equivalent in Java at
all; a real Java program needing the identical real capability has to
reach for an explicit, boxed, mutable holder (a single-element array, or
a dedicated small class with one field) specifically to work around the
effectively-final rule, real, extra ceremony neither JavaScript nor C#
ever requires for this exact real situation.

This lesson's own real, six-axis comparison, gathered in one place:
JavaScript's own **dynamic typing** catches nothing before a program
runs, proven this session by a real function happily rendering
`"banana minutes"`; C#'s and Java's own **static typing** catches an
entire real class of the identical mistake before either project's own
binary exists at all. JavaScript's own **objects** need no class at all
— `selection` exists the instant its own literal is parsed; C#'s and
Java's own objects always require one, real, separately-declared
blueprint first. JavaScript's own **functions** can stand entirely
alone, belonging to nothing; every real C# and Java method this whole
curriculum has ever written belongs to some class, with no exception.
JavaScript's own **closures** can freely mutate what they capture, the
identical real capability C#'s own closures share and Java's own real,
compiler-enforced "effectively final" rule explicitly forbids.
JavaScript's own **modules** bind directly to real files, by path; C#'s
and Java's own namespaces and packages are a real, separate, looser
grouping. And JavaScript's own **async model** shares C#'s own real
`async`/`await` syntax while running, underneath, on a single real
thread that C#'s own genuinely multi-threaded `Task` model was never
bound to at all.

This is the milestone this whole phase set out to reach: not the
ability to recite what `async` or `this` mean in JavaScript in
isolation, but the ability to read a real, working browser application,
built entirely without a framework, and explain, correctly, exactly
where its own language's real assumptions — dynamic typing, class-free
objects, mutable closures, file-bound modules, single-threaded
concurrency — genuinely diverge from the two statically-typed, managed
languages this whole curriculum already spent its first two phases
building. Phase 7 adds a real, compile-time type system directly on top
of this exact same project, closing the one gap this lesson's own first
Concept Unit proved, this session, was never actually closed at all.
