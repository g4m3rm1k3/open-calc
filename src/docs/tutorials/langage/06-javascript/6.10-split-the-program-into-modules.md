## Terms used in this lesson

- **ES module** — a real JavaScript file treated as its own, separate
  scope, whose own top-level declarations are private to it unless
  explicitly shared. Per MDN's own documentation, fetched and quoted
  this session, "module features are imported into the scope of a
  single script — they aren't available in the global scope." Every
  JavaScript file this project has written before this lesson —
  `app.js` alone — has been an ordinary, "classic" script instead,
  where every top-level `const`, `let`, and `function` effectively
  shares one common scope with the whole page.
- **Module boundary** — the real, explicit line between what one module
  shares with the rest of a program and what stays entirely private to
  it. `data.js`'s own real boundary, after this lesson, shares exactly
  one thing — `fetchEntries` — and nothing else.

## Objects and methods used

- **`export` (declaration)**
  *What it is:* a real JavaScript keyword marking a top-level
  declaration as visible to other modules.
  *Implementation:* per MDN's own documentation, fetched and quoted this
  session, "the `export` declaration is used to export values from a
  JavaScript module," and "exported values can then be imported into
  other programs with the `import` declaration."
  *Its use:* this lesson's own real code places it directly before
  `async function fetchEntries()`, in `data.js`, making that one real
  function — and, deliberately, nothing else in that file — available
  to be imported elsewhere.
  - *Type:* a real declaration modifier, not a function or method call.
  - *Responsibility:* mark exactly the declaration it's attached to as
    part of the module's own real, public surface.
  - *Depends on:* being written directly before a real top-level
    declaration, inside a file loaded as a real module.
  - *Connects to:* read by whatever `import` statement, elsewhere,
    names the identical real export.
  - *Shape:* the real, explicit, opt-in half of this lesson's own
    module boundary — nothing in `data.js` is shared unless it's marked
    this way.

- **`import` (declaration)**
  *What it is:* a real JavaScript keyword that brings a named export
  from another module into the current one.
  *Implementation:* per MDN's own documentation, fetched and quoted this
  session, "the static `import` declaration is used to import read-only
  live bindings which are exported by another module."
  *Its use:* this lesson's own real code places `import { fetchEntries }
  from "./data.js";` at the very top of `app.js`, the first real line
  of the entire file.
  - *Type:* a real declaration, always processed before any other code
    in the same real file runs, regardless of where it's physically
    written.
  - *Responsibility:* bind a real, named export from another module to
    a local name in the importing module — here, the identical real
    name, `fetchEntries`, though a real, different local name could have
    been chosen instead.
  - *Depends on:* a real path to the module being imported from, and a
    real, matching export name that module actually provides.
  - *Connects to:* names `data.js`'s own real `fetchEntries` export;
    `app.js`'s own real `loadEntries` function is what actually calls
    the resulting binding.
  - *Shape:* the real, receiving half of this lesson's own module
    boundary — `export` offers; `import` is what actually reaches
    across and takes it.
