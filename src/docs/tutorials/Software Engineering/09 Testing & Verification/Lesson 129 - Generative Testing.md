# Lesson 129: Generative Testing

**What you will build.** Lesson 128's own property test generates
`threshold` and `target` completely independently, then uses
`assume(target > threshold)` to throw away every generated pair that
doesn't happen to satisfy it. This lesson replaces that with a
different technique: a strategy that generates a `threshold` and a
strictly positive `gap`, then *constructs* `target` as `threshold +
gap` — guaranteeing `target > threshold` for every single value it
ever produces, with nothing left to discard. To prove the difference is
real, not stylistic, a throwaway example first pushes `assume()`
hard enough to trigger a genuine `hypothesis` failure — not a found
bug, but the library itself refusing to keep testing because too many
generated inputs are being thrown away — then shows the identical,
demanding constraint working perfectly with a constructed strategy
instead. The transferable problem this lesson names: Lesson 128 chose
*what rule* to check; this lesson chooses *how the inputs are shaped*
in the first place, and the difference has a real, measurable cost.

**What you need to know first.** Lesson 128 (Property-Based Testing) —
`@given`, `hypothesis.strategies`, and `assume()`, all reused and
directly contrasted against here. This lesson also reuses `reorder_
suggestion`'s own real precondition, `target > threshold`, established
in Lesson 119 and moved into `reorder_suggestion` itself in Lesson 128.

**Terms used in this lesson.**

- **Generative testing** — testing where the shape of the *generator*
  itself is deliberately engineered so that every value it produces is
  already valid, rather than generating broadly and discarding invalid
  attempts. Why it's distinct from Lesson 128's own property-based
  testing: Lesson 128 stated a rule and let `hypothesis` generate
  inputs freely, filtering afterward with `assume()`; this lesson
  designs the generator so there's nothing left to filter.
- **Filtering** (revisited from Lesson 128's own `assume()`) — discarding
  a generated input that doesn't satisfy some condition, and trying
  again. Why it has a real cost, proven directly in this lesson: every
  discarded attempt is wasted work, and if too high a fraction of
  generated inputs get thrown away, `hypothesis` itself treats that as
  a real problem worth stopping over, not a quiet inefficiency.

**Objects and methods used.**

- **`strategy.map(function)`**
  - *What it is:* a method available on every `hypothesis` strategy
    object.
  - *Implementation:* `some_strategy.map(function)` returns a new
    strategy: whenever the original `some_strategy` would have produced
    a value, `function` is applied to it first, and the *result* is what
    actually gets used. The new strategy only ever produces values
    `function` can return — never anything `function` wasn't given the
    chance to transform.
  - *Its use:* turns a strategy that generates `(threshold, gap)` pairs
    into one that generates `(threshold, threshold + gap)` pairs
    instead — guaranteeing the second number is always the larger one.
- **`hypothesis.strategies.tuples()`**
  - *What it is:* a strategy combinator from the `hypothesis.strategies`
    module.
  - *Implementation:* `st.tuples(strategy_a, strategy_b)` returns a new
    strategy producing real Python tuples, `(a, b)`, with `a` generated
    by `strategy_a` and `b` generated by `strategy_b`, independently of
    each other.
  - *Its use:* the starting point this lesson's own `.map()` call
    transforms — an independently generated `(threshold, gap)` pair,
    turned into a guaranteed-valid `(threshold, target)` pair.

## Concept Unit: Generative Testing — Designing the Generator, Not Just the Rule

### The Problem

Lesson 128's own check works, and it's genuinely useful. But look at how
it gets there: `threshold` and `target` are each drawn from `st.
integers(min_value=0, max_value=100)` completely independently, and
`assume(target > threshold)` throws away roughly half of everything
generated — every pair where `target` didn't happen to land above
`threshold`. That waste is mild here, since roughly half of two
independent numbers in the same range still satisfy `>`. What happens
to this same technique if the real requirement being tested for is
narrower — not just "greater than," but "at least 90 higher"?

### Introduce the Concept in Isolation

A small, throwaway, unrelated check — never part of `inventory-report`
— makes the real cost concrete. It reuses Lesson 128's own
`assume()`-based shape, but with a deliberately demanding condition:

```python
from hypothesis import given, assume, strategies as st

@given(
    threshold=st.integers(min_value=0, max_value=100),
    target=st.integers(min_value=0, max_value=100),
)
def check_big_gap(threshold, target):
    assume(target > threshold + 90)
    assert target - threshold > 90

check_big_gap()
print("check_big_gap passed")
```

Run for real:

```text
$ python3 filter_health_check.py
hypothesis.errors.FailedHealthCheck: It looks like this test is filtering out a lot of inputs. 4 inputs were generated successfully, while 50 inputs were filtered out.
```

Not a found bug — `hypothesis` itself refuses to keep testing, because
`assume(target > threshold + 90)` is throwing away the overwhelming
majority of what it generates: two independent numbers, each from `0`
to `100`, landing more than `90` apart from each other by pure chance
is rare. The identical requirement, expressed instead as a **composed
strategy** that builds a valid pair directly:

```python
from hypothesis import given, strategies as st

def combine(threshold_and_gap):
    threshold, gap = threshold_and_gap
    return (threshold, threshold + gap)

big_gap_pairs = st.tuples(
    st.integers(min_value=0, max_value=100),
    st.integers(min_value=91, max_value=200),
).map(combine)

@given(pair=big_gap_pairs)
def check_big_gap_constructive(pair):
    threshold, target = pair
    assert target - threshold > 90

check_big_gap_constructive()
print("check_big_gap_constructive passed")
```

Run for real:

```text
$ python3 constructive_big_gap.py
check_big_gap_constructive passed
```

No filtering, no failure, no wasted attempts — `st.tuples(...)` builds a
`(threshold, gap)` pair, `.map(combine)` transforms every single one
into `(threshold, threshold + gap)` before `hypothesis` ever sees it as
a candidate value, and `gap`'s own range (`91` to `200`) guarantees the
difference is always over `90`. This deliberate shaping of *how values
are generated*, rather than generating broadly and discarding what
doesn't fit, is called **generative testing**.

### Discard the Throwaway Example

`check_big_gap`, `check_big_gap_constructive`, and `combine` are not
part of `inventory-report` and will not appear in it. What survives is
the technique: when a valid input has a real, describable shape,
building a generator around that shape directly is both faster and more
reliable than generating freely and hoping enough valid examples survive
filtering.

```python
from inventory_report import reorder_suggestion

def combine_threshold_and_gap(threshold_and_gap):                                  # ← new
    threshold, gap = threshold_and_gap                                             # ← new
    return (threshold, threshold + gap)                                           # ← new

valid_threshold_target_pairs = st.tuples(                                          # ← new

    st.integers(min_value=1, max_value=100),                                       # ← new

@given(
    inventory=st.dictionaries(
        st.text(alphabet="abcdefghij", min_size=1, max_size=8),
        st.integers(min_value=0, max_value=1000),

    ),

)
def check_reorder_quantities_always_positive(inventory, threshold_target):         # ← changed
    threshold, target = threshold_target                                          # ← changed
    suggestions = reorder_suggestion(inventory, threshold=threshold, target=target)
    for name, qty in suggestions.items():
        assert qty > 0

print("check_reorder_quantities_always_positive passed")
```

### Mechanical Walkthrough

- **`def combine_threshold_and_gap(threshold_and_gap):`** — a plain
  function, the transformation `.map()` will apply to every generated
  value.
- **`threshold, gap = threshold_and_gap`** — tuple unpacking, a
  construct this project has used since Lesson 105 (`for name, count in
  inventory.items():`), here applied to a plain two-element tuple
  instead of a loop variable.
- **`return (threshold, threshold + gap)`** — builds and returns a new
  tuple: the same `threshold`, and a `target` computed directly from it
  — guaranteeing `target > threshold` whenever `gap` is positive, which
  its own strategy, below, guarantees separately.
- **`st.tuples(st.integers(min_value=0, max_value=100),
  st.integers(min_value=1, max_value=100))`** — full treatment of
  `st.tuples()` above: generates `(threshold, gap)` pairs, `threshold`
  from `0` to `100`, `gap` from `1` to `100` — never `0`, so `target`
  can never equal `threshold` either.
- **`.map(combine_threshold_and_gap)`** — full treatment above: applies
  the transformation to every generated `(threshold, gap)` pair,
  producing the final `(threshold, target)` pairs `@given` actually
  hands to the check function.
- **`threshold_target=valid_threshold_target_pairs`** — this strategy
  is now what `@given` uses for a single parameter, `threshold_target`,
  in place of Lesson 128's two separate, independent `threshold` and
  `target` parameters.
- **`threshold, target = threshold_target`** — unpacks the generated
  pair back into two names, immediately inside the check function.

### SE Lens

The alternative — Lesson 128's own `assume()`-based approach — is
simpler to write and easier to read at a glance: state the rule
directly, let `hypothesis` sort it out. That alternative isn't wrong;
it worked, and passed, for this exact property, in this exact lesson's
own predecessor. Its real cost only shows up as the valid domain
narrows — proven directly by this lesson's own `check_big_gap`, which
didn't just run slowly, it refused to run at all. Generative testing's
own cost is real too: `combine_threshold_and_gap` and `st.tuples(...).
map(...)` are more code, and more thinking, than one line of `assume()`
— a cost worth paying specifically when the valid subset of possible
inputs is narrow enough that filtering would waste real effort, and not
worth paying for a property like Lesson 128's own, where roughly half
of everything generated was already valid. The honest lesson underneath
both techniques: `hypothesis` cannot know which shape of generator is
right for a given property — that judgment call belongs to whoever
understands the actual valid domain being tested, the same way choosing
*which* boundary values to test (Lesson 122) required first correctly
identifying that a boundary existed at all.

## What Breaks Without This

This lesson's own isolated `check_big_gap` already showed it directly:
generating inputs broadly and filtering with `assume()` isn't a free
technique — it has a real, hard limit, and `hypothesis` itself enforces
that limit rather than silently tolerating it. Restated plainly: for a
property whose valid inputs make up roughly half of everything that
could be generated, as Lesson 128's own property did, filtering costs
almost nothing. For a property whose valid inputs are a narrow slice of
a much larger space, filtering can cost everything — up to and
including `hypothesis` refusing to run the test at all, rather than
silently testing something narrower and less meaningful than what was
actually asked for.
