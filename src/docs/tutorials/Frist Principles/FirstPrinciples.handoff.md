# First Principles — Handoff

This file is the living status document for the "Computation from First Principles" curriculum. Read this at the start of every new session working on this curriculum, before doing anything else. Update it before ending a session (or ask the user if it's fine to update it before stopping).

It exists specifically so a **new, short session** can pick up this work without needing the prior session's transcript — see the session-hygiene section below for why that matters.

## Why this curriculum exists

This is not curriculum-authoring for its own sake. The user's own framing: these lessons are meant to teach *them* what they need to know so we can build real projects together later.

The specific concern driving this: projects built mostly by agents tend to get big and messy. The point of this curriculum is for the user to become an effective **collaborator and reviewer** on that kind of work — to understand what to ask for, to understand how a codebase should be structured, and to be able to reason about a project without needing an agent to read a giant codebase back to them just to explain what's in it. This is preparation for coordinating on real projects, not an end in itself.

**What this means practically:** every lesson is held to a literal "100% perfect, follows the schema" bar, not an aspirational one. Every code example is genuinely run in Guile and its real output used — never fabricated or estimated. Every derivation has to actually be sound. The user is the one who will internalize this and build on it later.

## Session hygiene — read this every time

The user has flagged real usage-cost concerns from long sessions, from Claude Code's own usage-analytics message (seen more than once, numbers drifting slightly each time — a live snapshot, not a fixed threshold): most usage occurring above 150k tokens of context, a large share from sessions active 8+ hours, and a meaningful share from subagent-heavy sessions.

**The pacing signal is session duration (hours) and context size (tokens) — not lesson count.** This file previously said something like "build a batch of roughly 3–8 lessons per session, then stop" and the user explicitly corrected that: sessions are bounded by *hours* (the analytics flag 8+ hour sessions specifically), not by a quota of output. **Don't stop mid-work to check in or ask permission to continue just because a lesson finished** — the user's direct correction was that pausing to ask "should I keep going?" after each unit of output *adds* session overhead rather than reducing it. Keep following the schema continuously, lesson after lesson, until context genuinely grows large or the session genuinely runs long — that's when `/compact` or a fresh session is the right move, not after some number of lessons.

**Working agreement going forward:**

- **Start new sessions sooner** — triggered by context size and wall-clock time, not by having produced some number of lessons. Don't try to build the whole rest of the curriculum in one sitting, but don't stop-and-ask after every lesson either.
- **`/compact` mid-task** if a session is continuing this same curriculum work and context is growing large.
- **`/clear` when switching to a genuinely different task**, rather than carrying this curriculum's context into unrelated work, or vice versa.
- **Don't spawn subagents for this work.** Building a lesson requires real, verified Guile output and careful cross-lesson consistency (terms already introduced, numbers already established) — that context needs to live in the main session, not be re-derived cold by a subagent. Direct Bash + Write has been the right tool for every lesson so far; keep doing that.
- **No separate review/audit passes** over already-completed lessons — this was explicitly declined by the user once already. Get each lesson right the first time (see "How a lesson gets built" below); if an error is spotted incidentally while working nearby, fix it immediately, but don't schedule a dedicated sweep.
- **A genuine content-planning fork (like Lesson 73's BRD/Repetition-Rule conflict) is worth raising with the user when it comes up** — that's different from stopping between lessons to ask whether to proceed at all.

**A reasonable session shape:** read this file, read `LESSON SCHEMA.md` if it's been a while, then keep building lessons in sequence without pausing between them, watching context size, until it's genuinely time for `/compact` or a new session — at that point update this file's "Where we are" and "Session log" sections.

## How a lesson gets built (quick orientation for a fresh session)

1. Read `src/docs/reference/LESSON SCHEMA.md` if it's been a while — every lesson must follow it exactly (header, Concept Units each with Problem → isolated lab or justified skip → New Code → Updated Project shown in full → Mechanical Walkthrough → CS Lens → SE Lens → Run It, then Closing with exercises and a definition-of-done checklist).
2. Check the BRD (`FirstPrinciples.brd.md`) for the next lesson's title and one-line description.
3. Before writing prose, work out the lesson's real content in Guile first: use the scratchpad (`/tmp/scheme-testNN/` or similar, cleaned up with `rm -rf` when done) to derive, run, and verify every number that will appear in the lesson. Never estimate or fabricate output.
4. Check whether any procedure or term the lesson needs has already been introduced elsewhere, with `grep -ln` over existing `FP-L0*.md` files for the relevant backtick-quoted name, before deciding whether it needs a fresh "Objects and methods used" entry or an isolated Concept Isolation Rule lab. (See "Ideas for improving the process" below — a maintained index would remove the need to grep every time.)
5. Prefer connecting new lessons back to real evidence already established in earlier lessons over inventing fresh, disconnected examples — this has been one of the strongest patterns in the curriculum so far (see below).
6. Write the lesson file directly with Write, following the schema exactly.
7. Clean up scratch files. Do not leave temp `.scm` files around.
8. Update this handoff file's "Where we are" section.

## Patterns that have worked well — keep doing these

- **Connecting lessons to real prior evidence, not just new examples.** The strongest lessons in Era III (65 → 51's `2047`, 67 → 66's call counts, 68 → 67's `halving-count`, 69 pulling together six lessons' worth of real numbers, 71/72 → the same `f(n)` function reused across two lessons) work because a new formula or notation gets checked against something the curriculum already independently measured, not just a fresh, disconnected test case. Keep looking for these connections deliberately.
- **Multi-lesson arcs planned implicitly by momentum.** Lessons 64 through 72 built on each other as a real narrative (series → exponents → logs → growth rates → asymptotic scope → Big-O → Big-Theta), each one's "what's still unexplained" becoming the next one's problem statement. Worth doing this *deliberately* at the start of an Era or sub-arc — sketch the throughline for the next several lessons before writing the first one — rather than only discovering it lesson-by-lesson.
- **Honest, non-overclaiming treatment of imperfect data.** Several lessons (60's non-exact memory ratio, 65's `r = 1` edge case, 67's `fast-expt`-vs-`halving-count` gap, 69's timing noise) explicitly explained *why* a measurement didn't match a clean prediction exactly, rather than hiding or smoothing over it. This is a real strength of the curriculum's credibility — keep doing it rather than picking cleaner-but-less-honest numbers.
- **The doubling-ratio / real-crossover-point technique** introduced in Lessons 69–70 (measure at `n` and `2n`, read the ratio; find where two algorithms' real costs actually cross) is a genuinely reusable diagnostic — worth reaching for again in later Eras rather than treating it as scoped only to those two lessons.

## Ideas for improving the process going forward

- **A maintained Terms & Objects index.** Right now, checking whether `cond`, `even?`, `apply`, etc. have already been introduced means grepping every existing lesson file each time. A single running index file (term/procedure → lesson it was introduced in) would be faster, cheaper, and less error-prone than re-deriving this by search every lesson — worth creating once and updating each session rather than continuing the per-lesson grep pattern indefinitely.
- **A short "verified facts ledger."** Numbers like `fib(30) = 832040`, `2,692,537` calls, `2047 = 2¹¹ − 1`, etc. get reused across lessons repeatedly. A lightweight running table of "real number → what it means → which lesson established it" would make reuse faster and reduce the risk of two lessons citing slightly inconsistent versions of the same fact.
- **Sketch an Era's lesson-to-lesson arc before writing the first lesson in it**, the way Lessons 64–72 worked out in practice. Doesn't need to be formal — a few sentences of "lesson N sets up lesson N+1's problem" is enough — but doing it up front instead of discovering it organically would make the connections even tighter and reduce the chance of a missed opportunity to link two lessons.
- These are suggestions, not commitments — raise them with the user before changing the actual workflow, since the schema and no-review-passes rules are explicit, deliberate constraints from the user, not just default habits.
- **A real, recurring gap caught and fixed in Lessons 78–82 (see [[feedback-first-principles-show-instrumented-code]]):** when a Concept Unit's "Run It" reports real numbers gathered by adding a `set!` counter on top of an already-derived plain procedure, the counting code itself has to be shown in the lesson, not just verified in a scratchpad and left out because the plain version was the Concept Unit's own conceptual focus. Check this specifically before calling any future lesson done: does every numeric claim in a Run It block have a visible code block right above it that could actually produce that number?
