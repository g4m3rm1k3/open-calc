## Concept: Data-Driven Rendering

**What it is:** The visual output is generated by reading data, not by a
sequence of hardcoded drawing calls.

**The problem before (hardcoded drawing):**
```js
// Drawing every wall individually — 100+ lines, impossible to change:
ctx.fillRect(0,   0,  16, 16);  // top-left corner wall
ctx.fillRect(16,  0,  16, 16);  // next wall
ctx.fillRect(32,  0,  16, 16);  // next...
// ...hundreds more
```

**The solution:** Store what the maze looks like as numbers. Write ONE drawing
function that reads the numbers and draws accordingly.

**Canonical example — a text renderer:** A word processor doesn't hardcode where
every letter appears. It stores the text as characters and renders each one
from a font atlas. Change the text (data), the rendering updates automatically.
Same function, different output.

```js
// The render loop reads the data — one function handles all tiles:
for (let row = 0; row < MAZE_ROWS; row++) {
  for (let column = 0; column < MAZE_COLUMNS; column++) {
    if (maze[row][column] === 1) {
      drawWallAt(column, row);
    }
  }
}
```

**Why it matters here:** The maze data defines the game world. To change the
maze, change the array — the drawing function doesn't change at all.

**Watch for:** This pattern (data → render) is the foundation of every game
engine, CAD tool, and UI framework. In React, component state is the data.
The render function reads it. Same pattern, different domain.

## Concept: Nested `for` Loops for Grid Traversal

**What it is:** Two `for` loops, one inside the other, to visit every cell
in a 2D grid — all rows, and within each row, all columns.

**Canonical example — reading a book:** You read left to right across one line
(inner loop: columns). At the end of each line, you move to the next line
(outer loop: rows). You read every word by combining both loops.

```js
// Outer loop: one iteration per row (Y direction — top to bottom)
for (let row = 0; row < MAZE_ROWS; row++) {

  // Inner loop: one iteration per column (X direction — left to right)
  for (let column = 0; column < MAZE_COLUMNS; column++) {

    // Access the cell at this row and column:
    const cellValue = maze[row][column];

    // Draw the tile at its pixel position:
    const pixelX = column * TILE_SIZE;   // column → pixel X
    const pixelY = row    * TILE_SIZE;   // row → pixel Y
  }
}
```

**Why it matters here:** Every frame, the maze rendering loop visits all
28×31 = 868 tiles. For each wall tile, it draws a rectangle. This is 868
array reads and up to 868 `fillRect` calls per frame — all in one nested loop.

**Watch for:** The outer variable is `row` (Y) and inner is `column` (X). If
you swap them (`maze[column][row]`), you index the wrong dimension and the
maze appears transposed or crashes.

## Step 2 — Draw the Maze

Add the `drawMaze` function and call it from `render`:

```js
// ── Maze colors ────────────────────────────────────────────────────────────────

const COLOR_WALL = '#1a1aff';   // classic Pac-Man blue walls
const COLOR_PATH = '#000000';   // black paths

// drawMaze: renders every tile in the maze array.
// For each wall tile: draws a blue rectangle.
// Path tiles: already covered by the black canvas background — no drawing needed.
function drawMaze() {
  for (let row = 0; row < MAZE_ROWS; row++) {
    for (let column = 0; column < MAZE_COLUMNS; column++) {

      if (maze[row][column] === TILE_WALL) {
        // Convert tile coordinates to pixel coordinates for drawing.
        // Note: no TILE_SIZE/2 offset — we want the TOP-LEFT corner, not the center.
        const pixelX = column * TILE_SIZE;
        const pixelY = row    * TILE_SIZE;

        ctx.fillStyle = COLOR_WALL;
        ctx.fillRect(pixelX, pixelY, TILE_SIZE, TILE_SIZE);
      }
      // Paths, dots, and power pellets are handled in later labs.
    }
  }
}
```

Update `render()` — replace `drawGrid()` with `drawMaze()`:

```js
function render() {
  ctx.fillStyle = COLOR_PATH;
  ctx.fillRect(0, 0, CANVAS_WIDTH, CANVAS_HEIGHT);

  drawMaze();   // ← replaces drawGrid()
  // drawPlayerTileHighlight() can stay or be removed — your choice

  ctx.fillStyle = PLAYER_COLOR;
  ctx.fillRect(playerX, playerY, PLAYER_SIZE, PLAYER_SIZE);
}
```

searching, modifying. Learning one loop teaches all uses.

## Quick Check Answers

**1. Why store the maze as an array instead of hardcoded drawing calls?**
Because data and code are separated. Changing the maze means editing numbers
in an array, not hunting through hundreds of drawing commands. The `drawMaze`
function never changes — only the data changes. This is called data-driven
design and it is foundational to every game engine and UI framework.

**2. How do you draw all walls from `maze[row][column] === 1`?**
Nested loop: outer loop over rows, inner loop over columns. At each cell,
check if the value equals `TILE_WALL`. If yes, call `fillRect` at the
corresponding pixel position: `column * TILE_SIZE`, `row * TILE_SIZE`.

**3. 28 columns × 31 rows — how many tiles? How many `fillRect` calls?**
868 total tiles. Up to 868 `fillRect` calls — one per wall tile. In practice,
roughly 300–350 walls, so about that many `fillRect` calls per frame.
This is fast because `fillRect` is a GPU-accelerated canvas operation.
