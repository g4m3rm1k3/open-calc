# Frontend Client — Lesson 09 — Authentication

## What You Will Build

A real registration and login form. Submitting it sends real credentials to Conduit
and gets back a real **JWT** — a token proving who you are — which is stored so it
survives a page reload. A nav bar shows "Log In" / "Register" when logged out, or
"Log Out" when logged in. And the like button lesson 08 deliberately left broken now
works: clicking it, while logged in, really favorites the article on the server.

## Concept: What a JWT Actually Is

**Authentication** answers "who are you?" A **session** is the period during which a
server remembers the answer across multiple requests, since HTTP itself is
**stateless** — each request is handled with no memory of any previous one, unless
something is deliberately added to bridge them.

A **JWT** (JSON Web Token, pronounced "jot") is one common way to bridge that gap
without the server keeping a database of active sessions. It is a string with three
parts, separated by dots: a header, a payload (containing claims like the user's ID
and when the token expires), and a signature. The **signature** is generated by the
server using a secret key only it knows — anyone can *read* a JWT's payload (it is
only encoded, not encrypted), but nobody except the server can *forge* a valid
signature for a payload they invented. This is what makes it trustworthy: the client
carries the token and presents it with every request; the server verifies the
signature and, if it matches, trusts the claims inside without needing to look
anything up.

When you register or log in, Conduit issues you a JWT. From that point on, every
request that needs to know who you are must include it — Conduit will not remember
you between requests on its own.

## Step 1 — Add User Types and Auth Endpoints to `api.ts`

**The problem:** Registration and login are two new endpoints, both returning the
same shape: a user, including their token.

Add to `src/api.ts`:

```typescript
export interface User {
  email: string;
  username: string;
  bio: string | null;
  image: string | null;
  token: string;
}

interface UserResponse {
  user: User;
}

function formatApiErrors(errors: Record<string, string[]>): string {
  return Object.entries(errors)
    .map(([field, messages]) => `${field} ${messages.join(", ")}`)
    .join("; ");
}

export async function registerUser(username: string, email: string, password: string): Promise<User> {
  const response = await fetch(`${API_BASE_URL}/users`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ user: { username, email, password } }),
  });

  const data = await response.json();
  if (!response.ok) {
    throw new Error(formatApiErrors(data.errors));
  }
  return (data as UserResponse).user;
}

export async function loginUser(email: string, password: string): Promise<User> {
  const response = await fetch(`${API_BASE_URL}/users/login`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify({ user: { email, password } }),
  });

  const data = await response.json();
  if (!response.ok) {
    throw new Error(formatApiErrors(data.errors));
  }
  return (data as UserResponse).user;
}
```

**Walkthrough:** This is the first request in this project with a **request body** —
data sent *to* the server, not just parameters in the URL. `headers: { "Content-Type":
"application/json" }` tells the server "the body of this request is JSON text,
please parse it that way" — without it, a server may not know how to interpret the
raw bytes it received. `body: JSON.stringify({ user: { username, email, password } })`
converts a real JavaScript object into a JSON string — `JSON.stringify` is the exact
inverse of `response.json()` (which parses JSON text into a JavaScript value):
`stringify` goes object → text; `.json()` goes text → object. Conduit expects the
whole payload nested one level under a `"user"` key — `{ "user": { "username": ...,
... } }` — a convention specific to this API, worth checking against the docs at
`/redoc` for any new API you integrate with.

Notice `response.json()` is now called *before* checking `response.ok`. This is
deliberate: on failure, the response body still contains useful JSON — the `errors`
object from lesson 08 — and this project wants to read and display it, not discard
it. `formatApiErrors` turns `{ credentials: ["invalid"] }` into the readable string
`"credentials invalid"`. `Object.entries(errors)` converts an object into an array
of `[key, value]` pairs — `[["credentials", ["invalid"]]]` here — so `.map()` can
process each field. `([field, messages]) => ...` destructures each pair directly in
the parameter list. `messages.join(", ")` combines an array of strings into one,
separated by the given string.

**Why `Record<string, string[]>` for `errors`:** This is a TypeScript **utility
type** — `Record<K, V>` describes an object whose keys are all of type `K` and whose
values are all of type `V`. Here: any string key, each mapping to an array of
strings — exactly Conduit's real error shape from lesson 08's `{"errors":
{"credentials": ["invalid"]}}`.

## Step 2 — Store the Token

**The problem:** A token that disappears the moment the page reloads is useless for
a real session. It needs to persist.

Create `src/auth.ts`:

```typescript
const TOKEN_STORAGE_KEY = "conduit_token";

export function getToken(): string | null {
  return localStorage.getItem(TOKEN_STORAGE_KEY);
}

export function setToken(token: string): void {
  localStorage.setItem(TOKEN_STORAGE_KEY, token);
}

export function clearToken(): void {
  localStorage.removeItem(TOKEN_STORAGE_KEY);
}

export function isLoggedIn(): boolean {
  return getToken() !== null;
}
```

**Walkthrough:** `localStorage` is a browser API providing a simple key-value store,
scoped to the page's origin, that persists even after the browser is closed and
reopened — unlike an ordinary variable, which exists only in memory and is lost the
instant the page reloads. It only stores strings; a JWT is already a string, so no
conversion is needed here (storing an object would require `JSON.stringify` going in
and `JSON.parse` coming back out).

**Security lens — the real trade-off of `localStorage` for tokens.** Any JavaScript
running on this page — including, if the XSS protection from lesson 02 ever failed,
an attacker's injected script — can read anything in `localStorage`. A more
XSS-resistant alternative used in some production systems is an `httpOnly` cookie, a
cookie flagged so that *no* JavaScript can read it at all, only the browser itself,
which attaches it to requests automatically. That approach requires server-side
support Conduit's public API does not offer, so this project uses `localStorage`, the
same approach the official RealWorld reference frontends use — a reasonable,
widely-used choice, with this specific limitation worth knowing rather than assuming
away.

## Step 3 — Attach the Token to Authenticated Requests

**The problem:** Having a stored token does nothing until requests actually send it.

Add to `src/api.ts`, and update `toggleFavorite`:

```typescript
import { getToken } from "./auth.ts";

function authHeaders(): Record<string, string> {
  const token = getToken();
  return token ? { Authorization: `Token ${token}` } : {};
}

export async function toggleFavorite(slug: string, isFavorited: boolean): Promise<Article> {
  const method = isFavorited ? "DELETE" : "POST";

  const response = await fetch(`${API_BASE_URL}/articles/${slug}/favorite`, {
    method,
    headers: authHeaders(),
  });

  if (!response.ok) {
    throw new Error(`Request failed with status ${response.status}`);
  }

  const data: FavoriteResponse = await response.json();
  return data.article;
}
```

**Walkthrough:** `Authorization` is a standard HTTP header for exactly this purpose —
telling the server who is making the request. Its value has a **scheme** (a keyword
naming the kind of credential that follows) and the credential itself. Many APIs use
the scheme `Bearer`; Conduit specifically uses the scheme `Token` — `` `Token
${token}` ``. This is not a universal standard, only a convention each API chooses;
always check an API's documentation for its exact expected scheme rather than
assuming `Bearer` everywhere.

`authHeaders()` returns an empty object `{}` when there is no token, rather than,
say, `{ Authorization: "Token null" }` — spreading an empty object into a request's
headers simply adds nothing, which correctly reproduces lesson 08's original
unauthenticated behaviour for a signed-out visitor, while adding the real header the
moment a token exists.

Favorite the article now, while logged in (once Step 4 below exists) — it will
actually work. The 401 lesson 08 built is not being deleted; it is what still
happens for anyone not logged in, exactly as it should.

## Step 4 — Build the Auth Form

**The problem:** Nothing on the page can call `registerUser` or `loginUser` yet.

Create `src/components/AuthForm.ts`:

```typescript
import { loginUser, registerUser, type User } from "../api.ts";

export function createAuthForm(mode: "login" | "register", onSuccess: (user: User) => void): HTMLElement {
  const form = document.createElement("form");

  const usernameInput = document.createElement("input");
  usernameInput.type = "text";
  usernameInput.placeholder = "Username";

  const emailInput = document.createElement("input");
  emailInput.type = "email";
  emailInput.placeholder = "Email";

  const passwordInput = document.createElement("input");
  passwordInput.type = "password";
  passwordInput.placeholder = "Password";

  const errorMessage = document.createElement("p");
  errorMessage.className = "error-message";

  const submitButton = document.createElement("button");
  submitButton.type = "submit";
  submitButton.textContent = mode === "login" ? "Log In" : "Register";

  if (mode === "register") {
    form.appendChild(usernameInput);
  }
  form.appendChild(emailInput);
  form.appendChild(passwordInput);
  form.appendChild(errorMessage);
  form.appendChild(submitButton);

  form.addEventListener("submit", async (event) => {
    event.preventDefault();
    errorMessage.textContent = "";

    try {
      const user = mode === "login"
        ? await loginUser(emailInput.value, passwordInput.value)
        : await registerUser(usernameInput.value, emailInput.value, passwordInput.value);
      onSuccess(user);
    } catch (error) {
      errorMessage.textContent = error instanceof Error ? error.message : "Something went wrong.";
    }
  });

  return form;
}
```

**Walkthrough:** `input.type = "password"` renders the field's characters masked
(`••••••`) — a browser-provided behaviour, not something this project implements
itself. `form.addEventListener("submit", ...)` listens for the form's **submit
event**, which fires when the submit button is clicked or Enter is pressed inside the
form.

**`event.preventDefault()` — the single most important line in this function.** A
`<form>`'s default behaviour, the moment it is submitted, is to navigate the browser
to the URL in its `action` attribute (or the current page, if none is set), sending
all its fields along — a full page reload. In a single-page application, that default
behaviour would destroy everything this project has built: the router, the loaded
JavaScript, all in-memory state, gone, replaced by a fresh page load. `preventDefault()`
stops exactly that default action from happening, while still letting your own
`submit` event handler run normally. Every form in this project, from here on, needs
this line — it is not optional.

`mode === "login" ? await loginUser(...) : await registerUser(...)` picks which API
call to make based on which mode this form instance was created for — the same
ternary pattern from lesson 08, now choosing between two async function calls instead
of two HTTP methods.

**CS lens — narrowing `unknown` in a `catch` block.** In TypeScript's `strict` mode
(enabled since lesson 01's `tsconfig.json`), a variable caught in a `catch` block has
the type `unknown` — deliberately not `Error`, `string`, or anything else, because
JavaScript allows `throw`ing literally any value, not just `Error` objects.
`error instanceof Error` is a **type guard**: a runtime check whose result
TypeScript uses to narrow the type inside the branch where it is true — inside the
`?` branch of the ternary, `error` is known to be an `Error`, so reading `.message`
compiles; outside it, TypeScript would not have allowed that access at all, because
`unknown` permits no operations until its actual type has been confirmed.

`onSuccess(user)` is a **callback function** passed in by whatever creates this form
— `createAuthForm` does not know or decide what happens after a successful login; it
only knows how to *attempt* one and report the result. This is the same discipline
behind every component built so far: know your one job, let the caller decide what
happens next.

## Step 5 — Wire Up Auth Routes and the Nav Bar

**The problem:** `#/login` and `#/register` need to map to real pages, and the rest
of the page needs to visibly reflect whether someone is logged in.

Update `index.html`:

```html
<body>
  <h1>Frontend Client</h1>
  <nav id="nav-bar"></nav>
  <div id="app">Loading…</div>
  <script type="module" src="/src/main.ts"></script>
</body>
```

Update `src/main.ts`:

```typescript
import { fetchArticles, fetchArticleBySlug, fetchCommentsBySlug } from "./api.ts";
import { createArticleElement } from "./components/ArticleCard.ts";
import { createCommentList } from "./components/CommentList.ts";
import { createAuthForm } from "./components/AuthForm.ts";
import { isLoggedIn, setToken, clearToken } from "./auth.ts";

type Route =
  | { name: "list" }
  | { name: "detail"; slug: string }
  | { name: "login" }
  | { name: "register" };

const DETAIL_ROUTE_PREFIX = "#/articles/";

function parseRoute(hash: string): Route {
  if (hash === "#/login") return { name: "login" };
  if (hash === "#/register") return { name: "register" };
  if (hash.startsWith(DETAIL_ROUTE_PREFIX)) {
    return { name: "detail", slug: hash.slice(DETAIL_ROUTE_PREFIX.length) };
  }
  return { name: "list" };
}

function renderNavBar(): void {
  const navElement = document.getElementById("nav-bar");
  if (!navElement) return;

  navElement.textContent = "";

  if (isLoggedIn()) {
    const logoutButton = document.createElement("button");
    logoutButton.textContent = "Log Out";
    logoutButton.addEventListener("click", () => {
      clearToken();
      renderNavBar();
      location.hash = "#/";
    });
    navElement.appendChild(logoutButton);
  } else {
    const loginLink = document.createElement("a");
    loginLink.href = "#/login";
    loginLink.textContent = "Log In";

    const registerLink = document.createElement("a");
    registerLink.href = "#/register";
    registerLink.textContent = "Register";

    navElement.appendChild(loginLink);
    navElement.appendChild(registerLink);
  }
}

function renderAuthPage(appElement: HTMLElement, mode: "login" | "register"): void {
  appElement.textContent = "";
  appElement.appendChild(
    createAuthForm(mode, (user) => {
      setToken(user.token);
      renderNavBar();
      location.hash = "#/";
    }),
  );
}

// ... renderArticleListPage and renderArticleDetailPage unchanged from lesson 07 ...

async function renderRoute(): Promise<void> {
  const appElement = document.getElementById("app");
  if (!appElement) return;

  const route = parseRoute(location.hash);

  if (route.name === "detail") {
    await renderArticleDetailPage(appElement, route.slug);
  } else if (route.name === "login" || route.name === "register") {
    renderAuthPage(appElement, route.name);
  } else {
    await renderArticleListPage(appElement);
  }
}

window.addEventListener("hashchange", renderRoute);
renderNavBar();
renderRoute();
```

Save and reload. Register a real account (any username, email, and password — this
is a real account on a public demo server; do not use a real password you use
elsewhere). You are redirected to the article list, the nav bar now shows "Log Out,"
and clicking a heart button now actually favorites the article — reload the page and
the favorited state and updated count persist, because they are real, stored on
Conduit's server.

**Walkthrough:** `route.name === "login" || route.name === "register"` checks two
possibilities in one condition using `||` (logical OR) — true if either side is true.
TypeScript narrows `route.name` to exactly `"login" | "register"` inside this branch,
matching what `renderAuthPage`'s `mode` parameter expects, with no cast needed. The
callback passed to `createAuthForm` — `(user) => { setToken(user.token); ...
}` — is where this project decides what "successful login" actually *does*:
store the token, refresh the nav bar so it reflects the new state immediately, and
navigate to the article list. `createAuthForm` itself never needed to know any of
that.

## What Breaks Without This

**Without `event.preventDefault()` in `AuthForm.ts`:** Submitting the form triggers
a real, full-page navigation — the browser reloads, `localStorage`'s newly-set token
survives (it is disk-backed), but every other piece of in-memory application state is
destroyed and rebuilt from scratch. On a small project like this it can look like it
"worked" by accident; on a form with any unsaved client-side state, this would
silently discard it.

**Without `authHeaders()` in `toggleFavorite`:** Favoriting continues to fail with
the exact same `401` from lesson 08 even while logged in — a real, easy-to-make bug:
the token exists in `localStorage`, but nothing is reading it into the request, so
from the server's point of view nothing has changed since lesson 08 at all.
