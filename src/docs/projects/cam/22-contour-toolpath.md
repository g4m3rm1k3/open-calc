# CAD/CAM — Lesson 22 — Contour Toolpath

## What You Will Build

Select a closed sketch, choose a tool, and click "Generate Contour." A contour
toolpath appears in the viewport: a rapid move to the clearance height above the
start point, a plunge to the cut depth, a cut along every edge of the offset polygon
(from lesson 21), and a retract to clearance. The toolpath is displayed as a
simulated `ToolpathSegment[]` — the same type the simulator in lesson 19 renders.
A "Copy G-code" button appears below the viewport showing the generated G-code text.

## What You Need to Know First

Lessons 01–21. Lesson 18 defined `ParsedBlock`. Lesson 19 defined `ToolpathSegment`
and `simulateToolpath`. Lesson 20 defined `CuttingTool` and `toolRadius`. Lesson 21
defined `offsetPolygon` and `Vec2`. All four are combined here into the first complete
CAM operation: geometry → offset → G-code blocks → toolpath visualisation.

---

## The Problem

The offset polygon from lesson 21 describes where the tool centre must travel —
but it says nothing about depth, feed rate, approach, or retract. A CNC program
cannot just list XY positions. The full machining sequence for a contour is:

1. **Retract** — raise the tool to a safe clearance height (G0 Z[clearance])
2. **Position** — rapid the tool over the start point in XY (G0 X Y)
3. **Plunge** — feed the tool down to the cut depth (G1 Z[depth] F[plunge feed])
4. **Cut** — follow the offset polygon at the cut feed rate (G1 X Y F[cut feed])
5. **Close** — return to the start point to complete the closed loop
6. **Retract** — raise the tool back to clearance (G0 Z[clearance])

This lesson generates G-code text for all six stages, then pipes it through the
parser from lesson 18 and the simulator from lesson 19 to produce a `ToolpathSegment[]`
for the renderer. The architecture enforces dialect independence: the CAM engine
generates G-code text; the parser and simulator visualise it — the same way a real
CNC post-processor and machine controller are decoupled.

## Step 1 — Contour Parameters

### The problem

The contour operation needs parameters beyond the tool: cut depth, clearance height,
cut feed rate, plunge feed rate. These belong in a typed interface.

### Create `src/cam/contourOperation.ts`

```typescript
import type { Vec2 }        from './vec2.js'
import type { CuttingTool } from '../tools/tool.js'
import { toolRadius }        from '../tools/tool.js'
import { offsetPolygon }     from './polygonOffset.js'

export interface ContourParameters {
  vertices:       Vec2[]
  tool:           CuttingTool
  depthOfCut:     number
  clearanceHeight: number
  cutFeedRate:    number
  plungeFeedRate: number
}
```

**`ContourParameters` — why a dedicated type:**
The contour generator needs six inputs. Passing six separate function arguments would
work, but becomes unreadable at the call site: `generateContour(vertices, tool, -3,
5, 500, 150)` — which number is depth? Which is clearance? A dedicated parameter
type makes the call site self-documenting and allows the parameters to be constructed,
stored, and passed as a single unit.

**`depthOfCut: number` — convention for sign:**
By convention, depth values in G-code are negative when cutting below the work surface.
`depthOfCut = -3` means "3mm below the surface at Z=0." This follows the physical
reality of a vertical milling machine: the cutter moves in the negative Z direction
to enter the material.

## Step 2 — G-code Text Generation

### The problem

We need to convert `ContourParameters` into a valid G-code program string. G-code
generation is the **inverse of parsing**: where parsing extracts structure from text,
generation produces text from structure.

```typescript
export function generateContourGcode(params: ContourParameters): string {
  const { vertices, tool, depthOfCut, clearanceHeight, cutFeedRate, plungeFeedRate } = params

  if (vertices.length < 3) {
    throw new Error('Contour requires at least 3 vertices')
  }

  const radius          = toolRadius(tool)
  const offsetVertices  = offsetPolygon(vertices, radius)
  const startVertex     = offsetVertices[0]
  const lines: string[] = []

  function coord(value: number): string {
    return value.toFixed(3)
  }

  lines.push('(Contour toolpath generated by CAM project)')
  lines.push(`(Tool: ${tool.name}, D=${tool.diameter}mm)`)
  lines.push('G21 G90 G17')
  lines.push(`G0 Z${coord(clearanceHeight)}`)
  lines.push(`G0 X${coord(startVertex.x)} Y${coord(startVertex.y)}`)
  lines.push(`G1 Z${coord(depthOfCut)} F${plungeFeedRate}`)

  for (const vertex of offsetVertices) {
    lines.push(`G1 X${coord(vertex.x)} Y${coord(vertex.y)} F${cutFeedRate}`)
  }

  lines.push(`G1 X${coord(startVertex.x)} Y${coord(startVertex.y)} F${cutFeedRate}`)
  lines.push(`G0 Z${coord(clearanceHeight)}`)
  lines.push('M30')

  return lines.join('\n')
}
```

**`destructuring in function parameters` — first appearance:**
`const { vertices, tool, ... } = params` is **object destructuring** — it extracts
named properties from an object into local constants. Equivalent to writing
`const vertices = params.vertices; const tool = params.tool; ...` for each field.
Destructuring at the top of a function is idiomatic for typed parameter objects: the
remaining code uses the short names directly without the `params.` prefix.

**`coord(value: number): string` — inner helper function:**
`(3.141592653).toFixed(3)` produces `"3.142"`. `toFixed` rounds to the specified
number of decimal places and returns a string.

The `coord` helper is defined inside `generateContourGcode` — an **inner function**.
It is not exported because nothing outside this function needs it. Inner functions
close over the enclosing scope (they are **closures** — introduced in the calculator
project); here `coord` uses no closed-over variables, so it could also be a module-
level function. Placing it inside the generator keeps it conceptually local.

**Three decimal places — why:**
CNC controllers typically accept up to 4 decimal places for metric dimensions. Three
decimal places (0.001mm = 1 micron) is far more precise than any hobby CNC machine
can hold — it is the correct precision for the learning context. More decimal places
would be accepted but waste characters.

**`'(Comment text)'` — G-code comments:**
In Fanuc G-code, text inside parentheses is a comment — ignored by the controller.
We generate two comment lines: one describing the operation type and one specifying
the tool. On a real machine these comments appear on the controller display, giving
the operator context about what the program does.

**`'G21 G90 G17'` — the safe start block:**
Three modal G-codes on one line:
- `G21` — metric units (millimetres). Without this, G-code defaults to the
  controller's last mode — dangerous if the previous program used inches.
- `G90` — absolute positioning. The parser from lesson 18 interprets all X/Y/Z words
  as absolute coordinates. Without G90, coordinates might be interpreted as
  incremental offsets.
- `G17` — XY plane selection. Circular arcs are interpreted in the XY plane (not XZ
  or YZ). Required when arcs are added; harmless to include for linear-only programs.

Always begin a G-code program with these three. They set known modal states rather
than relying on whatever state the previous program left the controller in.

**`'M30'` — end of program:**
`M30` signals the controller that the program has ended and rewinds to the beginning.
Without it, many controllers continue reading from whatever memory follows the last
block — unpredictable behavior. `M30` is the required final line of every standalone
G-code program.

**Walkthrough — generating a program for the 20×20 square with a 6mm end mill:**
```
ContourParameters: vertices = square CCW, tool = 6mm HSS, depth = -3, clearance = 5,
cutFeed = 500, plungeFeed = 150

radius = 3mm
offsetVertices = [(3,3), (17,3), (17,17), (3,17)]
startVertex = (3,3)

Generated:
(Contour toolpath generated by CAM project)
(Tool: 6mm 2-Flute End Mill, D=6mm)
G21 G90 G17
G0 Z5.000
G0 X3.000 Y3.000
G1 Z-3.000 F150
G1 X3.000 Y3.000 F500   ← start vertex (same as current, no movement)
G1 X17.000 Y3.000 F500
G1 X17.000 Y17.000 F500
G1 X3.000 Y17.000 F500
G1 X3.000 Y3.000 F500   ← close: back to start
G0 Z5.000
M30
```

The first G1 after the plunge (at the start vertex) produces no movement — the tool
is already there. This is harmless and makes the loop structure uniform.

**CS lens — code generation as the inverse of parsing:**
Parsing converts text → structure. Code generation converts structure → text. Both
directions define the same language. A sound generator + parser pair can be tested
with **round-trip testing**: generate G-code, then parse it, and verify the parsed
blocks match the original intent. Lesson 24 uses this to validate the exporter.
Round-trip tests are a powerful verification tool: they catch bugs in both directions
simultaneously.

## Step 3 — Wiring Through the Parser and Simulator

### The problem

The generated G-code text must be visualised. We already have the complete pipeline
from lesson 19: `parseGcode → simulateToolpath → buildToolpathLines`. We use it here
to visualise the contour without writing any new rendering code.

```typescript
import { parseGcode }         from '../gcode/parser.js'
import { simulateToolpath }   from '../gcode/simulator.js'
import type { ToolpathSegment } from '../gcode/toolpathSegment.js'

export function contourToToolpathSegments(
  params: ContourParameters,
): { segments: ToolpathSegment[]; gcode: string } {
  const gcode   = generateContourGcode(params)
  const { blocks } = parseGcode(gcode.split('\n'))
  const segments   = simulateToolpath(blocks)
  return { segments, gcode }
}
```

**Walkthrough — through the full pipeline:**

```
generateContourGcode(params)
  → "G21 G90 G17\nG0 Z5.000\n..."

gcode.split('\n')
  → ["G21 G90 G17", "G0 Z5.000", ...]

parseGcode(lines)
  → [{ motionMode: 'rapid', targetZ: 5 }, { motionMode: 'linear', targetX: 3, ... }, ...]

simulateToolpath(blocks)
  → [
      { start:(0,0,0), end:(0,5,0), motionType:'rapid' },  ← Z retract
      { start:(0,5,0), end:(3,5,-3), motionType:'rapid' }, ← XY approach
      ...
    ]
```

Wait — the coordinate mapping. The G-code says `G0 Z5` which the parser stores as
`targetZ = 5`. The simulator's `currentX/Y/Z` are G-code coordinates. After simulation,
`buildToolpathLines` applies the remapping (`gcodeX, gcodeZ, -gcodeY`) to produce
Three.js coordinates. The pipeline correctly separates concerns: the simulator works
in G-code space; the renderer translates to Three.js space.

**SE lens — reusing the existing pipeline:**
`contourToToolpathSegments` does not write new rendering code. It generates G-code
and passes it through the existing parser and simulator. This is the **open/closed
principle**: the toolpath visualisation system is open for extension (new G-code
programs can be generated and fed in) without modification (the parser, simulator,
and renderer are unchanged). Adding the contour operation extends the system; it
does not modify it.

## Step 4 — The Contour Panel Component

### Create `src/cam/ContourPanel.tsx`

```typescript
import { useState }             from 'react'
import type { CuttingTool }     from '../tools/tool.js'
import type { Vec2 }            from './vec2.js'
import type { ToolpathSegment } from '../gcode/toolpathSegment.js'
import { contourToToolpathSegments } from './contourOperation.js'
import './ContourPanel.css'

interface ContourPanelProps {
  selectedTool:    CuttingTool | null
  sketchVertices:  Vec2[]
  onSegmentsReady: (segments: ToolpathSegment[]) => void
}

export function ContourPanel({
  selectedTool,
  sketchVertices,
  onSegmentsReady,
}: ContourPanelProps) {
  const [depthOfCut,      setDepthOfCut]      = useState(-3)
  const [clearanceHeight, setClearanceHeight] = useState(5)
  const [cutFeedRate,     setCutFeedRate]     = useState(500)
  const [plungeFeedRate,  setPlungeFeedRate]  = useState(150)
  const [gcodeText,       setGcodeText]       = useState('')
  const [errorMessage,    setErrorMessage]    = useState<string | null>(null)

  const canGenerate = selectedTool !== null && sketchVertices.length >= 3

  function handleGenerate(): void {
    if (selectedTool === null) return
    try {
      const { segments, gcode } = contourToToolpathSegments({
        vertices:        sketchVertices,
        tool:            selectedTool,
        depthOfCut,
        clearanceHeight,
        cutFeedRate,
        plungeFeedRate,
      })
      setGcodeText(gcode)
      setErrorMessage(null)
      onSegmentsReady(segments)
    } catch (error) {
      setErrorMessage(error instanceof Error ? error.message : 'Unknown error')
    }
  }

  return (
    <div className="contour-panel">
      <h2 className="panel-title">Contour</h2>

      {selectedTool === null && (
        <p className="panel-hint">Select a tool in the Tool Library first.</p>
      )}

      <label className="param-label">
        Depth of cut (mm)
        <input
          type="number"
          value={depthOfCut}
          step={0.5}
          onChange={(event) => setDepthOfCut(Number(event.target.value))}
          className="param-input"
        />
      </label>

      <label className="param-label">
        Clearance height (mm)
        <input
          type="number"
          value={clearanceHeight}
          step={1}
          onChange={(event) => setClearanceHeight(Number(event.target.value))}
          className="param-input"
        />
      </label>

      <label className="param-label">
        Cut feed rate (mm/min)
        <input
          type="number"
          value={cutFeedRate}
          step={50}
          onChange={(event) => setCutFeedRate(Number(event.target.value))}
          className="param-input"
        />
      </label>

      <label className="param-label">
        Plunge feed rate (mm/min)
        <input
          type="number"
          value={plungeFeedRate}
          step={10}
          onChange={(event) => setPlungeFeedRate(Number(event.target.value))}
          className="param-input"
        />
      </label>

      <button
        className="generate-btn"
        onClick={handleGenerate}
        disabled={!canGenerate}
      >
        Generate Contour
      </button>

      {errorMessage !== null && (
        <p className="error-message">{errorMessage}</p>
      )}

      {gcodeText !== '' && (
        <pre className="gcode-preview">{gcodeText}</pre>
      )}
    </div>
  )
}
```

**`error instanceof Error` — error type narrowing:**
`catch (error)` catches any thrown value — in JavaScript, you can throw a string, a
number, or an object. TypeScript types `error` as `unknown` inside a catch block.
`error instanceof Error` is a **type guard**: if true, TypeScript knows `error` is an
`Error` object with a `.message` string. The ternary provides a safe fallback for
non-Error thrown values.

**`disabled={!canGenerate}`:**
The button is disabled until a tool is selected and the sketch has at least 3 vertices.
`disabled` is a boolean HTML attribute on `<button>`. When true, the button does not
respond to clicks and is visually greyed out. Preventing the operation before
preconditions are met is better than running it and failing — the failure message is
less informative than the disabled state.

**`<label>` wrapping `<input>` — accessibility:**
When a `<label>` wraps an `<input>`, the label text is associated with the input
for accessibility tools. Screen readers announce the label text when the input
receives focus. Clicking the label text also focuses the input. This is the correct
HTML form pattern — always associate labels with inputs.

**`<pre className="gcode-preview">` — first appearance:**
`<pre>` renders its content with preserved whitespace and a monospace font — the same
rendering that a terminal or code editor applies to code. G-code is plain text with
one block per line; `<pre>` displays it correctly. Using `<div>` or `<p>` would
collapse whitespace and line breaks.

**Security — rendering user-generated text:**
`{gcodeText}` inside a JSX expression renders as plain text — React escapes all
special HTML characters. If `gcodeText` contained `<script>alert(1)</script>`, React
would render the literal characters `<script>...`, not execute the script. This is
safe. Using `dangerouslySetInnerHTML={{ __html: gcodeText }}` would be dangerous —
never use that for user-generated content. The `{expression}` JSX syntax is always
safe for text content.

## Connect the Pieces

The contour operation integrates every lesson from 07 to 21:

```
Sketch vertices (lessons 07–11)
  ──► offsetPolygon (lesson 21) ──► offset Vec2[]
  ──► generateContourGcode (this lesson) ──► G-code string
  ──► parseGcode (lesson 18) ──► ParsedBlock[]
  ──► simulateToolpath (lesson 19) ──► ToolpathSegment[]
  ──► buildToolpathLines (lesson 19) ──► THREE.LineSegments in scene
```

The architecture of that pipeline is the **layered architecture** pattern: each layer
accepts the output of the previous and knows nothing about layers above or below it.
This is identical in structure to a network stack (TCP/IP) or a rendering engine
(geometry → vertex shader → fragment shader → screen).

The `onSegmentsReady` callback in `ContourPanel` lifts the toolpath segments up to the
application shell, which calls `buildToolpathLines` and stores the returned line
objects for later removal. The same technique lifts `selectedTool` from the tool
library to the contour panel — the common parent always holds the shared state.

## What Breaks Without This

**Without `G21 G90` in the safe start block:**
On a controller whose previous program used imperial units (`G20`), the contour
coordinates `X3.000 Y3.000` would be interpreted as 3 inches, not 3mm. The tool would
rapid to 76.2mm — potentially crashing into the workholding or the machine table.
G-code programs that omit modal reset codes depend on the controller's previous state,
which is the most common source of CNC crashes in real shops.

**Without the plunge feed rate (`F[plungeFeedRate]` on the G1 Z move):**
The modal feed rate from the previous program, or zero if this is the first program,
would apply. Plunging at zero feed or at a high lateral feed rate drives the tool
straight down with no control over chip load — it can break the tool or damage the
spindle. Plunge feed rate should always be 25–50% of the lateral cut feed rate.

**Without the `disabled` state on the generate button:**
Clicking "Generate Contour" with no sketch selected calls `generateContourGcode` with
an empty vertex array. `offsetPolygon` returns `[]`. The loop produces no G-code
lines. `parseGcode` produces no blocks. `simulateToolpath` returns no segments.
`buildToolpathLines` produces empty geometry. No error, no feedback — the user does
not know why nothing happened. The `disabled` state and the hint message give
actionable feedback before the action fails silently.
