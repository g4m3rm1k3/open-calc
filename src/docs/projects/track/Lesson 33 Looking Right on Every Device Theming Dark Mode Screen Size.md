# Lesson 33: Looking Right on Every Device — Material Theming, Dark Mode, and Screen-Size Qualifiers

**What you will build:** A real, custom color palette replacing the
wizard's defaults, a correctly-adapting dark mode, one extracted
`<style>` resource removing duplicated attributes, and a genuine two-
pane layout on tablet-sized screens showing the item list and its
detail side by side. The transferable problem: every visual choice in
this project since Lesson 1 has been whatever the New Project wizard
generated. Android resource **qualifiers** — the mechanism this lesson
is really about — let the *same* resource name (`@color/colorPrimary`,
`activity_inventory.xml`) resolve to *different* actual files depending
on the device's current configuration, entirely outside application
code. This is the exact mechanism `dp`/`sp` (Lesson 3) already relied
on implicitly; this lesson makes it explicit and puts it to direct,
visible use.

**What you need to know first:** Lesson 3 (`dp`/`sp`, resource
references generally), Lesson 21 (`Theme.MaterialComponents.DayNight.NoActionBar`
— the `DayNight` half is this lesson's dark-mode unit, finally
explained), Lesson 18/19 (`InventoryListFragment`'s navigation, the SE
Lens that specifically flagged Activity-scoped `ViewModel` sharing as
groundwork for a two-pane layout).

## Concept Unit: A Real Color Palette, Not the Wizard's Defaults

### The Problem

`res/values/colors.xml`, generated by the wizard in Lesson 1 and never
touched since, holds a handful of arbitrary purple/teal defaults no
lesson ever chose deliberately.

### Project Change

- **Reference Source:** No reference counterpart.
- **Files affected:** `res/values/colors.xml`, `res/values/themes.xml`.
- **Change type:** Modify.

### The New Code

```xml
<resources>
    <color name="brandPrimary">#2E5945</color>
    <color name="brandPrimaryDark">#1B3A2B</color>
    <color name="brandAccent">#D98E04</color>
    <color name="lowStockRed">#B3261E</color>
</resources>
```

```xml
<style name="Theme.PocketInventory" parent="Theme.MaterialComponents.DayNight.NoActionBar">
    <item name="colorPrimary">@color/brandPrimary</item>
    <item name="colorPrimaryDark">@color/brandPrimaryDark</item>
    <item name="colorAccent">@color/brandAccent</item>
</style>
```

### The Updated Project

`colors.xml` gains four named, deliberately-chosen colors, replacing
whatever the wizard generated; `themes.xml`'s existing `Theme.PocketInventory`
style (Lesson 21) gains three `<item>` overrides pointing at them.

### Mechanical Walkthrough
- `<color name="brandPrimary">#2E5945</color>` — reappearing resource-
  declaration shape (`<color name="...">`, present since Lesson 1's
  wizard-generated file, never explained until now): a named color
  resource, hex-coded, referenced elsewhere as `@color/brandPrimary`
  (Lesson 2's `@type/name` syntax).
- `<item name="colorPrimary">@color/brandPrimary</item>` — **first
  appearance of theme attribute overriding.** `colorPrimary` is one of
  a fixed set of *theme attribute names* Material Components looks for
- by convention — every Material widget in this project (the `Toolbar`,
  Lesson 21; every `Button`; the `FloatingActionButton`) automatically
  colors itself using whichever concrete color these named attributes
  currently resolve to, without any individual widget's XML naming a
  color directly.

### Run It

Run the app. The Toolbar, FAB, and every Material-styled widget now
show the new palette — with **zero changes** to any individual layout
file (`fragment_inventory_list.xml`, `fragment_settings.xml`, none of
them touched this unit).

### CS Lens

Widgets referencing an *abstract role* (`colorPrimary`) rather than a
*concrete value*, resolved centrally by the active theme, is
**indirection through a named level**, the same shape as Lesson 3's
`?attr/actionBarSize` and, at a different layer entirely, Lesson 17's
`ItemRepository` seam — callers depend on a stable name, and a single,
central place decides the current, concrete answer.

### SE Lens

**Why not just set `android:backgroundTint="#2E5945"` directly on every
Button/FAB/Toolbar individually?** That would work, once, but changing
the brand color later — a real, common request — would mean hunting
down and editing every individual widget across every layout file
project-wide. Centralizing the decision in the theme means changing
three lines in `themes.xml` restyles the entire app consistently, the
identical "single source of truth, changed once" principle behind
Lesson 7's `Item` class and Lesson 17's Repository, here applied to
visual design instead of data.

## Concept Unit: `values-night` — Dark Mode Through a Resource Qualifier

### The Problem

`Theme.MaterialComponents.DayNight` (Lesson 21) already claims to
adapt to the system's dark mode setting — but this project has never
actually supplied *different* colors for the dark variant, so right
now dark mode likely just applies default Material dark colors around
this lesson's new custom palette, not colors chosen for it.

### Project Change

- **Reference Source:** No reference counterpart.
- **Files affected:** New file `res/values-night/colors.xml`.
- **Change type:** Create.

### The New Code

```xml
<resources>
    <color name="brandPrimary">#5B8F73</color>
    <color name="brandPrimaryDark">#0D1F16</color>
    <color name="brandAccent">#F2B33D</color>
    <color name="lowStockRed">#FF6B60</color>
</resources>
```

### The Updated Project

A whole new file, at a whole new path — `res/values-night/colors.xml`
— reusing the **exact same four resource names** as
`res/values/colors.xml`, with different hex values. Nothing in
`themes.xml` or anywhere else in the project changes at all.

### Mechanical Walkthrough
- `res/values-night/` — **first appearance of a resource qualifier
  folder** in this project, though the underlying mechanism has been
  implicit since Lesson 3: `-night` is a **configuration qualifier**
  Android's resource system checks automatically, at runtime, against
  the device's current dark-mode state — the exact same mechanism (a
  different qualifier, `-hdpi`/`-xhdpi` and so on) that already
  silently picks the right density-specific image assets any Android
  project ships, without a single `if` statement anywhere in your Java
  code.
- Identical `<color name="brandPrimary">...</color>` declarations,
- different values — **the entire mechanism.** `@color/brandPrimary`,
  referenced from `themes.xml`, resolves to `#2E5945` in light mode and
  `#5B8F73` in dark mode, automatically, based purely on which folder
  the OS currently considers active — no Java code anywhere decides
  this.

### Run It

Toggle the emulator's system dark mode setting (Settings → Display →
Dark theme, or the emulator's extended controls). Confirm the app's
colors genuinely change — brighter, adjusted tones in dark mode, not
just an automatically-inverted default — with **zero app restart
required**: `DayNight` themes react live, the moment the system setting
changes, tearing down and rebuilding the current Activity automatically
(the exact same destroy/recreate mechanism Lesson 5 taught for rotation
— a dark-mode toggle is itself a **configuration change**, handled by
the identical machinery).

### CS Lens

Resource qualifiers are a form of **environment-driven configuration
resolution** — the same general idea as environment variables selecting
a config file, or a CDN serving a different asset based on the
requesting device's detected capabilities — resolved automatically by
the platform, entirely outside your own code's control flow.

## Concept Unit: `<style>` — Extracting Repeated Attributes

### The Problem

Every `Button` across this project's layouts (Lesson 3's original,
Lesson 9's Save button, Lesson 22's dialog-adjacent styling) has
repeated similar attribute sets by hand, copy-pasted, with no single
place to adjust them together.

### Project Change

- **Reference Source:** No reference counterpart.
- **Files affected:** `res/values/styles.xml` (new); every layout with
  a primary action `Button`.
- **Change type:** Create, modify.

### The New Code

```xml
<style name="PrimaryActionButton" parent="Widget.MaterialComponents.Button">
    <item name="android:minWidth">200dp</item>
    <item name="android:textAllCaps">false</item>
    <item name="cornerRadius">8dp</item>
</style>
```

Applied to, for example, `AddItemFragment`'s Save button:

```xml
<Button
    android:id="@+id/saveButton"
    style="@style/PrimaryActionButton"
    ...
/>
```

### The Updated Project

A new resource file declaring one reusable style; every primary
`Button` across the app's layouts gains a `style="@style/PrimaryActionButton"`
attribute, removing whatever individually-duplicated sizing/casing
attributes previously existed on each one.

### Mechanical Walkthrough
- `<style name="PrimaryActionButton" parent="Widget.MaterialComponents.Button">`
- — **first appearance of a `<style>` resource** — a **named bundle of
  attribute values**, inheriting from a base style (`parent="..."`,
  the same inheritance idea as Lesson 2's `extends`, applied to XML
  resources instead of Java classes) and overriding specific ones.
- `<item name="android:minWidth">200dp</item>` — reappearing `<item>`
  shape (this lesson's theme-attribute unit), here setting an ordinary
  layout attribute rather than a theme-wide color role.
- `style="@style/PrimaryActionButton"` on a `<Button>` — **first
  appearance of applying a style.** A single attribute now supplies
- every value the `<style>` bundle declares — a real, direct DRY
  improvement, the XML-resource equivalent of Lesson 17's
  `ItemRepository` extraction: repeated configuration pulled into one
  place, referenced everywhere it's needed.

### SE Lens

**Why extract a style for a widget instead of just accepting some
duplication across a handful of buttons?** For two or three buttons,
duplication is genuinely tolerable — this unit's real value shows up
specifically because this project has *multiple* screens (Lesson 9,
21, 22) each with their own primary action button, and Lesson 33's own
earlier units already established this project cares about a single
source of truth for visual decisions; a `<style>` is that principle's
XML-native mechanism, at the cost of one more resource file and one
more layer of indirection to trace when reading any individual layout.

## Concept Unit: `layout-sw600dp` — a Genuinely Different Layout for Larger Screens

### The Problem

Lesson 18's SE Lens specifically flagged `ViewModel` scoped to the
Activity, not the Fragment, as groundwork for a screen that shows the
list *and* detail simultaneously on a large enough display — this unit
finally builds it.

### Project Change

- **Reference Source:** No reference counterpart.
- **Files affected:** New file
  `res/layout-sw600dp/activity_inventory.xml`; `InventoryListFragment.java`.
- **Change type:** Create, modify.
- **Dependencies:** `InventoryViewModel` (Lesson 15), scoped to the
  Activity.

### The New Code — the Alternate Layout

```xml
<LinearLayout xmlns:android="http://schemas.android.com/apk/res/android"
    xmlns:app="http://schemas.android.com/apk/res-auto"
    android:orientation="vertical"
    android:layout_width="match_parent"
    android:layout_height="match_parent">

    <com.google.android.material.appbar.MaterialToolbar
        android:id="@+id/toolbar"
        android:layout_width="match_parent"
        android:layout_height="?attr/actionBarSize" />

    <LinearLayout
        android:orientation="horizontal"
        android:layout_width="match_parent"
        android:layout_height="0dp"
        android:layout_weight="1">

        <androidx.fragment.app.FragmentContainerView
            android:id="@+id/navHostFragment"
            android:layout_width="0dp"
            android:layout_height="match_parent"
            android:layout_weight="1"
            android:name="androidx.navigation.fragment.NavHostFragment"
            app:defaultNavHost="true"
            app:navGraph="@navigation/nav_graph" />

        <FrameLayout
            android:id="@+id/detailContainer"
            android:layout_width="0dp"
            android:layout_height="match_parent"
            android:layout_weight="1" />

    </LinearLayout>

</LinearLayout>
```

### The Updated Project

`res/layout-sw600dp/activity_inventory.xml` — a whole new file at a
whole new qualified path — reuses `InventoryActivity`'s exact same
Toolbar/`NavHostFragment` structure from Lesson 21, adding one sibling:
a second, empty `detailContainer` `FrameLayout`, sitting beside the nav
host in a horizontal split. **`InventoryActivity.java` itself needs no
changes at all** — same class, same `R.layout.activity_inventory`
reference, resolved to a genuinely different file purely by which
folder the current device's configuration matches.

### Mechanical Walkthrough

- `res/layout-sw600dp/` — **first appearance of a layout-specific
  qualifier**, a different kind from `values-night`'s configuration
  qualifier but the identical underlying mechanism: `sw600dp` means
  "smallest-width at least 600dp" — a real, standard threshold roughly
  separating phones from tablets, chosen deliberately over raw pixel
  counts specifically because it's a `dp`-based (Lesson 3) measure,
  correctly accounting for density rather than raw pixel counts.
- `android:layout_weight="1"` — **first appearance.** Inside a
  `LinearLayout` (Lesson 7), distributes remaining space proportionally
  among siblings that declare a weight — both the nav host and
  `detailContainer` claim `weight="1"` with `0dp` width, splitting the
  available horizontal space evenly.
- `<FrameLayout android:id="@+id/detailContainer" ...>` — reappearing
  (`FrameLayout`, Lesson 18), an empty container with nothing placed
  inside it by default — only populated, conditionally, by Java code
  built next.

### The New Code — Detecting and Using the Second Pane

```java
adapter = new InventoryAdapter(item -> {
    View detailContainer = requireActivity().findViewById(R.id.detailContainer);
    if (detailContainer != null) {
        Bundle args = new Bundle();
        args.putParcelable("item", item);
        Fragment detailFragment = new ItemDetailFragment();
        detailFragment.setArguments(args);
        requireActivity().getSupportFragmentManager()
                .beginTransaction()
                .replace(R.id.detailContainer, detailFragment)
                .commit();
    } else {
        InventoryListFragmentDirections.ActionListToDetail action =
                InventoryListFragmentDirections.actionListToDetail(item);
        Navigation.findNavController(view).navigate(action);
    }
});
```

### The Updated Project

`InventoryListFragment`'s row-click lambda (Lesson 19) now branches:
if a `detailContainer` view exists in the currently-inflated
`activity_inventory.xml` (true only on the `layout-sw600dp` variant),
it loads `ItemDetailFragment` directly into that second pane via a
Fragment transaction (Lesson 18's exact mechanism) instead of
navigating away; otherwise, it falls back to Lesson 19's normal
single-pane navigation, completely unchanged.

### Mechanical Walkthrough
- `requireActivity().findViewById(R.id.detailContainer)` — reappearing
  (`findViewById`, Lesson 4), the actual detection mechanism: this
  returns a real `FrameLayout` on a large-screen device (where the
  `sw600dp` layout is active) and `null` everywhere else, since the
  phone-sized `activity_inventory.xml` (Lesson 21) has no view with
  this ID at all.
- `if (detailContainer != null) { ... } else { ... }` — **first
  appearance of this specific runtime layout-detection branch** — the
  Java-code counterpart to the resource system's own automatic file
  selection: the *layout* was chosen automatically by Android; *this*
  check is how application code discovers, at runtime, which one
  actually got chosen.
- `new Bundle(); args.putParcelable("item", item); new ItemDetailFragment(); detailFragment.setArguments(args);`
- — reappearing shapes (`Bundle`/`putParcelable`, Lesson 8;
  `setArguments`, the manual-Fragment-argument mechanism Lesson 19's
  Safe Args normally generates for you automatically — used directly
  here since this path bypasses the Navigation Component entirely).
- `getSupportFragmentManager().beginTransaction().replace(R.id.detailContainer, detailFragment).commit()`
  — reappearing verbatim, Lesson 18 — the manual Fragment transaction
  mechanism that lesson taught, still a real, live tool in this
  project's toolbox even after Lesson 19 replaced it for the *primary*
  single-pane navigation path.

### Run It

Run the app on a phone-sized emulator: tapping a row navigates away to
the detail screen exactly as it has since Lesson 19 — unchanged. Switch
to (or create) a tablet-sized emulator (or resize a resizable emulator
past the 600dp smallest-width threshold): tapping a row now shows the
detail *beside* the list, both visible simultaneously, with the list
itself never leaving the screen — real, working proof that
`res/layout-sw600dp/` genuinely activated a different structure, and
that `InventoryListFragment`'s runtime check correctly adapted its
behavior to match.

### CS Lens

Two independent adaptation mechanisms compose here: the **resource
system** selects which XML file loads, entirely declaratively, based on
device configuration; **application code** then queries the *result* of
that selection (`findViewById` returning `null` or not) to decide its
own behavior — a real, concrete instance of **feature detection**
(checking whether a capability exists and branching accordingly) rather
than **device/configuration detection** (checking a screen-size
threshold number directly in Java) — the more robust, generally
preferred version of this pattern, since it depends only on what's
actually present, not on correctly guessing every configuration that
might produce it.

### SE Lens

**Why detect the pane by checking `findViewById` for `null` instead of
directly querying the screen's width in Java** (`getResources().getConfiguration().smallestScreenWidthDp >= 600`,
a real, available alternative)? Both work, but checking for the view
directly means the *layout resource* stays the single source of truth
for "does this configuration get a two-pane layout" — change the
qualifier folder's threshold, or add a third qualifier tier
later, and this Java code needs zero changes, since it never encoded
the number `600` itself anywhere. Duplicating that threshold as a
magic number in Java as well would create exactly the kind of two-
places-must-agree risk Lesson 7's parallel-lists lesson first warned
against, six lessons before this project even had a list.

## Connect the Pieces

Full trace: `themes.xml` and `colors.xml` establish this project's
actual visual identity for the first time, automatically applied to
every Material widget across every screen without touching a single
layout file → `res/values-night/colors.xml`, reusing the identical
resource names with different values, makes `DayNight` (declared back
in Lesson 21, unexplained until now) a real, adapting dark mode instead
of an inert theme attribute → `PrimaryActionButton` centralizes what
was previously duplicated per-screen → `res/layout-sw600dp/activity_inventory.xml`
extends the same qualifier mechanism to structure itself, not just
colors, adding a second pane the phone-sized layout never had →
`InventoryListFragment`'s row-tap handler detects which structure is
actually active at runtime and branches between Lesson 18's manual
Fragment transaction and Lesson 19's Navigation Component accordingly
— one shared `InventoryViewModel`, scoped to the Activity since Lesson
15, correctly backing both simultaneously-visible Fragments on a large
screen with no duplicated data-loading logic anywhere.

## What Breaks Without This

Temporarily delete `res/values-night/colors.xml` entirely (leave
`themes.xml` referencing `@color/brandPrimary` unchanged). Toggle dark
mode: the app still runs, without crashing (`colors.xml`'s light-mode
values are used as the fallback in every configuration, including dark
mode, since no more-specific match exists) — but the color choices
that looked deliberate in light mode may look poorly contrasted or
simply wrong against a dark background, a real, easy-to-miss visual
regression rather than a loud failure. Restore the file afterward.
