# Lesson 2.12: Arguments in Signals

**What you will build.** `MainWindow.__init__` gains one more real
connection: `self.search_box.textChanged.connect(self.on_search_text
_changed)`, and a new method, `on_search_text_changed`, storing
whatever was typed as `self.current_search_text`. Nothing about
`clicked` (Lesson 2.11) ever carried information beyond the bare fact
"this happened" — `textChanged`, this lesson's own real subject, hands
its slot something real: the field's own new text, every time it
changes. The transferable problem: not every signal is a bare
announcement — many carry real, useful data about exactly what
happened, and a slot has to be written correctly to actually receive
it, not merely to run when the signal fires.

**What you need to know first.** Lesson 2.11 — signal, slot,
`Signal.connect` — this lesson's own entire mechanism, extended rather
than replaced. Lesson 2.6 — `QLineEdit`, `self.search_box` — the exact
field this lesson's own signal belongs to.

**Scope note.** `self.current_search_text` is stored, not used —
nothing in this project yet filters real `Asset` data by it, since
nothing in `asset_manager/desktop/` reads `asset_manager.domain` at
all, a discipline kept since Lesson 2.5. Actually filtering a real list
of assets is deferred to whichever future lesson first connects this
project's UI layer to real domain data.

## Terms used in this lesson

- **signal argument** — new. A real value a signal hands to every slot
  connected to it, alongside the bare fact that it fired — `textChanged`'s
  own argument is the field's new text; `clicked` (Lesson 2.11) carries
  no argument at all. A slot only receives arguments it's written to
  accept — this lesson's own second unit proves exactly how much
  flexibility that allows, and exactly where it stops.
- **`TypeError`** — reapplied in full from Lesson 1.7: a real, built-in
  exception Python raises when an operation gets a value of the wrong
  type, or the wrong number of arguments, for what it's doing. This
  lesson's own use is the identical cause Lesson 1.7 first showed it
  for — a call missing a required argument — except here the call
  happens inside Qt's own signal-dispatch machinery, calling a slot
  with fewer arguments than that slot's own signature requires, rather
  than this project's own code calling a function directly.

## Objects and methods used

**`QLineEdit.textChanged`**

- *What it is:* a real signal every `QLineEdit` carries, emitted every
  time its own text changes, for any reason — typed by a user, or set
  programmatically via `setText`.
- *Implementation:* emits one argument, the field's own complete new
  text, as a real `str`.
- *Its use:* `self.search_box.textChanged.connect(self.on_search_text
  _changed)` is this lesson's own real, central wiring.
- *Type:* a signal, reapplied in kind from Lesson 2.11's own `clicked`
  — the same underlying mechanism, carrying real data this time.
- *Responsibility:* announce a text change, and hand along exactly what
  the new text now is — nothing about validating it, or comparing it
  to the old value.
- *Depends on:* the field's own text actually changing.
- *Connects to:* whatever slot(s) are connected; this lesson connects
  exactly one, `self.on_search_text_changed`.
- *Shape:* the announcing half of this lesson's whole mechanism —
  identical in kind to `clicked`, genuinely different in that it
  carries real information along with the announcement itself.

## Concept Unit: A Signal Handing Its Slot a Real Value

### The Problem

Lesson 2.11's own `clicked` slot, `on_clicked`, took no parameters at
all — nothing about a click carries any extra information beyond "it
happened." `textChanged`, this lesson's own header already states,
hands along the field's own new text. Does a slot connected to it
actually *receive* that text as a real, usable argument?

> **Before reading on, try this:**
> - Lesson 2.11's own `on_clicked` was written `def on_clicked():` —
>   no parameters. Given `textChanged` carries a real value, what do
>   you predict a slot connected to it needs to look like instead —
>   still no parameters, or does it need one to actually receive
>   anything?
> - If `field.setText("a")`, then `field.setText("as")`, then `field
>   .setText("ass")` all run in a row, each one changing the field's
>   own text, do you predict a connected slot runs once total, or once
>   per `setText` call, each time with that call's own new value?

### Isolated Concept

```python
from PySide6.QtWidgets import QApplication, QLineEdit

app = QApplication([])

field = QLineEdit()

received = []


def on_text_changed(new_text):
    received.append(new_text)


field.textChanged.connect(on_text_changed)

field.setText("a")
field.setText("as")
field.setText("ass")

print(received)
```

Run for real (`lab1_signal_argument.py`, headless):

```
['a', 'as', 'ass']
```

`on_text_changed(new_text)` — one real parameter, `new_text`, unlike
Lesson 2.11's own parameter-free `on_clicked`. Real, confirmed proof,
not a claim: `received` ends up holding all three strings, in order —
`textChanged` fired three separate times, once per `setText` call, each
time handing `on_text_changed` that exact call's own new value as a
real argument, not merely notifying that *some* change happened.

Discarded: `field`/`received`/`on_text_changed` exist only to prove
this mechanism. None will appear in the Asset Manager project again in
this exact form.

### CS Lens

A direct application of Lesson 2.11's own Observer-pattern material,
now carrying a real payload alongside the notification itself — worth
its own real-world connection, since a notification carrying data,
rather than a bare announcement, is itself a meaningfully different
shape.

```
Also recognized in: a webhook's own POST body carrying real event data,
not just "something happened," a stock ticker broadcast carrying the
actual new price, not just "price changed," a DOM `input` event in a
browser carrying the element's own new value directly in the event
object
```

### SE Lens

The alternative not chosen is a signal announcing only that something
happened, leaving a slot to separately query the field's own current
state (`field.text()`) to learn what actually changed. The real benefit
of carrying the value directly instead: a slot never risks reading a
value that's already changed again by the time it asks — the exact
value handed to it is guaranteed to be the one that triggered this
specific emission, not whatever the field happens to hold at the moment
the slot gets around to checking.

## Concept Unit: Slot Signature Flexibility

### The Problem

The previous unit's slot declared exactly one parameter, matching
`textChanged`'s own one argument precisely. Does a slot have to match
exactly, or is there real flexibility — and in which direction, if any?

> **Before reading on, try this:**
> - If a slot connected to `textChanged` is written with *no*
>   parameters at all — the same shape Lesson 2.11's own `on_clicked`
>   used — do you predict connecting it to a signal that *does* carry
>   an argument fails outright, or does it still run, simply never
>   receiving the value?
> - If a slot instead declares *two* required parameters, but
>   `textChanged` only ever provides one, do you predict Qt somehow
>   supplies a second value anyway, or does calling that slot fail the
>   same way an ordinary Python function call with too few arguments
>   always has?
> - If calling a slot genuinely does raise a real `TypeError` because
>   of a mismatch like that, do you predict the whole application
>   crashes, uncaught — the same way this curriculum's own `break_*.py`
>   scripts have crashed since Lesson 1.6 — or does PySide6 handle a
>   slot's own exception somehow differently than an exception raised
>   anywhere else in this project's code?

### Project Change

- **Reference Source:** No reference counterpart — original curriculum
  project.
- **Files affected:** none — this unit continues proving mechanics in
  isolation; the next unit lands the real, permanent connection.
- **Change type:** N/A.

### Isolated Concept

A slot with *fewer* parameters than the signal provides:

```python
from PySide6.QtWidgets import QApplication, QLineEdit

app = QApplication([])

field = QLineEdit()

calls = []


def on_text_changed_no_args():
    calls.append("called")


field.textChanged.connect(on_text_changed_no_args)

field.setText("a")

print(calls)
```

Run for real (`lab2_mismatched_slot.py`, headless):

```
['called']
```

Real, confirmed proof, not a claim: a slot declaring *fewer* parameters
than the signal provides still runs correctly — PySide6 simply doesn't
hand it the extra argument, rather than refusing the connection or
raising any error at all.

A slot with *more* required parameters than the signal provides:

```python
from PySide6.QtWidgets import QApplication, QLineEdit

app = QApplication([])

field = QLineEdit()


def on_text_changed_too_many(new_text, extra_required_arg):
    print(new_text, extra_required_arg)


field.textChanged.connect(on_text_changed_too_many)

field.setText("a")
```

Run for real (`break_too_many_params.py`) — this run is *expected* to
report an error:

```
TypeError: on_text_changed_too_many() missing 1 required positional argument: 'extra_required_arg'
```

Real, confirmed proof, not a claim: a slot requiring *more* arguments
than `textChanged` actually provides fails — the identical `TypeError`
Python would raise calling any ordinary function with too few
arguments, since that's mechanically exactly what happened underneath.
The genuinely surprising part, confirmed directly: this error does
*not* crash the whole application, uncaught, the way a `break_*.py`
script has since Lesson 1.6 — PySide6 catches an exception raised
inside a slot, prints it, and lets the rest of the program keep
running, rather than letting it propagate up through Qt's own C++
signal-dispatch code, which isn't built to handle a Python exception
passing through it safely.

Discarded: `field`/`calls`/both throwaway slot functions exist only to
prove this contrast. None will appear in the Asset Manager project
again.

### CS Lens

This is **contravariant parameter flexibility** — a receiver is allowed
to ask for *less* than a caller offers (safe: the extra is simply
ignored), but never *more* (unsafe: nothing exists to supply it). This
is a hard concept, worth more than one real-world connection.

```
Also recognized in: a JavaScript event handler that can ignore the
event object parameter entirely if it doesn't need it, a REST API
endpoint tolerating extra, unused fields in a request body while
rejecting one missing a required field, an interface method allowed to
accept a narrower parameter type in some type systems but never a wider
one
```

### SE Lens

The alternative not chosen is Qt requiring a slot's own signature to
match a signal's arguments exactly, rejecting the connection outright
if they don't. The real benefit of the flexibility Qt actually provides
instead: a slot that doesn't care about a signal's own carried value —
Lesson 2.11's own `open_asset_editor`, which could be connected to
`textChanged` too, uninterested in whatever text was typed — never
needs a parameter it would just ignore. The real, honest cost, proven
directly above: an application catching and swallowing a slot's own
exceptions, rather than crashing loudly, can leave a real bug running
silently, printed but easy to miss, exactly the same category of risk
Lesson 2.11's own garbage-collection gotcha already demonstrated for a
different reason.
