  positioning, or styling beyond Qt's own defaults, none of which this
  lesson touches.
- *Depends on:* being given text, and, per this lesson's own proof,
  needing its parent actually shown before it reports itself visible.
- *Connects to:* constructed directly inside this lesson's own
  throwaway script; parented to a `QMainWindow`, reapplying Lesson

- *Shape:* the simplest possible real, visible widget — the natural

## Concept Unit: A Real, Visible Widget

### The Problem

Lesson 2.1's own window has been on screen since it was written, but
displays nothing at all — an empty rectangle. Lesson 2.3 already proved
`QObject`s can be parented to each other, with a real, checkable
relationship — does that exact mechanism, applied to something visible
this time, put real content inside a window? And does a child widget's
own visibility depend only on itself, or on its parent too?

>   `label.parent() is window`?
> - Lesson 2.1 already proved a bare `QMainWindow` reports
>   `isVisible()` as `False` until `show()` is called. If a `QLabel` is
>   created and parented to a window *before* that window is shown, do
>   you predict the label itself reports `isVisible()` as `True`
>   immediately — or does it depend on its parent's own visibility too?

### Isolated Concept

```python
from PySide6.QtWidgets import QApplication, QLabel, QMainWindow

app = QApplication([])

window = QMainWindow()
label = QLabel("Asset Manager", window)

print(label.text())
print(label.parent() is window)
print(label in window.children())
print(label.isVisible())

window.show()
print(label.isVisible())
```

Run for real (`lab1_qlabel.py`, headless):

```
Asset Manager
True
True
False
True
```

`label.text()` reads back exactly the string handed to the constructor
— real, confirmed proof `QLabel`'s own text is genuinely stored, not
just displayed transiently. `label.parent() is window` and `label in
window.children()` reapply Lesson 2.3's own parent/child proof, `is`
(Lesson 1.1) and `in` (general membership testing, reapplied baseline
since Lesson 1.3's own `.append()` material) confirming the identical
relationship from both directions, now on something visible for the
first time. The real surprise this unit exists to prove: `label
.isVisible()`, checked *before* `window.show()`, reads `False` — even
though `label` itself was never told to hide. Only after `window
.show()` runs does the identical `label.isVisible()` call read `True`.
Real, confirmed proof, not a claim: a child widget's own visibility
genuinely depends on its parent's, not only on itself — showing a
window is what makes every widget already inside it visible too, all
at once, not something each widget needs told individually.

Discarded: `window`/`label` exist only to prove this. Neither will
appear in the Asset Manager project again in this exact form — a
future lesson's own real widgets will be parented and shown the
identical way, for a real reason.

### CS Lens

This is **visibility inheritance through a containment hierarchy** — a
child's own effective, displayed state depending on every ancestor
above it, not just its own local setting. This is a hard concept,
worth more than one real-world connection.

```
Also recognized in: a hidden folder in a filesystem making every file
inside it inaccessible through normal browsing, regardless of each
individual file's own permissions, a collapsed section in a document
outline hiding every paragraph nested beneath it, a CSS display:none
rule on a parent element hiding every child element inside it, no
matter what each child's own style says
```

### SE Lens

The alternative not chosen is a widget that tracks and reports only its
own, local visibility setting, independent of its parent's. The real
benefit of Qt's own behavior instead: a window with dozens of child
widgets can be shown or hidden as one single, coherent unit —
`window.show()` alone, proven directly above, is enough to make every
widget inside it appear, without a caller needing to remember to call
`show()` separately on each one.
