**What you will build.** `MainWindow` (2.1 onward) gains a real menu
bar — its first, this project has never had one — with a `File` menu
holding four real entries: `New`, `Edit`, `Delete`, `Exit`. `New`

against this project's own actual window, and a real, verified proof

actually ends `app.exec()` (2.2) and lets the whole program finish.

**What you need to know first.** Lesson 2.11 — `self.open_asset_editor`,
and `Signal.connect` accepting a bound method directly; reused here

## Terms used in this lesson

- **mnemonic** (also called an **accelerator**) — new. A single
  underlined letter in a menu item's own label, activatable by pressing
  `Alt` plus that letter while the menu is open — exists so a keyboard-
  only user can operate a menu without a mouse at all. Written directly
  inside a `QAction`'s own text using an `&` immediately before the
  letter (`"&New"`); the `&` itself is never shown — Qt strips it and
  underlines the letter that follows.

## Objects and methods used

**`QAction`**

- *What it is:* a real class — from PySide6's `QtGui` module, not
  `QtWidgets`, a real, non-obvious fact worth stating plainly since
  every other new UI-related class this project has ever used (`QDialog`,
  `QMessageBox`, every widget since 2.1) came from `QtWidgets` instead —
  represents one real, triggerable action a user can take, independent
  of any specific button, menu, or toolbar it might be attached to.
- *Implementation:* `QAction(text: str, parent: QObject | None = None)`;
  carries a real `triggered` signal, and real `trigger()`, `setEnabled()`,
  `isEnabled()` methods.
- *Its use:* `new_action = QAction("&New", self)`, this lesson's own
  real, central new object — one for each of `New`/`Edit`/`Delete`/
  `Exit`.
- *Type:* a class, from `PySide6.QtGui` — a `QObject` (2.3), but,
  unlike every widget this project has built, *not* a `QWidget` at all;
  a `QAction` has no visual appearance of its own until it's attached
  to something (a menu, here) that knows how to display it.
- *Responsibility:* represent one real, nameable thing a user can do,
  and announce, via `triggered`, whenever that happens — nothing about
  *how* it's presented (a menu item, here; a toolbar button or keyboard
  shortcut, neither built by this project yet, are real, valid
  alternatives the identical `QAction` object could be attached to).
- *Depends on:* a real label string; optionally, a real `QObject` parent.
- *Connects to:* attached to a `QMenu` via `QMenu.addAction`; its own
  `triggered` signal connects to a real slot exactly the same way any
  other signal has since Lesson 2.11.
- *Shape:* this lesson's own real, central new mechanism — a UI action
  that exists independently of any one specific widget presenting it.

**`QAction.triggered`**

- *What it is:* a real signal every `QAction` carries — announces that
  the action was actually invoked, regardless of how.
- *Implementation:* emitted automatically when a user activates the
  action through whatever it's attached to (clicking a menu item,
  here), or, this lesson's own verification, by calling `.trigger()`
  directly.
- *Its use:* `new_action.triggered.connect(self.open_asset_editor)`,
  this lesson's own real, central wiring — the exact same real method
  `self.button.clicked` (2.11) already connects to, now reachable a
  second, independent way.
- *Type:* a signal — reapplying Lesson 2.11's own general signal
  material, this time on a `QAction` rather than a widget.
- *Responsibility:* announce that this specific action happened —
  nothing about what happens next, entirely the connected slot's own
  job, the identical division of labor every signal in this project has
  always kept.
- *Depends on:* the action actually being activated, through any of its
  real attachment points, or `.trigger()` called directly.
- *Connects to:* whatever slot(s) are connected via `.connect(...)`.
- *Shape:* the announcing half of this lesson's whole mechanism — the
  exact same real shape `Signal`/`SignalInstance` (2.14) already
  established, reused here on a class this project didn't write itself.

**`QAction.trigger`**

- *What it is:* a real method every `QAction` carries — programmatically
  invokes the action, emitting `triggered` exactly as a real user
  interaction would.
- *Implementation:* `trigger(self) -> None`.
- *Its use:* `new_action.trigger()`, throughout this lesson's own
  verification, is what lets a headless, unattended script prove a
  menu action's own connection actually fires — no real mouse, keyboard,
  or open menu needed, the identical real role `QPushButton.click`
  (2.11) has always played for buttons.
- *Type:* an instance method.
- *Responsibility:* trigger the exact same signal emission a real
  activation would — nothing about visually opening any menu this
  action might be attached to.
- *Depends on:* the action already existing.
- *Connects to:* emits `triggered`, which in turn calls every connected
  slot.
- *Shape:* this lesson's own entire verification mechanism for every
  `QAction` it tests — the concrete way "did the connection actually
  work?" gets a real, proven answer.

**`QAction.setEnabled`** *(and* `QAction.isEnabled`*)*

- *What it is:* a real method pair every `QAction` carries — controls,
  and reports, whether the action can currently be activated at all.
- *Implementation:* `setEnabled(self, enabled: bool) -> None`;
  `isEnabled(self) -> bool` — real, confirmed default is `True`.
- *Its use:* `edit_action.setEnabled(False)` and `delete_action
  .setEnabled(False)`, this lesson's own real, honest handling of two
  menu entries with nothing yet to act on — visible, but genuinely
  un-clickable, rather than hidden or faked.
- *Type:* an instance method pair.
- *Responsibility:* the single, real fact of whether this action
  currently accepts activation — nothing about *why*; that's left
  entirely to whatever code calls `setEnabled`.
- *Depends on:* nothing; callable at any time.
- *Connects to:* a disabled action's own `triggered` signal simply
  never fires, no matter how a user tries to activate it — real Qt
  behavior handling the actual blocking, not this project's own code.
- *Shape:* the real, honest mechanism behind "this exists, but isn't
  ready yet" — this lesson's own concrete answer to a gap Lesson 2.14
  and 2.15 both already named the same honest way, in prose rather than
  in a real, disabled UI element.

**`QMainWindow.menuBar`**

- *What it is:* a real method every `QMainWindow` carries — returns
  this window's own real menu bar, creating one automatically the first
  time it's called if none exists yet.
- *Implementation:* `menuBar(self) -> QMenuBar`.
- *Its use:* `menu_bar = self.menuBar()`, the first real line of this
  lesson's own new code — `MainWindow` has never called this before,
  meaning this is the exact moment a real `QMenuBar` first comes to
  exist for this project at all.
- *Type:* an instance method, on `QMainWindow`.
- *Responsibility:* guarantee exactly one real menu bar exists for this
  window, building one automatically if this is the first time it's
  asked for — nothing about what menus or actions that menu bar
  actually holds.
- *Depends on:* nothing beyond the `QMainWindow` itself already
  existing.
- *Connects to:* the returned `QMenuBar` is automatically placed at the
  top of the window, in `QMainWindow`'s own dedicated menu-bar region —
  real estate every `QMainWindow` has reserved since Lesson 2.1, unused
  by this project until now.
- *Shape:* the real entry point into this lesson's entire menu
  structure.

**`QMenuBar`** *(and* `QMenuBar.addMenu`*)*

- *What it is:* a real class from `PySide6.QtWidgets` — the horizontal
  bar holding top-level menus (`File`, and, in a larger application,
  siblings like `Edit` or `View`); `addMenu` is a real method building
  and adding one new top-level menu to it.
- *Implementation:* `addMenu(self, title: str) -> QMenu` — builds a
  real, empty `QMenu`, adds it to the menu bar under the given title,
  and returns it.
- *Its use:* `file_menu = menu_bar.addMenu("&File")`, this lesson's own
  real, single top-level menu.
- *Type:* a class, from `PySide6.QtWidgets` — a `QWidget`; `addMenu` is
  an instance method on it.
- *Responsibility:* hold an ordered list of top-level menus, and
  present each one's own label — nothing about what any individual menu
  actually contains.
- *Depends on:* a real title string for each menu added.
- *Connects to:* returns a real `QMenu` (below), which this lesson's
  own code then populates with real actions.
- *Shape:* this project's own first real menu bar — the container every
  future menu this project ever adds will live inside.

**`QMenu`** *(and* `QMenu.addAction`*,* `QMenu.addSeparator`*)*

- *What it is:* a real class from `PySide6.QtWidgets` — one real,
  named dropdown menu, holding an ordered list of actions and
  separators; `addAction`/`addSeparator` are real methods adding to
  that list.
- *Implementation:* `addAction(self, action: QAction) -> None`;
  `addSeparator(self) -> QAction` — a real, visual dividing line,
  itself represented internally as a special `QAction` whose own
  `isSeparator()` reads `True`, though this lesson's own code never
  calls that directly.
- *Its use:* `file_menu.addAction(new_action)`, called once per action,
  in the exact order they should appear; `file_menu.addSeparator()`
  visually separates `Delete` from `Exit`, the identical grouping
  convention real applications use to set a destructive-adjacent or
  unrelated action apart from the rest.
- *Type:* a class, from `PySide6.QtWidgets` — a `QWidget`.
- *Responsibility:* hold an ordered list of real actions (and
  separators), and present them, in order, the moment the menu is
  opened — nothing about what happens when any one of them is
  triggered; that's each `QAction`'s own connected slot.
- *Depends on:* real `QAction` objects to add.
- *Connects to:* built by `QMenuBar.addMenu`; every action added to it
  is automatically re-parented to it, the identical re-parenting
  mechanism Lesson 2.8 and 2.9 already proved for layouts.
- *Shape:* this lesson's own real, single dropdown menu — the concrete
  place `New`/`Edit`/`Delete`/`Exit` actually live.

**`QWidget.close`** *(via* `self.close`*)*

- *What it is:* a real method every `QWidget` carries — reapplied,
  inherited, exercised for the first time by something other than a

- *Implementation:* `close(self) -> bool` — real, internal behavior:

- *Responsibility:* close exactly one widget, dispatching a real
  `closeEvent` first — nothing about ending the whole application;
  that's a real, separate, automatic consequence proven in this
  lesson's own first unit, not something `close` itself decides.
- *Depends on:* nothing beyond the widget already existing.
- *Connects to:* `close`, called as a real, bound method, is directly
  connectable to `triggered` the same way `self.open_asset_editor`
  already is — reapplying Lesson 2.11's own "a bound method is a real,
  callable slot" material against an *inherited* method this project

- *Shape:* the real, standard way any widget, including this project's
  own `MainWindow`, is closed — proven here to reach all the way back

## Concept Unit: QAction and the Command Pattern

### The Problem

Every real, clickable thing this project has ever built has been a
widget itself — a `QPushButton` (2.5) directly connected to a slot.
Can one real "thing a user can do" exist as its own object, entirely
separate from any specific button or menu item, connectable the same
way, and triggerable programmatically the same way `QPushButton.click`
(2.11) has always let this project prove a connection works — and,
since this object is never explicitly stored as a `self.` attribute
anywhere in this lesson's own real landing, does it actually survive?

> **Before reading on, try this:**
> - `QPushButton.clicked` (2.5, 2.11) only exists because a real button
>   widget exists to carry it. Given `QAction` is described as
>   independent of any specific widget, what do you predict its own
>   `triggered` signal requires to exist at all — a visible widget
>   already on screen, or something less?
> - Lesson 2.11's own real gotcha was a widget with *no* real Qt
>   parent, kept alive only by a plain local variable, silently
>   garbage collected. Given `QAction(text, parent)`'s own second
>   argument is a real `QObject` parent (Lesson 2.3), passed directly
>   at construction time, what do you predict happens to a `QAction`
>   built this way if the local variable holding it goes out of scope —
>   the identical fate Lesson 2.11's own widget met, or something
>   different?

### Isolated Concept

```python
import gc
import weakref

from PySide6.QtGui import QAction
from PySide6.QtWidgets import QApplication, QMainWindow

app = QApplication([])

window = QMainWindow()

triggers = []
action_ref = None


def on_new_triggered():
    triggers.append("new")


def build_menu():
    global action_ref
    menu_bar = window.menuBar()
    file_menu = menu_bar.addMenu("&File")

    new_action = QAction("&New", window)
    new_action.triggered.connect(on_new_triggered)
    file_menu.addAction(new_action)

    edit_action = QAction("&Edit", window)
    edit_action.setEnabled(False)
    file_menu.addAction(edit_action)

    action_ref = weakref.ref(new_action)
    return file_menu, new_action, edit_action


file_menu, new_action, edit_action = build_menu()

print(type(file_menu))
print(new_action.isEnabled())
print(edit_action.isEnabled())

del new_action, edit_action
gc.collect()

print(action_ref())
print(action_ref().parent() is window)

print(triggers)
action_ref().trigger()
print(triggers)
```

`action_ref().parent() is window` confirms directly: the surviving
object's own real parent is `window`, exactly as passed. `action_ref

### CS Lens

This is the **Command pattern** — encapsulating "a thing that can be
done" as a real, standalone object, separate from whatever triggers it
or whatever code actually carries it out. This is a hard concept, worth

```
Also recognized in: a text editor's own "Undo" system, where each
```

```python
from PySide6.QtCore import QTimer
from PySide6.QtWidgets import QApplication, QMainWindow


class TrackedWindow(QMainWindow):
    def __init__(self) -> None:
        super().__init__()
        self.close_events = 0

    def closeEvent(self, event) -> None:
        self.close_events += 1
        super().closeEvent(event)


app = QApplication([])
window = TrackedWindow()
window.show()

print(window.close_events)

QTimer.singleShot(50, window.close)
exit_code = app.exec()

print(window.close_events)
```
