# Lesson 2.14: Custom Signals

**What you will build.** Every signal used so far — `QPushButton.clicked`
(Lesson 2.5, 2.11), `QLineEdit.textChanged` (Lesson 2.6, 2.13) — already
existed on a PySide6-provided class before this project ever touched it.
This lesson declares a brand-new signal this project itself owns, on a
class this project itself writes, and proves Qt's real machinery treats
it exactly the same way a built-in one is treated — connectable,
emittable, carrying real data to whatever slot is listening. That new
signal lands for real: `asset_manager/desktop/asset_editor.py`'s own
`build_asset_editor()` function (Lesson 2.9), still standing exactly as
Lesson 2.9 left it, becomes a real `AssetEditor(QWidget)` class — a
`Signal` can only be declared on a class, never a function — with a new
"Save" button that announces "an asset was submitted" without knowing or
caring who, if anyone, is listening. `MainWindow` (Lesson 2.11) listens,
and stores what it hears in a plain list — not yet a real domain
`Asset`, and not yet validated; both of those are explicitly Lesson
2.15's own job, not this one's. Only some of what this lesson touches is
meant to last: the custom signal itself, its declaration, and the real
wiring between `AssetEditor` and `MainWindow` all survive; treating the
raw submitted strings as a finished, trustworthy `Asset` does not, and
this lesson says so plainly at the point that gap opens.

**What you need to know first.** Lesson 2.11 — `Signal.connect`, signal
emission, the Observer pattern, and `QObject`'s own real role as the
base class every signal-carrying type needs; all three reapplied here
against a signal this project declares itself rather than one Qt
already provided. Lesson 2.3 — `QObject`, subclassed here directly for
the first time with no widget behavior riding along at all. Lesson 2.9 —
`build_asset_editor()`, `QFormLayout`, and the exact three fields this
lesson's own class wraps, unchanged. Lesson 1.7 — `Asset`'s own real
fields (`name`, `serial_number`, `category`), the shape this lesson's
submitted data still doesn't become, on purpose.

## Terms used in this lesson

- **custom signal** — new. A signal a project declares for itself,
  rather than one already provided by a PySide6 class like
  `QPushButton` or `QLineEdit` — exists because a project's own classes
  frequently need to announce project-specific events ("an asset was
  submitted") that no built-in Qt class could ever anticipate.
- **f-string** — reappearing. Python's own `f"..."` string syntax,
  evaluating any `{expression}` placed inside its braces and splicing
  the result directly into the surrounding text at runtime — exists so
  a string combining fixed text and computed values doesn't need
  separate concatenation or `.format()` calls.

## Objects and methods used

**`Signal`**

- *What it is:* a real class from PySide6's `QtCore` module — declaring
  one creates a brand-new signal, owned by whatever class it's declared
  on, rather than reusing a signal a PySide6-provided class already
  carries.
- *Implementation:* `Signal(*types: type)` — each positional argument
  names the real Python type one value emitted through this signal will
  carry; `Signal(str)` declares a signal carrying exactly one `str`,
  `Signal(str, str, str)` declares one carrying exactly three, in order.
- *Its use:* `asset_submitted = Signal(str, str, str)`, this lesson's own
  real, central declaration — three strings, matching `AssetEditor`'s
  own three fields exactly.
- *Type:* a class — but never constructed the way an ordinary object is;
  assigning `Signal(...)` as a class-level attribute is itself the whole
  declaration, not a step before some separate "real" declaration.
- *Responsibility:* exist as the announcing half of a signal/slot pair
  this project itself defines — nothing about who, if anyone, connects
  to it, and nothing about what happens when it's emitted; both are
  entirely the connected slot's own job, the identical division of labor
  Lesson 2.11's own `QPushButton.clicked` already established.
- *Depends on:* being declared inside a real `QObject` subclass (or a
  subclass of something built on top of `QObject`, like `QWidget`) —
  declaring one on a plain Python class with no such ancestry does not
  work; Qt's own signal machinery is what makes a declared `Signal`
  connectable and emittable at all, and only a `QObject`-derived class
  has that machinery.
- *Connects to:* declared once, at class level; every instance of that
  class gets its own independent, connectable, emittable copy —
  proven directly in this lesson's own first unit.
- *Shape:* a public announcement surface a project-defined class exposes
  to anything that wants to react to it, without that class needing to
  know anything about what reacts or how.

**`SignalInstance`**

- *What it is:* a real class from PySide6's `QtCore` module — what a
  `Signal` class-level declaration actually becomes once accessed
  through a real instance, rather than the class itself.
- *Implementation:* returned automatically by Qt's own machinery the
  moment a declared `Signal` is accessed as `some_instance.signal_name`
  rather than `SomeClass.signal_name`; carries the real `.connect(...)`
  and `.emit(...)` methods this lesson's own code calls.
- *Its use:* every `.connect(...)` and `.emit(...)` call in this lesson
  runs on a `SignalInstance`, never directly on the `Signal` class-level
  declaration itself — `doorbell.pressed`, `self.asset_submitted`
  (accessed as `self.asset_submitted.emit(...)` inside `AssetEditor`),
  and `self.editor.asset_submitted` (accessed the same way inside
  `MainWindow`) are all real `SignalInstance` objects, confirmed
  directly by this lesson's own first unit.
- *Type:* a class, from `PySide6.QtCore` — distinct from `Signal`
  itself, even though both are named and used as if they were the same
  thing at a glance.
- *Responsibility:* hold the real, per-instance list of connected slots
  for exactly one object's own copy of a declared signal, and carry out
  the real `connect`/`emit` mechanics against that specific list —
  nothing about any other instance's own connections.
- *Depends on:* a real instance of the `QObject`-derived class the
  `Signal` was declared on; there is no `SignalInstance` without one.
- *Connects to:* created automatically by Qt the first time a specific
  instance's signal attribute is accessed; every `.connect(...)` call on
  it adds one more slot to that specific instance's own list, entirely
  separate from any other instance of the same class.
- *Shape:* the real, live object every signal/slot interaction this
  project has ever performed — Lesson 2.11's own `button.clicked` was
  always a `SignalInstance` too, just never named as one until now.

**`Signal.emit`**

- *What it is:* a real method every `SignalInstance` carries — actually
  triggers the signal, calling every connected slot in turn.
- *Implementation:* `emit(self, *args) -> None` — the number and type of
  arguments must match what the signal's own `Signal(...)` declaration
  named; `Signal(str, str, str)` requires exactly three values passed to
  `emit`.
- *Its use:* `self.asset_submitted.emit(self.name_field.text(), ...)`,
  inside `AssetEditor.on_save_clicked`, is this lesson's own real,
  central trigger — the exact moment "an asset was submitted" actually
  becomes true for anything connected to hear it.
- *Type:* an instance method, on a `SignalInstance`.
- *Responsibility:* call every slot connected to this specific instance's
  signal, in the order they were connected, passing each one the exact
  arguments `emit` itself was given — nothing about deciding whether to
  emit, or what any connected slot does in response.
- *Depends on:* at least the exact number and type of arguments the
  signal's own declaration specified; nothing about there being any
  slots connected at all — an emit with zero connected slots still runs,
  it simply calls nothing.
- *Connects to:* called by whatever code decides the announced event has
  genuinely happened (`on_save_clicked`, here); calls out to every slot
  `.connect(...)` has registered.
- *Shape:* the triggering half of this lesson's whole mechanism — the
  counterpart to `Signal.connect` (Lesson 2.11), which only wires the
  pieces together without ever, itself, causing anything to run.

## Concept Unit: Declaring a Custom Signal

### The Problem

Every signal connected to or emitted so far — `QPushButton.clicked`
(Lesson 2.5, 2.11), `QLineEdit.textChanged` (Lesson 2.6) — already
existed on a PySide6-provided class before this project ever touched
it. `Signal.connect` (Lesson 2.11) is a method every signal has,
regardless of who defined it — but nothing so far has actually *defined*
one. Can project code declare a brand-new signal of its own, on a class
this project writes, and have Qt's real machinery treat it exactly the
same way — connectable, emittable, carrying real data — as a signal Qt
itself already provided?

> **Before reading on, try this:**
> - `QPushButton.clicked` always already existed by the time this
>   project's own code ever touched it. Given `Signal` is the real class
>   name PySide6 uses for a signal, what do you predict is needed to
>   make a brand-new one exist — can any class, anywhere, just write
>   `my_signal = Signal(...)` and have it work, or does declaring one
>   require something more specific about the class it's declared on?
> - `QPushButton.clicked` fires with either no data or a `checked: bool`
>   (Lesson 2.12); `QLineEdit.textChanged` hands its slot a real string.
>   Given a signal's connected slot can apparently receive real data,
>   what do you predict determines what type of data a brand-new,
>   project-defined signal is allowed to carry when it's declared?
> - Lesson 2.3 already proved `QObject` is the real base class giving
>   every widget its parent/child ownership behavior. Given `Signal` is
>   a Qt mechanism, not a plain Python one, what do you predict a class
>   needs to inherit from before it's allowed to declare a `Signal` at
>   all?

### Isolated Concept

```python
from PySide6.QtCore import QObject, Signal
from PySide6.QtWidgets import QApplication

app = QApplication([])


class Doorbell(QObject):
    pressed = Signal(str)


visits = []


def on_pressed(visitor_name):
    visits.append(f"door opened for {visitor_name}")


doorbell = Doorbell()
doorbell.pressed.connect(on_pressed)

print(visits)
print(type(doorbell.pressed))

doorbell.pressed.emit("Ada")

print(visits)
```

Run for real (`lab1_custom_signal.py`, headless):

```
[]
<class 'PySide6.QtCore.SignalInstance'>
['door opened for Ada']
```

`visits` starts empty — real, confirmed proof nothing has fired yet,
even though `doorbell.pressed.connect(on_pressed)` already ran; a
connection alone never triggers anything, the identical fact Lesson
2.11 already proved for `QPushButton.clicked`. `type(doorbell.pressed)`
reads `<class 'PySide6.QtCore.SignalInstance'>` — not `Signal`, the name
actually written in `Doorbell`'s own class body. This is called a
**`SignalInstance`**: accessing a class-level `Signal` declaration
through a real instance (`doorbell.pressed`, not `Doorbell.pressed`)
hands back a separate, real object — one specific to `doorbell` alone —
carrying the real `.connect` and `.emit` methods. `doorbell.pressed
.emit("Ada")` — real, confirmed proof, not a claim: `visits` now holds
one entry, `on_pressed` genuinely ran, and the one string `emit` was
given (`"Ada"`) arrived at `on_pressed` as its own `visitor_name`
argument, exactly matching the single `str` `Signal(str)` declared this
signal would carry.

Discarded: `Doorbell`, `on_pressed`, and `visits` exist only to prove
this mechanism in its smallest possible form. None will appear in the
Asset Manager project again — deliberately kept free of any `Asset`/
`Owner`/editor flavor, the same reasoning Lesson 2.11's own first unit
already gave for keeping its own throwaway example unrelated to the real
project.

### Mechanical Walkthrough

- **`from PySide6.QtCore import QObject, Signal`** — an import
  statement, reapplying ordinary Python import syntax; `QObject`
  reappears from Lesson 2.3, `Signal` is this lesson's own real subject,
  appearing in code for the first time.
- **`from PySide6.QtWidgets import QApplication`** and **`app =
  QApplication([])`** — reapplied, unchanged, from every lesson since
  2.1: Qt's own runtime must exist before any `QObject`-derived class is
  constructed, `Doorbell` included.
- **`class Doorbell(QObject):`** — a class declaration, reapplying
  Lesson 1.5's own subclass syntax, this time against `QObject`
  (Lesson 2.3) directly, with no `QWidget` or visible behavior anywhere
  in the chain — real, confirmed proof a class needs no visual
  representation at all to carry a real signal, only `QObject`'s own
  underlying machinery.
- **`pressed = Signal(str)`** — a class-level attribute assignment,
  reapplying ordinary Python `=` assignment; the right-hand side,
  `Signal(str)`, is a real constructor call on the `Signal` class,
  passed one type, `str` (a reappearing built-in Python type), naming
  the one value this signal will carry each time it's emitted. This
  single line *is* the entire declaration — nothing separate registers
  `pressed` with Qt afterward; assigning `Signal(...)` as a class
  attribute is itself what makes `pressed` a real, connectable,
  emittable signal the moment `Doorbell` is defined.
- **`visits = []`** — a plain list literal, reapplied general fluency
  since early in Series 1.
- **`def on_pressed(visitor_name):`** — a free function definition,
  reapplying Lesson 1.6's own free-function material; `visitor_name` is
  an ordinary parameter name, not special syntax — Qt itself decides
  what value lands here based purely on position, matching `emit`'s own
  arguments in order.
- **`visits.append(f"door opened for {visitor_name}")`** —
  `list.append`, reapplied baseline fluency, called on the value an
  f-string (`f"..."`) produces: `{visitor_name}` is evaluated and
  spliced directly into the surrounding text, replacing the whole
  `{...}` with `visitor_name`'s own real string value at the moment this
  line runs.
- **`doorbell = Doorbell()`** — constructing a real instance of
  `Doorbell`; no explicit `__init__` was written on `Doorbell` at all —
  Python falls back to `QObject`'s own inherited `__init__` (Lesson 1.5's
  own general inheritance material), which is enough here since
  `Doorbell` needs no setup beyond the class-level `Signal` declaration
  itself.
- **`doorbell.pressed.connect(on_pressed)`** — `doorbell.pressed`
  accesses the `pressed` attribute through a real instance rather than
  the class itself (`Doorbell.pressed`, never written in this lab); this
  is precisely what returns a real `SignalInstance`, this lesson's own
  new object, rather than the `Signal` class-level declaration.
  `.connect(on_pressed)` is `Signal.connect` (Lesson 2.11), reapplied
  unchanged: registers `on_pressed`, passed by name with no parentheses
  (Lesson 1.12's own first-class-function material), to be called
  automatically whenever `pressed` is emitted.
- **`print(visits)`** (first call) — reapplied `print`, confirming
  `visits` is still empty before anything has been emitted.
- **`print(type(doorbell.pressed))`** — `type()`, a reapplied built-in,
  called on the same `doorbell.pressed` expression `.connect` was just
  called on — proving directly what kind of object that expression
  actually produces.
- **`doorbell.pressed.emit("Ada")`** — `Signal.emit`, this lesson's own
  second new method: triggers `pressed`, calling every connected slot —
  here, exactly one, `on_pressed` — and passing each one the exact
  arguments given to `emit`, in order; one argument, `"Ada"`, matches
  the one `str` `Signal(str)` declared.
- **`print(visits)`** (second call) — confirms `on_pressed` genuinely
  ran exactly once, real proof the whole declare-connect-emit sequence
  works end to end.

### CS Lens

This is the same **Observer pattern** Lesson 2.11 already named for
`QPushButton.clicked` — one object (`doorbell`) maintaining a list of
interested parties (slots) and notifying each one automatically when its
own state changes, without needing to know anything about who's
listening or what they'll do — now shown from the *declaring* side
rather than the *consuming* side: this lesson's own real point is that
any project's own class can become the subject of that pattern, not only
a class Qt itself already ships. This is a hard concept, worth more than
one real-world connection.

```
Also recognized in: JavaScript's own CustomEvent, dispatched by a
project's own code rather than the browser itself, a message queue's
own publisher declaring a new topic no consumer has to know the
publisher's own internal code to subscribe to, a hardware sensor
library exposing its own "reading changed" event separately from
whatever built-in events its underlying operating system provides
```

### SE Lens

The alternative not chosen is `AssetEditor` calling straight into
`MainWindow`'s own code the moment a save happens — `MainWindow.
on_asset_submitted(...)`, called directly, hard-coded inside
`on_save_clicked` itself. The real benefit of a custom signal instead:
`AssetEditor` never needs to import `MainWindow`, know it exists, or
