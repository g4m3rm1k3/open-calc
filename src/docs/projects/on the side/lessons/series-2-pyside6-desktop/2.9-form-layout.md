## Terms used in this lesson

- **form** — new. A UI arrangement pairing each input field with its
  own caption, one per row — the specific, extremely common shape
  `QFormLayout` exists to build directly, rather than a generic
  developer hand-assembling a `QLabel` next to every field using
  `QHBoxLayout` (Lesson 2.8) repeated once per row.

## Objects and methods used

**`QFormLayout`**

- *What it is:* a real class from PySide6's `QtWidgets` module — a
  layout specifically arranging label/field pairs, one per row.
- *Implementation:* `QFormLayout(parent: QWidget | None = None)`;
  `addRow(self, label_text: str, field: QWidget) -> None`; `rowCount
  (self) -> int`; `labelForField(self, field: QWidget) -> QLabel`.
- *Its use:* `form = QFormLayout(editor)`, with three real `addRow`
  calls, is this lesson's own entire arrangement — every field's own
  caption handled by the layout itself, never a separately constructed
  `QLabel`.
- *Type:* a class, from `PySide6.QtWidgets` — itself a `QLayout`, the
  same base class `QVBoxLayout`/`QHBoxLayout` (Lesson 2.8) share.
- *Responsibility:* arrange a series of label/field pairs into rows,
  and, this lesson's own central new fact, build the label widget for
  each row automatically, from a plain string — nothing about
  validating what's typed into any field.
- *Depends on:* being constructed with, or later assigned to, a real
  widget to actually render inside.
- *Connects to:* set directly on `editor` at construction time
  (`QFormLayout(editor)`, passing the widget straight to the
  constructor, an alternative to Lesson 2.8's own separate `setLayout`
  call); every field passed to `addRow` is automatically re-parented to
  `editor`, the identical mechanism Lesson 2.8 already proved.
- *Shape:* a specialized sibling of `QVBoxLayout`/`QHBoxLayout` —
  same underlying layout machinery, purpose-built for exactly one
  common shape.

**`QFormLayout.addRow`**

- *What it is:* a real method adding one complete label/field row to a
  `QFormLayout`.
- *Implementation:* `addRow(self, label_text: str, field: QWidget) ->
  None` — internally builds a real `QLabel` from `label_text`,
  associates it with `field`, and adds both as one new row.
- *Its use:* called three times, once per field this lesson's editor
  needs — `"Name:"`, `"Serial Number:"`, `"Category:"`.
- *Type:* an instance method.
- *Responsibility:* build the row's own label, place both the label
  and the field correctly, and record the association between them —
  nothing about the field's own value or validation.
- *Depends on:* a real string for the label, and a real widget for the
  field.
- *Connects to:* the label it builds internally is retrievable
  afterward through `labelForField`, this lesson's own proof mechanism.
- *Shape:* the one method this entire lesson's real landing actually
  calls — three times, once per row.

**`QFormLayout.labelForField`**

- *What it is:* a real method retrieving the actual `QLabel` object
  `addRow` built internally for a given field.
- *Implementation:* `labelForField(self, field: QWidget) -> QLabel`.
- *Its use:* `form.labelForField(name_field).text()` proves, directly,
  that `addRow`'s own `"Name:"` string became a real, retrievable
  `QLabel`, not just decorative text with no real object behind it.
- *Type:* an instance method.
- *Responsibility:* report one fact — which real `QLabel` belongs to a
  given field — nothing about changing that association.
- *Depends on:* the field already having been added via `addRow`.
- *Connects to:* reads a real, internal object `addRow` already
  created; used only in this lesson's own verification, never in
  `asset_editor.py` itself.
- *Shape:* this lesson's own proof mechanism — the concrete, checkable
  fact behind "a form builds real labels automatically."

## Concept Unit: A Real, Automatic Label

### The Problem

Lesson 2.8's own layouts, `QVBoxLayout`/`QHBoxLayout`, arrange whatever
widgets or nested layouts are explicitly added to them — neither one
has ever built a *new* widget on a caller's behalf. Does `QFormLayout`
work the same way, requiring a separately constructed `QLabel` for
every field's own caption, or does it genuinely build that label
itself, from nothing but a plain string?

> **Before reading on, try this:**
> - `QVBoxLayout.addWidget(widget)` and `QHBoxLayout.addWidget(widget)`
>   both take an already-existing widget — Lesson 2.8 never had either
>   one build anything new. Given `QFormLayout.addRow(label_text,
>   field)`'s own first argument is a plain `str`, not a widget, what
>   do you predict happens to that string — is it stored as-is, purely
>   as text with no real object behind it, or does something more
>   happen to it?
> - If `addRow` genuinely does build a real `QLabel` internally, do you
>   predict there's a way to retrieve that exact object afterward — the
>   same way Lesson 2.3 already proved `QObject.children()` lets a
>   parent's own children be inspected directly — or is it built and
>   then effectively hidden, unreachable from outside `addRow` itself?

### Isolated Concept

```python
from PySide6.QtWidgets import QApplication, QFormLayout, QLineEdit, QWidget

app = QApplication([])

editor = QWidget()
name_field = QLineEdit()
form = QFormLayout(editor)
form.addRow("Name:", name_field)

print(form.rowCount())
print(name_field.parent() is editor)

label = form.labelForField(name_field)
print(label.text())
```

`form.rowCount()` reads `1` — real, confirmed proof one complete row
now exists. `name_field.parent() is editor` reads `True` — the
identical automatic re-parenting Lesson 2.8 already proved, now shown
for `QFormLayout` too: passing `editor` straight to `QFormLayout`'s
own constructor, rather than a separate `setLayout` call, still results
in every field ending up parented to `editor` correctly. The final two
lines answer this unit's own real question directly: `form
.labelForField(name_field)` returns a real object — not `None`, not an
error — and `label.text()` reads back exactly `"Name:"`, the plain
string originally passed to `addRow`. Real, confirmed proof, not a
claim: `QFormLayout` genuinely builds a real, independently retrievable
`QLabel` from nothing but a string, something neither `QVBoxLayout` nor
`QHBoxLayout` has ever done.

Discarded: `editor`/`name_field`/`form` exist only to prove this
mechanism. Neither will appear in the Asset Manager project again in

### CS Lens

This is a **factory method embedded in a configuration call** — a
single method call (`addRow`) that both configures an arrangement
*and* constructs a new object (the label) needed to do so, rather than
requiring the caller to construct that object separately first. This is
a hard concept, worth more than one real-world connection.

```
Also recognized in: an ORM's own migration builder, where
add_column("name", type=String) constructs the real underlying schema
object from a plain description rather than requiring a pre-built
column object, a UI form builder library generating a real label
element from a plain field name, a build system's own dependency
declaration syntax constructing a real target object from a short,
declarative line
```

### SE Lens

The alternative not chosen is `QVBoxLayout`/`QHBoxLayout`'s own,
already-familiar shape: constructing a separate `QLabel` by hand for
every field, then arranging label and field together with a nested
`QHBoxLayout` per row — exactly the manual pattern this lesson's own
header names directly. The real benefit of `QFormLayout` instead,
proven directly above: one line, `addRow("Name:", name_field)`,
replaces what would otherwise be three or four separate lines per
field, with real, consistent alignment across every row handled by the
layout itself — at the real cost of losing some fine-grained control a
fully manual, per-row `QHBoxLayout` would still offer.

### The New Code

```python
def build_asset_editor() -> QWidget:
    editor = QWidget()
    editor.setWindowTitle("Asset Editor")

    name_field = QLineEdit()
    serial_number_field = QLineEdit()
    category_field = QComboBox()
    category_field.addItems(["Laptop", "Monitor", "Keyboard", "Mouse", "Other"])

    form = QFormLayout(editor)
    form.addRow("Name:", name_field)
    form.addRow("Serial Number:", serial_number_field)
    form.addRow("Category:", category_field)

    return editor
```
