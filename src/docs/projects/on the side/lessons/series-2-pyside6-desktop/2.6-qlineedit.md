# Lesson 2.6: QLineEdit

**What you will build.** `asset_manager/desktop/main.py` gains a
`QLineEdit` — this project's first widget genuinely built to hold
editable content, not just display fixed text (`QLabel`) or wait to be
clicked (`QPushButton`). Given a placeholder, "Search assets...", it's
parented and shown the identical way every widget since Lesson 2.4 has
been. Nothing reads its actual text yet — the same "component before
integration" boundary Lesson 2.5 already drew for `QPushButton.clicked`
applies here too, for the identical reason: reacting to typed input is
still signal/slot territory, Lesson 2.11's own subject. The
transferable problem: a `QLabel`'s text is something the *program*
decides; a `QLineEdit`'s text is something the *user* decides — the
same `text()`/`setText()`-shaped API Lesson 2.4 already used, now
sitting on top of a widget whose entire purpose is letting someone
else change that value, not just read it.

**What you need to know first.** Lesson 2.5 — `QPushButton`, and the
`main()` structure this lesson modifies directly. Lesson 2.4 —
`QLabel.text()`, directly contrasted below against `QLineEdit`'s own,
genuinely different relationship to its own text.

**Scope note.** Same boundary Lesson 2.5 already drew for `QPushButton
.clicked`: this lesson does not connect any of `QLineEdit`'s own
signals (`textChanged`, `returnPressed`, neither used here) to
anything. Reacting to typed input, the same way reacting to a click
does, is real, load-bearing content this lesson leaves entirely to
Lesson 2.11.

## Objects and methods used

**`QLineEdit`**

- *What it is:* a real class from PySide6's `QtWidgets` module — a
  single-line, user-editable text input widget.
- *Implementation:* `QLineEdit(parent: QWidget | None = None)` — a
  constructor accepting only a parent, no initial text (unlike
  `QLabel`/`QPushButton`, both of which take their own text as their
  first argument); `text(self) -> str`; `setText(self, text: str) ->
  None`; `setPlaceholderText(self, text: str) -> None`;
  `placeholderText(self) -> str`.
- *Its use:* `search_box = QLineEdit(window)`, given a placeholder via
  `setPlaceholderText`, is this project's first real, permanent widget
  meant to hold a value someone *else* — a user, not this program's own
  code — decides.
- *Type:* a class, from `PySide6.QtWidgets` — a `QWidget`, the same
  ancestry `QLabel` and `QPushButton` both already have.
- *Responsibility:* accept and display typed text, and separately,
  display placeholder text only while its own real text is empty —
  nothing about validating or reacting to what's typed, both left to
  later lessons.
- *Depends on:* nothing beyond a parent to construct one; `setText`/
  `setPlaceholderText` are both optional, called after construction.
- *Connects to:* parented to `window` inside `main()`, the identical
  relationship every widget since Lesson 2.4 has had.
- *Shape:* this project's first widget whose real, current value can
  genuinely change from outside this program's own code — a real,
  new fact none of `QLabel`/`QPushButton` share.

**`QLineEdit.setPlaceholderText`** *(and its read side,*
*`placeholderText`)*

- *What it is:* a real pair of methods controlling text shown only
  while a `QLineEdit`'s own real text is empty.
- *Implementation:* `setPlaceholderText(self, text: str) -> None`;
  `placeholderText(self) -> str`.
- *Its use:* `search_box.setPlaceholderText("Search assets...")` gives
  an empty search box a real, visible hint about its own purpose,
  without that hint ever counting as real, typed content.
- *Type:* an instance method pair.
- *Responsibility:* store and report one specific string, shown by Qt
  itself only under one specific condition (the field being empty) —
  nothing about validating or affecting the field's own real text.
- *Depends on:* the widget already existing.
- *Connects to:* read by Qt's own rendering code whenever this widget
  is drawn with no real text of its own; unaffected by `setText`
  being called afterward, this lesson's own proof shows directly.
- *Shape:* a small, cosmetic configuration call, mechanically similar
  to `setWindowTitle` (Lesson 2.1) — set once, read automatically by
  Qt's own rendering, never called again by this project's own code.

## Concept Unit: Editable, Placeholder-Backed Text

### The Problem

`QLabel.text()` (Lesson 2.4) only ever reports whatever this project's
own code last set it to — nothing about a `QLabel` lets a user change
it directly. Does `QLineEdit` genuinely work differently — is its own
`text()` something that can hold real, separate, user-relevant content,
and is there a real, distinct way to show a hint before anything has
been typed at all, without that hint ever being mistaken for real
input?

> **Before reading on, try this:**
> - `QLabel("some text", parent)` and `QPushButton("some text", parent)`
>   both take their own text as the constructor's first argument.
>   `QLineEdit(parent)`, per this lesson's own header, does not. Given a
>   search box should usually start out empty — nothing typed into it
>   yet — what do you predict `search_box.text()` returns immediately
>   after construction, before anything else is called on it?
> - If a `QLineEdit` shows placeholder text — "Search assets..." — only
>   while it's genuinely empty, do you predict that placeholder is
>   itself stored *as* the field's own real text (so `text()` would
>   return it), or is it tracked completely separately, never appearing
>   in `text()` at all, even while it's the only thing visibly shown?
> - After real text is typed (or set programmatically) into a
>   `QLineEdit` that has a placeholder, do you predict the placeholder
>   itself is discarded — forgotten — or does it silently remain set,
>   simply not shown anymore while real text is present?

### Isolated Concept

This is exactly what `main.py`'s own two new lines depend on — proven
across every state this lesson's Socratic questions asked about:

```python
from PySide6.QtWidgets import QApplication, QLineEdit, QMainWindow

app = QApplication([])

window = QMainWindow()
search_box = QLineEdit(window)
search_box.setPlaceholderText("Search assets...")

print(repr(search_box.text()))
print(search_box.placeholderText())

search_box.setText("ThinkPad")
print(search_box.text())
print(search_box.placeholderText())
```

Run for real (`lab1_qlineedit.py`, headless):

```
''
Search assets...
ThinkPad
Search assets...
```

`repr(search_box.text())` — `repr()`, reapplied in full from Lesson
1.7 — prints `''`, the empty string, real, confirmed proof that a
fresh `QLineEdit` starts with genuinely empty real text, even while its
own `placeholderText()`, checked on the very next line, already reports
`"Search assets..."`. The two are proven, directly, to be entirely
separate facts: an empty `text()` and a real, non-empty
`placeholderText()`, coexisting, neither one containing the other's
value. `search_box.setText("ThinkPad")` sets real text for the first
time; `search_box.text()`, read again, now returns `"ThinkPad"` exactly
— real, confirmed proof `QLineEdit`'s own text genuinely can be changed
after construction, the fact that most distinguishes it from `QLabel`.
The final line, `search_box.placeholderText()`, still reads `"Search
assets..."`, completely unchanged — real, confirmed proof the
placeholder was never discarded by setting real text; it simply stops
being *shown*, per Qt's own rendering rule, the instant real text
exists, without the underlying value itself ever being touched.

Discarded: this isolated proof exists only to demonstrate the mechanics
already landed for real above. `search_box`, in `main.py` itself, is
not discarded — it's the real, permanent widget this unit's own Project
Change already landed.

### CS Lens

This is a **placeholder value** — a real UI pattern where a hint is
shown only in the *absence* of real data, tracked as a genuinely
separate fact from the data itself rather than as a fake default value
that would be indistinguishable from something a user actually typed.
This is a hard concept, worth more than one real-world connection.

```
Also recognized in: an HTML <input placeholder="..."> attribute — the
identical idea, same name, a different framework, a form field showing
greyed-out example text ("MM/DD/YYYY") that vanishes the instant real
input begins, a search engine's own greyed-out "Search..." text in its
own search bar, present in nearly every real application this project's
own reader has ever used
```

### SE Lens

The alternative not chosen is using a fake *default* value as the
placeholder instead — pre-filling `search_box`'s own real text with
`"Search assets..."` and clearing it manually the moment the field
gains focus. The real, honest cost of that alternative: a user who
tabs past the field without typing anything, or a program that reads
`text()` before the field is ever focused, would see or receive that
fake default as if it were genuine input — exactly the ambiguity a
real, separately-tracked placeholder avoids entirely, proven directly
by this unit's own final line showing the two values never once
collide.
