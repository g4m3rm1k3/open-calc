## Terms used in this lesson

- **Model/View architecture** — new. A real design split, general
  across all of Qt, between the object holding data (a **model**) and
  the object presenting it on screen (a **view**) — exists so the
  identical data can be shown different ways (a table, a list, a tree)
  without duplicating it, and so a view never needs its own separate
  copy of what it displays.

## Objects and methods used

**`QStandardItemModel`**

- *What it is:* a real class from PySide6's `QtGui` module — a
  concrete, ready-to-use model, holding a real, general-purpose grid of
  items; unlike a model this project writes itself (Lesson 2.20's own
  real subject), it needs no custom code at all to hold and report
  data — just real items, added directly.
- *Implementation:* `QStandardItemModel(rows: int, columns: int, parent:
  QObject | None = None)`; `setHorizontalHeaderLabels(self, labels:
  list[str]) -> None`; `appendRow(self, items: list[QStandardItem]) ->
  None`; `rowCount(self) -> int`; `columnCount(self) -> int`.
- *Its use:* `self.assets_model = QStandardItemModel(0, 3, self)`, this
  lesson's own real, central object — zero rows, three columns, one per
  `Asset` field this lesson's own table shows.
- *Type:* a class, from `PySide6.QtGui` — a real `QAbstractItemModel`
  subclass, the same real base class every Qt model, including Lesson
  2.20's own custom one, ultimately shares.
- *Responsibility:* hold an ordered grid of real items, and report its
  own current size and contents to anything that asks — nothing about
  how that grid is actually drawn on screen; that's `QTableView`'s own
  entire job.
- *Depends on:* nothing beyond an initial row/column count, which can
  be zero.
- *Connects to:* handed to `QTableView.setModel` (below); every row
  added via `appendRow` is immediately, automatically reflected by any
  view currently displaying this model — no manual redraw call
  anywhere in this lesson's own code.
- *Shape:* this lesson's own real, honest stand-in for the model
  `QAbstractTableModel` (2.20) will eventually replace — real and
  working now, not a placeholder that does nothing.

**`QStandardItem`**

- *What it is:* a real class from PySide6's `QtGui` module — one real
  cell's worth of data, held inside a `QStandardItemModel`.
- *Implementation:* `QStandardItem(text: str)` — stores `text` as this
  item's own displayable value.
- *Its use:* `QStandardItem(asset.name)`, `QStandardItem(asset
  .serial_number)`, `QStandardItem(asset.category)`, three real items
  built directly from `Asset`'s own real fields (1.7) each time a real
  asset is submitted successfully.
- *Type:* a class, from `PySide6.QtGui`.
- *Responsibility:* hold exactly one cell's own real value — nothing
  about which row or column it ends up in; that's decided entirely by
  the order it's added in.
- *Depends on:* a real string to display.
- *Connects to:* three of them, together, form one real row, added via
  `QStandardItemModel.appendRow`.
- *Shape:* the smallest real unit of data this lesson's own model
  actually stores.

**`QTableView`** *(and* `QTableView.setModel`*)*

- *What it is:* a real class from PySide6's `QtWidgets` module — a
  widget that displays a real model's own data as rows and columns;
  `setModel` is the real method connecting a view to the model it
  should display.
- *Implementation:* `QTableView(parent: QWidget | None = None)`;
  `setModel(self, model: QAbstractItemModel | None) -> None`; `model
  (self) -> QAbstractItemModel | None`.
- *Its use:* `self.assets_table = QTableView()`, followed by
  `self.assets_table.setModel(self.assets_model)`, this lesson's own
  real, central wiring.
- *Type:* a class, from `PySide6.QtWidgets` — a `QWidget`, the same
  ancestry every widget in this project shares.
- *Responsibility:* draw whatever real data its own model currently
  reports — every row, every column, every header label — and nothing
  about storing any of that data itself; a `QTableView` with no model
  set displays nothing at all, by design.
- *Depends on:* a real model, set via `setModel`, to have anything to
  show.
- *Connects to:* reads `rowCount()`, `columnCount()`, and each cell's
  own data directly from whatever model is currently set — this
  lesson's own `self.assets_model`.
- *Shape:* the real "View" half of this lesson's own Model/View split —
  this project's first real use of that architecture.

**`QAbstractItemModel.rowCount`** *(and* `columnCount`*,* `index`*,*
`QModelIndex.data`*,* `headerData`*)*

- *What it is:* a real method family every Qt model, including
  `QStandardItemModel`, carries — reports the model's own current size
  and contents.
- *Implementation:* `rowCount(self) -> int`; `columnCount(self) ->
  int`; `index(self, row: int, column: int) -> QModelIndex` — a real,
  lightweight reference to one specific cell, not the value itself;
  `QModelIndex.data(self, role: int = Qt.ItemDataRole.DisplayRole) ->
  object` — reads the actual value at that cell; `headerData(self,
  section: int, orientation: Qt.Orientation, role: int = Qt
  .ItemDataRole.DisplayRole) -> object` — reads back a column or row's
  own label.
- *Its use:* `model.rowCount()`, `model.index(0, 0).data()`, and
  `model.headerData(0, Qt.Orientation.Horizontal)`, throughout this
  lesson's own verification — the concrete way a headless script
  confirms the model's own real, current contents without a real,
  rendered table ever needing to be visible on screen.
- *Type:* an instance method family, on `QAbstractItemModel` — real,
  inherited, working methods `QStandardItemModel` already implements in
  full; the identical method names Lesson 2.20's own custom model will
  have to implement itself, from scratch.
- *Responsibility:* answer, on demand, exactly how large the model
  currently is and what each cell currently holds — nothing about
  deciding when that data changes; that's `appendRow` and similar real
  methods' own job.
- *Depends on:* a real, valid row/column (or section) to ask about.
- *Connects to:* called internally by `QTableView` itself, every time
  it needs to draw or redraw; called directly by this lesson's own
  verification code for the identical real answer, with no rendering
  involved.
- *Shape:* the real, standard interface every Qt model shares — proof
  that `QStandardItemModel` and Lesson 2.20's own custom model are
  interchangeable from any view's own point of view, so long as both
  implement this same real method family.

## Concept Unit: The Model/View Split

### The Problem

Every widget this project has ever built has held its own data directly
— a `QLineEdit`'s own typed text (2.6), a `QComboBox`'s own item list
(2.7). Can a table instead *never* hold its own data at all, reading
everything it displays from a completely separate object — and if
`Asset` (1.7) already exists as real data this project's own editor
already produces, does that separate object need to know anything about
`Asset` specifically to hold it?

> **Before reading on, try this:**
> - `QComboBox.addItems` (2.7) stores its own item list directly inside
>   the widget itself. Given a `QTableView`, by contrast, is described
>   as never storing its own data, what do you predict happens if you
>   construct a real `QTableView` and never give it a model at all —
>   does it show a real, empty grid, or something else?
> - `QStandardItemModel` is described as general-purpose, not written
>   specifically for this project's own `Asset` data. Given it still
>   needs to hold three real values per row (`name`, `serial_number`,
>   `category`), what do you predict `QStandardItem`'s own real job is —
>   does it know it's holding an `Asset`'s own field, or does it only
>   know it's holding one plain, displayable value?

### CS Lens

This is the **Model/View pattern** — separating the storage and
management of data (the model) from its visual presentation (the
view), so either can change independently and more than one view can
present the identical data at once. This is a hard concept, worth more
than one real-world connection.

```
Also recognized in: a spreadsheet application's own underlying cell
data versus its on-screen rendering, a database's own stored rows
versus a report generator reading them, a web framework's own
data layer versus the templates that render it, a music player's own
playlist data versus a shuffled or sorted view of the identical
underlying list
```

### SE Lens

The alternative not chosen — named directly by the blueprint's own
"don't start with `QTableWidget` as your primary architecture" — is
`QTableWidget`, a real, simpler PySide6 class that manages its own
internal item storage directly, with no separate model object at all,
much like `QComboBox`'s own item list (2.7). The real reason that
doesn't fit this project: `self.submitted_assets` (2.15) already *is*
this project's own real data, living on `MainWindow`; a `QTableWidget`
would force that same data to exist a second time, copied into the
widget's own internal storage, with no single source of truth and a
real, ongoing risk of the two silently drifting apart. `QStandardItemModel`,
by contrast, is a real, separate object this project's own code fills
directly from the same `Asset` values already flowing through `on_asset
_submitted` — one real copy, one real place data enters this project's
own UI.

1. **The Model/View split.** A real `QStandardItemModel`, holding
   three real `QStandardItem`s per row, proved a model can hold data
   with no awareness of what it represents — `table.model() is model`
   confirming a view reads a model strictly by reference, never a copy.
2. **A real table of submitted assets.** `self.assets_model`
   (`QStandardItemModel`) and `self.assets_table` (`QTableView`) land
   permanently inside `MainWindow`; `on_asset_submitted`'s own new
   lines mirror every successfully validated `Asset` into the model —
   `rowCount()` growing from `0` to `1` on a real, valid submission,
   staying at `1` on a real, rejected one.

This project's own real, growing list of assets finally has somewhere
to be seen — not yet reading `list[Asset]` directly, an honest,
temporary duplication Lesson 2.20's own real, custom model removes for
good.
