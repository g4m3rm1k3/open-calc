## Objects and methods used

**`QAbstractTableModel`**

- *What it is:* a real, abstract base class from PySide6's `QtCore`
  module — the real class every custom, two-dimensional (row/column)
  Qt model is expected to subclass; provides no working data storage of
  its own at all, unlike `QStandardItemModel` (2.19), which is
  ready-to-use out of the box.
- *Implementation:* `QAbstractTableModel(parent: QObject | None =
  None)` — a real constructor, but the class itself does nothing useful
  until `rowCount`, `columnCount`, and `data` are overridden by a real
  subclass; leaving any of the three unoverridden means that method
  simply returns its own default (`0` for the two counts, `None` for
  `data`), not an error.
- *Its use:* `class AssetTableModel(QAbstractTableModel):`, this
  lesson's own real, central subclass — the first time this project has
  ever subclassed a Qt model class directly, rather than using a
  ready-made one.
- *Type:* a class, from `PySide6.QtCore` — a real `QAbstractItemModel`
  subclass (2.19), specialized for exactly two-dimensional, table-shaped
  data; a `QObject` (2.3), not a `QWidget` — a model, like `QAction`
  (2.17), has no visual appearance of its own.
- *Responsibility:* define the real, required contract every table
  model must fulfill (`rowCount`, `columnCount`, `data`, at minimum) —
  nothing about *how* a subclass actually stores or produces its own
  data; that's entirely `AssetTableModel`'s own job.
- *Depends on:* a real subclass providing real implementations of its
  own required methods; a `QObject` parent, optionally, at construction.
- *Connects to:* `QTableView` (2.19) calls this class's own real,
  overridden methods directly, every time it needs to know the model's
  current size or contents — the identical real calling pattern 2.19's
  own `QStandardItemModel` already received, now answered by hand-
  written code instead of Qt's own built-in storage.
- *Shape:* the real base every custom Qt table model in this project
  will ever build on — this lesson's own real subject.

**`QAbstractTableModel.rowCount`** *(and* `columnCount`*)*

- *What it is:* two real methods every `QAbstractTableModel` subclass
  is expected to override — report the model's own current size.
- *Implementation:* `rowCount(self, parent: QModelIndex = QModelIndex())
  -> int`; `columnCount(self, parent: QModelIndex = QModelIndex()) ->
  int` — both take an optional `parent` parameter (relevant for tree-
  shaped models, not this lesson's own flat, table-shaped one) that
  this lesson's own code never actually uses.
- *Its use:* `return len(self._assets)` and `return len(self
  .COLUMN_HEADERS)`, this lesson's own real, complete implementations —
  computed live, every single call, never cached or stored separately.
- *Type:* instance methods, overridden on `AssetTableModel`.
- *Responsibility:* answer, correctly, right now, how many rows and
  columns this model currently holds — nothing about *why* that number
  might have changed since the last call; that's `beginInsertRows`/
  `endInsertRows`'s own job, below.
- *Depends on:* `self._assets`, this lesson's own real, shared
  reference to `MainWindow.submitted_assets` (2.15), already existing
  and correctly populated.
- *Connects to:* called by `QTableView` (2.19) every time it needs to
  know how large a grid to draw; called directly by this lesson's own
  verification code for the identical real answer.
- *Shape:* the real, minimal size-reporting half of this lesson's own
  model — reused, unchanged in kind, from `QAbstractItemModel`'s own
  real method family (2.19), now implemented by hand instead of
  inherited pre-built.

**`QAbstractTableModel.data`**

- *What it is:* a real method every `QAbstractTableModel` subclass is
  expected to override — reports the actual value at one specific cell.
- *Implementation:* `data(self, index: QModelIndex, role: int = Qt
  .ItemDataRole.DisplayRole) -> object` — `index.row()`/`index.column()`
  (2.19) name which cell is being asked about; `role`, a real enum
  member from `Qt.ItemDataRole`, names *what kind* of value is being
  requested — `DisplayRole`, the one this lesson's own code actually
  handles, means "the plain text to show"; every other real role
  (`Qt.ItemDataRole.EditRole`, `Qt.ItemDataRole.ToolTipRole`, and
  several others, none used by this lesson) asks for something
  different `QTableView` might separately request.
- *Its use:* this lesson's own real, central method — reads `self
  ._assets[index.row()]`, then returns exactly one of that `Asset`'s
  own three real fields (1.7), chosen by `index.column()`.
- *Type:* an instance method, overridden on `AssetTableModel`.
- *Responsibility:* answer, correctly, what one specific cell currently
  holds, for one specific kind of request (`role`) — explicitly
  returning `None` for every role this lesson's own code doesn't
  handle, rather than guessing or returning the wrong kind of value.
- *Depends on:* a real, valid `QModelIndex` naming a row and column
  that actually exist in `self._assets`.
- *Connects to:* called by `QTableView` once per visible cell, every
  time it redraws; reads directly from `self._assets`, the same shared
  list `MainWindow.submitted_assets` (2.15) is.
- *Shape:* the real, per-cell half of this lesson's own model — the
  method that makes `Asset`'s own real fields (1.7) actually appear,
  correctly, in a real, visible grid.

**`QAbstractTableModel.headerData`**

- *What it is:* a real method every `QAbstractTableModel` subclass may
  override — reports a column's (or row's) own label.
- *Implementation:* `headerData(self, section: int, orientation: Qt
  .Orientation, role: int = Qt.ItemDataRole.DisplayRole) -> object` —
  `orientation` (`Qt.Orientation.Horizontal` for column headers,
  `Qt.Orientation.Vertical` for row headers) reapplied unchanged from
  Lesson 2.19.
- *Its use:* `return self.COLUMN_HEADERS[section]`, when `orientation`
  is `Horizontal` and `role` is `DisplayRole` — this lesson's own real
  implementation, replacing `QStandardItemModel.setHorizontalHeaderLabels`
  (2.19), which this project no longer calls at all.
- *Type:* an instance method, overridden on `AssetTableModel`.
- *Responsibility:* answer one column's own real label — nothing about
  row headers, which this lesson's own code deliberately leaves
  unimplemented (returning `None`, the real, harmless default),
  since `QTableView` (2.19) already shows plain row numbers on its own.
- *Depends on:* `self.COLUMN_HEADERS`, a real, fixed, class-level list
  this lesson's own code defines.
- *Connects to:* called by `QTableView` once per column, whenever
  headers need to be drawn.
- *Shape:* the real, optional counterpart to `data` — labels, rather
  than values.

**`QAbstractItemModel.beginInsertRows`** *(and* `endInsertRows`*)*

- *What it is:* a real method pair every Qt model, including
  `QAbstractTableModel`, carries — the real, required way to tell every
  view currently displaying this model that new rows are about to
  appear (or have just finished appearing).
- *Implementation:* `beginInsertRows(self, parent: QModelIndex, first:
  int, last: int) -> None`, called immediately *before* the underlying
  data actually changes; `endInsertRows(self) -> None`, called
  immediately *after* — `first`/`last` name the real row-index range
  about to be inserted (`first == last` for inserting exactly one row).
- *Its use:* `self.beginInsertRows(QModelIndex(), row, row)`, then
  `self._assets.append(asset)`, then `self.endInsertRows()`, this
  lesson's own real, central sequence, inside `AssetTableModel
  .add_asset`.
- *Type:* an instance method pair, on `QAbstractItemModel` — inherited,
  not overridden; called, not implemented, by this lesson's own code.
- *Responsibility:* announce, precisely, which real rows are being
  added, and exactly when the addition is complete — nothing about
  actually performing the addition itself, which is entirely
  `add_asset`'s own job, sitting between the two calls.
- *Depends on:* being called in matched pairs, with the actual data
  change happening strictly between them — real, confirmed proof, this
  lesson's own verification, that skipping this pair entirely leaves
  the model's own reported size correct but silently never announces
  the change at all.
- *Connects to:* internally emits `rowsInserted`, a real signal
  (Lesson 2.11's own general material) every view listens for; a real
  `QTableView` (2.19) redraws itself the instant that signal fires —
  this lesson's own verification connects to it directly instead, since
  no real rendering is possible headless.
- *Shape:* the real, explicit bridge between "the underlying Python
  data changed" and "every view watching this model knows about it" —
  without it, a plain Python list's own `.append()` is invisible to Qt
  entirely.

## Concept Unit: Reading Data Live, Not Storing a Copy

### The Problem

`QStandardItemModel` (2.19) stores its own real `QStandardItem`s
internally — completely separate from `self.submitted_assets` (2.15),
the real `list[Asset]` this project's own domain layer actually
produces. Can a model instead read every value it reports directly from
that existing list, live, on every single call, storing nothing of its
own at all?

>   do you predict it needs to do with `index.column()` to decide which
>   one of those three fields to actually return?

```python
from dataclasses import dataclass

from PySide6.QtCore import QAbstractTableModel, QModelIndex, Qt
from PySide6.QtWidgets import QApplication, QTableView

app = QApplication([])


@dataclass
class FakeAsset:
    name: str
    serial_number: str
    category: str


class AssetTableModel(QAbstractTableModel):
    COLUMN_HEADERS = ["Name", "Serial Number", "Category"]

    def __init__(self, assets, parent=None):
        super().__init__(parent)
        self._assets = assets

    def rowCount(self, parent=QModelIndex()):
        return len(self._assets)

    def columnCount(self, parent=QModelIndex()):
        return len(self.COLUMN_HEADERS)

    def data(self, index, role=Qt.ItemDataRole.DisplayRole):
        if role != Qt.ItemDataRole.DisplayRole:
            return None
        asset = self._assets[index.row()]
        column = index.column()
        if column == 0:
            return asset.name
        if column == 1:
            return asset.serial_number
        if column == 2:
            return asset.category
        return None

    def headerData(self, section, orientation, role=Qt.ItemDataRole.DisplayRole):
        if role != Qt.ItemDataRole.DisplayRole:
            return None
        if orientation == Qt.Orientation.Horizontal:
            return self.COLUMN_HEADERS[section]
        return None


assets = [FakeAsset("ThinkPad X1", "SN-001", "Laptop")]
model = AssetTableModel(assets)
table = QTableView()
table.setModel(model)

print(model.rowCount())
print(model.columnCount())
print(model.headerData(1, Qt.Orientation.Horizontal))
print(model.index(0, 0).data())
print(model.index(0, 1).data())
print(model.index(0, 2).data())

assets.append(FakeAsset("Dell Monitor", "SN-002", "Monitor"))
print(model.rowCount())
print(model.index(1, 0).data())
```

`model.index(0, 2).data()` read `"ThinkPad X1"`, `"SN-001"`, `"Laptop"`
— real, confirmed proof answering this unit's own second Socratic
question: `data`'s own `index.column()` check (`0`, `1`, `2`) picks out

### CS Lens

This is a **live/computed view over existing data**, rather than a
**cached, duplicated copy** — the same underlying tradeoff a database
view (computing its own rows from other real tables, on every query,
rather than storing a separate copy) makes, and the same one Lesson
1.10's own `display_name` `@property` already made, computing a value
fresh from `Asset`'s own real fields rather than storing it separately.
This is a hard concept, worth more than one real-world connection.

```
Also recognized in: a spreadsheet's own computed cell, re-evaluating a

result, a web page's own reactive UI framework re-rendering directly

```

### SE Lens

The alternative not chosen is exactly Lesson 2.19's own real,
temporary design: a model that stores its own separate copy
(`QStandardItem`s), requiring every real change to be applied twice —
once to the real domain data, once to the model's own mirror of it.
The real benefit of reading live instead: there is structurally no way

rendering happens headless regardless), but a real, on-screen
`QTableView` genuinely would not update after this exact sequence,
without something more. The next unit supplies that something.

from dataclasses import dataclass

from PySide6.QtCore import QAbstractTableModel, QModelIndex, Qt
from PySide6.QtWidgets import QApplication

app = QApplication([])


@dataclass
class FakeAsset:
    name: str
    serial_number: str
    category: str


class AssetTableModel(QAbstractTableModel):
    def __init__(self, assets, parent=None):
        super().__init__(parent)
        self._assets = assets

    def rowCount(self, parent=QModelIndex()):
        return len(self._assets)

    def columnCount(self, parent=QModelIndex()):
        return 3

    def data(self, index, role=Qt.ItemDataRole.DisplayRole):
        return None

    def add_asset(self, asset):
        row = len(self._assets)
        self.beginInsertRows(QModelIndex(), row, row)
        self._assets.append(asset)
        self.endInsertRows()
