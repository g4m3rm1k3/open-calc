# Lesson 2.26: Application State

**What you will build.** `MainWindow.__init__` (2.1 onward) has quietly
accumulated four real `self.` attributes holding this project's own
state directly: `self.submitted_assets` (2.15, the real, live list every
other part of this project reads from), `self.validation_errors` (2.15,
a plain, ever-growing list of rejected submissions), `self
.current_search_text` (2.12, a tracked copy of the search box's own
text), and `self.editor` (2.11, a reference to whichever `AssetEditor`
dialog is currently open). Nothing about *how* they're declared marks
any real difference between them — all four read as identical lines.
This lesson removes one of them outright (`self.current_search_text`,
now a dead, duplicated copy of state `AssetFilterProxyModel`, 2.24,
already owns for real), and extracts the other two domain-adjacent
attributes (`self.submitted_assets`, `self.validation_errors`) into a
new, dedicated `ApplicationState` object `MainWindow` merely holds a
reference to — leaving only `self.editor`, genuine UI-lifetime state,
directly on `MainWindow` itself. The transferable problem: a widget
class that keeps accumulating real, unrelated state as bare `self.`
attributes is quietly becoming its own project's database, with no seam
marking where "this widget's job" ends and "this project's real data"
begins.

**What you need to know first.** Lesson 2.6, 2.12 — `self.search_box`,
`self.current_search_text`; this lesson deletes the latter outright.
Lesson 2.24 — `AssetFilterProxyModel`, `self._search_text`; the real,
already-existing, sole owner this lesson's first unit points to. Lesson
2.15 — `self.submitted_assets`, `self.validation_errors`,
`PLACEHOLDER_OWNER`, `InvalidAssetError`; both lists move house in this
lesson's second unit, unchanged in every other way. Lesson 2.20 —
`AssetTableModel`'s own real, confirmed contract: whatever list object
is handed to its constructor is the one it reads from, forever, by
reference, never a copy; this lesson's second unit depends on that
contract still holding once the list's real home changes. Lesson 2.11 —
`self.editor`; real UI-lifetime state, staying exactly where it already
is, used throughout this lesson as the contrasting example of what
*doesn't* move.

## Objects and methods used

**`ApplicationState`**

- *What it is:* a real, brand-new, plain Python class this lesson
  creates — a dedicated container holding this project's own
  domain-adjacent state, separate from any Qt widget.
- *Implementation:* `ApplicationState(self) -> None` — no constructor
  arguments; sets `self.assets: list[Asset] = []` and `self
  .validation_errors: list[InvalidAssetError] = []`, nothing else.
- *Its use:* `MainWindow.__init__` builds exactly one `self.state =
  ApplicationState()`, then hands `self.state.assets` — not a separate
  `self.submitted_assets` list — to `AssetTableModel` (2.20) at
  construction time.
- *Type:* a class — a plain Python class, not a `QObject` subclass,
  unlike almost everything else in `desktop/`. It holds no widget, no
  signal, no Qt import at all.
- *Responsibility:* own this project's real domain-adjacent data — the
  live list of submitted `Asset` (1.7) objects, and the list of rejected
  validation attempts — answerable for exactly that, and nothing about
  *how* or *when* either list changes; every mutation still happens from
  `MainWindow`'s own methods, reaching in through `self.state`.
- *Depends on:* nothing — constructed with no arguments, needing
  nothing handed to it.
- *Connects to:* constructed once, by `MainWindow.__init__`; `self.state
  .assets` is handed by reference to `AssetTableModel.__init__` (2.20),
  which stores that exact list object, never a copy — the identical
  single-reference contract 2.20 already proved, now with
  `ApplicationState` sitting between `MainWindow` and the model instead
  of a bare `self.` list; `self.state.validation_errors` is appended to
  directly from `on_asset_submitted`.
- *Shape:* a real, small, new architectural seam — not a widget, not a
  Qt class — sitting between `MainWindow` (real UI) and the data that
  used to live directly on it; the first object inside `desktop/` that
  exists purely to hold domain-adjacent state, not to display or manage
  anything on screen.

### Isolated Concept

This is exactly what the two real deletions above are correcting,
isolated down to its smallest possible shape:

```python
class Radio:
    def __init__(self):
        self.volume = 5

    def set_volume(self, value):
        self.volume = value


class VolumeDisplay:
    def __init__(self, radio):
        self.radio = radio
        self.shown_volume = radio.volume  # a copy, taken once

    def bump_volume(self, amount):
        self.radio.set_volume(self.radio.volume + amount)
        self.shown_volume = self.radio.volume  # kept in sync, but only here


radio = Radio()
display = VolumeDisplay(radio)
print(display.shown_volume)

display.bump_volume(3)
print(display.shown_volume, radio.volume)

radio.set_volume(1)
print(display.shown_volume, radio.volume)
```

Stated from confidence, not executed — plain attribute assignment and a
plain method call, nothing platform- or framework-dependent, nothing
whose exact shape is in doubt: `5`, then `8 8`, then `8 1`.
`display.shown_volume` starts as a real copy of `radio.volume`, taken
once inside `__init__`. `display.bump_volume(3)` changes `radio.volume`
*and* `display.shown_volume` together, since `bump_volume` updates both
by hand — this is exactly the shape `self.current_search_text` and
`self.proxy_model._search_text` are in today, both changed together
inside `on_search_text_changed`, which is precisely why they've never
yet visibly disagreed. But `radio.set_volume(1)`, called directly —
a second, real path to change `radio.volume` that doesn't go through
`bump_volume` at all — leaves `display.shown_volume` at its old value,
`8`, while `radio.volume` is now `1`. Nothing raised an error; the copy
just silently stopped being true. This is the general problem of
**redundant state**: the same real fact, tracked in two separate places,
staying correct only for as long as every writer remembers to update
both copies. The fix that generalizes: give a fact exactly one real,
authoritative owner — here, `radio.volume` — and have every other reader
hold a *reference* to that owner (`display.radio`) instead of a private
copy of its current value. This is called the **single source of
truth** principle. `main.py`'s own real case turns out to be an even
simpler version of it: `self.current_search_text` isn't a copy that
*could* eventually drift — it's a copy nothing ever reads back at all,
confirmed directly in this unit's own first Socratic question. The
real, authoritative owner already exists, `self.proxy_model`; the fix
isn't adding a reference, it's deleting the redundant copy outright.

Discarded: `Radio`, `VolumeDisplay`, `radio`, `display` — exist only to
prove the general shape of redundant state; none of them appear in this
project again.

### CS Lens

**Single source of truth** — keeping exactly one real, authoritative
place a fact lives, with every other part of a system reaching that
place through a reference or a direct question, rather than holding its
own independent copy of the current value. This is a hard concept,
worth more than one real-world connection.

```
Also recognized in: a relational database's own normalization rules
(storing a customer's address once, referenced by ID, rather than
copied into every order row); a spreadsheet's cell reference (=A1)
instead of retyping a value into a second cell; a UI framework's own
"lift state up" convention, keeping one component as the sole owner of
a value several children display; DNS's own single authoritative
record for a domain, with every resolver caching, never owning, a copy
of it
```

### SE Lens

The alternative not chosen: keep `self.current_search_text` and simply
promise to always update it whenever the search text changes, "just in
case something reads it later." The real cost of that choice, stated

remember two copies exist and which one is authoritative, and a real

### CS Lens

**Extract Class** — a real, named refactoring technique: when a class
has accumulated two or more genuinely separate responsibilities, pull
one of them out into its own, new class, and have the original class
hold a reference to it instead of the data itself. This connects
directly to **cohesion** — a class's own members should all relate to
one, single real responsibility — and to the **Single Responsibility
Principle**, the more general software-engineering rule this specific
refactoring exists to restore once it's been violated. This is a hard
concept, worth more than one real-world connection.

```
Also recognized in: a User model gaining its own separate UserProfile
or UserSettings object once it accumulates too many unrelated fields;
a game engine's own Entity/Component split, pulling physics, rendering,
and inventory data out of one bloated object; a web framework's Request
object holding a separate session object rather than every session
field living directly on Request; a car's own separate battery and
engine control units, each answerable for one real subsystem instead
of one master unit tracking everything
```

### SE Lens

The alternative not chosen: leave `submitted_assets`/`validation_errors`
as bare `self.` attributes on `MainWindow` forever, on the reasoning
that "it's just two lists, it's fine." The real tradeoff: as this
project grows — a save-to-file feature, a future undo/redo feature —
every one of those features would need to reach into `MainWindow`'s own

adding a new piece of domain-adjacent data as a bare `self.` attribute
on `MainWindow` again, the exact same way as before; only real,
continued judgment keeps it out of there.
