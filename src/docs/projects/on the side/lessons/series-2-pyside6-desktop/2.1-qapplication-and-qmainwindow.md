# Lesson 2.1: QApplication and QMainWindow

**What you will build.** `asset_manager/desktop/main.py` — this
project's first real window, a `QMainWindow` titled "Asset Manager,"
created and shown by a `QApplication`, kept on screen by a real,
running **event loop** until something tells it to stop. Nothing about
`Asset` or `Owner` changes at all; this lesson adds a second, entirely
new layer to the project — `asset_manager/desktop/`, sitting alongside
`asset_manager/domain/` — without touching the domain layer Series 1
already finished and tested. The transferable problem: every GUI
program this lesson's own reader has ever used — a browser, a text
editor, this very desktop — stays on screen and keeps responding to
clicks and keystrokes indefinitely, doing nothing else in between,
until it's told to close; that's not incidental behavior, it's a
specific, real mechanism this lesson names and starts for the first
time.

**What you need to know first.** Lesson 1.15 — Modules and Packages:
`asset_manager/`'s own real package structure, and `__name__`'s
behavior depending on whether a module is imported or run directly —
directly relevant to this lesson's own `if __name__ == "__main__":`.
Nothing about `Asset`/`Owner` themselves is reused here — this lesson
is deliberately, per Series 2's own stated goal, independent of the
domain layer for now.

## Terms used in this lesson

- **event loop** — new. A loop, started once and kept running, that
  waits for something to happen — a mouse click, a key press, a timer
  firing, or an explicit request to stop — and dispatches each one to
  the correct piece of code, then goes back to waiting. Exists because
  a GUI program's entire job, after its initial setup, is *reacting* to
  events whose timing it can't predict in advance — there's no fixed
  sequence of steps to just run through and finish, the way every
  script this curriculum has written before this lesson has worked.
- **`sys.argv`** — new. A real, built-in list Python provides
  automatically to every running program, holding the command-line
  arguments it was started with — `sys.argv[0]` is always the script's
  own name; anything after it is whatever the user typed following the
  program's name on the command line. Exists so a program can read what
  it was asked to do without needing its own separate mechanism for
  receiving that information.
- **`SystemExit`** — new. A real, built-in exception — deliberately
  different in kind from every exception this curriculum has raised on
  purpose before (Lesson 1.11's own `InvalidAssetError`, for instance):
  `sys.exit`'s own real mechanism, existing specifically so ending a
  program is, underneath, still an ordinary raise/propagate operation
  Python's own interpreter already knows how to handle, rather than a
  wholly separate "stop the program" primitive.
- **`if __name__ == "__main__":`** — new. A real, ordinary `if`
  statement (reapplied baseline from Lesson 1.2), checking a specific
  fact Lesson 1.15 already proved every module has: its own `__name__`.
  A module's `__name__` is the literal string `"__main__"` specifically
  when that module is the one Python was started with directly — `"asset
  _manager.desktop.main"` (its real dotted import path) if some other
  code imports it instead. This guards code that should only run when a
  file is executed directly, never when it's imported as a piece of a
  larger program.

## Objects and methods used

**`QApplication`**

- *What it is:* a real class from PySide6's `QtWidgets` module — every
  PySide6 program needs exactly one instance of it, created before any
  widget (a window, a button, anything visible) can exist.
- *Implementation:* `QApplication(sys.argv)` — its constructor accepts
  the program's own command-line arguments, letting Qt itself recognize
  and consume any of its own reserved flags before the rest of the
  program ever sees `sys.argv`; `QApplication.instance() ->
  QApplication | None` — a real class method returning the single,
  already-created instance, or `None` if none exists yet.
- *Its use:* `app = QApplication(sys.argv)` is the first real line of
  `main.py`'s own `main()` function — nothing else in this lesson can
  happen before it.
- *Type:* a class, from `PySide6.QtWidgets`.
- *Responsibility:* manage everything genuinely global to the whole
  running program — its event loop, its connection to the operating
  system's own windowing system, and, per this lesson's own proof, the
  single shared instance every other piece of Qt code can find again
  later via `QApplication.instance()`.
- *Depends on:* being constructed before any widget; depends on
  `sys.argv` for the command-line arguments it optionally reads.
- *Connects to:* created once, in `main()`; every widget this project
  will ever create, starting with this lesson's own `QMainWindow`,
  implicitly depends on it already existing.
- *Shape:* the true root of a PySide6 program — everything else in
  Series 2 sits underneath exactly one `QApplication` instance.

**`QMainWindow`**

- *What it is:* a real class from PySide6's `QtWidgets` module — a
  ready-made top-level window, the standard starting point for a
  desktop application's own main window.
- *Implementation:* `QMainWindow()` — a plain constructor, no required
  arguments; `setWindowTitle(title: str) -> None`; `show() -> None`;
  `isVisible() -> bool`.
- *Its use:* `window = QMainWindow()`, given a title and shown, is this
  project's first real, on-screen window.
- *Type:* a class, from `PySide6.QtWidgets` — itself a subclass of
  Qt's own `QWidget`, though this lesson doesn't yet need that
  relationship's own details.
- *Responsibility:* represent one real, top-level window — its title,
  its visibility, and, in later lessons, everything placed inside it.
- *Depends on:* a `QApplication` already existing — this lesson's first
  unit proves why directly.
- *Connects to:* created and configured inside `main()`, after
  `QApplication`; every future Series 2 lesson that adds a widget adds
  it *to* a window built starting here.
- *Shape:* this project's own application-level root widget — the
  container everything visible will eventually live inside.

**`QMainWindow.setWindowTitle`**

- *What it is:* a real method on `QMainWindow` (inherited from `QWidget`,
  its own parent class) setting the text shown in the window's own
  title bar.
- *Implementation:* `setWindowTitle(self, title: str) -> None`.
- *Its use:* `window.setWindowTitle("Asset Manager")` names this
  project's own window, real, visible text a user would actually see.
- *Type:* an instance method.
- *Responsibility:* store and display one specific string as this
  window's own title — nothing else.
- *Depends on:* the window already existing.
- *Connects to:* called once, directly after construction, inside
  `main()`.
- *Shape:* a small, direct configuration call — no return value, no
  side effect beyond the window's own displayed title.

**`QMainWindow.show`**

- *What it is:* a real method on `QMainWindow`, making a window
  actually visible.
- *Implementation:* `show(self) -> None`.
- *Its use:* `window.show()` is what makes this project's window appear
  at all — a `QMainWindow` built but never shown exists only in memory,
  invisible.
- *Type:* an instance method.
- *Responsibility:* make this specific window visible — nothing about
  keeping it visible or responding to anything afterward; that's the
  event loop's own job, this lesson's third unit.
- *Depends on:* the window already existing, and, this lesson's first
  unit proves, a `QApplication` already existing too.
- *Connects to:* called once, inside `main()`, directly after `setWindowTitle`.
- *Shape:* a one-way trigger — call it once, the window becomes
  visible; nothing about `show()` itself keeps the program running
  afterward.

**`QApplication.exec`**

- *What it is:* a real method on `QApplication`, starting the actual
  **event loop**.
- *Implementation:* `exec(self) -> int` — blocks, running the event
  loop, until something calls `quit()` (or a window's own close button
  is used, later lessons' own subject); returns an integer exit code
  once the loop actually stops.
- *Its use:* `return app.exec()` is `main()`'s own final line — the
  moment this project's program actually starts running, rather than
  merely being set up.
- *Type:* an instance method.
- *Responsibility:* run the event loop for as long as the program
  should stay alive, dispatching every real event (this lesson never
  triggers one on purpose; later lessons' own button clicks are the
  first ones this project responds to) until told to stop.
- *Depends on:* a `QApplication` instance to call it on; conceptually
  depends on at least one visible window existing first, or the loop
  would have nothing to keep the program open for.
- *Connects to:* called once, as the true last step of `main()`;
  everything this project's desktop layer ever does, from this lesson
  forward, happens *during* this one call, not before or after it.
- *Shape:* the boundary between "the program is being set up" and "the
  program is actually running" — this lesson's own central idea.

**`QApplication.quit`**

- *What it is:* a real method on `QApplication`, stopping a currently
  running event loop.
- *Implementation:* `quit(self) -> None` — makes the nearest, currently
  blocked `exec()` call return, its own exit code defaulting to `0`.
- *Its use:* passed, uncalled, to `QTimer.singleShot` — reapplying
  Lesson 1.12's own first-class-function/callback material directly:
  `app.quit`, named with no parentheses, is a real, storable reference
  to the method itself, not a call to it, handed to `QTimer.singleShot`
  to be called automatically, later, exactly the shape Lesson 1.12's
  own `retire`/`on_retired` proved.
- *Type:* an instance method.
- *Responsibility:* stop the event loop — nothing about closing windows
  or cleaning up state beyond that.
- *Depends on:* an event loop currently running to stop.
- *Connects to:* called automatically by `QTimer.singleShot`, in this
  lesson's own isolated proof only — never called anywhere in the real
  `main.py`, which relies on a future lesson's own window-close handling
  instead.
- *Shape:* the event loop's own off switch — the exact counterpart to
  `QApplication.exec`'s own on switch.

**`QTimer.singleShot`**

- *What it is:* a real, static method on PySide6's `QTimer` class,
  scheduling a callable to run once, after a delay, without needing a
  full `QTimer` instance constructed by hand.
- *Implementation:* `QTimer.singleShot(msec: int, callback: Callable)
  -> None` — its real signature; schedules `callback` to be called once
  the event loop has been running for at least `msec` milliseconds.
- *Its use:* `QTimer.singleShot(100, app.quit)` schedules `app.quit`
  to run 100 milliseconds after this lesson's own isolated proof starts
  its event loop — the only reason that verification script can finish
  and produce real, printed output at all.
- *Type:* a static method — called on the class itself, `QTimer`, never
  on an instance.
- *Responsibility:* schedule exactly one future call, at or after a
  given delay, then do nothing further — a single, one-time timer, not
  a repeating one.
- *Depends on:* a running event loop to actually deliver the scheduled
  call when the delay elapses — calling it before `app.exec()` starts
  schedules the call, but nothing fires it until the loop is genuinely
  running.
- *Connects to:* calls `app.quit` automatically, once, 100 milliseconds
  after being scheduled; used only in this lesson's own verification,
  never in the real `main.py`.
- *Shape:* a testing/automation convenience this lesson relies on
  directly — the specific mechanism that makes a blocking call provably
  testable without a human closing a real window by hand.

**`sys.exit`**

- *What it is:* a real function from Python's own standard-library
  `sys` module, ending the program with a specific exit code.
- *Implementation:* `sys.exit(code=0)` — raises a real `SystemExit`
  exception internally, which, left uncaught, ends the process,
  reporting `code` to whatever launched it (a terminal, a script, an
  operating system).
- *Its use:* `sys.exit(main())` hands `app.exec()`'s own returned exit
  code straight to the operating system, so a terminal running this
  program can tell whether it exited normally.
- *Type:* a free function from the `sys` module.
- *Responsibility:* end the program, reporting one specific integer
  outward — nothing about what happens before it's called.
- *Depends on:* the exit code it's given.
- *Connects to:* called once, only inside the `if __name__ ==
  "__main__":` guard, wrapping `main()`'s own return value.
- *Shape:* the program's own true final line — everything else in
  `main.py` runs before this.

### The Problem

Every widget PySide6 provides — `QMainWindow` included — depends on
something being set up before it can exist at all: a real connection to
the operating system's own windowing system, and a place for the event

### CS Lens

This is the **singleton pattern** — a design that guarantees exactly
one instance of a class exists for the lifetime of a program, with a
real, standard way to retrieve that one instance from anywhere. This is
a hard concept, worth more than one real-world connection.

```
Also recognized in: a program's own single database connection pool,

application, a country having exactly one head of state at a time — a
real-world role with the identical "exactly one, and a defined way to

```

### SE Lens

The alternative not chosen is allowing multiple `QApplication`
instances, each managing its own independent connection to the
operating system's windowing layer. The real reason this isn't
supported: the underlying operating-system resources a `QApplication`
manages — the event loop itself, the connection to the display server
— are gen uinely singular per process on every platform Qt supports;
modeling that as "you may create as many as you like" would invite a
real, confusing category of bug (two competing event loops, unclear
which one owns a given window) rather than prevent one.

### CS Lens

This is the **event-driven programming model** — a program structured
around waiting for and reacting to events, rather than running a fixed
sequence of steps from start to finish. This is a hard concept, worth
more than one real-world connection.

```
Also recognized in: a web server's own request-handling loop, waiting
for and responding to incoming connections indefinitely, JavaScript's
own browser event loop handling clicks and network responses, an
elevator's control system, idle until a button press or floor sensor
gives it something to respond to, a restaurant kitchen during service —
not executing one fixed recipe start to finish, but continuously
reacting to orders as they arrive
```

### SE Lens

The alternative not chosen — the only kind of program this curriculum
has written before this lesson — is a fixed, top-to-bottom script that
runs once and exits, exactly what every `verification/1.N/` script and
every one of `Asset`'s own methods has been. The real, honest tradeoff
an event loop introduces: a program built this way genuinely never
"finishes" in the way a script does; its entire architecture, starting
now, has to be built around *reacting* to events whose order and timing
aren't known in advance — a fundamentally different shape than every
domain-layer method Series 1 wrote, none of which needed to consider
what might happen while they were still running.
