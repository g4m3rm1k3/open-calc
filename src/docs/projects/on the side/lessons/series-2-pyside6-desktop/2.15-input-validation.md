# Lesson 2.15: Input Validation

**What you will build.** Two real, separate answers to the same
question — "what happens if a user types something wrong?" —
implemented at two genuinely different layers, matching the blueprint's
own distinction directly: `UI validation ≠ business validation`.
`AssetEditor.serial_number_field` (Lesson 2.9, 2.14) gains a real
`QValidator`, restricting what characters can be typed into it at all
— a real, keystroke-level, UI-layer defense. `MainWindow
.on_asset_submitted` (Lesson 2.14), which currently just appends
whatever three raw strings it receives to a plain list, is rewritten to
construct a real `Asset` (Lesson 1.7) from them — the first time this
project's desktop layer has ever imported or called into
`asset_manager.domain` at all — catching the real `InvalidAssetError`
(Lesson 1.11) `Asset.__init__` already raises on a blank name, something
no validator on `serial_number_field` could ever catch, since nothing
this project has built restricts `name_field` at all. Landing that
domain import for real surfaces a genuine, unavoidable mechanical fact
about how Python resolves imports, proven and fixed along the way:
`main.py`'s own sibling import of `asset_editor` has to become a
package-relative import, and the whole project now has to be run as a
real Python module (`python -m asset_manager.desktop.main`, from the
project's own root) rather than as a standalone script.

**What you need to know first.** Lesson 2.14 — `AssetEditor`,
`asset_submitted`, `MainWindow.on_asset_submitted`, and
`self.submitted_assets` — the exact real starting point this lesson
extends; 2.14's own closing named the gap this lesson exists to close.
Lesson 1.7 — `Asset`, `Owner`, both real dataclasses this lesson
constructs for the first time from GUI-collected data. Lesson 1.11 —

## Terms used in this lesson

- **validator** — new. An object attached to an input widget that
  checks, character by character as the user types, whether the
  current text is a complete, valid value; a partial value still being
  typed; or already impossible to ever complete correctly — exists so a
  widget can reject bad input the instant it would be typed, rather
  than only after the fact.
- **UI-level validation** — new. Validation performed by the interface
  itself, before data ever leaves the widget it was typed into —
  `serial_number_field`'s own new validator, this lesson's own first
  real example, is UI-level: it never touches `Asset`, `Owner`, or
  anything in `asset_manager.domain` at all.
- **domain-level validation** (also called **business validation**) —
  new. Validation performed by the domain layer itself, checking rules
  that belong to the real-world concept being modeled — `Asset.__post
  _init__` (Lesson 1.9, 1.11) already is this, unchanged; this lesson's
  own real point is that a GUI has to actually call into the domain
  layer to benefit from it, which nothing in this project has done
  until now.
- **exception handling** (`try`/`except`) — reappearing. Python's own
  mechanism for running code that might raise an error, and reacting
  specifically to that error rather than letting the program crash;
  `except InvalidAssetError as error:` catches exactly one real
  exception type, binding the actual raised object to `error` for
  inspection.
- **package-relative execution** (`python -m package.module`) — new. A
  way of running a Python file that treats it as part of a package
  rather than a standalone script — the concrete, real mechanism this
  lesson needs so `main.py` can import `asset_manager.domain` at all;
  contrasted directly below against `python path/to/script.py`, the way
  this project's own `main.py` has been run since Lesson 2.1.

## Objects and methods used

**`QRegularExpression`**

- *What it is:* a real class from PySide6's `QtCore` module — Qt's own
  compiled representation of a regular expression pattern.
- *Implementation:* `QRegularExpression(pattern: str)` — compiles
  `pattern`, a string written in real regular-expression syntax, into a
  reusable matching object.
- *Its use:* `QRegularExpression("[A-Za-z0-9-]*")`, this lesson's own
  real pattern — matches any string made entirely of letters, digits,
  or hyphens, including the empty string (`*` permits zero characters).
- *Type:* a class, from `PySide6.QtCore`.
- *Responsibility:* hold one compiled pattern, ready to be matched
  against real text — nothing about deciding what a partial or complete
  match should mean for a specific input widget; that's `QValidator`'s
  own job.
- *Depends on:* a real, syntactically valid regular-expression string.
- *Connects to:* handed directly to `QRegularExpressionValidator`'s own
  constructor, below — the pattern the validator checks every keystroke
  against.
- *Shape:* the raw pattern, separate from the object that actually
  applies it to a live widget.

**`QRegularExpressionValidator`**

- *What it is:* a real class from PySide6's `QtGui` module — a
  `QValidator` that accepts input matching a given
  `QRegularExpression`.
- *Implementation:* `QRegularExpressionValidator(regularExpression:
  QRegularExpression, parent: QObject | None = None)`; inherits
  `validate(self, input: str, pos: int) -> tuple[QValidator.State, str,
  int]` from `QValidator` itself — a real, three-value return: the
  validity state, the input text (potentially adjusted), and the
  cursor position.
- *Its use:*
  `QRegularExpressionValidator(QRegularExpression("[A-Za-z0-9-]*"))`,
  attached to `serial_number_field`, is this lesson's own real,
  central UI-level check.
- *Type:* a class, from `PySide6.QtGui` — a `QValidator` subclass.
- *Responsibility:* decide, for any given text and cursor position,
  whether that text is a complete match for its own pattern
  (`Acceptable`), a valid prefix of one (`Intermediate`), or impossible
  to ever complete into a match (`Invalid`) — nothing about actually
  stopping a keystroke; that enforcement happens inside `QLineEdit`
  itself, reading this validator's own answer.
- *Depends on:* a real `QRegularExpression` to check against.
- *Connects to:* handed to `QLineEdit.setValidator` (below); every
  keystroke a user types into that field calls this validator's own
  `validate` internally, before the character is accepted.
- *Shape:* this lesson's own real, concrete `QValidator` — the abstract
  base class itself is never instantiated directly.

**`QValidator.validate`**

- *What it is:* a real method every `QValidator` (including
  `QRegularExpressionValidator`, above) carries — the one method that
  actually performs a check.
- *Implementation:* `validate(self, input: str, pos: int) ->
  tuple[QValidator.State, str, int]`. `QValidator.State` is a real
  enum, also from `PySide6.QtGui`, with exactly three members:
  `Invalid = 0` (can never become valid), `Intermediate = 1` (not
  valid yet, but could still become valid with more typing — not
  triggered by this lesson's own pattern, since every valid prefix of
  `[A-Za-z0-9-]*` is already a complete match), and `Acceptable = 2`
  (a real, complete, valid value).
- *Its use:* `validator.validate("SN 001", 6)`, this lesson's own
  verification, calls it directly — the identical real method Qt itself
  calls internally on every keystroke, called here explicitly since a
  headless run has no real keyboard to generate keystrokes with.
- *Type:* an instance method, on `QValidator`.
- *Responsibility:* answer exactly one question — is this specific
  text, at this specific cursor position, `Invalid`, `Intermediate`, or
  `Acceptable` — nothing about modifying the widget itself.
- *Depends on:* the text to check, and the cursor position within it.
- *Connects to:* called by `QLineEdit` itself on every real keystroke;
  called directly by this lesson's own verification code instead, for
  the identical real answer without a real keyboard.
- *Shape:* the actual checking mechanism underneath every validator
  this project will ever use.

**`QLineEdit.setValidator`** *(and* `QLineEdit.validator`*)*

- *What it is:* a real method pair every `QLineEdit` carries —
  attaches a validator to the field, and reads back whichever one is
  currently attached.
- *Implementation:* `setValidator(self, validator: QValidator | None)
  -> None`; `validator(self) -> QValidator | None` — returns `None` if
  none has ever been set.
- *Its use:* `self.serial_number_field.setValidator(...)`, inside
  `AssetEditor.__init__`, is this lesson's own real, permanent
  attachment; `editor.serial_number_field.validator()` and
  `editor.name_field.validator()`, in this lesson's own verification,
  confirm which field actually has one.
- *Type:* an instance method pair, on `QLineEdit`.
- *Responsibility:* hold a reference to at most one validator per
  field, and, once one is set, consult it on every keystroke —
  `setValidator` itself does nothing beyond storing that reference.
- *Depends on:* a real `QValidator` instance, or `None` to remove one.
- *Connects to:* whatever validator is set is what `QLineEdit`'s own
  internal keystroke handling consults every time the user types.
- *Shape:* the real attachment point between a widget and the
  validation logic that constrains it — deliberately per-field, not
  automatic or global.

## Concept Unit: Restricting What Can Be Typed

### The Problem

Nothing built so far has ever stopped a user from typing *anything* into
a `QLineEdit` — `search_box` (2.6), `name_field`, `serial_number_field`
(2.9) all accept every character equally. Can a field reject bad
characters the instant they'd be typed, rather than only checking the
finished text after the fact — and if so, what does Qt's own real
mechanism for "is this text currently valid" actually look like, given
a user can be *partway* through typing something that isn't valid yet
but still could become valid?

> **Before reading on, try this:**
> - A serial number like `"SN-001"` uses letters, digits, and a hyphen.
>   If a validator's job is deciding whether typed text is allowed,
>   what do you predict happens to an *empty* field — is an empty
>   string immediately rejected as invalid, or does a validator have to
>   treat "nothing typed yet" as a special, allowed case?
> - Given a user types one character at a time, what do you predict a
>   validator needs to report about the text `"S"` alone, partway
>   through typing `"SN-001"` — is `"S"` itself already a complete,
>   valid serial number, or does the validator need some way to say
>   "not valid yet, but don't reject it either, since more typing could
>   still make it valid"?

### Isolated Concept

```python
from PySide6.QtCore import QRegularExpression
from PySide6.QtGui import QRegularExpressionValidator
from PySide6.QtWidgets import QApplication, QLineEdit

app = QApplication([])

field = QLineEdit()
pattern = QRegularExpression("[A-Za-z0-9-]*")
validator = QRegularExpressionValidator(pattern)
field.setValidator(validator)

print(validator.validate("", 0))
print(validator.validate("SN-001", 6))
print(validator.validate("SN 001", 6))
print(field.validator() is validator)
```

Run for real (`lab1_qregularexpressionvalidator.py`, headless):

```
(<State.Acceptable: 2>, '', 0)
(<State.Acceptable: 2>, 'SN-001', 6)
(<State.Invalid: 0>, 'SN 001', 6)
True
```

`validator.validate("", 0)` reads `Acceptable`, not `Invalid` — real,
confirmed proof answering this unit's own first Socratic question
directly: an empty string genuinely counts as a complete match here,
because the pattern's own `*` means "zero or more" — zero allowed
characters is still a full match, not a partial one. `validator
.validate("SN-001", 6)` also reads `Acceptable` — every character is a
letter, digit, or hyphen, and `6`, the cursor position, is simply where
a real cursor would sit after typing all six characters. `validator
.validate("SN 001", 6)` reads `Invalid` — the space at index two is
outside `[A-Za-z0-9-]`, and, this unit's own real point, there is no
way *more* typing could ever fix a character that's already wrong;
this pattern's own shape (every valid prefix is already a complete
match on its own) means `Intermediate` never actually appears in this
lesson's own real output, even though it's a real, third state
`QValidator` supports for patterns where a partial match genuinely
isn't complete yet. `field.validator() is validator` reads `True` —
real, confirmed proof `setValidator` genuinely stored the exact object
given, retrievable afterward, not a copy.

Discarded: `field`, `pattern`, and `validator` exist only to prove this
mechanism in isolation. None will appear in the Asset Manager project

### CS Lens

This is **regular-language membership testing** — checking whether a
string belongs to the set of strings a regular expression describes.
This is a hard concept, worth more than one real-world connection.

```
Also recognized in: a compiler's own lexer matching source text against

```

### SE Lens

The alternative not chosen is checking the field's own final text only
once, after the user finishes typing and clicks "Save" — a single,
after-the-fact `if` check, rather than a real-time, per-keystroke
`QValidator`. The real benefit of a validator instead: a user typing a
space by mistake sees it *rejected instantly*, rather than typing an
entire serial number, clicking Save, and only then discovering
something was wrong. The real cost: a validator needs a genuinely more
nuanced answer than plain `True`/`False` — `Acceptable`, `Intermediate`,
and `Invalid`, not just "valid" and "invalid" — since a user has to be
allowed to be *partway* through typing something correct without every
partial state being rejected outright; a simple boolean check couldn't
express that distinction at all.

## Concept Unit: Domain-Level Validation and Crossing the Boundary

### The Problem

`name_field` (2.9) has no validator, and, this lesson's own previous
unit already argued, reasonably shouldn't — a name's own real
constraint isn't a character format, it's a business rule: it must not
be blank. `Asset.__post_init__` (1.9, 1.11) already enforces exactly
that rule, for real — but `MainWindow.on_asset_submitted` (2.14)
currently never constructs a real `Asset` at all; it just appends the
three raw strings it receives to a plain list. Can this project's GUI
layer actually reach `asset_manager.domain` for the first time, and, if
`Asset.__init__` genuinely rejects bad input, can that rejection be
caught and handled rather than crashing the whole program?

`self.validation_errors = []`, `MainWindow.__init__`'s own new line,
gives caught validation failures somewhere real to live, the same
instance-attribute reasoning Lesson 2.11 already established for
`self.editor`. `on_asset_submitted` now genuinely constructs a real

exactly that real exception, appends the real caught object to
`self.validation_errors`, and `return`s immediately — `self
.submitted_assets.append(asset)` never runs on a failed construction,
since Python never reaches a line after a caught exception's own
`return`. On success, `self.submitted_assets` now holds real `Asset`
objects, not raw tuples — this lesson's own real upgrade over 2.14's
own deliberately provisional version.

**A necessary, real mechanical consequence, not a separate concept:**
`from asset_editor import AssetEditor` (2.14) becomes `from
.asset_editor import AssetEditor` — a package-relative import,
reapplying Lesson 1.15's own `from .owner import Owner` syntax exactly.
This is required the instant `main.py` also imports `asset_manager
.domain`: an *absolute* import like `from asset_manager.domain.asset
import Asset` only resolves if the project's own root directory (the
one directly containing `asset_manager/`) is on Python's own `sys
.path` — and it never was, since Lesson 2.1, because `main.py` has
always been run directly, `python main.py`, from inside `desktop/`
itself. Running a script directly puts *that script's own directory* on
`sys.path`, not the project's root — confirmed for real: running the
real, updated `main.py` the old way, `python main.py` from inside
`desktop/`, now raises `ModuleNotFoundError: No module named
'asset_manager'` on the very first new import line. The real fix is
**package-relative execution**: `python -m asset_manager.desktop.main`,
run from the project's own root — the `-m` flag treats `main.py` as
part of the `asset_manager.desktop` package rather than a standalone
script, and, running this way, Python puts the *current working
directory* (the project root, if run from there) on `sys.path` instead
— which is exactly what makes `asset_manager.domain` reachable at all.

relative in the same change: run via `-m`, `main.py`'s own directory
(`desktop/`) is no longer on `sys.path` either, so the old, bare
`from asset_editor import AssetEditor` would itself now fail; only a
real package-relative import survives both changes at once.

### SE Lens

The alternative not chosen is skipping domain-level validation entirely
and relying only on UI-level validators for everything, including
blank-name checking. The real reason that's the wrong tradeoff: a
validator only ever sees what's typed into *one specific widget* — it
has no way to express a business rule like "this value came from a
trusted API call, not a user, so it was never typed at all, but still
needs the identical check" — `Asset.__post_init__` (1.9, 1.11) already
runs that exact check regardless of *how* an `Asset` gets constructed,
proven directly by this unit's own real code, which never touches
`serial_number_field`'s own validator at all. The real, honest cost
this project is now carrying, stated plainly: `PLACEHOLDER_OWNER` is a
genuine simplification, not a hidden one — every submitted `Asset`
currently shares one identical, fake owner, because this project has no
real owner-selection UI yet; naming that gap here, rather than letting
it look like finished, considered design, is deliberate.
