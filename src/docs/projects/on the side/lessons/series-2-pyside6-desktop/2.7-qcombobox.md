## Objects and methods used

**`QComboBox`**

- *What it is:* a real class from PySide6's `QtWidgets` module — a
  dropdown widget offering a fixed list of choices, exactly one
  selected at a time.
- *Implementation:* `QComboBox(parent: QWidget | None = None)`; `add
  Items(self, texts: list[str]) -> None`; `count(self) -> int`;
  `currentText(self) -> str`; `itemText(self, index: int) -> str`;
  `setCurrentIndex(self, index: int) -> None`.
- *Its use:* `category_box = QComboBox(window)`, populated with five
  category strings via `addItems`, is this project's first widget
  offering a fixed, known set of choices rather than open text.
- *Type:* a class, from `PySide6.QtWidgets` — a `QWidget`, the same
  ancestry every widget since Lesson 2.4 shares.
- *Responsibility:* hold and display a fixed list of choices, track
  which one is currently selected, and let that selection be read or
  changed — nothing about validating or reacting to a change, both left
  to later lessons.
- *Depends on:* nothing beyond a parent to construct one; `addItems`
  called afterward to actually populate it — an empty `QComboBox` has
  nothing to select at all.
- *Connects to:* parented to `window` inside `main()`, the identical
  relationship every widget since Lesson 2.4 has had.
- *Shape:* this project's first "closed choice" widget — a genuinely
  different shape than `QLineEdit`'s open text, worth its own real
  contrast.

**`QComboBox.addItems`**

- *What it is:* a real method adding multiple items to a `QComboBox`
  in one call.
- *Implementation:* `addItems(self, texts: list[str]) -> None` —
  appends every string in `texts`, in order, as a new, separate item.
- *Its use:* `category_box.addItems(["Laptop", "Monitor", "Keyboard",
  "Mouse", "Other"])` populates the whole dropdown in a single call,
  the plain, hard-coded list this lesson's own scope note names
  directly.
- *Type:* an instance method.
- *Responsibility:* add items — nothing about selection, which item (if
  any) becomes current, or removing anything already there.
- *Depends on:* a real `list[str]` (Lesson 1.6's own generic type
  annotation, reapplied here as a real, concrete argument type).
- *Connects to:* called once, directly after construction, inside
  `main()`.
- *Shape:* the population step every `QComboBox` needs before it's
  useful — mechanically similar to `setPlaceholderText` (Lesson 2.6):
  configuration, called once, read automatically afterward by Qt's own
  rendering and selection logic.

**`QComboBox.currentText`** *(and its counterparts,* *`itemText`,*
*`count`, `setCurrentIndex`)*

- *What it is:* a real family of methods reading and changing a
  `QComboBox`'s own current state.
- *Implementation:* `currentText(self) -> str` — the text of whichever
  item is currently selected; `itemText(self, index: int) -> str` — the
  text of one specific item, by its position; `count(self) -> int` —
  how many items exist in total; `setCurrentIndex(self, index: int) ->
  None` — changes which item is selected.
- *Its use:* together, prove this lesson's own real subject: a
  `QComboBox` always has *some* current selection the instant it has
  any items at all, and that selection can be read or changed directly,
  without a user ever having interacted with it.
- *Type:* an instance method family.
- *Responsibility:* report or change exactly one fact each — nothing
  about validating an index, or reacting to a change.
- *Depends on:* `setCurrentIndex`/`itemText` both depend on a valid
  index actually existing, per `count`'s own real value.
- *Connects to:* all four called directly in this lesson's own isolated
  proof; none of them called anywhere in the real, landed `main.py`
  beyond `addItems` itself.
- *Shape:* the read/write surface for a widget whose entire state is
  "which one of these fixed choices is current."

## Concept Unit: A Fixed Set of Choices

### The Problem

`QLineEdit` (Lesson 2.6) starts with genuinely empty text — nothing
selected, nothing assumed. Does a widget offering a fixed *list* of
choices start the same way, with nothing selected until a user picks
something, or does having any items at all mean something is already,
necessarily, the current selection?

> **Before reading on, try this:**
> - Lesson 2.6 already proved `QLineEdit.text()` starts as `''` — no
>   value assumed. Given `QComboBox` instead offers a fixed list, do
>   you predict `currentText()`, checked immediately after populating
>   it with real items but before anything is explicitly selected,
>   also starts empty — or does having any items at all force
>   *something* to already be selected?
> - `Asset.category` (Lesson 1.7) is a plain `str` — `Asset("laptop, I
>   guess", ...)` would construct without complaint, since nothing
>   about that field's own type constrains its actual value. Given a
>   `QComboBox` offers a fixed, closed list instead, do you predict
>   `category_box.currentText()` could ever return a string that isn't
>   one of the exact strings handed to `addItems` — or is that
>   genuinely impossible by construction?

### Isolated Concept

This is exactly what `main.py`'s own two new lines depend on — proven
across every state this lesson's Socratic questions asked about:

```python
from PySide6.QtWidgets import QApplication, QComboBox, QMainWindow

app = QApplication([])

window = QMainWindow()
category_box = QComboBox(window)
category_box.addItems(["Laptop", "Monitor", "Keyboard", "Mouse", "Other"])

print(category_box.count())
print(category_box.currentText())
print(category_box.itemText(1))

category_box.setCurrentIndex(1)
print(category_box.currentText())
```

Run for real (`lab1_qcombobox.py`, headless):

```
5
Laptop
Monitor
Monitor
```

`category_box.count()` reads `5` — real, confirmed proof every string
handed to `addItems` genuinely became its own item. `category_box
.currentText()`, checked immediately afterward, with no explicit
selection ever made, already reads `"Laptop"` — the *first* item added
— real, confirmed proof, not a claim, answering this unit's own
Socratic question directly: a `QComboBox` with any items at all
*always* has a current selection; unlike `QLineEdit`'s genuinely empty
starting text, there is no "nothing selected" state once items exist.
`category_box.itemText(1)` reads `"Monitor"` — the second item,
zero-indexed, confirming items can be inspected individually by
position. `category_box.setCurrentIndex(1)` changes the selection
directly; `currentText()`, read again, now reads `"Monitor"` — real,
confirmed proof the selection genuinely changed, and, just as
important, that it changed to exactly one of the five strings
originally added — nothing about `setCurrentIndex` could ever produce
a `currentText()` outside that fixed list, the structural guarantee
`Asset.category`'s own plain `str` field has never had.

### CS Lens

This is a **closed/enumerated choice set**, in contrast with `Asset
.category`'s own **open string field** — the same structural distinction
type systems draw between an `enum` (a fixed, named set of legal
values) and an unconstrained `str`. This is a hard concept, worth more
than one real-world connection.

```
Also recognized in: a `<select>` element in HTML versus a plain
`<input type="text">`, a database column with a CHECK constraint or a
real ENUM type versus a plain, unconstrained VARCHAR, a multiple-choice
question versus a fill-in-the-blank one — one structurally limits what
a correct answer can even be; the other trusts the answer entirely
```

### SE Lens

The alternative not chosen is leaving asset category selection as free
text everywhere, `QLineEdit` reused instead of `QComboBox`. The real
tradeoff, honestly stated per this lesson's own scope note: a
`QComboBox` structurally *cannot* produce a value outside its own fixed
list — proven directly above — which is a real, meaningful guarantee a
plain text field can never offer; the actual cost is that this
guarantee currently applies only to this UI widget in isolation, not to
`Asset.category` itself, which remains a fully open `str` until some
future lesson actually wires the two together. Until that happens, this
project has two, honestly disagreeing ideas of "category" — a real,
temporary inconsistency worth naming rather than hiding.
