# Lesson 2.8: Layouts

**What you will build.** `asset_manager/desktop/main.py`'s own four
widgets — `button`, `search_box`, `category_box`, and the window
itself — stop being parented straight to `window` with no real
arrangement at all, and get a genuine layout: `search_box` and
`category_box` side by side in a `QHBoxLayout`, stacked above `button`
in an outer `QVBoxLayout`, the whole thing set on a real central
widget `QMainWindow` actually displays. Every widget this project has
built since Lesson 2.4 gets re-parented in the process — not by any
code explicitly reassigning a `parent`, but automatically, the instant
each one is added to a layout. The transferable problem: parenting a
widget (Lesson 2.3) controls its *ownership and lifetime* — who
destroys it, and when — but says nothing at all about *where it
appears on screen relative to anything else*; every widget this
project has shown so far has been positioned entirely by Qt's own
unmanaged default, and this lesson is the first to take real control of
that.

**What you need to know first.** Lesson 2.3 — `QObject`'s own
parent/child relationship, `parent()`/`children()` — this lesson's own
central proof is that adding a widget to a layout changes that exact
relationship automatically. Lessons 2.5–2.7 — `button`, `search_box`,
`category_box`, the three widgets this lesson re-arranges; nothing
about what any of them *do* changes, only where they live and how
they're parented.

## Terms used in this lesson

- **layout** — new. A real Qt object managing the size and position of
  every widget added to it, automatically recalculating that
  arrangement whenever the window is resized or a widget is added or
  removed — distinct from parenting (Lesson 2.3), which governs
  ownership and lifetime, never position.
- **central widget** — new. The one widget a `QMainWindow` designates
  as its own main content area — a real, required concept specifically
  because `QMainWindow` itself, unlike a plain `QWidget`, cannot have a
  layout set on it directly; it reserves its own layout for other
  structural regions (menus, toolbars, status bars — none used by this
  project yet) and delegates all real content to whichever widget is
  set as its central one.

## Objects and methods used

**`QVBoxLayout`**

- *What it is:* a real class from PySide6's `QtWidgets` module — a
  layout arranging every widget or nested layout added to it in a
  single vertical column, top to bottom, in the order each was added.
- *Implementation:* `QVBoxLayout(parent: QWidget | None = None)`;
  `addWidget(self, widget: QWidget) -> None`; `addLayout(self, layout:
  QLayout) -> None`; `count(self) -> int`.
- *Its use:* `main_layout`, this project's own outer layout, stacks the
  search row above the "Add Asset" button.
- *Type:* a class, from `PySide6.QtWidgets`.
- *Responsibility:* track every widget or nested layout added to it, in
  order, and compute their real, on-screen vertical arrangement —
  nothing about ownership, which remains governed by the separate
  parent/child mechanism this lesson's own first unit proves is wired
  up automatically.
- *Depends on:* eventually needing a real widget to be set on, via
  `setLayout` or `QMainWindow.setCentralWidget`, before it has any
  effect on what's actually shown.
- *Connects to:* holds `search_row` (a nested `QHBoxLayout`) and
  `button` directly; set on `central`, this project's own new central
  widget.
- *Shape:* this project's own outer, top-level arrangement.

**`QHBoxLayout`**

- *What it is:* a real class, identical in every way to `QVBoxLayout`
  except its own arrangement direction: a single horizontal row, left
  to right, instead of a vertical column.
- *Implementation:* identical shape to `QVBoxLayout` — same
  constructor, same `addWidget`/`count`.
- *Its use:* `search_row` places `search_box` and `category_box` side
  by side, rather than stacked.
- *Type:* a class, from `PySide6.QtWidgets`.
- *Responsibility:* identical to `QVBoxLayout`'s own, applied
  horizontally instead of vertically.
- *Depends on:* identical to `QVBoxLayout`'s own.
- *Connects to:* holds `search_box` and `category_box` directly; added
  to `main_layout` via `addLayout`, nesting one layout inside another.
- *Shape:* an inner, nested arrangement — one row inside the project's
  own outer column.

**`QWidget.setLayout`**

- *What it is:* a real method assigning a layout to a widget, making
  that widget responsible for actually displaying whatever the layout
  arranges.
- *Implementation:* `setLayout(self, layout: QLayout) -> None`.
- *Its use:* `central.setLayout(main_layout)` connects this project's
  own new, plain `QWidget` to the outer layout holding everything else.
- *Type:* an instance method.
- *Responsibility:* associate exactly one layout with this widget —
  Qt itself enforces at most one layout per widget.
- *Depends on:* a real `QLayout` to assign.
- *Connects to:* called on `central`, a brand-new, otherwise-empty
  `QWidget` this lesson creates specifically to hold the real layout.
- *Shape:* the bridge between an abstract arrangement (a layout, no
  visual presence of its own) and a real widget Qt can actually
  render.

**`QMainWindow.setCentralWidget`**

- *What it is:* a real method designating one specific widget as a
  `QMainWindow`'s own main content area.
- *Implementation:* `setCentralWidget(self, widget: QWidget) -> None`.
- *Its use:* `window.setCentralWidget(central)` is what finally connects
  this lesson's entire new layout structure to the real, on-screen
  window every widget has been shown in since Lesson 2.1.
- *Type:* an instance method.
- *Responsibility:* designate `central` as the widget `window` actually
  displays as its main content — implicitly re-parents `central` to
  `window` in the process, this lesson's own second unit proves
  directly.
- *Depends on:* a real widget to designate.
- *Connects to:* called once, inside `main()`, as close to
  `window.show()` as this lesson's own new code gets.
- *Shape:* the one, required connection between `QMainWindow`'s own
  structural machinery and this project's real content — without it, a
  `QMainWindow` would show nothing at all, regardless of how carefully
  a layout elsewhere was built.

## Concept Unit: Adding a Widget to a Layout Reparents It

### The Problem

Every widget this project has created since Lesson 2.4 has been
parented directly to `window` — `QPushButton("Add Asset", window)`,
for instance — establishing real, checkable ownership (Lesson 2.3), but
nothing about *where on screen* it actually appears. A `QMainWindow`,
this lesson's own header already states, can't have a layout set on it
directly at all — it needs a separate widget, its own **central
widget**, to hold one. If a widget already has a parent, and it's added
to a layout that itself belongs to a *different* widget, what actually
happens to that original parent relationship?

> **Before reading on, try this:**
> - Lesson 2.3 already proved `QObject.parent()` reports a real,
>   checkable fact. If a widget already parented to `window` is added
>   to a layout that belongs to some *other* widget entirely, do you
>   predict its own `parent()` stays `window`, unaffected — or does
>   adding it to that layout silently change what its real parent is?
> - Given a `QMainWindow` can't hold a layout directly, and needs a
>   separate central widget instead, what do you predict happens if
>   `window.show()` is called with *no* central widget ever set at
>   all — does the window show completely empty, or does it fail
>   outright?

### Isolated Concept

```python
from PySide6.QtWidgets import QApplication, QLabel, QMainWindow, QVBoxLayout, QWidget

app = QApplication([])

window = QMainWindow()
label = QLabel("Asset Manager", window)

print("before layout, label.parent() is window:", label.parent() is window)

central = QWidget(window)
layout = QVBoxLayout(central)
layout.addWidget(label)
window.setCentralWidget(central)

print("after layout, label.parent() is window:", label.parent() is window)
print("after layout, label.parent() is central:", label.parent() is central)
print("central.parent() is window:", central.parent() is window)
print("window.centralWidget() is central:", window.centralWidget() is central)
```

Run for real (`lab1_layout_reparenting.py`, headless):

```
before layout, label.parent() is window: True
after layout, label.parent() is window: False
after layout, label.parent() is central: True
central.parent() is window: True
window.centralWidget() is central: True
```

`label`, constructed exactly the way `button`/`search_box`/
`category_box` already are in the real project, starts out parented to
`window` — `label.parent() is window` reads `True`, reapplying Lesson
2.3's own proof directly. Then `layout.addWidget(label)` runs — real,
confirmed proof, not a claim: `label.parent() is window` now reads
`False`. Nothing in this script ever wrote `label.setParent(...)`
directly; adding a widget to a layout silently, automatically changes
its real parent to whatever widget that layout itself belongs to —
proven by the next line, `label.parent() is central`, reading `True`.
`central.parent() is window`, and `window.centralWidget() is central`,
confirm the final piece: `setCentralWidget` both designates `central`
as the window's real content *and* re-parents it to `window` — the
complete chain, `label` owned by `central`, `central` owned by
`window`, established without a single explicit `parent()` reassignment
anywhere in this script.

Discarded: `label`/`central`/`layout` exist only to prove this
mechanism. Neither will appear in the Asset Manager project again in
this exact form.

### CS Lens

This is **implicit ownership transfer as a side effect of composition**
— adding something to a container silently changing who's responsible
for it, rather than requiring an explicit, separate step. This is a
hard concept, worth more than one real-world connection.

```
Also recognized in: moving a file into a different folder in a
filesystem, which silently changes which folder "owns" it without a
separate ownership-transfer command, adding an employee to a new team
in an org chart, which changes their reporting line as a side effect of
the team assignment itself, C++'s own std::unique_ptr transferring
ownership automatically when moved into a container
```

### SE Lens

The alternative not chosen is requiring an explicit, separate
`widget.setParent(central)` call alongside `layout.addWidget(widget)`
for every single widget added to a layout. The real benefit of doing it
automatically instead, proven directly above: a reader adding a widget
to a layout can never forget the re-parenting step, or leave a widget
in a state where its visual position and its real ownership disagree —
the two facts are kept in sync by construction, at the real cost of a
genuinely surprising side effect (a parent silently changing) for
anyone who hasn't seen this proof before.

## Concept Unit: A Real, Nested Layout

### The Problem

This project's real window needs more than one widget arranged
correctly: `search_box` and `category_box` belong side by side, as a
row, while that whole row belongs stacked above `button`. Can a layout
hold *another* layout, not just individual widgets, to build this kind
of nested arrangement — and does the automatic re-parenting the
previous unit proved still reach every widget correctly, even nested
two layers deep?

> **Before reading on, try this:**
> - `QHBoxLayout` and `QVBoxLayout` share the identical shape, per this
>   lesson's own header — same constructor, same `addWidget`. If a
>   `QHBoxLayout` needs to be placed *inside* a `QVBoxLayout`, as one
>   of its own rows, do you predict there's a real, separate method for
>   adding a layout to a layout — distinct from `addWidget` — or does
>   `addWidget` itself already handle both cases?
> - If `search_box` ends up two layout-levels deep — inside
>   `search_row`, which is itself inside `main_layout` — and
>   `main_layout` belongs to `central`, do you predict `search_box
>   .parent()` ends up being `search_row` (the layout directly holding
>   it), or does it skip straight to `central`, the real widget at the
>   top of the whole structure?

### CS Lens

This is the **Composite pattern** — treating an individual object (a
widget) and a composition of objects (a layout containing other
layouts and widgets) through the same uniform interface (`addWidget`/
`addLayout`, both callable on any layout, at any nesting depth). This
is a hard concept, worth more than one real-world connection.

```
Also recognized in: a filesystem directory containing both files and
other directories, browsable through the identical interface either
way, a corporate org chart where a "team" node can itself contain
individual employees or further sub-teams, an HTML document's own DOM
tree, where a <div> can contain both plain text and further nested
<div> elements
```

### SE Lens

The alternative not chosen is a single, flat layout holding every
widget directly, with spacing and alignment tricks standing in for real
grouping. The real benefit of nesting instead, proven directly by this
unit's own structure: `search_row` groups `search_box` and
`category_box` as one real, addressable unit — inserted, removed, or
resized together, as a row — something a flat structure could only
approximate, never truly guarantee. The real cost: this project's
layout is now a genuine tree, two levels deep already, and every
additional grouping need going forward adds another real level to keep
track of.
