## Objects and methods used

**`QTableView.selectionModel`**

- *What it is:* a real method every `QTableView` (and every other
  `QAbstractItemView`) carries — returns the real, automatically-built
  `QItemSelectionModel` tracking that view's own current selection.
- *Implementation:* `selectionModel(self) -> QItemSelectionModel` — a
  real object built automatically the moment a real model is attached
  via `setModel` (2.19); confirmed directly: calling this immediately
  after `setModel` already returns a real, non-`None` object, with no
  separate construction step anywhere.
- *Its use:* `self.assets_table.selectionModel().currentRowChanged
  .connect(self.on_current_row_changed)`, this lesson's own real,
  central wiring.
- *Type:* an instance method, on `QAbstractItemView` (`QTableView`'s
  own real ancestor).
- *Responsibility:* provide access to the one real object tracking
  which cells/rows are currently selected or current — nothing about
  *how* a user's own clicks change that state; that's handled entirely
  by `QTableView`'s own internal, already-existing input handling.
- *Depends on:* a real model already set via `setModel` (2.19).
- *Connects to:* returns a real `QItemSelectionModel` (below); every
  real click on the table updates that same object automatically.
- *Shape:* the real entry point into everything this lesson teaches
  about selection.

**`QItemSelectionModel`** *(and its* `currentRowChanged` *signal)*

- *What it is:* a real class from PySide6's `QtCore` module — tracks
  exactly which cell is the current one, and which cells are selected,
  for one specific view.
- *Implementation:* carries `currentRowChanged(current: QModelIndex,
  previous: QModelIndex)`, a real signal, emitted specifically when the
  current *row* changes — distinct from the more general `currentChanged`,
  which also fires when only the current *column* changes within the
  same row; `currentIndex(self) -> QModelIndex` reports the real,
  current index directly, without needing to wait for a signal.
- *Its use:* `.currentRowChanged.connect(self.on_current_row_changed)`
  — reapplying Lesson 2.11's own general `Signal.connect` material
  against a signal this project's own code never constructed, only
  received automatically from `selectionModel()`.
- *Type:* a class, from `PySide6.QtCore` — a `QObject` (2.3); `current
  RowChanged` is a real signal it carries.
- *Responsibility:* track and announce exactly one real fact — which
  row is currently "the current one" — nothing about what any
  connected slot does in response, the identical division of labor
  every signal in this project has always kept.
- *Depends on:* a real view (here, `self.assets_table`) already having
  a real model attached.
- *Connects to:* built automatically by `QTableView`, returned by
  `selectionModel()`; its own `currentRowChanged` connects to `self
  .on_current_row_changed`, this lesson's own new real method.
- *Shape:* this lesson's own real, central new object — this project's
  first use of anything beyond a model or a view themselves.

**`QModelIndex.isValid`**

- *What it is:* a real method every `QModelIndex` carries — reports
  whether it actually refers to a real, existing cell.
- *Implementation:* `isValid(self) -> bool` — a freshly-constructed
  `QModelIndex()`, with no row or column given at all, is the real,
  standard way Qt represents "no cell," and reads `False`.
- *Its use:* `if not current.isValid():`, the first real check inside
  `on_asset_submitted`'s own sibling method, `on_current_row_changed` —
  handling the real, honest case where nothing is currently selected at
  all (this project's own real starting state, before any row is ever
  clicked).
- *Type:* an instance method, on `QModelIndex` — reapplied from Lesson
  2.19/2.20's own general material, checked directly for the first
  time.
- *Responsibility:* answer one real, narrow question — does this index
  refer to anything real at all — nothing about what row or column it
  names if it does.
- *Depends on:* nothing; always answerable.
- *Connects to:* `current`, this lesson's own new parameter, received
  directly from `currentRowChanged`'s own real emission.
- *Shape:* the real, honest way this lesson's own code tells "an asset
  is selected" apart from "nothing is selected right now."

**`QAbstractItemView.setSelectionBehavior`**

- *What it is:* a real method every `QTableView` (and other item
  views) carries — controls whether clicking selects a single cell, an
  entire row, or an entire column.
- *Implementation:* `setSelectionBehavior(self, behavior: QAbstractItemView
  .SelectionBehavior) -> None` — `Qt`'s own real, confirmed default is
  `SelectionBehavior.SelectItems` (single-cell); `SelectionBehavior

- *Its use:* `self.assets_table.setSelectionBehavior(QAbstractItemView

- *Type:* an instance method, on `QAbstractItemView`.
- *Responsibility:* decide the real, visible *extent* of what gets
  highlighted per click — nothing about which row is "current" for

  lesson's own verification confirmed by observing `currentRowChanged`

- *Depends on:* nothing beyond the view already existing.
- *Connects to:* changes only how `QTableView`'s own internal click
  handling visually selects cells — this lesson's own real,
  user-facing polish, matching what the detail panel now actually
  reflects (a whole asset's worth of fields, not one cell's).
- *Shape:* a real, deliberate UX choice, not a requirement for
  `currentRowChanged` itself to work.

## Concept Unit: QItemSelectionModel and currentRowChanged

### The Problem

`self.assets_table` (2.19) has never had anything connected to react
when a user clicks a row — every signal this project has ever connected
has come from a widget or an action (2.11, 2.14, 2.17) this project's
own code built directly. Does `QTableView` already track "which row is
currently selected" as a real, separate object, and can that object's
own real signal be connected the identical way every other signal in
this project already has been?

> **Before reading on, try this:**

>   `None`, or a real, already-existing object?

>   specific cell, naming both. Given this lesson's own real subject is
>   a signal named `currentRowChanged`, specifically about rows, what do
>   you predict happens if a user clicks a *different column*, but the
>   *same row*, they were already on — does `currentRowChanged` fire
>   again, or does it only fire when the row itself actually changes?

### Isolated Concept

```python
from PySide6.QtCore import QAbstractTableModel, QModelIndex, Qt
from PySide6.QtWidgets import QApplication, QTableView

app = QApplication([])


class SimpleModel(QAbstractTableModel):
    def __init__(self, rows, parent=None):
        super().__init__(parent)
        self._rows = rows

    def rowCount(self, parent=QModelIndex()):
        return len(self._rows)

    def columnCount(self, parent=QModelIndex()):
        return 2

    def data(self, index, role=Qt.ItemDataRole.DisplayRole):
        if role == Qt.ItemDataRole.DisplayRole:
            return self._rows[index.row()][index.column()]
        return None


model = SimpleModel([("ThinkPad X1", "SN-001"), ("Dell Monitor", "SN-002")])
table = QTableView()
table.setModel(model)

print(table.selectionModel() is not None)

selection_model = table.selectionModel()

current_rows_seen = []
selection_model.currentRowChanged.connect(
    lambda current, previous: current_rows_seen.append(current.row())
)

print(selection_model.currentIndex().isValid())

table.selectRow(1)
print(current_rows_seen)
print(selection_model.currentIndex().row())

table.selectRow(0)
print(current_rows_seen)
```

### CS Lens

This is the same **Observer pattern** this project has already met

subject (`QItemSelectionModel`) announcing a real state change to

### SE Lens

The alternative not chosen is this project's own code tracking "which
row is selected" itself — a plain instance attribute, updated by
connecting directly to `QTableView`'s own lower-level `clicked` signal
and computing the row from the clicked index by hand. The real benefit
of `QItemSelectionModel` instead: Qt itself already tracks this real
state correctly, including cases this project's own code would
otherwise have to handle separately (keyboard-driven selection, for
example, never touched by this lesson at all) — reusing it means this
lesson's own new code is only ever a single `connect` call and a
handler, not a parallel tracking system.
