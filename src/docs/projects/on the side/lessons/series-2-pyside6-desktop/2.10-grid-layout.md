checkbox pairs arranged in a real two-row, two-column grid, using

`QVBoxLayout`/`QHBoxLayout` (Lesson 2.8) position widgets by the order
they're added; `QFormLayout` (Lesson 2.9) positions them by pairing a
label with a field. `QGridLayout` does neither — every widget states
its own exact position directly, which raises a real question neither
of the previous two layouts could ever run into: what happens when two
widgets claim the *same* position?

**What you need to know first.** Lesson 2.8 — `QVBoxLayout`,
`QHBoxLayout`, and the automatic re-parenting every layout performs,
reapplied here without changes. Lesson 2.9 — `QFormLayout`, directly
contrasted against this lesson's own explicit-position model.

## Objects and methods used

**`QGridLayout`**

- *What it is:* a real class from PySide6's `QtWidgets` module — a
  layout arranging widgets in a two-dimensional grid, each one placed
  at an explicit row and column.
- *Implementation:* `QGridLayout(parent: QWidget | None = None)`;
  `addWidget(self, widget: QWidget, row: int, column: int) -> None`;
  `rowCount(self) -> int`; `columnCount(self) -> int`; `itemAtPosition
  (self, row: int, column: int) -> QLayoutItem | None`; `count(self) ->
  int`.
- *Its use:* `grid.addWidget(QLabel("Theme:"), 0, 0)` and three more
  calls like it build a real, two-row, two-column settings screen.
- *Type:* a class, from `PySide6.QtWidgets` — a `QLayout`, the same
  base class every layout this project has used shares.
- *Responsibility:* track every widget added to it, at its own
  explicit row and column, and compute the real on-screen grid those
  positions describe — nothing about automatically resolving two
  widgets given the same position, this lesson's own second unit
  proves directly.
- *Depends on:* eventually needing a real widget to be set on, the same
  requirement every layout in this project has had since Lesson 2.8.
- *Connects to:* every widget passed to `addWidget` is automatically
  re-parented to `settings`, the identical mechanism Lesson 2.8 already
  proved, now confirmed for `QGridLayout` too.
- *Shape:* a third sibling of `QVBoxLayout`/`QHBoxLayout`/
  `QFormLayout` — same underlying layout machinery, purpose-built for
  explicit, two-dimensional positioning.

**`QCheckBox`**

- *What it is:* a real class from PySide6's `QtWidgets` module — a
  checkable box paired with a text label.
- *Implementation:* `QCheckBox(text: str = "", parent: QWidget | None =
  None)` — the identical constructor shape `QPushButton` (Lesson 2.5)
  already has.
- *Its use:* `QCheckBox("Dark mode")`/`QCheckBox("Enabled")` stand in as
  plausible settings controls, purely to give this lesson's own grid
  something real to arrange — not itself this lesson's own subject.
- *Type:* a class, from `PySide6.QtWidgets` — a `QWidget`, the same
  ancestry every widget in this project shares.
- *Responsibility:* display a checkable box with a label — nothing
  about this lesson depends on its checked/unchecked state, never read
  anywhere in this lesson's own code.
- *Depends on:* nothing beyond its own text to construct.
- *Connects to:* added to `grid` via `addWidget`, re-parented to
  `settings` the same way every other widget in this unit is.
- *Shape:* incidental content for this lesson's own real subject,
  `QGridLayout`'s positioning — not itself explored further.

**`QGridLayout.itemAtPosition`**

- *What it is:* a real method retrieving whatever occupies one specific
  grid cell.
- *Implementation:* `itemAtPosition(self, row: int, column: int) ->
  QLayoutItem | None` — returns `None` if nothing was ever placed at
  that exact position.
- *Its use:* `grid.itemAtPosition(0, 0).widget()` reads back the real
  widget occupying row 0, column 0 — this lesson's own proof mechanism
  throughout, including its second unit's own collision proof.
- *Type:* an instance method.
- *Responsibility:* report whatever single item currently occupies one
  specific cell — nothing about resolving ambiguity if more than one
  widget was ever added there.
- *Depends on:* the row/column position given.
- *Connects to:* reads directly from the grid's own internal position
  tracking, built up by every prior `addWidget` call.
- *Shape:* the read side of this lesson's whole grid — the direct
  counterpart to `addWidget`'s own write side.

## Concept Unit: Explicit Row/Column Positioning

### The Problem

Every layout this project has used so far positions widgets either by
the order they were added (`QVBoxLayout`/`QHBoxLayout`, Lesson 2.8) or
by pairing a label with a field (`QFormLayout`, Lesson 2.9) — neither
one lets a caller state a widget's own position directly. Does
`QGridLayout` genuinely let a widget be placed at an exact, chosen
row and column, and is that position something that can be read back
afterward, the same way every other real fact this project has proven
has been checkable?

> **Before reading on, try this:**
> - `QVBoxLayout.addWidget(widget)` and `QFormLayout.addRow(label,
>   field)` both take no explicit position at all — order alone decides
>   where each one lands. Given `QGridLayout`'s own name, what
>   additional arguments do you predict its own `addWidget` needs,
>   beyond just the widget itself?
> - If four widgets are added to a `QGridLayout` at rows 0 and 1,
>   columns 0 and 1 — one widget per combination — do you predict
>   `rowCount()` and `columnCount()`, checked afterward, report `2` and
>   `2`, or do they report something else, like the total number of
>   widgets added?

### Isolated Concept

```python
from PySide6.QtWidgets import QApplication, QCheckBox, QLabel, QWidget, QGridLayout

app = QApplication([])

settings = QWidget()
grid = QGridLayout(settings)

grid.addWidget(QLabel("Theme:"), 0, 0)
grid.addWidget(QCheckBox("Dark mode"), 0, 1)
grid.addWidget(QLabel("Notifications:"), 1, 0)
grid.addWidget(QCheckBox("Enabled"), 1, 1)

print(grid.rowCount())
print(grid.columnCount())
print(grid.itemAtPosition(0, 0).widget().text())
print(grid.itemAtPosition(1, 1).widget().text())
```

Run for real (`lab1_qgridlayout.py`, headless):

```
2
2
Theme:
Enabled
```

`grid.addWidget(widget, row, column)` — real, confirmed proof, not a
claim: each widget lands at exactly the position stated, real and
checkable afterward. `rowCount()`/`columnCount()` both read `2` — the
real, occupied grid size, not a running total of widgets added (four
widgets, a `2×2` grid). `itemAtPosition(0, 0).widget().text()` reads
`"Theme:"`, and `itemAtPosition(1, 1).widget().text()` reads
`"Enabled"` — real, confirmed proof every widget can be looked up again
by its own exact position, something no earlier layout in this project
has ever offered. A `QCheckBox` (this lesson's own second widget type,
otherwise unremarkable — a checkable box with a label, mechanically
close to `QPushButton`) is used here purely as a plausible settings
control, not itself the subject of this lesson.

Discarded: `settings`/`grid` exist only to prove `QGridLayout`'s own
positioning. Neither will appear in the Asset Manager project again.

### CS Lens

This is **coordinate-based addressing** — locating something by an
explicit `(row, column)` pair rather than by sequence or by a paired
label. This is a hard concept, worth more than one real-world
connection.

```
Also recognized in: a spreadsheet's own cell references (A1, B2), a
chessboard's own algebraic notation, a 2D array or matrix in any
programming language, city blocks addressed by explicit street/avenue
coordinates rather than sequential numbering
```

### SE Lens

The alternative not chosen is forcing every grid-shaped arrangement
through nested `QHBoxLayout`s inside a `QVBoxLayout` — one inner row
per grid row, built by hand. The real benefit of `QGridLayout` instead:
a widget can be placed, moved, or aligned to a specific position
directly, without restructuring nested layouts to do it — at the real
cost of a design that scales awkwardly once real content ends up
sparse or irregular (a grid with genuinely empty cells, or widgets
spanning multiple cells — both real `QGridLayout` features this lesson
doesn't use, matching its own blueprint note: knowing it exists is
enough for now).

## Concept Unit: Position Collisions

### The Problem

Every position in the previous unit's own grid was claimed by exactly
one widget. Does `QGridLayout` actually enforce that — refusing, or at
least warning, if two different widgets are given the identical
row/column — or does it silently accept both, with no error at all?

> **Before reading on, try this:**
> - If two separate `addWidget` calls both name row `0`, column `0`,
>   do you predict the second call raises a real, catchable error
>   (reapplying Lesson 1.11's own `try`/`except` material as the
>   mechanism that would be needed to survive it) — or does it run
>   without complaint?
> - If both calls do succeed with no error, do you predict the *first*
>   widget added is silently discarded in favor of the second, or does
>   `QGridLayout` keep track of both, even though only one can actually
>   be shown at that exact position?

### Isolated Concept

```python
from PySide6.QtWidgets import QApplication, QLabel, QWidget, QGridLayout

app = QApplication([])

settings = QWidget()
grid = QGridLayout(settings)

first = QLabel("First")
second = QLabel("Second")

grid.addWidget(first, 0, 0)
grid.addWidget(second, 0, 0)

print(grid.count())
print(grid.itemAtPosition(0, 0).widget().text())
```

Run for real (`lab2_collision.py`, headless):

```
2
First
```

Real, confirmed proof, not a claim: neither `addWidget` call raises
anything — both run silently, with no error and no warning at all,
directly answering this unit's own first Socratic question. `grid
.count()` reads `2` — real, confirmed proof `QGridLayout` genuinely
keeps track of *both* widgets, neither one discarded — but `grid
.itemAtPosition(0, 0)`, asked which widget actually occupies that cell,
reports only `"First"`, the one added first. `QGridLayout` accepts a
position collision without complaint, silently, and leaves the actual,
visible result — which widget is genuinely seen on screen, whether they
overlap — entirely undefined by anything this lesson's own proof can
show from property checks alone.

### SE Lens

The alternative not chosen — Qt's own actual design — would be raising
a real error the instant a second widget claims an already-occupied
position, the same fail-fast philosophy Lesson 1.8's own `dataclass`
mutable-default refusal already demonstrated for a completely different
kind of mistake. The real, honest cost of Qt's actual, more permissive
choice, proven directly above: a genuine position collision, an easy
mistake in a large, hand-built grid, produces no error at all — only a
visually wrong result a developer has to notice by eye, with nothing in
this lesson's own property checks able to catch it automatically beyond
knowing to look for it.
