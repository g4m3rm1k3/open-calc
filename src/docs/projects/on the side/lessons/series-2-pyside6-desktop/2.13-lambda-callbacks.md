## Terms used in this lesson

- **`lambda`** — reapplied in full from Lesson 1.13: a keyword building
  a nameless function directly inside an expression, its body limited
  to exactly one expression, automatically returned. Lesson 1.13's own
  real use was a `sorted(..., key=...)` argument; this lesson's own use
  is identical in kind — a small, throwaway transformation, defined
  inline, needed at exactly one call site — applied to `Signal.connect`
  instead.
- **closure** — new. A function (here, always a `lambda`) that
  references a name from the scope it was defined in, rather than one
  of its own parameters or local variables — the specific mechanism
  behind this lesson's own central problem: a closure captures the
  *name itself*, not a frozen snapshot of whatever that name currently
  points to, meaning its value can keep changing after the closure was
  created, right up until the moment it's actually called.

## Concept Unit: A `lambda` Carrying Extra Context

### The Problem

`Signal.connect` (Lesson 2.11) only ever takes one plain callable —
nothing about it lets extra, fixed information be handed along
separately. If a click needs to trigger `delete_item("ThinkPad X1")`
specifically — a real call needing a real argument `clicked` itself
never provides — is there a way to wire that up without writing an
entirely new, separately-named function just to hold that one fixed
string?

> **Before reading on, try this:**
> - Lesson 1.13 already proved `lambda x: x * 3` builds a real,
>   callable function inline. Given `Signal.connect` just needs *some*
>   callable, with no required shape beyond being callable at all, do
>   you predict a `lambda` with no parameters at all — `lambda:
>   delete_item("ThinkPad X1")` — is legal, connectable code?
> - `delete_item("ThinkPad X1")`, called directly, would run
>   immediately. Given `lambda`'s own body is evaluated only when the
>   `lambda` itself is *called*, not when it's *defined*, do you
>   predict `delete_item` actually runs the instant `connect(...)` is
>   called, or only later, when the button is genuinely clicked?

### Isolated Concept

```python
from PySide6.QtWidgets import QApplication, QPushButton

app = QApplication([])

button = QPushButton("Delete")

deleted = []


def delete_item(name):
    deleted.append(name)


button.clicked.connect(lambda: delete_item("ThinkPad X1"))

button.click()
print(deleted)
```

Run for real (`lab1_lambda_connect.py`, headless):

```
['ThinkPad X1']
```

`lambda: delete_item("ThinkPad X1")` — a nameless function taking no
parameters, its one expression a real call to `delete_item` with a
fixed, hard-coded argument — is itself the callable `connect` receives;
nothing about `delete_item`'s own two-argument... one-argument shape
needs to match `clicked`'s own signature at all, since the `lambda`
sits *between* them, absorbing the mismatch. `button.click()` — real,
confirmed proof, not a claim: `deleted` ends up holding exactly
`"ThinkPad X1"`, proving the `lambda`'s own body only actually ran once
the button was genuinely clicked, not the instant `connect` was called.

Discarded: `button`/`deleted`/`delete_item` exist only to prove this
mechanism. None will appear in the Asset Manager project again.

### CS Lens

This is a **closure** — this lesson's own new Term — a function
retaining access to a name from its own defining scope (here,
`delete_item`, a name from the surrounding module) even after that
scope has technically finished running. This is a hard concept, worth
more than one real-world connection.

```
Also recognized in: JavaScript's own closures, the exact same mechanism
under the identical name, a C# or Java lambda expression capturing a
local variable from its enclosing method, a Python generator function
retaining access to its own local variables between successive calls
```

### SE Lens

The alternative not chosen is a separately-defined, named function for
every single fixed variation — `def delete_thinkpad(): delete_item
("ThinkPad X1")`, one per real case. The real benefit of `lambda`
instead, per this lesson's own header: no separate name is spent on
something used exactly once, at exactly one `connect` call. The real
cost, this lesson's next two units both prove directly: a `lambda`'s
own simplicity hides real, easy-to-miss mistakes the moment more than
one gets built in a loop.

## Concept Unit: The Loop Variable Trap

### The Problem

If several buttons are built in a loop, each meant to delete its own,
different item, does connecting a `lambda` to each one — the identical
pattern the previous unit already proved works — correctly give each
button its own, distinct value, or does something about building them
all from the same loop variable go wrong?

> **Before reading on, try this:**
> - A **closure** (this lesson's own new Term) captures a *name*, not a
>   frozen value. Given a `for name in names:` loop reuses the exact
>   same variable, `name`, reassigning it on every iteration, do you
>   predict a `lambda` built inside that loop, referencing `name`
>   directly, captures each iteration's own distinct value — or does it
>   capture the one, shared variable itself, whatever it happens to
>   hold whenever the `lambda` is actually called later?
> - If three buttons are each connected to a `lambda` referencing the
>   identical loop variable, and all three are clicked only *after* the
>   loop has fully finished, what value do you predict every single one
>   of them reports — three different, correct values, or the same one,
>   repeated three times?

### Project Change

- **Change type:** N/A.
- **Location:** N/A.

### Isolated Concept

```python
from PySide6.QtWidgets import QApplication, QPushButton

app = QApplication([])

names = ["ThinkPad X1", "Dell Monitor", "Logitech Mouse"]
buttons = []
clicked_names = []

for name in names:
    button = QPushButton(f"Delete {name}")
    button.clicked.connect(lambda: clicked_names.append(name))
    buttons.append(button)

for button in buttons:
    button.click()

print(clicked_names)
```

Run for real (`break_loop_variable_capture.py`, headless) — this run
is *expected* to produce a wrong, surprising result:

```
['Logitech Mouse', 'Logitech Mouse', 'Logitech Mouse']
```

Real, confirmed proof, not a claim: every single button, when clicked,
reports `"Logitech Mouse"` — the *last* item in `names` — not each
button's own, distinct item. All three `lambda`s were built referencing
the identical `name` variable; per this lesson's own closure Term, none
of them captured a snapshot of its value at the moment they were
created — each one only looked up whatever `name` currently held, at
the moment it was actually *called*. By the time any button is clicked,
the loop that built all three has already finished, and `name` holds
only its own final value, shared identically by every closure that
referenced it.

Discarded: `names`/`buttons`/`clicked_names` exist only to prove this
failure. None will appear in the Asset Manager project again in this
exact, broken form.

### CS Lens

A direct application of the previous unit's own closure idea, now
proving its real, load-bearing edge case — worth its own real-world
connection, since this exact mistake recurs, under the identical name,
well beyond Python or Qt specifically.

```
Also recognized in: the identical "loop variable capture" bug in
pre-ES6 JavaScript (fixed language-wide by `let`'s own per-iteration
scoping), a classic C# gotcha with `foreach` variables captured by
lambdas in older language versions, a batch of scheduled callbacks all
firing with the same, final value of a shared counter variable
```

### SE Lens

The alternative not chosen is simply not noticing — this exact mistake
produces no error, no warning, nothing at all to suggest anything went
wrong; three buttons, each visibly labeled with its own distinct item
name, silently all doing the same thing when clicked. The real, honest
cost, proven directly above: this is precisely the "lambda soup" this
lesson's own blueprint entry warns against by name — not lambdas
themselves being dangerous, but this one, specific, easy-to-miss
pattern, repeated across a real application's own many buttons, each
one silently wrong in the identical way.

## Concept Unit: Binding the Value, Correctly

### The Problem

Python's own real, standard fix for this exact trap is a default
argument — `lambda name=name: ...` — since a default value *is*
evaluated once, at the moment the `lambda` itself is defined, unlike a
name referenced inside its own body. Does that fix alone work
correctly here, or does `clicked`'s own real, carried argument (this
lesson's own header already named it: `checked: bool`) interact with
it in some way that needs accounting for too?

> **Before reading on, try this:**
> - `lambda name=name: clicked_names.append(name)` gives `name` a
>   default value, evaluated once, at `lambda`-definition time — inside
>   the loop, once per iteration, per this lesson's own fix. Given
>   default values, once bound, don't change afterward the way a
>   referenced outer variable does, do you predict this alone fixes the
>   previous unit's own trap?
> - `clicked` itself always carries a real argument, `checked: bool`,
>   confirmed in this lesson's own header. If a `lambda`'s *first*
>   parameter is `name`, given a default value, and `clicked` fires,
>   passing its own real `checked` argument, do you predict Qt skips
>   passing it, since `name` already has a default — or does `checked`
>   get passed into that same first parameter position anyway,
>   overriding the very default this fix depends on?

### Isolated Concept

The fix, attempted without accounting for `clicked`'s own real
argument:

```python
from PySide6.QtWidgets import QApplication, QPushButton

app = QApplication([])

names = ["ThinkPad X1", "Dell Monitor", "Logitech Mouse"]
buttons = []
clicked_names = []

for name in names:
    button = QPushButton(f"Delete {name}")
    button.clicked.connect(lambda name=name: clicked_names.append(name))
    buttons.append(button)

for button in buttons:
    button.click()

print(clicked_names)
```

Run for real (`lab3_without_checked_param.py`, headless) — this run is
*expected* to still be wrong, for a new, different reason:

```
[False, False, False]
```

Real, confirmed proof, not a claim: the default-argument fix alone
isn't enough. `clicked`'s own real `checked: bool` argument, `False`
for these ordinary buttons, gets passed into the `lambda`'s own *first*
parameter position — `name` — the instant the button is clicked,
silently overwriting the exact default this fix was relying on. The
previous unit's own bug (every button reporting the same, wrong string)
is gone — replaced by a different one (every button reporting `False`,
`clicked`'s own argument, not any item name at all).

The real, complete fix, accounting for both facts together:

```python
for name in names:
    button = QPushButton(f"Delete {name}")
    button.clicked.connect(lambda checked=False, name=name: clicked_names.append(name))
    buttons.append(button)
```

Run for real (`lab2_default_arg_fix.py`, headless):

```
['ThinkPad X1', 'Dell Monitor', 'Logitech Mouse']
```

Real, confirmed proof, not a claim: with `checked=False` occupying the
first parameter position, `clicked`'s own real argument lands there
instead, harmlessly ignored — `name`, now the *second* position, still
receives its own per-iteration default correctly, since nothing from
`clicked` reaches that far. Each button now reports its own, correct,
distinct item.

The alternative not chosen — writing a real, separately-named method
