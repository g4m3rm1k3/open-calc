# Lesson 2.11: Signals and Slots

**What you will build.** `asset_manager/desktop/main.py`'s own "Add
Asset" button, inert since Lesson 2.5, finally does something: clicking
it opens the Asset editor Lesson 2.9 already built, standalone, in
`asset_editor.py`. Getting there requires two real, separate pieces —
`QPushButton.clicked.connect(...)`, wiring the click to a real Python
function, and a genuine `MainWindow(QMainWindow)` subclass, deliberately
deferred since Lesson 2.1, now finally necessary for a reason this
lesson proves concretely rather than asserts: a widget opened inside a
plain function, with nothing outside that function holding onto it,
gets silently garbage-collected the instant the function returns —
even though it was shown, even though nothing about calling `.show()`
raised any error at all. The transferable problem: Lesson 2.2 already
proved Qt's own event loop dispatches raw events like a window close
request to a specific, named method (`closeEvent`); **signals and
slots** are a second, higher-level mechanism, layered on top of that
same event loop, letting *any* widget announce "something happened to
me" and letting *any* function or method react — the actual, general
mechanism every widget's own inertness since Lesson 2.5 has been
waiting for.

**What you need to know first.** Lesson 2.5 — `QPushButton`, and
`hasattr(button, "clicked")`'s own proof that the signal already
exists, unconnected, since that lesson. Lesson 2.9 — `build_asset
_editor()`, the exact function this lesson's own slot finally calls
for real. Lesson 2.2 — event, event handler — directly contrasted
against this lesson's own signal/slot mechanism, a second, related but
distinct way Qt lets code react to something happening. Lesson 1.5 —
subclass, `super()` — reapplied here against a real, external framework
class for the first time in this project's own *permanent* code
(Lesson 2.2's own subclass was throwaway).

## Terms used in this lesson

- **signal** — new. A real Qt mechanism: an announcement a `QObject`
  broadcasts when something happens to it — `QPushButton.clicked`,
  already proven to exist in Lesson 2.5, is one. Distinct from an
  **event** (Lesson 2.2): an event is the event loop's own raw,
  low-level occurrence; a signal is a higher-level announcement a
  specific widget makes, often itself triggered internally by an event,
  but never requiring the code reacting to it to know anything about
  events, the event loop, or how the signal actually got triggered.
- **slot** — new. Any callable — an ordinary function, a bound method,
  even a lambda (a later lesson's own subject) — connected to a signal,
  called automatically every time that signal is emitted. Exists as the
  receiving half of the signal/slot pair: a signal alone announces
  nothing to anyone until at least one slot is connected to it.

## Objects and methods used

**`QPushButton.clicked`**

- *What it is:* a real signal every `QPushButton` carries — reapplied
  from Lesson 2.5, where its bare existence was proven
  (`hasattr(button, "clicked")`) without being explained or used.
- *Implementation:* emitted automatically whenever the button is
  clicked — by a real user, or, this lesson's own verification
  mechanism, by calling `button.click()` directly.
- *Its use:* `self.button.clicked.connect(self.open_asset_editor)` is
  this lesson's own real, central wiring — the exact call every widget
  lesson since 2.5 has been building toward.
- *Type:* a signal — a real object, but never constructed directly by
  application code; provided automatically by the `QPushButton` class
  itself.
- *Responsibility:* announce, to anything connected, that this specific
  button was clicked — nothing about what happens next, entirely the
  connected slot's own job.
- *Depends on:* the button actually being clicked, by a user or by
  `click()`.
- *Connects to:* whatever slot(s) are connected via `.connect(...)` —
  zero, one, or more than one, though this lesson connects exactly one.
- *Shape:* the announcing half of this lesson's whole mechanism.

**`Signal.connect`**

- *What it is:* a real method every signal has, wiring a slot to it.
- *Implementation:* `connect(self, slot: Callable) -> None` — accepts
  any callable: an ordinary function (this lesson's own first,
  isolated proof), or a bound method (`self.open_asset_editor`, this
  lesson's own real landing).
- *Its use:* the one call actually connecting `button.clicked` to real
  code — without it, `hasattr(button, "clicked")` (Lesson 2.5) proved
  the signal exists, but nothing was ever listening to it.
- *Type:* an instance method, on a signal object.
- *Responsibility:* register one callable to be invoked every time the
  signal it belongs to is emitted — nothing about un-registering it
  (`disconnect`, not used in this lesson).
- *Depends on:* a real, callable slot.
- *Connects to:* called once, at setup time, wiring the signal to
  whatever slot is given; the actual call to that slot happens later,
  automatically, whenever the signal fires.
- *Shape:* the wiring step — signal and slot exist independently until
  `connect` links them.

**`QPushButton.click`**

- *What it is:* a real method that programmatically simulates a real
  mouse click on a button, emitting its `clicked` signal exactly as a
  genuine click would.
- *Implementation:* `click(self) -> None`.
- *Its use:* `button.click()`, throughout this lesson's own
  verification, is what lets a headless, unattended script prove a
  signal/slot connection actually fires — no real mouse or display
  needed.
- *Type:* an instance method.
- *Responsibility:* trigger the exact same signal emission a real click
  would — nothing about visually depressing the button or any other
  cosmetic effect this lesson's own headless proof can't see anyway.
- *Depends on:* the button already existing.
- *Connects to:* emits `clicked`, which in turn calls every slot
  connected to it.
- *Shape:* this lesson's own entire verification mechanism — the
  concrete way "did the connection actually work?" gets a real, proven
  answer rather than a description of what should happen.

**`weakref.ref`**

- *What it is:* a real class from Python's own standard-library
  `weakref` module — a reference to an object that does *not* keep it
  alive, distinct from an ordinary variable, which does.
- *Implementation:* `weakref.ref(object) -> weakref` — calling the
  returned weak reference, `ref()`, returns the real object if it's
  still alive, or `None` if it's already been garbage collected.
- *Its use:* `weakref.ref(editor)`, in this lesson's own second unit,
  is the mechanism proving, directly, whether a widget with no
  ordinary reference holding it has actually been destroyed — without
  a weak reference, there would be no way to check *after the fact*
  whether garbage collection already happened.
- *Type:* a class, from Python's own standard library.
- *Responsibility:* observe whether an object is still alive, without
  itself being a reason it stays alive — the opposite of what every
  ordinary Python reference (a variable, a list entry, an instance
  attribute) does.
- *Depends on:* a real object to watch.
- *Connects to:* used purely as this lesson's own proof mechanism;
  never appears in `asset_editor.py` or the real, landed `main.py`.
- *Shape:* a diagnostic tool, not part of the real solution — the real
  fix, this lesson's own third unit, is a plain instance attribute,
  not a weak reference at all.

**`QMainWindow.__init__`** *(via* `super().__init__()`*)*

- *What it is:* `QMainWindow`'s own real constructor — reapplied from
  every lesson that's ever created a `QMainWindow` directly (Lesson 2.1
  onward), called here for the first time from *inside* a subclass's
  own `__init__`, rather than being the constructor called directly.
- *Implementation:* takes no required arguments beyond `self`; sets up
  everything `QMainWindow`'s own real estate (title, central widget
  slot, menu/toolbar/status bar regions) needs before any of this
  project's own code runs.
- *Its use:* `super().__init__()`, the first line of `MainWindow.__init__`,
  reapplying Lesson 1.5's own `super()` material against a real,
  external framework class for the first time in this project's own
  permanent code.
- *Type:* an instance method — a dunder method — inherited, not
  overridden, by `MainWindow`.
- *Responsibility:* everything `QMainWindow` itself has always been
  responsible for, since Lesson 2.1 — unchanged by subclassing it.
- *Depends on:* being called before any of `MainWindow`'s own
  `__init__` code runs — Qt itself requires this, the same requirement
  Lesson 1.5 already established for calling a parent's own `__init__`
  before adding a subclass's own setup.
- *Connects to:* called once, as `MainWindow.__init__`'s own first
  line; everything after it — `self.button`, the layouts, `self.editor`
  — depends on this call having already happened.
- *Shape:* the required first step of subclassing any real framework
  class this project will ever subclass.

## Concept Unit: Connecting a Signal to a Slot

### The Problem

Lesson 2.5 already proved `QPushButton` carries a real `clicked`
attribute a `QLabel` doesn't — but never connected anything to it,
deliberately. Does actually wiring a real function to that signal make
clicking the button run that function for real — and can that
connection be proven headless, with no real mouse or display involved
at all?

> **Before reading on, try this:**
> - Lesson 2.5 already proved `hasattr(button, "clicked")` is `True`.
>   Given a signal exists, but nothing is connected to it, what do you
>   predict happens when the button is clicked — nothing at all, or an
>   error, since nothing is listening?
> - If `button.clicked.connect(some_function)` genuinely wires the two
>   together, do you predict `some_function` runs immediately, the
>   instant `connect` is called — or only later, the next time the
>   button is actually clicked?
> - Given this project's own verification has always run headless, with
>   no real display or mouse (Lesson 2.1 onward), how do you predict a
>   real button click could ever be proven to work at all, without
>   either one?

### Isolated Concept

```python
from PySide6.QtWidgets import QApplication, QPushButton

app = QApplication([])

button = QPushButton("Click me")

clicks = []


def on_clicked():
    clicks.append("clicked!")


button.clicked.connect(on_clicked)

print(clicks)
button.click()
print(clicks)
button.click()
print(clicks)
```

Run for real (`lab1_signal_slot_basics.py`, headless):

```
[]
['clicked!']
['clicked!', 'clicked!']
```

`button.clicked.connect(on_clicked)` — real, confirmed proof, not a
claim: `clicks` starts empty, exactly as predicted, since nothing has
been clicked yet. `button.click()` — a real method simulating an
actual click, emitting `clicked` exactly as a genuine one would — runs
`on_clicked` automatically; `clicks` now holds one entry. A second
`button.click()` runs it again — `clicks` holds two. This is called a
**signal** (`clicked`, something `QPushButton` itself announces) wired
to a **slot** (`on_clicked`, the callable actually connected to it) —
real, confirmed proof the connection genuinely calls the connected
function, every single time the signal fires, not just once.

Discarded: `button`/`clicks`/`on_clicked` exist only to prove this
mechanism in its smallest possible form. Neither will appear in the
Asset Manager project again — deliberately kept free of any
`Asset`/`Owner` flavor, since this lesson's own real landing is
significant enough that reusing that flavor here risked hiding the
mechanism itself behind domain-shaped familiarity.

### Mechanical Walkthrough

- **`button.clicked`** — a real **signal**, reapplied from Lesson 2.5's
  own bare existence proof (`hasattr`), now actually used: accessed as
  a plain attribute, no parentheses, since it's a real object in its
  own right, not a method to call.
- **`.connect(on_clicked)`** — `Signal.connect`, this lesson's own
  central new method: registers `on_clicked` — passed by name, with no
  parentheses, reapplying Lesson 1.12's own first-class-function
  material directly — to be called automatically whenever `clicked`
  fires.
- **`button.click()`** — `QPushButton.click`, this lesson's own
  verification mechanism: simulates a real click, triggering the exact
  same signal emission a genuine one would.
- **`clicks.append("clicked!")`** — an ordinary `list.append` call,
  reapplied baseline fluency since Lesson 1.3, proving `on_clicked`
  genuinely ran, each time, by leaving a real, countable trace.

### CS Lens

This is the **Observer pattern** — one object (the button) maintaining
a list of interested parties (slots) and notifying each one
automatically when its own state changes, without needing to know
anything about who's listening or what they'll do. This is a hard
concept, worth more than one real-world connection — and one this
project has already met once, informally: Lesson 1.12's own `retire`/
`on_retired` callback pattern, and Lesson 2.2's own `closeEvent`
override, are both real instances of the identical underlying idea,
each with its own specific shape.

```
Also recognized in: JavaScript's addEventListener, a magazine
subscription — the publisher doesn't know or care who's subscribed,
only that it needs to notify everyone on the list, a stock ticker
broadcasting price changes to every subscribed display without knowing
how many there are or what they do with the update
```

### SE Lens

The alternative not chosen is the button itself directly calling
whatever it should trigger — hard-coding `open_asset_editor()` directly
inside `QPushButton`'s own click-handling code. The real benefit of
signals and slots instead: `QPushButton` itself never needs to know
anything about asset editors, or this project at all — it only knows
how to announce "I was clicked," and this project's own code decides,
entirely separately, what that announcement should trigger. The real
cost: tracing what actually happens when a button is clicked now
requires finding the `connect` call first, rather than reading straight
through the button's own code — a real, worthwhile tradeoff for
reusable, general-purpose widgets, but a genuine indirection all the
same.

## Concept Unit: The Garbage Collection Gotcha

### The Problem

If a slot's own job is opening a new widget — the Asset editor, this
project's own real goal — where should that widget actually be stored?
Nothing about the previous unit's own `on_clicked` needed to keep
anything alive afterward; a real editor widget, shown and then
apparently forgotten the instant the slot function returns, might be a
very different story.

> **Before reading on, try this:**
> - If a slot function creates a widget as a plain local variable,
>   calls `.show()` on it, and then returns — with nothing outside that
>   function keeping a reference to it — do you predict the widget
>   stays open and visible, the same way a real, standalone window
>   would, or does something happen to it once the function's own local
>   variable goes out of scope?
> - Python's own garbage collector (assumed general fluency since
>   Lesson 2.3) reclaims objects nothing references anymore. Given a
>   widget passed to `.show()` doesn't automatically create a new,
>   separate reference to itself anywhere else, do you predict `.show()`
>   alone is enough to protect it from being collected once its own
>   local variable disappears?

### Project Change

- **Reference Source:** No reference counterpart — original curriculum
  project.
- **Files affected:** none yet — this unit proves the problem in
  isolation before the next unit lands the real fix.
- **Change type:** N/A.
- **Location:** N/A.
- **Dependencies:** none beyond the previous unit's own.

### Isolated Concept

```python
import gc
import weakref

from PySide6.QtWidgets import QApplication, QLabel, QMainWindow, QPushButton

app = QApplication([])

window = QMainWindow()
button = QPushButton("Open Editor", window)

editor_ref = None


def open_editor_unsafe():
    global editor_ref
    editor = QLabel("I am an editor")
    editor.show()
    editor_ref = weakref.ref(editor)
    print("inside slot, editor.isVisible():", editor.isVisible())


button.clicked.connect(open_editor_unsafe)
button.click()

gc.collect()

print("editor_ref() after gc.collect():", editor_ref())
```

Run for real (`lab2_gc_gotcha.py`, headless):

```
inside slot, editor.isVisible(): True
editor_ref() after gc.collect(): None
```

`open_editor_unsafe` builds a real `QLabel`, shows it — `editor
.isVisible()` reads `True`, right there, inside the slot, real,
confirmed proof it genuinely displayed — and stores a **weak
reference** (`weakref.ref`, a reference that does *not*, itself, keep
an object alive) to it in `editor_ref`, purely so this proof can check
what happened *afterward*. `button.click()` runs the slot, which then
returns; `editor`, the slot's own local variable, goes out of scope the
instant that happens, and nothing else — no ordinary reference
anywhere — points to the real widget it named. `gc.collect()` forces
Python's own garbage collector to run immediately, rather than
whenever it otherwise would. Real, confirmed proof, not a claim:
`editor_ref()`, called afterward, returns `None` — the widget genuinely
was collected. `global editor_ref` (reapplied general Python fluency)
is only this proof's own way of checking from outside; the real,
underlying problem is `open_editor_unsafe` itself, which gives its own
widget nowhere to live once the slot returns.

Discarded: `window`/`button`/`open_editor_unsafe` exist only to prove
this failure. None will appear in the Asset Manager project again in
this exact, broken form.

### CS Lens

This is **object lifetime tied to scope**, colliding with a real UI
requirement that a shown widget needs to outlive the function that
created it — the identical underlying idea Lesson 2.3's own `QObject`
parent/child material already introduced from a different angle
(ownership determining lifetime), now shown from the *Python*
reference-counting side instead of Qt's own C++ side. This is a hard
concept, worth more than one real-world connection.

```
Also recognized in: a database connection opened inside a function and
never stored anywhere, silently closed the instant the function
returns, a file handle (Lesson 1.14's own subject) that goes out of
scope without an enclosing `with` keeping it open for later use, a
thread started inside a function with no reference kept, unable to be
joined or checked on afterward
```

### SE Lens

The alternative not chosen — leaving `open_editor_unsafe` exactly as
written — would produce a real, visible bug: an editor that flashes
open and then vanishes, or, depending on timing, never visibly appears
at all, with no error, no traceback, nothing printed to explain why.
The real, honest cost of this failure mode specifically: it's silent —
proven directly above, `editor.isVisible()` reads `True` right up until
the moment everything is quietly destroyed, with nothing in an
ordinary run (without this lesson's own deliberate `weakref`/
`gc.collect()` proof) ever announcing that anything went wrong at all.

## Concept Unit: A Real `MainWindow` and the Real Connection

### SE Lens

The alternative not chosen is keeping every widget as a plain local
variable inside `main()`, connecting signals to plain functions the way
this lesson's own first unit did. The real, honest reason that doesn't
scale here, proven directly by this lesson's own second unit: a plain
function has no natural place to keep a reference alive between calls,
and `main()` itself returns only once, at the very end of the whole
program — by then, `app.exec()` has already been blocking for the
entire run. A class instance, by contrast, persists for exactly as long
as something (here, `main()`'s own `window` variable, held alive until
`app.exec()` finally returns) keeps a reference to it — precisely the
lifetime an editor opened at some unpredictable, later moment actually
needs.
