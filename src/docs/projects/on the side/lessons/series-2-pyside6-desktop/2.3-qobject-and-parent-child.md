# Lesson 2.3: QObject and Parent/Child

**What you will build.** Nothing lands in the tracked project this
lesson — per its own blueprint entry, this is a throwaway experiment.
What gets proven instead is a real, concrete fact about how every
PySide6 object this project has created so far — `QApplication`,
`QMainWindow`, and, underneath both, `QObject` itself — actually
manages its own lifetime: not through Python's own reference counting
and garbage collection alone, but through a second, parallel ownership
system Qt maintains itself, where one object can be given a *parent*,
and destroying that parent automatically destroys every object it owns.
The transferable problem: every plain Python object this curriculum has
ever created (`Asset`, `Owner`, every throwaway class since Lesson 1.1)
is cleaned up whenever nothing references it anymore, and nothing
about deleting *one* object ever cascades to delete a *different* one
it happens to hold a reference to — Qt's own `QObject` genuinely does
not work that way, and this lesson proves the difference directly,
not by assertion.

**What you need to know first.** Lesson 2.1 — `QApplication`,
`QMainWindow` — both are real `QObject`s, though this lesson is the
first to say so explicitly. Nothing about Python's own garbage
collection has ever been formally taught in this curriculum — it's
assumed general fluency, the same category `if`/`for`/`import` joined
in Lessons 1.2/1.3/1.6 — but this lesson depends on the reader already
knowing, informally, that a plain Python object is normally cleaned up
once nothing refers to it anymore, since that's the exact baseline
this lesson's own contrast is built against.

## Terms used in this lesson

- **ownership** — new, in this specific sense: a real relationship Qt
  itself tracks between two `QObject`s, distinct from an ordinary
  Python reference. An object with a **parent** is *owned* by it —
  when the parent is destroyed, Qt destroys every object it owns
  too, automatically, regardless of whether any Python variable still
  refers to them.
- **`RuntimeError`** — new. A real, built-in exception Python raises
  for an error that doesn't fit any more specific built-in exception —
  distinct from Lesson 1.7's `TypeError` (wrong type), Lesson 1.8's
  `ValueError` (wrong value), and Lesson 1.15's `ImportError` (an
  import failed): none of those name what's actually wrong here. Exists
  here as the mechanism this lesson's second unit uses to prove a
  `QObject`'s underlying object has genuinely been destroyed.
- **object lifetime** — new. How long an object continues to exist and
  remain usable. Every plain Python object's own lifetime, until this
  lesson, has been governed entirely by whether anything still
  references it; this lesson proves a `QObject` with a parent has its
  lifetime governed by something else instead.

## Objects and methods used

**`QObject`**

- *What it is:* a real class from PySide6's `QtCore` module — the base
  class nearly every other Qt class, including `QApplication` and
  `QMainWindow`, ultimately inherits from.
- *Implementation:* `QObject(parent: QObject | None = None)` — its
  constructor optionally accepts a parent directly; `parent(self) ->
  QObject | None`; `children(self) -> list[QObject]`.
- *Its use:* used directly, on its own, as the plainest possible
  `QObject` — no window, no widget, nothing visual — specifically to
  isolate parent/child ownership from every other fact a `QMainWindow`
  would also carry.
- *Type:* a class, from `PySide6.QtCore`.
- *Responsibility:* provide Qt's own parent/child ownership tracking,
  and the machinery every more specific Qt class (a window, a button,
  an application) builds on top of.
- *Depends on:* nothing to construct one at all; optionally, a parent
  object.
- *Connects to:* every widget this project has created, or ever will
  create, is a `QObject` underneath — `QApplication` and `QMainWindow`
  both inherit from it, even though neither lesson introducing them
  said so explicitly until now.
- *Shape:* the true foundation of every PySide6 class this project
  uses — this lesson's own subject is a fact about *all* of them, not
  a narrow detail about one.

**`QObject.objectName`**

- *What it is:* a real method reporting a `QObject`'s own optional,
  human-readable name — unset by default.
- *Implementation:* `objectName(self) -> str` — returns an empty
  string if no name was ever set with the corresponding `setObjectName`
  (not used in this lesson).
- *Its use:* called on `child` purely as *some* real method call — any
  one would do — specifically to force Python to actually reach into
  `child`'s own underlying C++ object, the exact moment this lesson's
  second unit needs something to fail if that object is already gone.
- *Type:* an instance method.
- *Responsibility:* report one optional, cosmetic fact about an
  object — genuinely unrelated to this lesson's own subject, chosen
  only because it's a harmless, side-effect-free way to touch the
  object.
- *Depends on:* the object it's called on still existing.
- *Connects to:* nothing else in this lesson.
- *Shape:* an incidental probe, not this lesson's own subject.

**`QObject.parent`**

- *What it is:* a real method reporting an object's own current parent.
- *Implementation:* `parent(self) -> QObject | None` — returns the
  real parent object if one was set, `None` otherwise.
- *Its use:* `child.parent() is parent` proves, directly, that passing
  an object to `QObject(parent)`'s own constructor really does
  establish a real, checkable ownership relationship.
- *Type:* an instance method.
- *Responsibility:* report one fact — this object's current parent —
  nothing about the parent's own state.
- *Depends on:* the object it's called on.
- *Connects to:* set automatically by `QObject`'s own constructor, when
  a parent argument is given.
- *Shape:* the read side of a two-way relationship — `children()`,
  below, is its counterpart.

**`QObject.children`**

- *What it is:* a real method reporting every object a given `QObject`
  owns.
- *Implementation:* `children(self) -> list[QObject]`.
- *Its use:* `parent.children()` confirms, from the *other* direction,
  that the same relationship `child.parent()` reported is genuinely
  two-way and tracked by the parent too.
- *Type:* an instance method.
- *Responsibility:* report the current, real list of this object's own
  children — nothing about their own state beyond the fact of
  ownership.
- *Depends on:* the object it's called on.
- *Connects to:* updated automatically whenever a new `QObject` is
  constructed with this object as its parent.
- *Shape:* the counterpart to `parent()` — together, they prove the
  relationship from both ends.

## Concept Unit: The Parent/Child Relationship

### The Problem

Every plain Python object this curriculum has ever created has its own
lifetime governed entirely by references — an `Asset` stays alive as
long as some variable, list, or other object still points to it, with
no other mechanism involved at all. Does `QObject` track something
*else*, a real, explicit relationship between two objects, checkable
directly, the way `is` (Lesson 1.1) already lets a reader check
identity?

> **Before reading on, try this:**
> - `QObject(parent: QObject | None = None)` names its own first
>   argument `parent` directly. Given every constructor this curriculum
>   has ever written stores its own arguments as instance attributes
>   (Lesson 1.1 onward), what do you predict happens to that argument —
>   does it just get stored as a plain attribute, or does something
>   about "being a parent" specifically suggest more is going on?
> - If a `QObject` genuinely tracks its own children, do you predict
>   that tracking is one-directional (only the child knows its parent)
>   or two-directional (the parent can also list everything it owns)?
> - Plain Python has no built-in concept of "this object owns that
>   one" beyond ordinary references. Given that, do you predict
>   `QObject`'s own parent/child tracking is implemented using Python's
>   own object model directly, or does it depend on something outside
>   Python's own reference-counting entirely?

`QObject(parent)` — passing an already-existing `QObject` directly to
another one's own constructor — real, confirmed proof, not a claim:

created — the identical relationship, confirmed from the *other*
direction too. This is called **ownership**: `parent` now owns
`child`, a real, two-way, Qt-tracked fact, distinct from an ordinary
Python reference (nothing about `parent` holding a plain attribute
pointing at `child`, or vice versa, is what's happening here — Qt
itself maintains this relationship).

### CS Lens

This is the **Composite ownership pattern** — a real, tracked
containment hierarchy where a parent is explicitly responsible for the
objects beneath it, distinct from the more general, implicit "anything
holding a reference" relationship most languages default to. This is a
hard concept, worth more than one real-world connection.

```
Also recognized in: a filesystem's own directory/file containment
(deleting a folder deletes everything inside it, regardless of whether
anything else references those files), a company's own organizational
chart determining who reports to whom, a DOM tree in a web browser,
where removing a parent element removes every element nested inside it
```

### SE Lens

The alternative not chosen — how every other class in this project has
worked since Lesson 1.1 — is relying entirely on Python's own reference
counting, with no explicit ownership concept at all. The real benefit
of Qt's own parallel system: a window with a hundred child widgets
never needs a hundred separate `del` statements, or careful tracking of
which Python variable still references which widget — destroying the
one parent is enough, proven directly in this lesson's second unit. The
real, honest cost: two lifetime systems now genuinely coexist for a
`QObject` — Python's own reference counting still applies to the
*Python wrapper* object, while Qt's own parent/child system separately
governs the *underlying* C++ object's real lifetime, a real source of
confusion this lesson's second unit makes concrete rather than
abstract.

## Concept Unit: Deleting a Parent Deletes Its Children

### The Problem

If `parent` genuinely owns `child`, does destroying `parent` actually
destroy `child` too — automatically, with nothing explicit done to
`child` itself — or is `parent()`/`children()` just bookkeeping with no
real consequence for either object's own lifetime?

> **Before reading on, try this:**
> - In plain Python, if `owner` holds a reference to `child`, and
>   nothing else does, deleting `owner`'s own variable (`del owner`)
>   only removes *that one reference* — if `child` is still referenced
>   elsewhere, it survives untouched. Given `QObject`'s own parent/child
>   system was already proven to be something *more* than an ordinary
>   reference, do you predict deleting a parent still leaves an
>   otherwise-referenced child alone, or does it destroy the child
>   regardless?
> - If a `QObject`'s underlying real object is destroyed, and Python
>   code then tries to call a method on it, do you predict Python
>   simply returns some default, empty-seeming result, or does calling
>   a method on a genuinely destroyed object raise a real, catchable
>   error?

### Isolated Concept

```python
import gc

from PySide6.QtCore import QObject

parent = QObject()
child = QObject(parent)

print("child created, parent() is parent:", child.parent() is parent)

del parent
gc.collect()

try:
    print(child.objectName())
    print("child still usable after parent deleted")
except RuntimeError as error:
    print(f"RuntimeError: {error}")
```

Run for real (`lab2_child_deleted_with_parent.py`, headless):

```
child created, parent() is parent: True
RuntimeError: libshiboken: Internal C++ object (PySide6.QtCore.QObject) already deleted.
```

`del parent` removes this script's own only reference to the *Python
wrapper* around the parent object; `gc.collect()` (Python's own,
already-assumed-baseline garbage collection, forced to run immediately
rather than whenever it would happen on its own) triggers Python to
actually clean it up. Real, confirmed proof, not a claim: `child
.objectName()`, called immediately afterward, doesn't return some
default, empty value — it raises a real `RuntimeError`, with a specific
message naming exactly what happened: the underlying C++ object
`child` wraps has *already been deleted*. Nothing in this script ever
told `child` itself to be destroyed — deleting `parent` alone was
enough, real, confirmed proof of the exact claim this lesson's whole
second unit exists to prove: ownership isn't just bookkeeping, it's a
real cascade, entirely independent of whether `child` still has a
living Python reference (this script's own `child` variable is still
perfectly valid Python-side — the *object it wraps* is what's gone).

Discarded: `parent`/`child` exist only to prove this cascade. Neither
will appear in the Asset Manager project again.

```

```

### SE Lens

The alternative not chosen is leaving every `QObject` to Python's own

project. The real, honest cost of Qt's own parallel system, proven
directly by this unit's own `RuntimeError`: a `QObject`'s Python

destroyed underneath it, a genuinely confusing failure mode with no
equivalent anywhere in plain Python, worth knowing about specifically
