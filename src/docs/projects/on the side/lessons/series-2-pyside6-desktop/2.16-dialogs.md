# Lesson 2.16: Dialogs

**What you will build.** `AssetEditor` (Lesson 2.9, 2.14) stops being a
plain `QWidget` with no real way to close itself and becomes a real
`QDialog` — Qt's own class for exactly this shape of interaction:
collect input, then either confirm it or back out. A new "Cancel"
button, connected to `self.reject()`, gives this project's first real
way to close the editor without submitting anything. `MainWindow
.on_asset_submitted` (2.14, rewritten 2.15) gains real control over
that dialog's own lifecycle from the outside: a successful submission
now calls `self.editor.accept()`, actually closing the dialog; a
caught `InvalidAssetError` (2.15) now shows a real `QMessageBox
.warning(...)` — this project's first time actually telling the user
something went wrong, rather than only catching the error silently —
and deliberately leaves the dialog open afterward, so a bad submission
can be corrected without starting over.

**What you need to know first.** Lesson 2.14 — `AssetEditor(QWidget)`,
`asset_submitted`, and the reasoning that made `AssetEditor` a real
class at all. Lesson 2.15 — `InvalidAssetError`, `self.validation
_errors`, and `MainWindow.on_asset_submitted`'s own current `try`/
`except` shape, extended here rather than replaced. Lesson 2.11 —
`self.editor`, and the real garbage-collection reasoning that already
made `MainWindow` responsible for keeping it alive; this lesson adds a
second responsibility, controlling *when* it closes. Lesson 2.9 —
`QFormLayout.addRow`'s single-argument form, reused unchanged for the
new "Cancel" button.

## Terms used in this lesson

- **modal** — new. A window that blocks interaction with every other
  window in the same application until it's closed — exists so a user
  can't accidentally act on stale information in a background window
  while a dialog is still open, asking for a decision.
- **dialog result** — new. A small, fixed piece of state every
  `QDialog` carries, recording whether it was most recently confirmed
  or backed out of — exists so code outside the dialog can ask, after
  the fact, "did the user actually go through with this?"

## Objects and methods used

**`QDialog`**

- *What it is:* a real class from PySide6's `QtWidgets` module — a
  `QWidget` purpose-built for exactly one interaction shape: collect
  something from the user, then close, having either been confirmed or
  backed out of.
- *Implementation:* `QDialog(parent: QWidget | None = None)`; carries
  `exec(self) -> int`, `accept(self) -> None`, `reject(self) -> None`,
  and `result(self) -> int`.
- *Its use:* `AssetEditor(QDialog)`, this lesson's own real, central
  change — `AssetEditor` was a plain `QWidget` (2.9, 2.14) with no real
  concept of "confirmed" or "backed out of" at all.
- *Type:* a class, from `PySide6.QtWidgets` — a `QWidget` subclass, the
  same ancestry every widget in this project already shares.
- *Responsibility:* everything a `QWidget` already does (2.1 onward),
  plus a real, tracked `result` reflecting whether `accept`/`reject` was
  most recently called — nothing about what "confirmed" or "backed out
  of" means for any specific dialog's own content; that's left entirely
  to the subclass.
- *Depends on:* nothing beyond a `QApplication` already existing, the
  same requirement every widget has carried since Lesson 2.1.
- *Connects to:* `AssetEditor`'s own `cancel_button.clicked` connects to
  `self.reject`; `MainWindow.on_asset_submitted`, outside `AssetEditor`
  entirely, calls `self.editor.accept()` directly.
- *Shape:* this project's first real `QDialog` — every dialog this
  project builds from here forward inherits this same real shape.

**`QDialog.exec`**

- *What it is:* a real method every `QDialog` carries — runs the dialog
  **modally**: shows it, and blocks the calling code, right where it's
  called, until the dialog closes.
- *Implementation:* `exec(self) -> int` — the real return value is
  always one of `QDialog.DialogCode`'s two members, `Rejected = 0` or
  `Accepted = 1`; `QDialog.DialogCode` is a real enum, also from
  `PySide6.QtWidgets`.
- *Its use:* `dialog.exec()`, this lesson's own isolated proof — called
  directly, rather than `.show()`, specifically to demonstrate real
  modal blocking before this lesson's own real landing makes a
  different, deliberate choice not to use it.
- *Type:* an instance method, on `QDialog`.
- *Responsibility:* show the dialog, prevent interaction with anything
  else in the application, and not return control to the calling code
  at all until `accept`/`reject` is called — nothing about what happens
  afterward; that's the caller's own job, once `exec` finally returns.
- *Depends on:* the dialog eventually calling `accept`/`reject` on
  itself, directly or indirectly (a connected button, for example) —
  otherwise `exec` never returns at all.
- *Connects to:* starts a real, nested event loop, separate from
  `app.exec()`'s own outer one (Lesson 2.2 onward); ends the instant
  `accept`/`reject` runs.
- *Shape:* the real, standard way a modal dialog is used — this
  lesson's own real landing deliberately doesn't call it, explained in
  this lesson's own SE Lens.

**`QDialog.accept`** *(and* `QDialog.reject`*)*

- *What it is:* a real method pair every `QDialog` carries — closes the
  dialog and records which outcome actually happened.
- *Implementation:* `accept(self) -> None` — sets `result()` to
  `QDialog.DialogCode.Accepted` (`1`) and hides the dialog;
  `reject(self) -> None` — sets `result()` to `QDialog.DialogCode
  .Rejected` (`0`) and hides the dialog.
- *Its use:* `self.cancel_button.clicked.connect(self.reject)`, inside
  `AssetEditor.__init__`, this lesson's own real, permanent wiring;
  `self.editor.accept()`, inside `MainWindow.on_asset_submitted`, called
  from *outside* `AssetEditor` entirely, on a successful submission.
- *Type:* an instance method pair, on `QDialog`.
- *Responsibility:* `accept` and `reject` each do exactly two things —
  record which outcome happened, and close the dialog — nothing about
  validating whether that outcome was actually earned; any code calling
  either one is responsible for deciding that first.
- *Depends on:* nothing beyond the dialog already existing; either can
  be called at any time, by anything with a reference to the dialog.
- *Connects to:* `accept`/`reject` are themselves real, callable slots
  (Lesson 2.11) — connectable to any signal, the same as any ordinary
  method; `cancel_button.clicked` connects directly to `reject` with no
  wrapping function needed, reapplying Lesson 2.11's own "a bound method
  is a real, callable slot" material.
- *Shape:* the two real ways a `QDialog`'s own lifecycle actually ends.

**`QDialog.result`**

- *What it is:* a real method every `QDialog` carries — reports which
  outcome, `Accepted` or `Rejected`, most recently happened.
- *Implementation:* `result(self) -> int` — reads `Rejected` (`0`) by
  default, before either `accept`/`reject` has ever been called.
- *Its use:* `editor.result()`, in this lesson's own verification,
  confirms the real, current outcome directly, without needing to
  separately track it.
- *Type:* an instance method.
- *Responsibility:* report the single, current outcome — nothing about
  the dialog's own visibility or content.
- *Depends on:* nothing; always answerable, even before the dialog has
  ever been shown.
- *Connects to:* reads whatever `accept`/`reject` (above) most recently
  set.
- *Shape:* the read side of the same real state `accept`/`reject`
  write to.

**`QMessageBox`**

- *What it is:* a real class from PySide6's `QtWidgets` module — a
  `QDialog` subclass, pre-built specifically for showing a short
  message and collecting one simple response (`OK`, `Cancel`, `Yes`,
  and similar).
- *Implementation:* `QMessageBox.warning(parent: QWidget | None, title:
  str, text: str) -> QMessageBox.StandardButton` — a real `staticmethod`
  (Lesson 1.3's own material, reapplied): called on the class itself,
  `QMessageBox.warning(...)`, never on an instance, since no instance
  exists yet when it's called; internally constructs a real
  `QMessageBox`, shows it modally (via its own internal `exec()`,
  identical in kind to `QDialog.exec` above), and returns which
  standard button the user actually clicked.
- *Its use:* `QMessageBox.warning(self.editor, "Invalid Asset",
  str(error))`, inside `MainWindow.on_asset_submitted`, this lesson's
  own real, central use — showing the exact message `InvalidAssetError`
  (2.15) already carries.
- *Type:* a class, from `PySide6.QtWidgets` — a `QDialog` subclass;
  `warning` itself is a `staticmethod` on that class, not an instance
  method.
- *Responsibility:* build, show, and wait for a response to one
  complete warning dialog in a single call — nothing about deciding
  *when* a warning is warranted; that's entirely the caller's own job.
- *Depends on:* a parent widget (or `None`), a title, and the message
  text to display.
- *Connects to:* internally builds a real `QMessageBox` instance and
  calls its own `exec()`; this lesson's own verification locates that
  instance afterward via `QApplication.activeModalWidget` (below),
  since `warning` itself never hands the caller a direct reference to
  it.
- *Shape:* a real, pre-built convenience over constructing a
  `QMessageBox` and calling `exec()` by hand — this project's first use
  of a `QDialog` subclass it didn't write itself.

**`QMessageBox.text`**

- *What it is:* a real method every `QMessageBox` carries — reports the
  message string it was constructed with.
- *Implementation:* `text(self) -> str`.
- *Its use:* `box.text()`, in this lesson's own verification, confirms
  the exact message `QMessageBox.warning` was given actually landed on
  the real, constructed dialog.
- *Type:* an instance method, on `QMessageBox`.
- *Responsibility:* report the message text currently set — nothing
  about the dialog's own title or buttons.
- *Depends on:* the message box already being constructed with real
  text.
- *Connects to:* reads back whatever `QMessageBox.warning`'s own third
  argument (or, on a hand-built `QMessageBox`, `setText`) most recently
  set.
- *Shape:* this lesson's own real verification mechanism — never called
  from inside `main.py` itself.

**`QMessageBox.button`** *(and* `QMessageBox.StandardButton`*)*

- *What it is:* a real method retrieving the actual button widget for
  one of a `QMessageBox`'s own standard buttons; `QMessageBox
  .StandardButton` is a real enum, also from `PySide6.QtWidgets`, naming
  every button a `QMessageBox` can show.
- *Implementation:* `button(self, which: QMessageBox.StandardButton) ->
  QAbstractButton` — `QMessageBox.StandardButton.Ok`, the only member
  this lesson's own code uses, has the real value `1024`; the enum
  itself has many other real members (`Cancel`, `Yes`, `No`, and
  others) not used anywhere in this lesson.
- *Its use:* `box.button(QMessageBox.StandardButton.Ok)`, in this
  lesson's own verification, retrieves the real, actual `OK` button
  widget so it can be clicked directly — the same real click-simulation
  technique (`QPushButton.click`, Lesson 2.11) already used throughout
  this project, applied here to a button this project's own code never
  explicitly constructed.
- *Type:* an instance method, on `QMessageBox`.
- *Responsibility:* translate a named standard button into the real
  widget `QMessageBox` itself built for it — nothing about clicking it.
- *Depends on:* the requested button actually being one this specific
  `QMessageBox` was told to show; `QMessageBox.warning`'s own default
  is exactly one button, `Ok`.
- *Connects to:* the returned button is a real `QPushButton`-like
  object; clicking it is what actually makes the message box's own
  internal `exec()` return.
- *Shape:* this lesson's own real verification mechanism — never called
  from inside `main.py` itself.

**`QApplication.activeModalWidget`**

- *What it is:* a real method every `QApplication` carries — reports
  whichever modal widget, if any, currently has exclusive interaction.
- *Implementation:* `activeModalWidget(self) -> QWidget | None` — `None`
  if nothing modal is currently open.
- *Its use:* `app.activeModalWidget()`, in this lesson's own
  verification, is the concrete way a headless script locates the real
  `QMessageBox` `QMessageBox.warning` builds internally — `warning`
  itself returns no reference to it until *after* it closes, so nothing
  else can find it while it's still open.
- *Type:* an instance method, on `QApplication`.
- *Responsibility:* report exactly one fact — which widget, if any,
  currently has modal focus — nothing about the widget's own content.
- *Depends on:* a real `QApplication` already existing; something
  modal actually being open at the moment it's called.
- *Connects to:* used here purely as this lesson's own proof mechanism,
  scheduled via `QTimer.singleShot` (2.1) to run *while* `QMessageBox
  .warning`'s own internal `exec()` is still blocking.
- *Shape:* a diagnostic/verification tool — never appears inside
  `main.py` or `asset_editor.py` themselves.

## Concept Unit: Modal Execution and Dialog Result

### The Problem

`AssetEditor` (2.9, 2.14) has never had a real way to close itself —
`MainWindow.open_asset_editor` (2.11) shows it and nothing else ever
tells it to close; the same is true of every `QWidget` this project has
ever built. `QDialog` claims to add exactly that. Does `.exec()`
genuinely block the calling code until the dialog closes — and if so,
how could a headless script, with no real user to click anything, ever
prove that without hanging forever?

> **Before reading on, try this:**
> - Every widget shown so far used `.show()` (2.1 onward), which
>   returns immediately, letting the rest of the calling code keep
>   running right away. Given `QDialog.exec()` is described as
>   "blocking," what do you predict happens to a line of code written
>   directly after `dialog.exec()` — does it run immediately, the same
>   as after `.show()`, or does it wait for something first?
> - This project's own established technique for testing something
>   that needs to happen *while* a blocking call is still running is
>   `QTimer.singleShot` (Lesson 2.1, used there to auto-quit `app
>   .exec()`). Given `dialog.exec()` won't return until `accept`/
>   `reject` is called, what do you predict `QTimer.singleShot` could be
>   used for here, scheduled *before* calling `exec()`?

### Isolated Concept

```python
from PySide6.QtCore import QTimer
from PySide6.QtWidgets import QApplication, QDialog, QPushButton, QVBoxLayout

app = QApplication([])


class ConfirmDialog(QDialog):
    def __init__(self) -> None:
        super().__init__()
        self.ok_button = QPushButton("OK")
        self.ok_button.clicked.connect(self.accept)
        layout = QVBoxLayout(self)
        layout.addWidget(self.ok_button)


dialog = ConfirmDialog()

print(dialog.result())

QTimer.singleShot(50, dialog.ok_button.click)
outcome = dialog.exec()

print(outcome)
print(outcome == QDialog.DialogCode.Accepted)
print(dialog.result())
```

Run for real (`lab1_qdialog_exec.py`, headless):

```
0
1
True
1
```

`dialog.result()`, before `exec()` is ever called, already reads `0` —
real, confirmed proof `QDialog.DialogCode.Rejected` (`0`) is the real,
built-in default, even for a dialog that's never been shown at all.
`QTimer.singleShot(50, dialog.ok_button.click)` schedules a real click
50 milliseconds in the future — but `dialog.exec()` is called
immediately after, on the very next line; real, confirmed proof this
unit's own first Socratic question: `exec()` genuinely blocks, since
nothing after it — including the scheduled timer itself — ever gets a
chance to run until `exec()`'s own internal, nested event loop starts
processing events, which is exactly when the 50-millisecond timer
finally fires, clicks `ok_button`, and that click's own `self.accept()`
call is what makes `exec()` finally return. `outcome` reads `1`, real,
confirmed proof `exec()`'s own return value is exactly `QDialog
.DialogCode.Accepted`; `dialog.result()`, read again afterward, matches.

Discarded: `ConfirmDialog`, `dialog`, and `ok_button` exist only to
prove this mechanism in its smallest possible form. None will appear in
the Asset Manager project again — `AssetEditor`'s own real Cancel
button, next unit, uses `reject`, not `accept`, and this project's own
real landing deliberately never calls `.exec()` at all.

### CS Lens

This is a **nested (re-entrant) event loop** — a second, independent
event-processing loop, started from inside code that's already running
as a *result* of the outer event loop (`app.exec()`, Lesson 2.2)
processing some other event, and which must itself finish before
control returns to whatever called it. This is a hard concept, worth
more than one real-world connection.

```
Also recognized in: a debugger's own breakpoint pause, which runs its
own inner command loop without ever exiting the paused program, a
recursive function call, an operating system's own modal "Save changes
before closing?" prompt, blocking the rest of the desktop until
answered, a web browser's own synchronous `alert()` call, halting all
further JavaScript execution until dismissed
```

### SE Lens

The alternative not chosen is a plain, non-modal `.show()` (2.1
onward), the same call every other widget in this project has used.
The real benefit of `.exec()` instead: the calling code can write
straight-line logic — "show this, then, once it's actually done, do the
next thing" — without needing a separate signal connection just to find
out when the dialog finished; `outcome = dialog.exec()` reads almost
exactly like calling any ordinary function that returns a value. The
real cost: nothing else in the entire application can be interacted
with while `exec()`'s own nested loop is running — a real, deliberate
tradeoff this lesson's own next two units decide, for a real, honest
reason, not to make for `AssetEditor` itself.
