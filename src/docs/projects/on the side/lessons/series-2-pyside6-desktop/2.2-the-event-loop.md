# Lesson 2.2: The Event Loop

**What you will build.** Two throwaway proofs, no permanent project
code — this lesson's own blueprint entry says "survives conceptually,"
not "survives," and that distinction is deliberate: everything genuine
this lesson needs — a real subclass of `QMainWindow`, a real overridden
event-handling method — is the same shape a later lesson (`QPushButton`,
Series 2's own next real widget) will need to introduce for real
anyway, so nothing here is worth landing twice. What gets proven
instead is the complete cycle Lesson 2.1 left half-drawn: `main() →
event loop → user interaction → callback → event loop`. Lesson 2.1
proved the event loop blocks and can be stopped; Lesson 1.12 already
proved a function can be handed to other code and called later. This
lesson connects them for real, tracing one concrete interaction —
closing a window — all the way through: from a real, running event
loop, to a real callback Qt itself calls automatically, back to that
same loop noticing there's nothing left to wait for.

**What you need to know first.** Lesson 2.1 — `QApplication`,
`QMainWindow`, `app.exec()`'s own blocking behavior, `QTimer.singleShot`.
Lesson 1.5 — subclass, parent class, overriding, `super()` — Lesson
1.5's own demonstration was explicit throwaway, never landing in this
project; this lesson is the first time subclassing lands against a
*real*, external, framework-provided class rather than a small,
custom one. Lesson 1.12 — first-class object, callback — this
lesson's own "callback" step is the concrete, real case that whole
lesson was building toward.

**Scope note.** This lesson deliberately does not use PySide6's own
Signals and Slots mechanism — that's Lesson 2.11's own subject,
described in its own blueprint entry as "one of the major Qt lessons,"
and using it here first would deliver, ahead of schedule, exactly what
that lesson is meant to teach in full. This lesson's own callback
instead uses a different, equally real Qt mechanism: overriding a
window's own event-handling method directly, the same overriding idea
Lesson 1.5 already taught, applied here to a framework-provided method
for the first time.

## Terms used in this lesson

- **event** — new. A single, specific occurrence the event loop
  dispatches — a mouse click, a key press, a timer firing, or, this
  lesson's own concrete example, a request to close a window. Distinct
  from the **event loop** itself (Lesson 2.1): the loop is the
  mechanism that waits and dispatches; an event is one specific thing
  it dispatches.
- **event handler** — new. A method Qt itself calls automatically,
  by name, in direct response to one specific kind of event —
  `closeEvent`, this lesson's own example, is called automatically the
  instant a window receives a close request, the exact same "Qt looks
  for a specific, reserved name and calls it for you" shape Lesson
  1.9's own `__post_init__` already established for `dataclass`,
  applied here by a GUI framework instead.

## Objects and methods used

**`LoudWindow` (this lesson's own throwaway subclass)**

- *What it is:* a throwaway class, subclassing `QMainWindow` directly —
  this project's first subclass of any real PySide6 class.
- *Implementation:* `class LoudWindow(QMainWindow): def
  closeEvent(self, event): print(...); event.accept()` — overrides one
  specific method, `closeEvent`, inherited from `QMainWindow`'s own
  parent classes.
- *Its use:* proves overriding a framework-provided event handler
  actually works, and traces exactly when Qt calls it.
- *Type:* a class — a subclass.
- *Responsibility:* nothing beyond what any `QMainWindow` already does,
  plus one specific, added reaction to being closed.
- *Depends on:* `QMainWindow` already providing a `closeEvent` method to
  override in the first place.
- *Connects to:* Qt's own event-dispatch machinery calls
  `LoudWindow.closeEvent` automatically; nothing in this lesson's own
  code calls it by name directly.
- *Shape:* a throwaway demonstration of the exact same shape a real,
  permanent window subclass will eventually take.

**`QWidget.closeEvent`**

- *What it is:* a real method every `QWidget` (and therefore every
  `QMainWindow`, which is one) already has — Qt calls it automatically
  whenever that widget receives a request to close.
- *Implementation:* `closeEvent(self, event: QCloseEvent) -> None` —
  its real signature; the default implementation, inherited unless
  overridden, simply allows the close to proceed.
- *Its use:* overridden by `LoudWindow` to run custom code — a
  `print`, standing in for whatever real reaction a later lesson might
  need — at the exact moment a close request arrives.
- *Type:* an instance method, meant to be overridden.
- *Responsibility:* decide whether, and how, this specific widget
  actually closes — accepting or rejecting the request, and doing
  anything else the override adds.
- *Depends on:* being called by Qt's own event-dispatch code — never
  meant to be called directly by application code.
- *Connects to:* called automatically, by Qt, whenever `window.close()`
  is called or a real close request (a user clicking a window's own
  close button) arrives; this lesson's own override calls
  `event.accept()` in turn, telling Qt the close should proceed.
- *Shape:* a framework-defined extension point — the exact mechanism
  this lesson's whole cycle is built around.

**`QCloseEvent.accept`**

- *What it is:* a real method on the event object `closeEvent`
  receives as its own parameter.
- *Implementation:* `accept(self) -> None` — marks the event as
  accepted, meaning the close should actually proceed.
- *Its use:* `event.accept()`, called inside `LoudWindow.closeEvent`,
  confirms the close should genuinely happen — without it, an override
  could instead call `event.ignore()` (not used in this lesson) to
  refuse the close entirely, useful for a future "unsaved changes"
  confirmation this project doesn't need yet.
- *Type:* an instance method.
- *Responsibility:* record one specific decision — proceed with the
  close — nothing about the close itself, which Qt's own machinery
  carries out afterward.
- *Depends on:* being called from inside a real event handler that
  received this exact event object.
- *Connects to:* read by Qt's own event-dispatch code immediately after
  `closeEvent` returns, to decide whether to actually close the window.
- *Shape:* the reply half of the event-handler contract — `closeEvent`
  receives the request; `event.accept()` sends the answer back.

**`QWidget.close`**

- *What it is:* reapplied, in spirit, from Lesson 2.1's own `QMainWindow
  .show()` — a real method requesting that a widget close.
- *Implementation:* `close(self) -> bool` — triggers `closeEvent`
  (possibly asynchronously, depending on how it's invoked) and returns
  whether the close was actually accepted.
- *Its use:* `window.close()`, called directly in this lesson's first
  unit, and scheduled via `QTimer.singleShot` in its second, standing in
  for the "user interaction" step of this lesson's own cycle — a real
  user clicking a window's own close button triggers the identical
  method internally.
- *Type:* an instance method.
- *Responsibility:* request that this widget close, triggering its own
  `closeEvent` in the process.
- *Depends on:* the widget already existing.
- *Connects to:* calls `closeEvent` on the same object, synchronously
  when called directly (this lesson's first unit proves this), or as a
  dispatched event when triggered through a running event loop (this
  lesson's second unit).
- *Shape:* the trigger side of this lesson's whole cycle — the "user
  interaction" the diagram names.

## Concept Unit: Overriding an Event Handler

### The Problem

Lesson 1.5 already proved a class can override a method it inherits
from a parent class — but only ever demonstrated on a small, throwaway
example this project immediately discarded. Does that same mechanism
work identically against a *real*, external framework class like
`QMainWindow` — and if a window is asked to close, does overriding the
right method actually let custom code run in response?

> **Before reading on, try this:**
> - Lesson 1.5 already proved `class Cat(Animal):` can override a
>   method `Animal` already defines, and Python calls the *overridden*
>   version when it's invoked on a `Cat` instance. Given `QMainWindow`
>   is a real, ordinary Python class underneath its own framework
>   machinery, do you predict the identical mechanism works for
>   overriding one of *its* own methods?
> - `QMainWindow` already has some existing, default behavior for
>   closing — every window can already be closed without any custom
>   code at all. If a subclass overrides that specific method, do you
>   predict the override *replaces* the default behavior entirely, or
>   does something still need to happen to let the close actually
>   proceed?
> - If `window.close()` is called directly, with no event loop running
>   at all yet, do you predict the overridden method still runs
>   immediately, synchronously — or does it need a running event loop
>   to be dispatched at all?

### Isolated Concept

```python
from PySide6.QtWidgets import QApplication, QMainWindow


class LoudWindow(QMainWindow):
    def closeEvent(self, event):
        print("closeEvent fired: the user closed the window")
        event.accept()


app = QApplication([])

window = LoudWindow()
window.setWindowTitle("Asset Manager")
window.show()

print("before window.close()")
window.close()
print("after window.close()")
```

Run for real (`lab1_close_event.py`, headless):

```
before window.close()
closeEvent fired: the user closed the window
after window.close()
```

Real, confirmed proof, not a claim: `"closeEvent fired..."` prints
between the two `print` calls surrounding `window.close()` — the
overridden method genuinely ran, and it ran *synchronously*, as a
direct consequence of calling `close()`, with no event loop running at
all yet (`app.exec()` is never called in this script). `class
LoudWindow(QMainWindow):`, reapplying Lesson 1.5's own subclass syntax
exactly, is what makes this override possible at all — `QMainWindow`
already has its own default `closeEvent`, inherited from further up its
own class hierarchy, and `LoudWindow`'s own version replaces it, the
identical mechanism Lesson 1.5 proved on a small, throwaway example, now
proven against a real, external framework class. `event.accept()`
answers the one real question `closeEvent` exists to decide — should
this close actually proceed — confirming it should.

Discarded: `LoudWindow` exists only to prove overriding a framework
event handler works. It will not appear in the Asset Manager project
again in this exact form — the real subclass a later lesson lands will
look structurally identical, built for a real reason rather than as
a proof.

### CS Lens

This is the **Template Method pattern** — a base class defining the
overall structure of an operation (here, "close this widget"), with
specific steps left open for a subclass to fill in or override. This is
a hard concept, worth more than one real-world connection.

```
Also recognized in: a base HTTP request handler class whose subclasses
override only the specific method for GET or POST, a game engine's own
base "Actor" class calling a fixed lifecycle (spawn, update, destroy)
while subclasses override each step's own behavior, a recipe template
that fixes the overall steps (prep, cook, plate) while leaving specific
ingredients and techniques to the cook following it
```

### SE Lens

The alternative not chosen is a completely custom, non-inherited close
mechanism — a plain function a caller has to remember to call before
ever discarding a window. The real benefit of overriding an existing
framework method instead: Qt's own machinery already calls `closeEvent`
at every real path that can close a widget — a user's own click on a
window's title-bar close button, a programmatic `close()` call like
this lesson's own, or a parent application shutting down — meaning a
subclass gets its custom reaction wired into every one of those paths
automatically, rather than needing separate handling duplicated at each
one.

## Concept Unit: The Full Cycle, Through a Running Event Loop

### The Problem

The previous unit proved `closeEvent` fires — but synchronously, with
no event loop running, which is not how a real user's own click would
ever reach it. Does the identical override still fire correctly when
the "close" request arrives *through* a genuinely running event loop,
the way Lesson 2.1's own diagram — `main() → event loop → user
interaction → callback → event loop` — actually describes?

> **Before reading on, try this:**
> - Lesson 2.1 already proved `app.exec()` blocks until something calls
>   `app.quit()`. If a window's own close, rather than a direct
>   `app.quit()` call, is what eventually happens while the loop is
>   running, do you predict the loop notices and stops on its own, or
>   does it keep running even after every window is gone?
> - Given the previous unit proved `closeEvent` can fire synchronously,
>   with no event loop at all, do you predict scheduling the *same*
>   `window.close()` call through `QTimer.singleShot` (Lesson 2.1's own
>   mechanism) — this time *during* a running `app.exec()` — changes
>   anything about when `closeEvent` actually fires, or does it fire the
>   same way either way?
> - Trace the full diagram by name: `main()` calls `app.exec()`,
>   starting the event loop; some time later, an interaction happens.
>   What do you predict is the *last* line of output this lesson's own
>   proof produces — something printed by `closeEvent` itself, or
>   something printed after `app.exec()` finally returns?

### Isolated Concept

```python
from PySide6.QtCore import QTimer
from PySide6.QtWidgets import QApplication, QMainWindow


class LoudWindow(QMainWindow):
    def closeEvent(self, event):
        print("callback: closeEvent fired")
        event.accept()


app = QApplication([])

window = LoudWindow()
window.setWindowTitle("Asset Manager")
window.show()

print("main(): about to start the event loop")
QTimer.singleShot(100, window.close)
exit_code = app.exec()
print(f"back in main(): event loop exited with code {exit_code}")
```

Run for real (`lab2_full_cycle.py`, headless):

```
main(): about to start the event loop
callback: closeEvent fired
back in main(): event loop exited with code 0
```

This is a control-flow timing question, not a changing-value one — the
real proof is *when* each line runs, tracing the blueprint's own
diagram directly:

1. `print("main(): about to start the event loop")` — `main()`'s own
   code, running before the loop exists at all.
2. `QTimer.singleShot(100, window.close)` — schedules the "user
   interaction" step: `window.close`, named with no parentheses,
   reapplying Lesson 1.12's own callback material exactly the way
   Lesson 2.1 already used it for `app.quit`.
3. `exit_code = app.exec()` — **event loop**: starts running, blocking
   `main()`'s own code at exactly this line.
4. 100 milliseconds later, still inside that same `app.exec()` call,
   the scheduled `window.close()` fires — this is the diagram's own
   **user interaction** step, standing in for a real click.
5. `window.close()` triggers `LoudWindow.closeEvent` — the diagram's
   own **callback** step — printing `"callback: closeEvent fired"`,
   proving it ran *during* `app.exec()`, not before or after it.
6. `event.accept()`, inside that same callback, lets the close proceed;
   since this is the application's only open window, and `QApplication`
   quits automatically once its last window closes (confirmed this
   session: `app.quitOnLastWindowClosed()` is `True` by default), the
   loop itself decides to stop — the diagram's own **back to event
   loop** step, here meaning the loop noticing there's nothing left to
   wait for and ending on its own.
7. `app.exec()` finally returns, `exit_code` becomes `0`, and
   `"back in main(): event loop exited with code 0"` prints last —
   real, confirmed proof that control only returns to `main()`'s own
   code once the entire cycle has genuinely finished.

Discarded: `LoudWindow` and this whole script exist only to trace this
cycle. Neither will appear in the Asset Manager project again in this
exact form.

### CS Lens

A direct application of the previous unit's own event-handler idea,
now shown running through a genuine event loop rather than
synchronously — worth its own real-world connection, since tracing a
full request/response-style cycle recurs well beyond GUI programming.

```
Also recognized in: an HTTP request traveling through a web server's
own request-handling loop and back out as a response, a hardware
interrupt handler running mid-instruction on a CPU and returning control
once it finishes, a customer service call: hold music (the loop,
waiting), a specific request (the interaction), a specific agent's own
response (the callback), then back to the queue for the next caller
```

### SE Lens

The alternative not chosen is polling — repeatedly checking, in a tight
loop, "has the window been asked to close yet?" instead of waiting to
be told. The real tradeoff event-driven dispatch avoids: polling wastes
real CPU time checking a condition that's false the overwhelming
majority of the time, and either responds instantly (burning CPU
constantly) or with real, noticeable lag (checking only occasionally) —
an event loop instead sits idle, using essentially no CPU, until the
operating system itself wakes it up with something to actually do.
