## Objects and methods used

**`QPushButton`**

- *What it is:* a real class from PySide6's `QtWidgets` module — a
  clickable button widget.
- *Implementation:* `QPushButton(text: str = "", parent: QWidget | None
  = None)` — its constructor, identical in shape to `QLabel`'s own;
  `text(self) -> str`, the read side.
- *Its use:* `QPushButton("Add Asset", window)` is this project's first
  real button, parented to the same window `QLabel` was in Lesson 2.4.
- *Type:* a class, from `PySide6.QtWidgets` — a `QWidget`, and, beneath
  that, a `QObject` (Lesson 2.3), the identical ancestry `QLabel`
  already has.
- *Responsibility:* display a clickable button with a real label — and,
  distinctly from `QLabel`, carry the real machinery (a `clicked`
  signal, proven to exist in this lesson without being used) for
  reacting to being clicked.
- *Depends on:* being given its own text; nothing else to construct.
- *Connects to:* parented to `window` inside `main()`, the identical
  relationship `QLabel` had in Lesson 2.4's own throwaway proof, now
  landed for real.
- *Shape:* this project's first real, permanent, interactive widget —
  still inert, per this lesson's own scope, until Lesson 2.11 connects
  it to something.

**`hasattr`**

- *What it is:* a real Python built-in function, checking whether an
  object has an attribute with a given name.
- *Implementation:* `hasattr(object, name: str) -> bool`.
- *Its use:* `hasattr(button, "clicked")` proves, directly, that a real
  `QPushButton` instance carries something named `clicked` that a plain
  `QLabel` instance genuinely does not — this lesson's own central
  contrast, checked without ever using whatever `clicked` actually is.
- *Type:* a built-in free function.
- *Responsibility:* answer one yes/no question about a specific object
  — nothing about what the attribute actually contains or does.
- *Depends on:* the object and the attribute name it's given.
- *Connects to:* called directly in this lesson's own isolated proof.
- *Shape:* a minimal, safe way to observe that something exists without
  needing to explain or use it.

## Concept Unit: A Real, Interactive Widget

### The Problem

Lesson 2.4 already proved a `QLabel` can be created, parented to a
window, and made visible — and `QPushButton`'s own constructor, per
this lesson's own header, takes the identical shape. Is a button
genuinely just a label with a different visual style, or does Qt
itself already treat the two differently, in some real, checkable way,
before either one is ever clicked?

> **Before reading on, try this:**
> - `QPushButton(text, parent)` and `QLabel(text, parent)` share the
>   identical constructor shape, per this lesson's own header. Given
>   that, do you predict creating and parenting a button is any
>   different, mechanically, from creating and parenting a label — or
>   is the entire difference something that only shows up once a user
>   actually interacts with it?
> - A button exists specifically to be clicked; a label doesn't. If Qt
>   builds that distinction into the button *itself*, rather than
>   leaving it entirely to whatever code later decides to do with a
>   click, what kind of real, inspectable difference do you predict
>   exists between a fresh `QPushButton` instance and a fresh `QLabel`
>   instance, even before either one is clicked even once?

### Isolated Concept

This is exactly what `main.py`'s own new line depends on — proven both
sides of the real contrast between a button and a label:

```python
from PySide6.QtWidgets import QApplication, QLabel, QMainWindow, QPushButton

app = QApplication([])

window = QMainWindow()
button = QPushButton("Add Asset", window)
label = QLabel("Asset Manager", window)

print(button.text())
print(button.parent() is window)
print(hasattr(button, "clicked"))
print(hasattr(label, "clicked"))
```

Run for real (`lab1_qpushbutton.py`, headless):

```
Add Asset
True
True
False
```

`button.text()` and `button.parent() is window` reapply Lesson 2.4's
own proof, unchanged — real, confirmed evidence that a `QPushButton` is
constructed and parented exactly the way a `QLabel` is. The final two
lines are this lesson's own real subject: `hasattr(button, "clicked")`
reads `True` — a fresh `QPushButton` genuinely carries something named
`clicked`, real and inspectable, before it's ever been clicked once.
`hasattr(label, "clicked")` reads `False` — the identical check, on a
`QLabel`, finds nothing there at all. Real, confirmed proof, not a
claim: `QPushButton` and `QLabel` are not identical widgets wearing
different visual skins — one of them is genuinely, structurally built
for interaction, in a way checkable before any interaction ever
happens, and the other simply isn't.

This lesson deliberately stops here — `clicked` itself is never
connected to anything, never called, never explained beyond the bare
fact that it exists. What it actually *is*, and how to react to it,
is real, load-bearing content this lesson leaves entirely to Lesson
2.11's own subject.

Discarded: `label`, in this isolated proof, exists only for the
contrast. It will not appear in the Asset Manager project again in
this exact form. `button`, unlike every throwaway example so far, is
*not* discarded — it's the real, permanent widget this unit's own
Project Change already landed.
