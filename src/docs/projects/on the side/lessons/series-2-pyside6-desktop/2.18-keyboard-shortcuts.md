## Terms used in this lesson

- **key sequence** — new. One or more real keys, optionally combined
  with modifier keys (`Ctrl`, `Shift`, `Alt`), that together identify
  one specific keyboard shortcut — exists as its own real concept,
  separate from a single keypress, since a shortcut like `Ctrl+N`
  genuinely requires two keys held together, not one.
- **deprecated** — new. Marked by a library's own authors as still
  functional today but planned for eventual removal, with a preferred
  replacement usually named alongside the warning — exists so a
  library can signal "this still works, but stop building new code on
  it" without breaking everything that already depends on it
  immediately.

## Objects and methods used

**`QKeySequence`**

- *What it is:* a real class from PySide6's `QtGui` module — represents
  one real key sequence, independent of any specific action or widget.
- *Implementation:* `QKeySequence(sequence: str)` — parses a real
  string like `"Ctrl+N"`; `QKeySequence(key: QKeySequence.StandardKey)`
  — a separate real constructor overload, resolving a *platform-
  conventional* shortcut instead of a literal string; `toString(self)
  -> str`; `isEmpty(self) -> bool`.
- *Its use:* `QKeySequence("Ctrl+Q")` and `QKeySequence(QKeySequence
  .StandardKey.New)`, this lesson's own real, central objects — one
  built from a literal string, one from a real, named platform
  convention.
- *Type:* a class, from `PySide6.QtGui`.
- *Responsibility:* represent exactly one real key combination, and
  answer whether two are equal — nothing about what happens when it's
  actually pressed; that's `QAction`'s own job, once attached.
- *Depends on:* a real, valid sequence string, or a real
  `QKeySequence.StandardKey` member.
- *Connects to:* handed directly to `QAction.setShortcut` (below).
- *Shape:* the raw shortcut definition, separate from the action it
  will eventually be attached to.

**`QKeySequence.StandardKey`**

- *What it is:* a real enum, also from `PySide6.QtGui` — names common,
  platform-conventional shortcuts (`New`, `Quit`, `Save`, and many
  others) without the caller needing to know each platform's own
  literal key combination.
- *Implementation:* `QKeySequence.StandardKey.New` resolves, on this
  project's own real, current platform, to the identical real sequence
  `"Ctrl+N"` — confirmed directly, not assumed. `QKeySequence
  .StandardKey.Quit`, checked the identical way, does **not** resolve
  to `"Ctrl+Q"` here — it resolves to a special `Key_Exit` virtual key
  most physical keyboards don't have at all, real, confirmed proof a
  "standard" key can still be practically unusable on a specific,
  real, current platform.
- *Its use:* `QKeySequence(QKeySequence.StandardKey.New)`, this
  lesson's own real choice for the `New` action — confirmed correct
  before being relied on; `Exit` deliberately uses a literal
  `"Ctrl+Q"` string instead, for the concrete, verified reason above.
- *Type:* an enum, from `PySide6.QtGui`.
- *Responsibility:* map a named, common intent ("the shortcut for
  creating something new") to whatever the real, current platform
  actually expects — nothing about guaranteeing that mapping is always
  the single most useful choice, this lesson's own real, confirmed
  finding for `Quit`.
- *Depends on:* nothing beyond Qt's own platform detection, already
  resolved by the time this project's own code ever runs.
- *Connects to:* passed directly to `QKeySequence`'s own second
  constructor overload.
- *Shape:* a real, honest example of "conventional" not always meaning
  "correct for this specific case" — checked, not assumed, before this
  lesson relied on it for `Exit`.

**`QAction.setShortcut`** *(and* `QAction.shortcut`*)*

- *What it is:* a real method pair every `QAction` carries — attaches a
  real `QKeySequence` to the action, and reads back whichever one is
  currently attached.
- *Implementation:* `setShortcut(self, shortcut: QKeySequence) -> None`;
  `shortcut(self) -> QKeySequence` — returns an empty `QKeySequence`
  (`isEmpty()` reading `True`) if none has ever been set.
- *Its use:* `new_action.setShortcut(QKeySequence(QKeySequence
  .StandardKey.New))` and `exit_action.setShortcut(QKeySequence
  ("Ctrl+Q"))`, this lesson's own real, permanent landing;
  `edit_action.shortcut().isEmpty()`/`delete_action.shortcut().isEmpty()`,
  in this lesson's own verification, confirm neither one was ever given
  a shortcut at all.
- *Type:* an instance method pair, on `QAction`.
- *Responsibility:* hold a reference to at most one real key sequence
  per action, and, once one is set, make that action reachable by
  pressing it — nothing about *which* widget or window needs to be
  focused for that to work; that's governed by the action's own real,
  built-in shortcut context, unchanged by this lesson's own code.
- *Depends on:* a real `QKeySequence`, or an empty one to clear it.
- *Connects to:* once set, Qt's own real, internal shortcut-dispatch
  machinery watches for the matching key combination anywhere within
  the action's own reachable window, and calls `.trigger()` (2.17)
  automatically the moment it's pressed.
- *Shape:* the real attachment point between a key sequence and the
  action it activates — the same real relationship `QLineEdit
  .setValidator` (2.15) already established between a widget and the
  rule constraining it, applied here to a very different kind of rule.

**`QWidget.addAction`**

- *What it is:* a real method every `QWidget` carries — registers a
  real `QAction` as one this specific widget's own shortcut context
  actively watches, separate from that action's own real `QObject`
  parent (2.17), which only governs memory lifetime.
- *Implementation:* `addAction(self, action: QAction) -> None` — adds
  `action` to this widget's own real `actions()` list (2.17's own
  distinction: a `QAction`'s parent and a widget's own tracked actions
  are two separate, real facts).
- *Its use:* `window.addAction(new_action)`, in this lesson's own
  second unit, makes `new_action`'s own shortcut genuinely reachable
  from `window` directly — this lesson's own third unit proves a
  `QAction` reachable only through a menu, with no direct `addAction`
  call of its own, still works window-wide, without ever needing this
  method at all.
- *Type:* an instance method, on `QWidget`.
- *Responsibility:* add one real action to this widget's own tracked
  list — nothing about that action's own memory lifetime, already
  governed separately by its real `QObject` parent.
- *Depends on:* a real `QAction` to add.
- *Connects to:* every action a widget's own shortcut context can see
  — either added directly here, or reachable indirectly through a
  child widget like a `QMenu` (this lesson's own third unit's own real
  proof).
- *Shape:* this lesson's own second unit's own isolated verification
  mechanism — never called anywhere inside `main.py` itself, since the
  real project's own actions reach `window` indirectly, through
  `file_menu`.

**`QTest.keyClick`**

- *What it is:* a real function from PySide6's own `QtTest` module —

- *Implementation:* `QTest.keyClick(widget: QWidget, key: Qt.Key,

- *Depends on:* the target widget already existing and shown; the

- *Connects to:* dispatches through the identical real event path a

- *Shape:* this lesson's own entire verification mechanism for proving

**`QApplication.setActiveWindow`**
