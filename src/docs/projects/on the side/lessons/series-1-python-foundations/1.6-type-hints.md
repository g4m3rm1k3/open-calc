# Lesson 1.6: Type Hints

**What you will build.** Every parameter and return value in `Asset` and
`Owner` gains a written, checkable-by-eye type — turning two files whose
expected shapes previously lived only in prose (or in a reader's head)
into signatures a person, or a tool, can read cold. The project also
gains its first free function, `find_by_serial`, existing specifically
to give `list[Asset]` and `Optional[Asset]` a real, permanent use beyond
`Asset`/`Owner`'s own already-scalar parameters. Nothing about what any
of this code actually *does* at runtime changes — every value that
worked before this lesson still works exactly the same way afterward.
The transferable problem: documentation versus enforcement — writing
down what a function expects and returns, while proving, directly, that
Python itself never checks any of it.

**What you need to know first.** Lesson 1.1 — Classes and Objects:
`class`, `__init__`, instance attributes, `self`, `is`, `return`. Lesson
1.2 — Object State: `bool`, and `Asset.mark_retired`'s guard clause and
its two `bool` results — reused here only for orientation, since this
lesson's Updated Project steps show `mark_retired` exactly as Lesson 1.2
left its body. Lesson 1.4 — Composition: `Owner`, `Asset.owner`, and the
HAS-A relationship — reused directly, since this lesson's first real
annotation, `owner: Owner`, names the exact class Lesson 1.4 introduced.

**Baseline scope note.** Unchanged from Lessons 1.1–1.5 — general Python
fluency below the level of classes remains assumed and not re-taught
here. This lesson's own real project code introduces a `for` loop and
Python's `import` statement for the first time anywhere in this
project's tracked files; both are general Python fluency below the
level of classes, the same category `if` (Lesson 1.2) and list
literals/`.append()` (Lesson 1.3) already joined, and are added to that
same assumed baseline here rather than taught as new curriculum
concepts — recorded formally in `TAUGHT-CONCEPTS.md`.

## Terms used in this lesson

- **`self`** — reapplied in full from Lessons 1.1–1.5: the conventional
  name for an instance method's first parameter, automatically bound to
  the specific instance a method is called on.
- **instance attribute** — reapplied in full from Lesson 1.1: a piece of
  data stored on one specific instance, written as `self.x = value`.
- **method** — reapplied in full from Lesson 1.1: a function defined
  inside a class body whose first parameter is `self`.
- **`is`** — reapplied in full from Lesson 1.1: compares whether two
  names refer to the exact same object in memory, never whether their
  contents look alike.
- **`==`** — reapplied in full from Lesson 1.1, sharpened here: on a
  plain object with no `__eq__` of its own (an `Asset`, an `Owner`),
  `==` falls back to identity — the exact same comparison `is`
  performs. On a `str`, `==` performs value comparison instead, because
  `str` defines its own `__eq__` that compares characters, not
  identity. Same operator, different comparison, entirely depending on
  the type sitting on its left.
- **`return`** — reapplied in full from Lesson 1.1: ends a function
  immediately and hands a value back to whoever called it; a function
  with no `return` statement at all hands back `None`.
- **`bool`** — reapplied in full from Lesson 1.2, used here for the
  first time as a type *name* rather than a value: `True`/`False` are
  `bool` values; writing `bool` in an annotation names the type those
  values belong to.
- **`None`** — the singleton value meaning "no value" — used two
  genuinely different ways in this lesson: as an ordinary *value*
  (`return None`), and, distinctly, as a *type* inside an annotation
  (`Union[str, None]`), where it names "the type whose only possible
  value is `None`," not the value itself.
- **`NameError`** — a real, built-in exception Python raises when it
  evaluates a name — a variable, a class, anything — that doesn't exist
  in any scope it can currently see. Exists here as the mechanism
  proving that a type annotation naming a class is a real, resolved
  expression, not an inert string.
- **type annotation (parameter position)** — writing `: Type` directly
  after a parameter's name in a `def` line, documenting the kind of
  value that parameter expects. Exists to let a reader, or a tool, learn
  a function's expected inputs from its signature alone, without
  reading the body or every call site.
- **return type annotation** — writing `-> Type` directly after a
  function's closing parenthesis, before the final colon, documenting
  what that function hands back. Exists as the output-side counterpart
  to a parameter annotation — the same documentation idea, applied to
  the other end of a function.
- **`Union`** — a real name imported from Python's `typing` module, used
  as `Union[X, Y]` in annotation position to document "this value is
  genuinely one of these listed types, and only these." Exists because
  a single plain type annotation can't otherwise say "could be either
  of these two things."
- **`Optional`** — a real name imported from `typing`, used as
  `Optional[X]`, documenting "this value is either an `X`, or it's
  `None`." Exists as a shorthand for the single most common two-case
  union in real code — `Union[X, None]` — so that specific, extremely
  frequent case doesn't have to be spelled out by hand every time.
- **generic type annotation (`list[X]`)** — subscripting a container
  type with the type of what it holds, in annotation position —
  `list[Asset]` documents "a list, specifically containing `Asset`
  objects," not just "a list of something." Exists because `list`
  alone, in an annotation, says nothing about what's inside it — the
  one fact a reader of a function taking a list usually needs most.
- **`__annotations__`** — a real `dict` attribute Python automatically
  builds and attaches to any function or method that has at least one
  annotation, mapping each annotated parameter's name — plus
  `'return'`, when a return annotation exists — to the actual object
  written after its colon or arrow. Exists to make every annotation
  genuinely inspectable at runtime, the same way `__dict__` (Lesson
  1.3) and `__bases__` (Lesson 1.1) make other class internals
  inspectable rather than hidden.

## Objects and methods used

**`Owner.__init__`**

- *What it is:* the constructor for `Owner`, reapplied from Lesson
  1.4 — the method Python calls automatically, once, the instant
  `Owner(...)` builds a new instance.
- *Implementation:* `def __init__(self, name: str, email: str) -> None:`
  — gains two parameter annotations and one return annotation this
  lesson; the body is untouched, still two plain assignments.
- *Its use:* this lesson's code annotates it so a reader — or an
  editor's autocomplete — can see, without opening any call site, that
  `name` and `email` are expected to be strings, and that calling it
  produces no return value.
- *Type:* an instance method — a dunder method.
- *Responsibility:* receive an owner's identifying data and store it
  onto the new instance — unchanged from Lesson 1.4; this lesson
  changes only how that contract is documented, not what it does.
- *Depends on:* the instance Python already allocated (`self`), and two
  caller-supplied values, now documented as `str`.
- *Connects to:* called by Python itself at construction; nothing else
  in this lesson calls it directly.
- *Shape:* the same boundary role as always — raw caller values crossing
  into stored state — now with that boundary's expected shapes written
  directly into the signature.

**`Asset.__init__`**

- *What it is:* the constructor, reapplied from Lessons 1.1 and 1.4.
- *Implementation:*
  `def __init__(self, name: str, serial_number: str, category: str, owner: Owner) -> None:`

  unchanged.
- *Its use:* this lesson's code annotates it so `owner` is documented as
  specifically an `Owner` instance, not just "whatever value showed up
  fourth" — the first annotation in this project naming a
  project-defined class rather than a builtin.
- *Type:* an instance method — a dunder method.
- *Responsibility:* unchanged from Lessons 1.1/1.4 — set up every
  instance attribute an `Asset` needs from the moment it exists.
- *Depends on:* `self`, three string values, and — now documented
  explicitly — a real `Owner` instance; also depends, for the first
  time, on `Owner` itself being an importable name inside `asset.py`'s
  own namespace, or the annotation can't be written at all.
- *Connects to:* called by Python at construction; the `owner`
  annotation connects `asset.py` to `owner.py` by name for the first
  time, via the new `from owner import Owner` line.
- *Shape:* the same boundary as always, now with an explicit,
  checkable-by-eye contract for what crosses it.

**`Asset.describe`**

- *What it is:* reapplied from Lesson 1.1 — a read-only method building
  a human-readable summary string.
- *Implementation:* `def describe(self) -> str:` — gains a return
  annotation; the body,
  `return f"{self.name} — {self.category} (S/N {self.serial_number})"`,
  is untouched.
- *Its use:* documents, in writing, for the first time, that this
  always returns a string — previously only inferable by reading the
  f-string inside it.
- *Type:* an instance method.
- *Responsibility:* unchanged — produce `Asset`'s own human-readable
  description.
- *Depends on:* `self`'s own `name`, `category`, and `serial_number`
  attributes, already set by `__init__`.
- *Connects to:* called by anything holding an `Asset` that wants a
  summary; calls nothing else.
- *Shape:* a read-only query method — no state changes, a pure function
  of `self`'s existing attributes.

**`Asset.mark_retired`**

- *What it is:* reapplied from Lesson 1.2 — the guarded state-changing
  method that retires an asset.
- *Implementation:* `def mark_retired(self) -> bool:` — gains a return
  annotation; the guard clause and its two branches are untouched.
- *Its use:* documents that this always returns one of exactly two
  `bool` values — `True` (it retired the asset) or `False` (it was
  already retired) — never anything else, without a reader needing to
  trace both branches to learn that.
- *Type:* an instance method — a state-changing method (mutator), per
  the term Lesson 1.2 defined.
- *Responsibility:* unchanged — enforce the invariant that an asset can
  only transition from active to retired once, reporting whether this
  specific call was the one that did it.
- *Depends on:* `self.is_retired`'s current value.
- *Connects to:* called by anything that wants to retire an asset and
  needs to know whether the call actually changed anything.
- *Shape:* a state-changing method with a `bool` result — the project's
  only method whose real invariant is now visible directly in its own
  signature.

**`find_by_serial`**

- *What it is:* a brand-new, free (non-method) function — the project's
  first — that searches a collection of `Asset` objects for one
  matching a given serial number.
- *Implementation:*
  `def find_by_serial(assets: list[Asset], serial_number: str) -> Optional[Asset]:`
  — iterates `assets`, returns the first `Asset` whose `serial_number`
  attribute equals the one being searched for, or `None` if none match.
- *Its use:* this lesson's real, project-landing use for both
  `list[Asset]` (its parameter) and `Optional[Asset]` (its return
  type) — the two constructs `Asset`/`Owner`'s own existing scalar
  parameters never needed.
- *Type:* a free function — module-level, not bound to any class,
  taking no `self`.
- *Responsibility:* search a given list of assets for one exact
  serial-number match and report the result — nothing else; it doesn't
  mutate `assets`, doesn't touch any `Asset`'s own state, and doesn't
  raise when nothing matches.
- *Depends on:* a `list` of already-constructed `Asset` objects handed
  in by the caller, and each of those `Asset`s already having a real
  `serial_number` attribute (guaranteed by `Asset.__init__`).
- *Connects to:* called by anything that has a collection of assets and
  one serial number to look up; calls nothing but attribute access on
  the `Asset`s it's given.
- *Shape:* a standalone query utility living in `asset.py` alongside the
  `Asset` class it operates on, rather than a method on any one
  instance — the first piece of this project's code that isn't itself a
  class or a method of one.

## Concept Unit: Parameter Type Annotations — Written, Not Enforced

### The Problem

Right now, nothing in `Owner.__init__(self, name, email)` says, anywhere
a reader can see without opening every call site, what *kind* of value
`name` or `email` is supposed to be. A comment could say so in English,
but nothing stops a comment from going stale the moment the code
changes and nobody updates it. Is there a way to write the expected
type directly into the signature itself — real syntax, not a comment —
in a form both a human and a tool could read?

> **Before reading on, try this:**
> - Lesson 1.1 already showed `self` is just a parameter name Python
>   binds a value to automatically. Given that, what do you think
>   writing `name: str` right after a parameter name — instead of plain
>   `name` — might do, syntactically?
> - `Owner("Jane Doe", "jane.doe@example.com")` runs fine today. Do you
>   think Python would refuse to run `Owner(42, True)` just because `42`
>   isn't a string — or does Python only care that *some* value showed
>   up for each parameter, regardless of its type?
> - `Asset.__init__` currently takes `owner` as a plain parameter. If
>   you wanted its annotation to say "this must specifically be an
>   `Owner`," what name would you write after the colon, given `Owner`
>   is a real class already sitting in `owner.py`?

### Isolated Concept

This is exactly what `Owner.__init__` and `Asset.__init__` just did
above, isolated down to the smallest possible case:

```python
def greet(name: str):
    print(f"Hello, {name}")


greet("Ada")
greet(42)

print(greet.__annotations__)
```

Run for real (`lab1_parameter_annotations.py`):

```
Hello, Ada
Hello, 42
{'name': <class 'str'>}
```

`greet(name: str)` — the identical syntax `Owner.__init__` and
`Asset.__init__` just gained above — annotates `name` as a `str`.
`greet("Ada")` runs and prints normally, unsurprising. `greet(42)` also
runs — and also prints, `Hello, 42` — even though `42` is an `int`, not
a `str`. Real, confirmed proof, not a claim: Python raised no error, no
warning, nothing at all, calling a `str`-annotated parameter with an
`int`. The annotation is written down; it is never checked against
what's actually passed in. This is called a **type annotation** — real
Python syntax, stored and inspectable, but never enforced by Python
itself at the moment a function is called.

The last line proves "stored and inspectable" isn't just a claim
either: `greet.__annotations__` is a real, ordinary `dict`, built by
Python the moment `greet` was defined, mapping each annotated
parameter's name to the actual object named after its colon —
here, `{'name': <class 'str'>}`, the real `str` type itself, not the
text `"str"`. Nothing about this is hidden or magic; it's a plain
attribute sitting on the function, readable with an ordinary `print`.

That last fact — the annotation is a *real, evaluated expression*, not
a string that only matters to a linter — has a sharp edge worth seeing
directly. `asset.py`'s own `owner: Owner` annotation only works because
`Owner` is now a real, importable name inside `asset.py`. What happens
if a class annotates a parameter with a name that was never imported at
all?

```python
class Gadget:
    def __init__(self, owner: Owner):
        self.owner = owner
```

Run for real (`break_unresolved_annotation.py`) — this run is *expected*
to fail:

```
Traceback (most recent call last):
  File "break_unresolved_annotation.py", line 1, in <module>
    class Gadget:
  File "break_unresolved_annotation.py", line 2, in Gadget
    def __init__(self, owner: Owner):
                              ^^^^^
NameError: name 'Owner' is not defined
```

Real, confirmed proof: the moment Python executes `class Gadget:`'s
body and reaches the `def __init__` line, it has to evaluate `Owner` —
the name written after the colon — as a real expression, right then,
to build `__init__`'s `__annotations__` dict. Since nothing anywhere
imported or defined a name called `Owner` in this file, that evaluation
fails with a **`NameError`** — the exact same exception that fires for
any other unresolved name, because an annotation's right-hand side
isn't special syntax exempt from normal name lookup; it's an ordinary
expression like any other. This is precisely why `asset.py`'s own
change needed `from owner import Owner` added at the top *before*
`Asset.__init__`'s own `owner: Owner` annotation could be written at
all — without it, defining the real `Asset` class would fail exactly
the way `Gadget` just did.

Discarded: `greet` and `Gadget` exist only to prove how parameter
annotations work, and what breaks without a resolvable name. Neither
will appear in the Asset Manager project again.

### Mechanical Walkthrough

- **`self`** (both signature lines) — reapplied in full from Lessons
  1.1–1.5: still the conventional name for each method's first
  parameter, automatically bound to the specific instance being built.
  Unchanged by this unit — `self` itself carries no annotation here,
  since Python already knows its type is whatever class it's defined
  inside; only the parameters *after* it gain one.
- **`from owner import Owner`** (asset.py, new line 1) — an ordinary
  Python import statement, general Python fluency below the level of
  classes and not itself new syntax — but its *presence* is a genuinely
  new fact about this project: this is the first time any file in the
  Asset Manager imports another file from the Asset Manager itself.
  Every earlier use of both `Asset` and `Owner` together (Lesson 1.4's
  own demonstrations, this curriculum's verification scripts) happened
  in a *third* file that imported or defined both — never inside
  `asset.py` needing to know about `owner.py` directly. It's needed now
  for one specific reason: `Asset.__init__`'s new `owner: Owner`
  annotation requires `Owner` to be a real, resolvable name inside
  `asset.py`'s own namespace, exactly as `break_unresolved_annotation.py`
  just proved by failing without one.
- **`name: str`, `serial_number: str`, `category: str`** (asset.py, line
  5) and **`name: str`, `email: str`** (owner.py, line 2) — the same
  annotation shape `greet(name: str)` just proved in isolation, applied
  three and two times respectively: a colon, then a type name,
  immediately after each parameter. Each documents "this parameter is
  expected to hold a `str`" — and, per the isolated lab's own proof,
  documents it *only*; nothing about calling `Asset(42, ...)` or
  `Owner(True, ...)` would fail differently than it does today.
- **`owner: Owner`** (asset.py, line 5) — the one annotation in this
  unit naming something other than a builtin. Mechanically identical to
  `name: str` — a colon, then a name — but the name being evaluated,
  `Owner`, is a real class, imported one line above specifically so
  this evaluation succeeds. This documents "this parameter must be an
  `Owner` instance" the same way `name: str` documents "this parameter
  must be a `str`" — and carries the exact same non-enforcement: nothing
  about this annotation would stop `Asset("x", "y", "z", "not an
  Owner")` from running today, exactly as `greet(42)` ran without error
  above.

### CS Lens

This is a **type annotation** — a real instance of **gradual typing**:
layering optional, non-enforced type information on top of a language
that is, underneath, still fully dynamically typed. This is a hard
concept, worth more than one real-world connection.

```
Also recognized in: TypeScript's type layer on top of ordinary
JavaScript, Python's own `typing` module combined with a separate
checker like mypy or pyright, Racket's Typed Racket dialect, Objective-C
's optional nullability annotations bolted onto an otherwise untyped
message-passing language
```

### SE Lens

The alternative not chosen is documenting expected types only in
English — a comment or a docstring saying "`name` should be a string."
A written annotation is checkable by an editor's autocomplete and by a
separate static type-checking tool the moment one is introduced,
without needing a human to keep a comment in sync by hand. The real,
current cost, honestly stated: this project doesn't run a type checker
yet, so today these annotations catch *nothing* automatically — a
caller could still pass `Owner(42, True)` and nothing would object,
exactly as `greet(42)` didn't. The benefit right now is purely for
human readers and editor tooling; the enforcement half of "gradual
typing" is debt this project is knowingly not paying down yet.

## Concept Unit: Return Type Annotations

### The Problem

A parameter annotation now documents what goes *into* `Owner.__init__`
and `Asset.__init__` — but nothing yet documents what any of these
methods *hand back*. `Asset.describe` clearly returns something; a
reader has to read its whole body to learn it's specifically a `str`.
`Asset.mark_retired` returns `True` in one branch and `False` in
another; a reader has to trace both branches to learn it's always a
`bool`. Is there a place in the signature itself — not just the
parameter list — to document a function's own *output*?

> **Before reading on, try this:**
> - Given that a parameter's type is written right after its own name
>   with a colon, where in a `def` line do you think the *return*
>   type might be written, given there's no "return parameter" to
>   attach a colon to?
> - `Asset.__init__` doesn't have a `return` statement anywhere in its
>   body — Lesson 1.1 already established that a function with no
>   `return` hands back `None`. What do you predict its own return
>   annotation should say, given that?
> - `Asset.mark_retired` returns `True` in one branch of its guard
>   clause and `False` in the other — two different values, but both the
>   same *type*. Do you think its return annotation names one type or
>   two?

## Concept Unit: Union — A Value That Could Be One of Several Types

### The Problem

Every annotation written so far names exactly one type, with total
certainty: `name` is always a `str`; `mark_retired` always returns a
`bool`. But real functions sometimes genuinely accept, or return, a
value that could legitimately be one of *several* different types —
and a plain `Type` annotation has no way to say "either of these two,"
only "exactly this one." Is there a real annotation for "this value is
one of several specific types, and only these"?

> **Before reading on, try this:**

>   Python's standard library has a whole module, `typing`, dedicated to
>   annotation-related tools, do you think a name like `Union`, imported
>   the same way as anything else, might exist there specifically to
>   solve the "one of several types" problem?
> - If `Union[int, str]` turns out to be real, working syntax, what do
>   you predict happens if a function annotated that way is called with
>   a `bool` instead — does `bool` count as either `int` or `str`, or

## Concept Unit: Optional — The Union Every Project Uses Most

### The Problem

A function that searches for something — an item in a list, a row in a
database — has one extremely common shape: it usually finds what it's
looking for and returns it, but sometimes it doesn't, and has to return
*something* anyway. Returning `None` in that case is the obvious choice
Python already offers — but a plain return annotation like `-> Asset`
would be a lie the moment the search fails and `None` comes back
instead. `Union[Asset, None]` would say it honestly — but is there a
shorter, more common way to write "this, or `None`," given how often
exactly this shape comes up?

> **Before reading on, try this:**
> - Given `Union[X, Y]` documents "one of these two types," what do you
>   predict `Union[str, None]` specifically documents — and does that
>   sound like a shape you've seen before, even outside annotations?
> - `typing` is where `Union` lives. Do you think a name like
>   `Optional`, imported from the same module, might exist purely as a
>   shorter way to write `Union[X, None]`, rather than as some entirely
>   separate mechanism?
> - If `Optional[str]` and `Union[str, None]` really do mean the exact
>   same thing, what do you predict happens if you compare them directly
>   with `==` — does Python treat them as equal, or as two different
>   objects that merely behave alike?

### Isolated Concept

```python

    return None
```

The first line is real, confirmed proof, not an assumption:

`Optional` exists purely as a shorter way to write the single most
common two-case union there is.

  attribute read, the same dot-access mechanism reapplied since Lesson
  1.1. `==` here is reapplied from Lesson 1.1, sharpened exactly as
  this lesson's own Header Terms entry states: both sides of this
  comparison are `str` values, so this `==` runs `str`'s own value
  comparison — checking whether the two strings hold the same
  characters — not the identity-based fallback Lesson 1.1 originally
  taught for plain objects like `Asset` or `Owner` themselves.
- **`return asset`** (asset.py, new line 27) and **`return None`**
  (asset.py, new line 28) — `return`, reapplied in full from Lesson
  1.1: the first hands back the real, matching `Asset` the moment one is
  found, ending the function immediately without checking any further
  elements of `assets`; the second only runs if the loop finishes
  without ever hitting that `return` — every element checked, none
  matching — handing back the literal `None` value the function's own
  `Optional[Asset]` annotation already promised was possible.

### CS Lens

This is a **generic type** — a type parameterized by another type,
exactly the same idea `Union` and `Optional` already used, now applied
to a container instead of a plain value-or-absence. This is a hard
concept, worth more than one real-world connection.

```
Also recognized in: Java's and C#'s `List<T>`, C++'s `std::vector<T>`,
TypeScript's `Array<T>` (equivalently `T[]`), a SQL query's typed result
set, where every row is understood to share one known column shape
```

### SE Lens

The alternative not chosen is annotating `assets` as plain `list`, with
no element type at all. `list` alone is legal, honest syntax — it just
throws away the one piece of information a reader of a search function
usually wants most: a list of *what*. `list[Asset]` costs nothing extra
to write over bare `list` and documents the real contract this function
actually relies on — every element having a `.serial_number` attribute,
guaranteed only because every element is genuinely an `Asset`. The
same honest caveat as every other annotation in this lesson still
applies: nothing about `list[Asset]` stops a caller from passing
`find_by_serial(["not", "assets"], "SN-1")` today — the annotation
documents the contract; it doesn't guard the door.

`list[Asset]` and `Optional[Asset]` are no longer just proven in
isolation — `find_by_serial` uses both for real, permanently, to do
something `Asset` and `Owner`'s own scalar parameters never needed:
document a value that's a *collection* of something specific, and a
result that might not exist at all.

## Closing

### Connect the Pieces

One concrete `Asset`, traced through every unit built in this lesson,
start to finish:

1. **Parameter annotations.** `jane = Owner("Jane Doe",
   "jane.doe@example.com")` calls the newly annotated
   `Owner.__init__(self, name: str, email: str)` — the two strings
   satisfy `name: str` and `email: str` exactly as they always would
   have, annotated or not; `Owner.__init__.__annotations__` now
   confirms both in a real, inspectable `dict`.
2. **Parameter annotations, the class case.** `laptop = Asset("ThinkPad
   X1", "SN-48213", "Laptop", jane)` calls
   `Asset.__init__(..., owner: Owner)` — legal only because `asset.py`
   now starts with `from owner import Owner`, without which this exact
   annotation would fail to define at all, exactly as
   `break_unresolved_annotation.py` proved for `Gadget`.
3. **Return annotations.** `laptop.describe()` returns `"ThinkPad X1 —
   Laptop (S/N SN-48213)"`, matching its own `-> str`; `laptop
   .mark_retired()` returns `True`, matching its own `-> bool` — both
   values Python would have produced with or without either annotation,
   proof that documentation and behavior are two separate things.
4. **`list[Asset]` and `Optional[Asset]`, together.** With a second
   asset, `monitor`, joining `laptop` in one real `list[Asset]`,
   `find_by_serial(inventory, "SN-99120")` searches it and returns
   `monitor` itself — `is monitor` confirms the identical object, not a
   copy — while `find_by_serial(inventory, "SN-00000")` searches the
   same list and returns the literal `None` its own `Optional[Asset]`
   promised was always possible.

Every one of these four calls would have run exactly the same way,
producing exactly the same values, in the version of this project
Lesson 1.5 left behind — nothing about adding a single annotation, from
the first `name: str` to the last `Optional[Asset]`, changed what this
project *does*. What changed is what a reader — or an editor, or, one
day, a type checker this project doesn't run yet — can now learn about
every one of these calls without running any of them at all.
