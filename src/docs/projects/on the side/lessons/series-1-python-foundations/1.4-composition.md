# Lesson 1.4: Composition

**What you will build.** `Asset` gains an owner — a real `Owner`
object, built from its own class, not just another string bolted onto
`Asset` itself. This is the Asset Manager's second real class, and,
more importantly, the first time one object holds an entire other
object as part of its own data. The transferable problem: how does one
object hold a genuine reference to a separate, independently-built
object, rather than flattening everything it needs into primitive
fields — and what does inspecting that relationship directly actually
prove about it?

**What you need to know first.** Lesson 1.1 — Classes and Objects:

Object State: reused only for orientation, since this lesson's Updated

`mark_retired`.

**Baseline scope note.** Unchanged from Lessons 1.1–1.3 — general Python

## Terms used in this lesson

- **`self`** — reapplied in full from Lessons 1.1 and 1.2: the
  conventional name for an instance method's first parameter.
- **instance attribute** — reapplied in full from Lesson 1.1: a piece
  of data stored on one specific instance, written as `self.x = value`.
- **`is`** — reapplied in full from Lesson 1.1: compares whether two
  names refer to the exact same object in memory, not whether their
  contents look alike.
- **composition** — one object storing a reference to a separate,
  independently constructed object as one of its own instance
  attributes. Exists as a distinct idea from every instance attribute
  this curriculum has used so far — `Asset.name`, `Asset.is_retired` —
  because the stored value here is itself a full object with its own
  class, its own attributes, and its own identity, not a primitive
  value like a string or a `bool`.
- **HAS-A relationship** — the informal name for what composition
  describes: "an `Asset` HAS-A `Owner`." Exists to name the relationship
  itself, distinct from other relationships between classes this
  curriculum hasn't covered yet (an IS-A relationship, for one, is a
  later lesson's own subject).

## Objects and methods used

**`Owner.__init__`**

- *What it is:* the constructor for a brand-new class, `Owner` — the
  method Python calls automatically, once, the instant `Owner(...)`
  builds a new instance.
- *Implementation:* `def __init__(self, name, email):` — an instance
  method taking `self` plus two plain values; stores both directly,
  identical in shape to `Asset.__init__`, Lesson 1.1.
- *Its use:* this lesson's code uses it to build a real `Owner`,
  independently, before any `Asset` ever references it.
- *Type:* an instance method — a dunder method, per the term Lesson 1.1
  defined.
- *Responsibility:* receive an owner's identifying data and store it
  onto the new instance — the same charter `Asset.__init__` has for
  `Asset`'s own data, applied here to a different class entirely.
- *Depends on:* the instance Python already allocated (`self`), and the
  two caller-supplied values (`name`, `email`).
- *Connects to:* called by Python itself at construction; nothing else
  in this lesson calls it directly except the one demonstration that
  builds an `Owner` to hand to an `Asset`.
- *Shape:* the same boundary role `Asset.__init__` already has —
  raw caller values crossing into an instance's own stored state —
  proving this mechanism isn't special to `Asset`; every class gets it.

**`Asset.__init__`**

- *What it is:* the constructor, reapplied from Lessons 1.1 and 1.2 —
  the method Python calls automatically, once, at construction.
- *Implementation:* `def __init__(self, name, serial_number, category, owner):`
  — gains a fourth parameter, `owner`, in this lesson; the body gains
  one more line storing it.
- *Its use:* this lesson's code uses it to accept an already-built
  `Owner` and hold onto it as part of the new `Asset`.
- *Type:* an instance method — a dunder method.
- *Responsibility:* per Lessons 1.1 and 1.2, set up every instance
  attribute an `Asset` needs from the moment it exists — now including
  one whose value is itself a full object, not a primitive.
- *Depends on:* the instance being built (`self`), the three
  caller-supplied primitive values, and — new in this lesson — a fully
  constructed `Owner` instance, which must already exist before
  `Asset(...)` is ever called.
- *Connects to:* called by Python at construction; the `owner` value it
  stores is read back later through `asset.owner.name` and
  `asset.owner.email`, reaching into the `Owner` instance's own data.
- *Shape:* unchanged in role from Lesson 1.1 — the boundary where a
  caller's values cross into stored state — now proven to accept a
  full object as one of those values, not only primitives.

## Concept Unit: Composition — One Object Holding Another

### The Problem

Every `Asset` attribute so far — `name`, `serial_number`, `category`,
`is_retired` — has been a primitive value: a string or a `bool`. Real
assets have owners — a person, with their own name and their own
email — and flattening that directly onto `Asset` itself
(`asset.owner_name`, `asset.owner_email`, two more plain strings) would
technically work. But what if "owner" deserves to be represented as its
own real object, with `Asset` simply holding onto it, the same way
`self.name = name` already holds onto a value?

> **Before reading on, try this:**
> - If `Asset` gained `owner_name` and `owner_email` as two more plain
>   string attributes, the same shape as `name` and `serial_number`,
>   what happens the day an owner also needs a phone number? Where
>   would that go, and what would have to change?
> - `self.name = name` inside `__init__` can store *any* value passed
>   to it — Lesson 1.2 already stored a `bool` there just as easily as
>   Lesson 1.1 stored a string. Do you think that same line could also
>   store a value that's itself a fully constructed object, built from
>   a completely different class?
> - If `self.owner = owner` stores a real `Owner` instance rather than
>   copying its individual fields onto `Asset`, how would you read that
>   owner's own `name` back out, given what you already know about dot
>   notation reaching through one level?

### Isolated Concept

```python
class Engine:
    def __init__(self, horsepower):
        self.horsepower = horsepower

class Car:
    def __init__(self, engine):
        self.engine = engine

engine = Engine(300)
car = Car(engine)
print(car.engine.horsepower)
print(car.engine is engine)
```

Run for real (`lab1_composition.py`):

```
300
True
```

`Engine` and `Car` are both ordinary classes, defined exactly the way
Lesson 1.1 already taught in full — nothing about their own `__init__`
methods is new. `Car.__init__`'s body, `self.engine = engine`, is the
same attribute-assignment mechanism this curriculum has used since
Lesson 1.1 — what's new is entirely on the *right-hand side*: `engine`
here isn't a string or a `bool`, it's a fully built `Engine` instance,
constructed independently, before `Car(engine)` is ever called.
`car.engine.horsepower` reads through two dots in a row: the first,
`.engine`, finds the `Engine` instance stored on `car`; the second,
`.horsepower`, reads that `Engine`'s own attribute. `car.engine is
engine` confirms, precisely — the same `is` check Lesson 1.1 gave full
treatment to — that `Car` doesn't copy `Engine`'s data into new fields
of its own; it holds onto the *exact same object* that was passed in.

This is called **composition**, informally described as a **HAS-A
relationship**: "a `Car` HAS-A `Engine`."

Discarded: `Engine` and `Car` exist only to prove how composition works.
Neither will appear in the Asset Manager project again.

### Mechanical Walkthrough

- **`owner`** (the new parameter, line 2) — an ordinary parameter,
  mechanically identical to `name`, `serial_number`, and `category`
  already sitting in the same signature — reapplied from Lesson 1.1.
  What's new isn't the parameter mechanism at all; it's the *kind* of
  value this lesson's own usage will pass for it: not a primitive, but
  a fully constructed `Owner` instance, built before `Asset(...)` is
  ever called — exactly what the isolated `Engine`/`Car` example just
  proved.
- **`self`** — reapplied in full: the specific `Asset` instance
  currently being built.
- **`.`** — attribute access on the assignment's left side, reapplied
  from Lesson 1.1: `self.owner` names a new slot belonging to this one
  instance.
- **`owner`** (right of `=`, line 7) — reading the parameter, reapplied:
  whatever real object was passed in gets stored here, unexamined and
  unchanged, the same way `self.name = name` never inspects or alters
  the string it's given.
- **`=`** — assignment, reapplied.

### CS Lens

This is **composition**, restated by name: building a class out of
references to other, independently meaningful objects, rather than out
of only primitive values. This is a hard concept, worth more than one
real-world connection.

```
Also recognized in: a `Car` holding an `Engine` object in any
object-oriented language, a GUI `Window` holding real `Button` objects
rather than raw pixel coordinates, an HTTP request object holding a
real `Headers` object, a company `Department` holding real `Employee`
objects
```

### SE Lens

The alternative not chosen is flattening `Owner`'s fields directly onto
`Asset` — `owner_name` and `owner_email` as two more plain strings —
instead of a real, separate `Owner` object. Composition keeps
`Owner`'s own concerns inside `Owner` itself, reusable by anything else
in the project that ever needs to represent an owner, and growing
`Owner` later (a phone number, say) touches only `Owner`, never
`Asset`. Flattening avoids the small overhead of an extra object and an
extra dot in every access, at a real cost: two different assets that
are *supposed* to share the same real owner would each carry their own
separately-typed copy of that owner's data, with nothing connecting
them or keeping them in sync if one copy is ever corrected and the
other isn't — a problem composition doesn't fully solve here either
(nothing yet stops two *separate* `Owner` objects from describing the
same real person), but flattening would make categorically worse by
losing even the possibility of a single shared reference.

## Closing

### Connect the Pieces

One concrete asset and its owner, traced through this lesson's single
concept, start to finish:

1. `jane = Owner("Jane Doe", "jane.doe@example.com")` builds a real,
   independent `Owner` — nothing about it references any `Asset` at
   all.
2. `laptop = Asset("ThinkPad X1", "SN-48213", "Laptop", jane)` builds a
   real `Asset`, and `Asset.__init__`'s new line,
   `self.owner = owner`, stores `jane` — not a copy of her data, the
   object itself — onto `laptop`.
3. `laptop.owner.name` reaches through `laptop` into the exact `Owner`
   object stored there, returning `"Jane Doe"` — the same value
   `jane.name` itself would return, because `laptop.owner is jane`.

One real object, `jane`, built once, is now reachable two different
ways — directly, or through `laptop.owner` — and both paths lead to the
exact same thing in memory, never a separate copy.
