# Lesson 1.2: Object State

**What you will build.** `Asset` gains the ability to change after it
already exists — specifically, to be marked retired — instead of only
ever holding the fixed data it was born with. The transferable problem
underneath that feature: how does an object's own data change safely,
after the object is already built and other code may already be
holding a reference to it, and how do you stop that change from ever
leaving the object in a state that shouldn't be possible?

**What you need to know first.** Lesson 1.1 — Classes and Objects:
`class`, instance, `__init__`, instance attributes (`self.x = value`),
methods, and `self`, all fully explained there and reused below.

**Baseline scope note.** Per Lesson 1.1's own scope note, general
Python fluency below the level of classes is assumed and not re-taught
here. That baseline is extended slightly in this lesson to explicitly
include `if` conditionals — ordinary control flow is more basic than
classes are, the same way `print` and f-strings already were. `pass`,
`self`, and Python's own boolean literals remain covered by full
Header entries below wherever they're directly evidentiary for one of
this lesson's own concepts, per Lesson 1.1's own line between baseline
scaffolding and taught vocabulary.

## Terms used in this lesson

- **`self`** — reapplied in full from Lesson 1.1: the conventional name
  for an instance method's first parameter, through which Python
  automatically passes the exact instance a method was called on, so
  the method's code knows which object's own data to read or change.
- **instance attribute** — reapplied in full from Lesson 1.1: a piece
  of data stored on one specific instance, written as `self.x = value`,
  separate from every other instance of the same class.
- **method** — reapplied in full from Lesson 1.1: a function defined
  inside a class body whose first parameter is `self`, reached through
  an instance (`instance.method()`).
- **`return`** — reapplied in full from Lesson 1.1: a keyword that ends
  a method immediately and sends a value back to whatever called it.
- **`bool`** — Python's true/false type; `True` and `False` are its only
  two values. Lesson 1.1 only ever *produced* a `bool` as the result of
  a comparison (`fido == rex`); this is its first appearance written
  directly as a literal in this lesson's own code. Exists as a distinct
  type (not, say, the integers `1`/`0`) so code can ask a plain
  yes/no question about an object's state.
- **default value** — a value an attribute starts with that isn't
  supplied by whoever calls the constructor, chosen instead by the
  class itself. Exists so a caller never has to type a value that's
  obviously always the same at the moment of creation, and can never
  forget to supply it either.
- **state-changing method** (sometimes called a *mutator*) — a method
  whose job is specifically to change data an instance already has,
  rather than only read it. Exists as a distinct idea from an
  ordinary read-only method like Lesson 1.1's `describe` — this
  lesson's `mark_retired` is the first method in this project that
  writes to `self` after `__init__` has already finished running.
- **invariant** — a rule about an object's own state that should always
  hold true, no matter what sequence of method calls an object has been
  through. Exists because without one stated and enforced, nothing stops
  an object from drifting into a state that doesn't make sense — here,
  nothing would stop "retiring" an asset that's already retired from
  meaning something different each time it happened.
- **guard clause** — a check placed at the very top of a method that
  stops the method from doing anything further when running it
  wouldn't be valid. Exists as the specific mechanism this lesson uses
  to enforce an invariant — the rule is checked once, in one place,
  before any of the method's real work runs.

## Objects and methods used

**`Asset.__init__`**

- *What it is:* the constructor, reapplied from Lesson 1.1 — the method
  Python calls automatically, once, the instant `Asset(...)` builds a
  new instance.
- *Implementation:* `def __init__(self, name, serial_number, category):`
  — unchanged in signature from Lesson 1.1; this lesson adds one more
  line to its body, establishing a fourth piece of state that isn't a
  parameter.
- *Its use:* this lesson's code uses it to give every new `Asset` a
  starting value for `is_retired` without requiring the caller to
  supply one.
- *Type:* an instance method — a dunder method, per the term defined in
  Lesson 1.1.
- *Responsibility:* per Lesson 1.1, set up every instance attribute an
  `Asset` needs from the moment it exists — now including one the
  caller never supplies, not only the three that come from its own
  parameters.
- *Depends on:* the instance Python already allocated (`self`), and the
  three caller-supplied values; `is_retired`'s value depends on nothing
  external at all — it's fixed by `__init__`'s own code.
- *Connects to:* called by Python itself, invisibly, at construction;
  `mark_retired`, below, is the first method in this project to read
  and change what `__init__` establishes here after the fact.
- *Shape:* unchanged from Lesson 1.1 — the boundary where a caller's raw
  values, plus this class's own fixed defaults, cross into an
  instance's stored state.

**`Asset.mark_retired`**

- *What it is:* a state-changing method that marks an `Asset` retired,
  refusing to do anything if it already is.
- *Implementation:* `def mark_retired(self):` — takes only `self`;
  returns a `bool` — `True` when it actually changed something, `False`
  when the asset was already retired and nothing happened.
- *Its use:* this lesson's code uses it to prove that a method can
  change data `__init__` already set up, safely, even when called more
  than once.
- *Type:* an instance method — ordinary, not a dunder; Python never
  calls it on its own.
- *Responsibility:* enforce the rule that an asset can only transition
  from not-retired to retired once, and report, truthfully, whether
  this particular call was the one that did it.
- *Depends on:* the instance it's called on (`self`) already having
  `is_retired` set — true of every `Asset` because `__init__` always
  sets it.
- *Connects to:* called by this lesson's own demonstration code
  (`laptop.mark_retired()`); reads and writes `self.is_retired`, the
  same attribute `__init__` established; returns a `bool` outward to
  whatever called it.
- *Shape:* a public surface on `Asset` that both changes state and
  reports on that change — distinct from `describe` (Lesson 1.1), which
  only ever reads.

## Concept Unit: Default Attribute Values — State the Class Decides, Not the Caller

### The Problem

Every instance attribute `Asset` has today — `name`, `serial_number`,
`category` — traces directly back to one of `__init__`'s own
parameters. But a freshly built asset also needs to start out *not
retired*, and nobody calling `Asset(...)` should have to remember to
type `is_retired=False` by hand just to say "this is a normal, brand
new asset." How can `__init__` give an attribute a value the caller
never has to supply at all?

> **Before reading on, try this:**
> - Every attribute `Asset` has today traces back to one of `__init__`'s
>   parameters. If you wanted every new `Asset` to start with some
>   fixed value nobody has to type — always `False`, say — where would
>   that value come from, if not a parameter?
> - Given `self.name = name` copies a parameter onto the instance, what
>   do you think `self.is_retired = False` would do differently, given
>   `False` isn't a parameter at all?
> - If `Asset("ThinkPad X1", "SN-48213", "Laptop")` is only ever called
>   with three arguments, could the resulting object still end up
>   holding four separate pieces of stored state? Reason through why or
>   why not before reading on.

### Isolated Concept

```python
class Dog:
    def __init__(self, name):
        self.name = name
        self.is_hungry = True

fido = Dog("Fido")
rex = Dog("Rex")
print(fido.is_hungry)
print(rex.is_hungry)
```

Run for real (`lab1_default_attribute.py`):

```
True
True
```

`self.is_hungry = True` sits inside `__init__` exactly where
`self.name = name` does — the identical attribute-assignment mechanism
Lesson 1.1 already gave full treatment to. The difference is entirely
on the right-hand side: `name` is a parameter, so its value depends on
what the caller passed in; `True` is a plain literal, so its value
doesn't depend on the caller at all. `Dog("Fido")` supplies exactly one
argument, yet both `fido` and `rex` end up with `is_hungry` stored as
`True`, because every `Dog`, regardless of what name it's given, starts
life exactly the same way where hunger is concerned.

This is called a **default value**.

Discarded: this `Dog` class exists only to prove how default attribute
values work. It will not appear in the Asset Manager project again.

### CS Lens

This is the idea of a **sensible default** — giving something a
reasonable starting value automatically, rather than requiring it to be
supplied every time.

```
Also recognized in: default parameter values in a function's own

value when a setting is left unspecified
```

### SE Lens

boilerplate to every single call site for a value that's obviously

copy-pasted `Asset(...)` call with the wrong starting value typed in by

cost: the true starting value now lives only inside `__init__`'s own
body — a reader can no longer see it spelled out at any individual call
site, and has to open the class itself to discover what a "normal" new
`Asset` actually starts out holding.

## Concept Unit: Methods That Modify State — Writing to `self` After Construction

### The Problem

`is_retired` now exists and reads `False`, forever — there's no way,
once an `Asset` is built, to ever change it. `describe` (Lesson 1.1)
already proved a method can *read* `self`'s attributes. Can a method
also *change* one, at some point after `__init__` has already finished
running?

> **Before reading on, try this:**
> - `describe` reads `self.name` but never writes to it. What do you
>   think happens if a method's body contains `self.is_retired = True`
>   instead of a `return` statement — is that even legal, given
>   `__init__` already finished running long before this method is ever
>   called?
> - If two completely different methods both contain a line shaped like
>   `self.x = something`, is the underlying mechanism the same in both,
>   or does a method need special permission to change state that a
>   different method already set up?
> - Given `fido.feed()` should stop the dog from being hungry, what
>   single line — using the exact shape `__init__` already used to set
>   `is_hungry` in the first place — do you think belongs inside
>   `feed`'s own body?

### Isolated Concept

```python
class Dog:
    def __init__(self, name):
        self.name = name
        self.is_hungry = True

    def feed(self):
        self.is_hungry = False

fido = Dog("Fido")
print(fido.is_hungry)
fido.feed()
print(fido.is_hungry)
```

Run for real (`lab2_mutating_method.py`):

```
True
False
```

`self.is_hungry = False` inside `feed` uses the identical
attribute-assignment mechanism `__init__` already used to set
`is_hungry` to `True` in the first place. The difference is entirely in
*when* it runs: `__init__` runs exactly once, automatically, the
instant `Dog(...)` builds the object; `feed` runs whenever this
lesson's own code calls `fido.feed()` explicitly, at any later point,
on an object that's already fully built and already has a value stored
for `is_hungry`. The printed lines are real proof of that: `True`
before the call, `False` after — the exact same attribute, on the exact
same already-existing object, genuinely changed value. No method in
Lesson 1.1 ever did this; every attribute there was written exactly
once, inside `__init__`, and never touched again.

This is called a **state-changing method**.

mutate `self`. It will not appear in the Asset Manager project again.

  inside `Asset`'s body.
- **`mark_retired`** — the name chosen for this method — an ordinary

- **`self`** — reapplied in full: without it, `mark_retired` would have

### CS Lens

This is the **mutator** pattern — a method whose entire purpose is
changing an object's own already-established state, rather than only
reporting on it.

```
Also recognized in: setter methods in Java and C++, a SQL UPDATE
statement changing a row already on disk, a thermostat's own method for
changing its target temperature, a game character's own method for
taking damage
```

## Concept Unit: Invariants — Protecting a Rule About Valid State

### The Problem

The previous unit's own real run proved the gap: `mark_retired()`
returned `True` on its second call, even though the asset was already
retired and nothing actually changed. Nothing stops calling code from
trusting that lie. How does an object's own method become responsible
for protecting a rule about which states are actually valid — rather
than leaving it to whoever happens to call it?

> **Before reading on, try this:**
> - Look at the previous unit's real output: `False`, `True`, `True`,
>   `True`, `True`. The second `mark_retired()` call did nothing
>   real — `is_retired` was already `True`. What do you think that
>   second call *should* return instead, if the return value is
>   supposed to mean "did this call actually change anything"?
> - In plain English, before writing any code: what should happen when
>   `mark_retired()` is called on an asset that's already retired —
>   should it silently do nothing and say so, or something else? There
>   isn't one universally right answer yet (raising a real error is
>   Lesson 1.11's own territory) — just reason through what "silently
>   do nothing, and report that nothing happened" would look like.
> - If `self.is_retired` is already `True`, what single condition,
>   checked at the very top of `mark_retired`, would let the method
>   exit immediately without touching anything else in its body?

### Isolated Concept

First, the same bug the previous unit found on `Asset`, reproduced on
the throwaway `Dog`, with a return value attached this time to make it
concrete:

```python
class Dog:
    def __init__(self, name):
        self.name = name
        self.is_hungry = True

    def feed(self):
        self.is_hungry = False
        return True

fido = Dog("Fido")
print(fido.feed())
print(fido.feed())
```

Run for real (`lab3_invariant_before.py`):

```
True
True
```

Both calls report `True` — "yes, I fed the dog" — even though the
second call found the dog already fed and changed nothing. Anything
relying on that return value (logging that food was given, charging for
a meal) would be fooled the second time.

Now, the fix:

```python
class Dog:
    def __init__(self, name):
        self.name = name
        self.is_hungry = True

    def feed(self):
        if not self.is_hungry:
            return False
        self.is_hungry = False
        return True

fido = Dog("Fido")
print(fido.feed())
print(fido.feed())
print(fido.feed())
```

Run for real (`lab3_invariant_after.py`):

```
True
False
False
```

`if not self.is_hungry:` checks the rule *before* anything else in the
method runs. First call: `is_hungry` is `True`, so `not self.is_hungry`
is `False`, the `if` doesn't trigger, and `feed` proceeds normally,
returning `True`. Second and third calls: `is_hungry` is already
`False`, so `not self.is_hungry` is `True`, the `if` triggers
immediately, and `feed` returns `False` without touching `is_hungry`
again — an honest report, every time, no matter how many times it's
called.

This is called an **invariant** — here, "a dog is never fed twice in a
row without getting hungry again first" — enforced by a **guard
clause**: the `if not self.is_hungry: return False` line, which stops
the rest of the method from running at all when the rule would be
broken.

Discarded: this `Dog` class exists only to prove how a guard clause
protects an invariant. It will not appear in the Asset Manager project
again.

### Mechanical Walkthrough

- **`if`** — a conditional statement (assumed baseline per this
  lesson's own scope note, above): runs the indented block beneath it
  only when the condition that follows evaluates to true, and skips it
  otherwise.
- **`self.is_retired`** — reapplied in full from the previous two
  units: reading, not writing, the specific `Asset` instance's own
  stored flag.
- **(no `== True`)** — worth naming precisely: the condition is
  `if self.is_retired:`, not `if self.is_retired == True:`. Because
  `self.is_retired` is already a `bool`, per the term defined above,
  it's already exactly the kind of value an `if` needs — writing
  `== True` alongside it would compare a boolean against a boolean to
  produce another boolean, which is redundant, not incorrect.
- **`:`** — opens the `if` block, the same colon-then-indent shape
  every other block in this lesson has used.
- **`return False`** — reapplied `return` from Lesson 1.1, this time
  returning the `bool` literal `False` — the **guard clause** defined
  above, in full: this line, and only this line, is what makes the rest
  of `mark_retired`'s body unreachable when the asset is already
  retired.

### CS Lens

This is **invariant enforcement via a guard clause** — checking a rule
about valid state at the very top of a method, before any of its real
work runs. This is a hard concept, worth more than one real-world
connection.

```
Also recognized in: a database CHECK constraint rejecting an invalid
row before it's written, a bank withdrawal method refusing to overdraw
an account, a state machine's transition table permitting only certain
next-states, a thread-safe queue checking "not empty" before popping
```

### SE Lens

The alternative not chosen is leaving the check to every *caller* of
`mark_retired`, instead of inside the method itself — trusting whoever
calls it to check `asset.is_retired` first, every time, everywhere in
the codebase that might ever call it. Putting the guard inside the
method means the rule can never be violated no matter how many
different places end up calling `mark_retired` — one guard protects
every caller, forever, including ones not written yet. The real cost:
the method now has two genuinely different outcomes (`True` or `False`)
that every caller technically ought to handle, rather than one
guaranteed result — a caller that only ever expects `True` and ignores
the return value entirely will silently miss the case where nothing
happened.
