# Lesson 1.3: Instance vs Class Attributes

**What you will build.** Nothing survives into the Asset Manager project
this lesson — per the blueprint, this is a **Lab**: a deliberately
disposable experiment (this curriculum's own Rule 2). What gets built
instead is a working intuition for one of Python's most common real
bugs: a value that looks like it belongs to one object, but is actually
shared, invisibly, by every object of that class — and specifically,
why that sharing turns dangerous the instant the shared value is
something that can be changed in place, rather than replaced outright.
The transferable problem: knowing precisely, for any value written
inside a class, whether it belongs to one instance or to the class
itself, shared by every instance that will ever exist.

**What you need to know first.** Lesson 1.1 — Classes and Objects:
`class`, instance, `__init__`, instance attributes, `self`, methods,
`is`. Lesson 1.2 — Object State: state-changing methods, writing to
`self` after construction.

**Baseline scope note.** Per Lessons 1.1 and 1.2's own scope notes,
general Python fluency below the level of classes is assumed and not
re-taught here. That baseline is extended in this lesson to include
Python's `list` literal syntax (`[]`) and its `.append()` method —
ubiquitous general-purpose Python, the same category as `print` and
f-strings already were. What this lesson does *not* treat as baseline —
because it's the entire subject of this lesson — is exactly which
object a `list` used inside a class actually belongs to.

## Terms used in this lesson

- **`self`** — reapplied in full from Lessons 1.1 and 1.2: the
  conventional name for an instance method's first parameter, through
  which Python passes the specific instance a method was called on.
- **instance attribute** — reapplied in full from Lesson 1.1: a piece of
  data stored on one specific instance, written as `self.x = value`,
  separate from every other instance of the same class.
- **class attribute** — a value written directly inside a class's body,
  at the same indentation level as its methods, rather than inside
  `__init__` via `self.x = value`. Exists as a genuinely different kind
  of storage from an instance attribute: it belongs to the *class*
  itself, in one single copy, shared by every instance of that class —
  not copied per instance the way `self.x = x` inside `__init__` is.
- **mutable** — describes a value whose own contents can be changed in
  place after it's created, without creating a new object to replace
  it. A `list` is mutable: `.append()` changes the same list object
  that already existed.
- **immutable** — describes a value that can never be changed in place;
  every apparent "change" actually produces a brand-new object instead.
  Every string this curriculum has used so far (`asset.name`, for
  instance) is immutable — this distinction matters here because it's
  exactly what determines whether sharing a class attribute is harmless
  or dangerous.
- **attribute shadowing** — what happens when an instance attribute is
  given the same name as an existing class attribute: reading that name
  on the instance now finds the instance's own value first, leaving the
  class attribute — and every other instance — completely untouched.
  Exists as the mechanism that explains why *reassigning* a shared
  value through one instance is safe, while *mutating* one is not.
- **attribute lookup** — the search Python performs, in order, when
  code reads `instance.name`: check the instance's own stored
  attributes first; only if nothing is found there, fall back to
  checking the class. Exists as the one real mechanism underneath every
  other term in this lesson — class attributes, shadowing, and the trap
  this lesson demonstrates are all direct consequences of this one
  search order.
- **`__dict__`** — a real, inspectable attribute every Python object and
  class carries, holding exactly the data stored directly on it as a
  plain dictionary. Exists here as proof, not assertion: this lesson
  uses it to show, concretely, which object actually owns a given
  value, rather than asking the reader to take attribute lookup's
  behavior on faith.

## Concept Unit: Class Attributes — One Value, Shared by Every Instance

### The Problem

Every attribute this curriculum has built so far — `Asset.name`,
`Asset.is_retired` — was written inside `__init__` as `self.x = value`,
which Lesson 1.1 already proved gives every instance its own separate
copy. But not every value written inside a class needs a separate copy
per instance — some values are genuinely the same for every instance
that will ever exist. Is there a way to write a value once, inside the
class, without it living inside `__init__` at all?

> **Before reading on, try this:**
> - Every attribute you've seen so far lives inside `__init__`, set via
>   `self.x = value`. What do you think happens if a line like
>   `species = "Canis familiaris"` is written directly inside a class's
>   body, but *outside* any method at all — not inside `__init__`, not
>   inside any `def`?
> - If every `Dog` really does belong to the same species, is there any
>   actual reason to copy that exact same string onto every single
>   instance separately, the way `self.name` copies a different value
>   onto each one?
> - You already know `Dog.__init__` is written as a name reached
>   through the class itself. Given that, what do you think
>   `Dog.species` — the class name, a dot, then a name with no `self`
>   anywhere near it — would actually refer to?

### Isolated Concept

```python
class Dog:
    species = "Canis familiaris"

fido = Dog()
rex = Dog()
print(fido.species)
print(rex.species)
print(fido.species is rex.species)
print(Dog.species)
```

Run for real (`lab1_class_attribute.py`):

```
Canis familiaris
Canis familiaris
True
Canis familiaris
```

`species = "Canis familiaris"` sits directly inside `class Dog:`, at
the same indentation level `def __init__` would use — not inside any
method at all. Neither `fido` nor `rex` was ever told its own species;
`Dog()` here takes no arguments whatsoever. Yet both `fido.species` and
`rex.species` read `"Canis familiaris"` — and `fido.species is
rex.species` reads `True`, proof, not assumption, that this isn't two
separate strings that merely look alike (the way Lesson 1.1 proved
`fido.name` and `rex.name` were always separate objects) — it's the
exact same string object, read through two different instances.
`Dog.species`, reached through the class itself with no instance
involved at all, reads the identical value, because that's genuinely
where it lives.

This is called a **class attribute**.

```

```

### SE Lens

The alternative not chosen is giving every `Dog` its own independent
copy — `self.species = "Canis familiaris"` inside `__init__`, exactly
like `self.name` — instead of a class attribute. A class attribute uses
exactly one copy in memory no matter how many `Dog` instances exist,
and updating it in one place (rare, but real — reclassifying a species,
say) instantly reflects through every instance without touching any of
them individually. The real cost: any single instance that ever needs a
genuinely different value has to explicitly create its own instance
attribute to override it — nothing about a class attribute gives an
individual instance a cheap, built-in way to diverge, the way a
parameter to `__init__` would.

## Concept Unit: Attribute Shadowing — Assigning Through an Instance Never Touches the Class

### The Problem

`Dog.species` is shared by every instance — but nothing about Python
stops one specific dog from needing a different value someday (a
crossbreed, say). If `fido.species = "Wolf"` is written, does that
change `Dog.species` itself — meaning every other dog would suddenly
read `"Wolf"` too — or does something else happen?

> **Before reading on, try this:**
> - `self.name = name` inside `__init__` is ordinary attribute
>   assignment, already fully explained in Lesson 1.1. Given that
>   `fido.species = "Wolf"` uses the exact same `instance.attribute =
>   value` shape, what do you predict happens to `rex.species` — the
>   *other* dog — immediately afterward?
> - If assigning `fido.species = "Wolf"` really did change the one
>   shared string every `Dog` reads, would `Dog.species` itself also
>   read `"Wolf"` afterward? Reason through what you'd expect to see if
>   you printed it.
> - Lesson 1.1 already proved `self.x = value` inside `__init__`
>   creates a brand new entry belonging only to that one instance. Is
>   there any reason that exact same statement, written somewhere
>   *other* than `__init__`, would behave differently?

### Isolated Concept

```python
class Dog:
    species = "Canis familiaris"

fido = Dog()
rex = Dog()
fido.species = "Wolf"
print(fido.species)
print(rex.species)
print(Dog.species)
```

Run for real (`lab1b_reassignment_shadows.py`):

```
Wolf
Canis familiaris
Canis familiaris
```

`fido.species = "Wolf"` does not change the shared string at all — it
creates a brand-new instance attribute, named `species`, that belongs
to `fido` alone, exactly the same mechanism Lesson 1.1 already gave
full treatment to for `self.name = name` inside `__init__`. `rex` and
`Dog` itself are both completely unaffected: `rex.species` and
`Dog.species` still read `"Canis familiaris"`. From this point forward,
reading `fido.species` finds `fido`'s own instance attribute first and
never even looks at the class's — this is called **attribute
lookup**: Python checks the instance's own stored data first, and only
falls back to the class when nothing is found there. Because `fido` now
has its own `species` entry, that fallback never happens for `fido`
again.

This is called **attribute shadowing**.

a shared default, rather than silently allowing an ordinary assignment

any single instance can cheaply diverge from a shared default with no
special syntax at all. The real cost is exactly what the next unit
exposes from the opposite direction: it's just as easy to create a

## Concept Unit: The Mutable-Class-Attribute Trap

### The Problem

`fido.species = "Wolf"` proved that assigning a brand-new value through
an instance is always safe — it shadows, it never reaches back and
changes the class's own copy. But not every operation on an attribute
is an assignment. What happens if, instead of replacing a shared class
attribute outright, code calls a method *on* it that changes its
existing contents in place — the way `.append()` changes a list without
replacing it?

> **Before reading on, try this:**
> - A `list` class attribute, `tricks = []`, is shared the same way
>   `species` was. If `fido.tricks.append("sit")` runs, is that
>   statement an *assignment* to `fido.tricks` (which the previous unit
>   proved always shadows safely), or something else entirely? Look
>   carefully at whether `=` appears anywhere in that line.
> - Given the previous unit's own proof that `fido.species` falls back
>   to reading `Dog.species` whenever `fido` has no instance attribute
>   of its own — and given that `fido` here never did anything to
>   create its own `tricks` — which object does `fido.tricks.append(...)`
>   actually call `.append()` on: something belonging only to `fido`, or
>   something else?
> - If `.append()` changes a list's contents without creating a new
>   list object at all, and `rex.tricks` refers to that *exact same*
>   object `fido.tricks` does, what would you predict `rex.tricks`
>   shows immediately after `fido.learn_trick("sit")` runs — even
>   though `rex` was never told about "sit" at all?

### Isolated Concept

```python
class Dog:
    tricks = []

    def __init__(self, name):
        self.name = name

    def learn_trick(self, trick):
        self.tricks.append(trick)

fido = Dog("Fido")
rex = Dog("Rex")
fido.learn_trick("sit")
print(fido.tricks)
print(rex.tricks)
print(fido.tricks is rex.tricks)
```

Run for real (`lab2_mutable_trap.py`):

```
['sit']
['sit']
True
```

Only `fido.learn_trick("sit")` was ever called — `rex` was never told
about any trick at all. And yet `rex.tricks` also shows `['sit']`.
`fido.tricks is rex.tricks` confirms exactly why: `True` — they are, at
this moment, the literal same list object, not two lists that happen to
match. `self.tricks.append(trick)` inside `learn_trick` never assigns
anything to `self.tricks` — there's no `=` in that line at all — it
looks up `tricks` (finds `Dog`'s shared class attribute, via the exact
same attribute-lookup fallback the previous unit proved, because
neither `fido` nor `rex` has ever created an instance attribute of that
name) and calls `.append()` directly on that one shared list, in place.
Real, direct proof of exactly which object owns it — not just the `is`
check above, but the underlying storage itself:

```python
class Dog:
    tricks = []

    def __init__(self, name):
        self.name = name

    def learn_trick(self, trick):
        self.tricks.append(trick)

fido = Dog("Fido")
fido.learn_trick("sit")
print(fido.__dict__)
print(Dog.__dict__["tricks"])
```

Run for real (`lab2b_dict_proof.py`):

```
{'name': 'Fido'}
['sit']
```

`fido.__dict__` — a real attribute every object carries, holding
exactly what's stored directly on it — contains only `name`. `tricks`
isn't there at all, even though `fido.tricks` reads `['sit']` and even
though `learn_trick` was called *on* `fido`. The trick it learned is
sitting in `Dog.__dict__["tricks"]` instead — the class's own storage,
not `fido`'s. Every `Dog` that ever exists shares that one list, for as
long as `tricks` stays a class attribute.

This is called the **mutable-class-attribute trap**.

### SE Lens

The alternative not chosen — writing `tricks` as a class attribute in

intentional collection (a real cache every instance should read from

is good for. The real cost this unit exposes is that a class-level
mutable value looks *identical*, in the code itself, whether sharing

## Concept Unit: The Fix — Give Every Instance Its Own List

### The Problem

The trap only exists because `tricks = []` lives in the class body,
outside `__init__`. Lesson 1.1 already proved that anything set up
inside `__init__` via `self.x = value` becomes a separate copy per
instance. Does moving the list's creation into `__init__` fix this, the
exact same way it already works for every other instance attribute this
curriculum has built?

> **Before reading on, try this:**
> - `self.name = name` inside `__init__` already gives every `Dog` its
>   own separate `name`. If `self.tricks = []` is written the exact
>   same way, inside `__init__`, what do you predict happens to the
>   `is` comparison the previous unit used to prove the two dogs shared
>   one list?
> - Every time `Dog(...)` runs, `__init__` runs once, automatically,
>   per Lesson 1.1. If `self.tricks = []` sits inside it, how many
>   separate list objects would exist after creating three different
>   dogs — one shared list, or three independent ones?
> - Once `tricks` is created inside `__init__`, does `self.tricks.append(trick)`
>   inside `learn_trick` need to change at all, or does the exact same
>   line now do something different simply because of *where* `tricks`
>   itself was created?

### Isolated Concept

```python
class Dog:
    def __init__(self, name):
        self.name = name
        self.tricks = []

    def learn_trick(self, trick):
        self.tricks.append(trick)

fido = Dog("Fido")
rex = Dog("Rex")
fido.learn_trick("sit")
print(fido.tricks)
print(rex.tricks)
print(fido.tricks is rex.tricks)
```

Run for real (`lab3_instance_fix.py`):

```
['sit']
[]
False
```

`self.tricks = []` now sits inside `__init__`, in exactly the same
position `self.name = name` already does — and per Lesson 1.1's own
proof that `__init__` runs once per instance, each `Dog(...)` call now
builds its own, brand-new, empty list. `rex.tricks` correctly reads
`[]` — `rex` never learned anything — and `fido.tricks is rex.tricks`
now reads `False`: two separate list objects, not one shared between
them. `learn_trick`'s own body — `self.tricks.append(trick)` — did not
change at all between the broken version and this fixed one; the bug
was never in `learn_trick`, only in *where* `tricks` was first created.

This confirms the fix: give every instance its own copy, inside
`__init__`, the same mechanism this curriculum has already used for
every other instance attribute.

### CS Lens

This is **per-instance initialization** — allocating a fresh, independent
copy of a mutable value for every object, at the moment it's built,
instead of sharing one.

```
Also recognized in: a constructor allocating a fresh array or buffer
per object in C++ or Java, a fresh session object created per incoming
HTTP request, per-component state in a UI framework that is never
shared across separate instances of the same component
```

### SE Lens

The alternative not chosen is leaving `tricks` as a class attribute but
defensively resetting it — `self.tricks = []` — at the start of every
method that touches it, rather than fixing it once in `__init__`.
Fixing it in `__init__` guarantees every instance starts independent
the moment it's born, since `__init__` runs exactly once per instance,
with no method ever needing to remember to defend against the shared-
list trap. The "reset defensively in every method" alternative is
strictly worse here — more places to remember, more places to forget —
included mainly to make clear *why* `__init__` specifically is the
right place: it's the one point in an instance's life every instance is
guaranteed to pass through, exactly once.

## Closing

### Connect the Pieces

One shared value, traced through every unit built in this lesson, start
to finish — no project code changes as a result, per this lesson's own
"Throw away: everything":

1. **Class attributes.** `tricks = []`, written directly inside
   `class Dog:`, creates exactly one list, owned by the class itself —
   proven by `Dog.__dict__["tricks"]` holding it directly, and by no
   instance ever having a `tricks` entry of its own in its `__dict__`.
2. **Attribute shadowing.** A plain assignment through an instance —
   `fido.species = "Wolf"` — never reaches that shared storage at all;
   it creates a new entry belonging only to `fido`, leaving `Dog` and
   every other instance untouched.
3. **The trap.** `fido.learn_trick("sit")` contains no assignment to
   `tricks` anywhere — only `.append()`, called on whatever object
   attribute lookup finds. Since neither dog has its own `tricks` entry,
   that search falls through to the one shared list, and `.append()`
   changes it in place — visible through `rex.tricks` too, even though
   `rex` was never told about "sit."
4. **The fix.** Moving `tricks = []` inside `__init__`, as
   `self.tricks = []`, gives every instance its own list at the exact
   moment it's built — the identical mechanism Lesson 1.1 already
   proved for `self.name`. `learn_trick`'s own body never had to
   change; only where `tricks` was born did.

One list, shared by accident, leaked across two supposedly separate
dogs — and the fix was never a different method, only a different
*place* for one line of code to live.
