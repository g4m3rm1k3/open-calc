# Lesson 1.16: Testing Pure Python

**What you will build.** A real, permanent `tests/` directory, sitting
alongside `asset_manager/`, containing `tests/test_asset.py` — five
real tests, run by `pytest`, a real third-party testing framework this
project installs for the first time. Every real behavior this
curriculum has hand-verified since Lesson 1.1 — that `Asset`
construction stores every field correctly, that `mark_retired` guards
correctly on both its branches, that a blank `name` raises
`InvalidAssetError` carrying the right `field`, that the same exception
is still catchable as plain `ValueError` — now has a real, automated
check that can be re-run in one command, forever, instead of trusting
that a verification script run once, months ago, still describes how
the code behaves today. The transferable problem: manually re-checking
"does this still work?" by eye, after every change, doesn't scale — and
becomes actively unreliable the moment a project has more than a
handful of behaviors worth protecting.

**What you need to know first.** Lesson 1.9 — `Asset.__post_init__`'s
three validation checks. Lesson 1.2 — `mark_retired`'s own guard clause
and its two `bool` results. Lesson 1.11 — `InvalidAssetError`, its
`field` attribute, and that it's also a `ValueError`. Lesson 1.15 —
`asset_manager/domain/`, the real package these tests import from.

## Terms used in this lesson

- **`assert`** — new. A statement that checks a condition and raises a
  real `AssertionError` if it's falsy — reapplying Lesson 1.9's own
  truthy/falsy material, now used to make a claim fail loudly and
  immediately if it's wrong, rather than reading a value and deciding
  what to do about it (an `if`'s own job). `pytest` specifically
  rewrites plain `assert` statements inside test files to show the
  actual computed values on failure, not just the bare fact that
  something didn't match.
- **`pip`** — new. Python's own standard package installer, bundled
  with Python itself — run from a terminal, never imported inside
  Python code. `pip install pytest` downloads `pytest` (and anything it
  itself depends on) from the Python Package Index and makes it
  importable, the same way Python's own standard-library modules
  already are, without needing to be copied into this project by hand.
  Exists because Python's own standard library, everything this
  project has used through Lesson 1.15, deliberately doesn't include
  every useful package — `pytest` is real, widely-used, third-party
  code, not part of Python itself.
- **test discovery** — new. `pytest`'s own convention for finding tests
  automatically: any file named `test_*.py`, and any function inside it
  named `test_*`, is treated as a real test and run — no manual
  registration, no import list to maintain by hand.

## Objects and methods used

**`pytest`**

- *What it is:* a real, third-party Python testing framework — this
  project's first dependency on code that isn't part of Python's own
  standard library.
- *Implementation:* installed via `pip install pytest`; run from a
  terminal as `pytest` or `python -m pytest`, either discovering every
  `test_*.py` file under the current directory automatically, or
  targeting one specific file/test by name.
- *Its use:* runs every test this lesson writes, reporting each one as
  passed or failed, with real, specific output for any failure.
- *Type:* an installed package, invoked as a command-line program.
- *Responsibility:* discover test files and test functions by their
  names, run each one, and report results — nothing about what the
  tests themselves check; that's entirely up to the code inside them.
- *Depends on:* test files and functions following its own naming
  convention to be discovered at all.
- *Connects to:* invoked from a terminal; imports and calls whatever
  code the tests themselves import — here, `asset_manager.domain.asset`
  and `asset_manager.domain.owner` directly, the real package Lesson
  1.15 built.
- *Shape:* an external, installed tool sitting outside the project's
  own source, driving it from the outside the same way a human running
  `python` interactively always has.

**`pytest.raises`**

- *What it is:* a real function `pytest` provides specifically for
  testing that a block of code raises an expected exception.
- *Implementation:* `pytest.raises(expected_exception) ->
  ExceptionInfo[E]` — used as a context manager (Lesson 1.14's own
  `with`), its real, documented signature; used as `with pytest.raises
  (SomeException) as exc_info:`, it succeeds — the test continues
  normally — only if the code inside the `with` block actually raises
  `SomeException` (or a subclass, reapplying Lesson 1.11's own IS-A
  relationship for exceptions); if the block raises nothing, or raises
  something else, the test fails instead.
- *Its use:* `with pytest.raises(InvalidAssetError) as exc_info:
  Asset("   ", ...)` proves construction genuinely fails the way Lesson
  1.9/1.11 already hand-verified — now as a real, repeatable, automated
  check.
- *Type:* a function, used here as a context manager.
- *Responsibility:* watch a block of code for one specific exception
  type, turning "an exception was raised" from a test-ending crash into
  a condition the test can specifically assert on.
- *Depends on:* the exception type it's watching for, and a block of
  code to run inside its own `with`.
- *Connects to:* wraps a real call into `Asset.__post_init__` (via
  `Asset(...)`); the object it binds via `as exc_info` connects to
  whatever exception actually got raised, through its own `.value`.
- *Shape:* a specialized context manager — Lesson 1.14's own idea,
  reapplied here for a testing-specific purpose: guaranteed handling of
  one specific, expected failure, not guaranteed cleanup of a resource.

**`ExceptionInfo.value`**

- *What it is:* a real attribute on the object `pytest.raises(...)`
  binds via `as exc_info` — holds the actual exception instance that
  was raised and caught.
- *Implementation:* `exc_info.value` — the real, concrete exception
  object itself, not just its type or its message text.
- *Its use:* `exc_info.value.field` reads `InvalidAssetError`'s own
  `field` attribute (Lesson 1.11) directly off the actual exception
  that was raised, proving not just *that* something failed, but
  *which* field caused it.
- *Type:* an instance attribute.
- *Responsibility:* give test code access to the real, raised exception
  instance, not just confirmation that raising happened.
- *Depends on:* `pytest.raises` having actually caught a matching
  exception.
- *Connects to:* read directly by this lesson's own test code.
- *Shape:* the bridge between "an exception of the right type was
  raised" and "and here's what it actually contains."

**Everything else in the file, not this lesson's own subject but still explained**

**`Asset.__post_init__`**

- *What it is:* reapplied from Lessons 1.9/1.11 — the validation hook.
  Untouched by this lesson.
- *Implementation:* unchanged since Lesson 1.11.
- *Its use:* exercised by this lesson's own tests, not modified by
  them.
- *Type:* an instance method.
- *Responsibility:* unchanged.
- *Depends on:* unchanged.
- *Connects to:* called by every `Asset(...)` this lesson's tests
  construct.
- *Shape:* unchanged.

**`Asset.mark_retired`**

- *What it is:* reapplied from Lesson 1.2. Untouched by this lesson.
- *Implementation:* unchanged since Lesson 1.9.
- *Its use:* exercised directly by two of this lesson's own tests,
  covering both of its own branches.
- *Type:* an instance method — a state-changing method (mutator).
- *Responsibility:* unchanged.
- *Depends on:* `self.is_retired`'s current value.
- *Connects to:* called by this lesson's own test code.
- *Shape:* unchanged.

same statement Python has always had, becomes far more informative the
instant it runs inside a `pytest`-discovered test file.

Discarded: `test_addition_works`/`test_addition_is_wrong_on_purpose`
exist only to prove `pytest`'s own discovery and output mechanics.
Neither will appear in the Asset Manager project again.

This is **automated testing** — encoding a claim about correct
behavior as real, runnable code, so it can be re-checked mechanically
instead of trusted from memory or a one-time manual run. This is a
hard concept, worth more than one real-world connection.

```
Also recognized in: a factory's own automated quality-control check run

```

### SE Lens

tradeoff: every verification script this curriculum has wr itten was

re-runs them automatically. A real test suite costs ongoing
maintenance (tests can go stale, or need updating when behavior
deliberately changes) in exchange for exactly that guarantee.

## Concept Unit: Testing Validation and Exceptions

### The Problem

Lesson 1.9/1.11 already proved, by hand, that a blank `name` raises
`InvalidAssetError` carrying the right `field`, and that the same
exception is still catchable as plain `ValueError`. A test function
that expects an exception can't just `assert` normally — the exception
itself would end the test function immediately, the same way it would
end any other code. Is there a way to write a test that specifically
*expects* a raise, and still makes assertions about what was raised?

> **Before reading on, try this:**
> - If `Asset("   ", ...)` raises `InvalidAssetError` the instant it's
>   called, and a test function just wrote that line directly with no
>   special handling, do you predict the test finishes and reports a
>   result, or does the raised exception itself crash the test
>   function before any `assert` after it could ever run?
> - Lesson 1.14 already proved `with` guarantees cleanup around a
>   block, regardless of how that block exits. Given `pytest.raises`
>   is used as a `with`-based context manager, do you predict it uses
>   that same guaranteed-handling idea to specifically catch an
>   expected exception, turning "an exception happened" from a crash
>   into something the test can examine afterward?
> - If `pytest.raises(InvalidAssetError)` successfully catches a real
>   `InvalidAssetError`, and that class carries a real `field`
>   attribute (Lesson 1.11), do you predict there's a way to read that
>   specific attribute from inside the test — proving not just that
>   something failed, but that the *right* field caused it?
