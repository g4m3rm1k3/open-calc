## Terms used in this lesson

- **`lambda`** — new. A keyword that builds a function directly inside
  an expression, with no `def`, no name, and a body limited to exactly
  one expression whose value is automatically returned — `lambda x: x *
  3` is a complete, callable function, equivalent in behavior to `def
  triple(x): return x * 3`, written inline instead of as its own
  statement. Exists for the specific case where a function is needed
  only once, right where it's used, and giving it a permanent name
  and a separate `def` block would say more about its importance than
  it actually has.
- **`__name__`** — new. A real, built-in attribute every function
  object carries, holding its own name as a plain string —
  `double.__name__` is `"double"`, the exact name it was defined with.
  Exists as a concrete, inspectable fact this lesson uses to prove
  `lambda` genuinely has no name of its own: a lambda's own `__name__`
  is always the literal string `"<lambda>"`, never anything more
  specific, regardless of what variable it happens to be assigned to.

## Objects and methods used

**`sorted`**

- *What it is:* a real Python built-in function that returns a new,
  sorted `list` built from any iterable — never modifies its input.
- *Implementation:* `sorted(iterable, key=None, reverse=False) -> list`
  — its real, documented signature; `key`, this lesson's own focus, is
  a function called once per element, and the *results* of those calls
  are what actually get compared to decide sort order, not the elements
  themselves.
- *Its use:* `sorted(assets, key=lambda a: a.name)` sorts a list of
  throwaway asset-like objects by their own `name` attribute, without
  `sorted` itself needing to know anything about what an "asset" is.
- *Type:* a built-in free function.
- *Responsibility:* produce a new list containing every element of its
  input, ordered according to `key`'s own return values (or the
  elements themselves, when `key` is left at its default, `None`) —
  nothing about mutating the original iterable.
- *Depends on:* an iterable to sort, and, when `key` is supplied, a
  callable accepting one element and returning something comparable.
- *Connects to:* called directly by this lesson's own throwaway code;
  calls `key` once per element in the list it's sorting, exactly the
  way Lesson 1.12's own `retire` called `on_retired` — a function
  handed in, called by name-agnostic code that only knows it received
  something callable.
- *Shape:* a built-in higher-order function — a function that itself
  accepts another function as an argument, reapplying Lesson 1.12's own
  callback idea inside the standard library itself.

## Concept Unit: `lambda` Builds an Ordinary Function

### The Problem

Lesson 1.12 already proved a `def`-written function is a real,
first-class object — assignable, storable, passable. Is there a way to
build that same kind of object *without* a separate `def` statement and
a name — directly inside an expression, wherever a function happens to
be needed?

> **Before reading on, try this:**
> - `def triple(x): return x * 3` is three real facts bundled into one
>   statement: a name (`triple`), a parameter (`x`), and a body (`return
>   x * 3`). If a function could be written with no name at all, what
>   do you predict would have to happen to the other two facts — does a
>   nameless function still need a parameter list and a body, or does
>   removing the name change what's possible to express?
> - Lesson 1.12 proved `type(shout)` returns `<class 'function'>` for
>   an ordinary `def`-written function. Do you predict a function built
>   without `def` — anonymously — has that same real type, or some
>   different, special "anonymous function" type of its own?
> - Every function this project has used has a real `__name__` — Lesson
>   1.1's own methods, `describe`, `mark_retired`, all have names
>   matching how they were written. If a function is genuinely built
>   with no name, what do you predict its own `__name__` attribute
>   actually holds — an empty string, `None`, or something else
>   entirely?

### Isolated Concept

```python
def double(x):
    return x * 2


triple = lambda x: x * 3

print(double(5))
print(triple(5))
print(type(double))
print(type(triple))
print(double.__name__)
print(triple.__name__)
```

Run for real (`lab1_lambda_basics.py`):

```
10
15
<class 'function'>
<class 'function'>
double
<lambda>
```

`triple = lambda x: x * 3` builds a real function and assigns it to
`triple`, exactly the way `stored = shout` assigned an existing
function in Lesson 1.12 — the difference is that `lambda x: x * 3`
builds the function *itself*, right there, rather than referencing one
already defined elsewhere with `def`. `double(5)` and `triple(5)` both
print correctly — `10` and `15` — real, confirmed proof that calling a
`lambda`-built function works exactly like calling any other one.
`type(double)` and `type(triple)` both print the identical `<class
'function'>` — real, confirmed proof that `lambda` builds the exact
same kind of object Lesson 1.12 already proved every function is, no
special "anonymous function" type involved at all.

The final two lines prove the one genuine difference: `double.__name__`
reads `"double"`, the real name it was defined with — but
`triple.__name__` reads `"<lambda>"`, literally that string, every
single time, for every lambda ever written, regardless of what variable
it happens to be assigned to. This is called **`lambda`** — real syntax
building a genuinely nameless function, one whose body is limited to
exactly one expression (no `if` statements, no multiple lines, nothing
`return` would need spelled out — the expression's own value is
automatically what gets returned).

Discarded: `double` and `triple` exist only to prove `lambda` builds an
ordinary function. Neither will appear in the Asset Manager project
again.

### CS Lens

This is an **anonymous function** — a function value with no bound
name of its own, defined inline exactly where it's needed. This is a
hard concept, worth more than one real-world connection.

```
Also recognized in: JavaScript's own arrow functions and anonymous
function expressions, Java's lambda expressions (`(x) -> x * 3`), a
one-off sticky note versus a permanent filed document — both carry
real information, but only one is worth naming and keeping
```

### SE Lens

The alternative not chosen is always using `def`, giving every function
a name even when it's used exactly once, right where it's defined. The
real tradeoff: a named `def` is easier to find by searching, easier to
reuse a second time, and can hold a multi-line body a `lambda`
structurally cannot — `lambda`'s own one-expression limit is not a
missing feature, it's the deliberate boundary keeping it honest about
being a small, throwaway transformation rather than real logic that
deserves a name and a home.

## Concept Unit: `lambda` as a Sort Key

### The Problem

Lesson 1.12's own `retire` function proved a function can be handed to
another function as an argument, uncalled, to be called later. Python's
own built-in `sorted` does exactly this with its `key` parameter — but
writing a full, separately-named `def` just to say "sort by this one
attribute," used exactly once, at exactly this call site, feels like a
lot of ceremony for a one-line idea. Can `lambda` fill that gap
directly?

> **Before reading on, try this:**
> - If `sorted(assets, key=some_function)` calls `some_function` once
>   per element to decide sort order, and a throwaway asset-like object
>   has a `name` attribute, what do you predict the smallest possible
>   function for "give me this element's `name`" would need to look
>   like — one parameter, one expression, nothing else?
> - Given the previous unit already proved a `lambda` is called exactly
>   like any other function, do you predict `sorted(assets, key=lambda
>   a: a.name)` — no separate `def` anywhere — is legal, working
>   Python, built entirely inline inside the call to `sorted` itself?
> - If this same sort needed to happen in three different places in a
>   real, larger program, do you predict a `lambda`, written fresh each
>   time, is still the better choice — or does having a name worth
>   reusing become the deciding factor at that point?

### Isolated Concept

```python
class ThrowawayAsset:
    def __init__(self, name):
        self.name = name

    def __repr__(self):
        return f"ThrowawayAsset({self.name!r})"


assets = [ThrowawayAsset("Monitor"), ThrowawayAsset("Chair"), ThrowawayAsset("Laptop")]

by_name = sorted(assets, key=lambda a: a.name)
print(by_name)
```

Run for real (`lab2_lambda_sort_key.py`):

```
[ThrowawayAsset('Chair'), ThrowawayAsset('Laptop'), ThrowawayAsset('Monitor')]
```

`assets` starts in this exact order: Monitor, Chair, Laptop. `sorted
(assets, key=lambda a: a.name)` — real, confirmed proof, not a claim:
the returned list is genuinely reordered, `Chair`, `Laptop`, `Monitor`
— alphabetical by `name`, exactly what `lambda a: a.name` told
`sorted` to compare instead of comparing the `ThrowawayAsset` objects
themselves (which have no `<` of their own defined at all, and would
raise a real `TypeError` if `sorted` tried to compare them directly
without a `key`). Nothing about this `lambda` was assigned to a
variable anywhere — it exists for exactly the width of this one call to
`sorted`, discarded the instant `sorted` finishes calling it once per
element.

Discarded: `ThrowawayAsset`, `assets`, and the `lambda` itself exist
only to prove this pattern. None will appear in the Asset Manager
project again.

### CS Lens

A direct application of the previous unit's own anonymous-function
idea, combined with Lesson 1.12's own callback pattern — `key`
functions in general are worth their own real-world connection, since
the underlying idea recurs well beyond sorting.

```
Also recognized in: a database ORDER BY clause naming which column to
sort by without needing a whole separate query, JavaScript's
Array.prototype.sort(compareFn), a spreadsheet's own custom sort
dialog letting a user pick which column to sort by, per sort, without
writing any code at all
```

### SE Lens

The alternative not chosen is a separately-named `def get_name(asset):
return asset.name`, then `sorted(assets, key=get_name)`. The real
tradeoff: a named `def` is strictly more capable (could hold a
multi-line body, could be reused at other call sites, shows up by name
in a traceback if something inside it ever raised) — but for a
transformation this small, used exactly once, the `lambda` version
keeps the sort key visible directly at the call site, with nothing to
scroll away to find; the moment the same key logic is needed a second
time elsewhere, or needs to be more than one expression, that's the
real signal to switch to a named `def` instead.
