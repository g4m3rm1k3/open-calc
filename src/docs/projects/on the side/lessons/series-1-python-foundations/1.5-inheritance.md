# Lesson 1.5: Inheritance

**What you will build.** Nothing survives into the Asset Manager
project this lesson — the blueprint's own words: "the point is
understanding inheritance — not forcing inheritance into the Asset
Manager." What gets built instead is a deliberately simple, throwaway
`Shape`/`Circle` pair proving three real mechanisms: a class can be
built as an extension of another, a subclass can replace a piece of
behavior it inherits, and a subclass can reach back and reuse the
parent's own version of something it's replacing, instead of being
forced to choose between keeping it entirely or duplicating it
entirely. The transferable problem: how two classes share behavior
*on purpose*, through a stated relationship, rather than by copying the
same code into both.

**What you need to know first.** Lesson 1.1 — Classes and Objects:
`class`, `__init__`, instance attributes, `self`, methods, `__bases__`.
Lesson 1.3 — Instance vs Class Attributes: attribute lookup and
shadowing, reused here by direct analogy for *method* lookup. Lesson
1.4 — Composition: cited specifically to contrast — this lesson's own
relationship between two classes (IS-A) is a genuinely different
relationship from composition's HAS-A, not a variation of it.

**Baseline scope note.** Unchanged from Lessons 1.1–1.4 — general Python
fluency below the level of classes remains assumed and not re-taught
here.

## Terms used in this lesson

- **`self`** — reapplied in full from Lessons 1.1–1.4: the conventional
  name for an instance method's first parameter.
- **instance attribute** — reapplied in full from Lesson 1.1: a piece of
  data stored on one specific instance.
- **method** — reapplied in full from Lesson 1.1: a function defined
  inside a class body whose first parameter is `self`.
- **subclass** — a class defined with an existing class named in
  parentheses right after its own name (`class Circle(Shape):`),
  automatically gaining everything that named class already does,
  without retyping any of it.
- **parent class** (also called a *base class*) — the class named in a
  subclass's own definition — `Shape` is `Circle`'s parent class.
  Exists as the other half of the same relationship "subclass" names,
  seen from the opposite direction.
- **IS-A relationship** — the informal name for what subclassing
  describes: "a `Circle` IS-A `Shape`." Exists to contrast directly with
  Lesson 1.4's **HAS-A relationship** (composition) — an `Asset` HAS-A
  `Owner`, but never IS one; a `Circle`, by contrast, genuinely IS a
  `Shape`, not merely holding a reference to one.
- **overriding** — defining a method in a subclass using the exact same
  name as a method its parent class already has, so calls made on the
  subclass use the new version instead of the inherited one. Exists as
  the mechanism that lets a subclass behave differently from its
  parent for one specific piece of behavior, without losing everything
  else it inherits.

## Objects and methods used

**`super()`**

- *What it is:* a built-in function that, called from inside a
  subclass's own method, returns a stand-in for "this instance, but
  looked up starting from the parent class" — letting that method call
  the parent's own version of something it's overriding.
- *Implementation:* `super()` — called with no arguments here; returns
  an object through which the parent class's methods can be called,
  with `self` already correctly bound to the actual instance in use.
- *Its use:* this lesson's code uses it inside `Circle.__init__` and
  `Circle.describe` to call `Shape`'s own versions, reusing their logic
  instead of duplicating it.
- *Type:* a built-in function.
- *Responsibility:* provide access to the parent class's own method
  implementations from inside an overriding method — nothing else; it
  doesn't create an object and doesn't change any class's own
  definition.
- *Depends on:* being called from inside a method defined on a
  subclass, where Python already knows both the subclass and the
  specific instance the method is running against.
- *Connects to:* called directly by this lesson's own `Circle` methods;
  whatever it returns has `Shape`'s own methods called on it in turn
  (`super().__init__(...)`, `super().describe()`).
- *Shape:* a bridge between an overriding method and the specific
  version it's overriding — the mechanism that makes "extend, don't
  replace" possible.

## Concept Unit: Subclassing — Building a New Class as an Extension of an Existing One

### The Problem

Lesson 1.1 already proved every class implicitly inherits from
`object`, whether or not anything says so. But what about inheriting
from a class *you* wrote — reusing everything it already does, without
retyping any of it?

> **Before reading on, try this:**
> - Lesson 1.1 proved `Dog.__bases__` shows `(object,)` even though
>   nothing in `class Dog: pass` names a parent. If you *did* want to
>   name a specific parent of your own, what do you think the syntax
>   `class Circle(Shape):` might do, given the parent's name sits
>   exactly where `Dog()`'s constructor call would usually go?
> - If `Circle` is written with an empty body (`pass`) but names
>   `Shape` as its parent, and `Shape` already has a working
>   `__init__`, do you think `Circle(...)` would have *any* `__init__`
>   behavior at all — and if so, whose?
> - What do you predict `Circle.__bases__` would show, given
>   `Dog.__bases__` already proved this exact attribute exists and
>   tells the truth about a class's real parent?

### Isolated Concept

```python
class Shape:
    def __init__(self, name):
        self.name = name

class Circle(Shape):
    pass

circle = Circle("circle")
print(circle.name)
print(Circle.__bases__)
```

Run for real (`lab1_subclassing.py`):

```
circle
(<class '__main__.Shape'>,)
```

`class Circle(Shape):` — the parenthesized name right after the class's
own name — names `Shape` as `Circle`'s parent. `Circle`'s own body is
just `pass`, the same no-op statement Lesson 1.1 gave full treatment
to — genuinely empty; no `__init__` is written anywhere inside `Circle`
itself. Yet `Circle("circle")` runs successfully, and `circle.name`
reads `"circle"` afterward: because `Circle` never defines its own
`__init__`, Python falls back to `Shape`'s — the same "check here
first, fall back if nothing's found" shape Lesson 1.3 already proved
for attribute lookup, now applied to *method* lookup instead.
`Circle.__bases__` — the identical real attribute Lesson 1.1 used to
prove `Dog` implicitly inherits `object` — now reports
`(<class '__main__.Shape'>,)`: real, direct proof that `Circle`'s
parent really is `Shape`, not `object` directly.

This is called **subclassing**: `Circle` is a **subclass** of `Shape`;
`Shape` is `Circle`'s **parent class**. The relationship itself is an
**IS-A relationship** — "a `Circle` IS-A `Shape`" — a genuinely
different relationship from Lesson 1.4's composition, where an `Asset`
*has* an `Owner` without ever being one.

## Concept Unit: Overriding — Replacing an Inherited Method

### The Problem

Right now, `Circle` just *is* a `Shape` with a different name typed in
at construction — any method `Shape` has would say the exact same kind
of thing for every subclass, with no way to specialize. What if a
`Circle` needs to describe itself differently from a generic `Shape`?

> **Before reading on, try this:**
> - If `Shape.describe` and a method `Circle` writes share the exact
>   same name, `def describe(self):`, what do you predict happens when
>   `circle.describe()` is called — does Python get confused about
>   which one to run, or is there a clear, predictable rule?
> - Lesson 1.3 already proved that an instance attribute shadows a
>   class attribute of the same name when read through the instance.
>   Do you think method lookup on a subclass follows a similar "closest
>   match wins" rule?
> - If `Circle` defines its own `describe`, but `Shape.describe` still
>   exists exactly where it always was, does calling `.describe()` on a
>   plain `Shape` (not a `Circle`) still use `Shape`'s own version, or
>   does defining `Circle`'s version somehow change `Shape` too?

### Isolated Concept

```python
class Shape:
    def __init__(self, name):
        self.name = name

    def describe(self):
        return f"This is a {self.name}."

class Circle(Shape):
    def describe(self):
        return f"This is a circle-shaped {self.name}."

shape = Shape("shape")
circle = Circle("circle")
print(shape.describe())
print(circle.describe())
```

Run for real (`lab2_overriding.py`):

```
This is a shape.
This is a circle-shaped circle.
```

`Circle` defines its own `describe`, using the identical `def` syntax
Lesson 1.1 already gave full treatment to. Calling `shape.describe()` —
a plain `Shape`, not a `Circle` — uses `Shape`'s own version,
completely unaffected by anything `Circle` does. Calling
`circle.describe()` uses *`Circle`'s* version instead, even though
`Circle` still inherits from `Shape` and even though `Shape.describe`
still exists, untouched, exactly where it always was. Python's method
lookup checks the specific class first (`Circle`), and only falls back
to the parent (`Shape`) when the specific class doesn't define its
own — the same "closest match wins" shape Lesson 1.3 already proved for
attribute shadowing, applied here to methods instead of plain data.

This is called **overriding**.

### SE Lens

The alternative not chosen is giving `Circle`'s method a different
name entirely — `circle_describe()` — instead of reusing `Shape`'s
exact name. Overriding, what's chosen here, lets any code that already
knows how to call `.describe()` on a `Shape` work *unchanged* on a

Renaming would avoid any risk of a subclass accidentally shadowing

## Concept Unit: `super()` — Reaching Back to the Parent's Own Version

### The Problem

The previous unit's `Circle.describe` fully rewrote its message,
duplicating the exact idea `Shape.describe` already expressed. Worse,
the moment `Circle` needs its own `__init__` — to accept and store a
radius, say — it would need to remember to set `self.name` too, or lose
it, duplicating `Shape.__init__`'s own job entirely. Is there a way for
`Circle` to call `Shape`'s own version of something from inside its own
override, instead of choosing between "keep the whole thing" (no
override) and "replace the whole thing" (full duplication)?

> **Before reading on, try this:**
> - If `Circle` needs its own `__init__` to accept and store a radius,
>   but `Shape.__init__` already knows how to set `self.name`
>   correctly, do you think there's a way for `Circle.__init__` to
>   *call* `Shape.__init__`, rather than retyping `self.name = name` a
>   second time?
> - `Circle.__bases__` already proved, in the first unit, that `Circle`
>   knows exactly which class is its parent. Given that, what do you
>   think a function literally named `super()`, called from inside one
>   of `Circle`'s own methods, might return?
> - If `Circle`'s own `describe` calls `super().describe()` as its very
>   first line, and `Shape.describe` returns a full sentence, what do
>   you predict `circle.describe()` returns overall — just that
>   sentence, or something built on top of it?

### Isolated Concept

```python
class Shape:
    def __init__(self, name):
        self.name = name

    def describe(self):
        return f"This is a {self.name}."

class Circle(Shape):
    def __init__(self, radius):
        super().__init__("circle")
        self.radius = radius

    def describe(self):
        base_description = super().describe()
        return f"{base_description} Its radius is {self.radius}."

circle = Circle(5)
print(circle.name)
print(circle.radius)
print(circle.describe())
```

Run for real (`lab3_super.py`):

```
circle
5
This is a circle. Its radius is 5.
```

`super().__init__("circle")` inside `Circle`'s own `__init__` calls
`Shape.__init__` directly. Real proof, not assertion: `circle.name`
reads `"circle"` afterward, even though `Circle`'s own `__init__` never
writes `self.name = name` anywhere in its own body. `super()` returns a
stand-in for "`Circle`'s parent" — calling `.__init__(...)` on it runs
`Shape`'s constructor, with `self` already correctly bound to the exact
`Circle` instance under construction. `self.radius = radius` right
after is ordinary attribute assignment, fully explained since Lesson
1.1, adding `Circle`'s own extra piece of state on top of what
`Shape.__init__` already set up. Inside `describe`, `super().describe()`
calls `Shape`'s version specifically (not `Circle`'s own — calling its
own version from inside itself would just run the same code again),
returning `"This is a circle."`; `Circle`'s own `describe` then builds
on top of that returned string instead of rewriting it from scratch.

Now, the exact failure the Socratic questions above asked to reason
through — what happens without `super().__init__(...)`:

```python
class Circle(Shape):
    def __init__(self, radius):
        self.radius = radius

circle = Circle(5)
print(circle.describe())
```

Run for real (`break_missing_super_init.py`):

```
Traceback (most recent call last):
  File "break_missing_super_init.py", line 13, in <module>
    print(circle.describe())
          ~~~~~~~~~~~~~~~^^
  File "break_missing_super_init.py", line 6, in describe
    return f"This is a {self.name}."
                        ^^^^^^^^^
AttributeError: 'Circle' object has no attribute 'name'
```

Real, confirmed proof: without `super().__init__("circle")` ever
running, `self.name` is never set anywhere at all — `Circle`'s own
`__init__` completely replaces `Shape`'s (per the previous unit's own
overriding mechanism, which applies to `__init__` exactly as it applies
to any other method), and nothing else ever sets `self.name`. `describe`
here is *inherited* from `Shape`, since this broken `Circle` defines no
override of its own — and it fails the identical way Lesson 1.1's own
`break_unstored_attribute.py` failed: a value nobody ever stored can't
be read back.

This is called **`super()`** — the mechanism that lets an override
*call*, rather than fully replace, the parent's own version.

This is **super-call delegation** — an override reusing its parent's

```
Also recognized in: `super()` calling a parent constructor in Java,

calling `next()` to continue rather than replacing the whole chain
```

### SE Lens

The alternative not chosen is fully duplicating `Shape.__init__` and
`Shape.describe`'s own logic inside `Circle`, instead of calling
`super()`. `super()` means a later change to `Shape`'s own logic — say,
capitalizing `self.name` — automatically applies to `Circle` too, with
zero changes anywhere in `Circle`'s own code; duplication would
silently miss that update entirely, the same class of risk the first
unit's SE lens already named for subclassing itself, now specifically
about method *bodies* rather than whole classes. The real cost of
`super()`: `Circle.describe`'s own output is now permanently coupled to
the exact wording `Shape.describe` returns — changing `Shape`'s message
changes every subclass's automatically too, which is sometimes exactly
what's wanted and sometimes isn't.

### Connect the Pieces

One concrete `Circle`, traced through every unit built in this lesson,
start to finish — no project code changes as a result, per this
lesson's own "Throw away: example":

1. **Subclassing.** `class Circle(Shape):` makes `Circle` a subclass of

2. **`super()`.** `Circle(5)` runs `Circle.__init__`, which calls

   rather than retyped — setting `self.name` to `"circle"` before

   state on top.
3. **Overriding.** `circle.describe()` calls *`Circle`'s* own
   `describe`, not `Shape`'s — the closest-match-wins rule the second
   unit proved — which itself calls `super().describe()` to reuse
   `Shape`'s own sentence, then extends it:

   ```
   This is a circle. Its radius is 5.
   ```

One `Circle`, built through a parent it never had to retype, describing
itself with a sentence it never had to write from scratch — subclassing
gave it a starting point, `super()` let it reuse what was already
correct, and overriding let it add exactly the one piece that made it
specifically a circle, not just any shape.
