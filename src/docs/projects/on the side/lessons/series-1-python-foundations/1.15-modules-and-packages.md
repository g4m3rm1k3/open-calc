# Lesson 1.15: Modules and Packages

**What you will build.** The Asset Manager's own file layout changes for
the first time since this project began — `asset.py` and `owner.py`,
flat files sitting side by side, become `asset_manager/domain/asset.py`
and `asset_manager/domain/owner.py`, real files inside a real Python
*package*. `asset.py`'s own import of `Owner` changes from `from owner
import Owner` to `from .owner import Owner` — a **relative import**,
naming a sibling module inside the same package rather than a
top-level file. Nothing about what either class *does* changes; what
changes is where the files live, and what it takes to import them
correctly from outside. The transferable problem: two files sitting
next to each other works fine until a project has more than a handful
of them — at that point, a real, named structure for grouping related
files, and a real mechanism for importing between them, stops being
optional.

**What you need to know first.** Lesson 1.6 — Python's own `import`
statement, already added to this project's assumed baseline scope, and
`from owner import Owner`, the exact line this lesson's own third unit
changes. Lesson 1.4 — composition, `Asset.owner` — the relationship
this lesson's own restructuring never touches, only relocates.

## Terms used in this lesson

- **module** — new. Any single Python file, considered as something
  importable — `asset.py` has been a module since it was first created
  in Lesson 1.1, even though this project has never used that specific
  word for it until now. Every `import` this project has ever written
  (Lesson 1.6 onward) has been importing a module.
- **package** — new. A directory containing an `__init__.py` file,
  making that directory itself importable, and every module inside it
  importable *through* it — `asset_manager/`, this lesson's own real
  landing, becomes a package the moment `asset_manager/__init__.py`
  exists, even if that file is completely empty.
- **`__init__.py`** — new. A real, specially-named file Python looks
  for to decide whether a directory is a package; its own contents run
  once, automatically, the first time anything imports that package —
  this lesson's own `__init__.py` files are left completely empty,
  since nothing in this project yet needs code to run at package-import
  time.
- **relative import** — new. An import statement naming a sibling
  module by a leading dot, relative to the *importing* module's own
  position inside a package, rather than by the package's full name —
  `from .owner import Owner`, written inside `asset_manager/domain/
  asset.py`, means "import `owner`, the module sitting right next to
  me in this same directory," without spelling out `asset_manager
  .domain` at all.
- **`ImportError`** — new. A real, built-in exception Python raises
  when an `import` statement — of any form, relative or absolute —
  cannot be resolved. Exists here as the mechanism proving a relative
  import genuinely requires a known parent package to resolve against;
  running a file directly removes that context entirely, rather than
  merely making the import slower or less convenient.
- **absolute import** — new. An import statement naming a module by its
  full path from the top of a package, regardless of where the
  importing code itself lives — `from asset_manager.domain.owner import
  Owner`, written from *outside* the `asset_manager` package entirely,
  is this lesson's own real example of one.

## Concept Unit: Modules and Import Caching

### The Problem

`asset.py`, `owner.py`, and every one of this curriculum's own
verification scripts have been calling `import` since Lesson 1.6,
always treating it as a simple, one-time action. Does a module's own
top-level code — everything sitting directly inside a `.py` file,
outside any function or class — actually run again every single time
something imports it, or does Python do something smarter once a
module has already been loaded once?

> **Before reading on, try this:**
> - `asset.py` has a real, top-level `from owner import Owner` line —
>   code that runs the instant `asset.py` itself is first imported. If
>   two completely different files both wrote `import asset` at the
>   top, do you predict `asset.py`'s own top-level code — including
>   that `import` line — runs twice, once for each importer, or only
>   once, total?
> - Given Lesson 1.7 already proved `dataclass` reads a class's
>   `__annotations__` dict once, at class-definition time, not on every
>   later access — if Python treats *importing* a module with a similar
>   "do the expensive part once" philosophy, what do you predict a
>   second `import` of the same already-imported module actually costs?

- **Reference Source:** No reference counterpart — original curriculum

- **Files affected:** none yet — this unit proves module import

  `asset.py`/`owner.py` for real.

### Isolated Concept

`greeter.py`:

```python
print("loading greeter.py")


def greet(name):
    return f"Hello, {name}"
```

`main.py`, sitting next to it:

```python
import greeter

print(greeter.greet("Ada"))

import greeter

print(greeter.greet("Grace"))
```

Run for real (`main.py`, from `lab1_module_caching/`):

```
loading greeter.py
Hello, Ada
Hello, Grace
```

`"loading greeter.py"` — `greeter.py`'s own top-level `print` — appears
exactly *once*, even though `import greeter` is written twice in
`main.py`. Real, confirmed proof, not a claim: the second `import
greeter` did not re-run `greeter.py`'s own code at all; both calls to
`greeter.greet(...)` still work correctly afterward, proving `greeter`
itself was genuinely, fully available both times. This is called
**import caching** — Python keeps track of every module it has already
loaded, and a second `import` of the same one reuses that already-built
module instead of running its file a second time.

A **module** is simply any single `.py` file, considered as something
importable this way — `greeter.py` is one; `asset.py` and `owner.py`
have been modules since Lesson 1.1, even before this project ever used
that word for them.

Discarded: `greeter.py`/`main.py` exist only to prove import caching.
Neither will appear in the Asset Manager project again.

### CS Lens

This is **memoization** applied to module loading — computing something
expensive once and reusing the stored result on every later request,
rather than recomputing it. This is a hard concept, worth more than one
real-world connection.

```
Also recognized in: a web browser's own cache, reusing an already-
downloaded image instead of fetching it again, a build system skipping
a compilation step whose inputs haven't changed since the last build, a
database's own query result cache, Python's own functools.lru_cache
decorator applying the identical idea to ordinary function calls
```

### SE Lens

The alternative not chosen is re-running a module's own top-level code
on every import, the way calling an ordinary function repeats its own
work every time. The real benefit of caching instead: a module that
does real, possibly expensive setup at import time — connecting to a
database, reading a config file — only pays that cost once, no matter
how many other files import it. The real, honest cost: if a module's
own top-level code has side effects that assume they're running fresh
each time, caching can produce surprising behavior — not a concern for
`asset.py`/`owner.py`, whose own top-level code has always been limited
to `import` statements and class definitions, never anything with a
side effect of its own.

### Mechanical Walkthrough

- **`from .owner import Owner`** (asset.py, line 4) — the single
  leading dot is a **relative import**: `.` means "this same package,"
  and `owner` names the sibling module directly inside it — `owner.py`,
  sitting right next to `asset.py` after the move. Mechanically similar
  to Lesson 1.6's own `from owner import Owner`, with the dot marking
  the difference between "a module found by searching from the top of
  Python's import path" and "a module found relative to where I myself
  live inside a package."
- **`from asset_manager.domain.asset import Asset`** (the confirmation
  script, outside the package) — an **absolute import**: no leading
  dot, the full dotted path from `asset_manager` all the way down to
  `asset`, naming exactly where `Asset` lives regardless of where the
  importing code itself is.

### CS Lens

This is **relative addressing** versus **absolute addressing** — naming
something by its position *relative to* where you currently are, versus
naming it by a complete, unambiguous path from a fixed, shared root.
This is a hard concept, worth more than one real-world connection.

```
Also recognized in: a relative file path (../sibling/file.txt) versus
an absolute one (C:\Users\...\file.txt), giving directions as "turn
left, then two blocks" versus a full street address, a spreadsheet's
own relative versus absolute (with $) cell references
```

### SE Lens

The alternative not chosen throughout `asset.py` is using an absolute
import even for this one sibling relationship —
`from asset_manager.domain.owner import Owner`, written inside `asset
.py` itself. The real tradeoff: an absolute import inside the package
would keep working even if `asset.py` and `owner.py` were later moved
to different subpackages relative to each other (since it names the
full path, not a relative position) — but it's more to type, more
tightly couples `asset.py`'s own code to the package's full name
(`asset_manager`), and is less idiomatic for naming a genuine sibling.
The real, honest cost of the relative import chosen here instead: this
lesson's own second failure proves it directly — `asset.py` can no
longer be run as a standalone script, something it technically could
do before this lesson (even though nothing in this project has ever
actually run it that way).
