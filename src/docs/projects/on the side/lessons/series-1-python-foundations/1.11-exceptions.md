# Lesson 1.11: Exceptions

**What you will build.** `Asset.__post_init__`'s three validation checks
(Lesson 1.9) stop raising a plain, generic `ValueError` and start
raising a brand-new class this project defines itself,
`InvalidAssetError` — a real subclass of `ValueError`, carrying not
just a message but a queryable `field` attribute naming exactly which
check failed. Alongside that real landing, this lesson covers
`try`/`except`, `else`, and `finally` — the control-flow machinery every
exception this project has ever raised (`NameError`, `TypeError`,
`ValueError`, and now `InvalidAssetError`) has always propagated
straight past uncaught, in every lesson before this one. The
transferable problem: raising an exception is only half the story —
this lesson is about the other half, catching one deliberately, and
about a project defining its *own* named failure conditions instead of
only ever borrowing generic, general-purpose ones.

**What you need to know first.** Lesson 1.5 — Inheritance: subclass,
parent class, IS-A relationship, `super()` — all reapplied for real,
for the first time, since `InvalidAssetError(ValueError)` is this
project's first inheritance relationship that actually lands in
`asset.py`; Lesson 1.5's own example was explicitly thrown away, never
landing anywhere. Lesson 1.8 — `ValueError`, the exact class
`InvalidAssetError` subclasses. Lesson 1.9 — `Asset.__post_init__` and
its three existing guard clauses, modified here to raise the new class
instead of the old one.

## Terms used in this lesson

- **subclass / parent class (base class)** — reapplied in full from
  Lesson 1.5: a subclass is defined with a parent class named in
  parentheses after its own name — `class InvalidAssetError(ValueError):`
  — inheriting everything the parent already provides. Lesson 1.5's own
  demonstration was explicit throwaway, discarded before ever landing in
  this project; this lesson is the first time this project's own
  tracked code actually has one.
- **IS-A relationship** — reapplied in full from Lesson 1.5: every
  `InvalidAssetError` *is a* `ValueError` too — anything written to
  catch `ValueError` generically still catches `InvalidAssetError`
  without ever being told the new class exists, proven directly in this
  lesson's own isolated lab.
- **`super()`** — reapplied in full from Lesson 1.5: inside a subclass's
  own `__init__`, calls the parent class's own version of that method,
  bound to the same instance — `super().__init__(message)` runs
  `ValueError`'s own real constructor, which is what actually stores
  `message` as this exception's text.
- **`try`** — new. A block that tells Python "run this code, but if any
  of it raises an exception, don't let the program crash immediately —
  check the `except` clauses that follow first." Exists because,
  without it, every exception this project has raised so far (Lessons
  1.6–1.11) has had exactly one possible outcome: an uncaught traceback,
  ending the program.
- **`except`** — new. A clause following `try`, naming one specific
  exception type (or a tuple of several) to catch; its own indented
  block runs only if the `try` block actually raised a matching
  exception, and the exception is considered *handled* — the program
  continues normally afterward instead of crashing.
- **`else` (in a `try` statement)** — new. A clause after every `except`
  clause, whose block runs only if the `try` block completed with *no*
  exception at all — genuinely different from simply writing that code
  directly inside the `try` block itself, because code inside `else` is
  never at risk of being caught by the same `except` clause that guards
  the `try` block above it.
- **`except ... as name`** — new. The optional part of an `except`
  clause that binds the actual caught exception instance to a local
  name, usable inside that clause's own block — `except ValueError as
  error:` makes `error` refer to the real, specific exception object
  that was raised, letting code read its message (`str(error)`) or, for
  a custom exception carrying extra data, any attribute it defines,
  rather than only knowing an exception of that type occurred.
- **`IndexError`** — new. A real, built-in exception Python raises when
  a sequence (a `list`, a `str`, a `tuple`) is indexed with a position
  that doesn't exist — `values[1]` on a one-element list, for example.
  Exists here as the concrete exception this unit's `bad_version`/
  `good_version` contrast is built around.
- **`ZeroDivisionError`** — new. A real, built-in exception Python
  raises when a division operation's divisor is `0`. Exists here as the
  concrete exception `finally`'s own isolated proof is built around,
  chosen specifically because it's trivially easy to trigger on demand.
- **`finally`** — new. A clause that runs unconditionally — whether the
  `try` block succeeded, raised a caught exception, or even in the
  middle of a `return` already underway inside `except` — exists
  specifically for cleanup code that must run no matter what happened.

## Objects and methods used

**`InvalidAssetError`**

- *What it is:* a brand-new exception class this project defines
  itself — the first exception in this project that isn't a plain
  Python builtin.
- *Implementation:* `class InvalidAssetError(ValueError): def
  __init__(self, field: str, message: str) -> None: self.field = field;
  super().__init__(message)` — subclasses `ValueError` directly; its own
  `__init__` takes two arguments, stores `field` as a new, real instance
  attribute, and hands `message` to `ValueError`'s own `__init__` via

  itself display `message`'s text.

  "an `Asset` was given an invalid value for one particular field" —

  machine-readable field name (new behavior) for that one failure.

  `message` string; depends on `ValueError`'s own `__init__` existing
  to hand `message` off to.

  `InvalidAssetError` specifically (to read `.field`) or as plain

## Concept Unit: `try` and `except`

### The Problem

Every exception this project has ever raised — Lesson 1.6's `NameError`,
Lesson 1.7's `TypeError`, Lesson 1.8's and 1.9's `ValueError` — has
always propagated straight past uncaught, ending the program with a
traceback. Is there a way to run code that *might* raise an exception,
and, if it actually does, keep the program running instead of crashing?

> **Before reading on, try this:**
> - Every `break_*.py` verification file this curriculum has ever run
>   has been *expected* to crash, deliberately. If a real program
>   wanted to attempt something risky — like converting user-typed text
>   to a number — without crashing the instant that text turns out to
>   be invalid, what shape do you predict the surrounding code would
>   need, given nothing in this project's own code has ever tried to
>   survive an exception before?
> - `int("42")` succeeds; `int("not a number")` raises a real
>   `ValueError` — familiar territory since Lesson 1.8. If a block of
>   code could say "attempt this, and if it raises a `ValueError`
>   specifically, run this other code instead," what do you predict the
>   two keywords marking those two sections might be, given how
>   deliberately paired `if`/`else` already are?
> - Once an exception is caught this way, do you predict the program
>   resumes running normally right after the catching code, or does
>   Python still end the program once the catching code finishes?

  this project has no caller yet that constructs assets from

- **Change type:** N/A.

### Isolated Concept

```python
def to_int(value):
    try:
        return int(value)
    except ValueError:
        return None


print(to_int("42"))
print(to_int("not a number"))
```

Run for real (`lab1_try_except.py`):

```
42
None
```

`to_int("42")` — `int("42")` succeeds inside the `try` block, returning
`42` immediately; the `except` clause never runs at all. `to_int("not a
number")` — `int("not a number")` raises a real `ValueError`, exactly
as Lesson 1.8 already proved for a case like this; instead of that
exception propagating uncaught, `except ValueError:` catches it, and
its own block — `return None` — runs instead. Real, confirmed proof,
not a claim: the program did not crash; `print(to_int("not a
number"))` still ran and printed `None`, right after the failed
conversion, exactly as if nothing had gone wrong at the call site
itself.

This is called `try`/`except` — a **`try`** block naming code that
might raise, followed by one or more **`except`** clauses, each naming
one exception type to catch and a block to run instead, only if that
exact type (or a subclass of it, proven directly in this lesson's
fourth unit) was actually raised.

Discarded: `to_int` exists only to prove `try`/`except`'s own basic
behavior. It will not appear in the Asset Manager project again.

### Mechanical Walkthrough

- **`def to_int(value):`** — an ordinary function definition, reapplied
  general syntax from every earlier lesson; no type annotations here,
  since this throwaway example is deliberately kept minimal.
- **`try:`** — new: opens a block Python will attempt to run in full,
  watching for any exception raised anywhere inside it.
- **`return int(value)`** — `int(...)`, reapplied from Lesson 1.6's own
  discussion of type non-enforcement, called for real here — the
  "risky" operation this whole unit is built around, since it's exactly
  the call already known, from Lesson 1.8, to raise `ValueError` on
  bad input.
- **`except ValueError:`** — new: names the *exact* exception type this
  clause catches; `ValueError`, reapplied in full from Lesson 1.8, is
  the same class `int(...)` is already known to raise for unparseable
  text.
- **`return None`** — reapplied general syntax; runs only if `except
  ValueError:`'s own condition matched, handing back `None` instead of
  letting the exception propagate.

### CS Lens

This is **exception handling** — separating the code that might fail
from the code that decides what to do when it does, rather than
checking for every possible failure condition inline before attempting
an operation. This is a hard concept, worth more than one real-world
connection.

```
Also recognized in: Java's and C#'s own try/catch, JavaScript's
try/catch around a fallible fetch() call, a circuit breaker pattern in
distributed systems isolating a failing service call, a physical fuse
in an electrical circuit — designed specifically to fail safely rather
than let a fault propagate further
```

### SE Lens

The alternative not chosen is checking validity *before* attempting the
risky operation — `if value.lstrip("-").isdigit(): return int(value)
else: return None` — avoiding the exception entirely rather than
catching it. The real tradeoff: a pre-check like that has to correctly
anticipate every way the operation could fail, and can drift out of
sync with what actually makes `int(...)` raise; `try`/`except` instead
lets the operation itself be the source of truth about what's valid,
at the real cost of an exception object actually being constructed and
raised — measurably more expensive than a plain `if` check, though
irrelevant at this project's current scale.

## Concept Unit: The `else` Clause

### The Problem

Code that should only run once a `try` block has genuinely succeeded
could just be written as the last lines inside that same `try` block —
but if *that* code happens to raise the same exception type the
`except` clause is watching for, would it get silently, incorrectly
caught too, even though the original risky operation actually
succeeded?

> **Before reading on, try this:**
> - If a `try` block contains two risky lines, one after another, and
>   only the *second* one raises, does the single `except` clause below
>   them know which line actually failed — or does it treat both the
>   same way, regardless of which one raised?
> - Given that risk, do you predict a `try` block's own `else` clause —
>   if one exists — runs *inside* the same protected region as the
>   `try` block itself, or somewhere `except` can no longer reach it?
> - If code placed in `else` raises the *same* exception type the
>   `except` clause above it is watching for, do you predict that
>   exception gets caught anyway, or does it propagate uncaught, since
>   `else` only runs after the `try` block has already fully finished?

### Project Change

- **Reference Source:** No reference counterpart — original curriculum
  project.
- **Files affected:** none — proven in isolation, same reasoning as the
  previous unit.
- **Change type:** N/A.
- **Location:** N/A.
- **Dependencies:** none.

### Isolated Concept

```python
def bad_version(values):
    try:
        first = values[0]
        second = values[1]
    except IndexError:
        return "no first element"
    return f"{first}, {second}"


def good_version(values):
    try:
        first = values[0]
    except IndexError:
        return "no first element"
    else:
        second = values[1]
        return f"{first}, {second}"


print(bad_version([1]))
print(good_version([1]))
```

Run for real (`lab2_else_clause.py`) — the second line is *expected* to
fail:

```
no first element
Traceback (most recent call last):
  File "lab2_else_clause.py", line 21, in <module>
    print(good_version([1]))
  File "lab2_else_clause.py", line 16, in good_version
    second = values[1]
IndexError: list index out of range
```

`bad_version([1])` — a one-element list — is genuinely misleading: real,
confirmed proof, not a claim. `values[0]` succeeds (`[1]` has a first
element); `values[1]` then raises a real `IndexError`, because index
`1` is out of range for a one-element list. Since *both* lines sit
inside the same `try` block, the `except IndexError:` clause catches
this second failure too, and returns `"no first element"` — a wrong
diagnosis, since the first element genuinely existed; it was the
*second* index that failed.

`good_version([1])` separates the two: only `values[0]` sits inside
`try`; `values[1]` moves to an `else` clause, running only after the
`try` block finishes with no exception at all. When `values[1]` raises
`IndexError` there, it propagates completely uncaught — the traceback
shown above is real and expected, not a bug — because `except
IndexError:` only ever watches the `try` block itself, never `else`.
This is exactly what the **`else` clause** is for: code that depends on
the `try` block having already succeeded, kept genuinely outside that
block's own protected region, so a *different* failure in that later
code is never misattributed to the original risky operation.

Discarded: `bad_version`/`good_version` exist only to prove this
contrast. Neither will appear in the Asset Manager project again.

### CS Lens

A direct extension of the previous unit's own exception-handling idea —
`else` narrows the *scope* of what a given `except` clause is actually
responsible for, worth its own real-world connection since the
principle behind it recurs elsewhere.

```
Also recognized in: keeping a database transaction's own commit call
outside a broad except block that's only meant to catch connection
errors, a linter warning against catching an overly broad exception
type around too much code, a security review flagging a try block that
silently swallows more failure modes than it was written to handle
```

### SE Lens

The alternative not chosen is simply writing success-path code as the
last lines inside `try`, accepting the risk `bad_version` just proved
real. The tradeoff: `else` costs one more block and one more
indentation level, for a real, concrete safety guarantee — a failure in
success-path code is never silently misreported as the original risky
operation failing, which `bad_version`'s own wrong message ("no first
element", when the first element genuinely existed) proves is a real,
not theoretical, risk.

## Concept Unit: The `finally` Clause

### The Problem

Some code needs to run no matter what happened — succeeded, failed and
got caught, or failed and didn't. Is there a clause that runs
unconditionally, even when an `except` clause's own block is in the
middle of a `return`?

> **Before reading on, try this:**
> - If a `try` statement has a `finally` clause, and the `try` block
>   succeeds with no exception at all, do you predict `finally` still
>   runs, or only `else` (if present) runs instead?
> - If an `except` clause's own block contains a `return` statement,
>   and a `finally` clause exists below it, do you predict `finally`
>   runs *before* that `return` actually hands control back to the
>   caller, or does the `return` skip `finally` entirely, the way it
>   would skip any other code positioned after it?
> - Given `finally`'s own name, what real-world cleanup task — closing
>   a file, releasing a lock, printing a status message — do you
>   predict it's actually meant for, given it runs whether or not
>   anything went wrong?

### Project Change

- **Reference Source:** No reference counterpart — original curriculum
  project.
- **Files affected:** none — proven in isolation, same reasoning as the
  previous two units.
- **Change type:** N/A.
- **Location:** N/A.
- **Dependencies:** none.

### Isolated Concept

```python
def process(value):
    print("starting")
    try:
        result = 100 / value
    except ZeroDivisionError:
        print("cannot divide by zero")
        return None
    finally:
        print("cleanup runs no matter what")
    return result


print(process(5))
print(process(0))
```

Run for real (`lab3_finally_clause.py`):

```
starting
cleanup runs no matter what
20.0
starting
cannot divide by zero
cleanup runs no matter what
None
```

This is a control-flow timing question, not a changing-value one — the
real proof is *when* `"cleanup runs no matter what"` prints relative to
each function actually returning:

1. `process(5)` — `print("starting")` runs first.
2. `result = 100 / value` succeeds (`100 / 5` is `20.0`); no exception,
   so `except` never runs.
3. `finally`'s own block runs next — `"cleanup runs no matter what"`
   prints — *before* `process`'s own `return result` actually hands
   `20.0` back to the caller, because a `finally` clause always runs
   before a `try` statement is considered finished, success or not.
4. `print(process(5))` finally prints `20.0`, confirming the return
   value survived `finally` running in between.
5. `process(0)` — `print("starting")` runs again.
6. `result = 100 / value` raises `ZeroDivisionError` (`100 / 0`); the
   `except ZeroDivisionError:` clause catches it, printing `"cannot
   divide by zero"`, then reaches `return None`.
7. Real, confirmed proof of the genuinely surprising fact this unit
   exists to prove: `return None` does *not* immediately hand control
   back — `finally`'s own block still runs first, printing `"cleanup
   runs no matter what"` *after* the `except` block's own `return` has
   already been reached, but *before* that return actually completes.
8. Only after `finally` finishes does `process(0)`'s `None` actually
   reach `print(process(0))`.

This is called the **`finally` clause** — the one part of a `try`
statement guaranteed to run regardless of whether the `try` block
succeeded, failed and was caught, or is in the middle of returning
from inside an `except` block.

Discarded: `process` exists only to prove `finally`'s own timing. It
will not appear in the Asset Manager project again.

### CS Lens

This is **guaranteed cleanup** / the **finally block pattern** — code
that must run regardless of how a protected region of code actually
exits, whether normally or via an exception. This is a hard concept,
worth more than one real-world connection.

```
Also recognized in: a file handle's own close() call, a database
connection's own release back to a pool, Java's and C#'s identical
try/finally, a `with` statement's own automatic cleanup (a future
lesson's own subject, built on this exact same guarantee), an
electrical safety interlock that always de-energizes a circuit when a
panel is opened, success or failure
```

### SE Lens

The alternative not chosen is writing the cleanup code once after the
`try` statement and once again inside every `except` clause that
returns early — real, working, but duplicated, and fragile the moment a
new `except` clause is added later and the cleanup line is forgotten in
it. `finally`'s real cost: it always runs, even for exception types
never explicitly caught by any `except` clause — a `finally` block
placed carelessly can end up hiding or altering an exception it wasn't
actually meant to touch, if it contains a `return` or another exception
of its own.

## Concept Unit: Custom Exceptions

### The Problem

`Asset.__post_init__` currently raises a plain `ValueError` for all

invalid, but has to parse the message text itself to learn *which*
field. Given Lesson 1.5 already proved a class can subclass another

raise a real, named exception class this project defines itself —

> **Before reading on, try this:**
> - Lesson 1.5 already proved `class Cat(Animal):` makes `Cat` a real
>   subclass of `Animal`, inheriting its methods. Given `ValueError`
>   is a real, ordinary Python class — reapplied since Lesson 1.8 —

- **`class InvalidAssetError(ValueError):`** — reapplied subclass syntax

- **`def __init__(self, field: str, message: str) -> None:`** — an
  ordinary method signature, reapplied general syntax; two parameters
  beyond `self`, both annotated `str` per Lesson 1.6's own conventions.
- **`self.field = field`** — an ordinary instance attribute assignment,
  reapplied from every earlier lesson — storing `field` directly on the
  new exception instance, something plain `ValueError` never provides.
- **`super().__init__(message)`** — **`super()`**, reapplied in full
  from Lesson 1.5: returns a reference to the parent class,
  `ValueError`, bound to this same instance; `.__init__(message)` calls
  `ValueError`'s own real constructor with `message`, which is what
  makes `str(error)` and the traceback's own displayed text actually
  work — without this line, `ValueError`'s own message-storing behavior
  would never run at all, and `str(error)` would print an empty string
  instead.
- **`raise InvalidAssetError("name", "Asset name must not be empty")`**
  (asset.py, line 23, and its two siblings) — `raise`, reapplied in
  full from Lesson 1.9: constructs a new `InvalidAssetError`, calling
  its own `__init__` with the field name and message, then immediately
  raises it — mechanically identical to Lesson 1.9's own plain
  `ValueError` raises, with a different, more specific class supplying
  the actual behavior.

### CS Lens

This is **exception hierarchies** — organizing failure conditions with
the same subclass/parent-class relationships ordinary classes use,
letting code catch broadly (a generic parent type) or narrowly (a
specific subclass) depending on how much it actually needs to know.
This is a hard concept, worth more than one real-world connection.

```
Also recognized in: Java's own checked exception class hierarchies,
HTTP status codes organized into families (4xx client errors, 5xx
server errors) that a client can handle broadly or specifically, a
medical diagnosis taxonomy where a broad category and a specific
condition both apply to the same patient at once, a company's own
organizational chart, where reporting to a specific manager also means
reporting, transitively, to everyone above them
```

### SE Lens
