# Lesson 1.7: Dataclasses

**What you will build.** `Owner` and `Asset` both trade their hand-written
`__init__` for a short, declarative list of typed class attributes under
a single decorator, `@dataclass`. Nothing about what either class
*stores* changes — `Owner` still has a `name` and an `email`; `Asset`
still has a `name`, `serial_number`, `category`, `owner`, and
`is_retired`. What changes is *who writes* the constructor, and two
methods neither class has ever had before: a real `__repr__` and a real
`__eq__`, both generated the instant the decorator is applied. The
transferable problem: constructor bodies that are genuinely the same
shape every time — assign each parameter to a matching attribute,
nothing else — are exactly the kind of boilerplate a language can
generate correctly on your behalf, and generating it buys more than
saved typing: it buys a `__repr__` and an `__eq__` this project has never
had, and a real, load-bearing shift in what `==` even means for these two
classes.

**What you need to know first.** Lesson 1.1 — Classes and Objects:
`class`, `__init__`, instance attribute, `self`, `is`, and — critically —
`==`'s *default* behavior on a plain class with no `__eq__` of its own,
which this lesson directly overturns for `Owner` and `Asset`
specifically. Lesson 1.4 — Composition: `Owner`, `Asset.owner`, and the
HAS-A relationship this lesson's own generated `__repr__` for `Asset`
shows nested inside its output. Lesson 1.6 — Type Hints: the `name: Type`
annotation syntax this lesson reuses in a new position — directly inside
a class body, never inside a `def` line's parentheses — and
`__annotations__`, the same inspectable dict `@dataclass` itself reads to
decide what fields to generate code for.

## Terms used in this lesson

- **`class`** — reapplied in full from Lesson 1.1: the keyword that opens
  a class definition, a blueprint for building instances that all share
  the same methods.
- **`self`** — reapplied in full from Lesson 1.1: the conventional name
  for an instance method's first parameter, automatically bound to the
  specific instance a method is called on. Still present in
  `Asset.describe` and `Asset.mark_retired`, both untouched by this
  lesson; no longer written by hand in either class's constructor, since
  this lesson replaces both hand-written `__init__` methods with a
  generated one.
- **instance attribute** — reapplied in full from Lesson 1.1: a piece of
  data stored on one specific instance. `Owner`'s `name`/`email` and
  `Asset`'s five attributes are still instance attributes after this
  lesson — only how each gets declared and assigned changes.
- **`is`** — reapplied in full from Lesson 1.1: compares whether two
  names refer to the exact same object in memory, never whether their
  contents look alike. This lesson's central contrast depends on `is`
  staying exactly what it's always been, while `==` changes underneath
  it.
- **`==`** — reapplied in full from Lesson 1.1, and directly overturned
  for `Owner` and `Asset` specifically: on a plain object with no
  `__eq__` of its own, `==` falls back to identity — the exact same
  comparison `is` performs, so `Owner("A", "a@x.com") == Owner("A",
  "a@x.com")` was `False` for two separately-built, identical-looking
  `Owner`s before this lesson (they're different objects). Once
  `@dataclass` generates a real `__eq__`, the exact same expression
  becomes `True` — same operator, same two objects' field values, a
  completely different comparison underneath, because a real method now
  intercepts it instead of falling through to `object`'s default.
- **dunder method** — reapplied in full from Lesson 1.1: a method whose
  name starts and ends with two underscores, invoked by Python itself in
  response to a language-level operation rather than called directly by
  name. `__init__` (already known), and `__repr__`/`__eq__` (new to this
  project this lesson) are all dunder methods — the three `@dataclass`
  generates by default.
- **type annotation** — reapplied in full from Lesson 1.6, used here in a
  genuinely new position: every annotation Lesson 1.6 wrote sat inside a
  `def` line — a parameter's `name: Type`, or a return's `-> Type`. This
  lesson's annotations, `name: str` and `email: str` sitting directly
  inside a class body with no `def` anywhere nearby, are the same
  colon-then-type syntax applied to a class's own attributes instead of a
  function's parameters — and, unlike a plain assignment, `@dataclass`
  actually reads these annotations to decide what code to generate,
  covered fully below.
- **decorator** — new. Syntax placing `@name` directly above a `class` or
  `def` line, meaning: call `name` with the thing defined immediately
  below as its one argument, then rebind the original name to whatever
  that call returns. `@dataclass` above `class Owner:` is exactly
  equivalent to writing `class Owner: ...` first, then, immediately
  after, `Owner = dataclass(Owner)` — decorator syntax exists so that
  rebind-after-definition, an extremely common pattern (register a class,
  wrap a function, generate methods for a class), can be written directly
  above the definition it modifies instead of as a separate statement
  below it, which a reader could easily miss or a later edit could
  separate from the definition it belongs to.
- **field default value** — new. Writing `= value` directly after a
  class-body field's type annotation — `is_retired: bool = False` —
  giving that field a value it takes on when the generated constructor's
  caller doesn't supply one. Exists so a field doesn't have to become a
  required argument on every single call when it has one
  obviously-correct starting value nearly all the time.
- **`bool`** — reapplied in full from Lesson 1.2 (as a value) and Lesson
  1.6 (as a type name): `is_retired: bool = False` uses `bool` in both
  senses in the same line — `bool` naming the type, `False` a literal
  value of that type.
- **`TypeError`** — new. A real, built-in exception Python raises when an
  operation gets a value of the wrong type, or the wrong number of
  arguments, for what it's doing. Exists here as the mechanism proving
  `dataclass` refuses to build a class with a required field declared
  after a defaulted one — the same category of exception (a real, named,
  built-in class) as Lesson 1.6's `NameError`, raised for a different
  reason: not an unresolved name, but a call `dataclass` itself makes
  internally, on the class's own behalf, that would otherwise build an
  invalid signature.
- **`object`** — reapplied in full from Lesson 1.1: the real built-in
  class every other class implicitly inherits from, whether it says so
  or not. Relevant here specifically because `object` itself already
  defines default `__repr__` and `__eq__` methods — the ones a class
  falls back to using when it defines none of its own, exactly what
  `PlainPoint`'s isolated proof shows for `__repr__`, and exactly what
  Lesson 1.1 already proved for `==` on every plain class in this
  project before this lesson.
- **`__class__`** — new. A real attribute every object carries,
  automatically, pointing to the exact class that built it — `jane.
  __class__` is `Owner` itself, the class object, not a string naming
  it. Exists because an object's own class is something code sometimes
  needs to ask about directly (to compare two objects' types, or to look
  up that class's own name), rather than only being knowable by already
  having written `isinstance(jane, Owner)` with `Owner` hard-coded by
  the person writing the check.
- **`__qualname__`** — new. A real attribute a class carries, holding its
  own fully-qualified name as a plain string (`"Owner"`, `"Asset"`) — the
  same name that appeared after the `class` keyword when it was defined.
  Exists so code building a representation of an object (exactly what
  `__repr__` does) can read the class's real name live, rather than a
  name someone typed by hand into the method body, which could drift out
  of sync if the class were ever renamed.
- **`NotImplemented`** — new. A real, built-in singleton value — not the
  same thing as the `NotImplementedError` exception, and never raised —
  that a dunder method like `__eq__` returns to mean "I don't know how
  to compare against this particular other type; ask something else."
  Exists so Python's own `==` machinery can correctly try the *other*
  operand's own comparison method next, instead of a mismatched-type
  comparison silently and permanently deciding "not equal" too early.

## Objects and methods used

**`dataclass`**

- *What it is:* a decorator function, imported from Python's
  standard-library `dataclasses` module, that inspects a class's own
  annotated attributes and generates real methods for it.
- *Implementation:* `def dataclass(cls=None, /, *, init=True, repr=True,
  eq=True, order=False, ...)` — its real signature, from CPython's own
  `dataclasses.py`, confirmed this session — takes the class being
  decorated as its first argument, plus keyword-only flags controlling
  which methods get generated; this lesson uses every flag at its
  default value, so no flag is ever written explicitly in this lesson's
  own code.
- *Its use:* applied directly above both `Owner` and `Asset`, replacing
  what would otherwise be two hand-written `__init__` methods (and
  adding two methods, `__repr__`/`__eq__`, neither class has ever had)
  with generated equivalents.
- *Type:* a free function — module-level, imported by name, not a method
  on anything.
- *Responsibility:* read a class's own `__annotations__` dict — the exact
  dict Lesson 1.6 already proved Python builds automatically for any
  annotated `def` — to learn what fields exist and in what order, then
  build and attach `__init__`, `__repr__`, and `__eq__` methods (by
  default) matching those fields — nothing more; it never validates
  field values, never changes what a field is allowed to hold, and never
  touches any method the class body already defines by hand.
- *Depends on:* the class object itself, handed to it by decorator
  syntax, and that class's own `__annotations__` dict — a class with no
  annotated attributes at all would have `dataclass` generate an empty,
  no-argument `__init__`.
- *Connects to:* invoked automatically by Python at class-definition
  time, the instant decorator syntax evaluates `@dataclass` above `class
  Owner:`; the class it returns is the exact same name (`Owner`,
  `Asset`) every later line of this project's code refers to — nothing
  calling `Owner(...)` or `Asset(...)` needs to know it was ever wrapped
  this way.
- *Shape:* a class-transformation boundary — code that runs once, at
  definition time, before a single instance exists, permanently shaping
  what every future instance's class supports.

**`Owner.__init__`**

- *What it is:* `Owner`'s constructor, reapplied from Lesson 1.4 — the
  method Python calls automatically, once, the instant `Owner(...)`
  builds a new instance. No longer hand-written this lesson; generated
  by `dataclass` instead.
- *Implementation:* equivalent to `def __init__(self, name: str, email:
  str) -> None: self.name = name; self.email = email` — mechanically
  identical to the hand-written version Lesson 1.4 wrote, built instead
  from `Owner`'s own two annotated fields, in the exact order they're
  declared.
- *Its use:* still the only way `Owner` instances get built; this lesson
  changes who wrote it, not what calling it does.
- *Type:* an instance method — a dunder method — generated, not
  hand-written, for the first time in this project.
- *Responsibility:* unchanged from Lesson 1.4 — receive an owner's
  identifying data and store it onto the new instance.
- *Depends on:* the instance Python already allocated (`self`), and two
  caller-supplied values, `name` and `email`.
- *Connects to:* called by Python itself at construction, exactly as
  before; nothing about *who* calls it changed.
- *Shape:* the same boundary role as always — raw caller values crossing
  into stored state — now produced by `dataclass` reading `Owner`'s own
  field declarations instead of by a hand-written body.

**`Owner.__repr__`**

- *What it is:* a new method on `Owner` this project has never had
  before — the dunder method Python calls to build an object's official
  string representation, used by `repr()` and, when a class defines no
  string-conversion method of its own, by `print()` and `str()` as well.
- *Implementation:* the real generated method, confirmed this session
  directly from CPython's own `dataclasses.py` (Python 3.14): `return
  f"{self.__class__.__qualname__}(name={self.name!r},
  email={self.email!r})"` — every field listed in declaration order as
  `field=value`, each value's own `repr()` used for its printed form
  (hence the quotes around each string), and the class name read live
  from `self.__class__` rather than hard-coded, so a subclass would
  print its own name correctly too.
- *Its use:* the entire reason two, separately-constructed `Owner`s can
  be told apart from each other, or confirmed identical, just by
  printing them — something this project's `Owner` class has never been
  able to do until this lesson.
- *Type:* an instance method — a dunder method — generated.
- *Responsibility:* build one specific, complete, readable string showing
  this exact instance's current field values — nothing else; it never
  mutates anything, and it's called only when something asks for this
  object's representation.
- *Depends on:* `self.name` and `self.email`'s current values, and,
  recursively, each of those values' own `__repr__` (here, `str`'s own,
  since both fields are plain strings).
- *Connects to:* called by the built-in `repr()` function, by
  `print()`/`str()` (since `Owner` defines no separate `__str__`), and,
  recursively, by any *other* dataclass's own generated `__repr__` if
  that dataclass happens to hold an `Owner` — exactly `Asset`'s
  situation, below.
- *Shape:* a debugging/inspection boundary — output meant for a
  developer reading a terminal or a log, not user-facing text (that role
  belongs to `Asset.describe`, untouched by this lesson).

**`Owner.__eq__`**

- *What it is:* a new method on `Owner` this project has never had
  before — the dunder method Python calls whenever the `==` operator is
  used with an `Owner` on its left-hand side.
- *Implementation:* the real generated method, confirmed this session
  directly from CPython's own `dataclasses.py` (Python 3.14): `def
  __eq__(self, other): if self is other: return True; if other.__class__
  is self.__class__: return self.name==other.name and
  self.email==other.email; return NotImplemented` — an identity
  fast-path first (skips field comparison entirely when it's literally
  the same object), then a type check, then every field compared with
  `and`, short-circuiting on the first mismatch, rather than the
  tuple-packing a reader might expect from the documentation's own
  "compared as if it were a tuple of its fields" description.
- *Its use:* the entire reason two, separately-constructed `Owner`s with
  identical `name`/`email` now compare equal with `==` — something this
  project's `Owner` class has never been able to do until this lesson;
  every earlier lesson's `==` on an `Owner` or `Asset` fell back to
  identity.
- *Type:* an instance method — a dunder method — generated.
- *Responsibility:* decide whether two objects represent the same
  *data*, not the same object in memory — the complete job `==` is being
  asked to do the moment a reader writes `owner1 == owner2` instead of
  `owner1 is owner2`.
- *Depends on:* both objects' `__class__` (to refuse comparing an
  `Owner` to something unrelated) and both objects' full set of field
  values.
- *Connects to:* invoked by Python automatically whenever `==` appears
  with an `Owner` on the left; returns `NotImplemented` (never a plain
  `False`) for a mismatched type, which is what lets Python correctly
  fall back to trying the *other* operand's own `__eq__`, or finally
  `False`, instead of declaring two unrelated objects unequal too early.
- *Shape:* a core language-operator boundary — code invisibly wired into
  `==` itself, not something any of this project's own code calls by
  name.

**`Asset.__init__`**

- *What it is:* `Asset`'s constructor, reapplied from Lessons 1.1 and
  1.4. No longer hand-written; generated by `dataclass`.
- *Implementation:* equivalent to `def __init__(self, name: str,
  serial_number: str, category: str, owner: Owner, is_retired: bool =
  False) -> None: ...` — five parameters matching `Asset`'s five
  annotated fields in declaration order, the last one, `is_retired`,
  carrying a default value, covered fully in this lesson's fourth unit.
- *Its use:* still the only way `Asset` instances get built; unlike
  `Owner`'s conversion, this one changes something real: `is_retired`
  becomes an optional, caller-settable parameter for the first time —
  previously, no version of `Asset.__init__` this project has ever had
  accepted it as an argument at all; it was always forced to `False`
  internally.
- *Type:* an instance method — a dunder method — generated.
- *Responsibility:* unchanged in spirit from Lessons 1.1/1.4 — set up
  every instance attribute an `Asset` needs from the moment it exists —
  with one honestly-stated new capability: a caller can now choose to
  construct an already-retired `Asset` directly, covered in this
  lesson's fourth unit.
- *Depends on:* `self`, three string values, a real `Owner` instance,
  and, optionally, a `bool` for `is_retired`.
- *Connects to:* called by Python at construction, exactly as before.
- *Shape:* the same boundary as always, now generated from `Asset`'s own
  field declarations rather than a hand-written body — and, for
  `is_retired` specifically, a boundary that's genuinely more permissive
  than it was a lesson ago.

**`Asset.__repr__`**

- *What it is:* a new method on `Asset`, generated by `dataclass`,
  identical in kind to `Owner.__repr__` above.
- *Implementation:* the same real generated shape, extended to five
  fields: `return
  f"{self.__class__.__qualname__}(name={self.name!r},
  serial_number={self.serial_number!r}, category={self.category!r},
  owner={self.owner!r}, is_retired={self.is_retired!r})"` — `owner`'s
  own value rendered through *its* `!r`, which, since `Owner` is now
  also a dataclass, is `Owner`'s own generated `__repr__` output nested
  directly inside `Asset`'s.
- *Its use:* proves, for real, that generated `__repr__` composes
  correctly across two related dataclasses without either one needing to
  know about the other's printed form.
- *Type:* an instance method — a dunder method — generated.
- *Responsibility:* build one complete, readable string showing every
  one of `Asset`'s five current field values, including a full nested
  rendering of its `owner`.
- *Depends on:* all five of `self`'s current field values, and,
  recursively, `self.owner`'s own `__repr__`.
- *Connects to:* called by `repr()`, and by `print()`/`str()` in
  `Asset`'s case too; calls `Owner.__repr__` indirectly, through
  Python's own `repr()` machinery, whenever it reaches the `owner`
  field.
- *Shape:* the same debugging/inspection boundary as `Owner.__repr__`,
  now demonstrating composition (Lesson 1.4's own HAS-A relationship)
  showing up automatically in generated output, with no extra code
  written for it.

**`Asset.__eq__`**

- *What it is:* a new method on `Asset`, generated by `dataclass`,
  identical in kind to `Owner.__eq__` above.
- *Implementation:* the same real generated shape, extended to five
  fields: `if self is other: return True; if other.__class__ is
  self.__class__: return self.name==other.name and
  self.serial_number==other.serial_number and
  self.category==other.category and self.owner==other.owner and
  self.is_retired==other.is_retired; return NotImplemented` —
  `self.owner==other.owner` calling `Owner`'s own generated `__eq__` in
  turn, the same nested composition `__repr__` already shows.
- *Its use:* two `Asset`s built from separately-constructed but
  identical `Owner`s and identical scalar fields now compare equal —
  proving field-value equality composes the same way `__repr__` does.
- *Type:* an instance method — a dunder method — generated.
- *Responsibility:* decide whether two `Asset`s represent the same data,
  field by field, `owner` included.
- *Depends on:* both objects' `__class__` and full set of field values,
  including each one's `owner`'s own equality.
- *Connects to:* invoked by `==`; calls `Owner.__eq__` indirectly, as
  part of the `and`-chained field comparison, the moment it reaches the
  `owner` field.
- *Shape:* the same core language-operator boundary as `Owner.__eq__`.

**`repr()`**

- *What it is:* a real Python built-in function — always available, no
  import needed — that returns an object's "official" string
  representation.
- *Implementation:* `repr(object) -> str` — calls `object.__repr__()`
  and returns whatever string that method hands back.
- *Its use:* this lesson's own isolated labs and the real project's
  final confirmation both call it explicitly, rather than relying on
  `print()`'s implicit fallback, to make clear exactly which method's
  output is being shown.
- *Type:* a built-in free function.
- *Responsibility:* nothing beyond forwarding to whatever `__repr__` the
  object it's given actually defines — the default, inherited from
  `object` itself, when a class defines none of its own.
- *Depends on:* the single object passed to it having a callable
  `__repr__` — every object does, since `object` itself defines a
  default one.
- *Connects to:* called directly by this lesson's own code; calls the
  target object's `__repr__` in turn — `object.__repr__` for
  `PlainPoint` in this lesson's isolated lab, `Owner.__repr__`/
  `Asset.__repr__` for the real project's own confirmation.
- *Shape:* a thin, direct entry point into whatever `__repr__` an object
  actually has — no logic of its own.

## Concept Unit: The `@dataclass` Decorator and the Generated `__init__`

### The Problem

`Owner.__init__` is two lines: `self.name = name`, `self.email = email`.
Nothing about those two lines is specific to `Owner` — they're "take
each parameter, store it under the same name" repeated once per field,
the exact same shape Lesson 1.1's `Asset.__init__` used, and the exact
same shape composition (Lesson 1.4) added `owner` to. If a class's
constructor is genuinely just this — no computed values, no validation,
nothing but plain assignment — is there a way to get that constructor
without writing it by hand at all?

> **Before reading on, try this:**
> - `Owner`'s two fields, `name` and `email`, are both already written
>   down somewhere in the class — as `self.name`/`self.email`
>   assignments inside `__init__`. If Python could read a list of a
>   class's field *names and types* directly, without a body to
>   execute, where do you think that list is already sitting, given
>   Lesson 1.6 already proved every annotated function has a real,
>   inspectable `__annotations__` dict?
> - Lesson 1.6 wrote annotations like `name: str` only ever inside a
>   `def` line's parentheses. What do you predict happens if the exact
>   same `name: str` syntax is written as its own line, directly inside
>   a class body, with no `def` anywhere near it — is that legal Python
>   at all?
> - If a tool existed that read a class's own field declarations and
>   *built* `__init__` for you automatically, what would have to change
>   about how the class is written for that tool to know it should do
>   this — some kind of marker, distinguishing "please generate a
>   constructor for me" from an ordinary class with no constructor at
>   all?

### Project Change

- **Reference Source:** No reference counterpart — original curriculum
  project.
- **Files affected:** `owner.py` — modified.
- **Change type:** replace (the entire hand-written `__init__` method is
  removed and replaced with two annotated class-level fields; a new
  import line is added at the top of the file).
- **Location:** the whole `Owner` class body — previously just `def
  __init__(self, name: str, email: str) -> None: ...` — is replaced; a
  new `from dataclasses import dataclass` line is added above the
  class, and `@dataclass` is added directly above `class Owner:`.
- **Dependencies:** `dataclasses`, a Python standard-library module — no
  installation needed, available in every Python install this project
  targets.

### The New Code

```python
from dataclasses import dataclass
```


  decorator syntax as `owner.py`'s own, calling `dataclass(Asset)` the
  instant the class body finishes executing and rebinding `Asset` to
  whatever comes back.
- **`class Asset:`** — reapplied in full from Lesson 1.1: unchanged
  syntactically; the class body is now entirely field declarations plus
  two untouched methods.
- **`name: str`, `serial_number: str`, `category: str`** (lines 9–11) —
  reapplied field-annotation syntax from this lesson's first unit,
  applied here to three of `Asset`'s own fields; none carries a
  default, so all three become required positional-or-keyword
  parameters of the generated `__init__`, in this declared order.
- **`owner: Owner`** (line 12) — the same field-annotation syntax,
  naming a project-defined class rather than a builtin — mechanically
  identical to `owner: Owner` already proven safe as a parameter
  annotation in Lesson 1.6; here it names a *field*, not a parameter,
  but the underlying rule (the name must be real and resolvable,
  exactly as Lesson 1.6's `Gadget`/`NameError` proof showed for
  parameter annotations) applies identically, satisfied here by the
  same `from owner import Owner` line already present since Lesson 1.6.
- **`is_retired: bool = False`** (line 13) — a **field default value**,
  new this lesson: `bool`, reapplied from Lessons 1.2/1.6, names the
  type; `= False` gives it a default, generated into `Asset.__init__`
  as `is_retired: bool = False` in the parameter list itself, exactly
  the way an ordinary Python function parameter gets a default.
  Declared last, deliberately, per the field-ordering rule the isolated
  `Broken` example just proved by failing when that order is reversed.
- **The generated `Asset.__init__`** (not itself a visible code line,
  the direct result of lines 9–13) — five parameters, `is_retired`
  optional and defaulting to `False`. This changes something real: a
  caller can now write `Asset("x", "y", "z", jane, is_retired=True)`
  and construct an already-retired asset directly — no version of
  `Asset.__init__` before this lesson has ever accepted that argument
  at all; `is_retired` was always forced to `False` inside the old
  hand-written body, regardless of what a caller supplied, because
  nothing a caller supplied was ever consulted for it.

### CS Lens

This is a **required-before-optional parameter ordering constraint** —
the rule that every fixed-arity function-like construct with optional
parameters needs some way to resolve "which argument did the caller
mean to skip," and the simplest resolution is refusing to let an
optional one hide a required one behind it. This is a hard concept,
worth more than one real-world connection.

```
Also recognized in: Python's own ordinary function default arguments —
the identical rule, decades older than dataclasses, C++ and Java's
overloaded/default-argument methods, SQL stored-procedure parameters
with defaults, command-line argument parsers that require positional
arguments before optional flags
```

### SE Lens

The alternative not chosen is keeping `is_retired` out of the generated
`__init__` entirely — possible with `dataclasses.field(init=False,
default=False)`, a second tool this lesson deliberately doesn't reach
for, to keep this lesson's own new material to one mechanism (a plain
field default) instead of two. The real, honest cost of that choice:
`is_retired` becoming constructible directly is a genuine, if small,
semantic loosening from every earlier lesson's version of `Asset` —
previously impossible, now one keyword argument away. Nothing about
this project's own single real invariant (`mark_retired`'s own guard,
unchanged and still enforced) breaks because of it — an asset
constructed already-retired is a legitimate state, not a corrupted one —
but it is a real, deliberate scope decision this lesson names plainly
rather than leaving for a reader to notice on their own.
