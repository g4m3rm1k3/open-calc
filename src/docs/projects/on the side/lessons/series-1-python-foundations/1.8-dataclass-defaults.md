# Lesson 1.8: Dataclass Defaults

**What you will build.** Nothing lands in the tracked project this
lesson — per its own blueprint entry, this is a Lab, a deliberately
disposable experiment, and nothing built here survives into `asset.py`
or `owner.py`. What gets built instead is a working, throwaway `Basket`
class, pushed through three stages: an ordinary Python function that
silently shares one mutable default across every call that doesn't
override it; a `@dataclass` field that tries the identical trick and is
flatly refused; and `dataclasses.field(default_factory=list)`, the real
fix, proven to give every instance its own independent list. The
transferable problem: a default value that's evaluated *once*, at
definition time, and then reused for every call or every instance
afterward, behaves completely differently depending on whether that
default is mutable — and Python's own dataclass machinery bakes in a
hard stop against the dangerous case, rather than trusting every future
programmer to remember never to do it.

**What you need to know first.** Lesson 1.3 — Instance vs Class
Attributes: mutable/immutable, and the mutable-class-attribute trap —
the closest previous relative of this lesson's own trap, though a
genuinely different mechanism, distinguished directly below. Lesson 1.7
— Dataclasses: `decorator`, `@dataclass`, and field default value
(`= value` directly after a class-body field's annotation) — this
lesson's whole subject is the one case that syntax can't safely cover.

## Terms used in this lesson

- **mutable/immutable** — reapplied in full from Lesson 1.3: a mutable
  object (a `list`, a `dict`, a `set`) can be changed in place after
  creation, keeping the same identity; an immutable one (a `str`, an
  `int`, a `bool`, `None`) cannot — any apparent change actually builds
  and returns a brand-new object. This lesson's entire trap depends on
  exactly this distinction: `False` (Lesson 1.7's `is_retired` default)
  is immutable, so sharing it costs nothing; a bare `[]` is mutable, so
  sharing it is dangerous.
- **decorator** — reapplied in full from Lesson 1.7: syntax placing
  `@name` directly above a `class` or `def` line, meaning "call `name`
  with the thing below it, then rebind the original name to whatever
  comes back." `@dataclass`, this lesson's own decorator, is the exact
  same mechanism.
- **field default value** — reapplied in full from Lesson 1.7: writing
  `= value` directly after a class-body field's type annotation, giving
  that field a value it takes on when a caller doesn't supply one. This
  lesson proves the one case where writing it this way — `items: list =
  []` — doesn't merely fail to help; `dataclass` refuses to accept it at
  all.
- **`list` literal (`[]`)** — reapplied from Lesson 1.3's assumed
  baseline scope: an empty, ordinary `list`, built fresh every time the
  literal syntax `[]` is evaluated — the exact fact this lesson's whole
  trap depends on, and the exact fact a *default value* violates by
  only ever evaluating that literal once, not once per call or once per
  instance.
- **mutable default argument trap** — new. The classic Python pitfall
  where a function parameter's default value — evaluated exactly once,
  when the `def` line itself runs, not once per call — is a mutable
  object: every call that relies on the default gets the *same* object,
  not a fresh one, so mutations made during one call are still visible
  the next time the default is used. Exists as a fact worth knowing
  specifically because Python's own syntax gives no warning at the
  point of writing `def f(x=[]):` — it's valid, unremarkable-looking
  code that behaves correctly for exactly one call.

- **`ValueError`** — new. A real, built-in exception Python raises when
  an operation gets a value of the right *type* but a wrong or
  unacceptable *value* — distinct from Lesson 1.7's `TypeError`, which
  covers a wrong type or wrong argument shape entirely. Exists here as
  the mechanism proving `dataclass` itself rejects a mutable field
  default: the value handed to `default` is a real `list`, the correct
  *type* for the field's own `list` annotation, but rejected as an
  unacceptable *value* for a default specifically, because of what
  sharing it would mean.

## Objects and methods used

**`field`**

- *What it is:* a real function, imported from the same `dataclasses`
  module as `dataclass` itself, used inside a class-body field's
  annotation to configure that field's behavior beyond a plain `=
  value` default — most commonly, as this lesson uses it, to supply a
  *factory* instead of a literal default value.
- *Implementation:* `def field(*, default_factory=..., ...)` — its real
  signature, from CPython's own `dataclasses.py`, confirmed this
  session, takes every parameter keyword-only, each one left unset
  unless the caller supplies it; `default_factory`, the one this lesson
  uses, accepts any zero-argument callable.
- *Its use:* `items: list = field(default_factory=list)` replaces the
  refused `items: list = []`, telling `dataclass` "call this function
  fresh for every instance that needs a default, instead of reusing one
  shared value."
- *Type:* a free function — module-level, imported by name.
- *Responsibility:* describe how one specific field should be built and
  treated by the methods `dataclass` generates — nothing about any
  *other* field, and nothing about the class as a whole (that's
  `dataclass`'s own job, reapplied from Lesson 1.7).
- *Depends on:* being assigned directly as a field's own value, in the
  exact position an ordinary default would go — `dataclass` recognizes
  the object `field(...)` returns and treats it specially, rather than
  using it literally as the default value itself.
- *Connects to:* called once, at class-definition time, by the class
  body itself; read by `dataclass` when it processes that field;
  `default_factory`, specifically, is called again *later* — once per
  instance, at construction time, whenever that instance's caller
  doesn't supply its own value.
- *Shape:* a per-field configuration boundary, sitting between a bare
  field annotation and `dataclass`'s own class-wide processing.

**`dataclass`**

- *What it is:* reapplied from Lesson 1.7 — the decorator function
  reading a class's own field declarations and generating `__init__`,
  `__repr__`, and `__eq__` from them.
- *Implementation:* unchanged from Lesson 1.7; this lesson exercises one
  specific internal check inside it — real source, confirmed this
  session, at `dataclasses.py`'s `_get_field` function — that inspects
  every field's own default value and raises if that default is a
  `list`, `dict`, or `set` (or, more generally, any type whose instances
  are checked as hashable — this lesson only ever exercises `list`, one
  concrete case of that broader check).
- *Its use:* this lesson's second unit deliberately triggers that
  specific check, proving it exists and reading its real error text.
- *Type:* a free function — a decorator.
- *Responsibility:* unchanged from Lesson 1.7, with one addition this
  lesson makes visible: refuse to generate an `__init__` at all, for
  the *whole* class, if any single field's own default is a known
  dangerous mutable type.
- *Depends on:* unchanged from Lesson 1.7.
- *Connects to:* unchanged from Lesson 1.7; this lesson's own `Basket`
  never reaches the point of having a generated `__init__` to call, in
  its second unit, because this exact check stops it first.
- *Shape:* unchanged from Lesson 1.7.

## Concept Unit: The Mutable Default Argument Trap

### The Problem

Every default value this project has ever written — `is_retired: bool =
False` (Lesson 1.7) — has been immutable: a `bool`, evaluated once,
shared freely, because nothing about sharing an immutable value can ever
go wrong. What happens if an ordinary Python function's default value is
something mutable instead — a `list`, built with `[]`? Does every call
that relies on that default get a fresh, empty list, the same way
calling `list()` fresh would, or something else entirely?

> **Before reading on, try this:**
> - Lesson 1.3 already proved a *class* attribute is shared by every
>   instance unless an instance sets its own. Given a function's default
>   parameter value is also written once, in the `def` line, and not
>   repeated per call, do you predict it behaves more like a class
>   attribute (shared) or more like a fresh local variable (private to
>   each call)?
> - If `def add_item(item, basket=[]):` is called twice in a row, each
>   time relying on the default rather than passing a `basket`
>   explicitly, do you predict the second call sees an empty list again,
>   or does it see whatever the first call already put into it?
> - Lesson 1.3's own class-attribute trap was fixed by giving each
>   instance its own attribute inside `__init__`, evaluated fresh per
>   instance rather than once per class. Does that same fix — "evaluate
>   it somewhere that runs again for each new case," rather than once,
>   up front — seem like it could apply here too, even though this
>   isn't a class attribute at all?

### Isolated Concept

```python
def add_item(item, basket=[]):
    basket.append(item)
    return basket


first_call = add_item("apple")
print(first_call)

second_call = add_item("banana")
print(second_call)

print(first_call is second_call)
```

Run for real (`lab1_mutable_default_trap.py`):

```
['apple']
['apple', 'banana']
True
```

`add_item("apple")` — the first call, relying entirely on `basket`'s
default — appends `"apple"` and returns `['apple']`, unsurprising.
`add_item("banana")` — a second, separate call, also relying on the
default, with no `basket` passed explicitly either time — returns
`['apple', 'banana']`, not `['banana']` alone. Real, confirmed proof,
not a claim: the second call's "default, empty list" already contained
`"apple"` before `"banana"` was ever appended. The final line,
`first_call is second_call`, prints `True` — `first_call` and
`second_call` are not two equal-looking lists; they are, literally, the
exact same object, per Lesson 1.1's own definition of `is`.

This is called the **mutable default argument trap**: `basket=[]`, the
literal `[]`, is evaluated exactly *once* — the moment Python executes
the `def add_item(...)` line itself, building the function object —
never again per call. Every call that doesn't override `basket`
explicitly receives that same one list, built once and reused forever,
exactly the way Lesson 1.3 already proved a class attribute is one
shared value until an instance gives itself its own. Nothing about
calling `add_item` looks dangerous at the call site; the danger is
entirely in the `def` line, evaluated long before any call happens.

Discarded: `add_item` exists only to prove this trap in the plainest
possible form — an ordinary function, no class, no `@dataclass`
anywhere. It will not appear in the Asset Manager project again. The
next unit asks the sharper question this lesson is actually about:
what happens when the identical trap is attempted inside a
`@dataclass`'s own field declarations instead.

### CS Lens

This is **eager evaluation of a default parameter, combined with shared
mutable state** — a language design choice (Python evaluates a `def`
line's default expressions once, at definition time, not once per call)
colliding with mutability (an object that can be changed in place,
rather than replaced). This is a hard concept, worth more than one
real-world connection.

```
Also recognized in: JavaScript's own historical `var` closures capturing
one shared mutable binding across a loop (a different mechanism, the
same "one shared thing, expected to be many separate things" shape), a
cached, shared database connection object accidentally reused across
unrelated requests, a single shared `Random` or `Scanner` instance
handed out from one static field in Java, a spreadsheet formula that
references one shared "helper" cell instead of computing its own value
```

### SE Lens

The alternative not chosen — writing `def add_item(item, basket=None):
if basket is None: basket = []` — is the actual idiomatic fix ordinary
Python code reaches for, deliberately not shown as a full solution
here, since this lesson's real destination is `dataclass`'s own
built-in answer, in its third unit. The real, honest cost of the
version just proven: nothing about `def add_item(item, basket=[]):`
looks wrong when written, or when read casually later; the bug is
silent until two calls that both rely on the default happen to run in
the same program, which can be far removed in time and location from
where the function was originally defined.

## Concept Unit: `dataclass` Refuses a Mutable Default

### The Problem

`is_retired: bool = False`, Lesson 1.7's own field default, is
immutable — sharing it costs nothing. If a dataclass field's default
were written the identical way, but with a mutable value instead —
`items: list = []` — would `@dataclass` generate the exact same silent
trap the previous unit just proved for an ordinary function, or does it
do something else?

> **Before reading on, try this:**
> - The previous unit proved `basket=[]` on an ordinary function shares
>   one list across every call. Given `@dataclass` reads field
>   declarations and generates a real `__init__` from them — mechanically
>   very close to a function's own parameter list, per Lesson 1.7 — do
>   you predict `items: list = []` as a dataclass field produces the
>   identical silent trap, one shared list across every instance that
>   doesn't override it?
> - Lesson 1.7 already proved `@dataclass` performs at least one
>   deliberate safety check before generating `__init__` — refusing a
>   required field declared after a defaulted one, with a real
>   `TypeError`. Given that precedent, do you think `@dataclass` might
>   check for a *mutable* default too, rather than silently generating
>   the trap — and if so, what do you predict happens instead of a
>   working, silently-broken class?

### Isolated Concept

from dataclasses import dataclass


@dataclass
class Basket:
    items: list = []

## Concept Unit: `field(default_factory=list)`

### The Problem

The previous unit's error message said plainly: `use default_factory`.
Is there a way to tell `@dataclass` "build a fresh, empty list for
every instance that needs one" — evaluated once *per instance*, not
once for the whole class — rather than reusing one shared object the
way a bare `= []` tried and failed to do?

> **Before reading on, try this:**
> - The problem with `items: list = []` was that `[]` only ever
>   evaluates once. If, instead of a literal value, a field's default
>   were a *function* that gets *called* fresh each time a new instance
>   needs one, would that function need to take any arguments to build
>   an empty list — or could the plainest possible "build one" function
>   already sitting in Python's own builtins do the job with nothing
>   handed to it at all?
> - `list`, on its own, with no parentheses, is a real Python object — a
>   class, callable as `list()` to build a fresh empty list. Given
>   `field()`'s `default_factory` parameter wants "a function to call,"
>   not "a value," what do you predict happens if `list` itself — not
>   `list()`, not `[]` — is handed to it directly?
> - Once `Basket` uses `field(default_factory=list)` correctly, do you
>   predict two separately-built `Basket` instances share one `items`
>   list, the way the first unit's `add_item` calls did — or does each
>   get its own, independent one this time?

### Isolated Concept

```python
from dataclasses import dataclass, field


@dataclass
class Basket:
    items: list = field(default_factory=list)


first_basket = Basket()
first_basket.items.append("apple")
print(first_basket.items)

second_basket = Basket()
print(second_basket.items)

print(first_basket.items is second_basket.items)
```

Run for real (`lab2_default_factory.py`):

```
['apple']
[]
False
```

`items: list = field(default_factory=list)` replaces the refused `items:
list = []`. `field(default_factory=list)` hands `list` itself — the
real builtin class, callable with no arguments to build a fresh, empty
list — as the *factory*, not a value. `dataclass`, reading this,
generates an `__init__` that calls `list()` fresh, once, every single
time a new `Basket` is constructed without its own `items` argument —
not once for the whole class, the exact fix for the previous two
units' shared trap. `first_basket = Basket()` calls that generated
`__init__`, which calls `list()` once, building `first_basket`'s own,
private, empty list; appending `"apple"` mutates only that one list.
`second_basket = Basket()` calls `__init__` again — `list()` is called
a *second* time, building a completely separate empty list, still
empty, unaffected by `first_basket`'s own append. The final line,
`first_basket.items is second_basket.items`, prints `False` — real,
confirmed proof, not a claim: these are two distinct objects, exactly
the opposite of the first unit's own `True` for `first_call is
second_call`.

This is called `default_factory` — a `field()` keyword argument naming
a zero-argument callable `dataclass` invokes fresh, per instance, rather
than a literal value evaluated once, per class.

Discarded: this working `Basket` exists only to prove `default_factory`
fixes the trap. Neither this `Basket` nor `add_item` from the first unit
will appear in the Asset Manager project again — per this lesson's own
Lab designation, nothing here lands in `asset.py` or `owner.py`.

## Closing

### Connect the Pieces

One throwaway `Basket`, traced through every unit built in this lesson,
start to finish — nothing here lands in the real project, per this
lesson's own Lab designation, but the trace still matters for what it
proves:

1. **The mutable default argument trap.** `add_item("apple")` and
   `add_item("banana")`, two separate calls to an ordinary function
   relying on `basket=[]`, silently share one list — `first_call is
   second_call` prints `True`, proving Python evaluates a default
   value once, at definition time, never again per call.
2. **`dataclass` refuses a mutable default.** `items: list = []`,
   written the identical way inside a `@dataclass`, is not silently
   allowed to repeat that trap — `@dataclass` raises a real
   `ValueError` the instant it runs, naming the exact field and
   pointing directly at the fix.
3. **`field(default_factory=list)`.** `Basket()` built twice in a row
   now produces two genuinely separate lists — `first_basket.items is
   second_basket.items` prints `False`, the exact opposite of unit
   one's own `True`, because `default_factory` calls `list()` fresh
   for every instance instead of reusing one shared object built once.

Every one of these three facts is now provably true, by real,
executed code — not because `field(default_factory=list)` "feels
safer," but because unit one proved the trap exists, unit two proved
`@dataclass` already refuses to let a field repeat it silently, and
unit three proved the specific fix that error message pointed to
actually works.
