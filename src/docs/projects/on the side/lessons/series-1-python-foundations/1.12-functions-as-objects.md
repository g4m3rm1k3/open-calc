## Terms used in this lesson

- **first-class object** — new. A value that can be assigned to a
  variable, stored in a data structure, passed as an argument, and
  returned from a function — everything Lesson 1.1's own `Asset`
  instances could already do. Exists as a name for the specific claim
  this lesson proves: that an ordinary Python function has every one of
  those same capabilities, not just the ability to be called.
- **callback** — new. A function passed as an argument to another
  function, specifically so that receiving function can call it later,
  at a moment of its own choosing — not immediately, and not
  necessarily even once. Exists because the code deciding *when*
  something should happen (a button was clicked, an asset was retired)
  is often written long before, and by someone different than, the code
  that knows *what* should happen in response.

## Concept Unit: Functions Are First-Class Objects

### The Problem

Every function this project has ever written has been called
immediately, by name, with parentheses — `laptop.describe()`,
`find_by_serial(inventory, "SN-1")`. Is a function itself a real,
ordinary Python object — something that could be assigned to a
variable, stored in a `list` alongside other values, or handed to
another piece of code *without* being called at all — or is a function
fundamentally different from every other value this project has used?

> **Before reading on, try this:**
> - `type(some_asset)` (Lesson 1.1) returns `Asset` — the real class
>   backing that specific value. Given every value in Python has *some*
>   class, what do you predict `type(shout)` returns for an ordinary
>   function named `shout` — nothing at all, since functions aren't
>   objects, or a real, named class the same way `Asset` is one?
> - `stored = shout` — assigning a function to a variable, with no
>   parentheses after `shout` at all. Do you predict this calls `shout`
>   immediately and stores whatever it returns, or does it store the
>   function itself, uncalled, ready to be called later through `stored`
>   instead?
> - If a `list` can hold `Asset` instances (Lesson 1.6's own
>   `list[Asset]`), do you predict a `list` can hold functions
>   themselves the same way — and if so, what would calling one, read
>   out of that list, actually look like?

### Isolated Concept

```python
def shout(message):
    print(message.upper())


print(type(shout))

stored = shout
stored("hello")

actions = [shout, print]
for action in actions:
    action("dispatched")
```

Run for real (`lab1_functions_as_values.py`):

```
<class 'function'>
HELLO
DISPATCHED
dispatched
```

`type(shout)` prints `<class 'function'>` — real, confirmed proof, not
a claim: `shout` itself, the function, has a real class, exactly the
way `type(some_asset)` named `Asset` back in Lesson 1.1. `stored =
shout` — no parentheses — does not call `shout` at all; it copies the
reference to the *function itself* into `stored`, proven directly by
`stored("hello")` on the next line successfully calling it, printing
`HELLO`. The final block builds `actions = [shout, print]` — a real
`list` holding two functions, `shout` (this project's own) and `print`
(a builtin, reapplied general fluency, itself just as much a real
function as `shout` is) — and calls each one, in turn, through the loop
variable `action`. `shout("dispatched")` prints `DISPATCHED`
(uppercased, per `shout`'s own body); `print("dispatched")` prints
`dispatched` unchanged, since `print` does no such transformation.

This is called a **first-class object** — a function that can be
assigned, stored, and passed around exactly like any other value,
because in Python, it genuinely is one.

Discarded: `shout`, `stored`, and `actions` exist only to prove
functions are first-class objects. None will appear in the Asset
Manager project again.

### CS Lens

This is **first-class functions** — a language design choice where
functions are ordinary values, not a fundamentally separate kind of
thing only callable by name. This is a hard concept, worth more than
one real-world connection.

```
Also recognized in: JavaScript functions (assignable, passable, the
entire foundation of its callback-heavy style), Kotlin's and Swift's
own function types, a spreadsheet cell that can hold a formula
referencing another cell's own formula rather than just a fixed number,
languages like older Java or C that deliberately do *not* have this —
requiring a wrapper object or a raw function pointer instead
```

### SE Lens

The alternative not chosen is a language where functions can only ever
be called directly by their own fixed name, never stored, passed, or
substituted — meaning any code that wants to react differently
depending on context has to be restructured with conditionals baked in
at the point of the call, rather than handed a different function to
run. The real cost of first-class functions instead: a function passed
around loses its own name at the call site (`action("dispatched")`
gives no hint, by itself, whether `action` is `shout` or `print` this
time) — genuinely more flexible, genuinely harder to trace by reading
alone, without following where `action` actually came from.

## Concept Unit: The Callback Pattern

### The Problem

The previous unit proved a function can be handed to another piece of
code without being called immediately. What's that actually *for*? If
one function's whole job is "do a thing, then let someone else react to
it," can it accept another function as one of its own parameters,
specifically so it can call that function itself, at the exact moment
it decides the reaction should happen?

> **Before reading on, try this:**
> - `retire(asset, on_retired)` — if `on_retired` is itself a function,
>   passed in the same uncalled way `stored = shout` proved in the
>   previous unit, where inside `retire`'s own body do you predict
>   `on_retired` actually gets called — before, during, or after
>   whatever `retire` itself does first?
> - Given the previous unit proved `actions = [shout, print]` could
>   hold *any* function, do you predict `retire` could be called with
>   genuinely different functions as `on_retired` on different calls —
>   one that prints a log line, another that does something completely
>   different — with zero changes needed inside `retire` itself?
> - The blueprint's own real-world hint for this lesson is "this
>   prepares you for Qt." Given a GUI button's whole job is reacting to
>   a click at some unpredictable future moment, do you predict a
>   callback is a natural fit for connecting "a button was clicked" to
>   "run this specific code" — or does a GUI framework need something
>   fundamentally different from what `retire`/`on_retired` just proved?

### Isolated Concept

```python
class ThrowawayAsset:
    def __init__(self, name):
        self.name = name


def retire(asset, on_retired):
    print(f"retiring {asset.name}")
    on_retired(asset)


def log_retirement(asset):
    print(f"LOG: {asset.name} was retired")


laptop = ThrowawayAsset("ThinkPad X1")
retire(laptop, log_retirement)
```

Run for real (`lab2_callback_pattern.py`):

```
retiring ThinkPad X1
LOG: ThinkPad X1 was retired
```

`retire(laptop, log_retirement)` passes `log_retirement` the same
uncalled way the previous unit proved — no parentheses at the call
site. Inside `retire`'s own body, `print(f"retiring {asset.name}")`
runs first, proving `retire` does its own work *before* reacting;
`on_retired(asset)` runs second — this is the moment `log_retirement`
actually gets called, and only because `retire`'s own body chose to
call it, using the parameter name `on_retired`, with no knowledge, at
the point `retire` was *defined*, of which specific function it would
eventually be. This is called the **callback pattern** — real,
confirmed proof, not a claim: `retire` never once mentions
`log_retirement` by name anywhere in its own body; it only knows it
received *some* callable value named `on_retired`, and calls it.

Discarded: `ThrowawayAsset`, `retire`, and `log_retirement` exist only
to prove this pattern. None will appear in the Asset Manager project
again — this project's real `Asset` gains no callback mechanism from
this lesson; per this lesson's own blueprint note, that becomes real,
load-bearing code once Series 2's signals and slots arrive.

### CS Lens

This is the **Observer pattern**, specifically its callback-function
form — one piece of code performing an action, and a separate piece of
code reacting to it, connected only through a function reference passed
in ahead of time, with neither side needing to know the other's
internal details. This is a hard concept, worth more than one
real-world connection.

```
Also recognized in: a GUI button's own click handler (this lesson's own
named destination), JavaScript's addEventListener, a webhook — a URL a
service calls automatically when something happens, with no ongoing
connection to whoever registered it, a restaurant's own "buzzer"
handed to a waiting customer, called back the moment their table is
ready
```

### SE Lens

The alternative not chosen is `retire` doing the reacting itself
directly — hard-coding `print(f"LOG: {asset.name} was retired")`
straight into `retire`'s own body. The real tradeoff: hard-coding it
is simpler to read in isolation, but means every different reaction
`retire` might ever need — logging, a UI notification, an email —
requires editing `retire` itself; the callback version lets `retire`
stay completely unchanged while the caller supplies whatever reaction
actually makes sense for that specific call, at the real cost of a
reader not being able to tell, from `retire`'s own body alone, what
`on_retired` will actually do without also finding every place `retire`
is called.
