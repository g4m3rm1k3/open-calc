# Lesson 1.10: Properties

**What you will build.** `Asset` gains `display_name` — a value that
reads exactly like an attribute (`laptop.display_name`, no parentheses)
but is actually computed fresh, every single time it's accessed, from
`name` and `is_retired`, `Asset`'s own already-stored fields. Nothing
new is stored on `Asset`; `display_name` never appears as one of its
declared fields, never shows up in its generated `__repr__` or
`__eq__`, and can drift the instant `is_retired` changes, with zero
extra code to keep it in sync. The transferable problem: some values a
class exposes are genuinely stored data (`name`, `is_retired`), and some
are just *derived* from that data — and a caller reading either one
shouldn't have to know, or care, which is which from the syntax alone.

**What you need to know first.** Lesson 1.7 — Dataclasses: `Asset`'s own
five declared fields, `is_retired` specifically — this lesson computes
directly from it, never storing a duplicate. Lesson 1.1 —
`Asset.describe`, the project's original human-readable summary method,
directly contrasted below against `display_name`'s different purpose
and different calling syntax.

**Scope note.** The blueprint entry for this lesson names two example
properties: `asset.display_name` and `asset.is_retired`. `is_retired`
is not used here — `Asset` already has a real, stored field with that
exact name (a plain `bool`, since Lesson 1.7), and a class cannot have
both a stored field and a `@property` sharing one name; `mark_retired`
also directly assigns `self.is_retired = True`, which a getter-only
property (the only kind this lesson teaches) would break outright. The
blueprint's own two names are read here as illustrative examples, not a
literal pair to force onto the project — `display_name` is this
lesson's one real, landed property; `is_retired` stays exactly what
Lesson 1.7 already made it, a plain stored field.

## Terms used in this lesson

- **decorator** — reapplied in full from Lesson 1.7: syntax placing
  `@name` directly above a `class` or `def` line, meaning "call `name`
  with the thing below it, then rebind the original name to whatever
  comes back." `@property`, this lesson's own decorator, is the exact
  same mechanism, applied to a method instead of a class.
- **`bool`** — reapplied in full from Lessons 1.2/1.6/1.7: `is_retired`,
  the field `display_name` reads to decide what to return, is a `bool`.
- **`TypeError`** — reapplied in full from Lesson 1.7: a real, built-in
  exception Python raises when an operation gets a value of the wrong
  type, or the wrong number of arguments, for what it's doing. Lesson
  1.7 saw `dataclass` itself raise this for a field-ordering mistake;
  this lesson's own use is a genuinely different cause — attempting to
  *call* a plain `float` (`c.area`'s already-computed result) as if it
  were a function, which the `float` type simply doesn't support.
- **`f"..."` (f-string)** — reapplied general Python fluency, already
  used since `Asset.describe` (Lesson 1.1): a string literal with `{
  }`-enclosed expressions substituted in directly. `display_name` uses
  one to build `"{name} (Retired)"`.

## Objects and methods used

**`property`**

- *What it is:* a real, built-in class — not a function, though it's
  almost always used through the `@property` decorator syntax rather
  than called directly — that turns a method into something accessed
  like a plain attribute, with no parentheses at the call site.
- *Implementation:* `property(fget=None, fset=None, fdel=None,
  doc=None)` — its real, documented signature; `@property` above a
  method is sugar for calling `property` with that method as `fget`
  (the function to run when the attribute is *read*) and every other
  argument left at its default — this lesson never supplies `fset` or
  `fdel`, so `display_name` can be read but never assigned to directly.
- *Its use:* `@property` above `Asset.display_name` is what lets
  `laptop.display_name` work with no parentheses, running the method's
  body fresh on every access instead of returning one fixed, stored
  value.
- *Type:* a built-in class — an instance of it (built by the
  decorator, holding `display_name`'s own method as its `fget`) is what
  actually gets attached to `Asset`.
- *Responsibility:* intercept attribute access — reading
  `laptop.display_name` — and, instead of looking up a stored value the
  way `laptop.name` does, call the function it was built with and
  return whatever that call produces.
- *Depends on:* the function handed to it as `fget` — here,
  `display_name`'s own method body — being callable with just `self`.
- *Connects to:* attached to `Asset` at class-definition time, the
  moment `@property` runs; invoked automatically by Python's own
  attribute-lookup machinery every time `laptop.display_name` is read,
  never called directly by name anywhere in this project's own code.
- *Shape:* a read boundary between a caller and a class — syntactically
  identical to reading a stored field, mechanically a method call
  underneath.

**`Asset.display_name`**

- *What it is:* a brand-new calculated property on `Asset` — this
  project's first value that looks like an attribute but is never
  stored.
- *Implementation:* `@property\ndef display_name(self) -> str: if
  self.is_retired: return f"{self.name} (Retired)"; return self.name`
  — reads two of `Asset`'s own already-stored fields, `is_retired` and
  `name`, and returns one or the other string depending on
  `is_retired`'s current value; never assigns to anything, never
  changes any state.
- *Its use:* gives a caller one short, UI-friendly label for an asset
  that already reflects retirement status, without that caller needing
  to check `is_retired` itself and build the label by hand every time.
- *Type:* an instance method, wrapped by `property` via the `@property`
  decorator — accessed as `laptop.display_name`, never `laptop.
  display_name()`.
- *Responsibility:* compute one short, human-readable label from
  `Asset`'s own current state — nothing about validating, storing, or
  changing anything; a pure, read-only function of `self`.
- *Depends on:* `self.name` and `self.is_retired`'s current values, read
  fresh on every access — never cached, never stored separately.
- *Connects to:* called automatically by Python's attribute-lookup
  machinery whenever `laptop.display_name` is read; calls nothing else.
- *Shape:* a derived, read-only view over two of `Asset`'s own stored
  fields — the project's first attribute whose value is never itself
  part of `Asset`'s own generated `__repr__` or `__eq__`, since it was
  never declared as a dataclass field at all.

- *Type:* an instance method — not a property.
- *Responsibility:* unchanged — produce a longer, technical summary

  `display_name`'s own short, retirement-aware label, even though both

**`Asset.mark_retired`**

- *What it is:* reapplied from Lesson 1.2 — the guarded state-changing

- *Responsibility:* unchanged.
- *Depends on:* `self.is_retired`'s current value.
- *Connects to:* called by anything that wants to retire an asset;
  `display_name`'s own next read is the direct, visible consequence.
- *Shape:* unchanged.

  Lesson 1.9 left it.
- *Its use:* unaffected — every `Asset` it returns already has a real,

- *Type:* a free function.
- *Responsibility:* unchanged.
- *Depends on:* a `list` of already-constructed `Asset` objects.
- *Connects to:* called by anything with a collection of assets and one
  serial number to look up.
- *Shape:* unchanged.

## Concept Unit: `@property` and a Calculated `display_name`

### The Problem

`Asset.describe()` already builds a summary string — but it's called
with parentheses, like any ordinary method, and it always includes the
serial number and category, more detail than a short UI label usually
needs. If a caller just wants one short name for an asset — one that
already reflects whether it's retired, without checking `is_retired`
itself every time — is there a way to expose that as something read
like a plain attribute, `laptop.display_name`, with no parentheses,
even though it's actually computed each time rather than stored?

> **Before reading on, try this:**
> - `laptop.name` (a stored field) and `laptop.describe()` (a method)
>   are read two different ways today — one with no parentheses, one
>   with. If a class could designate *some* method to be read the first
>   way instead of the second, what do you predict the calling syntax
>   for it would actually look like — still `laptop.display_name()`,
>   or something else?
> - `is_retired` already exists as a real, stored `bool` on `Asset`.
>   Given a value that's *computed from* `is_retired` rather than
>   *stored as* a separate field never needs its own dataclass
>   declaration, do you predict `display_name` would need to be added
>   to `Asset`'s own list of annotated fields the way `name` or
>   `is_retired` were — or does it live somewhere else in the class
>   body entirely?
> - If `laptop.mark_retired()` is called after `laptop.display_name` has
>   already been read once, do you predict reading `laptop.display_name`
>   a second time shows the same value as the first read, or a
>   different one — given nothing about `display_name` is ever stored?

### Project Change

- **Reference Source:** No reference counterpart — original curriculum
  project.
- **Files affected:** `asset.py` — modified.
- **Change type:** add (one new property; no existing field or method
  changes).
- **Location:** inside `class Asset:`, directly after `__post_init__`
  and directly before `describe`.
- **Dependencies:** none — `property` is a built-in, no import needed.

### The New Code

```python
@property
def display_name(self) -> str:
    if self.is_retired:
        return f"{self.name} (Retired)"
    return self.name
```

### Isolated Concept

This is exactly what `display_name`, shown above, depends on — isolated
down to the smallest possible case:

```python
class Circle:
    def __init__(self, radius: float) -> None:
        self.radius = radius

    @property
    def area(self) -> float:
        return 3.14159 * self.radius ** 2


c = Circle(2.0)
print(c.area)
```

Run for real (`lab1_property_basics.py`):

```
12.56636
```

`c.area` — no parentheses, exactly like reading `c.radius` — prints
`12.56636`, real, confirmed proof that `@property` above `area`'s own
method definition made it accessible this way. `area`'s own body runs
every time `c.area` is read; nothing about `Circle` stores an `area`
attribute anywhere — `__init__` only ever assigns `self.radius`. This
is exactly what `display_name` does on the real `Asset`: `is_retired`
and `name` are the only things actually stored; `display_name` itself
never is.

What happens if `area` is called the way an ordinary method would be,
with parentheses?

```python
print(c.area())
```

Run for real (`break_calling_property.py`) — this run is *expected*
to fail:

```
Traceback (most recent call last):
  File "break_calling_property.py", line 11, in <module>
    print(c.area())
          ~~~~~~^^
TypeError: 'float' object is not callable
```

Real, confirmed proof, not a claim: `c.area` already *is* the computed
result — a plain `float`, `12.56636` — by the time Python evaluates it;
adding `()` after it tries to *call* that `float` as if it were a
function, and a `float` isn't callable at all. This is the exact
mechanical reason `laptop.display_name` — not `laptop.display_name()`
— is the only correct way to read it: the parentheses aren't optional
styling, they're a real, different operation that fails outright once
`@property` has already replaced a method call with a plain value.

Discarded: `Circle`/`c` exist only to prove `@property`'s own calling
syntax and what happens when it's called wrong. Neither will appear in
the Asset Manager project again.

### Mechanical Walkthrough

- **`@property`** (asset.py, new line 23) — **decorator** syntax,
  reapplied in full from Lesson 1.7: calls the built-in `property`
  class with `display_name`'s own method as its `fget` argument, then
  rebinds the name `display_name` to the resulting `property` object —
  mechanically identical to how `@dataclass` above `class Owner:`
  rebinds `Owner`, just applied to a method instead of a class.
- **`def display_name(self) -> str:`** (line 24) — an ordinary method
  signature, reapplied general syntax from every earlier lesson;
  `self`, reapplied in full from Lesson 1.1, is still the instance
  being read; `-> str`, reapplied from Lesson 1.6, documents its return
  type exactly as any other method's would.
- **`if self.is_retired:`** (line 25) — an `if` conditional, reapplied
  baseline scope since Lesson 1.2, reading `self.is_retired` — the
  real, stored `bool` field Lesson 1.7 declared — directly; a truthy
  check, reapplied from Lesson 1.9: `True` runs the next line, `False`
  falls through to line 27.
- **`return f"{self.name} (Retired)"`** (line 26) — an f-string,
  reapplied general fluency from Lesson 1.1, substituting `self.name`'s
  current value directly into the literal text `" (Retired)"`.
- **`return self.name`** (line 27) — a plain attribute read, reapplied
  from every earlier lesson, returned as-is when `is_retired` is
  `False`.

### CS Lens

This is a **computed property** — exposing a value through the same
syntax as stored data, while actually deriving it on demand from other
state. This is a hard concept, worth more than one real-world
connection.

```
Also recognized in: a spreadsheet formula cell that recalculates
automatically whenever a cell it references changes, a SQL VIEW that
computes its rows from underlying tables on every query rather than
storing a duplicate copy, C#'s and Kotlin's own native property syntax
(get/set accessors baked directly into the language), a getter method in
Java or JavaScript wrapped to look like plain field access
```

### SE Lens

The alternative not chosen is a second stored field —
`self.display_name = name`, assigned once inside `__post_init__` — kept
manually in sync by hand every time `is_retired` changes. The real,
honest cost of that alternative: `mark_retired` would need its own extra
line updating `display_name` too, and every future place that changes
`is_retired` would carry the same silent obligation, with nothing
enforcing it — exactly the kind of "two copies of one fact, drifting
apart" bug a computed property makes structurally impossible, since
`display_name` has no stored value of its own to drift. The real cost
of the property version instead: `display_name`'s own body runs fresh
on every single read, however cheap that computation is here — for a
genuinely expensive computation, a stored, manually-synced value (or a
cached one) could be the better tradeoff; nothing about `@property`
itself picks the right answer for every case.

The first line, `laptop.display_name`, read right after construction,

computed property tracks its underlying state automatically, with
nothing manually kept in sync. The third line, `laptop.describe()`,
untouched by this lesson, still returns exactly what Lesson 1.9 already
proved, unaffected by `is_retired` changing at all.
