# Lesson 1.1: Classes and Objects

**What you will build.** The very first piece of the Asset Manager: an
`Asset` class that can be built into a real, individual object — a
laptop, a monitor, any single physical thing the manager will track —
holding its own name, serial number, and category, and able to describe
itself on request. The transferable problem underneath that feature:
how do you represent one cohesive "thing," with both its own data and
its own behavior, as a single unit — instead of a scatter of loose
variables that only stay in sync by convention, with nothing enforcing
that they belong together at all?

**What you need to know first.** Nothing — this is the first lesson in
the curriculum. General fluency with core Python syntax below the level
of classes is assumed as a starting baseline: variables, calling a
function, `print`, string literals, and f-string interpolation
(`f"{x}"`). None of that baseline is re-taught here; this lesson's own
subject begins exactly at the `class` keyword.

**Baseline scope note.** Every symbol below is either genuinely new to
this curriculum, or a piece of baseline syntax that is directly
evidentiary for one of this lesson's own concepts — used as part of
*proving* what a class or an instance actually is, not just incidental
scaffolding used only to observe output. `print`, string literals, and
f-string interpolation stay in the assumed baseline and get no entry
below, per "What you need to know first," above. `pass`, `self`, `is`,
and `==` do get entries, because each one is used below as direct
evidence for a concept this lesson teaches, not merely to print a
result.

## Terms used in this lesson

- **`class`** — a blueprint that defines what data and behavior every
  object built from it will have. Exists so many objects can share one
  definition instead of each one being built by hand from scratch, with
  no guarantee any two "laptops" in the code actually share a shape.
- **instance** — one concrete object built from a class's blueprint.
  Exists as a separate concept from the class itself because a blueprint
  alone isn't a usable thing — a class describes what a `Dog` or an
  `Asset` *would* look like; an instance is an actual one, with its own
  identity, distinct from every other instance built from the same
  class.
- **`pass`** — a statement that does nothing at all. Exists because
  Python's grammar requires every block (a class body, a function body)
  to contain at least one statement; without `pass`, an intentionally
  empty body would be a syntax error, not just an empty one.
- **implicit inheritance** — the fact that a class silently inherits
  from Python's built-in `object` class even when nothing in the `class`
  statement names a parent. Exists as a term worth naming precisely
  because it explains, concretely, *why* an apparently empty class like
  `class Dog: pass` already has default behavior (a printable form,
  identity-based equality) rather than none at all.
- **`self`** — the conventional name for an instance method's first
  parameter. Exists because a method's code needs to know *which*
  instance it's running against — Python automatically passes the exact
  instance a method was called on into this parameter, which is how
  `fido.greet()` and `rex.greet()` can run the identical method body and
  still each act on their own data.
- **dunder method** — a method whose name is bracketed by double
  underscores, like `__init__`. Exists as Python's own convention for
  marking a name it will call automatically, under specific
  circumstances, rather than an ordinary name a programmer chose and
  calls directly — the naming pattern itself is the signal.
- **instance attribute** — a piece of data stored on one specific
  instance, written as `self.x = value`. Exists so each instance can
  hold its own independent state — one `Dog`'s `name` existing
  completely separately from another `Dog`'s `name`, rather than every
  instance of a class being forced to share one value.
- **method** — a function defined inside a class body whose first
  parameter is `self`. Exists so behavior that acts on an instance's own
  data can be reached *through* that instance (`instance.method()`),
  keeping the data and the code that acts on it physically next to each
  other instead of passed around as unrelated pieces.
- **`is`** — an operator that compares whether two names refer to the
  exact same object in memory, not whether their contents look alike.
  Exists because two separate objects can hold identical-looking data
  while still being genuinely different things — `is` is how code asks
  "are these literally the same one?" instead of "do these look the
  same?"
- **`==`** — Python's equality operator, asking "are these equal?"
  Exists as a separate question from `is` because *what counts as
  equal* is something a class gets to define — but on a class that
  hasn't defined its own comparison logic (as is true everywhere in
  this lesson), `==` falls back to the exact same identity check `is`
  performs. That fallback is worth knowing precisely, because it's easy
  to wrongly assume `==` always compares contents.

## Objects and methods used

**`Asset.__init__`**

- *What it is:* the constructor — a special method Python calls
  automatically, exactly once, at the moment `Asset(...)` builds a new
  instance.
- *Implementation:* `def __init__(self, name, serial_number, category):`
  — an instance method taking `self` plus three plain values; it has no
  `return` statement, so it implicitly returns `None`, and that return
  value is always discarded — `Asset(...)` itself always evaluates to
  the new instance, never to whatever `__init__` returns.
- *Its use:* this lesson's code uses it to receive an asset's
  identifying data at the moment of creation and immediately store it
  onto the new instance, so a freshly built `Asset` is never left
  half-formed.
- *Type:* an instance method — specifically a *dunder* ("double
  underscore") method, one of a small set of exact names Python
  recognizes and calls on its own, rather than a name this lesson chose
  and calls directly.
- *Responsibility:* accept whatever arguments were passed to the class
  call, and set up every instance attribute that instance needs from the
  moment it exists — the one place answerable for a new `Asset`'s
  starting state.
- *Depends on:* the bare instance Python has already allocated (bound to
  `self`) before `__init__` ever runs, and the three values
  (`name`, `serial_number`, `category`) the caller supplied to
  `Asset(...)`.
- *Connects to:* called by Python itself, invisibly, the instant
  `Asset(...)` runs — never called directly by this lesson's own code.
  It calls nothing further; everything it does is write onto `self`,
  which later methods (`describe`, below) read back.
- *Shape:* the boundary where a caller's raw values cross into an
  instance's own private, stored state — the single doorway all of an
  `Asset`'s starting data has to pass through.

**`Asset.describe`**

- *What it is:* an ordinary instance method that reads an `Asset`'s
  already-stored data and returns one human-readable summary string.
- *Implementation:* `def describe(self):` — takes only `self`, no other
  parameters; returns a `str` built from an f-string.
- *Its use:* this lesson's code uses it to prove that behavior can act
  on the same data `__init__` stored, through the object itself, without
  the caller ever needing to know how that data is laid out internally.
- *Type:* an ordinary instance method — not a dunder. Python never calls
  this on its own; it only runs when this lesson's own code calls
  `laptop.describe()` explicitly.
- *Responsibility:* format this one instance's own `name`, `category`,
  and `serial_number` into a single presentable string — nothing more.
  It doesn't change any state, validate anything, or print anything
  itself.
- *Depends on:* the instance it's called on (`self`) already having
  `name`, `category`, and `serial_number` set — which is only true
  because `__init__` already ran.
- *Connects to:* called by this lesson's own demonstration code
  (`laptop.describe()`); reads the three attributes `__init__` wrote;
  returns its result outward to whatever called it — here, `print`.
- *Shape:* a public, read-only surface on `Asset` — the first piece of
  behavior a caller can reach without touching the instance's attributes
  directly.

**Everything else in the file, not this lesson's subject but still explained**

**`object`**

- *What it is:* the built-in class every Python class implicitly
  inherits from, whether or not that's written anywhere.
- *Implementation:* `object` — a real built-in class, constructible with
  no arguments, supplying default implementations including
  identity-based `__eq__` and a default `__repr__` (the
  `<class '...'>` / `<... object at 0x...>` text seen below).
- *Its use:* this lesson's code never names `object` directly, but every
  default behavior observed in it — `Dog.__bases__` showing `(object,)`,
  `print(Dog)`'s output, `fido == rex` reading `False` with no custom
  equality written anywhere — comes from it.
- *Type:* a built-in class.
- *Responsibility:* provide the minimum working behavior every Python
  object needs before any subclass customizes it — comparability, a
  printable form, and a small, standard set of dunder methods.
- *Depends on:* nothing — it's the root of every class in this lesson;
  there's nothing above it to depend on.
- *Connects to:* every class this lesson defines (`Dog`, `Asset`)
  inherits from it automatically — shown concretely below by
  `Dog.__bases__` returning `(<class 'object'>,)`. Nothing in this
  lesson overrides any of its methods yet.
- *Shape:* the floor beneath the entire class system this lesson builds
  on — untouched directly, but load-bearing for everything shown.

**`__bases__`**

- *What it is:* a real attribute Python attaches to every class,
  holding the tuple of classes it directly inherits from.
- *Implementation:* `SomeClass.__bases__` — a plain attribute read (no
  parentheses, not a method call), returning a `tuple` of class objects.
- *Its use:* this lesson's code uses it as direct, inspectable proof of
  implicit inheritance — showing `Dog.__bases__` really does contain
  `object`, rather than just asserting that it does.
- *Type:* a class attribute — a dunder, per the term defined in Terms
  used in this lesson, above, though a data attribute rather than a
  method (no `()` follows it).
- *Responsibility:* report a class's own direct parent classes —
  nothing about grandparent classes further up, and nothing about
  instances, only the class itself.
- *Depends on:* nothing supplied by this lesson's code — Python
  populates it automatically for every class, the moment the `class`
  statement finishes.
- *Connects to:* read directly by this lesson's own verification code
  (`print(Dog.__bases__)`); its result is handed straight to `print`.
- *Shape:* an inspection tool, the same category as `type()` below —
  a way to ask a class, from the outside, what it's built from.

**`type()`**

- *What it is:* a built-in function that, called with one argument,
  returns the class that argument is an instance of.
- *Implementation:* `type(x)` — one positional argument, returns a class
  object.
- *Its use:* this lesson's code uses it to prove, concretely, that
  `fido` really is a `Dog` and `laptop` really is an `Asset`, rather
  than asserting it in prose with nothing backing it up.
- *Type:* a built-in function.
- *Responsibility:* report an object's class — nothing else; it
  creates nothing and compares nothing.
- *Depends on:* the one object passed to it.
- *Connects to:* called directly by this lesson's own verification code;
  its return value is handed straight to `print`.
- *Shape:* an inspection tool sitting outside any class this lesson
  defines — a way to ask any object, from the outside, what it is.

**`AttributeError`**

- *What it is:* the built-in exception Python raises when code tries to
  read an attribute that doesn't exist on the object being asked.
- *Implementation:* `AttributeError` — a built-in exception class (a
  subclass of `Exception`), raised automatically by attribute lookup;
  never constructed directly by this lesson's own code.
- *Its use:* this lesson's code deliberately triggers it to prove, with
  a real failure rather than a claim, that a value received by
  `__init__` is not automatically an attribute — storing it is a
  separate, necessary step.
- *Type:* a built-in exception class.
- *Responsibility:* signal, specifically, that attribute lookup
  (`obj.name`) failed to find `name` anywhere on the object or its
  class — a distinct signal from other error types that mean other
  kinds of failure.
- *Depends on:* nothing supplied by this lesson's code — Python's own
  attribute-lookup machinery constructs and raises it internally the
  moment a lookup fails.
- *Connects to:* raised by Python's attribute lookup inside `fido.name`
  / `laptop.name` below; not caught anywhere in this lesson's failure
  demonstrations, so it propagates all the way up and ends the program —
  which is exactly what proves the point being made.
- *Shape:* part of Python's own error-signaling boundary — the
  mechanism that turns "you asked for something that isn't there" into
  a stoppable, inspectable event instead of silent wrong behavior.

## Concept Unit: The `class` Keyword — A Blueprint, Not a Thing

### The Problem

The Asset Manager needs to track individual assets — a laptop, a
monitor — each with its own name, serial number, and category. Written
as loose variables, tracking one laptop looks like `laptop_name`,
`laptop_serial`, `laptop_category`. Nothing in that code says those
three variables belong to the same laptop except the shared word
"laptop" in each name — a convention a human has to maintain by hand,
that Python enforces nothing about.

> **Before reading on, try this:**
> - If you were tracking one laptop today using three separate
>   variables like that, what would you have to do, by hand, the moment
>   you also needed to track a second laptop at the same time?
> - What stops a monitor's `serial_number` from accidentally getting
>   compared against a laptop's `name`, if everything is just loose
>   variables with no shared container tying them together?
> - Python already lets you group values into a `dict`, e.g.
>   `{"name": "ThinkPad X1", "category": "Laptop"}`. Once you also want
>   *behavior* — an action the laptop's own data can perform, not just
>   storage — what do you think a plain `dict` is missing?

### Isolated Concept

Before touching the real Asset Manager project, here's the smallest
possible demonstration of what a `class` actually is, using a
throwaway example completely unrelated to assets:

```python
class Dog:
    pass

print(Dog)
print(Dog.__bases__)
```

Run for real (`lab1_class_blueprint.py`):

```
<class '__main__.Dog'>
(<class 'object'>,)
```

This proves two things at once. First, `Dog` itself — the class, not
any dog — is a real, printable object the moment Python finishes
reading the `class` statement; `<class '__main__.Dog'>` is Python's
default way of printing a class: the word `class`, followed by the
class's full name (`__main__` is the name Python gives the file being
run directly; `Dog` is the class name itself). No dog has been created
yet — `pass` means the body does nothing — but the blueprint itself
already exists as a real thing in memory. Second, `Dog.__bases__`
(itself a real, inspectable attribute Python attaches to every class)
shows `(<class 'object'>,)` — a one-item tuple containing `object`.
That's real proof, not an assertion, that `class Dog: pass`, despite
naming no parent anywhere, still silently inherits from the built-in
`object` class described in Objects and methods used, above. This
mechanism — a class silently inheriting from `object` unless told
otherwise — is called **implicit inheritance**.

This is called a **class**: a blueprint, not a thing built from it.

Discarded: this `Dog` class exists only to prove what `class` does. It
will not appear in the Asset Manager project again.

### Mechanical Walkthrough

Every distinct syntactic element in the New Code above, in order:

- **`class`** — the keyword that begins a class definition. Exactly
  what the isolated `Dog` example above demonstrated: this is the
  blueprint-declaring keyword, and per the Repetition Rule, that full

- **`Asset`** — the name being given to this new class. By convention

- **`:`** — the colon that opens the class body, exactly as it opens the

- **`pass`** — the no-op statement defined in Terms used in this lesson,

  satisfies that requirement while adding no actual behavior, leaving

  existing blueprint, with nothing describing any data or behavior yet.

### CS Lens

This is the concept of **abstraction via a type definition** —
separating "the general shape of a kind of thing" from "one particular
thing of that kind." This is a hard concept: one of the foundational
ideas object-oriented programming is built on, not routine syntax, so
it earns more than one real-world connection.

```
Also recognized in: struct definitions in C, table schemas in SQL,
message definitions in Protocol Buffers, interface definitions in
TypeScript, class definitions in every other object-oriented language
```

### SE Lens

The alternative not chosen here is staying with loose parallel
variables, or a bare `dict` like `{"name": ..., "category": ...}`,
instead of defining a class. A class buys a few concrete things a dict
doesn't: a real, named type that can be checked (`isinstance(x, Asset)`,
covered in a later lesson), a fixed place to attach behavior to (the
methods built later in this same lesson), and typo protection that a
dict's string keys don't offer — `asset["categroy"]` on a misspelled
dict key silently returns nothing useful (or raises `KeyError` far from
where the typo was made), while a misspelled attribute access is closer
to the point of the mistake once instance attributes exist. The real
cost: a class requires committing to a shape up front, by writing this
definition before any data can exist — a dict lets a shape stay loose
and change moment to moment during quick prototyping, which a class
does not offer for free.

## Concept Unit: Instantiation — Building an Actual Object

### The Problem

`class Asset: pass` now exists in `asset.py`. But a blueprint for a
house isn't a house anyone can live in — nothing that could be called
"an asset" exists yet, only the shape one *would* have. What actually
turns a blueprint into a real, individual thing?

> **Before reading on, try this:**
> - Given `class Dog: pass`, what line of code do you think would
>   create one actual dog from that blueprint? (Hint: a class's name,
>   used the same way you'd call a function.)
> - If you create two dogs from the exact same blueprint, back to back,
>   are they the same dog, or two separate dogs that just happen to look
>   identical right now?
> - You may already know Python has an `is` operator, distinct from
>   `==`. Before reading on: given its name, what do you think it
>   actually checks?

### Isolated Concept

```python
class Dog:
    pass

fido = Dog()
rex = Dog()
print(type(fido))
print(fido == rex)
print(fido is rex)
print(fido is fido)
```

Run for real (`lab2_instantiation.py`):

```
<class '__main__.Dog'>
False
False
True
```

`Dog()` — the class name, followed by parentheses, exactly like calling
a function — is what actually builds a real object from the blueprint.
Each call to `Dog()` builds a completely separate one: `fido` and `rex`
are two distinct objects, even though they came from the exact same
class with the exact same (currently empty) shape. `type(fido)` prints
`<class '__main__.Dog'>`, confirming `fido` is a real `Dog`, the same
way `print(Dog)` in the previous unit confirmed `Dog` itself was a real
class — `type()`, defined in Objects and methods used, above, is what
performed that check here. `fido == rex` reads `False`: per the `object`
entry in Objects and methods used, above, `Dog` never defined its own
equality logic, so `==` falls back to `object`'s default, which is
identity — and `fido` and `rex` are not the same object. `fido is rex`
reads `False` for the identical reason, using the `is` operator directly
instead of `==`'s fallback. `fido is fido` reads `True` — the same name,
compared against itself, is always the same object.

This is called **instantiation**: calling a class to produce one real
**instance** of it.

Discarded: this `Dog` class and its instances exist only to prove what
instantiation does. Neither will appear in the Asset Manager project
again.

## Concept Unit: `__init__` — Code That Runs Automatically at Creation

### The Problem

`Asset()` now builds a real, distinct object every time it's called —
but an empty one. Every real asset the manager tracks needs to arrive
already knowing its own name, serial number, and category, not receive
them some separate way after the fact. Is there a way to make code run
automatically, exactly once, at the exact moment an object is built?

> **Before reading on, try this:**
> - You've only called `Dog()` with empty parentheses so far. What do
>   you think happens if you try `Dog("Fido")` right now, against
>   `class Dog: pass`? Reason it through before reading on.
> - If you wanted code to run automatically, exactly once, the instant
>   an object is created — before anything else touches it — what would
>   you use that moment for?
> - If Python looked for one specific, specially-named method to call
>   automatically at creation time, what would make a good name for
>   it — something unlikely to collide with a name you'd pick for an
>   ordinary method of your own?

### Isolated Concept

```python
class Dog:
    def __init__(self, name):
        print(f"Creating a Dog named {name}...")

fido = Dog("Fido")
rex = Dog("Rex")
```

Run for real (`lab3_init_autorun.py`):

```
Creating a Dog named Fido...
Creating a Dog named Rex...
```

Neither `print` call was written anywhere near `fido = Dog("Fido")` —
they live entirely inside `__init__`'s own body. Both lines still
printed, once each, in the same order the two `Dog(...)` calls were
made, with no explicit call to `__init__` anywhere in this code. That's
real proof, not an assertion: Python recognizes this exact method name
and calls it automatically, every time a new instance is being built,
passing along whatever arguments were given to the class call
(`"Fido"`, `"Rex"`) as `__init__`'s own arguments.

This is called the **constructor**, and the mechanism itself — code
Python invokes automatically, by name, rather than code this lesson
calls directly — is why `__init__` is described as a **dunder method**:
its name is bracketed by double underscores (`__init__`, not `init`),
which is Python's own convention for marking a name as one it will call
on its own, under specific circumstances, rather than an ordinary name
a programmer chose.

### The New Code

## Concept Unit: Instance Attributes — Making Data Survive the Constructor

### The Problem

`Asset.__init__` now receives `name`, `serial_number`, and `category`
every time an `Asset` is built — but receiving a value and keeping it
are two different things. Right now, does `laptop.name` actually work
after `laptop = Asset("ThinkPad X1", "SN-48213", "Laptop")` finishes
running?

> **Before reading on, try this:**
> - Given `def __init__(self, name): pass`, reason through what happens
>   to the `name` parameter once `__init__` finishes running and
>   control returns to whoever called `Dog(...)`. Does anything about it
>   survive?
> - Ordinary function parameters normally disappear the moment the
>   function returns. What do you think has to happen, inside
>   `__init__`, for a value to survive past that point and become part
>   of the object permanently?
> - `self` refers to the specific instance being built, as the previous
>   unit established. Given that, what single statement would you write
>   inside `__init__` to make `name` stick around as part of that
>   instance, rather than vanishing when `__init__` returns?

### Isolated Concept

First, confirm the gap actually exists, rather than assuming it:

```python
class Dog:
    def __init__(self, name):
        pass

fido = Dog("Fido")
print(fido.name)
```

Run for real (`break_unstored_attribute.py`):

```
Traceback (most recent call last):
  File "break_unstored_attribute.py", line 6, in <module>
    print(fido.name)
          ^^^^^^^^^
AttributeError: 'Dog' object has no attribute 'name'
```

This is real, proven confirmation of what the Socratic questions above
asked to reason through: `Dog("Fido")` runs `__init__` successfully —
no error there — but `name` was only ever a local parameter inside
`__init__`. The moment `__init__` returns, that parameter is gone, the
same as any ordinary function's parameters would be. `fido.name` then
fails with `AttributeError`, the exception defined in Objects and
methods used, above: Python looked for an attribute called `name`
directly on the `fido` object, found nothing there and nothing on its
class either, and raised this specific error to say so.

The confirmed real project has the identical shape:
`verification/1.1/break_asset_unstored_attribute.py` builds
`laptop = Asset("ThinkPad X1", "SN-48213", "Laptop")` against exactly
the `__init__` the previous unit just added, and `laptop.name` fails
with the same error:

```
AttributeError: 'Asset' object has no attribute 'name'
```

Now, the fix:

```python
class Dog:
    def __init__(self, name):
        self.name = name

fido = Dog("Fido")
rex = Dog("Rex")
print(fido.name)
print(rex.name)
```

Run for real (`lab4_stored_attribute.py`):

```
Fido
Rex
```

`self.name = name` is the one line that changes everything: it takes
the `name` parameter — about to vanish once `__init__` returns — and
writes it onto `self`, the specific instance being built, under the
attribute name `name`. Because it's stored on the instance itself
rather than living only inside `__init__`'s local scope, `fido.name`
and `rex.name` both work afterward, and each holds its own value —
`fido.name` reads `"Fido"`, `rex.name` reads `"Rex"`, never the other's.

This is called an **instance attribute**.

instance attributes work. Neither will appear in the Asset Manager
project again.

### Mechanical Walkthrough

- **`self`** — the same parameter from the previous unit's Terms entry
  and Mechanical Walkthrough, reapplied here in full: the specific
  `Asset` instance currently being built by this exact call to
  `__init__`.
- **`.`** — attribute access, here used on the left side of an
  assignment rather than to read a value: `self.name` names a slot
  called `name` that belongs to this particular instance, distinct from
  the plain local variable `name` sitting in `__init__`'s parameter
  list.
- **`name`** (right of `=`) — the plain parameter from the previous
  unit's walkthrough, still just a local value at this point in the
  code, about to be read one final time before it would otherwise
  vanish.
- **`=`** — assignment, the same operator the second unit's
  `laptop = Asset()` used, reapplied here: it evaluates the right side
  (the parameter `name`) and binds it to the target on the left
  (`self.name`) — except this target is an attribute slot on an object,
  not a plain local variable, so what it creates outlives this single
  line and this single function call.
- **`self.serial_number = serial_number`**, **`self.category = category`**
  — the identical mechanism, repeated for the other two parameters: per
  the Repetition Rule, this is the exact same idea as `self.name = name`
  just above, not a new concept, and each one independently makes its
  own parameter permanent on this instance.

### CS Lens

This is **encapsulated per-instance state** — data that belongs to, and
lives inside, one specific object rather than floating free elsewhere.
This is a hard concept, worth more than one real-world connection.

```
Also recognized in: object fields in Java, C++, and C#, a database
row's own column values (each row = one instance's own data), a struct
instance in C, a single row of a spreadsheet
```

### SE Lens

The alternative not chosen is storing every asset's data in one shared
structure elsewhere — a global dict keyed by some ID, for instance —
instead of on the instances themselves. Instance attributes give
automatic cleanup: once nothing refers to `laptop` anymore, its data
goes with it, with no separate bookkeeping required to remove a stale
entry from some external table. They also keep data physically
colocated with the behavior that acts on it (the next unit's method
reads these same three attributes directly through `self`). The real
cost: because the data lives inside each instance rather than in one
shared place, nothing outside the instances automatically knows how
many assets exist or what they all are — collecting or searching across
many assets at once requires deliberately writing code to do that,
which a shared external structure would offer for free. This is a
concern a later lesson, once the project needs to manage more than one
asset at a time, revisits directly.

## Concept Unit: Methods — Behavior That Lives on the Object

### The Problem

`laptop = Asset("ThinkPad X1", "SN-48213", "Laptop")` now builds a fully
real object with its own stored data. But nothing on it can *do*
anything yet — every attribute is inert storage, readable but inactive.
How does behavior that acts on that stored data get attached to the
object itself, rather than living somewhere else, disconnected from it?

> **Before reading on, try this:**
> - You already know how to write an ordinary function that takes a
>   value and returns something built from it — for example, a function
>   that takes a name and returns a greeting string. Given that
>   `self.name` is already stored on every `Dog`, what do you think that
>   function would need to look like to work as part of the class,
>   instead of outside it?
> - If that function needs `self.name`, what does it need to receive as
>   a parameter to get access to `self` at all — the same way
>   `__init__` did?
> - Once a function like that is defined inside the class body, how do
>   you think you'd actually call it on one specific dog — the same dot
>   syntax already used to read `fido.name`, or something different?

### Isolated Concept

```python
class Dog:
    def __init__(self, name):
        self.name = name

    def greet(self):
        return f"Woof! My name is {self.name}."

fido = Dog("Fido")
print(fido.greet())
```

Run for real (`lab5_methods.py`):

```
Woof! My name is Fido.
```

`greet` is defined inside the class body with `def`, exactly like
`__init__` was — the only structural difference is the name itself:
Python doesn't call `greet` automatically the way it calls `__init__`;
it only runs when this lesson's own code calls it directly, as
`fido.greet()` does below. Its first parameter is `self`, for the exact
same reason `__init__`'s first parameter was: without it, `greet` would
have no way to know *which* dog's `name` to read. Calling it is
`fido.greet()` — the same dot syntax already used to read `fido.name`,
except here it's followed by `()`, calling the method rather than
reading a stored value. Inside `greet`, `self.name` reads back exactly
what `__init__` stored on this specific instance — `"Fido"` — and the
f-string builds the full greeting around it.

This is called a **method**.

### Mechanical Walkthrough

- **`def`** — the same keyword from the third unit's walkthrough,
  reapplied: this begins a new method definition, `describe`, inside
  `Asset`'s body.
- **`describe`** — the name chosen for this method — an ordinary name,
  not a dunder, so (per the isolated `greet` example, above) Python will
  never call it automatically; it only runs when called explicitly.
- **`self`** — the same parameter explained in full in the third and
  fourth units, reapplied here for the third time: without it,
  `describe` would have no way to know which `Asset`'s data to read.
- **`return`** — a keyword that ends the method immediately and sends a
  value back to whatever called it — here, the finished string, handed
  back to `print(laptop.describe())` below.
- **`f"{self.name} — {self.category} (S/N {self.serial_number})"`** — an
  f-string (assumed baseline per the scope note, above) whose
  interpolated parts are not ordinary variables but attribute
  reads — `self.name`, `self.category`, `self.serial_number` — each one
  the exact same dot-access mechanism the fourth unit's walkthrough
  already explained in full, reapplied here three times over to read
  back what `__init__` stored, rather than to store anything new.

### CS Lens

This is **behavior colocated with the data it acts on** — one of
object-oriented programming's central ideas, sometimes phrased as "tell,
don't ask." This is a hard concept, worth more than one real-world
connection.

```
Also recognized in: methods on a class in any object-oriented language,
a stored procedure defined alongside the database table it operates on,

```

### SE Lens

The alternative not chosen is a free function taking the three raw
values separately — `describe(name, category, serial_number)` — instead
of a method on `Asset`. A method guarantees it can only ever be called
against a real, fully constructed `Asset`, so `self.name`,
`self.category`, and `self.serial_number` are always genuinely
available and were always set together, by the same `__init__`. A free
function offers no such guarantee: it could be called with three
completely mismatched values that were never validated as belonging to
the same asset at all. The real cost is coupling — this method is
permanently tied to `Asset`; it can't be reused for some other kind of
data the way a free function taking three plain strings could be reused
anywhere.
