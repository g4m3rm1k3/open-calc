# Lesson 1.9: Dataclass Validation

**What you will build.** `Asset` gains real constructor-time validation
for the first time in this project's history: an empty, or
whitespace-only, `name`, `serial_number`, or `category` is now rejected
with a real `ValueError`, the instant a bad `Asset` is constructed —
raised from a new method, `__post_init__`, that `dataclass` calls
automatically as the literal last line of its own generated `__init__`.
`Owner` gets no such change this lesson — a deliberate scope boundary,
not an oversight, explained directly below. The transferable problem:
Lesson 1.7's own SE Lens already named the real cost of a generated
`__init__` — "the *option* to add validation directly inside
`__init__`'s own body is gone the moment `@dataclass` takes over."
`__post_init__` is `dataclass`'s own deliberate answer to exactly that
gap: one guaranteed hook, called automatically after every field is
already set, letting a class stay fully declarative for its *data*
while still getting one real place to run logic once construction's
automatic part finishes.

**What you need to know first.** Lesson 1.7 — Dataclasses: `@dataclass`,
generated `__init__`, and that lesson's own SE Lens, naming the exact
gap this lesson closes. Lesson 1.8 — Dataclass Defaults: `ValueError`,
already fully introduced there as the exception `dataclass` itself
raises for a mutable field default — reused here, for the first time,
as an exception *this project's own code* raises deliberately, not one
raised internally by `dataclass`.

**Scope note.** The blueprint entry for this lesson names three fields
specifically — `name`, `serial_number`, `category` — all on `Asset`.
`Owner`'s own `name`/`email` get no validation this lesson; that's a
deliberate scope boundary matching the blueprint's own stated target,
not a claim that `Owner` doesn't need it or is somehow harder to
validate. `Asset.owner` and `Asset.is_retired` are also left
unvalidated: `owner` because "a valid `Owner`" is a question about a
*different* class, out of this lesson's own scope, and `is_retired`
because `bool` has no invalid *value* to reject beyond the type
non-enforcement Lesson 1.6 already covered in full.

## Terms used in this lesson

- **`raise`** — new. The statement that immediately stops normal
  execution and hands control to the nearest matching `except` block, or,
  if none exists, terminates the program with a traceback — the exact
  mechanism behind every exception this project has seen so far
  (Lesson 1.6's `NameError`, Lesson 1.7's `TypeError`, Lesson 1.8's
  `ValueError`), but always raised internally, by Python or by
  `dataclass`'s own code, never once by this project's *own* code
  before this lesson. `raise ValueError("...")` builds a new
  `ValueError` instance, exactly like calling any other class, and
  immediately raises it.
- **truthy/falsy, and the `not` operator** — new, added to this
  project's assumed baseline scope from this lesson forward (the same
  category as `if`, Lesson 1.2; `for`/`import`, Lesson 1.6). Every
  Python value has a real, defined boolean meaning even when it isn't
  literally `True` or `False` — an empty string (`""`) is **falsy**
  (behaves as `False` inside an `if`), and any non-empty string is
  **truthy** (behaves as `True`). `not value` produces the opposite:
  `True` when `value` is falsy, `False` when it's truthy. This lesson's
  entire validation depends on this fact specifically: `not
  self.name.strip()` is `True` exactly when `self.name.strip()` is
  empty.
- **`ValueError`** — reapplied in full from Lesson 1.8: a real, built-in
  exception raised when an operation gets a value of the right *type*
  but a wrong or unacceptable *value*. Lesson 1.8 saw `dataclass` itself
  raise this internally, for a mutable field default; this lesson's own
  project code raises it directly, for the first time, for a
  business-meaningless value — an empty string — that is nonetheless a
  perfectly well-typed `str`.

## Objects and methods used

**`Asset.__post_init__`**

- *What it is:* a brand-new method on `Asset` — the specific hook
  `dataclass` looks for, by this exact name, and calls automatically
  once every field has already been assigned.
- *Implementation:* `def __post_init__(self) -> None: if not
  self.name.strip(): raise ValueError("Asset name must not be empty");
  if not self.serial_number.strip(): raise ValueError("Asset serial
  number must not be empty"); if not self.category.strip(): raise
  ValueError("Asset category must not be empty")` — three independent
  guard clauses, one per validated field, each checked in field-
  declaration order, each raising immediately on the first failure it
  finds rather than collecting every problem at once.
- *Its use:* the entire reason a bad `Asset` — one with a blank
  `name`, `serial_number`, or `category` — can no longer be
  constructed at all, silently or otherwise.
- *Type:* an instance method — not a dunder method (its name has
  leading and trailing double underscores, but, unlike `__init__` or
  `__repr__`, Python's own language machinery never calls it directly
  for any built-in operation; only `dataclass`'s own generated code
  calls it, and only because it happens to look for this exact name).
- *Responsibility:* reject construction of any `Asset` whose `name`,
  `serial_number`, or `category` is empty or contains only
  whitespace — nothing about `owner` or `is_retired`, and nothing about
  *changing* any value, only refusing bad ones.
- *Depends on:* `self.name`, `self.serial_number`, `self.category`
  already being set — guaranteed, because of exactly where `dataclass`
  places its call, covered in full in this lesson's first unit.
- *Connects to:* called automatically, exactly once per construction,
  by the generated `Asset.__init__`, as its own literal last line;
  calls nothing but `str.strip()` and the built-in `ValueError`.
- *Shape:* a construction-time validation boundary — this project's
  first, closing the exact gap Lesson 1.7's own SE Lens named.

**`str.strip`**

- *What it is:* a real, built-in method every `str` instance has —
  returns a new string with leading and trailing whitespace removed.
- *Implementation:* `str.strip(self, chars=None) -> str` — with no
  argument (this lesson's only use), removes any combination of
  spaces, tabs, and newlines from both ends; the original string is
  never modified (`str` is immutable, reapplied from Lesson 1.3),
  `strip()` always returns a new one.
- *Its use:* `self.name.strip()` turns a whitespace-only string like
  `"   "` into `""`, an empty string — the exact form the truthy/falsy
  check above needs to correctly treat "all spaces" the same as
  "genuinely nothing typed at all."
- *Type:* an instance method on `str`.
- *Responsibility:* strip leading/trailing whitespace from one string
  and hand back the result — nothing about the original string, and
  nothing about whitespace *inside* the string (`"a b"` strips to `"a
  b"`, unchanged).
- *Depends on:* the string it's called on; takes no required arguments.
- *Connects to:* called three times inside `Asset.__post_init__`, once
  per validated field; its own return value is never stored back onto
  `self` — only checked, then discarded.
- *Shape:* a small, pure, read-only string transformation — no state
  anywhere is changed by calling it.

**`dataclass`**

- *What it is:* reapplied from Lesson 1.7 — the decorator function
  generating `__init__`, `__repr__`, and `__eq__` from a class's own
  field declarations.
- *Implementation:* unchanged from Lesson 1.7, with one more real fact
  this lesson exercises, confirmed this session directly from CPython's
  own `dataclasses.py`: `dataclass` checks whether the class already
  defines a method literally named `__post_init__`; if so, the
  generated `__init__`'s own source ends with one extra line calling
  it — `self.__post_init__()` — appended *after* every field-assignment
  line, never before.
- *Its use:* this lesson's entire mechanism depends on `dataclass`
  finding `Asset.__post_init__` by exactly that name and wiring the
  call in automatically — nothing in `Asset`'s own field declarations
  asks for this separately.
- *Type:* a free function — a decorator.
- *Responsibility:* unchanged from Lesson 1.7, plus this lesson's own
  addition: detect and wire in a `__post_init__` call, if one exists,
  as the true final step of the generated `__init__`.
- *Depends on:* unchanged from Lesson 1.7, plus, for this specific
  behavior, the class already having a method named `__post_init__`
  defined in its own body at the moment `@dataclass` runs.
- *Connects to:* unchanged from Lesson 1.7; now also calls `Asset.
  __post_init__` indirectly, from inside the `__init__` it generates.
- *Shape:* unchanged from Lesson 1.7.

**`Asset.__init__`**

- *What it is:* reapplied from Lessons 1.1, 1.4, and 1.7 — `Asset`'s
  generated constructor.
- *Implementation:* equivalent to `def __init__(self, name: str,

- *Type:* an instance method — a dunder method — generated.

- *Depends on:* unchanged from Lesson 1.7.

  call, to `Asset.__post_init__`, as its own final line.
- *Shape:* the same boundary as Lesson 1.7 left it, now with a real
  validation gate at its exit rather than none at all.

## Concept Unit: The `__post_init__` Hook

### The Problem

Lesson 1.7's own SE Lens named a real, honest cost of a generated
`__init__`: no room left for custom logic, since the whole body is
built automatically from field declarations. Is there any hook at all —
some specific thing `dataclass` looks for and calls automatically — or
is a generated `__init__` genuinely a dead end for ever running code of
your own during construction?

> **Before reading on, try this:**
> - Lesson 1.7 proved the generated `__init__` ends with one assignment
>   line per field, in declaration order, and nothing else. If
>   `dataclass` were willing to call one more method automatically,
>   after every field is already set, where in that generated body do
>   you predict the call would have to go — before the field
>   assignments, or after all of them?
> - Python already has a real convention for "special methods Python or
>   a library calls automatically, by name, without you calling them
>   directly" — every dunder method this project has seen counts.
>   Given that pattern, what do you predict the *name* of a hook meant
>   specifically for "run this right after construction" might look
>   like?
> - If a class defines a method with that exact predicted name, but
>   never calls it anywhere in its own code, do you think `dataclass`
>   would need to be told to call it — some extra decorator argument,
>   the way `repr=True` exists — or could it simply check whether a
>   method by that name already exists on the class, the moment it
>   processes it?

### Project Change

- **Reference Source:** No reference counterpart — original curriculum

- **Files affected:** none yet — this unit isolates the hook's own
  timing before the next unit lands real validation in `asset.py`.
- **Change type:** N/A.

### Isolated Concept

```python
from dataclasses import dataclass


@dataclass
class Loud:
    value: int

    def __post_init__(self):
        print(f"post_init running, self.value is already {self.value}")


print("before construction")
loud = Loud(42)
print("after construction")
```

Run for real (`lab1_post_init_timing.py`):

```
before construction
post_init running, self.value is already 42
after construction
```

This is a timing question, not a changing-value one — the real proof is
*when* each line runs relative to the others, not any computed result:

1. `print("before construction")` — runs first, proving nothing about
   `Loud` has happened yet; no instance exists.
2. `loud = Loud(42)` — calls the generated `__init__`, which, per real
   source confirmed this session directly from `dataclasses.py`,
   assigns `self.value = 42` first, then calls `self.__post_init__()`
   as its own literal last line — never before any field assignment,
   because `dataclass` builds that call as one more line appended after
   every other line in the generated body, not inserted first.
3. The `print` inside `__post_init__` fires *during* that same call to
   `Loud(42)`, before `loud = Loud(42)` has even finished — which is
   exactly why `self.value` already reads `42` inside it: the field
   assignment genuinely happened first, a fact this print proves rather
   than assumes.
4. `print("after construction")` — runs last, once `Loud(42)` has fully
   returned, `__post_init__` included.

This is called the **`__post_init__` hook** — a method name `dataclass`
looks for automatically, with no separate decorator argument needed to
turn it on, wiring in exactly one call to it, always as the true final
step of the generated `__init__`, if a class happens to define one.

Discarded: `Loud` exists only to prove this hook's own timing, with no
validation logic at all — pure proof of *when*, not *what*. It will not
appear in the Asset Manager project again. The next unit gives `Asset`
a real `__post_init__` that actually validates something.

- **`@dataclass`** — reapplied in full from Lesson 1.7: the same
  decorator, now exercising a behavior this lesson makes visible for
  the first time — detecting `__post_init__` and wiring in a call to it.
- **`class Loud:`**, **`value: int`** — reapplied field-declaration

  about the declaration itself.
- **`def __post_init__(self):`** — new: an ordinary method definition,
  syntactically no different from any other method this project has
  ever written — its special behavior comes entirely from `dataclass`
  recognizing its exact name, not from any special syntax marking it.
- **`print(f"post_init running, self.value is already {self.value}")`**
  — an f-string, reapplied general Python fluency (already used in
  `Asset.describe` since Lesson 1.1), reading `self.value` — proving,
  by printing its real value, that the field assignment already
  happened by the time this line runs.
- **`loud = Loud(42)`** — an ordinary call to the generated `__init__`,
  reapplied from every earlier lesson; the only new fact is *what else*
  happens inside that one call, proven by the trace above.

### CS Lens

This is a **lifecycle hook** — a named extension point a framework or
generated system calls automatically at one specific, guaranteed moment
in an object's life, without the class needing to participate in
however that moment is actually triggered. This is a hard concept,
worth more than one real-world connection.

```
Also recognized in: Android's Activity.onCreate(), called automatically
by the OS at one guaranteed point in an activity's life, Django model's
save() hook and signals, a web framework's componentDidMount()/useEffect
firing after a UI component first renders, a database trigger firing
automatically after a row insert completes
```

### SE Lens

The alternative not chosen is giving up on generated `__init__`
entirely and going back to a fully hand-written constructor the moment
any custom logic is needed — exactly what Lesson 1.7's own SE Lens
worried might be the only option. `__post_init__` is the real
middle ground: every field still gets declared once, plainly, and
`dataclass` still writes the repetitive assignment code, while the
class keeps exactly one guaranteed place for anything that assignment
alone can't do. The real, honest limit: `__post_init__` runs *after*
every field is already set, never before or during — it can validate
or adjust what's already there, but it can't intercept or transform a
value before its first assignment the way a fully hand-written
`__init__` could.

## Concept Unit: Validating `name`, `serial_number`, and `category`

### The Problem

Every `Asset` this project has ever constructed has accepted any string
at all for `name`, `serial_number`, and `category` — including an empty
one, or one that's nothing but spaces. Nothing about `Asset`'s own type
annotations (`str`, reapplied from Lesson 1.6) rejects this; Lesson
1.6's own isolated proof already showed annotations are never checked
by Python itself. Now that `__post_init__` is proven to run reliably
after every field is set, can it actually reject a blank value for
real, and stop a bad `Asset` from finishing construction at all?

> **Before reading on, try this:**

### CS Lens

A direct application of the previous unit's own lifecycle-hook idea,
now enforcing a real **invariant** (reapplied in full from Lesson
1.2: a condition that must always hold true for an object to be in a
valid state) at the earliest possible moment — construction itself —
rather than checking it later, possibly after invalid data has already
spread through other parts of a program. No separate CS Lens beyond
what the previous unit and Lesson 1.2 already gave in full.

### SE Lens

The alternative not chosen is validating later — leaving `Asset`
constructible with blank fields, and instead checking validity right
before something important happens (saving to a database, displaying
it in a UI). The real tradeoff: validating at construction means a
blank-fielded `Asset` can never exist anywhere in this program at all,
not even briefly — the strongest possible guarantee, at the cost of
raising an exception at the exact moment of `Asset(...)`, which every
single call site now has to be prepared to handle failing, not just
ones that happen to touch a database or a UI later. This project has
