## Terms used in this lesson

- **`with`** — new. A statement that wraps a block of code around a
  **context manager**, guaranteeing one specific piece of cleanup code
  runs the instant that block ends — whether it finished normally or
  exited early because of an exception. `with open(path, mode) as f:`
  is this lesson's own example: `f` is bound for the duration of the
  indented block below it, and is guaranteed closed the moment that
  block ends, by any means.
- **context manager** — new. Any object that defines the specific pair
  of methods (`__enter__` and `__exit__`, both dunder methods,
  reapplied in full from Lesson 1.1) a `with` statement calls
  automatically — `__enter__` when the block begins, `__exit__`
  unconditionally when it ends. A file object returned by `open()` is
  one; this lesson never writes a context manager of its own, only uses
  one already provided by Python's own standard library.
- **file handle** — new. The real, open connection between a running
  program and a file on disk that `open()` returns — not the file's
  *contents*, a live, stateful resource that stays connected to the
  operating system until explicitly closed, at real, ongoing cost
  (an operating system only allows a limited number of files open at
  once per program) until that happens.

## Objects and methods used

**`open`**

- *What it is:* a real Python built-in function that opens a file and
  returns a file handle object.
- *Implementation:* `open(file, mode='r', ...) -> file object` — its
  real, documented signature; `mode="w"`, this lesson's own use, opens
  the file for writing, creating it if it doesn't already exist and
  erasing any existing content if it does.
- *Its use:* `open("throwaway.txt", "w")` both directly, and inside a
  `with` statement, is this lesson's own concrete resource being
  acquired and, eventually, released.
- *Type:* a built-in free function.
- *Responsibility:* ask the operating system for a real, open
  connection to a specific file, in a specific mode, and hand back an
  object representing that connection.
- *Depends on:* a real path on disk, and a mode string describing what
  the caller intends to do with it.
- *Connects to:* called directly by this lesson's own throwaway code;
  the object it returns is itself the context manager `with` uses.
- *Shape:* a resource-acquisition boundary — the exact moment a limited,
  real operating-system resource becomes this program's responsibility
  to eventually release.

**`file.close`**

- *What it is:* a real method every file handle object has, releasing
  its underlying operating-system resource.
- *Implementation:* `file.close() -> None` — flushes any unwritten data
  and releases the connection; after this call, the file handle is
  marked closed and can no longer be read from or written to.
- *Its use:* called automatically, exactly once, by a file's own
  `__exit__` when a `with` block ends — never written explicitly
  anywhere in this lesson's own `with`-based code, only inside the
  manual comparison this lesson's second unit proves is unsafe.
- *Type:* an instance method on a file object.
- *Responsibility:* release the real, limited resource `open()`
  acquired — nothing about the file's own content, only the connection
  itself.
- *Depends on:* the file handle already being open.
- *Connects to:* called by this lesson's own manual example directly;
  called automatically, by `with`, via the file object's own
  `__exit__`, in every other example this lesson shows.
- *Shape:* a resource-release boundary — the counterpart to `open`'s
  own acquisition.

**`file.closed`**

- *What it is:* a real, read-only attribute every file handle carries,
  reporting whether it's currently closed.
- *Implementation:* `file.closed -> bool` — `False` immediately after
  `open()` succeeds, `True` after `close()` has run, by any means.
- *Its use:* this lesson's own proof mechanism throughout — every claim
  about whether a file is actually closed is checked directly against
  this attribute, real output, not assumed.
- *Type:* an instance attribute (a real `bool`, not a method — read
  with no parentheses).
- *Responsibility:* report one fact truthfully, at the moment it's
  read.
- *Depends on:* the file object it belongs to.
- *Connects to:* read directly by this lesson's own code, immediately
  after every operation whose effect on this specific fact is being
  proven.
- *Shape:* a small, read-only inspection point — this lesson's entire
  evidence mechanism.

## Concept Unit: `with` Guarantees Cleanup

### The Problem

`open(path, "w")` returns a real file handle — a live connection to the
operating system that stays open, at real cost, until something closes
it. Every file this project has never yet opened would, eventually,
need exactly that: guaranteed to be closed, without a programmer having
to remember to write `f.close()` at the correct point, every single
time, in every possible path a function's code might take through it.

> **Before reading on, try this:**
> - `f = open(path, "w"); f.write("hello"); f.close()` is the direct,
>   manual way to do this — three separate statements. If Python
>   offered a single statement that opened a file, ran a block of code
>   using it, and closed it automatically once that block ended, what
>   shape do you predict that statement might take, given `with` is
>   this lesson's own name?
> - `f.closed`, read immediately after `open()` succeeds, is `False`.
>   If a `with` statement really does guarantee closing at the end of
>   its own block, do you predict `f.closed`, read again right after
>   that block ends, reports `True` — even though no explicit
>   `f.close()` was ever written anywhere in the code?
> - If `f.closed` were checked *inside* the `with` block, before it
>   ends, do you predict it would already read `True`, or does the
>   guarantee only take effect once the block is fully finished?

### Isolated Concept

```python
with open("throwaway.txt", "w") as f:
    f.write("hello")
    print(f.closed)

print(f.closed)
```

Run for real (`lab1_with_basics.py`):

```

```

`with open("throwaway.txt", "w") as f:` opens the file and binds it to
`f`, exactly like a plain `f = open(...)` would — the difference is
everything the `with` statement itself now guarantees about what
happens once its own indented block ends. Inside that block, `f.write
("hello")` runs, then `print(f.closed)` reads `False` — real, confirmed
proof that the file is still genuinely open while its own block is
still running. The final `print(f.closed)`, sitting *outside* the
`with` block's own indentation, reads `True` — real, confirmed proof
that the file was actually closed, automatically, the instant the
block ended, with no `f.close()` ever written anywhere in this code.

This is called a **`with` statement**, wrapped around a **context
manager** — here, the file object `open()` returns. Mechanically,
`with open(...) as f:` calls the returned object's own `__enter__`
method (which, for a file, simply returns the file object itself,
becoming `f`) when the block begins, and its `__exit__` method,
unconditionally, the moment the block ends — `__exit__`, for a file, is
what actually calls `close()` internally.

### CS Lens

This is the **RAII pattern** (Resource Acquisition Is Initialization) —
tying a resource's release directly to the lifetime of a block of code,
so acquiring it and guaranteeing its release are inseparable, rather
than two manually-paired steps a programmer has to remember to keep in
sync. This is a hard concept, worth more than one real-world
connection.

```
Also recognized in: C++'s own RAII, the pattern's original name and
home, Java's and C#'s try-with-resources/using statements, a rental car
agreement that automatically ends and returns the deposit the moment
the car is brought back, regardless of what happened during the rental,
a hotel key card that stops working automatically at checkout time with
no separate action required
```

### SE Lens

The alternative not chosen is the plain `f = open(...)` /
`f.close()` pair, written by hand, every time. The real tradeoff:
`with` costs nothing extra to write — genuinely no more characters than
opening a variable-worthy statement already would — while removing an
entire category of bug: a forgotten `close()` call, or one skipped
because of an early `return` or an exception, covered directly in this
lesson's next unit. The manual version's own real appeal is only that
it looks simpler in isolation, for the one case where nothing ever goes
wrong between opening and closing.

## Concept Unit: Exception Safety

### The Problem

Lesson 1.11 already proved `finally` runs even when an exception is
raised and caught partway through a `try` block. Does `with`'s own
guarantee behave the same way — closing a file even when something
inside its block raises — or does an exception skip cleanup the same
way it would skip any other code positioned after the line that failed?

> **Before reading on, try this:**
> - A plain `f = open(path, "w"); f.write(...); f.close()`, written
>   as three separate statements, has `f.close()` as its own, final
>   line. If an exception is raised by the `f.write(...)` line, do you
>   predict `f.close()` still runs afterward, or does control jump
>   straight past it, the same way any other code after a raise would
>   be skipped?
> - Given `with`'s own cleanup is mechanically similar to `finally`'s
>   guarantee (Lesson 1.11), do you predict a `with` block behaves the
>   same way a manual `f.close()` would when an exception is raised
>   inside it — silently skipped — or does it behave more like
>   `finally`, running regardless?
> - If both a manual close and a `with`-based close are tested the
>   exact same way — writing to the file, then deliberately raising an
>   exception before either version's own cleanup would normally run —
>   do you predict both file handles end up closed, or only one of
>   them?

### Isolated Concept

```python
f = open("throwaway.txt", "w")
try:
    f.write("hello")
    raise ValueError("something went wrong")
except ValueError:
    pass
print(f"manual open/close, still closed? {f.closed}")


try:
    with open("throwaway.txt", "w") as g:
        g.write("hello")
        raise ValueError("something went wrong")
except ValueError:
    pass
print(f"with statement, still closed? {g.closed}")
```

Run for real (`lab2_exception_safety.py`):

```
manual open/close, still closed? False
with statement, still closed? True
```

Both blocks do the identical thing: open a file, write to it, then
deliberately raise a `ValueError` before any explicit `close()` call
would normally be reached — `f.close()` is never even written in the
first block, exactly matching what would happen if it were written as
the very next line and the exception above it prevented that line from
ever running. Both `ValueError`s are caught by their own surrounding
`except`, so neither script crashes.

Real, confirmed proof, not a claim: `f.closed` — the plain, manual file
— reads `False`. The exception genuinely skipped past where a
`f.close()` line would have been, exactly the way any code after a
`raise` is skipped, leaving the real, limited operating-system resource
still open, leaked, with no code left anywhere in this script that will
ever close it now. `g.closed` — the `with`-managed file — reads `True`.
The exact same exception, raised inside the `with` block, did *not*
prevent the file from closing, because `with`'s own cleanup is wired
into the block's *exit*, not its normal completion — the identical
guarantee Lesson 1.11's own `finally` already proved for a `return`
statement mid-`except`, now proven again for a `with` block's own
`__exit__`.
