# Lesson 01: The Shape of a Kotlin Program

**What you will build:** Nothing app-related yet — the smallest possible
Kotlin program, compiled and run by hand, contrasted directly against
Java's own required shape. The transferable problem: Java forced every
line of code to live inside a class, with one exact required
entry-point method signature. Kotlin, running on the exact same JVM,
drops that requirement entirely — and understanding *what* actually
happens to a top-level Kotlin function when it's compiled is what turns
"Kotlin is more concise" from a vague impression into a concrete,
verified fact.

**What you need to know first:** A working knowledge of Java and
Android — classes, objects, `extends`/`@Override`, Activities, the
Manifest, `RecyclerView`, and the runtime permission flow. This series
does not re-teach any of that; it teaches what's different, and new, in
Kotlin specifically.

**Terms introduced in this lesson:**
- **Top-level function** — a function declared directly in a `.kt` file,
  with no enclosing class required at all.
- **`val` / `var`** — Kotlin's two variable declaration keywords; `val`
  creates a reference that can never be reassigned after initialization,
  `var` can be reassigned.
- **String template** — `"$name"` or `"${expression}"` syntax embedding a
  variable or expression's value directly inside a string literal.

## Concept Unit: No Wrapping Class Required

### The Problem

Java's entry point required an exact, ceremonial shape:
`public class X { public static void main(String[] args) { ... } }` —
a whole class, just to hold one method, just to satisfy the JVM's
lookup rule. Kotlin runs on the identical JVM, with the identical
lookup rule underneath — so how does Kotlin avoid the ceremony?

### Introduce the Concept in Isolation

```kotlin
fun main() {
    val greeting = "Hello, Kotlin"
    println(greeting)
}
```

Save this as `Hello.kt`. Compile and run:

```
kotlinc Hello.kt -include-runtime -d Hello.jar
java -jar Hello.jar
```

Real output:

```
Hello, Kotlin
```

`fun main()` is a **top-level function** — declared directly in the
file, no enclosing class written anywhere. This is not Kotlin skipping
the JVM's entry-point rule; it's Kotlin's compiler generating the
wrapping class *for you*, automatically, behind the scenes. Prove this
directly rather than taking it on faith:

```
javap -p HelloKt.class
```

Real output:

```
public final class HelloKt {
  public static final void main();
}
```

`javac`/`java` never entered this picture — `kotlinc` compiled
`Hello.kt` into real `.class` files, and one of them,
`HelloKt.class`, is a synthetic class the compiler generated by taking
the filename (`Hello.kt`), appending `Kt`, and placing every top-level
function inside it as a `static` method — exactly matching what Java's
own `HelloWorld` class had to be written by hand. Kotlin's "no class
needed" is real from the source you type, and equally real that the
JVM's actual requirement — some class, some `main` method — was never
actually removed, only generated for you.

### Discard the Throwaway Example

`Hello.kt` and its compiled output are deleted now — the mechanism
they proved (Kotlin generates the class Java requires you to write by
hand) carries forward into every `.kt` file this series creates.

### CS Lens

This is **syntactic sugar with a verifiable, mechanical translation** —
not magic, a compiler performing a specific, inspectable transformation
(top-level function → static method on a generated class) on your
behalf. The `javap` output above is the same kind of proof this series
already trusted for Java's own compiler-generated behavior: never assert
what a compiler "does automatically" without a way to show it.

### SE Lens

**Why does Kotlin bother hiding a mechanism that's still, underneath,
identical to Java's?** Requiring a class for a five-line script is pure
ceremony with no benefit for small programs and scripts — Java's own
design reasoning for requiring it (large, multi-file programs need one
unambiguous entry point) doesn't disappear,
Kotlin just stops making *every* file pay that ceremony cost for the
common case of a straightforward program, generating the required
structure automatically instead of demanding it be typed by hand.

## Concept Unit: `val` and `var`

### The Problem

Java required a full type name on every declaration
(`String message = "hi";`) with no built-in concept of "this reference
can never be reassigned" beyond the separate `final` keyword, rarely
used by habit. Kotlin makes immutability the *default* question asked
at every single declaration.

### Introduce the Concept in Isolation

```kotlin
fun main() {
    val name = "Alex"
    var score = 0

    score = 10
    println("$name has $score points")

    name = "Sam"
}
```

Attempt to compile this exactly as written. Real error:

```
error: val cannot be reassigned
    name = "Sam"
    ^
```

`val` (short for "value") declares a reference that can be assigned
**once**, at initialization, and never again — attempting to reassign it
is a compile error, not a runtime one. `var` (short for "variable")
behaves like Java's ordinary declarations: reassignable freely. Neither
line declares an explicit type (`String`, `Int`) — Kotlin's compiler
**infers** the type from the initializer's own value, and still enforces
it exactly as strictly as if it had been written out; assigning
`score = "wrong type"` later would still be rejected, this time for a
type mismatch rather than reassignment.

Remove the last line (`name = "Sam"`) and rerun. Real output:

```
Alex has 10 points
```

`"$name has $score points"` is a **string template**: `$name` and
`$score` are replaced directly with each variable's current value,
without the explicit string concatenation (`"..." + name + "..."`) Java
required at every step.

### Discard the Throwaway Example

Deleted now. `val`/`var` and string templates carry forward into every
line of Kotlin code this project writes from here on.

### CS Lens

Making immutability the *default* choice, with mutability requiring an
explicit, different keyword, is a deliberate inversion of Java's own
default (every variable mutable unless explicitly marked `final`).
This connects to a real, broader software engineering idea: a value that
provably never changes after creation is easier to reason about
correctly, especially once code involves more than one thread or more
than one place holding a reference to it — a `val` reference can never
be the reason a bug involves the wrong value being read after
unexpected reassignment, because reassignment is a compile error.

### SE Lens

**Why invert Java's default instead of keeping mutable-by-default and
just adding a `val` keyword as an option, the same shape as Java's
`final`?** A default that requires *effort* to opt out of (typing `var`
instead of `val`) produces, in practice, far more immutable code across
a real codebase than a default that requires effort to opt *into*
(remembering to type `final` on every variable that should never
change) — Java's own `final` exists but is inconsistently used across
real-world code specifically because it's the non-default, easy-to-skip
choice. Kotlin's inversion is a language design decision made
specifically to correct for that observed real-world pattern.

## Connect the Pieces

One trace: `kotlinc` compiled `Hello.kt` into a real `HelloKt.class`,
confirmed directly with `javap` to contain the exact
`public static void main()` shape the JVM has always required — the
same requirement, generated rather than hand-written. `val name` and
`var score` demonstrated Kotlin's inverted mutability default, with the
compiler rejecting a `val` reassignment at compile time exactly as
strictly as a type error.

## What Breaks Without This

Already shown above: reassigning a `val` produces a real, immediate
compile error naming the exact violation. Change `var score = 0` to
`val score = 0` and try `score = 10` — the identical error appears,
proving the rule applies uniformly, not just to the specific `name`
variable used in the original example.

## Exercises

1. Declare a `val` with an explicit type annotation instead of relying
   on inference — `val name: String = "Alex"` — and confirm it behaves
   identically. Confirm type inference is a convenience, not a
   different, weaker kind of typing.
2. Run `javap -p -c HelloKt.class` (the `-c` flag disassembles method
   bodies) and find the actual bytecode instruction calling `println` —
   direct, further proof that generated Kotlin bytecode is ordinary JVM
   bytecode, not some separate runtime.
