# Lesson 01: Anatomy of a WPF Project

**What this covers:** every file `dotnet new wpf` generates, what each one
actually is, and the one mechanism (`partial class`) that makes WPF's
two-files-per-window layout work at all. Read this before opening your
assigned project — every file you see in it is one of these.

**What you need to know first:** [Lesson 00](lesson-00-csharp-for-java-kotlin-developers.md)
and [00b](lesson-00b-delegates-events-and-lambdas.md).

## The file set

A generated WPF app (`dotnet new wpf -n MyApp`) produces this, minimum:

```
MyApp/
├── MyApp.csproj
├── App.xaml
├── App.xaml.cs
├── MainWindow.xaml
└── MainWindow.xaml.cs
```

Every WPF project you'll ever open — including your assignment — is this
same shape, just with more windows/pages added. Each piece:

## `.csproj` — the project manifest

```xml
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup>
    <OutputType>WinExe</OutputType>
    <TargetFramework>net8.0-windows</TargetFramework>
    <Nullable>enable</Nullable>
    <ImplicitUsings>enable</ImplicitUsings>
    <UseWPF>true</UseWPF>
  </PropertyGroup>
</Project>
```

XML describing how to build the project — C#'s rough equivalent of
`package.json`/`requirements.txt` plus build config combined.

- `Sdk="Microsoft.NET.Sdk"` — build using .NET's standard, modern
  "SDK-style" logic: `.cs` files anywhere under this folder are compiled
  in automatically, by convention — you never list them by hand.
- `<OutputType>WinExe</OutputType>` — a Windows GUI executable, no console
  window (vs. `Exe`, a console app, or `Library`, a `.dll`).
- `<TargetFramework>net8.0-windows</TargetFramework>` — which .NET
  version, and the required `-windows` suffix that unlocks Windows-only
  APIs. There is no cross-platform WPF; this suffix is always present.
- `<Nullable>enable</Nullable>` — nullable reference type checking, from
  Lesson 00.
- `<UseWPF>true</UseWPF>` — the flag that actually makes this a WPF
  project: it tells the build to also compile `.xaml` files and link the
  WPF framework libraries. Without this line, `<Window>` and every other
  WPF class fail to resolve.

If your assignment adds a NuGet package (SQLite, a JSON library, anything
`dotnet add package X` installs), it shows up here as a
`<PackageReference Include="X" Version="..." />` inside a
`<ItemGroup>` — the direct equivalent of a line in `requirements.txt` or
`package.json`'s `dependencies`.

## The `partial class` mechanism — why every window is two files

Open `MainWindow.xaml.cs`:

```csharp
namespace MyApp;

public partial class MainWindow : Window
{
    public MainWindow()
    {
        InitializeComponent();
    }
}
```

`InitializeComponent()` has no visible body anywhere in this file. It
isn't missing — it's generated by the build, from `MainWindow.xaml`, into
a *third*, invisible piece of this same class, merged in by the compiler.
Proof, with disposable code that has nothing to do with WPF:

```csharp
// Robot.Body.cs
partial class Robot
{
    public string Name = "Rex";
    public void Greet() => Console.WriteLine($"{Name} says hi from Body.cs");
}

// Robot.Brain.cs
partial class Robot
{
    public void Think() => Console.WriteLine($"{Name} says hi from Brain.cs");
}
```

```csharp
var r = new Robot();
r.Greet();
r.Think();
```

**Real output:**
```
Rex says hi from Body.cs
Rex says hi from Brain.cs
```

Two separate files, each declaring `partial class Robot`, are really the
*same* class — `Think()` (in `Brain.cs`) reads `Name` (in `Body.cs`) with
no import or reference between the files at all. `partial` tells the
compiler "don't complain this class is declared more than once — merge
every `partial` piece with this exact name into one class before
compiling anything else." Without `partial` on both, this is a compile
error: `Robot` defined twice.

This is why `MainWindow.xaml.cs` compiles even though it calls a method
whose body it never shows: the build reads `MainWindow.xaml` and
generates a third `partial class MainWindow` piece (a `.g.cs` file you
never open by hand) containing the real `InitializeComponent()`, built
from the markup. Your hand-written `.xaml.cs` and the generated `.g.cs`
merge into one class, same mechanism as `Robot`.

## `x:Class` — the line that links markup to code

```xml
<!-- MainWindow.xaml -->
<Window x:Class="MyApp.MainWindow"
        xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
        xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
        Title="MainWindow" Height="450" Width="800">
    <Grid>
    </Grid>
</Window>
```

`x:Class="MyApp.MainWindow"` is the single most load-bearing attribute in
the file: it tells the build *which* `partial class` this markup's
generated half belongs to. Change it to a name that doesn't match the
real class and the build breaks — the generated `InitializeComponent()`
has nowhere real to attach:

```
error CS0103: The name 'InitializeComponent' does not exist in the current context
```

Note the error points at the `.xaml.cs` file's call site, not the `.xaml`
file where the real mistake lives — a real, common WPF debugging trap:
the error surfaces one layer away from its actual cause. If you ever
rename a window class in your assignment, `x:Class` in the matching
`.xaml` has to be renamed to match, by hand — nothing does it for you
automatically.

## `App.xaml` / `App.xaml.cs` — the application object, not a window

```xml
<!-- App.xaml -->
<Application x:Class="MyApp.App"
             xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
             xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
             StartupUri="MainWindow.xaml">
    <Application.Resources>
    </Application.Resources>
</Application>
```

`Application` is a different real WPF class than `Window` — it represents
the whole running process, not any one screen; there's exactly one
instance of it per app, ever. `StartupUri="MainWindow.xaml"` is the real
answer to "how does `MainWindow` ever get shown at all" — nothing in
`MainWindow.xaml.cs` calls `new MainWindow().Show()`; `App` does it
automatically on startup because this attribute names which window. If
your assignment needs to change what window opens first (a login screen
before the main window, for example), this is the line to change — or
replace with manual startup logic in `App.xaml.cs`'s `OnStartup`
override, the more flexible alternative when the first screen depends on
runtime logic (is there a saved session?) rather than being fixed.

`<Application.Resources>` is where app-wide `Style`s and
`ResourceDictionary` merges live — empty here, real by Lesson 08.

## Where a window's own content lives: `<Grid>`

```xml
<Window ...>
    <Grid>
    </Grid>
</Window>
```

A `Window` can hold exactly **one** direct child — this is a hard rule,
not a style choice; `<Window><TextBlock/><Button/></Window>` with two
siblings directly inside `Window` is a compile error. `Grid` (Lesson 03)
is almost always that one child, because it's itself a container that can
hold many children arranged in rows/columns — the practical way around
the one-child rule.

## Mechanical walkthrough of the merge, end to end

1. `dotnet build` reads the `.csproj`, sees `UseWPF=true`, and runs a
   XAML-specific compile step before ordinary C# compilation: every
   `.xaml` file is parsed and turned into a generated `partial class`
   (a `.g.cs` file) with a real `InitializeComponent()` that builds the
   object tree the markup described.
2. That generated partial merges with your hand-written
   `public partial class MainWindow : Window { ... }` — the exact
   `Robot`-proven mechanism above, now doing real work.
3. `dotnet run` starts the compiled `.exe`. `App.xaml`'s `StartupUri`
   fires, constructing a `MainWindow` — its constructor runs, calls
   `InitializeComponent()`, and the real tree the XAML described gets
   built and shown.

## SE Lens

The alternative WPF could have chosen — and the one `InitializeComponent()`
itself is secretly doing under the hood — is building the entire visual
tree by hand in C# (`new Grid(); grid.Children.Add(new TextBlock { Text
= "..." });`). Both are real, valid WPF; there's no XAML requirement at
the framework level. The tradeoff `partial`/XAML pays for: a nested XML
element structure visually mirrors the nested visual structure it
produces on screen, which a flat sequence of `new`/`.Add()` calls doesn't
— at the cost of two files to keep mentally associated per window, and a
generated third piece you can't `Ctrl+click` into by reading source
alone.

## What to check first in your assigned project

- Open the `.csproj` — confirm `<UseWPF>true</UseWPF>` is there, note the
  `TargetFramework`, and read the `<ItemGroup>` for any `PackageReference`
  — that's your dependency list.
- Count the `.xaml`/`.xaml.cs` pairs — each pair is one window or one
  `UserControl` (a reusable piece of UI, not covered until later in this
  reference, but structurally the same file-pair shape).
- Open `App.xaml`, find `StartupUri`, and that's your actual entry point
  — start reading the app from there, not from wherever the file
  alphabetically sorts first.
