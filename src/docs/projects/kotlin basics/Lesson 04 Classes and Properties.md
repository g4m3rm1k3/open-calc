# Lesson 04: Classes and Properties

**What you will build:** Nothing app-related yet — a disposable class
proving how much of Java's field/constructor/getter/setter ceremony
Kotlin compresses into one declaration, and exactly what that
compression actually generates underneath. The transferable problem:
Java's constructor, private fields, and getter/setter methods were four
separate, hand-written pieces working together to express one idea — "an
object with controlled, readable state." Kotlin has one syntax for that
whole idea, and trusting what it generates instead of writing it by hand
requires seeing, concretely, that nothing was actually skipped, only
generated.

**What you need to know first:** Java's constructors, `private` fields,
and getter/setter methods.

**Terms introduced in this lesson:**
- **Primary constructor** — a constructor declared directly in a class's
  header, as part of the class declaration itself, rather than as a
  separate block.
- **Property** — a `val` or `var` declared inside a class; automatically
  backed by a private field and public getter (and setter, for `var`),
  generated by the compiler.

---

## Concept Unit: The Primary Constructor Generates Fields and Accessors

### The Problem

A Java class representing "a labeled point" needs, at minimum: two
private fields, a constructor assigning them, and two getter methods —
four separate pieces of ceremony for one idea. Kotlin has a single
declaration expressing the same idea.

### Introduce the Concept in Isolation

```kotlin
class LabeledPoint(val label: String, var x: Int, var y: Int)

fun main() {
    val origin = LabeledPoint("Origin", 0, 0)

    println("${origin.label}: (${origin.x}, ${origin.y})")

    origin.x = 10
    println("${origin.label}: (${origin.x}, ${origin.y})")
}
```

Compile and run:

```
kotlinc LabeledPoint.kt -include-runtime -d LabeledPoint.jar
java -jar LabeledPoint.jar
```

Real output:

```
Origin: (0, 0)
Origin: (10, 0)
```

`class LabeledPoint(val label: String, var x: Int, var y: Int)` is the
entire class — a **primary constructor**, declared directly inside the
class header's parentheses, with no separate constructor block written
at all. `val label` and `var x`/`var y` inside that parameter list are
**properties**, not plain constructor parameters: writing `val` or `var`
here (rather than a bare, unqualified parameter) tells the compiler to
generate a real, private backing field for each one, plus a public
getter (`label`, `x`, `y`, called with no parentheses — `origin.x`, not
`origin.getX()`), and, because `x` and `y` are `var`, a public setter as
well (`origin.x = 10` calls that generated setter, not a raw field
write). `label`, `var`-less at the call site but declared `val` in the
constructor, has no setter generated at all — attempting `origin.label =
"New"` would be a compile error, the exact same reassignment protection
Lesson 01 already proved for a plain local `val`.

### Discard the Throwaway Example

`LabeledPoint` is deleted now. Every class this project's Kotlin rebuild
declares from here on uses this exact primary-constructor-with-
properties shape.

### CS Lens

This is the same **encapsulation** principle Java's manual
field/getter/setter pattern already implements — private state, exposed
through controlled accessors — with the ceremony generated by the
compiler instead of typed by hand. Nothing about the actual *runtime
shape* differs: a real private field and real accessor methods exist in
the compiled `.class` file either way, confirmable with `javap` exactly
as Lesson 01 confirmed Kotlin's generated `main` method.

### SE Lens

**Why does Kotlin default to generating a getter and setter for every
property, rather than requiring them to be written explicitly, the way
Java requires?** Java's own getter/setter ceremony exists specifically
to preserve the *option* of adding validation or side effects later
without breaking calling code (the Java series' own SE Lens on this
exact point already made this argument) — but the overwhelming majority of real
fields never actually need anything beyond a plain read or write.
Kotlin generates the plain version by default and lets you *override*
just the getter or setter for the specific properties that ever need
real logic (shown in Exercise 2 below), rather than paying the
boilerplate cost on every property whether or not it's ever needed.

## Connect the Pieces

One trace: `LabeledPoint("Origin", 0, 0)` called the primary
constructor, which the compiler expanded into three real backing fields
and their accessor methods. `origin.x` read through the generated
getter; `origin.x = 10` wrote through the generated setter; `origin.label`
had no setter generated at all, because it was declared `val`.

## What Breaks Without This

Attempt `origin.label = "New"` in a scratch copy. Real error:

```
error: val cannot be reassigned
```

The identical error Lesson 01 already proved for a local `val`,
confirming a `val` property behaves by the exact same rule, not a
special, separate case for class members.

## Exercises

1. Add a fourth property, `val description: String`, computed instead
   of stored — declare it as `val description: String get() =
   "$label at ($x, $y)"` (a **custom getter**, computing its value fresh
   on every read instead of being backed by a stored field at all) —
   and confirm it updates automatically after `origin.x` changes,
   proving it's genuinely recomputed each time, not cached from
   construction.
2. Declare a second class the same way, with all-`val` properties (no
   `var` anywhere), and confirm every property is read-only from
   outside — direct proof that switching `val`/`var` per property, not
   per class, controls mutability at the individual field's own
   granularity.
