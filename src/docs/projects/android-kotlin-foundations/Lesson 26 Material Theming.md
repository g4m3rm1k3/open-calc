# Lesson 26: Material Theming

**What you will build:** One consistent color palette applied across
this project's two Compose screens via a real `MaterialTheme` wrapper,
plus deliberate, unequal spacing restoring the visual grouping Java's
Lesson 34 already established for the login screen. The transferable
problem: Java's Lesson 34 defined colors once, in `colors.xml`, and
applied them app-wide through one `themes.xml` entry inherited
automatically by every Activity — a real, working mechanism this
project's own `MainActivity` still uses, unchanged. The two Compose
screens this series built, though, never read `themes.xml` at all;
Compose has its own, separate theming mechanism, and this project — with
one View-based screen and two Compose screens — genuinely needs both,
side by side, rather than one replacing the other.

**What you need to know first:** Java's Lesson 34 in full (`colors.xml`,
`themes.xml`, style inheritance via `parent`, `colorPrimary`/
`colorAccent`, and the Gestalt proximity/margin reasoning for visual
grouping). This series' own Lesson 14 (`Modifier`), Lesson 25
(`InventoryApp`, the merged Compose screens this lesson themes).

**Terms introduced in this lesson:**
- **`ColorScheme`** — a real Kotlin object holding a complete, named set
  of colors (primary, secondary, background, and more), the Compose
  analog of `themes.xml`'s `colorPrimary`/`colorPrimaryDark`/
  `colorAccent` theme attributes.
- **`MaterialTheme`** — a composable that makes a `ColorScheme` (and
  typography, and shapes) available to every composable nested inside
  it, the Compose analog of a Manifest-level `android:theme` attribute
  applying to a whole Activity.

## Concept Unit: `themes.xml` Still Applies — to `MainActivity` Only

### The Problem

Confirm precisely what Java's Lesson 34 mechanism still covers in this
project, and what it doesn't. `MainActivity`'s Manifest entry still
declares `android:theme="@style/Theme.YourApp"` (Java's own Lesson 34
mechanism, generated by the wizard and never touched since this
series' own Lesson 04), and `MainActivity`'s login screen — still
View Binding-based — genuinely inherits `colorPrimary`/`colorAccent`
from it, exactly as Java's Lesson 34 already proved. Neither
`InventoryApp`'s `NavHost` nor anything composed inside it reads

### CS Lens

This is a real, concrete instance of the same UI-system boundary this
series' own Lesson 25 already named for navigation: theming, like
navigation, has one mechanism on each side of the View/Compose divide,
and neither one automatically extends across it.

## Concept Unit: `ColorScheme` and `MaterialTheme` — Compose's Own Mechanism

### The Problem

The two Compose screens need the identical brand colors Java's Lesson
34 already chose (`#1565C0` primary, `#FF6F00` accent), applied once,
inherited by every composable, the same "define once, apply everywhere"
goal — through a genuinely different real mechanism.

### The New Code

```kotlin
private val AppColorScheme = lightColorScheme(
    primary = Color(0xFF1565C0),
    secondary = Color(0xFFFF6F00)
)

@Composable
fun InventoryAppTheme(content: @Composable () -> Unit) {
    MaterialTheme(
        colorScheme = AppColorScheme,
        content = content
    )
}
```

```kotlin
setContent {
    InventoryAppTheme {
        InventoryApp()
    }
}
```

### Mechanical Walkthrough

- `lightColorScheme(primary = Color(0xFF1565C0), secondary = Color(0xFFFF6F00))`
  — **first appearance.** A real, standard Compose Material 3 function
  building a complete `ColorScheme` object — one holding dozens of named
  color roles (`primary`, `secondary`, `background`, `error`, and more),
  most left at Material's own sensible defaults here, with only
  `primary` and `secondary` overridden — the direct Compose analog of
  Java's Lesson 34 `<style parent="Theme.MaterialComponents...">`
  inheriting a complete base theme and overriding only three specific
  slots. `Color(0xFF1565C0)` is Compose's own color type, constructed
  from the identical hex value Java's Lesson 34 already chose
  (`#1565C0`), with a leading `FF` added for full opacity — Compose
  colors carry an explicit alpha channel Android's XML `#RRGGBB` shorthand
  doesn't require writing out.
- `fun InventoryAppTheme(content: @Composable () -> Unit)` — **first
  appearance of a composable parameter with a composable function
  type.** `content: @Composable () -> Unit` is this series' own Lesson
  08 function-type syntax, with `@Composable` marking the function type
  itself — not just this declaring function — as something only
  composable code can be passed as. This is the real, standard shape
  every "wrapper" composable in Compose takes, the direct analog of
  `LazyColumn`'s own content-lambda parameter (this series' own Lesson
  16).
- `MaterialTheme(colorScheme = AppColorScheme, content = content)` —
  **first appearance.** A real, built-in Compose function that makes
  `colorScheme` available, via a `CompositionLocal` (this series' own
  Lesson 24 concept, reappearing here for the mechanism actually
  powering `MaterialTheme` internally), to every composable nested
  inside its `content` lambda — the direct Compose analog of a Manifest
  `android:theme` attribute applying to everything an Activity displays.
- `InventoryAppTheme { InventoryApp() }` — wrapping the entire `NavHost`
  (this series' own Lesson 25) in the theme, exactly the way Java's
  Lesson 34 theme attribute automatically covered every widget on every
  screen with zero per-layout edits — here, zero per-composable edits.

### CS Lens

Both mechanisms — XML style inheritance and `MaterialTheme`'s
`CompositionLocal`-based propagation — solve the identical
**separation of concerns** problem Java's Lesson 34 already named for
`colors.xml`: define shared values once, reference them everywhere, so
one edit changes every consumer consistently. The *mechanism* differs
because the two UI systems' own architectures differ (a Manifest
attribute versus a composition-scoped value), but the underlying design
goal is unchanged.

### SE Lens

**Why does Compose theming use a runtime mechanism (`CompositionLocal`,
resolved when each composable actually runs) instead of Java's
build-time style inheritance, resolved once when the layout is
inflated?** Compose's approach lets a theme genuinely change *while the
app is running* — a real, common requirement (switching between light
and dark mode without restarting the Activity) that Java's XML theme
system handles only by re-inflating layouts against a different theme
resource. `MaterialTheme`'s color values being read fresh, per
composition, is exactly what makes recomposition (this series' own
Lesson 15) capable of picking up a live theme change automatically,
the same mechanism already responsible for picking up any other
observable state change.

## Concept Unit: Grouping Through Spacing — Compose's Version

### The Problem

Java's Lesson 34 used unequal `android:layout_marginBottom` values to
make the login screen's fields read as one group and its buttons read
as a separate group — a real, deliberate application of the Gestalt
proximity principle already named there. Does the identical technique
translate to Compose's `Modifier`-based spacing?

### The New Code

```kotlin
Column(modifier = Modifier.padding(24.dp)) {
    TextField(value = username, onValueChange = { username = it }, modifier = Modifier.padding(bottom = 8.dp))
    TextField(value = password, onValueChange = { password = it }, modifier = Modifier.padding(bottom = 24.dp))
    Button(onClick = { /* login */ }, modifier = Modifier.padding(bottom = 8.dp)) {
        Text(text = "Log In")
    }
    Button(onClick = { /* create account */ }) {
        Text(text = "Create Account")
    }
}
```

### Mechanical Walkthrough

- `Modifier.padding(bottom = 8.dp)` between the two fields, versus
  `Modifier.padding(bottom = 24.dp)` after the password field — the
  identical **unequal spacing** idea from Java's Lesson 34: a small gap
  between elements that belong together (the two fields), a
  deliberately larger gap marking a real group boundary (fields versus
  buttons) — expressed as a named `Modifier` parameter instead of an
  XML `android:layout_marginBottom` attribute, same underlying Gestalt
  proximity principle, same reasoning, different syntax.

### SE Lens

**Compose's own layout system has no separate "margin" versus
"padding" distinction the way Java's Lesson 34 named — is that a real
capability gap?** No — `Modifier.padding(...)`, applied to an
individual child inside a `Column`, achieves the identical visual
result Java's Lesson 34 `layout_marginBottom` achieved: space pushed
*outside* that specific child, separating it from its neighbor.
Compose doesn't need a separate margin/padding vocabulary because a
`Modifier` chain applies directly to the one composable it's attached
to, at the exact point where "space around this specific element" is
declared — there's no separate parent-versus-child attribute split to
maintain, since the modifier is always scoped to whichever composable
it's passed into.

## Connect the Pieces

One trace: `MainActivity`'s login screen kept inheriting
`colorPrimary`/`colorAccent` from `themes.xml`, exactly as Java's Lesson
34 already proved, completely unaffected by anything in this lesson.
`lightColorScheme(...)` built the Compose equivalent of that same color
choice, and `MaterialTheme`, wrapping `InventoryApp`'s entire `NavHost`
(this series' own Lesson 25), made it available to every composable
inside via the identical `CompositionLocal` mechanism already introduced
for `LocalContext` (Lesson 24). Unequal `Modifier.padding` values on the
login screen's own composable equivalent restored the same visual
grouping Java's Lesson 34 already established through unequal XML
margins — one design principle, two real, separately-justified
mechanisms, applied consistently across the UI-system boundary this
series has named honestly since Lesson 25.

## What Breaks Without This

Remove `InventoryAppTheme { }` from around `InventoryApp()`, leaving
`setContent { InventoryApp() }` directly, and run the app.

Real result, when you do this yourself: every `Button` and other
Material component across both Compose screens renders using Compose
Material 3's own built-in default purple color scheme, visibly
inconsistent with `MainActivity`'s still-correctly-themed blue login
screen — a real, observable proof that `MaterialTheme`'s color values
have to be explicitly supplied; nothing about being inside an Activity
whose Manifest declares `android:theme` causes Compose to pick it up
automatically. Restore the `InventoryAppTheme` wrapper before moving on.
