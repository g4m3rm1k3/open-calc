## Concept Unit: Scaling a Working System

### The Problem
Once a small system is running well, you often want to expand it. Doing too much too soon usually breaks it. We need a safe way to scale.

### Introduce the concept in isolation
**Throwaway lab** (think of these two versions):

**Version A (unsafe scaling)**: “I was walking 20 minutes → now I’ll run 10 km every day.”  
**Version B (safe scaling)**: “I was walking 20 minutes → I’ll add 5 more minutes this week.”

Try the safe version mentally.

**What this proves**: Small, gradual increases (usually 5–10%) are much more sustainable than big jumps.

**Discard the throwaway example.**

### Project Change
- Continue in `systems-mastery/lesson6.md`

### The New Code — type it yourself
Add to your workbook:

```markdown
# Systems Mastery - Lesson 6

## Current System Status
(Is it running consistently? Yes / Somewhat / No)

## Scaling Plan (if it's working well)
- Current level:
- Next small increase (aim for +5-10%):
- When I will try it:
```

### The Updated Project
Your workbook now has a scaling template.

### Mechanical walkthrough
1. **Check current status** — Only scale if the system is already consistent.
2. **Small increase** — Add a little more effort, time, or frequency (never a huge jump).
3. **Time boundary** — Decide when you will attempt the increase.

### Systems Thinking Lens
This is **gradual load increase** — the same principle used in strength training, learning, and engineering (stress testing systems slowly).

### Engineering / Design Lens
Safe scaling follows the principle of **progressive overload**.  
**Alternative not chosen**: Going all-in with big ambitious changes.  
**Tradeoff**: Slow scaling feels less exciting, but it prevents injury, burnout, and abandonment.

### Run it
If your system is stable, plan one small scaling step.

## Concept Unit: Handling Plateaus and Failure

### The Problem
Progress is rarely linear. You will hit plateaus (no visible improvement) and failures (you stop completely for days/weeks). Most people quit here.

### The New Code — type it yourself
Add to `lesson6.md`:

```markdown
## Plateau or Failure Recovery Plan
- How I will notice it early:
- What I will do when it happens (one small restart action):
- What I learned from this setback:
```

### The Updated Project
Your workbook now includes a recovery template.

### Mechanical walkthrough
1. **Early detection** — Use your tracking to spot when progress has stalled or stopped.
2. **Restart action** — Have a pre-decided tiny action to get moving again (e.g., “just do 5 minutes”).
3. **Learning** — Extract the lesson so the same failure is less likely next time.

### Systems Thinking Lens
Plateaus and failures are normal **system feedback**. They tell you something needs adjustment — resistance, insufficient recovery, or wrong approach.

### Engineering / Design Lens
Failure is data, not a verdict.  
**Alternative not chosen**: Seeing failure as proof you’re “bad” or the goal is impossible.  
**Tradeoff**: Treating failure as learning requires emotional maturity and humility, but it turns setbacks into fuel for better systems.

### Run it
If you’ve had any recent plateau or failure, fill in the recovery plan and take the small restart action.

### Connecting sentence
We now have tools for long-term sustainability: scaling when successful, recovering when struggling.
