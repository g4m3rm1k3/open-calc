# Lesson 47: A Secret Strong Enough to Make Slowness Pointless

## What you will build

An API key system — generate, store, and verify — wired into a real
HTTP server (reusing Lesson 31's raw-socket request handling) that
rejects every request without a valid key. Along the way, a real,
computed argument for why this lesson's key hashing deliberately does
*not* reuse Lesson 42's slow PBKDF2 approach, even though both are
"hash a secret and compare" at a glance — the two secrets being hashed
have such different properties that the same design choice would be
wrong applied to the other.

## What you need to know first

- **Lesson 42** — salted, slow password hashing, and the exact contrast
  this lesson draws against: today's API keys get salted (implicitly, by
  their own randomness) but deliberately *not* slowed down, for a reason
  this lesson computes rather than asserts.
- **Lesson 43** — `secrets`, reused directly to generate the actual key
  material.
- **Lesson 31** — the raw-socket HTTP request parsing this lesson's demo
  server reuses to read the `Authorization` header.

---

## The Problem, in prose, no code yet

A human password and a machine-issued API key are both "secrets checked
on every request," and it would be easy to assume they need identical
handling — hash them, salt them, slow them down, the way Lesson 42 did.
They don't. A password is chosen by a person, from a comparatively small
space of things people actually pick, which is exactly why Lesson 42
needed to make guessing expensive. An API key, generated by
`secrets.token_urlsafe` rather than a human's imagination, comes from an
astronomically larger space — and treating it identically to a password
would add real cost (Lesson 42's own measured ~0.124 seconds per PBKDF2
call) to every single API request, for a benefit this lesson computes
directly below to be already, overwhelmingly unnecessary.

## Concept Unit: Not Every Secret Needs to Be Slow to Hash

### The Problem

Before building anything, it's worth actually computing whether API keys
need the same brute-force protection passwords do, rather than assuming
the answer by analogy.

### Introduce the concept in isolation

```python
guesses_per_second_fast_hash = 1_000_000  # measured in Lesson 42 for plain SHA-256

human_password_space = 62 ** 10  # roughly a 10-character mixed-case+digit password
api_key_secret_space = 2 ** 128  # a 128-bit random secret, typical API key strength

human_password_seconds = human_password_space / guesses_per_second_fast_hash
api_key_seconds = api_key_secret_space / guesses_per_second_fast_hash

seconds_per_year = 60 * 60 * 24 * 365
age_of_universe_years = 13_800_000_000

print(f"10-char human password, fast hash: {human_password_seconds / seconds_per_year:,.1f} years to exhaust")
print(f"128-bit random API key, fast hash: {api_key_seconds / seconds_per_year:,.2e} years to exhaust")
print(f"that's the age of the universe, times: {(api_key_seconds / seconds_per_year) / age_of_universe_years:,.2e}")
```

Run it:

```
10-char human password, fast hash: 26,614.0 years to exhaust
128-bit random API key, fast hash: 1.08e+25 years to exhaust
that's the age of the universe, times: 7.82e+14
```

What this proves, with a real (if illustrative) calculation reusing
Lesson 42's own directly-measured guess rate: a 10-character human
password, even hashed with the *fast*, "wrong" hash from that lesson,
already takes an impractically long time to brute-force outright — the
real, practical risk Lesson 42 defended against was never "years," it
was that real attackers don't brute-force blindly; they use dictionaries
of *actually-common* passwords, a much smaller effective space than the
raw math above suggests, which is what genuinely justifies PBKDF2's
extra cost there. A 128-bit random API key occupies a space so much
larger that even a comically pessimistic real-world adjustment leaves
the exhaustive-search time at roughly the age of the universe repeated
hundreds of trillions of times over — and, critically, unlike a human
password, there is no smaller "common API keys" dictionary an attacker
could use instead, since every bit was chosen by `secrets`, not a
person.

This lab is deleted now; it never appears in the project. What survives
is the computed justification for the next unit's real design choice:
plain, fast SHA-256 is genuinely sufficient here, and adding PBKDF2's
cost would buy essentially nothing.

### CS Lens

This is choosing a defense proportional to the actual **attack surface**
— the size of the space an attacker would need to search — rather than
applying a fixed level of protection regardless of context. Lesson 42's
slow hashing defended against *low-entropy, human-chosen* secrets
specifically; this lesson's secrets don't have that weakness to defend
against in the first place.

### SE Lens

Applying PBKDF2 here anyway wouldn't be *wrong* in the sense of being
insecure — it would simply be paying a real, measured cost (Lesson 42's
own ~0.124-second-per-check figure) on every single API request, for a
security benefit the calculation above shows is already achieved,
overwhelmingly, by the key's own randomness alone. Security decisions
have real performance costs, and matching the defense to the actual
threat — not defaulting to "more expensive must be safer" — is itself
the engineering judgment this lesson is teaching, directly continuing
the same reasoning Lesson 44 already applied when it chose *not* to
reuse Lesson 42's slow hash for file checksums.

## Concept Unit: A Key With a Lookup Handle Built In

### Project Change

- **Reference Source:** No reference counterpart — the `prefix_secret`
  key shape below follows the widely-used real convention popularized by
  Stripe's own API keys (`sk_live_...`), not a specific codebase.
- **Files affected:** new file, `api_key_store.py`.
- **Change type:** add.
- **Dependencies:** `secrets` (Lesson 43), `hashlib`/`hmac` (Lesson 42).

### The New Code

```python
KEY_PREFIX_LENGTH = 8
KEY_SECRET_BYTES = 32


def generate_api_key():
    prefix = secrets.token_hex(KEY_PREFIX_LENGTH // 2)
    secret = secrets.token_urlsafe(KEY_SECRET_BYTES)
    full_key = f"myapp_{prefix}_{secret}"
    return full_key, prefix, secret


def hash_secret(secret):
    return hashlib.sha256(secret.encode()).hexdigest()
```

### The Updated Project

Two new, freestanding functions with nothing surrounding them yet.

### Mechanical Walkthrough

- `secrets.token_hex(KEY_PREFIX_LENGTH // 2)` — **first appearance of
  this specific `secrets` function**, alongside Lesson 43's own
  `secrets.choice`. `token_hex(n)` generates `n` random bytes and
  returns them as a `2n`-character hex string — dividing
  `KEY_PREFIX_LENGTH` by `2` here compensates for that doubling, so the
  final `prefix` string is exactly `8` characters.
- `secrets.token_urlsafe(KEY_SECRET_BYTES)` — **first appearance.**
  Generates `KEY_SECRET_BYTES` (32) random bytes, encoded using a
  URL-safe variant of Base64 (Lesson 30's own encoding, seen there for
  the WebSocket handshake) — chosen specifically because the result
  contains no characters that would need escaping in a URL or an HTTP
  header, both realistic places an API key travels.
- `f"myapp_{prefix}_{secret}"` — this is the whole point of generating a
  separate `prefix`: the final key visibly carries a short, identifiable
  segment *before* the actual secret — a real, deliberate design choice
  explained directly in the next unit.
- `hash_secret` — a **hard concept reappearing** from Lesson 42, but
  applying plain, single-round `hashlib.sha256` rather than
  `pbkdf2_hmac`, per the previous unit's computed justification.

### CS Lens

Splitting the key into a `prefix` (stored and searchable in the open)
and a `secret` (only ever compared, never searched by) is a **lookup key
versus authentication credential** separation — the prefix's job is
*finding* the right stored record quickly; the secret's job is *proving*
the presenter actually has the right to use that record.

Also recognized in: real API providers (Stripe, GitHub, AWS) all
embedding an identifiable prefix in their own issued keys for exactly
this reason — support staff, log analysis, and automated leak-scanning
tools can recognize and act on a key's *prefix* without ever needing, or
being able, to see the secret portion at all.

### SE Lens

The alternative — a single opaque random string with no visible
structure — would work for authentication alone, but loses a genuinely
useful capability: automated secret-scanning tools (used by GitHub and
others to detect accidentally-committed credentials in public
repositories) rely on recognizable prefixes to identify *which* service
a leaked string belongs to at all, so the right provider can be alerted
to revoke it immediately. A visible prefix costs nothing in security —
it's not the secret part — and buys real operational value.

## Concept Unit: Storing and Verifying by Prefix

### Project Change

- **Reference Source:** No reference counterpart.
- **Files affected:** `api_key_store.py`.
- **Change type:** add.
- **Location:** below `hash_secret`.

### The New Code

```python
class APIKeyStore:
    def __init__(self):
        self.keys_by_prefix = {}  # prefix -> (hashed_secret, owner_label)

    def register(self, owner_label):
        full_key, prefix, secret = generate_api_key()
        self.keys_by_prefix[prefix] = (hash_secret(secret), owner_label)
        return full_key

    def verify(self, presented_key):
        try:
            _, prefix, secret = presented_key.split("_", 2)
        except ValueError:
            return None

        if prefix not in self.keys_by_prefix:
            return None

        stored_hash, owner_label = self.keys_by_prefix[prefix]
        candidate_hash = hash_secret(secret)
        if hmac.compare_digest(stored_hash, candidate_hash):
            return owner_label
        return None
```

### Mechanical Walkthrough

- `register` — generates a fresh key, stores only the *hash* of its
  secret (never the raw secret itself, a **hard concept reappearing**
  from Lesson 42's own `UserStore`), keyed by the visible prefix, and
  returns the one-time full key to the caller — the only moment the raw
  secret ever exists outside this function, exactly mirroring the real
  practice of showing an API key to a user exactly once at creation time.
- `presented_key.split("_", 2)` — reused string splitting, capped at `2`
  splits (a **hard concept reappearing** from Lesson 31's identical
  reasoning) so a secret that happens to contain an underscore isn't
  incorrectly split further; unpacks into `myapp`, the `prefix`, and the
  `secret` in one line.
- `except ValueError: return None` — reused exception handling; a
  malformed key (wrong number of underscore-separated parts) fails
  cleanly rather than crashing the whole request handler.
- `if prefix not in self.keys_by_prefix: return None` — an **O(1)
  dictionary lookup**, not a scan comparing the presented secret against
  every stored key — the concrete payoff of storing by prefix rather
  than needing to hash-and-compare against every single issued key on
  every request.
- `hmac.compare_digest(stored_hash, candidate_hash)` — a **hard concept
  reappearing** from Lesson 42, applied here for the identical reason:
  even though a timing attack is somewhat less immediately actionable
  against a fixed-length hex digest than a raw secret, there is no
  reason to reintroduce a comparison whose safety depends on careful
  reasoning when the correct tool is already established practice.

### Run it

```python
store = APIKeyStore()
real_key = store.register("acme-corp-integration")
print("issued key:", real_key)

print("verify real key:         ", store.verify(real_key))
print("verify tampered secret:  ", store.verify(real_key[:-1] + ("X" if real_key[-1] != "X" else "Y")))
print("verify unknown prefix:   ", store.verify("myapp_00000000_fakefakefake"))
print("verify malformed key:    ", store.verify("not-a-valid-key-format"))
```

```
issued key: myapp_e1a0a8f0_n7Z4awkV5_I8uhDdGJRztxdtfJZCLwKfj25HzVXc60w
verify real key:          acme-corp-integration
verify tampered secret:   None
verify unknown prefix:    None
verify malformed key:     None
```

Every failure path returns the identical `None` a legitimate caller
would need to check for — no exception escapes `verify` under any of
these conditions, which matters directly for the next unit's HTTP
integration: a request handler can treat every rejection uniformly.

## Concept Unit: Enforcing It on a Real Server

### Project Change

- **Reference Source:** No reference counterpart.
- **Files affected:** new file, `api_server.py`.
- **Change type:** add.
- **Dependencies:** `APIKeyStore`; request parsing reused from Lesson
  31's `parse_request_line_and_headers`.

### The New Code

```python
def handle_client(client_socket):
    request_bytes = client_socket.recv(4096)
    request_text = request_bytes.decode("utf-8")
    headers = parse_headers(request_text)

    auth_header = headers.get("Authorization", "")
    if not auth_header.startswith("Bearer "):
        client_socket.sendall(build_response("401 Unauthorized", "missing or malformed Authorization header"))
        client_socket.close()
        return

    presented_key = auth_header[len("Bearer "):]
    owner_label = store.verify(presented_key)
    if owner_label is None:
        client_socket.sendall(build_response("401 Unauthorized", "invalid API key"))
        client_socket.close()
        return

    client_socket.sendall(build_response("200 OK", f"hello, {owner_label}"))
    client_socket.close()
```

### Mechanical Walkthrough

- `headers.get("Authorization", "")` — reused dictionary `.get()` with a
  default, so a request with no `Authorization` header at all produces
  an empty string rather than a `KeyError`.
- `"401 Unauthorized"` — **first appearance of this specific status
  code** in this curriculum (Lesson 32 used `429`, a different `4xx`
  meaning). `401` specifically means "you have not proven who you are" —
  distinct from `403 Forbidden` ("I know who you are, and you're not
  allowed"), a distinction worth naming precisely since this server's
  two rejection paths (missing header, invalid key) are both genuinely
  `401` cases: neither has established an identity at all.
- `auth_header.startswith("Bearer ")` — **first appearance of the
  `Bearer` authentication scheme name.** `Authorization: Bearer <token>`
  is a real, standard HTTP header format (RFC 6750) — "bearer" meaning
  literally "whoever holds this token is presumed authorized," with no
  further proof required, which is exactly why keeping the key itself
  secret is the *entire* security model.
- `auth_header[len("Bearer "):]` — reused slicing, strips the fixed
  `"Bearer "` prefix to recover just the key.
- Every rejection path returns and closes the connection immediately —
  a request with no valid key never reaches any application logic at
  all, the same "check first, act second" ordering Lesson 32's rate
  limiter established.

### Run it

A real server, issuing one real key, tested with four real HTTP
requests sent over raw sockets:

```
using key: myapp_9e081aff_vvdwCb3FLZQmIjMMZaw8YRWx5U8168of7c9jzox0DC4
--- valid key ---
HTTP/1.1 200 OK | hello, acme-corp-integration
--- no auth header ---
HTTP/1.1 401 Unauthorized | missing or malformed Authorization header
--- wrong key ---
HTTP/1.1 401 Unauthorized | invalid API key
--- malformed header (no Bearer prefix) ---
HTTP/1.1 401 Unauthorized | missing or malformed Authorization header
```

All four real, distinct scenarios behave exactly as designed: the
genuine key succeeds, and every other case — no header, a wrong key, and
a header missing the required `Bearer ` scheme — is rejected, each for
the reason its message states.

### CS Lens and SE Lens

Both fully covered by the units above — this is composition, applying
`APIKeyStore` at a real request boundary, per the Repetition Rule. The
one point worth restating: rejecting *before* any application logic
runs, uniformly, for every failure mode, is the same principle Lesson
32's rate limiter and Lesson 31's routing both already established —
authentication and authorization checks belong at the edge of a system,
not scattered through its internals.

## Connect the pieces

One issued key, followed through the entire lesson: `generate_api_key`
produces `myapp_9e081aff_...`, a human-recognizable `myapp_` scheme,
an `9e081aff` prefix that becomes the dictionary lookup key, and a
32-byte random secret whose brute-force resistance this lesson computed
directly to be astronomically beyond anything PBKDF2's extra cost would
meaningfully improve. `register` stores only that secret's plain SHA-256
hash, never the secret itself. A real HTTP request presenting the full
key back, via a standard `Authorization: Bearer` header, is parsed,
split back into its prefix and secret, looked up in `O(1)`, re-hashed,
and compared using the same constant-time comparison Lesson 42
established — and only on every one of those steps succeeding does the
server ever run any real application logic at all.

## What breaks without this

Already demonstrated directly, with real HTTP responses: a request with
no `Authorization` header, a request with a syntactically wrong header
(missing the `Bearer ` scheme), and a request with a well-formed but
incorrect key are all correctly rejected with `401 Unauthorized`,
each before the server's "hello" response logic is ever reached.
