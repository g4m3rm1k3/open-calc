# TypeScript Spreadsheet — Lesson 02 — Selecting a Cell

## What You Will Build

Click any cell, and it highlights. Click a different one, and the
highlight moves — never two cells at once, never zero once you have
clicked at least one. This is the first real state this project tracks,
and the first type deliberately allowed to mean "nothing is selected yet,"
a genuine, valid state this application starts in.

## Step 1 — A Type That Can Be "Nothing"

**The problem:** Before any cell has ever been clicked, nothing describes
that honestly — there is no coordinate to point at, and forcing one to
exist anyway would mean inventing a fake "default" cell that is secretly
selected before a person has done anything at all.

Add to `script.ts`, near the top:

```typescript
let selectedCoordinate: Coordinate | null = null;
```

**Walkthrough — your first union type.** `Coordinate | null` reads as "a
`Coordinate`, *or* `null`" — the `|` is TypeScript's **union** operator,
combining two types into one that accepts either. `selectedCoordinate` can
legally hold a real `{ col, row }` object, or the special value `null`
meaning "no coordinate" — nothing else. This is not a workaround; it is the
honest, complete description of every state this variable can actually be
in, at any point in this application's life. Starting it as `null` means
the very first moment the page loads — before any click has happened — is
represented truthfully, not glossed over.

**Why this matters more than it looks like it does.** Without the union,
you would have to choose: either force `selectedCoordinate` to always hold
a real `Coordinate` (picking some cell, arbitrarily, to be "selected" from
the start — a lie about what actually happened), or type it as `any`,
which tells TypeScript to stop checking it at all. `Coordinate | null` is
the honest middle path a well-designed type system exists specifically to
make possible: real, checked structure most of the time, with an explicit,
equally-checked escape hatch for the one legitimate case where there is
genuinely nothing yet.

## Step 2 — Guarantee a Coordinate Is Never Mutated in Place

**The problem:** Nothing currently stops a future line of code from
writing `selectedCoordinate.col = 99` directly — quietly changing a
coordinate object after it was created, instead of replacing it with a new
one. For this project, that would be a mistake worth catching immediately,
not discovering later as a confusing bug.

Update the `Coordinate` interface in `script.ts`:

```typescript
interface Coordinate {
  readonly col: number;
  readonly row: number;
}
```

**Walkthrough:** `readonly` in front of a property means it can be set once
— when an object literal matching this interface is first created — and
never reassigned afterward. `const selected: Coordinate = { col: 0, row:
0 }; selected.col = 5;` is now a real, caught TypeScript error on that
second line, even though `selected` itself was never declared `const`
specifically to prevent reassignment of its *fields* (that is what
`readonly` does) — `const` alone only stops *`selected` itself* from being
pointed at a different object entirely, which is a different guarantee.

**SE lens — why this project chooses "replace" over "mutate" for
coordinates specifically.** Every place this project ever changes which
cell is selected will do so by creating a brand-new `Coordinate` object,
never by editing an existing one's fields — Step 3 does exactly this.
`readonly` does not enable that choice; the choice was already made. What
`readonly` adds is TypeScript actively *enforcing* it — turning "we always
do it this way" from a convention someone has to remember into a rule the
compiler checks for you, every time.

## Step 3 — Select a Cell on Click

**The problem:** Clicking a cell currently does nothing at all.

Update `renderGrid()` in `script.ts` — the inner loop that creates each
`<td>` — adding one line:

```typescript
for (let col = 0; col < COLUMN_COUNT; col++) {
  const cell = document.createElement('td');
  cell.id = `cell-${cellId({ col, row })}`;
  cell.className = 'cell';
  cell.addEventListener('click', () => selectCell({ col, row }));
  tableRow.appendChild(cell);
}
```

Add a new function to `script.ts`:

```typescript
function selectCell(coordinate: Coordinate): void {
  if (selectedCoordinate) {
    const previousElement = requireElement(`cell-${cellId(selectedCoordinate)}`);
    previousElement.classList.remove('cell-selected');
  }

  selectedCoordinate = coordinate;

  const nextElement = requireElement(`cell-${cellId(coordinate)}`);
  nextElement.classList.add('cell-selected');
}
```

Add to the CSS tab:

```css
.cell-selected {
  outline: 2px solid #2563eb;
  outline-offset: -2px;
  background-color: #eff6ff;
}
```

Click **▶ Preview**. Click any cell: it highlights with a blue outline.
Click a different cell: the highlight moves there, and only there.

**Walkthrough — the closure, and why `let col` and `let row` make it
work.** `() => selectCell({ col, row })` is a function created fresh, once,
during *each* pass through the nested loops — and it **closes over** the
specific `col` and `row` values from that exact pass, remembering them for
as long as the click listener exists, however many more loop iterations
happen afterward. This only works correctly because `col` and `row` are
declared with `let` inside the loop itself — `let` (like `const`) creates a
brand-new, independent binding on every single iteration, so the closure
created for cell `{ col: 2, row: 3 }` can never accidentally end up
remembering `{ col: 5, row: 9 }` from a later iteration of the same loop.
This is the identical guarantee that makes closures inside loops safe
anywhere in JavaScript — worth knowing by name, because the *lack* of it
is a real, classic bug (demonstrated in "What Breaks Without This" below).

**Walkthrough — `selectCell`, reading it in order.** `if
(selectedCoordinate) { ... }` runs only when something was already
selected — skipped entirely on the very first click, which is exactly why
`Coordinate | null` from Step 1 matters here concretely: this check *is*
type narrowing, the same idea lesson 01's `requireElement` used. Inside it,
`cellId(selectedCoordinate)` reconstructs the *previous* selection's DOM
id, and `.classList.remove('cell-selected')` clears its highlight before
anything else happens. `selectedCoordinate = coordinate;` then replaces the
whole variable with the brand-new object Step 3's click handler built —
never editing the old one's fields, exactly the discipline Step 2's
`readonly` now enforces. Finally, the newly selected cell's real element is
found and given the highlight class.

**SE lens — targeted updates instead of a full re-render.** Every render
function in this curriculum's companion [Video Notes](../video-notes/README.md)
project clears its entire container and rebuilds it from scratch on every
change. `selectCell` does the opposite on purpose: it touches exactly the
two cells actually affected — the old selection and the new one — and
nothing else. Both approaches are legitimate engineering choices, not one
correct and one wrong; a spreadsheet's sixty independently-addressable
cells, each with a real, stable DOM id since lesson 01, are specifically
well suited to targeted updates, since clicking one cell has no real reason
to touch the other fifty-nine.

`classList.remove(...)` and `classList.add(...)` are the same `classList`
API [Video Notes lesson 16](../video-notes/16-settings-and-themes.md)
used for its theme toggle — here, used to add and remove a single class
from two different elements directly, rather than toggling one class on
one fixed element.

## Connect the Pieces

```
script.ts    selectedCoordinate: Coordinate | null — the one variable
             describing what is currently selected, honestly allowed to
             be nothing
             selectCell() — the only place that variable ever changes,
             and the only place cell-selected is ever added or removed
```

Every cell created by lesson 01's `renderGrid()` now also wires up its own
click listener, using the exact `cellId()` function lesson 01 already
wrote — no new id-generation logic was needed anywhere in this lesson.

## What Breaks Without This

**Using `var` instead of `let` for the loop variables (temporarily change
`for (let col = ...)` to `for (var col = ...)` to see it):** `var` is
**function-scoped**, not block-scoped — every iteration of the loop shares
the *same* `col` and `row` variables, holding whichever values the loop
last finished with by the time any click actually happens. Every cell
becomes clickable, but clicking *any* of them selects the *same* last cell
— a real, classic JavaScript bug, reproduced here on purpose. Change it
back to `let` afterward.

**Without the `if (selectedCoordinate)` check in `selectCell`:** Delete it
temporarily and call `cellId(selectedCoordinate)` unconditionally instead.
`cellId` expects a real `Coordinate`, never `null` — Monaco immediately
shows a red squiggle under `selectedCoordinate`, refusing to let this
compile at all, because it can prove `selectedCoordinate` might genuinely
be `null` the very first time `selectCell` ever runs. This is worth
triggering on purpose: it is exactly what a type system catching a real
mistake *before* it becomes a runtime bug looks like, rather than the
plain JavaScript version of this same mistake, which would only surface
the first time a person actually clicked a cell.
