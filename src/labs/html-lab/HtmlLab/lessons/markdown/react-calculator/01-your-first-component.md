## Step 1 — Start a Blank Project and Add a Container

**The problem:** A brand-new HTML Lab project has no dedicated place for
React to render into, and no file that HTML Lab will treat as JSX.

Click **+ New** to start a blank project. Click the **HTML** tab and type:

```html
<div id="app"></div>
```

**Walkthrough.** This is the only HTML this entire project writes by hand,
ever. Everything else — the display, every button, the whole scientific
keypad — is going to be generated by React, from inside the `.tsx` file
you're about to create. `id="app"` gives this one empty `<div>` a name so
that code can find it later with `document.getElementById('app')`, the
exact same DOM lookup the TypeScript Spreadsheet project used for
`'header-row'` and `'spreadsheet-body'` in its own lesson 01.

**SE lens — why one div, and not more raw HTML.** A real-world React
project (built with Vite, Next.js, or Create React App) ships an
`index.html` containing exactly one empty container element and nothing
else meaningful inside `<body>` — React is handed that one element and told
"everything inside here is yours." This project follows that same
convention from lesson one, specifically so the boundary is never blurry:
anything inside `#app` is React's responsibility; nothing outside it will
ever exist in this project.

## Step 2 — Create Your First `.tsx` File

**The problem:** HTML Lab's JavaScript tab currently holds one plain file,
`script.js` — a `.js` file gets no TypeScript checking, and critically,
HTML Lab will not treat anything inside it as JSX, even if you type
JSX-shaped syntax into it.

Click the **JavaScript** tab. Rename `script.js` to `App.tsx`.

**Walkthrough — the four extensions HTML Lab actually treats
differently.** Monaco and the transpiler both decide what a file *is*
purely from its name's ending, exactly the same way `.ts` was the whole
signal in the TypeScript Spreadsheet project:

- **`.js`** — plain JavaScript. No type checking. No JSX.
- **`.ts`** — TypeScript. Full Monaco type checking. Still no JSX — writing
  `<div>` inside a `.ts` file is a syntax error, because `.ts` files use
  `<Type>value` as a completely different feature (an older casting syntax)
  that would collide with it.
- **`.jsx`** — plain JavaScript that is also allowed to contain JSX. No
  type checking.
- **`.tsx`** — both at once: full TypeScript checking *and* JSX allowed.
  This is what every file in this project will end in, because this
  project wants both things every single lesson.

**SE lens — what happens the instant a `.tsx` file exists, that you did
not do yourself.** The moment any file in this project ends in `.jsx` or
`.tsx`, HTML Lab automatically adds two `<script>` tags to whatever ▶
Preview generates, loading React and ReactDOM from a CDN (a server that
just hosts the finished, pre-built library file — no installation, no
`npm`, because this sandbox has no terminal to run `npm` in at all). This
is the same idea `npm install react` accomplishes in a real project —
making the `React` and `ReactDOM` names available to your code — just
solved a different way, because this environment doesn't have the tooling
a real project would use to bundle a downloaded package into your code.
Nothing about the *code you write* is any different either way.

## Step 3 — Write and Mount Your First Component

**The problem:** `App.tsx` exists, but it's still the old file's leftover
content (or empty) — nothing describes what should go inside `#app` yet.

Replace everything in `App.tsx` with:

```tsx
function requireElement(id: string): HTMLElement {
  const element = document.getElementById(id);
  if (!element) {
    throw new Error(`Expected an element with id "${id}"`);
  }
  return element;
}

function App() {
  return (
    <div className="calculator">
      <p>Hello, Calculator</p>
    </div>
  );
}

const container = requireElement('app');
ReactDOM.createRoot(container).render(<App />);
```

Click **▶ Preview**. A small box appears on the page containing the text
"Hello, Calculator."

**Walkthrough — `requireElement`, reused on purpose.** This is the exact
same function, unchanged, from lesson 01 of the TypeScript Spreadsheet
project: `document.getElementById` officially returns `HTMLElement | null`
— a union meaning "one of these two possibilities" — because the id you
ask for might not exist. `requireElement` checks once and throws a clear,
specific error immediately if nothing was found, so every line after it
can treat the result as a guaranteed real `HTMLElement`, never a possibly-
`null` one. There is no automatic way to carry a function from one HTML Lab
project to another, so it's typed again here, by hand — small enough that
retyping it is faster than explaining a workaround, and a useful reminder
of exactly why it exists.

**Walkthrough — your first JSX, read literally.** `<div className="calculator">`
inside a `.tsx` file looks like HTML, but it is not a string, and it is not
HTML — it's an expression, compiled by Babel into a plain JavaScript
function call, before your code ever reaches the browser. Written out by
hand, without JSX, the exact same component is:

```typescript
function App() {
  return React.createElement(
    'div',
    { className: 'calculator' },
    React.createElement('p', null, 'Hello, Calculator')
  );
}
```

`React.createElement(type, props, ...children)` takes three kinds of
argument: what to create (a tag name string, or another component
function), an object of that element's props (`className`, event handlers,
anything else — `null` if there are none), and then any number of
children. JSX exists purely so you never have to write nested calls like
that by hand — `<div className="calculator"><p>Hello, Calculator</p></div>`
says the same thing in a shape that actually looks like the HTML it will
become. Babel performs this exact conversion, mechanically, on every `.tsx`
file in this project, which is also *why* `React` has to be available as a
global name (Step 2's CDN script) even though this file never writes
`import React` anywhere — the compiled code calls `React.createElement`
directly, by name.

**Note — `className`, not `class`.** JSX uses `className` instead of HTML's
`class`, because `class` is already a reserved word in JavaScript (used to
define real classes — lesson 27 of this project uses one). This is the
first of several small naming differences between JSX and HTML you'll meet;
each is called out the first time it matters.

**CS lens — a component is a function that returns a description, not a
DOM element.** `App()` never once calls `document.createElement`. Calling
`App()` does not put anything on the page by itself — it returns a
plain JavaScript object tree (the result of those `React.createElement`
calls) describing *what should exist*. This is the core idea of
**declarative UI**: you describe the desired end state, and a separate
system — React itself — figures out the actual DOM operations needed to
make the real page match it. Contrast this directly with `renderGrid()`
from the TypeScript Spreadsheet project, which called
`document.createElement` and `.appendChild` itself, by hand, for every
single cell — that is **imperative** UI: a list of steps to perform, rather
than a description of an end state. Both projects build a real interface;
they represent it in opposite ways. Every lesson from here on is, in one
sense, an exploration of what declarative UI buys you that imperative UI
does not.

**Walkthrough — mounting.** `document.getElementById('app')` (wrapped in
`requireElement`) finds the one real DOM node this project committed to in
Step 1. `ReactDOM.createRoot(container)` creates what React 18 calls a
**root** — a connection point between one real DOM node and a React
component tree, capable of running React's newer concurrent rendering
features. (An older API, `ReactDOM.render(<App />, container)`, did the
same basic job in React 17 and earlier without a separate root object —
you may see it in older tutorials; `createRoot` is what every current
React project uses.) `.render(<App />)` then hands that root your
top-level component, and React takes it from there: calling `App()`,
walking the object tree it returns, and creating the real DOM nodes needed
to match it — the exact translation from "description" to "actual page"
the CS lens above named.

## Connect the Pieces

```
index.html   <div id="app"></div> — the one real element this project
             ever hand-writes; everything inside it belongs to React
App.tsx      requireElement() — reused, unchanged, from the TypeScript
             Spreadsheet project
             App() — the first component; describes one <div> and one <p>
             ReactDOM.createRoot(container).render(<App />) — the one line
             that connects the description to the real page
```

## What Breaks Without This

**Deleting `<div id="app"></div>` from the HTML tab, but leaving
`App.tsx` unchanged:** `requireElement('app')` finds nothing, and throws
`Expected an element with id "app"` — a clear, specific error, visible in
the browser console (press F12, click the **Console** tab — this is the
same panel every lesson from here on will ask you to check whenever
something doesn't look right). Without `requireElement`'s guard, this
would instead fail one line later, inside `ReactDOM.createRoot`, with a
much less specific error about receiving `null` where a real DOM element
was expected.

**Renaming `App.tsx` back to `App.jsx` (or `.js`):** With `.jsx`, this
lesson's code still works — `.jsx` also allows JSX, it just skips
TypeScript's checking of the `id: string` parameter and everything else.
With plain `.js`, ▶ Preview fails outright: the JSX syntax `<div
className="calculator">` is not valid JavaScript, and nothing renders.
